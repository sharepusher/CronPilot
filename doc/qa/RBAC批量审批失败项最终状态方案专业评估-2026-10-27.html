RBAC 批量审批失败项最终状态方案专业评估

日期：2026-10-27 · 结论：A，专业通过，建议按设计实施

1. 事实核验

已核对 app/rbac/services.py::approve_registration()：其嵌套 _reject_pending() 会设置 registration request 的 status='rejected' 并 commit()，但返回 {ok: False}。已核对 app/rbac/views.py::_batch_review_response() 和 _batch_failure_from_result()：现有 response 只含 success/failure 数量、id 与消息。已核对 registration_review.html::handleBatchResponse()：partial failure 硬编码“失败项保持原状态”。因此问题成立，置信度高；它是 P2 结果真值与操作可理解性缺陷，不是自动拒绝本身的安全缺陷。

2. 维度评估

维度评价依据
准确性A服务事务确实可在 ok=false 时持久化 rejected，现有 UI 全称断言可被真实路径反证。
专业性A将 requested-action outcome 与 persistence disposition 分离，符合命令处理与结果建模原则；避免把显示层消息作为协议。
合理性A-保留旧 success/failure/outcome 兼容语义，仅添加字段；服务层是唯一拥有事务真相的来源。
安全性Aunknown 默认不承诺未变化，并提示刷新核验，降低网络/内部异常后重复执行的风险。
可测试性A可对每个 disposition 同时断言 JSON 与数据库；计数守恒可作为稳定契约门禁。

3. 备选方案淘汰

方案评估结论
仅删除“保持原状态”不再直接撒谎，但结果仍不可判定，用户须逐条猜测。不采用
改为“请查看详情”止血可行，却把领域状态藏在中文描述中，API/页面无法可靠聚合。不采用
让前端匹配“自动拒绝”文案强耦合文案、难国际化，且无法覆盖异常状态。不采用
结构化 disposition + final_status事实同源、可扩展、可计数守恒、兼容旧字段。采用

4. 实施约束

  • auto_rejected 不计入 success_count；它表示请求“通过”失败但记录已被系统拒绝。
  • 所有 service failure 必须显式产生 disposition；View 不得根据 msg 猜测。不可判定的异常只能是 unknown。
  • 页面契约校验遇到未知枚举、计数不守恒或字段缺失必须 fail-closed，提示刷新核对。
  • 新增 JSON 字段须标记 ⚠️ API Breaking Change，并完成前后端契约、数据库结果和浏览器批量路径验证。

5. 放行条件

批准实施，但以 B0 红线测试先行：必须复现自动拒绝的 ok=false + rejected，并同时验证 unchanged 与 unknown 分支；再修改服务、View 和页面。实施完成后需按仓库规则输出含预防措施的修复复盘，复跑文档与 UI 门禁。
