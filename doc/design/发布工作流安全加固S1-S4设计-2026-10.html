发布工作流安全加固 S1–S4 设计

编号：Security Release S1–S4 · 状态：已确认并实施 · 日期：2026-10-27 · 适用范围：发布工作流、版本校验、发布资产完整性；无前端可见变更。

推荐决策：按 High → Medium 顺序实施四批安全加固：S1 凭据与权限隔离，S2 严格 tag 输入与 Release Notes fallback，S3 上传后资产完整性校验，S4 结构化发布状态元数据。每批独立测试、可回滚，不重建或修改历史 tag。

1. 问题

Security Review 发现发布工作流在同一 job 中同时执行 tagged commit 代码并持有 contents: write 与 checkout 持久化凭据；tag 输入和 Release Notes fallback 允许异常版本路径；上传后仅核验资产名称；语义门禁依赖单一自然语言短语。

2. 根因

  • 构建与发布权限没有按信任边界分离。
  • 版本号由 GitHub ref 直接流入 shell/文件名，缺少统一的严格 SemVer 断言。
  • 上传验证检查元数据名称，而非回读后的内容、摘要与来源 commit。
  • 发布就绪状态存在于 prose 中，没有声明式、可机器验证的来源。

3. 方案与优先级

批次实施内容安全目标不做
S1 High构建 checkout 设置 persist-credentials: false；构建 job 使用 contents: read；发布动作拆至最小权限 job/受保护 environment；第三方 Action 固定 commit SHA。降低 tagged commit 被执行时的 token 读取与仓库写入爆炸半径。不把不可信构建产物直接赋予写权限；不修改历史 tag。
S2 Medium新增共享 SemVer 校验函数，强制 ^v[0-9]+\.[0-9]+\.[0-9]+$；tag 工作流拒绝 malformed ref；tag 模式只允许精确版本章节，不回退 [Unreleased]。阻断异常 tag、路径注入和未发布草稿被包装为正式 Release。不改变本地预发布草稿的显式提取能力。
S3 Medium上传后用 gh release download 或等价 API 回读 tarball、checksum、build report；验证本地与远端 SHA-256、checksum 内容、build report 的 source_commit == GITHUB_SHA，并确认 Release 仍为预期 draft/version 后才 publish。保证最终公开资产是本次构建的内容，而不只是同名文件。不允许对已发布 Release 使用 --clobber 覆盖。
S4 Medium引入 release manifest 的显式 release_blockers、readiness 与 version 字段；tag 来源 commit 仅由构建后生成的 build report 记录和校验，不把自然语言正则宣称为完整语义安全。消除同义文案、语言切换和标点差异造成的 false negative，同时避免源码清单对自身 commit SHA 的自引用。不做通用 NLP；自然语言仍用于面向用户的说明。

4. 范围

包含：.github/workflows/release-asset.yml、scripts/check_version_consistency.py、scripts/extract_release_notes.py、发布资产校验脚本、专项测试、必要的 Release Notes/manifest 文档和 CI 权限声明。

不包含：业务代码、数据库、已发布 tag/Release 删除或重建、GitHub 组织级分支保护配置（需管理员另行配置）。

5. 分批与回滚

  1. S1：先静态检查 workflow 与权限，确认构建 job 不再持有写 token；失败可回滚 workflow commit。
  2. S2：先补 malformed tag、fallback 和 shell-safe version 测试，再接入 workflow；失败只阻止新 tag。
  3. S3：在 draft Release 测试上传/回读，确认不发布错误资产；失败保留 draft，不删除资产。
  4. S4：新增 manifest 的版本/就绪/blocker 状态门禁；tag commit 只由 build report 在构建后绑定。失败保留 draft，不改变业务。

6. 验收

  • S1：workflow 静态测试确认 persist-credentials: false、构建 job 无 contents: write、publish job 权限最小且 Actions 使用 SHA。
  • S2：恶意/异常 tag、shell 特殊字符、缺少精确版本节和仅有 [Unreleased] 均在构建前失败；正常 SemVer 正常通过。
  • S3：篡改远端 tarball、checksum、build report 或 source commit 的模拟测试均失败；未篡改资产通过。
  • S4：release_blockers 非空、readiness 非 ready/published、manifest 版本不匹配或出现遗留 source_commit 均失败；正常 manifest 通过，build report 继续校验 tag commit。
  • 全量相关测试、Ruff、文档同步、链接和版本一致性门禁通过。

7. 风险

  • 拆 job 可能需要 GitHub artifact 传递和受保护 environment 配置；没有组织级权限时只能先落地构建只读与回读校验。
  • 固定 Action SHA 增加维护成本；应记录 Action 名称、SHA 和升级理由。
  • manifest 引入新事实源，若同步失败会造成发布阻断；必须由 tag workflow 校验并在发布包中记录。

8. 实施记录

  • S1：构建与发布拆分为独立 job；构建 job 只读、checkout 不持久化凭据；Action 固定 commit SHA；发布 job 使用受保护 release environment。
  • S2：tag 严格 SemVer；tag 模式禁止 Release Notes 回退 [Unreleased]；版本一致性脚本支持显式 tag 校验。
  • S3：上传后回读三项资产，比较归档/checksum/build report，校验 checksum 和 source_commit == GITHUB_SHA 后才解除 draft。
  • S4：新增 release/release-manifest.json，严格只允许版本、readiness、空 blocker 三字段；来源 SHA 留在构建后生成的 build report，消除 manifest 自引用。

9. 验收结果

  • Security Release 相关测试 16/16 通过，Ruff 通过。
  • 版本一致性（含显式 v4.1.1 tag）通过；文档完整性与链接门禁通过。
  • 历史 v4.1.1 tag 重新构建 270 文件、641342 bytes，发布包校验通过；另在临时仓库创建新提交/新 v4.1.2 tag 并验证 manifest 状态门禁通过。
  • 未在本地伪造 GitHub Actions/远端 Release 的实际执行结果；需在下一次真实 tag workflow 中核验远端受保护环境与回读流程。
