1. 问题

列表「结果」列：在「失败」/「异常」后追加 · 4xx / · 5xx / · 关键词 / · 连接 / · URL拦截 子标签。 但「返回内容」列已展示 HTTP 状态码与响应摘要，fail / error 主标签（不同颜色+不同文案）已完成语义分类，子标签是冗余叠加。视觉上破坏了状态标签的简洁性。

详情页「失败原因」板块：混杂原始枚举码（http_4xx）、英文 label（Target:、Timeout:）、健康计数，而这些信息已分布在「请求」「元数据」板块中，是重复且排版混乱的堆叠。同时 meta 行显示的是原始枚举码而非可读文案。

2. 根因

2026-08-27 「结果列细分」设计的核心目标是：区分筛选按钮「仅失败」与「仅异常」对应的不同状态。该目标已通过拆分 fail / error 为独立分支（红色「失败」vs 橙色「异常」）实现。子标签当初用于进一步细分原因，但其承载的信息与「返回内容」列完全重叠（HTTP 码可见），实际沦为多余注脚。

详情页「失败原因」板块是早期将多处上下文信息聚合为「诊断摘要」的尝试。各信息源（URL、超时阈值、健康计数）已有专属板块后，聚合板块变为纯冗余，且因未做国际化/格式统一导致中英混排、原始枚举码裸露。

深层根因：子标签和聚合板块本质上违反了信息不重复原则（DRY for UI）——同一信息（HTTP 状态码、失败原因）在列表页的两个列和详情页的两个板块中各展示一次。早期设计缺乏「信息已有展示位置时不重复」的 Review checklist，导致在追加细分功能时未检查信息是否已在其他位置可见。

2b. 行业参考

产品执行日志状态列详情页失败信息与本设计的对照
Grafana Alerting 单一状态标签（Firing / Normal / Pending），无子标签 Alert Rule Detail 展示完整条件表达式和评估结果，无冗余摘要板块 佐证：状态列只做语义分类，详细原因交给详情页的专属板块
Datadog Events 彩色 dot + 状态文案（OK / Warn / Alert），无附加子标签 Event Detail 分板块展示（Monitor 配置、触发条件、相关 Metrics），板块间无信息重叠 佐证：状态列保持简洁，详情页各板块职责分明不重复
GitHub Actions 单一 icon + 状态文案（✓ / ✗ / ⊘），日志链接在行尾 Job Detail 按 Step 展开日志，无聚合诊断摘要 佐证：列表层面极简，诊断完全交给下钻详情
Apache Airflow 彩色圆点 + 状态名（success / failed / running），无附加信息 Task Instance Detail 按类别分 Tab（Log / XCom / Details），信息分层不重叠 佐证：调度领域标杆，状态列不承载诊断信息

行业共识：在可观测性 / 调度 / CI 工具中，执行记录的状态列几乎无一例外地遵循「单一语义标签 + 颜色区分」范式。诊断级别的信息（错误码、失败原因、上下文）一律由详情页或展开行承载。CronPilot 的子标签设计偏离了这一行业惯例。

方案 A（推荐）：双处精简

A1 — 列表结果列：移除子标签

保留 fail / error / timeout 各自独立分支（颜色+文案区分已足够），仅移除 .el-log-sub span：

A2 — 详情页：移除冗余板块，改善 fail_reason 可读性

取舍判断：方案 B 的唯一优势场景是「返回内容」列不可见时——但 CronPilot 执行记录列表中「返回内容」为固定列（无列隐藏功能），且列宽足以展示 HTTP 码前缀。因此 B 的优势场景在当前产品中不存在。加之行业惯例（§2b）一致支持状态列极简化，不推荐 B。

8. 风险

  • 子标签移除后，列表层面无法一眼区分 4xx / 5xx / 关键词；但该信息已在「返回内容」列和详情页可见，可接受。
  • fail_reason 为空的旧记录：枚举映射 fallback 到原始值，不影响展示。
  • 无后端变更、无数据迁移。回滚仅需恢复两处模板改动 + 一条 CSS 规则恢复。
  • 列表扫描效率：移除子标签后，运维人员无法在结果列一眼区分「HTTP 4xx 失败」与「关键词匹配失败」——须查看同行「返回内容」列。缓解措施：① CronPilot 已提供筛选按钮（仅失败 / 仅异常 / 仅超时）可快速过滤目标记录，降低逐行扫描需求；② 「返回内容」列在列表中始终可见且位于结果列左侧，HTTP 码（404 / 502）或关键错误文案在前 10 字符即可辨识。综合评估：扫描效率下降可控，不影响核心诊断工作流。
  • API 消费者兼容：本次仅修改模板 HTML 渲染层，不影响 API 返回的 status / fail_reason 字段。如有外部脚本解析列表页 HTML（非推荐用法），子标签 DOM 移除可能影响解析——但 CronPilot 有标准 API 端点，应引导使用 API 而非 HTML 解析。
  • 「失败原因」板块中的连续失败计数 / 时间戳（health.consecutive_failures / last_fail_at / last_success_at）：该信息属于任务级别健康趋势（非单次执行诊断），语义上更适合放在任务详情页（task_detail_v2）的 job_health 板块中展示。本次移除后如需补回，应作为任务详情页健康面板的独立优化跟进，不在本批次范围内。
