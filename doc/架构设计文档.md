## 1. 文档说明

**目的：**为开发、运维、集成方提供 CronPilot 的结构性视图，说明模块边界、运行时拓扑、数据流向及扩展点。

**读者：**后端工程师、SRE、架构师、需对接回调的业务研发。

**范围：**应用层（`app/`）、数据层（`datas/`）、配置与容器化部署；不包含业务回调服务内部实现。

| 术语 | 含义 |
| --- | --- |
| 调度 Job | APScheduler 中 id 为 `cron_{cron_infos.id}` 的持久化任务 |
| 回调 | 触发时对 `req_url` 发起的 HTTP GET |
| 双库 | `cron_db_url`（JobStore）与 `cron_job_log_db_url`（业务 ORM） |
| 体验版 | `is_dev=1`，禁用秒级字段 |

## 2. 架构目标与约束

### 2.1 设计目标

| 目标 | 架构手段 | 源码体现 |
| --- | --- | --- |
| Crontab 语义兼容 | 字段级 Cron + APScheduler cron trigger | `views.py` 校验 + `scheduler.add_job` |
| 可视化运维 | SSR Web + Session 鉴权 | `main/views.py`、templates |
| 自动化集成 | REST API + access\_token | `api/views.py` |
| 水平扩展 | Redis 任务互斥 + 文件锁拉取 Job | `single_task`、`CuBackgroundScheduler` |
| 故障可感知 | 关键词检测 + 三通道推送 | `crons.cron_do`、`send_text` |
| 低部署成本 | Docker + Supervisor + 默认 SQLite | Dockerfile、docker-compose |

### 2.2 约束条件

- 回调仅支持 **GET**，超时固定 **120s**（`requests.get(..., timeout=120)`）
- 集群模式要求 MySQL JobStore + Redis，SQLite 仅适合单机
- 每 Gunicorn worker 独立启动完整 Scheduler（非集中式 Master）
- Web 鉴权为单密码 Session，无 RBAC

系统在生态中的角色是 **调度编排中枢（Orchestrator）**：不执行业务逻辑，只负责按时间表触发 HTTP 调用并审计结果。

## 4. 容器架构（Level 2）

```
┌──────────────────────────────── Docker Host / 物理机 ────────────────────────────────┐
│  Supervisor (nodaemon)                                                                │
│    └── docker_start.sh                                                                │
│          ├── flask db migrate / upgrade  (首次初始化 migrations)                      │
│          └── gunicorn -c docker_gun.py manage:app                                     │
│                ├── Worker 1 (gevent) ──► Flask App + APScheduler Instance             │
│                ├── Worker 2 ...                                                       │
│                └── Worker N (docker: 4, gun.py本地: 2)                                │
│                                                                                       │
│  每个 Worker 进程内：                                                                  │
│  ┌─────────────────────────────────────────────────────────────────────────────────┐ │
│  │  WSGI Layer: Flask Application (create_app)                                      │ │
│  │    ├── Blueprint: main  (/, Web UI)                                              │ │
│  │    ├── Blueprint: api   (/api, JSON API)                                         │ │
│  │    ├── SQLAlchemy ORM  → cron_job_log_db                                         │ │
│  │    └── Flask-APScheduler → CuBackgroundScheduler                                 │ │
│  │              ├── SQLAlchemyJobStore → cron_db (apscheduler_jobs)               │ │
│  │              ├── ThreadPoolExecutor (max_workers=30)                             │ │
│  │              └── portalocker(scheduler.lock) 进程间互斥拉取 due jobs             │ │
│  └─────────────────────────────────────────────────────────────────────────────────┘ │
│                                                                                       │
│  文件系统：datas/logs/{info,error,server}.log  |  scheduler.lock  |  caches/         │
└───────────────────────────────────────────────────────────────────────────────────────┘
```

### 4.1 运行时双进程模型说明

**重要：**Gunicorn 多 worker 意味着同一主机存在 **N 个 APScheduler 实例**。它们通过 `scheduler.lock`（portalocker 非阻塞排他锁）保证**同一时刻仅一个进程**执行 `_process_jobs()` 拉取到期任务；任务执行函数 `cron_do` 在集群模式下再由 Redis `@single_task` 保证跨节点互斥。

### 5.2 Web 管理端调用链（与 APScheduler 的关系）

**结论：**管理页面（任务添加/编辑、执行时间、启停、删除等）**不会**由浏览器直接调用 APScheduler 或 Flask-APScheduler 接口。前端仅通过 HTML 表单 / Ajax 请求 Flask 的 `main` 蓝图路由；服务端在 `cron_service` 或 `main/views.py` 内完成校验、写 `cron_infos`，再调用 `scheduler.add_job` / `pause_job` / `resume_job` / `remove_job`。

```
┌─────────────── 浏览器（jQuery + common.js）────────────────────────────┐
│  cron_add.html / cron_edit.html  →  js-ajax-form  →  POST Flask 路由    │
│  cron_list.html  →  js-ajax-dialog-btn / js-ajax-delete  →  GET 路由     │
│  ❌ 无 apscheduler SDK；❌ 不请求 /api/cron（管理 UI 走 main，不走 api）   │
└───────────────────────────────┬────────────────────────────────────────┘
                                ▼
┌─────────────── Flask 表现层（app/main/views.py）────────────────────────┐
│  /cron_add  /cron_edit  /update_status  /cron_del  /cron_list  …         │
└───────────────────────────────┬────────────────────────────────────────┘
                                ▼
┌─────────────── 服务层（app/services/）──────────────────────────────────┐
│  cron_validator.validate_cron_form  — Web/API 共用校验（执行时间字段等）   │
│  cron_service.add_cron_web / edit_cron_web / create_cron / update_cron   │
│       → INSERT/UPDATE cron_infos  → register_cron_job()                  │
└───────────────────────────────┬────────────────────────────────────────┘
                                ▼
┌─────────────── 调度层（进程内 Flask-APScheduler，非 HTTP）────────────────┐
│  scheduler.add_job('cron_{id}', cron_do, trigger=date|cron, …)           │
│  scheduler.pause_job / resume_job / remove_job                           │
│  持久化 → apscheduler_jobs（SQLAlchemyJobStore）                          │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 管理页操作对照表

| 管理页操作 | 前端请求 | Flask 路由 | 服务/逻辑 | APScheduler（服务端） |
| --- | --- | --- | --- | --- |
| 添加任务（含执行时间） | `POST` 表单 Ajax | `/cron_add` | `add_cron_web` → `create_cron` | `add_job` |
| 编辑任务 / 改时间 | `POST` 表单 Ajax | `/cron_edit` | `edit_cron_web` → `update_cron` | `add_job(replace_existing)` |
| 启动 / 停止 | `GET` Ajax 对话框 | `/update_status` | `main/views.py` 直接 | `resume_job` / `pause_job` |
| 删除 / 批量删 | `GET` / `POST` | `/cron_del`、`/cron_batch_del` | ORM 删除 + `job_log_service` | `remove_job` |
| 任务列表 / 执行记录 | `GET` 页面 | `/cron_list`、`/job_log_*` | ORM 分页查询 | 无（只读 DB） |

**操作审计（现状）：**上表管理写操作**不落库操作记录**，仅更新 `cron_infos` 当前态。谁、何时、改了什么**不可追溯**。任务**执行**记录见 `job_log`（到点回调结果），与配置变更审计不同。P1 规划见 [OPT-P1-09](产品优化需求-借鉴Plombery.html#opt-p1-09)。

外部系统集成走 **REST API**（`/api/cron`、`/api/cron/status`），同样经 `cron_service` 写库后由服务端注册调度，**亦非**直连 APScheduler。详见 [技术方案与前端设计](技术方案与前端设计.html) 第 6 节 API 规范。

### 6.4 管理操作审计（P1 规划 · OPT-P1-09）

**现状：**无 `operation_log` 表；添加/编辑/启停/删除仅改 `cron_infos` 与 APScheduler，不写审计行。执行侧仅有 `job_log`（回调 HTTP 结果）与可选 `job_log_items`（业务 `add_log` 进度）。

| 记录类型 | 表 | 记录什么 | 现状 |
| --- | --- | --- | --- |
| 任务执行 | `job_log` | 到点 GET 回调的响应、耗时、UUID | ✅ 已有，管理端「任务执行记录」 |
| 执行进度 | `job_log_items` | 业务 `POST /api/cron/add_log` | ✅ 已有 |
| 配置变更审计 | `operation_log`（规划） | 添加/编辑/删任务、启停、API 改配置 | ❌ 未实现 |
| 服务端异常 | `datas/logs/error.log` | 未捕获异常栈 | ✅ 有，非结构化、非按任务检索 |

#### 表结构草案（`cron_job_log_db`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER PK | 自增 |
| `create_time` | VARCHAR(25) | 与 `job_log` 一致，本地时间字符串 |
| `action` | VARCHAR(32) | `create_cron` `update_cron` `delete_cron` `toggle_status` `batch_delete_cron` `delete_job_log` … |
| `channel` | VARCHAR(8) | `web` | `api` | `system` |
| **操作人（预留多用户 / RBAC，P1 建列、P2 接账号体系）** | | |
| `operator_type` | VARCHAR(16) | `user` | `api_client` | `system` | `legacy_admin`（单密码过渡期） |
| `operator_id` | VARCHAR(64) | 稳定主体 ID：未来 `users.id`；API 为 client/token 哈希；legacy 为 session 哈希；system 为空 |
| `operator_name` | VARCHAR(120) | 展示名快照：用户名、邮箱、`API集成`、`系统`、`管理员`（删用户后仍可读） |
| `operator_roles_json` | TEXT | 操作时角色快照 JSON 数组，如 `["admin"]`、`["scheduler_admin","viewer"]` |
| `operator_permissions_json` | TEXT | 操作时权限码快照，如 `["cron:read","cron:write","cron:delete"]`；全权限可 `["*"]` |
| **请求与目标** | | |
| `client_ip` | VARCHAR(45) | 可选，取自 `X-Forwarded-For` / `remote_addr` |
| `target_type` | VARCHAR(16) | `cron` | `job_log` |
| `target_id` | INTEGER | `cron_infos.id` 或 `job_log.id`；删除后仍可凭 `task_name` 检索 |
| `task_name` | VARCHAR(120) | 冗余，便于删任务后查询 |
| `detail_json` | TEXT | 变更摘要 JSON，如 `{"hour":{"old":"9","new":"10"}}` |
| `result` | VARCHAR(8) | `ok` | `fail` |
| `error_msg` | VARCHAR(255) | 失败时简短原因 |

#### 写入点（服务层统一）

```
app/services/operation_log_service.record_operation(...)
  ↑ 由 cron_service / main/views / api/views 在 commit 成功后调用
  覆盖：create_cron · update_cron · delete · toggle_status · API upsert/status
```

#### 管理页「操作记录」

- 路由：`GET /operation_log_list`（需 `@login_required`）
- 筛选：任务名、`action`、**操作人**、**角色**、时间范围、`channel`
- 列表列：时间、操作、**操作人**、**角色**、任务名、渠道、结果、详情（展开 `detail_json` / 权限快照）
- 导航：与「任务执行记录」并列，勿与 `job_log` 混为一页
- 保留：配置项 `operation_log_counts`，超限按 id 删最旧（同 `job_log_counts`）

### 6.5 管理操作审计详细设计（OPT-P1-09）

#### 6.5.1 设计目标与边界

| 要记录 | 不记录 |
| --- | --- |
| 任务配置的增删改、启停（Web + API） | 到点 HTTP 回调执行（已有 `job_log`） |
| 操作时间、渠道、结果、字段级 diff | 登录成功/失败（首批可不做，避免噪音） |
| **操作人**、**角色与权限快照**（操作时态） | 只读查询（列表、看执行记录） |
| 删任务后的历史（靠冗余 `task_name`） | — |

#### 6.5.2 时序：写入时机

```
Browser/API     views/cron_service      DB                 operation_log_service
     │                  │                   │                         │
     │──写任务请求──────►│──validate────────►│                         │
     │                  │──INSERT/UPDATE───►│ cron_infos              │
     │                  │──scheduler.*──────►│ apscheduler_jobs        │
     │                  │──commit──────────►│                         │
     │                  │──record_operation─┼────────────────────────►│ INSERT
     │◄──响应───────────│                   │                         │
     │                  │  ※ 审计失败仅打 error.log，不回滚业务事务      │
```

#### 6.5.4 detail\_json 约定

| action | detail\_json 示例 |
| --- | --- |
| `create_cron` | `{"task_name":"daily","hour":"9","minute":"0","req_url":"https://..."}` |
| `update_cron` | `{"hour":{"old":"9","new":"10"},"req_url":{"old":"...","new":"..."}}` |
| `toggle_status` | `{"status":{"old":0,"new":1}}` |
| `delete_cron` | `{"snapshot":{"task_name":"...","hour":"9",...}}` 删除前最后一屏配置 |
| `batch_delete_cron` | `{"ids":[1,2,3],"task_names":["a","b","c"]}` |

#### 6.5.5 操作人、角色与权限快照

**原则：**审计行保存**操作当时**的主体与授权态，不存 live 外键到当前用户表（用户删改角色后历史仍可读）。P2 接入 `users` / RBAC 后，`operator_id` 对齐用户主键即可。

| 来源 | channel | operator\_type | operator\_id / name | roles / permissions（快照） |
| --- | --- | --- | --- | --- |
| Web Session（单密码过渡期） | `web` | `legacy_admin` | id=session 哈希；name=`管理员` 或 conf `admin_display_name` | `["admin"]` / `["*"]` |

#### 权限码草案（与 P2 RBAC 对齐，P1 可先落常量）

| permission | 含义 | 典型角色 |
| --- | --- | --- |

### 6.6 P2 多用户与 RBAC 详细设计（OPT-P2-10）

在 P1 `operation_log` 已预留 `operator_*` 列的前提下，P2 落地账号体系与权限校验，使「操作人 + 角色」从过渡期 `legacy_admin` 升级为真实用户/API 主体。

#### 6.6.1 设计目标

| 目标 | 说明 |
| --- | --- |
| 多用户 | 本地账号和/或 OAuth（[OPT-P2-07](产品优化需求-借鉴Plombery.html#opt-p2-07)）统一落到 `users` |
| RBAC | 角色 → 权限码；路由与写操作 `@require_permission` |
| 可审计 | `resolve_operator_from_request()` 从当前用户展开 roles/permissions 写入快照 |
| 可迁移 | `auth_mode=legacy` 与 `rbac` 共存一段时间 |

#### 6.6.2 数据模型（`cron_job_log_db`）

| 表 | 字段（要点） | 说明 |
| --- | --- | --- |
| `users` | `id` PK · `username` UNIQUE · `email` UNIQUE nullable · `password_hash` nullable · `display_name` · `status` 1=启用 0=禁用 · `auth_source` local/oauth\_\* · `oauth_sub` · `last_login_at` · `created_at` | OAuth 用户可无本地密码 |
| `roles` | `id` PK · `code` UNIQUE · `name` · `description` · `is_system` 内置角色不可删 | 种子：admin / scheduler\_admin / viewer / auditor |
| `user_roles` | `user_id` + `role_id` PK · `granted_at` · `granted_by` nullable | 多角色并集授权 |
| `role_permissions` | `role_id` + `permission_code` PK | 权限码字符串，见 §6.5.5 |
| `api_clients` | `id` PK · `name` · `token_hash` UNIQUE · `status` · `permissions_json` TEXT · `created_at` | 可选；多 API 集成方时替代单一 `api_access_token` |

```
┌─────────┐     ┌────────────┐     ┌───────┐     ┌──────────────────┐
│  users  │────►│ user_roles │────►│ roles │────►│ role_permissions │
└────┬────┘     └────────────┘     └───────┘     │ permission_code  │
     │                                              └──────────────────┘
     │  Session user_id / OAuth 绑定 oauth_sub
     ▼
┌──────────────┐          ┌─────────────────┐
│ operation_log│◄────────│ api_clients      │  token 校验 → operator_id
│ operator_*   │          │ (可选多客户端)    │
└──────────────┘          └─────────────────┘
```

#### 6.6.3 内置角色与权限矩阵（种子数据）

| role.code | 名称 | permissions |
| --- | --- | --- |
| `admin` | 管理员 | `*`（全部） |
| `scheduler_admin` | 调度员 | `cron:read` `cron:write` `cron:toggle` |
| `viewer` | 只读 | `cron:read` |
| `auditor` | 审计员 | `cron:read` `operation_log:read` |

权限展开：`user.permissions = ⋃ role_permissions`；含 `*` 则通过所有校验。

#### 6.6.4 鉴权与会话

```
conf.ini auth_mode=legacy | rbac

legacy（默认，兼容现状）
  check_pass → Session[authenticated]=1
  OperatorContext(legacy_admin, permissions=["*"])

rbac
  check_pass / OAuth callback → Session[user_id]=N
  加载 users + user_roles → g.current_user, g.permissions
  @login_required → 已登录
  @require_permission("cron:write") → 403 + 可选记 operation_log result=fail
```

装饰器落点：`main/views` 写操作、`operation_log_list` 需 `operation_log:read`；`api/views` 校验 token 后映射 `api_clients` 或全局 API 角色。

#### 6.6.5 OperatorContext 解析（RBAC 模式）

| 场景 | operator\_type | operator\_id | operator\_name | roles / permissions |
| --- | --- | --- | --- | --- |
| Web 已登录用户 | `user` | `str(users.id)` | `display_name` 或 username | 当前并集快照 JSON |
| API client | `api_client` | `str(api_clients.id)` | `api_clients.name` | client 配置或绑定角色 |
| 系统任务 | `system` | 空 | `系统` | `["system"]` / `["*"]` |

#### 6.6.6 从单密码迁移

1. 配置 `auth_mode=rbac`，执行迁移脚本 `scripts/migrate_legacy_admin_user.py`（规划）。
2. 创建用户 `admin`，`password_hash` 复用现有 `login_pwd`（pbkdf2 已有则直接拷贝）。
3. 赋予 `admin` 角色；保留 `auth_mode=legacy` 可回退。
4. 历史 `operation_log` 中 `legacy_admin` 行保留，新行为 `user`。

#### 6.6.7 管理页（仅 admin）

| 路由 | 权限 | 功能 |
| --- | --- | --- |
| `/users_list` | `user:read` 或 admin | 用户列表、启用/禁用 |
| `/user_edit` | `user:write` | 创建用户、分配角色（checkbox roles） |
| `/api_clients_list` | `api_client:write` | 多 API 令牌管理（可选） |

扩展权限码（P2）：`user:read` `user:write` `api_client:write` — 仅 `admin` 角色默认拥有。

#### 6.6.8 与 OAuth（OPT-P2-07）关系

- OAuth 回调：按 `oauth_sub` 查找或自动创建 `users`（`auth_source=oauth_google` 等）。
- 首次 OAuth 登录默认角色 `viewer`，由 admin 在「用户管理」提权。
- Session 仍用 `user_id`；与本地密码用户同一套 RBAC。

#### 6.6.9 验收标准

- `viewer` 无法访问 `/cron_add`（403）。
- `scheduler_admin` 可改任务但不可删任务（无 `cron:delete`）。
- `auditor` 可看操作记录，不可改任务。
- 操作审计行 `operator_id` 等于 `users.id`，roles/permissions 与操作时一致。
- `auth_mode=legacy` 升级后旧部署一键迁移 admin 用户。

### 8.1 两层互斥的设计 rationale

| 层级 | 机制 | 解决的问题 |
| --- | --- | --- |
| L1 进程间 | portalocker + scheduler.lock | 同机多 Gunicorn worker 重复 poll due jobs |

### 15.4 权限求值算法

```
# permission_service.py（伪代码）
def expand_permissions(user_id) -> set[str]:
    if user_has_role(user_id, "admin"):  # 可选：admin 角色内置 *
        return {"*"}
    codes = set()
    for role in get_user_roles(user_id):
        codes |= get_role_permissions(role.id)
    return codes

def has_permission(perms: set[str], required: str) -> bool:
    return "*" in perms or required in perms
```

多角色取**并集**；禁用用户（`status=0`）在 `session_auth` 层直接拒绝，权限集为空。

```
Client           api_token_auth      permission_service    cron_service

  │──POST /api/cron───►│ validate token       │                    │
  │                    │→ ApiClient or legacy │                    │
  │                    │──expand perms───────►│                    │
  │                    │                      │──upsert_cron──────►│
  │                    │                      │ operator=api_client│
```

#### 15.5.3 OAuth 登录（与 OPT-P2-07）

```
IdP → /oauth/callback → find users by oauth_sub
  → 不存在则 insert users + user_roles(viewer)
  → Session[user_id]=id → redirect /cron_list
```

### 15.6 Session 与请求上下文

| 键 / 对象 | legacy | rbac |
| --- | --- | --- |
| `session["authenticated"]` | 1 | 弃用或冗余 |
| `session["user_id"]` | — | 整数 PK |
| `g.current_user` | — | `User` ORM 或 namedtuple |
| `g.permissions` | `{"*"}` | `set[str]` 请求内缓存 |
| `g.api_client` | — | API 请求时可选 |

### 15.7 路由 → 权限映射（管理端）

| 路由 | 方法 | permission |
| --- | --- | --- |
| `/cron_list`、`/job_log_*`（读） | GET | `cron:read` |
| `/cron_add` | GET/POST | `cron:read` / `cron:write` |
| `/cron_edit` | GET/POST | `cron:read` / `cron:write` |
| `/update_status` | GET | `cron:toggle` |
| `/cron_del`、`/cron_batch_del` | GET/POST | `cron:delete` |
| `/job_log_delete` 等 | — | `job_log:delete` |
| `/operation_log_list` | GET | `operation_log:read` |
| `/users_list`、`/user_edit` | — | `user:read` / `user:write` |
| `/api_doc` | GET | `cron:read` |

API：`/api/cron`、`/api/cron/status` 需 `cron:write` / `cron:toggle`（或 client 级 permissions\_json）；`/api/cron/add_log` 仍为业务回调通道，保持 token 校验不变。

### 15.8 DDL 草案（MySQL / SQLite 通用）

```
CREATE TABLE users (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  username VARCHAR(64) NOT NULL UNIQUE,
  email VARCHAR(120) UNIQUE,
  password_hash VARCHAR(255),
  display_name VARCHAR(120) NOT NULL DEFAULT '',
  status SMALLINT NOT NULL DEFAULT 1,
  auth_source VARCHAR(32) NOT NULL DEFAULT 'local',
  oauth_sub VARCHAR(128),
  last_login_at VARCHAR(25) DEFAULT '',
  created_at VARCHAR(25) NOT NULL,
  updated_at VARCHAR(25) NOT NULL
);
CREATE UNIQUE INDEX uq_users_oauth ON users(auth_source, oauth_sub);

CREATE TABLE roles (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  code VARCHAR(32) NOT NULL UNIQUE,
  name VARCHAR(64) NOT NULL,
  description VARCHAR(255) DEFAULT '',
  is_system SMALLINT NOT NULL DEFAULT 0
);

CREATE TABLE user_roles (
  user_id INTEGER NOT NULL,
  role_id INTEGER NOT NULL,
  granted_at VARCHAR(25) NOT NULL,
  granted_by INTEGER,
  PRIMARY KEY (user_id, role_id)
);

CREATE TABLE role_permissions (
  role_id INTEGER NOT NULL,
  permission_code VARCHAR(64) NOT NULL,
  PRIMARY KEY (role_id, permission_code)
);

CREATE TABLE api_clients (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name VARCHAR(120) NOT NULL,
  token_hash VARCHAR(64) NOT NULL UNIQUE,
  status SMALLINT NOT NULL DEFAULT 1,
  permissions_json TEXT NOT NULL DEFAULT '[]',
  created_at VARCHAR(25) NOT NULL
);
```

### 15.9 与 operation\_log 集成

```
resolve_operator_from_request()
  ├─ Web + rbac  → user + expand_permissions → OperatorContext 快照 JSON
  ├─ Web + legacy → legacy_admin
  ├─ API         → api_client + permissions_json
  └─ system      → system

record_operation(..., operator=ctx)  # commit 业务后调用，见 §6.5.2
```

权限拒绝时（可选）：`record_operation(action=..., result=fail, error_msg="forbidden")`，需防刷接口限流。

### 15.10 配置项（conf.ini 规划）

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `auth_mode` | `legacy` | `legacy` | `rbac` |
| `admin_display_name` | 管理员 | legacy 模式 operation\_log 展示名 |
| `session_lifetime_hours` | 24 | Session 过期 |
| `oauth_enabled` | 0 | OPT-P2-07 |
| `rbac_default_role` | viewer | OAuth 首次登录默认角色 |

### 15.11 安全与运维约束

- **密码**：复用 P0 `pbkdf2`；禁止日志打印 token / 密码。
- **Session**：生产 `SECRET_KEY` 独立配置；HTTPS 反代时 `Secure` cookie。
- **API token**：库内仅存 `sha256(token)`；展示时仅一次明文。
- **提权**：仅 `user:write` 可改角色；禁止自我删除唯一 admin（业务规则）。
- **缓存**：`g.permissions` 仅请求内有效；改角色后下次请求生效。

### 15.12 ADR-06：选用应用内 RBAC 而非外置 IAM

| 决策 | 理由 | 代价 |
| --- | --- | --- |
| 内置 roles + permission\_code | 轻量部署、SQLite 友好、与 operation\_log 快照自然契合 | 大型企业需再对接 SSO |
| 权限快照写入审计 | 合规可追溯「当时有何权限」 | 行体积略增 |
| legacy 与 rbac 双模式 | 平滑升级现有单密码用户 | 分支测试矩阵增大 |

### 15.13 测试策略

| 层级 | 用例 |
| --- | --- |
| 单元 | `has_permission`、`expand_permissions` 多角色并集、`*` 短路 |
| 单元 | `build_cron_diff`、`OperatorContext` 序列化 |
| 集成 | viewer POST `/cron_add` → 403；admin → 200 + operation\_log |
| 集成 | API client 仅 `cron:write` 不可 `cron:delete` |
| 迁移 | `auth_mode` legacy→rbac 后原密码可登录 `admin` |

## 12. 架构决策记录（ADR）

| ID | 决策 | 理由 | 代价 |
| --- | --- | --- | --- |
| ADR-01 | 选用 APScheduler 而非 Celery Beat | 轻量、内嵌 Flask、Crontab 语义直接 | 多 worker 需自研锁 |
| ADR-02 | HTTP GET 回调而非 Agent 拉取 | 集成简单，防火墙友好 | 无请求体、幂等需业务保证 |
| ADR-03 | 双数据库 URL | JobStore 与业务 schema 解耦 | 运维需维护两套连接 |
| ADR-04 | SSR 管理台而非 SPA | 2019 前后主流、部署简单 | 前端体验与可维护性弱 |
| ADR-05 | portalocker + Redis 双锁 | 渐进式支持集群 | 语义复杂，调试难度大 |
| ADR-06 | 应用内 RBAC + 审计权限快照 | 轻量部署、与 operation\_log 契合 | 大企业需 SSO；见 [§15](#rbac-arch) |

## 13. 与 Plombery 架构对照

对照基准：Plombery `docs/architecture.html`（v1.0 · 2026-05）及 `src/plombery`、`frontend/src` 源码。
页面级交互、API 契约、代码路径的**完整 16 章对比**见
<Plombery深度对比分析.html>。

### 13.1 架构范式差异（C4 视角）

| 视图 | CronPilot | Plombery |
| --- | --- | --- |
| 系统角色 | 外部**编排中枢**：触发业务 HTTP，不执行业务逻辑 | 嵌入式**执行运行时**：在用户 Python 进程内跑 Pipeline |
| 容器（运行时） | Gunicorn 多 worker × 每 worker 一套 Scheduler | Uvicorn 单 worker × AsyncIOScheduler 与 FastAPI 同循环 |
| 外部依赖 | 业务回调 URL、可选 Redis/MySQL、通知通道 | 可选 OAuth IdP、Apprise 通知；无「回调农场」 |
| 前端容器 | 无独立前端服务（Jinja SSR 同进程） | React SPA 静态资源由 FastAPI 挂载 |

### 13.2 分层架构对照

```
CronPilot                          Plombery
────────────────────────────────────────────────────────────
表现  Jinja2 + jQuery (SSR)              React 19 SPA + TanStack Query
接口  Flask main (HTML) + api (JSON)     FastAPI REST /api + Socket.IO /ws
领域  CronInfos + cron_do(HTTP)          Pipeline/Task/Trigger + executor.run
调度  CuBackgroundScheduler + ThreadPool  AsyncIOScheduler + async run()
数据  cron_infos / job_log (DB)          pipeline_runs (DB) + .data/runs/ (FS)
横切  conf.ini / 企微钉钉 / Redis锁       Settings yaml / Apprise / contextvars
```

### 13.3 前后端交互架构

| 维度 | CronPilot | Plombery |
| --- | --- | --- |
| 交互模式 | 多页 SSR；表单 POST → JSON `{errcode,errmsg,url}`（`js-ajax-form`） | SPA；REST JSON + HTTP 状态码；422 字段级错误 |
| 任务配置 UI | Web 动态 CRUD `cron_infos` | 代码 `register_pipeline`；UI 仅展示与手动 Run |
| 运行观测 UI | 日志表 + iframe 明细；无 Run 状态机页面 | RunsList + WS `run-update`；LogViewer + WS `logs.{id}` |
| 认证流 | 单密码 Session | OAuth2 Session（可关闭） |

### 13.4 调度与执行架构

| 项 | CronPilot | Plombery |
| --- | --- | --- |
| Job 函数 | `cron_do` → HTTP 客户端 | `run` → 循环 `_execute_task` |
| 拓扑 | 1 Job : 1 URL | 1 Trigger : 1 Pipeline : N Task（线性） |
| 成功语义 | 响应体 + error\_keyword；无 COMPLETED 状态 | Task 异常 → PipelineRun FAILED |
| coalesce | false | true |
| 多副本 | 文件锁 + Redis 锁（设计支持集群） | 文档禁止多 worker；无内置分布式锁 |

### 13.5 数据架构对照

| 数据 | CronPilot | Plombery |
| --- | --- | --- |
| 定义持久化 | DB 表（可 API 改） | 代码内存注册 |
| 运行记录 | `job_log`（回调响应 TEXT） | `pipeline_runs` + `tasks_run[]` |
| 大对象 | 塞进 content 字段 | 文件系统 `task.json`、`logs.jsonl` |
| 双存储 | JobStore DB + 业务 DB | SQLite 元数据 + .data 产物 |

### 13.6 部署拓扑对照

#### CronPilot

- Supervisor → Gunicorn gevent (N workers)
- 集群：共享 MySQL JobStore + Redis
- 无需 WebSocket 代理

#### Plombery

- Nginx TLS + Uvicorn workers=1
- 必须代理 `/ws` WebSocket
- 单卷：db + .data

### 13.7 ADR 级对照（为何选型不同）

| 决策点 | CronPilot 选择 | Plombery 选择 |
| --- | --- | --- |
| 执行位置 | ADR-02 HTTP 回调 | 进程内 Python（Library-first） |
| UI 技术 | ADR-04 SSR 简化部署 | SPA 内嵌包（单进程交付） |
| 扩展方式 | DB/API 动态任务 | 代码注册 Pipeline |
| 水平扩展 | ADR-05 双锁 | 单实例；扩展靠外置调度或未来 Redis 锁 |
| 可观测 | 日志表 + 关键词告警 | 双存储 + WS 实时 + Apprise 状态告警 |

### 13.8 架构层选型建议

| 架构诉求 | 更合适 |
| --- | --- |
| 异构微服务统一 Cron 入口、调度与业务解耦 | CronPilot |
| Python 数据管道、要强 Run 状态机与实时日志 | Plombery |
| 既要统一调度台又要 Python 多步管道 | CronPilot 触发 → Plombery `POST /api/pipelines/{id}/run` |

## 14. 可借鉴的架构优化方向

完整论证见 [产品优化需求（详版 PRD）](产品优化需求-借鉴Plombery.html)；
对比文档 [§17](Plombery深度对比分析.html#s17) 含差距总览与路线图。此处仅列架构层要点。

### 14.1 守正：必须保留

- HTTP GET 回调 + 跨语言；Web/API 动态 `cron_infos`
- 双锁集群、秒级 Cron、签名与 add\_log

### 14.2 出奇：优先借鉴（不改变执行模型）

| 领域 | 借鉴 Plombery | 架构落点 |
| --- | --- | --- |
| 可观测 | Run 状态机 + 结构化日志 | `job_log.status`、SSE、`/metrics` |
| 契约 | REST + OpenAPI + 422 | 统一 envelope、校验服务层 |
| 存储 | DB 元数据 + 文件大对象 | 超大响应落盘 |
| 安全 | OAuth 可选 | SSRF 白名单 + 密码哈希（P0） |
| 工程 | pytest + 新 Python | SQL 参数化、CI |

### 14.3 不借鉴

进程内 Pipeline、代码唯一任务定义、强制单 worker、全量 React 重写 —— 均会削弱 CronPilot 现有定位。
