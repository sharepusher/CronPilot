## 三、数据模型

```
job_log（在 A′ 已有列基础上追加）
  ├─ http_status   INTEGER NULL     ← 已有（b105e47）
  ├─ status        VARCHAR(16)      ← 新增：success | fail | error
  └─ fail_reason   VARCHAR(128)     ← 新增：短枚举/标签，可空

旧数据：status NULL → UI 按 http_status + content 推断展示「—」或「未知」
```

### 3.1 status 枚举（已确认草案）

| 值 | 含义 | 典型场景 |
| --- | --- | --- |
| `success` | 本次回调判定为成功 | HTTP 2xx 且未命中失败规则 |
| `fail` | 已发出 HTTP 请求，但业务/规则判定失败 | 4xx/5xx（配置开启时）、error\_keyword 命中 |
| `error` | 未得到正常 HTTP 响应 | 超时、连接失败、SSRF 拦截、任务不存在等（`content` 以「发生严重错误」开头） |

### 3.2 fail\_reason 示例（写入时标准化，非用户自由文本）

| fail\_reason | 触发条件 |
| --- | --- |
| `http_4xx` / `http_5xx` | `fail_on_http_4xx_5xx=1` 且对应状态码 |
| `keyword` | 响应体命中 `error_keyword` 任一词（不区分大小写） |
| `timeout` | `requests` 超时（`ReadTimeout` 等） |
| `connection` | 连接/DNS/SSL 等请求层异常 |
| `blocked_url` | SSRF / URL 校验未通过（未发起请求） |
| `internal` | 其它未分类异常 |

多条规则同时命中时：**优先写最主要一条**（建议顺序：error 类 > http\_5xx > http\_4xx > keyword）。

## 四、判定逻辑（cron\_do）

请求前 URL/任务校验失败 → status=error, fail\_reason=blocked\_url|internal, http\_status=NULL
↓
requests.get(timeout=120s) 异常 → status=error, fail\_reason=timeout|connection|internal
↓
得到 status\_code + body → 写 http\_status, content
↓
若 fail\_on\_http\_4xx\_5xx 且 code≥400 → status=fail, fail\_reason=http\_4xx|http\_5xx
否则若 keyword 命中 → status=fail, fail\_reason=keyword
否则 → status=success, fail\_reason=NULL
↓
若 status≠success → wechat\_info\_err（与现有关键词告警合并，避免重复两条）

### 4.1 配置项（conf.ini / conf.ini.example）

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `fail_on_http_4xx_5xx` | `1` | `1`：4xx/5xx 记 `fail` 并告警；`0`：仅 keyword/异常算失败（兼容极老行为） |
| `error_keyword` | `fail,error` | 保持现有；命中则 `fail`（可与 HTTP 规则叠加，告警一次） |

| status | 徽章 | 第一行其余部分 |
| --- | --- | --- |
