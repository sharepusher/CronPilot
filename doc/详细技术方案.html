1. 项目背景与目标

企业在多服务、多环境中分散维护 crontab，存在不可视、难审计、无法 API 化、集群重复执行等问题。CronPilot 提供中心化调度台：统一配置周期规则，通过 HTTP 触发既有业务接口，并沉淀执行日志与失败通知。

1.1 建设目标

编号目标验收标准
G1任务统一管理Web 列表、搜索、启动/暂停、下线（无物理删除）
G2Crontab 兼容支持日/周/时/分/秒及 */n、列表、区间
G3开放集成REST API 增改任务、启动/暂停、上传执行明细
G4集群安全多节点部署时同一任务不重复执行
G5故障可达异常/关键词命中推送企微、钉钉、WebHook

5. 模块详细设计

5.1 应用工厂 create_app

create_app(config_name)
  ├── app.config ← DevelopmentConfig / ProductionConfig
  ├── logging → datas/logs/info.log (INFO filter), error.log (ERROR)
  ├── db.init_app(app)
  ├── scheduler.app = app; scheduler.init_app(app); scheduler.start()
  ├── register_blueprint(main)
  └── register_blueprint(api, url_prefix='/api')

5.2 cron_do 执行逻辑（伪代码）

def cron_do(cron_id):
    with app.app_context():
        cif = CronInfos.get(cron_id)
        if not cif or invalid url: write job_log(error); return
        log_id = uuid4()
        sign = MD5(sorted_query_params + api_key)
        t0 = now()
        try:
            resp = GET(cif.req_url, params={log_id, sign}, timeout=120)
            body = resp.text or json
            if any(kw in body.lower() for kw in error_keywords):
                send_alert(task_name, body)
            JobLog.create(cron_id, body, take_time=now-t0, log_id=log_id)
        except Exception as e:
            JobLog.create(error); send_alert(e)

5.3 Web 与 API 校验复用问题

main/views.py 与 api/views.py 中 Cron 字段校验逻辑高度重复（约 300+ 行 ×2）。技术债务：应抽取 services/cron_validator.py 与 services/cron_service.py（add_or_update、toggle_status）。

5.4 前端 Ajax 契约（Web）

表单 class js-ajax-form 提交后期望 JSON：

6. 数据库设计

6.1 逻辑 DDL（参考 ORM）

CREATE TABLE cron_infos (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  task_name VARCHAR(120) NOT NULL,
  task_keyword VARCHAR(500) DEFAULT '',  -- LIFECYCLE-2：新建/编辑必填 1～500
  run_date VARCHAR(25) DEFAULT '',
  day_of_week VARCHAR(10) DEFAULT '',
  day VARCHAR(20) DEFAULT '',
  hour VARCHAR(10) DEFAULT '',
  minute VARCHAR(10) DEFAULT '',
  second VARCHAR(10) DEFAULT '',
  req_url VARCHAR(200) DEFAULT '',
  status SMALLINT DEFAULT 1,  -- 0暂停 1运行 -1下线
  created_at VARCHAR(25) DEFAULT '',     -- LIFECYCLE-2
  updated_at VARCHAR(25) DEFAULT '',     -- 仅配置编辑刷新
  retire_reason VARCHAR(500) DEFAULT '', -- 人工下线必填 1～500（与说明同长）
  retired_at VARCHAR(25) DEFAULT ''
);

LIFECYCLE-2 字段与校验见 任务生命周期 §四。完整变更历史走 OPT-P1-09 operation_log，不另建任务更新日志表。

CREATE TABLE job_log (
  id INTEGER PRIMARY KEY,
  log_id VARCHAR(65) NOT NULL DEFAULT '',
  cron_info_id INTEGER NOT NULL,
  content TEXT NOT NULL,
  create_time VARCHAR(25) NOT NULL,
  take_time VARCHAR(25) DEFAULT ''
);
CREATE INDEX ix_job_log_log_id ON job_log(log_id);
CREATE INDEX ix_job_log_cron_info_id ON job_log(cron_info_id);

CREATE TABLE job_log_items (
  id INTEGER PRIMARY KEY,
  log_id VARCHAR(65) NOT NULL,
  content TEXT NOT NULL
);

APScheduler 自动维护 apscheduler_jobs 表（字段含 id、next_run_time、job_state 等），勿手工修改。

9. 回调集成规范（业务方必读）

9.1 回调请求格式

项值
MethodGET
Query 追加cronpilot_log_id, cronpilot_sign
HeaderUser-Agent: CronPilot
Timeout120 秒（超时记 job_log 异常并告警）

9.2 签名验证步骤

  1. 读取本次请求全部 query 参数（含 cronpilot_log_id，不含 sign）
  2. 按参数名字典序升序排列
  3. 拼接：key1=val1&&key2=val2&&...&&api_key={conf.api_key}（空值参数按源码跳过）
  4. MD5(拼接串) 与 cronpilot_sign 比较
// Python 参考（与 get_cronpilot_sign 一致）
def verify(params: dict, api_key: str, sign: str) -> bool:
    keys = sorted(k for k in params if params[k])
    s = "&&".join(f"{k}={params[k]}" for k in keys) + f"&&api_key={api_key}"
    return hashlib.md5(s.encode()).hexdigest() == sign

9.3 业务方响应建议

  • 快速返回：耗时 < 120s，长任务应异步处理 + 调用 add_log 上报进度
  • 避免响应体包含 error_keyword（默认 "fail"）除非确实失败
  • 实现幂等：同一 log_id 重复回调不应产生副作用
  • 验签失败应返回 403 并记录（当前系统仍记 200 响应体）

9.4 集成时序（长任务）

1. CronPilot → GET 业务 /task?cronpilot_log_id=UUID&sign=...
2. 业务立即返回 {"accepted":true}（<1s）
3. 业务异步执行，每步 POST /api/cron/add_log
4. 最终状态写入 add_log 或让主日志 content 不含 fail 关键词

基于 plombery/docs/architecture.html 与双项目源码。以下为摘要。

结论先行：

  • CronPilot：以“HTTP 回调触发”为中心的通用定时调度台，适合多语言业务系统的统一触发与审计。
  • Plombery：以“Python Pipeline（代码即配置）”为中心的嵌入式调度框架，强调任务链、运行元数据、实时日志流。

16.1 定位与边界（Execution Model）

维度CronPilotPlombery
执行载体 外部系统（回调 URL 的业务服务） 本进程 Python 代码（@task 函数）
任务模型 “单个任务 = 一个触发器 + 一个 HTTP GET” “Pipeline = 有序 Task 集合 + 触发器列表 + 可选 Pydantic 输入”
数据流 平台不传递任务输出给后续任务（只存日志） 上游 task 返回值 → 下游 task 第一个位置参数（线性流水线数据流）
面向对象 运维视角：任务与触发规则管理 开发者视角：把“任务编排”作为 Python 库嵌入应用

16.2 调度器与并发模型

项CronPilotPlombery
Web 框架Flask (WSGI)FastAPI (ASGI)
SchedulerAPScheduler 3.10 + 自定义 BackgroundSchedulerAPScheduler 3.11 + AsyncIOScheduler
并发执行ThreadPoolExecutor（max_workers=30）AsyncIO（sync 任务用 asyncio.to_thread）
misfire_grace_time50s60s（文档）
coalescefalse（积压不合并）true（积压合并一次）
水平扩展策略允许多 worker/多节点：文件锁 + Redis 锁协调明确建议单 worker/单副本；多副本会重复触发，需额外分布式锁

16.3 状态与审计（Run / Log / Output）

维度CronPilotPlombery
运行状态机 任务级：status ∈ {1,0,-1}；执行结果主要靠日志文本 运行级：PENDING/RUNNING/COMPLETED/FAILED/CANCELLED（PipelineRun）
日志 以回调响应体为主（TEXT）；另有 job_log_items 供业务回传进度 结构化 JSONL（logs.jsonl）+ WebSocket 实时推送（logs.{run_id}）
任务输出 平台不保存“业务输出对象”（只保存回调返回内容） 每个 task 输出落文件：.data/runs/run_{id}/{task}.json（DB 存元数据）
实时性 无实时流（页面刷新/分页查询） Socket.IO：run-update、logs 流（UI 实时刷新）

16.4 安全与认证

项CronPilotPlombery
Web 认证三角色 RBAC：用户名+密码校验 rbac_users.password_hash + Session（空表种子 admin/login_pwd）可选 OAuth2（Google/Microsoft）+ Session（Authlib）
API 认证可选 access_token（query/form）NeedsAuth 依赖注入（启用 auth 时）
执行鉴权回调签名：cronpilot_sign（MD5 + api_key）交由业务验签任务在进程内执行；主要保护 UI/API 与 data 路径访问
SSRF 风险高：req_url 可配置任意 URL（需加固白名单/禁内网段）低：无外部回调执行模型（但仍有外部通知/HTTP 依赖）

16.5 通知与告警

维度CronPilotPlombery
触发策略异常 + 响应体命中 error_keyword按 PipelineRunStatus 匹配 NotificationRule
通道企业微信 / 钉钉 / WebHook（固定实现）Apprise（Slack/Email/Discord 等 80+，URL 配置化）
消息内容纯文本 + 时间戳可模板化（邮件 HTML 模板）

16.6 适用场景与选型建议

你要解决的问题更适合原因
多语言微服务统一“到点触发业务接口”CronPilotHTTP 回调天然跨语言；平台只做调度与审计
Python 脚本/数据管道，想要 UI + 运行元数据 + 实时日志PlomberyPipeline/Task 原生模型 + Socket.IO 实时观测
需要 DAG 分支/并行/复杂依赖与大规模分布式两者都不理想应考虑 Airflow/Prefect/Dagster 等专业编排器

16.7 迁移与共存策略（可落地）

方案 A：CronPilot 继续做“触发层”，Plombery 做“执行层（Python 管道）”

  • 在 Plombery 暴露一个受保护的 HTTP 端点（如 /api/pipelines/{id}/run）
  • CronPilot 的任务回调指向该端点，沿用现有 cron 管理与审计
  • 优点：保留 CronPilot 对外统一入口；Python 复杂逻辑由 Plombery 管控
  • 注意：要处理认证（token/签名）与幂等（按 log_id 去重）

方案 B：以 Plombery 替代 CronPilot（仅当你主要跑 Python 任务）

  • 把每个 req_url 背后的“业务动作”实现成 Plombery 的 @task；多个步骤组成 pipeline
  • 用 Plombery trigger 表达 cron；UI 查看 runs + logs
  • 限制：部署需严格单 worker/单副本（或额外引入分布式锁/单调度实例）
