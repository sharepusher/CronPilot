一、问题

全面 Code Review 发现 3 处安全/数据完整性风险：

编号问题位置风险
S-1 /api/cron/add_log 缺少 scope 检查 app/api/views.py:426-440 持有 scope 受限 token 的用户可向 scope 外任务的日志写入内容（需知道 trace_id）
S-2 scheduler.lock 使用 CWD 相对路径 app/CuBackgroundScheduler.py:58
app/CuGeventScheduler.py:58		 CWD 不是项目根目录时锁文件路径错误 → 多 worker 重复轮询任务
S-3 toggle_status() 调度器操作先于 DB 提交 app/services/cron_service.py:51-58 DB commit 失败时调度器已执行 resume/pause → 状态不一致

二、根因

S-1：add_log 遗漏 scope

add_log 是业务方回传进度的端点，早于 API S6（用户级 Token 隔离）实现。S6 逐端点加 check_api_scope() 时，add_log 因"只是追加日志条目、不修改任务"而被认为低风险遗漏。但 scope 的语义是"不可见 = 不可操作"，写入日志条目也是操作。

S-2：scheduler.lock 相对路径

继承自上游 xiaoniu_cron，open("scheduler.lock", "wb") 未经 P1-5 同类排查覆盖。configs.py 的 conf.ini 相对路径已修复（P1-5），但调度器文件不通过 configs() 读取，属于独立的相对路径实例。

S-3：toggle_status 操作顺序

P1-2 统一状态切换时，将 Web 和 API 的逻辑提取到 cron_service.toggle_status()，保留了原始 Web 视图中"先调度器后提交"的顺序。原设计未分析事务失败场景。

三、方案

S-1 修复：add_log 加 scope 检查

在 cron_add_log() 中，通过 trace_id 查到 JobLog 后，加载其关联的 CronInfos，调用 check_api_scope(ci)：

jl = db.session.scalars(select(JobLog).where(JobLog.trace_id == cronpilot_trace_id)).first()
if not jl:
    return api_return(errcode=1, errmsg='cronpilot_trace_id 不存在')

# --- S-1 新增 scope 检查 ---
ci = db.session.get(CronInfos, jl.cron_id)
if ci:
    from . import check_api_scope
    denied = check_api_scope(ci)
    if denied is not None:
        return denied

S-2 修复：scheduler.lock 绝对路径

将 open("scheduler.lock", "wb") 改为 open(os.path.join(os.path.dirname(os.path.dirname(os.path.abspath(__file__))), "scheduler.lock"), "wb")，使用项目根目录。两个文件同步修改。

S-3 修复：toggle_status 先提交后调度

将 db.session.commit() 移到 scheduler.resume/pause_job 之前；调度器操作失败时回滚 DB 状态：

cif.status = new
db.session.add(cif)
db.session.commit()

try:
    if new == 1:
        scheduler.resume_job('cron_%s' % cif.id)
    else:
        scheduler.pause_job('cron_%s' % cif.id)
except Exception:
    logger.error('scheduler op failed after DB commit, rolling back', exc_info=True)
    cif.status = old
    db.session.add(cif)
    db.session.commit()
    return False, '调度器操作失败，状态已回滚', None, None

七、风险

风险缓解
S-1：add_log 的 trace_id 可能关联已删除的 cronci 为 None 时跳过 scope 检查（兼容性保护）
S-2：修改锁路径后旧锁文件残留锁文件是运行时创建的临时文件，下次重启自动使用新路径
S-3：调度器操作失败的回滚新增事务回滚本身也可能失败，但此时 DB 和调度器至少尝试了一致
