注册审批结果状态显示设计

状态：待确认  |  日期：2026-08-28  |  关联：OPT-P1-10 注册审批

1. 问题

P1. 已审批状态不可辨 — 已通过 / 已拒绝（无原因）/ 已过期的注册申请，操作列统一显示 —，管理员无法直观判断审批结果。
P2. 审批决策信息不足 — 审批者做决定时，表格仅展示基本信息（用户名/花名/邮箱/岗位），缺少关键审批依据：
  • 申请角色（role）— viewer / operator / admin 权限差异巨大，直接影响审批标准
  • 申请业务组（group_ids）— 决定用户可访问的资源范围
  • 申请原因（reason）— 申请者自述的使用目的
这些字段在模型 RbacRegistrationRequest 中已有，但审批页面未展示。

2. 根因

P1：操作列 Jinja 条件分支仅处理了 pending 和 rejected + review_comment，其余状态 fallback 到 —。

P2：注册审批页面直接复用了简化表格，未设计展开详情机制。视图函数未传递 group_name_map，模板无组名解析能力。

3. 参考与交互方案对比

3a. 详情展示方式三方案对比

维度A. "详情"按钮展开行B. 独立详情页C. 点击整行展开

行业参考Jira Backlog、GitHub PR企业 OA 审批Notion 数据库行
选择方案 A（按钮展开行）：
  1. 批量审阅场景 — 注册审批需逐条审阅多条申请，频繁页面跳转的方案 B 效率最低
  2. 避免交互冲突 — P1 批量操作引入了复选框，方案 C 的整行点击与复选框、操作按钮严重冲突（需对每个行内交互元素做 event.stopPropagation()，维护成本高且易遗漏）
  3. 信息量适中 — 注册详情仅 6-8 个字段，展开行完全够用，无需独立页面
  4. 一致性 — 操作列已有"通过/拒绝"按钮，追加"详情"按钮符合用户心智模型

3b. ID 列分析

结论：移除 ID 主列，在展开详情行中以辅助信息形式展示。
维度分析
用户价值ID 为自增数据库主键，对审批人无业务语义；审批关注点是「谁/什么角色/什么时候」
行业参考GitHub PR 列表不展示数据库 ID；Jira 展示人类可读 issue key（PROJ-123），非主键
空间成本ID 列占 ~60px 宽度，在 8 列表格中属低价值消耗
批量操作替代复选框 value 已承载 ID 传递，用户无需感知
排序替代「申请时间」列天然提供时序；「用户名」已满足唯一标识（pending_username UNIQUE）
调试需求在展开详情行中显示 申请编号: #6（灰色辅助文字），仅排查时可见

6b. 审批通过后的数据流转

审批通过后，approve_registration()（app/rbac/services.py L961–1033）执行以下流程：

步骤操作数据映射
1校验申请状态为 pending—
2检查用户名冲突（启用用户）若冲突 → 自动拒绝并写 review_comment='用户名已被占用'
3删除同名已停用旧用户（释放 UNIQUE）—
4创建 RbacUser见下方字段映射表
5绑定业务组req.group_ids → 逐个写入 UserGroup(user_id, group_id)；__ALL__ 不写行
6更新申请状态req.status='approved'、req.reviewer_id、req.update_time
7自动签发 API Token_auto_issue_token(user)
8审计日志action='user:register_approve'

字段映射：注册申请 → 用户记录

RbacRegistrationRequest→RbacUser同步方式
req.username→user.username直接复制
req.password_hash→user.password_hash直接复制（哈希值，非明文）
req.email→user.email直接复制
req.role→user.role直接复制
req.job_title→user.job_title直接复制（含 other:xxx 格式）
req.nickname→user.nickname直接复制
req.group_ids→UserGroup 关联表拆分逗号 → 逐行写入
req.reason→不同步申请原因仅保留在注册申请表中，不迁入用户表
关键说明：审批通过后，用户的所有基础信息（用户名、密码、邮箱、角色、岗位、花名、业务组）一次性同步到 RbacUser + UserGroup。此后用户可在「个人资料」页面自行修改花名、邮箱、岗位，但角色和业务组只能由管理员在「用户管理」页面修改。注册申请记录（RbacRegistrationRequest）作为审计痕迹永久保留，不会删除。

7. 并发审批安全分析

多管理员可能同时审批同一条注册申请。以下分析现有防护机制及各并发场景的处理结果。

7a. 现有双层防护

层级机制位置作用
第 1 层 — 应用层if req.status != 'pending': returnservices.py L969–970先提交者改状态为 approved/rejected，后到者读到非 pending 直接返回"该申请已处理"
第 2 层 — 数据库层pending_username UNIQUE 约束rbac_registration_request.py L39–44审批通过后 pending_username 设为 NULL，同时创建 RbacUser。UNIQUE 约束防止两个 pending 请求使用同一用户名

场景Admin AAdmin B结果安全？

7c. 用户体验优化建议

#问题建议优先级
1Admin B 页面仍显示"通过/拒绝"按钮（页面加载时 status 还是 pending）AJAX 返回"已处理"后，JS 动态将该行按钮替换为状态标签，而非仅弹 toastP2（可后续迭代）
2SQLite 写锁粒度较粗（WAL 模式），高并发写入性能受限SQLite 部署规模下无需优化；若迁移 MySQL/PostgreSQL 可考虑添加 version 列乐观锁P3（远期）

结论：当前应用层检查 + 数据库 UNIQUE 约束的双层防护已覆盖所有可预见并发场景。SQLite 的写事务天然串行化进一步降低了竞态风险。

7b. 批量审批操作

仅对 pending 状态的记录启用批量操作（已通过/已拒绝/已过期不可再操作）：

交互方式

  1. 表头增加「全选」复选框（<input type="checkbox" class="rr-select-all">）
  2. 每行 pending 记录前增加行复选框（<input type="checkbox" class="rr-select" value="ID">）
  3. 非 pending 行无复选框（已处理不可再操作）
  4. 选中 ≥ 1 条时，筛选栏右侧出现「批量通过 (N)」「批量拒绝 (N)」按钮
  5. 批量通过 → CpConfirm 二次确认 → POST /rbac/registration_review/batch_approve
  6. 批量拒绝 → CpModal（含拒绝原因 textarea）→ POST /rbac/registration_review/batch_reject

安全考量

  • @csrf_protect 必须（同单条审批）

  • Scope 检查：按组管理员不可批量审批其 Scope 外的申请（由 approve_registration 内部检查保证）

12. 风险

  • 低风险：模板条件分支 + 展开行 toggle，不改核心审批逻辑
  • 后端查询：group_name_map 和 reviewer_map 各一次查询，数据量极小（业务组 < 20，审批人 < 10）
  • 搜索性能：LIKE '%keyword%' 在 < 1000 行注册申请表上无性能风险；后续若数据增长可加索引
  • 批量操作并发：每条独立调用 approve_registration()，pending_username UNIQUE 约束保证并发安全；单条失败不影响其余（逐条执行 + 汇总结果）
  • 回退：Git revert 单 commit（Batch 3/4 的路由新增可独立回退）
