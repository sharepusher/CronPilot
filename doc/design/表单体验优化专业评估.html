2. 逐项专业评估

2.1 C1 — Cron 表达式必填标注 + AJAX 错误字段定位

变更内容

  • Cron 表达式区域的 <label> 增加 <span class="tf-required">*</span> 必填标识
  • 容器 #cron_div 增加 data-field="cron_div" 属性
  • common-redesign.js AJAX 错误回调读取 data.field，定位对应元素并添加 tf-field-error 高亮 + scrollIntoView

合理性评估

A — 完全合理

  • 设计正确性：必填字段标注是 WCAG 2.1 的 SC 3.3.2 Labels or Instructions 基本要求。Cron 表达式作为核心必填字段缺少标识确实是遗漏
  • 实现正确性：data-field 属性不影响渲染；scrollIntoView 的 block: 'center' 确保错误区域居中可见
  • 兼容性：不改变任何现有行为，仅在后端返回 field 时增强定位

准确性验证

检查项结果
data-field="cron_div" 与后端返回的 field 值匹配通过
必填标记使用 .tf-required 类（项目规范）通过
不影响编辑模式（已有 Cron 值）通过

2.2 C2 — AJAX 错误区域高亮改为 section-level

变更内容

  • 当错误目标是区段容器（如 cron_div）且内含子 .tf-field 元素时，使用 tf-section-error（仅标签变红）替代 tf-field-error（所有子 input 边框变红）
  • 新增 CSS 规则 .tf-section-error > .tf-label 仅影响直接子级标签

合理性评估

A — 完全合理，是一次关键修复

  • 问题严重性：原实现将 Cron 区域所有 6 个子 input 同时标红，用户误以为每个子字段都必填，实际上只需填入有效组合即可。这是一个误导性反馈
  • 行业对标：Google Forms、Jira 等系统在复合字段（日期区间、地址等）校验失败时仅高亮区域标题，不逐个标红子字段——符合「错误粒度应与校验粒度匹配」原则
  • CSS 设计：使用 > 子选择器（.tf-section-error > .tf-label）精确控制作用范围，不污染嵌套层级

风险评估

风险等级分析
子选择器 > 在 DOM 重构后失效低仅影响新增的 section 容器模式，且项目有 check_ui_contract.py 监控

2.3 C3 — Phase 1：任务表单内联字段错误文案

变更内容

  • AJAX 错误响应含 field 时：在目标字段下方动态插入 .tf-error-msg 内联文案，隐藏原有 .tf-hint，不弹 Toast
  • 无 field 时：保持 Toast 降级
  • <form> 添加 novalidate，移除所有 required/min/max HTML5 约束属性
  • CSS：.tf-error-msg 12px + var(--cp-danger) + ::before 警告图标 + fadeIn 动画
  • 用户修改字段后自动清除错误状态并恢复 hint

合理性评估

A+ — 业界最佳实践，实现质量高

  • 心理学依据：格式塔接近性原则（Law of Proximity）— 错误信息与出错字段的物理距离直接影响认知效率。Jakob Nielsen 的可用性研究表明，表单错误内联显示比全局消息的修正成功率高 22%
  • 行业标准：Material Design 3、Ant Design 5、Bootstrap 5 Forms、GitHub Form Validation 均采用此模式作为默认方案
  • 禁用原生校验的决策：完全正确。HTML5 原生校验气泡（:invalid + 浏览器 tooltip）在样式、文案、时机上均不可控，与自定义内联文案产生视觉冲突。所有主流 UI 框架（React Hook Form、Formik、VeeValidate）均建议 novalidate
  • 安全性：移除 required 不影响安全性——后端服务层是唯一可信的校验源。前端 required 仅是用户体验辅助，移除后用户仍会在提交后 < 200ms 内看到服务端校验结果
  • ARIA 无障碍：role="alert" 使屏幕阅读器自动朗读错误信息，符合 WCAG 2.1 SC 4.1.3

架构设计质量

维度评价
分层清晰度优 — CSS 样式层 / JS 行为层 / HTML 结构层分离清晰
可扩展性优 — 任何新表单只需添加 data-field + 后端返回 field 即可启用，无需改 JS
降级策略优 — 无 field → Toast；找不到目标元素 → Toast。两层降级确保错误信息不丢失
状态管理优 — input 事件自动清除，不需要额外的状态追踪

合理性评估

A — 架构一致、实现可靠

  • CSS 提升决策正确：按项目 CSS 归属决策树（cronpilot-format-guard.mdc），跨页面复用的 UI 组件样式应归入 redesign-components.css。.tf-error-msg 从页面作用域提升到全局是架构上的必要调整
  • 选择器泛化策略合理：[class*="-hint"] 相比逐页适配（.tf-hint, .cr-hint, .pw-hint...）更简洁且自动兼容未来新表单。作用域限定在 [data-field] 容器内，误匹配风险极低
  • 关键词推断方案的权衡：理想方案是让服务层直接返回 field key，但 CronPilot 的服务层 create_user/update_user 等函数返回 {'ok', 'msg'} 二元结构，改动影响面大。视图层关键词推断是一个务实的折中——关键词匹配失败时安全降级为 Toast，不丢失错误信息
  • 自动推断机制：_users_form_response 通过检测 template 名称自动选择推断函数，消除了调用方需要显式传 data 的负担——这是一个好的工程设计

合理性评估

B+ — 适用于当前阶段，但需文档标注适用场景

  • 合理性：CronPilot 定位为内部运维调度台（非面向公网的 SaaS），部署在受信任内网。50 次失败 / 15 分钟的阈值在内网场景下合理——团队共享 IP 办公、开发/测试频繁登录不会误锁
  • 行业参照：
    • AWS IAM Console：连续 5 次失败锁定 1 小时（面向公网，严格）
    • GitLab Self-managed 默认：10 次 / 10 分钟（内网部署，中等）
    • Jenkins：无内置限流（依赖网络层 WAF）
    • Airflow：无内置限流
  • 风险：若 CronPilot 未来暴露在公网，50 次阈值会削弱暴力破解防护。建议在部署文档中注明「公网部署需配合 WAF / fail2ban」

安全影响分析

攻击场景原阈值防护新阈值防护评估
自动化暴力破解（每秒 10 次） 0.5 秒内触发（5 次 / IP） 5 秒内触发（50 次 / IP） 降低但可接受：内网场景暴力破解概率极低
多人共享 IP 办公室 高误杀率（5 次即锁定整个 IP） 几乎无误杀 显著改善
针对单用户的凭据填充 10 次 / 10 分钟 50 次 / 30 分钟 降低：依赖密码策略（≥6 位）+ 内网访控

5. 改进建议（后续版本）

#建议优先级收益
1 服务层原生 field key：在 create_user/update_user 等服务函数中直接返回 field key，消除视图层关键词推断 P2 消除推断层脆弱性；降低错误消息文案变更时的维护成本
2 客户端预校验：对明确的前端可判断规则（非空、长度、格式）添加 blur 事件预校验，减少不必要的服务端往返 P3 进一步提升表单填写体验；但需控制前后端校验规则的一致性
3 多 field 错误并行显示：后端返回 fields: [{field, msg}] 数组，前端同时标记多个错误字段 P3 减少用户逐个修正的提交次数
4 E2E 自动化测试：用 Playwright 覆盖表单验证的关键路径（空提交 → 内联错误出现 → 修改 → 错误消失） P2 保障 JS 行为的回归安全性
5 Hint 类名统一：长期将 cr-hint/pw-hint/uf-hint 等统一为 tf-hint，减少认知负担 P3 代码一致性，但当前通配方案已足够
6 登录限流环境分级：配置文件区分 development/production 环境的限流参数，生产环境保持更严格的阈值 P1 兼顾开发效率和生产安全
