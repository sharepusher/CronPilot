1. 问题与证据

修复前，用户打开已有任务，不更改任何内容，直接保存；update_cron() 仍先赋值和更新元数据，再重建业务组/标签关联，提交配置，重新注册调度任务，最后独立提交操作日志。

已执行 .venv-py311/bin/python scripts/verify_cron_edit_baseline.py：no_change 样例使用单组、单标签暂停任务，记录 6 条真实 DML、2 次 commit、1 次 register 和 1 次 pause；时间与操作人变化，日志增加 1 条。该数字只是这一样例，不外推为所有任务固定成本。问题已被证明；写入失败的线上频率没有测量。

根因是写服务没有在任何赋值、自动 flush、关联同步和外部调用之前判断“目标值是否已经等于当前持久化值”。前端也没有使用页面原值阻止无变化提交。ORM 偶尔不产生某一列 UPDATE，并不能阻止关系表重建和调度调用。

2. 范围与完成定义

本文只解决整个编辑请求没有有效变化时的零副作用。真正修改一个字段后的其他关系是否还全量重建，不在本次完成定义；由后续按需优化评估。旧表单覆盖、日志原子性、调度失败恢复和暂停注册窗口仍按原问题保留，不宣称本批关闭。

不新增数据库字段和迁移，不改业务角色权限，不改调度器的真实变更应用顺序。无变化保存不是“修复调度异常”命令：即使 job 缺失，也不借保存按钮隐式重注册，应使用现有明确操作入口。

验收不变量：对于通过授权、可编辑、请求目标等于当前配置的任务，业务表和关系表零 INSERT/UPDATE/DELETE，零配置 commit，时间/操作人不变，零变更操作日志，零 scheduler 写操作。可以读取当前任务、组和标签；SQLAlchemy 读请求可能产生短读事务，不宣称整个请求“绝无事务”。

3. 无变化如何判断

前端比较“当前表单”与“页面加载时实际显示的原始表单”，后端比较“按该入口语义解释后的目标配置”与“数据库当前配置”。两个基准用途不同：前端减少无效提交，后端抵御绕过 JS。前端认为没改时，即使 DB 已被别人改变，也只是留页不写库；前端认为改了而后端发现目标已存在，则仍返回 no_change。

比较对象规则防误判要求
task_name、task_keyword请求采用既有 trim 规则；任务名也纳入比较，虽页面 readonly。当前 DB 的非空文本不随意 trim 成另一个值后宣称已相同。不借本批新增任务名编辑能力；不因比较遗漏说明字段而吞掉真实修改。
调度模式与 run_date/day_of_week/day/hour/minute/second模式选择与字段处理沿用当前规范化。空文本与遗留 NULL 的展示等价需固定测试；不把空值与 *、0 与空秒、不同 Cron 语法擅自等价。体验版禁用秒字段沿用现行规则。模式相关字段、disabled 字段也须按提交语义比较，不能直接序列化 DOM 后就断言业务等价。
req_url、req_method、req_bodyURL/Body trim、方法 upper 沿用当前校验器。Body 保持文本比较；JSON 键序改变不在本次自动合并范围。GET 下现有非空 Body 仍按当前持久化语义纳入比较。不打印 URL/Body 到控制台、日志或浏览器持久缓存，不引入新的明文快照 token。
timeout_sec空输入对应 None，合法数字按整数比较；None 与显式 5 不等价。不能忽略超时而误判 no-op；非法数字先报字段错误。
scope_type + 业务组关联作为一个整体比较。GROUP 对应恰好一条有效关系，GLOBAL 对应零关系。比较实际完整关联集合，而非只取第一条。历史多组或 GLOBAL 带关联的异常结构不能被直接视为 no-op，也不能本批自动清理。应返回配置需检查并保持零写入。
标签读取现有关联、Tag.name 和 group_id；按当前 trim、lower 去重和无序集合语义比较，标签命名空间必须属于目标业务组/全局。比较只读，不调用 get_or_create_tag 或 sync_task_tags。不能跨组把同名标签视为相同关系；已有大小写冲突等异常进入检查路径，不擅自归并。
恢复运行意图暂停任务显式 resume_after_save=true 是有效变化；运行任务再次请求运行本身不构成变化；下线任务既有拒绝优先。不能把状态命令遗漏而错误阻止恢复；虽然当前页面没有恢复开关，共享服务已有此参数，必须测试。
元数据与 CSRFupdated_at、last_operator_name、last_operated_at 为写入副作用，不作为用户输入比较项；csrf_token、按钮 loading 文案不参与业务比较。比较前不能 stamp_last_operator 或 apply_normalized_to_model。

字段缺失按现有入口解释：API 未传 scope/tag 时比较域不包括它们，保持既有服务行为；Web 明确提交空标签表示清空，是实质变化。API 普通配置字段的既有默认仍可能清空/重置字段，不在本批偷偷变为 PATCH。GLOBAL 与 group_id=None 的现有真实变化行为风险保留，不能利用 no-op 优化顺手修另一问题。

4. 流程与校验顺序

GET 编辑页：沿用权限与读取 → 渲染原值 → 请求结束；不跨用户编辑时间持有事务

点击或回车：轻量规范化 → 与原表单比较
  明确相同：显示“未检测到变更，无需保存”，不发 POST
  有变化/无法证明相同：进入现有提交与 loading 守卫

POST：认证/授权/CSRF/目标可编辑检查 → 纯输入解析与规范化
  → 读取当前配置、完整组/标签关联（不赋值、不写库）
  → 无法证明相同/发现非法结构：错误或继续既有完整校验
  → 全部相同且无状态变化：返回 no_change，不进入写路径
  → 真实变化：完整业务校验通过后，进入原有更新流程

纯规范化与动态校验须分清：字符串/数字/标签结构先检查；SSRF DNS、一次性时间过期等随时间变化的校验，在“真实修改”路径仍完整执行。对于确实相同且只读的请求，无须为了再次保存旧配置做 DNS 探测或要求重选一次性时间；no_change 不代表当前配置被重新批准执行。实施时可抽出既有纯解析内核并保持旧 validator 默认完整行为，不增加全局 skip_validation 开关。新增任务/API 真变更不能绕过完整校验。

比较路径必须在 ORM 赋值之前执行，避免查询自动 flush 已有脏对象。请求不应带入别的待写业务对象；不能为返回 no_change 而全局 rollback 共享 Session，从而撤销调用方已有工作。no-op 不显式 commit，由请求清理结束读事务。发现服务被嵌入已有写事务的调用方时，记录该调用契约并测试，而不是任意改变它的事务。

5. 共享服务与返回兼容

权威比较应在 Web/API 共同可用的写入边界之前；不要只在 Web view 加一次 if，而让 API 继续制造副作用。设计增加内部显式结果（changed/no_change + task），由适配层使用；现有 update_cron() 的返回 CronInfos、upsert_cron_by_task_name() 的二元组和 edit_cron_web() 的旧调用约定须保留兼容包装，避免隐式改变全部调用方。具体新内部函数名在实施时以全仓库调用点核对后确定。

Web 适配输出 no_change，公共 Ajax 已识别该 outcome 留页；仍须实测 loading 重置、toast 和原生响应。API 保持既有响应结构及成功语义，本批仅抑制有效 no-op 的副作用，不新增 API 字段。若实施确需改动公开 API 字段，须先回到本文补充兼容说明并再次确认，发布说明标注 API Breaking Change。

原生 POST 的 no_change 回退采用重定向回同一编辑页并显示固定提示，沿用既有入口参数构造；不得使用用户任意 next URL。结果提示只解释最近请求，不能当作数据库事实或权限依据。

8. 验收标准与风险

  • 相同任务：GROUP/GLOBAL、空标签/已有标签、运行/暂停、GET/POST、NULL/显式超时、周期/一次性；任务和关联/日志零 DML，元数据完全不变，commit=0，scheduler 全部写操作=0。
  • 规范化：说明首尾空格、方法大小写、标签重复/重排/命名空间；不把 NULL 超时与 5、空 Cron 与 *、JSON 重排误认等价。标签脏结构报错零写入。
  • 真变更反例：只改说明/timeout/Body/标签/业务组/调度方式，各自不能误报 no_change；暂停任务显式恢复不能短路。
  • 入口兼容：Web、API upsert 更新分支、直接服务调用返回兼容；新增任务原行为；旧暂停保持和恢复用例通过。
  • 校验：未授权/CSRF/下线优先拒绝；真变更不绕过 SSRF、非法 JSON、过期时间；仅无变化不因 DNS/旧时间阻塞。
  • UI：Operator 完整登录操作与截图；无变化/改后还原 Network 断言零 POST，正常修改一次 POST；回车/双击/无 JS；提示后可继续编辑保存，按钮无卡死。
  • 数据库隔离：单测 sqlite:///:memory:，真实 MySQL 使用专用隔离库；实际 SQL 与调度调用计数不能仅依赖“最终字段一样”。

主要风险是漏字段导致真实变化被吞、缺省语义被改变、前端初始化导致误比较、比较阶段 autoflush，以及无变化被误作授权绕过。防护是正反矩阵、只读比较和入口回归。旧页面覆盖仍可能发生；本设计不新增页面版本或三方比较，后续问题②单独解决。

9. 专业性、准确性与合理性评估

问题有真实服务/SQL 证据，准确性高；改善减少无意义写入与调度调用，不能声称消除所有写失败。对单任务字段和小型标签集合做内存比较，无需复杂 SQL 或全局缓存；后端增加必要的关联读取，读取按已有 task_id 索引定位。成本随该任务标签数增长，而非任务总量；不写未经测量的收益比例。

不新增版本表和调度恢复系统，使首项方案可独立实施；两级预检符合用户“提交前能判断就先判断”的要求，后端兜底避免绕过 JS。实际变更保持旧流程，因此此批是可控优化，不包装为完整事务或并发治理完成。
