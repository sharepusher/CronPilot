1. 问题

当前用户新增和编辑入口主要根据目标角色判断 __ALL__ 是否允许：只要提交的目标角色是 admin，就不会被“非 admin 不允许全局”分支拒绝。代码没有同步判断当前操作人是否本来就有权授予全局 Scope。

因此，一个只能管理部分业务组的 Biz Admin，只要能管理某个目标用户，就可能通过直接构造 POST，或在多组页面中选择 admin 与“全部（全局权限）”，把目标用户变成无组关系的全局管理员。新增用户入口存在同样模式。

安全影响：受限管理员可以借由另一个账号扩大自身组织边界。这属于权限提升，不是普通表单校验问题；只隐藏前端选项不能关闭风险。

2. 根因与现有正确基线

2.1 根因

  • 把“目标用户是否可以使用全局 Scope”与“操作人是否有权授予全局 Scope”合并成一个角色判断。
  • validate_groups_for_role() 只验证目标角色和组参数语义，不携带 actor 授权上下文。
  • 用户表单始终渲染 __ALL__ option，JavaScript 只按目标角色显示或隐藏。
  • 用户新增和编辑各自写了相似判断，没有共享“授予者 × 目标角色 × 目标 Scope”的统一策略。
  • 现有 test_admin_with_all_accepted_on_add 使用用户名 admin，实际覆盖的是“种子管理员允许”正向路径，该期望正确，不应改成拒绝。真正的测试缺口是：没有用非种子、具有一个或多个具体组的 Biz Admin 覆盖新增和编辑的 admin + __ALL__ 拒绝路径。

2.2 已有正确基线

注册审批服务已经区分审批者权限：种子/全局管理员可审批全局 admin 申请；按组管理员只能审批其组集合完全覆盖的 admin 申请，并拒绝 __ALL__。本需求应复用该政策含义，不应再创造第四套判断。

3. 权威授权矩阵

操作人目标角色请求 Scope结果
种子管理员admin__ALL__允许；仍须通过其他用户安全规则。
全局管理员admin__ALL__允许。
种子/全局管理员admin/operator/viewer任意有效具体组集合允许；非 admin 不允许 __ALL__。
按组管理员admin/operator/viewer操作人当前组集合的非空子集允许；admin 仍是受组约束的 Biz Admin。
按组管理员admin__ALL__ 或持久化空组的全局语义拒绝。
按组管理员任意包含操作人范围外组拒绝。
operator/viewer任意任意由 user:manage 拒绝，不进入授予逻辑。

该矩阵同时适用于新增、编辑和注册审批。任何入口不得仅因目标角色是 admin 就接受 __ALL__。

4. 推荐方案

4.1 统一服务端授权判定

新增一个无副作用的内部策略函数，输入操作人当前数据库身份、目标角色和请求组，输出规范化后的允许结果或稳定拒绝原因。具体函数名由实施阶段确定，行为必须等价于：

请求值规范化
  → 校验目标 role
  → 校验 __ALL__ 与具体组不能混选
  → 校验所有具体组真实存在
  → 从数据库读取操作人当前 role / username / group_ids / active
  → 确认操作人仍有 user:manage
  → 若请求 __ALL__：要求目标 role=admin 且操作人当前 bypass scope
  → 若请求具体组且操作人非 bypass：要求 requested_groups ⊆ actor_groups
  → 通过后才进入创建或编辑写入

拒绝分支必须发生在任何用户、组关系、Token、缓存和成功审计副作用之前。页面 Session 可用于展示，但不能单独作为最终授权事实。

4.2 写入口覆盖

入口现状本需求动作
/rbac/users/add目标 role=admin 即可绕过非 admin 全局限制。在 create_user() 前调用统一 actor 授权；按组管理员只能提交自身组子集。
/rbac/users/edit与新增入口同类；另有目标 Scope 检查但不限制授予全局能力。保留目标可管理性检查，并增加授予能力检查；未来事务服务实施时必须在写边界复用同一策略。
注册单条审批已有 admin 申请覆盖关系和 __ALL__ 限制。保持行为；可逐步复用统一策略，重构不得降低现有保护。
注册批量审批逐条调用单条审批服务。保持逐条 fail-closed；越权项不得因批量响应整体成功码而实际落库。
create_user()/set_user_groups()当前是业务写入函数，不包含完整 actor 授权。管理端调用链必须经过统一授权；全仓搜索所有调用方并登记受信任内部调用，禁止未来新增入口绕过。

4.3 前端最小暴露

后端向用户表单提供只读布尔上下文 can_assign_global：

  • 种子/全局管理员：角色为 admin 时显示“全部（全局权限）”。
  • 按组管理员：模板不渲染 __ALL__ option，而不是只靠 JavaScript 隐藏；提示改为“只能分配您当前管理范围内的业务组”。
  • 无论页面是否渲染，直接构造 group_ids=__ALL__ 都必须由后端拒绝。

不新增对话框、不改变表单布局、不修改全局 Ajax 行为；页面改动仅限 option 条件渲染和权限提示。

4.4 拒绝响应与审计

  • __ALL__ 越权：返回“您无权授予全局管理权限”。
  • 具体组越界：返回“不能分配您管理范围之外的业务组”。
  • Ajax 返回 errcode=1、无成功 URL；原生 POST 回渲染表单。
  • 拒绝可以记录现有 scope:deny 安全审计；审计失败只能记录受保护日志，不能把拒绝改为允许。
  • 拒绝日志记录 actor user ID、目标 user ID（新增时为空）、入口和原因码，不记录密码、Token、邮箱或请求全文。

5. 范围与非范围

5.1 范围

  • 用户新增和编辑入口的全局权限授予校验。
  • 按组管理员的具体组子集校验。
  • 用户表单 __ALL__ option 的服务端条件渲染。
  • 注册单条/批量审批已有保护的回归测试。
  • 所有 create_user()、set_user_groups() 和注册审批调用方的全仓扫描。

5.2 非范围

  • 不实施用户编辑 change set、单事务或 no-op；由独立方案负责。
  • 不改变角色权限集合，不新增 RBAC 角色。
  • 不迁移现有用户组数据，不自动降权已有全局管理员。
  • 不修改注册申请人可提交 admin + __ALL__ 的申请能力；实际授权仍由审批者边界控制。
  • 不在本批解决 Session 权限实时刷新、最后管理员并发不变量或全站 Scope 框架重构。

6. 安全数据流

管理端 POST → 登录 / auth_version / user:manage / CSRF → 读取 actor 当前数据库角色与组 → 校验目标是否在 actor 可管理范围（编辑） → 规范化 target role + requested groups → 校验 actor 是否有权授予该 Scope ├─ __ALL__：仅 actor 为 seed/global 且 target role=admin └─ 具体组：scoped actor 只能授予 actor_groups 的非空子集 → 通过：进入既有创建/编辑业务写入 → 拒绝：零业务副作用 + fail-closed 响应

拟改文件新增 tests/test_rbac_global_scope_assignment.py；仅在必要时补充 tests/test_registration.py，不修改种子 admin 允许用例的期望。
动作用内存数据库建立种子 admin、非种子全局 admin、单组 Biz Admin、多组 Biz Admin、operator/viewer 五类 actor；对新增和编辑各写正向、负向及零副作用断言。
红线验收当前代码上，G-03/G-04 应因越权被实际允许而稳定失败；种子 admin 允许、非 admin 目标禁止 __ALL__、现有审批范围用例仍通过。失败必须指向权限缺口，不得由 fixture/缺表异常代替。
退出/停止若红线用例在旧实现上通过，先复核 actor 是否被误设为种子/全局 admin；发现新 Scope 写入口则更新清单，不进入 S1。

前置S0 红线结果和入口清单已冻结。
拟改文件app/rbac/policy.py、app/rbac/services.py、tests/test_rbac_global_scope_assignment.py。
动作在 policy.py 中实现无副作用的“actor 是否可授予 target scope”判定，显式输入 actor 用户名/角色/当前组、target 角色及已规范化的请求 Scope；在 services.py 负责组参数规范化、真实存在性和 actor 数据库状态读取。禁止函数内读 Session 或提交事务。
绿线验收授权矩阵单元测试全通过；缺失 actor、非活动 actor、无效组、混选及组越界全部 fail-closed；策略输入不从 target 角色反推 actor 能力。
回滚/停止该批未接入路由，可整批回滚；如需依赖 Session 隐式状态才能判定，停止并重设 API。

8.3 S2：新增/编辑后端写入边界

前置S1 纯策略全绿，并已确认 authorize 类函数真实存在后再导入。
拟改文件app/rbac/views.py、app/rbac/services.py、tests/test_rbac_global_scope_assignment.py；如影响路由完整性，同步更新相关静态检查。
动作新增和编辑 POST 在第一个业务副作用之前，用 actor ID 回读当前数据库用户、活动状态和组关系，再调用 S1 策略。编辑入口同时保留“actor 可管理 target”检查。拒绝后不得调用 update_user()、set_user_groups() 或任何 commit。
绿线验收S0 的新增/编辑红线用例变绿；拒绝前后用户行、UserGroup、Token、个人信息和成功审计快照一致；Ajax/原生 POST 均返回稳定拒绝。
回滚/停止后端守卫是安全核心，S3/S4 发生问题时不得回滚守卫。如拒绝发生在任何写入之后，立即停止；本需求不宣称解决编辑路由的多次 commit 原子性。

绿线验收Biz Admin 的 GET DOM 不含全局 option，seed/global admin 的 DOM 包含；选角色、提交和错误回渲全流程无 JS 错误；表单 Ajax 和防重复提交门禁不回退。

前置S2/S3 专项用例通过。

动作补齐单条与批量审批的 __ALL__ 正反用例；全仓搜索 create_user、set_user_groups、approve_registration 和 __ALL__ 写入点，逐一标记“已守卫/受信任内部/不可达”。审批现有 Session 判定不得被误称为数据库实时判定；若统一到 S1 策略，必须同步修正 fixture 并证明行为等价或更严格。
绿线验收单条/批量审批、RBAC Scope、侧边栏、Ajax 表单、import smoke、路由完整性和 86 条路由冒烟全绿；每个生产调用方均可证明经过守卫。
回滚/停止任一调用方无法归类，或审批保护回退，均不得进入 S5。
生产写入调用方S4 归类保护边界
users_add → create_user已守卫S2 路由在首个业务副作用前调用 validate_user_scope_assignment()。

其他生产调用方不可达全仓搜索未发现其他 create_user、update_user、set_user_groups 或 approve_registration 生产调用点。

8.7 不得跨批的边界

  • S0 不改生产代码；S1 不接入路由；S2 不顺带实施用户编辑差异写入或单事务重构。

11. 风险与回滚

风险控制回滚原则
现有错误测试和实际使用依赖受限管理员授予全局权限视为安全修复，不保留兼容放行；Release Notes 说明权限收紧。不得通过关闭后端守卫回滚；必要时由 seed/global admin 完成合法授权。
前端隐藏导致全局管理员也看不到选项正反两类角色浏览器测试；模板上下文由服务端明确传入。可回滚模板隐藏，但后端守卫必须保留。
Session 与数据库 actor 状态不一致最终授权读取数据库当前角色与组；Session 仅提供 actor ID 和页面上下文。不得回退为只信任 Session。
集中策略影响注册审批先锁定审批现有测试；重构只在等价证明后进行。审批可继续保留现有专用守卫，但新增/编辑不得无守卫。
拒绝审计写入失败先拒绝，再 best-effort 审计；日志失败不改变授权结果。不能因可观测性故障放行安全操作。

12. 完成定义

只有以下条件全部成立，才能标记本需求已完成：

  • 所有新增、编辑和审批入口都满足同一授权矩阵；
  • 多组按组管理员无法通过 UI、直接 POST 或批量审批授予全局 Scope；
  • 种子/全局管理员的合法能力没有回退；
  • Scope 授权拒绝路径零业务写入且审计失败不导致放行；其他表单失败路径由独立事务方案负责；
  • 全仓调用方扫描无遗漏，专项、RBAC、Scope、路由和 UI 门禁通过；
  • 两类目标角色浏览器正反向证据已持久化或可由自动化重复生成；
  • 修复复盘、Release Notes、HTML/Markdown、索引和本地验收环境全部交付。
完成状态：S0–S5、F-01/B0–B3 与 F-02/R2-0–R2-4 已全部完成并正式关闭。新增、编辑、审批写入及注册审批读取均以数据库当前事实为授权依据；可重复浏览器证据已落库。用户编辑差异写入/no-op/单事务仍是独立方案，不因本需求关闭而自动实施。
