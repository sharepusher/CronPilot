任务创建页三项改进设计 — OPT-P1-11

状态：已完成

创建时间：2026-08-05

关联：用户反馈 2026-08-05；涉及 cron_add.html、cron_edit.html、数据模型

一、问题

反馈 1：业务组文案冗余

当操作人仅属于一个业务组时，任务创建页显示「所属业务组：风控业务 (risk-control-business)」， 但表单 label 本身已是「业务组」，「所属业务组：」前缀重复，信息密度低。

反馈 2：多组用户无法指定任务多组可见

当前每个任务仅绑定单个 group_id（cron_infos.group_id）， 拥有多组权限的用户无法让一个任务对多个业务组同时可见。

反馈 3：缺少业务/服务标签维度

任务缺乏跨业务组的归类方式（如「国家：日本」「业务线：支付」「服务：risk-engine」）， 无法按服务/业务维度筛选和检索任务。

二、根因

问题根因
文案冗余模板中硬编码了「所属业务组：」前缀，未对单组 vs 多组分别优化文案
单组限制cron_infos.group_id 为单值 INT，数据模型不支持多组
缺少标签系统无标签数据模型，任务仅有 task_name + task_keyword 两个文本维度

三、方案

3.1 反馈 1：文案精简

改法：移除「所属业务组：」前缀，单组时直接显示组名；多组时显示下拉。

场景当前改后
单组所属业务组：风控业务 (risk-control-business)风控业务 (risk-control-business) 仅同组可见
多组下拉单选下拉多选（见 3.2）

3.2 反馈 2：任务多组可见（方案 A1 — 关联表）

数据模型变更

-- 新建关联表
CREATE TABLE task_groups (
    id       INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id  INTEGER NOT NULL,
    group_id INTEGER NOT NULL,
    UNIQUE(task_id, group_id)
);
CREATE INDEX idx_task_groups_group ON task_groups(group_id, task_id);
CREATE INDEX idx_task_groups_task  ON task_groups(task_id, group_id);
迁移策略：新增 task_groups 表后，一次性将现有 cron_infos.group_id 数据迁移至 task_groups，所有查询统一改用 task_groups， 然后 删除 cron_infos.group_id 列。不保留旧列做兼容。
保留 cron_infos.scope_type（GLOBAL/GROUP），用于区分全局共享与组限定。

UI 交互

角色当前改后
非 admin（scope_locked）单组自动绑定该组不变
非 admin 多组下拉单选checkbox 多选（仅限本人所属组）
admin（全局/多组）scope_type 切换 + 单选组scope_type 切换 + checkbox 多选组

查询变更

-- 旧：WHERE group_id = ?
-- 新：WHERE id IN (SELECT task_id FROM task_groups WHERE group_id = ?)
--     OR scope_type = 'GLOBAL'

性能评估（1w-10w 任务）

指标值
task_groups 行数（10w 任务 × 平均 2 组）~20w 行，< 4MB
按组查询（带索引）< 5ms (SQLite) / < 2ms (MySQL)
分页列表（JOIN + LIMIT）< 10ms
缓存策略初期无需；10w+ 可加 lru_cache(TTL=60s) 于热路径

3.3 反馈 3：业务/服务标签系统（A+C 方案）

数据模型

CREATE TABLE tags (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        VARCHAR(64) NOT NULL UNIQUE,
    created_by  VARCHAR(120) NOT NULL DEFAULT '',
    create_time VARCHAR(25) NOT NULL DEFAULT '',
    update_time VARCHAR(25) NOT NULL DEFAULT ''
);
CREATE INDEX idx_tags_name ON tags(name);

CREATE TABLE task_tags (
    id      INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id INTEGER NOT NULL,
    tag_id  INTEGER NOT NULL,
    UNIQUE(task_id, tag_id)
);
CREATE INDEX idx_task_tags_tag  ON task_tags(tag_id, task_id);
CREATE INDEX idx_task_tags_task ON task_tags(task_id, tag_id);

用户侧行为

场景行为
创建任务输入框支持自由输入 + 已有标签自动补全（autocomplete）；可添加多个标签
输入新标签按回车或逗号确认 → 变成标签 chip → 系统自动去重后加入 tags 表
选择已有标签输入时下拉提示匹配的标签，点击选中
标签显示任务列表中标签以 chip/badge 形式展示，可点击筛选
任务筛选任务列表增加标签筛选维度

管理员侧行为

操作影响
重命名标签UPDATE tags SET name=? WHERE id=? — 任务关联不变，自动展示新名
合并标签UPDATE task_tags SET tag_id=存留id WHERE tag_id=被合并id + 删除被合并 tag — 透明
删除标签DELETE FROM task_tags WHERE tag_id=? + 删除 tag — 任务丢失该标签但任务本身不受影响

标签输入提示

建议用户输入维度：国家/地区、业务线、服务名。示例标签：JP 支付 risk-engine 风控-反欺诈

七、风险

风险缓解
cron_infos.group_id 到 task_groups 迁移数据一致性迁移脚本幂等；迁移后验证 task_groups 行数 = 有 group_id 的 cron_infos 行数
所有引用 cron_infos.group_id 的查询需改造全局搜索 .group_id 引用，逐点改为 JOIN task_groups；scope_type 引用保留不变
标签命名不规范导致碎片化管理员合并/重命名功能；前端 autocomplete 引导复用
cron_edit 页面同步改造与 cron_add 一同改造，保持一致
