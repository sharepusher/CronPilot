# v4.0.0 之后提交深度 Review

日期：2026-09-20 · 范围：`v4.0.0..700ec94` · 方法：提交链路审阅、Bugbot 正确性检查、实现与设计/发布计划交叉核验。

## 1. 结论

**不建议发布 4.1.0，也不建议将当前范围标为可合并完成。** 已确认 3 个 P1 正确性缺陷：当前实现未收敛到数据库自增 ID，且遗留生成器可造成主键冲突；另一个会使启用 DNS pinning 的公网 IPv6 任务必然失败。执行侧观测的 R3/R4/R6/R7 仍是已登记但未关闭的发布阻断/观察项；发布计划还保留一处 R2 状态漂移。

## 2. 已确认问题

| ID | 级别 | 位置 | 证据与影响 | 修复方向 |
| --- | --- | --- | --- | --- |
| CR-1 | P1 | `datas/model/cron_infos.py:9-14`、`job_log.py:8-13`、`job_log_event.py:8-14` | 用户确认的目标是业务表使用数据库自增 ID，但三张生产表仍设为 `default=next_id`，`execution_tracer.py` 还显式调用该生成器。现有 OPT-P0-21 收敛设计至少要求 job\_log 与其他业务表恢复自增，当前实现已经偏离该设计。 | 先更新正式设计，以“数据库自增 ID”为唯一目标；移除全部生产 `next_id` 调用，核对所有外键/引用列与 SQLite/MySQL 自增迁移兼容，并补插入后 ID 回填测试。 |
| CR-2 | P1 | `datas/utils/id_generator.py:18-45` | 在尚未移除生成器的当前版本中，它只使用进程内线程锁和序列，而 `gun.py` 配置 `workers=2`；同秒跨 worker 可生成重复主键。时钟回拨也会令时钟恢复时重复既有序列。 | CR-1 的自增迁移会根除该风险；迁移前不得以 worker 位扩展继续固化生成器方案。补多 worker 与时钟回拨的回归，证明旧路径不再被调用。 |
| CR-3 | P1 | `app/services/url_security.py:181-188` | DNS pinning 对公网 IPv6 直接把裸地址写进 netloc，生成如 `https://2606:4700::1111/a` 的非法 URL；Requests 在 prepare 时抛 `InvalidURL`，IPv6 目标任务无法执行。 | 将 IPv6 netloc 写为 `[ipv6]`（端口置于方括号外）；补 IPv6 adapter 和端到端 prepared-request 测试。 |

## 3. 测试覆盖审计

现有 `tests/test_id_generator.py` 覆盖同进程线程并发、顺序和单秒溢出；`tests/test_p0_phase_a.py` 覆盖 IPv4 pinning。两组共 44 项现有检查均无法覆盖“生产路径已不再调用生成器”、数据库自增回填、多进程、时钟回拨或 IPv6 URL 构造，故“全绿”不能证明上述 P1 风险已消除。

## 4. 方案与实现一致性

- **执行侧观测：**`执行侧观测优化完成后全面Review` 已正确列出 R3（外层异常阶段）、R4（状态枚举门禁）、R6（唯一约束迁移）和 R7（混合事件 fallback）未关闭；这些项仍不应被 Release Notes 或路线图暗示为完成。
- **发布计划漂移：**`4.1.0发布前变更梳理与文档收敛` 已在结论中标记 R2 已关闭，但发布顺序仍写“R2 关闭且门禁全绿后”。这不改变运行行为，却会误导发布操作者；应改为以 R3/R4/R6/R7 和本报告 CR-1～CR-3 为准。
- **ID 方案冲突（2026-09-20 用户澄清）：**用户明确目标是数据库自增 ID。当前代码仍在 cron\_infos、job\_log、job\_log\_event 和 ExecutionTracer 使用生成器；既有 OPT-P0-21 收敛设计也仅允许 cron\_infos 使用生成器，故现状同时偏离用户目标与既有收敛范围。修复前必须以用户目标更新正式设计和迁移验收矩阵。
- **设计覆盖缺口：**SSRF/DNS pinning 设计未把 IPv6 URL 语法作为验收项；应补充 bracket、端口和 HTTP/HTTPS 的矩阵。

## 5. 建议修复顺序

1. 先为 CR-1/CR-2 创建“生成器下线、数据库自增 ID”正式设计，逐列分析主键和引用列的独立语义、SQLite/MySQL 迁移、回填与回滚。
2. 按确认设计移除生成器生产调用，补自增回填和旧 50-bit ID 兼容测试。
3. 处理 CR-3：修复 IPv6 bracket，补 IPv4/IPv6、带端口和 HTTP/HTTPS 测试。
4. 再处理执行观测 R3/R4/R6/R7，并更新 4.1.0 发布计划的阻断清单。
