§1 · S1 + S2：登出 CSRF（GET 方法清 session）

1.1 问题

两个登出路由均接受 GET 请求清除 session，无有效 CSRF 保护：

路由文件行号问题
/rbac/logout app/rbac/views.py 247–253 虽有 @csrf_protect，但装饰器对 GET 请求 pass-through（设计如此：Safe methods 不校验 CSRF）
/logout app/main/views.py 1209–1212 仅 GET，无 @csrf_protect，无 @login_required

前端 _topbar.html:61 用 <a href="/rbac/logout"> 发起 GET 登出。攻击者可在任意页面嵌入 <img src="/rbac/logout"> 强制已登录用户登出。

1.2 根因

上游 xiaoniu_cron 无 CSRF 机制，登出是简单的 GET→clear→redirect。CronPilot RBAC 改造引入了 CSRF 体系，但登出因"不涉及写操作"被忽视。csrf_protect 的 Safe method pass-through 设计是正确的 REST 语义，但登出是状态变更操作，不应使用 GET。遗留 /logout 是上游残留路由，RBAC 改造后未移除。

1.3 方案

推荐方案：POST-only + 前端 JS 提交

变更说明
rbac/views.py logout methods=['GET', 'POST'] → methods=['POST']。GET 请求返回 405。
main/views.py logout + check_pass 删除遗留 /logout 和 /check_pass 路由（重定向 shim 已无用途，RBAC 登录流程完全替代）。
redesign/_topbar.html <a href="/rbac/logout"> → <a href="#" onclick="...submit logout form...">：动态创建 POST 表单 + CSRF token 提交。已有 change_password.html 的 pw-logout-btn 实现可参考。
v1 模板 admin_base.html 同步修改登出链接为 POST 提交（或 JS form.submit）。

备选方案（不推荐）：GET + 确认页

GET 到确认页 → 用户点"确认登出"→ POST 提交。多一步交互，体验差。

1.4 范围

文件变更
app/rbac/views.pylogout 改 POST-only
app/main/views.py删除 /logout + /check_pass
app/templates/redesign/_topbar.html登出链接 → JS POST
app/templates/admin_base.htmlv1 登出链接 → JS POST 或 POST form
app/templates/redesign/change_password.html已有 JS POST 登出实现，无需修改

明确不做：不修改 csrf_protect 装饰器的 Safe method pass-through 设计（这是正确的 REST 语义）。

1.5 风险

  • v1 模板的登出链接若遗漏修改，用户将无法登出 → 兜底方案：清浏览器 session cookie
  • 删除 /check_pass 可能影响上游引用 → 搜索确认无其他入口引用

1.6 验收

# 1. GET /rbac/logout 应 405
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:5001/rbac/logout
# → 405

# 2. POST /rbac/logout + CSRF token 应 302 → /rbac/login
# (先获取 CSRF token 登录，再 POST logout)

# 3. /logout 和 /check_pass 应 404
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:5001/logout
# → 404

# 4. 浏览器验收：点击退出登录 → 实际登出并跳转到登录页

§2 · S3：标签 CRUD 缺 scope 校验

2.1 问题

标签的创建、修改、删除路由（tag_create / tag_update / tag_delete）仅检查 @require_permission('user:manage')，无 scope 层面校验。按组管理员（Biz Admin）可通过修改 POST body 中的 group_id 越权操作其他组或全局标签。

2.2 根因

标签系统在用户管理/组管理之后开发，开发时 UI 层面用前端 JS 控制了 group_id 下拉选项（只展示用户所属组），误以为前端限制等于安全防护。同期的组管理路由（groups_edit）有 _actor_bypasses_scope() 检查，但标签路由开发时未对齐该模式。

2.3 方案

tag_create — 校验 group_id 归属

def tag_create():
    ...
    group_id = int(raw_gid) if raw_gid and raw_gid.isdigit() else None
    # ── scope 校验 ──
    if not _actor_bypasses_scope():
        actor_gids = session.get('group_ids') or []
        if group_id is None:
            return web_api_return(code=1, msg='非全局管理员不能创建全局标签')
        if group_id not in actor_gids:
            return web_api_return(code=1, msg='无权操作该业务组的标签')
    ...

tag_update / tag_delete — 校验标签归属组

def tag_update():
    tag_id = request.values.get('tag_id')
    # ── 先查标签归属 ──
    from datas.model.tag import Tag
    tag = db.session.get(Tag, int(tag_id))
    if not tag:
        return web_api_return(code=1, msg='标签不存在')
    if not _actor_bypasses_scope():
        actor_gids = session.get('group_ids') or []
        if tag.group_id is None or tag.group_id not in actor_gids:
            return web_api_return(code=1, msg='无权操作该标签')
    ...

tag_tasks — 读取也需 scope 限制

tag_tasks（GET 查询标签关联的任务）同样需要校验标签归属组，避免信息泄露。

2.4 范围

文件变更
app/rbac/views.pytag_create / tag_update / tag_delete / tag_rename / tag_tasks 加 scope 校验
tests/test_tag_scope.py (new)scope 校验单元测试

明确不做：不修改 tag_service.py（业务逻辑层保持纯净，scope 校验在视图层）。

2.5 风险

  • Seed Admin（绕过 scope）不受影响
  • 单组 Biz Admin 操作自己组的标签不受影响
  • 若 Biz Admin 无组分配（group_ids = []），无法创建任何标签 → 合理的安全行为

2.6 验收

# 1. 单测
python3 -m unittest tests.test_tag_scope -v

# 2. 浏览器验证（Biz Admin 登录）
# - 创建标签：下拉只显示自己组 → OK（前端已限制）
# - curl 篡改 group_id：应被拦截并返回错误信息
curl -X POST .../tags/create -d "name=test&group_id=999&csrf_token=..." → errcode=1

§3 · S4：注册审批 username 存储型 XSS

3.1 问题

registration_review.html 第 139 行和第 153 行，username 从 data-username 属性取值后直接拼入 bodyHtml HTML 字符串，传给 CpModal({ bodyHtml: ... })。CpModal 内部用 innerHTML 赋值。

攻击链路

  1. 恶意用户注册 username = '<img src=x onerror=alert(document.cookie)>'
  2. Jinja2 在 data-username="{{ req.username }}" 中自动转义 → data-username="&lt;img..."
  3. 浏览器解析 HTML 属性时解码 HTML entities → DOM 属性值为原始 <img src=x onerror=alert(...)>
  4. jQuery .data('username') 返回解码后的字符串
  5. 拼入 bodyHtml → innerHTML → 脚本执行

3.2 根因

开发者信任 Jinja2 自动转义提供了完整的 XSS 防护，但忽略了 HTML entity 的编解码链路：模板转义保护的是 HTML 解析阶段（防止属性值跳出引号），但 JS 从 DOM 读取后的值是已解码的原始字符串，再次插入 innerHTML 时等于"二次注入"。

同类风险存在于所有 data-* 取值后拼 HTML 的模式。

3.3 方案

推荐方案：HTML 转义函数 + textContent

在 registration_review.html 的 {% block js %} 中添加转义函数（或复用已有的 escHtml），所有 data-* 取值后拼入 HTML 的位置使用转义：

function escHtml(s) {
    var div = document.createElement('div');
    div.textContent = s;
    return div.innerHTML;
}

// 修复前：
bodyHtml: '...确认批准用户 <strong>' + username + '</strong>...'
// 修复后：
bodyHtml: '...确认批准用户 <strong>' + escHtml(username) + '</strong>...'

同类修复

文件行号问题
registration_review.html139approve bodyHtml 拼 username
registration_review.html153reject bodyHtml 拼 username
task_form.html247addTag() 用 innerHTML 拼 tag name
tags.html449confirmDelete() 拼 tagName 入 title

3.4 范围

文件变更
app/templates/redesign/registration_review.html2 处 username 拼 HTML → 加 escHtml()
app/templates/redesign/task_form.htmladdTag() 的 innerHTML → textContent + DOM API
app/templates/redesign/tags.htmlconfirmDelete() tagName → escHtml()

明确不做：不修改 CpModal / CpConfirm 底层（bodyHtml 参数设计就是接受 HTML，调用方负责转义）。

3.5 风险

  • 转义后 <strong>username</strong> 仍正常加粗显示 → 无视觉影响
  • 若 username 合法包含 &（极少见），转义后显示为 &amp; → 可接受的安全-视觉权衡

3.6 验收

# 1. 创建含特殊字符的注册用户
# username: <img src=x onerror=alert(1)>
# 2. 以管理员登录审批页面，点击"通过" → 对话框应显示纯文本，无 alert 弹窗
# 3. grep 检查
grep -n "innerHTML\|bodyHtml.*+.*data\|\.html(" app/templates/redesign/registration_review.html
# 确认所有用户输入都经过 escHtml

§4 · S5：API 装饰器 catch-all 异常泄露

4.1 问题

app/decorated.py:32-34 的 api_deal_return 装饰器在 except Exception 中返回 str(e)。当前仅 app/api/views.py:585 的 crons_legacy（/api/cron/add 旧路径兼容层）使用此装饰器。

4.2 根因

与 P0-3 完全同源。decorated.py 是上游 xiaoniu_cron 的遗留代码，P0-3 修复时搜索范围限于 main/views.py + rbac/views.py，未扩展到 API 层。

4.3 方案

# decorated.py 第 32-34 行
except Exception as e:
    import logging
    logging.getLogger(__name__).error('api_deal_return exception: %s', e, exc_info=True)
    return api_return(errcode=1, errmsg='服务器内部错误')

4.4 范围

文件变更
app/decorated.pycatch-all 返回通用错误信息，异常写入 logger

明确不做：不重构 api_deal_return 整体结构（遗留兼容层不值得大改）。

4.5 风险

极低。仅改错误分支的返回文案，不影响正常分支逻辑。

4.6 验收

# 1. 代码验证
grep -n "str(e)" app/decorated.py  → 无匹配

# 2. 全仓库验证
grep -rn "errmsg=.*str(e)\|msg=str(e)" app/ → 无匹配
