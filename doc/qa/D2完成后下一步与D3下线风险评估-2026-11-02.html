1. 结论与优先级

建议下一步开展 D3-0：任务下线的一致性与重试独立设计。D2 本批 Web/API 明确目标重试已交付，跨进程迟到写不属于已解决保证；本次未重新运行 D2 全量验收，引用其交付证据而非宣称新增验证。没有据此评估发现必须先推翻 D2 的结论。D3 已发现可复现的不一致，优先级高于继续增加启停 UI 或性能优化。低频操作不等于高概率故障；这里评估的是故障发生后的影响，不提供未经测量的发生概率。

2. 已读代码与问题准确性

  • cron_service.retire_cron_by_id 和 retire_cron_by_task_name 均先 remove_job，再 apply_retire 和 DB commit。Web /cron_retire 与 API /api/cron/retire 已检查权限及 Scope，但共享结果处理未采用 D2 的提交/调度事实分层。
  • 两个共享函数和 Web 路由在 status=-1 时提前成功返回。若后续改为先提交 DB，删除失败后重试可能被该提前返回挡住；不能只修改共享函数而忽略 Web 路由。
  • app/crons.py:cron_do 读取任务后进入 URL/签名/HTTP 执行链路，当前未见针对已下线 status=-1 的显式发送前拒绝。cron_check 中有残留调度清理，但不能把它当成每次发送前的保护或立即恢复保证；create_app 启动时调用 cron_check，也不足以承诺运行期间及时清理。

3. 隔离复现与证据

2026-11-02 使用现有内存业务库 fixture、独立临时 SQLite SQLAlchemyJobStore、实际 APScheduler/Flask-APScheduler。调度器全局暂停避免任务执行；创建 Job 后，对 retire_cron_by_id 的 DB commit 注入失败，随后结束事务并读取两个存储。结果：

{"job_absent_after_commit_failure": true, "db_status_after_rollback": 0,
 "original_database_used": false, "callback_executed": false}

复现结果 JSON。这证明暂停任务仍未下线但 Job 已被删除。运行中任务也经过同一顺序，但本轮没有实际发 HTTP 或开展运行中场景验证，不把类推冒充额外实测。

复现脚本位于 scripts/verify_cron_retire_baseline.py，运行命令：.venv-py311/bin/python scripts/verify_cron_retire_baseline.py；该脚本是评估工具，依赖仓库测试 fixture。它只创建独立临时 JobStore 与内存业务表，最后清理，不修改原开发库。

4. 根因与不能直接采用的修复

根因是跨存储操作缺少目标保存、外部副作用与恢复的统一约定；异常不等于删除未发生，重复下线也不等于调度一定已清理。简单交换为 DB 先提交虽然消除“提交失败但 Job 已丢”的路径，却会引入“已下线但 Job 残留”的窗口。当前执行链路缺少显式下线拦截，因此必须先设计发送前保护再设计 DB-first 移除，不能把交换两行作为完整修复。

发送前检查也存在检查之后与 HTTP 发送之间的竞态，不能声称终止已开始的请求或实现绝对零后续请求。若要求更强保证，需要另评估执行协调机制；本阶段仍以低频操作、清晰错误和可恢复状态为目标。

5. 下一步应形成的单问题设计

  1. 定义下线成功：持久化不可恢复的下线目标、原因、时间；正常调度移除按接口契约判成功，异常核实仅证明观察到的状态。已开始的任务执行不被撤销。
  2. 明确执行保护：对已下线任务增加发送前拒绝的设计；不得顺便改变暂停任务手动执行等其他语义。梳理日志/指标/结果枚举，若新增取值必须完整检查消费者；具体呈现方案留待正式设计确认。
  3. 统一提交与移除：保存冲突先报错且不操作调度；提交未知不盲目移除；提交成功后移除失败不自动撤销下线目标。正常返回不为确认成功额外查 JobStore。
  4. 显式清理重试：重复清理同一任务须有权限/Scope/版本约束；任务已下线仍可核实并清理残留 Job，存在则移除，不存在则清理已达成；停止态或读失败不能冒称已核实。原因、时间和成功审计不能因同目标重试重复覆盖。
  5. 覆盖入口：Web、API、共享两个函数统一，特别处理 Web 提前成功分支。自动一次性下线和其他系统路径列为影响面，逐一说明复用或豁免，避免无设计改变生命周期。

6. 分批建议与验收

D3-0 完成独立设计、页面结果 Before/After、接口假设验证和用户确认；D3-1 实现执行保护及服务契约；D3-2 接入 Web/API 与明确目标清理重试；D3-3 双后端、目标角色浏览器、复盘、文档与当前代码预览。实际实施批次以正式设计为准，本评估不授权实现。

  • 真实 SQLite/MySQL：提交失败、提交未知、删除前失败、删除已发生后异常、Job 缺失、停止/pending、后续版本变化及日志异常。
  • 正常成功零额外查询；已下线但 Job 残留可以重试；重复清理不恢复任务、不重复改原因时间、不过量写审计。
  • 使用受控 HTTP 测试服务或请求 spy，验证读取到已下线任务后不发送 HTTP，并明确已发出请求无法撤销的边界。
  • Web/API 正向、无权限、其他业务组、陈旧 Cookie 和 CSRF；真实浏览器填写原因→确认→结果→失败重试。回归 D1、D2、超时字段、下线不可恢复和调度生命周期。

7. 专业性、合理性、性能与风险

准确性：结论来自当前实现和真实 JobStore 隔离复现，区分已实测与待设计。合理性：聚焦下线链路一个问题，执行保护与重试都是其完整性要求，不追加自动后台协调系统。专业性：不把调度删除等同 HTTP 已终止，也不把 DB 下线等同 JobStore 清理成功。性能上优先使用执行链路已读取的任务状态作本地判断，重试是低频按 ID 查询；是否追加更晚的新鲜读取须在设计中权衡，不提前许诺零 IO 成本。主要风险包括延迟/已运行任务、跨进程迟到写、一次性生命周期，以及自动下线与人工下线语义混用。

8. 本轮边界

只完成只读代码评估和隔离复现，没有修复动作、未改业务代码、未重启或修复原开发库、未提交。文档检查：check_doc_completeness --check 通过（390 HTML 登记）；check_doc_links --check 通过（3015 引用、0 broken）；html_docs_to_markdown --check 通过。D2 后续仍可加强未覆盖的故障矩阵，但没有证据支持将完整重构或吞吐优化作为 D3 前置。

9. 执行保护：在哪里判断、如何阻断

当前任务入口先创建 pending 日志，进入 cron_do 后读取 CronInfos，再进行 URL 安全校验、签名和 HTTP 调用。建议设计以下两道保护；不是删除 Job 后才保护，也不把 APScheduler 删除当作终止执行。

  1. 入口保护：读取到的任务不存在或 status=-1，则不再进入 URL/签名/HTTP 链路，记录“未执行触发：任务已下线/任务不存在”。保留已入队和拦截记录，不能留下 running 日志或误报 HTTP 成功；不能借此把暂停 status=0 的手动执行规则一并改变。
  2. 发送前保护：URL 校验、参数准备可能耗时，任务可能在此期间下线。因此在每个实际 HTTP 发送路径之前，以独立只读连接读取最新持久化状态，读取完成关闭连接再决定是否发送；不能复用 SQLAlchemy identity map 中先前的 cif。读到已下线或不存在即拒绝发送；读库失败也不沿用旧状态放行，而是记录基础设施核验失败、不发 HTTP。
  3. 结束与可观察性：发送被阻断的日志记录必须进入明确终态，显示“未执行触发”及原因、任务/执行标识，不生成 HTTP 响应码。下线拦截与 DB 核验故障要区分；状态/原因、筛选、统计、告警和健康指标必须在正式设计中逐一对齐，不能只新增中文文案而其他页面仍判成功或永远运行中。

例一：任务已排队，管理员下线后工作线程才读取状态，入口直接拦截。例二：线程已完成入口检查，进行 URL 校验时管理员下线，发送前新鲜检查拦截。例三：HTTP 已发出或发送前检查之后才下线，不能保证撤销；页面必须说明“已发出的请求可能继续完成”。不使用跨 HTTP 请求持有 DB 锁来宣称绝对互斥。

性能：入口利用原有任务读取；发送前保护预计每次 HTTP 尝试新增一次按主键只读查询，显式承担这项成本，不能称为零 IO。查询失败选择不发送；不使用可能过期的本地缓存来代替这道下线判断。具体后端一致性、隔离级别和连接释放须以双后端测试验证。

10. 谁重试、重试什么、系统做什么

重试发起人：具有 cron:retire 且对该任务具有当前 Scope 权限的用户，或携带合法且具备相应权限/Scope 的 API Token 的客户端。不是所有能查看任务的人都能清理。D3 首期不增加后台无限重试、定时轮询或要求用户查库；系统先在当前请求中进行有限核实，仍有问题时提供明确重试入口。

  1. 用户首次填写原因并确认下线；系统校验当前权限、任务版本和原因，提交下线目标、原原因和时间。DB 提交结果不能确认时，不继续删除调度，显示“下线保存结果暂时无法确认，请刷新核实”。刷新后若未保存，可按新的确认流程再次下线；若已经保存，则进入清理流程，不重复写原因。
  2. 已确认下线保存后，系统尝试一次移除指定 JobStore 的任务。同步正常返回按契约确认本次移除完成，不再为正常成功额外查询；界面显示“任务已下线，调度记录已清理”。这不是撤销已发出请求的证明。
  3. 移除抛出不能证明结果的异常时，系统自动查询一次实际 JobStore。观察到已不存在，可提示“任务已下线，当前已核实无调度记录”；观察到仍存在或查询失败时，不断言原操作最终失败，提示“任务已下线，调度清理尚未确认，可稍后重试清理”。不恢复成运行/暂停。
  4. 用户点击“重试清理调度”，或 API 客户端重新发送明确的清理目标及服务端签名基线。系统重新校验当前身份、权限、Scope、任务下线状态和版本。任务或版本变化、基线篡改/缺失、凭据失效时拒绝，不把旧请求绑定到新目标。
  5. 重试先读取实际 JobStore：任务已不存在则返回“已核实无调度记录”，零调度写；还存在则移除一次，再按正常返回/异常核实规则反馈；服务停止或查询失败时不把 pending 中没有 Job 当作持久化已清理。
  6. 重试不执行 apply_retire，不更新原原因、retired_at，不重新启用任务，也不重新注册。实际清理操作记录操作人、任务、目标版本、时间和结果；已不存在的 no-op 不重复生成“首次下线成功”的审计记录。

明确目标“确保此已下线任务不存在于 JobStore”适合重试：重复检查发现已不存在就不再写。与取反操作不同，不会第二次又启用任务。API 继续用已认证入口，具体重试头/字段与 Web 入口命名在正式设计中冻结，届时按仓库规范标注兼容性，不能直接假设 D2 的 token 可以用于下线清理。

晚到的并发旧写仍可能在检查之后重新注册 Job；版本检查不能冒称调度 fencing。执行保护能阻断读取到已下线状态的执行请求，重试负责清除残留项，但不承诺永远不再出现 Job。自动一次性下线和启动时 cron_check 的现有行为必须单独列出影响分析，不把它们等同于首期新增的后台恢复能力。

11. 用户到底看到什么

系统事实反馈示例可执行动作
下线目标与移除均已确认任务已下线，调度记录已清理。已发出的请求可能继续完成。返回列表/查看执行记录。
DB 保存未确认下线保存结果暂时无法确认。刷新核实当前任务；不能显示已下线，也不先删 Job。
DB 已下线，移除结果尚不能确认任务已下线；调度清理尚未确认，可稍后重试清理。显示“重试清理调度”，保留原目标签名；由系统查询，不要求用户查库。
稍后清理发现已不存在任务已下线，当前已核实无调度记录。成功结束，不重新移除或改下线原因。
调度服务不可用任务已下线，暂时无法核实调度清理。保留稍后重试，不自动恢复任务。
发生并发变更或当前权限不允许任务已有后续变化，请刷新确认／当前无权执行此操作。停止旧重试；重新加载，权限恢复前不能操作。
残留调度触发但被执行保护拦截执行记录：未执行触发，任务已下线；未发送 HTTP。用户可查看拦截记录，有下线权限者可清理调度。

页面建议在已下线信息卡中保留原原因/时间，并显示独立的“调度清理结果”区域及必要的重试按钮；列表的“已下线”仅表示业务目标，不能代替实时调度核实。初次进入页面若未查询 JobStore，显示“尚未核实”，不能凭 status=-1 伪造“清理成功”。不需要新增永久同步状态字段才能展示当前一次查询结果；但刷新和结果过期不能继续冒充当前事实。

这些是下一份 D3 正式设计的交互与验收要求，还没有实现。正式稿应给出页面 Before/After、确认取消与重复提交保护、HTTP/API 返回契约、日志分类和双后端测试，之后再进入实现。
