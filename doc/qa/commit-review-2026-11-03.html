1. 审查发现（按严重程度）

R1 · P1 · SQLite 任务编辑与启停仍允许撤权在途请求完成写入

定位：app/services/cron_edit_concurrency.py:148–156、app/services/cron_status_apply.py:80–81,109–114。两者通过 FOR UPDATE 重读 actor，但没有用户编辑已接入的 SQLite 物理写入保护；任务 edit_revision 不能证明 actor 权限未发生变化。

任务编辑：遗留问题再次确认。执行仓库现有 task probe，DELETE/WAL 两种模式均由独立进程在 actor 已读取后提交降权，原保存仍返回 updated，最终 actor=viewer、说明=requested。任务的 SQLite 原子保护设计仍为待确认，save_task_edit 尚未接入保护，因此该结果与其设计状态一致，不能声称用户编辑修复已关闭整个 SQLite 条目。

启停：本轮补充同类实证。在临时文件 SQLite 中，服务读过 Operator 后、读组关系前，另一个 engine/connection 将其改为 Viewer 并提交。随后调用真实 save_status 与真实 APScheduler，任务从暂停写为运行，真实 Job 由暂停恢复。调度器全局暂停防止任何实际执行；只替换模块中的调度器对象为本次隔离实例，没有替换权限或保存逻辑。

{"independent_revocation_committed":true,"ok":true,"current_role":"viewer","stored_status":1,"real_job_resumed":true}

实证证明服务内部撤权窗口及真实 Job 状态改变，不冒称已重放完整 HTTP 攻击链；没有证实 MySQL 行锁下相同交错成立。D2 文档已经保留未覆盖全部撤权竞态的边界，本轮将其变为具体反例。

建议：任务编辑按待确认设计处理锁外 URL 校验和受保护重算；启停另明确保存边界与提交后外部副作用的授权时点。不要将任意未来撤权都定义为取消已经合法提交的操作；本例撤权发生在本次业务写入前，且原请求没有保护其已读授权。新增与真实撤权入口配套的竞争矩阵，而非只测试保存调用前已降权。

证据：任务双模式结果 · 启停结果。复现入口：

R2 · P2 · 启停提交后的摘要生成会隐式读取，读取失败逃出错误契约

定位：app/services/cron_status_apply.py:122–123。commit 成功后通过 status_config(task) 生成重试上下文；当前 Session 在提交后使 ORM 属性过期，该函数访问时间字段触发重新 SELECT。该调用位于提交异常分类和调度异常分类两个 try 之外。

本轮内存库复现：真实提交状态后，在首次 SELECT cron_infos 时注入读取失败，观察到异常直接抛出、状态已经持久化为 1、调度尚未调用、上下文为空。生产 Web/API 都传入 context，因此并非仅直接服务的无效参数组合。

{"commit_completed":true,"post_commit_read_failed":true,"exception_escaped":"RuntimeError","stored_status":1,"scheduler_apply_calls":0,"retry_context":{}}

影响：调用方可能得到通用异常或 HTTP 错误，而不是“目标状态已保存、尚未应用/无法完成核验”的受控结果。错误发生在调度写入前，不能误称调度调用已失败或已成功。该实验注入固定读取异常，未模拟真实网络断线或所有 DBAPI 错误种类。

建议：提交前从同一快照固定摘要及签名所需纯值；提交后的所有可失败操作纳入明确分类。单纯将读取异常吞掉再继续调度不符合设计。防护用例应在真实 after_commit 后拦截首次读取，断言保存事实、调度调用次数、返回语义和重试能力；现有 check_version 读失败用例没有经过本分支。

证据：结果；可执行：
