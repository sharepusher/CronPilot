# 统一错误处理方案文档交付失误深度复盘

日期：2026-09-23 · 版本：**v1.1** · 状态：**已复盘** · 范围：P0 统一错误处理方案、管理平台 REST API 后续方案及其交付规范

**复盘结论：**本次不是单一格式疏漏，而是“需求语义—架构边界—文档结构—交付链接—浏览器可验证性”五层交付契约没有在首轮形成闭环。后续已将关键约束写入文档规范，但自动门禁仍需继续建设。

## 1. 事件概览与影响

| 阶段 | 出现的问题 | 用户可见影响 |
| --- | --- | --- |
| 方案初稿 | 没有先把外部 API、管理平台 Ajax、SSR 导航/form、scheduler 分层。 | request\_id 是否必填、是否服务端生成、是否覆盖 HTML 路径反复摇摆。 |
| 语义修订 | 先后出现“一律忽略入站 Header”“缺失服务端生成”“缺失也必须报错”等互相冲突的表述。 | 用户需要反复纠正请求方责任、请求/响应同 ID 和 API 字段契约。 |
| 文档交付 | 版本记录先放在文档末尾；交付回复使用了内部 Markdown 链接和路径，而非用户要求的可复制完整 URL。 | 用户无法在打开文档前确认版本，也无法稳定复制链接到浏览器。 |
| 浏览器验证 | 没有在首次交付前验证本地 URL 的实际跳转；浏览器策略阻止自动打开时才被动说明。 | 用户看到的仍可能是旧标签页或无法直接访问的地址。 |

**交付影响：**虽然最终设计文件、Markdown 同步和索引检查通过，但交付过程不满足“用户可直接确认、复制、打开和识别版本”的完整标准；这属于流程质量事故，不应以“文件已经写入”视为完成。

## 2. 根因分析：从行为层追溯

### 2.1 首要根因：没有先建立交付契约矩阵

开始分析时直接进入方案内容，先讨论 Header、trace 和 JSON 信封，后补充调用方、SSR、浏览器和文档交付边界。缺少一张先行矩阵：

| 维度 | 本应先固定的答案 | 实际表现 |
| --- | --- | --- |
| 传输类型 | 公开 REST/JSON、管理端 JSON、SSR 文档、scheduler 分开 | 一度把全局 HTTP 请求当作同一种来源 |
| request\_id 责任 | 外部值可重复；本端生成的异步/调度值由本端保证 UUID v4 | 先用统一 fallback 覆盖所有来源，后被纠正 |
| 缺失行为 | 已登记 REST/JSON 端点缺失即 400；SSR 排除 | 先设计为服务端生成，再改为缺失报错 |
| 文档输出 | HTML/MD、版本记录位置、完整 URL、浏览器可达性 | 只验证文件和索引，未验证交付形态 |

### 2.2 次要根因：把“内容正确”误当成“交付完成”

工作重心放在 APIFlask、OpenAPI、ContextVar 和错误信封等专业内容，形成了“方案技术上越来越完整”的错觉，但没有把用户实际验收动作作为同等级目标：打开哪个 URL、看到哪个版本、复制哪一行、如何确认 HTML 与 MD。结果是技术内容改对了，交付接口仍不合格。

### 2.3 组织性根因：规则存在，但没有在行动前转化为检查表

仓库已有设计先行、HTML/MD 同步、文档索引、复盘和可验证环境规则；但这些规则是分散文本，没有形成“文档交付前一页式检查表”，也没有门禁检查“版本记录位于顶部”和“回复中的 URL 是纯文本完整地址”。因此规则在事后修复中才被逐步补齐。

## 3. 逐项问题复盘

| 问题 | 直接原因 | 深层原因 | 应采取的控制 |
| --- | --- | --- | --- |
| request\_id 语义反复 | 先写实现形态，后问来源和责任 | 缺少传输分层和“谁生成、谁负责唯一性”字段 | 设计开头必须有来源矩阵和反例；缺失/非法/SSR 三类负向用例先写 |
| 把管理平台等同纯 REST | 只看到 Ajax/API，没有先盘点 SSR 导航和原生 form | 没有以路由清单而不是技术偏好判断架构事实 | M0 路由盘点先于管理端 REST 化；每条路由标注 JSON required 或 SSR excluded |
| 版本记录放末尾 | 把版本历史当附录，而非文档入口元信息 | 缺少“读者打开第一屏应知道什么”的文档信息架构检查 | 版本记录紧跟标题/元信息/确认门禁；当前版本首行且与标题一致 |
| URL 无法复制/跳转 | 使用了内部 Markdown 路径链接和尖括号形式 | 没有区分应用渲染链接与浏览器地址栏可复制 URL | 回复只输出百分号编码的完整 URL 纯文本代码块，一行一个，并验证浏览器行为 |
| 浏览器仍显示旧页 | 只写文件，没有确认当前标签页是否刷新到新版本 | 未将“用户实际看到的页面”纳入文档交付验收 | 交付前打开/刷新 HTML URL；若安全策略阻止，必须记录阻塞并提供可复制地址 |

## 4. 测试与门禁漏洞

| 现有检查 | 能发现什么 | 不能发现什么 | 补强方向 |
| --- | --- | --- | --- |
| `html_docs_to_markdown.py --check` | HTML/MD 是否同步 | HTML 内容是否符合信息架构、版本记录是否置顶 | 增加文档元信息结构检查 |
| `check_doc_completeness.py --check` | 索引登记、链接完整性 | 交付回复是否给出完整 URL、浏览器是否能打开 | 增加交付清单静态检查；浏览器验证保留人工/自动化步骤 |
| `git diff --check` | 空白字符问题 | 语义边界、版本位置、链接格式 | 不能把通用 diff 检查误当文档验收 |
| 人工 Review | 可发现专业语义问题 | 没有清单时容易漏掉基础交付项 | 使用固定交付检查表，并在最终回复前逐项勾选 |
| 浏览器打开 | 真实页面可达性和版本可见性 | 未执行时完全没有证据 | HTML 交付必须记录打开结果、当前 URL 和页面版本 |

## 5. 修复与当前状态

1. P0 方案已改为 REST/JSON 专属 request\_id 契约：缺失/非法 400，SSR 排除。
2. 新增管理平台渐进式 REST API 后续方案，明确 Session/CSRF/RBAC 与外部 Token API 隔离。
3. 两份设计均已补顶部版本变更记录和交付契约矩阵，当前版本分别为 rev.7 和 v0.3。
4. HTML/Markdown 已同步，索引已登记，文档完整性检查通过。
5. `cronpilot-documentation.mdc` 已新增完整 URL、纯文本代码块、百分号编码、浏览器可达性、版本记录置顶和契约矩阵前置规范。
6. 本地浏览器自动跳转曾被安全策略阻止，已将其定义为交付阻塞条件，不再假装“已打开”。

## 6. 预防方案与落地计划

| 优先级 | 措施 | 落地位置 | 验证方式 |
| --- | --- | --- | --- |
| P0 | 文档顶部元信息模板：标题、版本、日期、状态、确认门禁、版本记录 | `.cursor/rules/cronpilot-documentation.mdc`；后续设计模板 | 人工检查 + 静态脚本断言版本记录在首个正文章节之前 |
| P0 | 交付 URL 固定为百分号编码完整 URL 的纯文本代码块，一行一个；HTML/MD 成对 | 同上；交付回复检查表 | 抽取最终回复中的 URL，执行 `test -f` 或 HTTP 状态检查 |
| P0 | 设计开头先写传输/来源/唯一性/缺失行为矩阵 | 所有 API、错误处理、架构设计 | Review 未通过矩阵不得进入实施批次 |
| P1 | 新增文档结构门禁：当前版本与标题一致、版本记录置顶、HTML/MD 同步 | `scripts/check_doc_completeness.py` 或独立 docs lint | `python scripts/check_doc_completeness.py --check` |
| P1 | 交付回复生成器/模板，禁止仅输出内部链接格式 | 文档交付工具或固定回复模板 | 单元测试覆盖中文文件名 URL 编码、HTML/MD 配对和纯文本输出 |
| P1 | 浏览器验收记录当前 URL、页面标题和版本文本；策略阻止时记录原因 | 交付闭环记录 | 浏览器状态 + 页面断言，不以文件存在替代打开验证 |

## 7. 关闭条件

本次复盘只有在以下条件全部满足后才关闭：两份设计顶部版本记录和标题版本一致；HTML/MD 与索引检查通过；文档交付规范包含完整 URL 纯文本格式；至少一次交付回复按新格式提供 HTML/MD URL；文档结构门禁或等价人工检查能够复现上述断言；后续 API 设计继续保留来源矩阵和 SSR/REST 边界。
