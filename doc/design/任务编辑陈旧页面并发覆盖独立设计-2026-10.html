1. 问题与根因

示例：甲打开页面时说明是 A；乙保存为 B；甲只修改超时，提交的完整表单仍带旧说明 A。当前 update_cron 的赋值逻辑把说明也写回 A，乙的修改丢失。第一个问题的 no-op 比较只判断目标是否与当前配置相同；此时并不相同，仍会进入全量写入。

现有隔离基线已证明顺序提交也能覆盖，无须大量用户或高并发。代码依据是 app/main/views.py:cron_edit 和 app/services/cron_service.py:_edit_cron_web_result/update_cron_with_outcome/apply_normalized_to_model。当前 CronInfos 没有并发版本字段，updated_at 不是原子版本：同一时刻可多次修改，关系变化也未必更新它。

根因是请求未携带可信原始基线，字段出现被当作修改意图；比较与写入缺少原子条件。仅 POST 时重新 get、只加行锁或前端 dirty 标记，都不能判断用户看过什么。

2. 方案选择与边界

推荐：可信字段基线 + 三方比较 + edit_revision 原子条件更新。字段比较允许合并无关并发；原子版本条件防止“比较通过后又被别人修改”的竞态。整资源版本不匹配就直接拒绝也是合理的保守方案，但会拒绝本可安全保留的无关字段更新，因此本稿选择三方比较。

GET 读出完整一致的展示快照后结束请求事务，用户思考期间不持锁。保存时才开短事务；数据库当前事实不能复用早期 identity map 或 MySQL 旧读快照。服务明确拥有保存事务；只读入口预检与写边界之间不能存在待写的其他业务对象，不能无条件 rollback 调用方事务。

本批允许为并发保护新增 edit_revision，并修改必要的其他写入口以共同维护版本；不新增调度状态表或后台应用者。不改变管理员业务权限。日志与调度仍有既有独立失败边界，不能因新增版本就宣称后三项解决。

2.1 是否必须新增字段：时间戳与无新列替代方案

决策过程：并发保护并非理论上必须新增字段；比较现有时间戳及替代锁协议后，用户已明确选择新增 edit_revision 并确认实施。更新时间戳保留原有含义，下表仅作为备选方案的历史比较。

代码证据：datas/utils/times.py 的 utc_now_hms 返回 int(time.time()*10)，是百毫秒而非毫秒/微秒；1000.01 秒和 1000.09 秒两次调用均为 10000。app/services/cron_service.py 的普通编辑会更新 updated_at，但 toggle_status、apply_retire 与自动下线 fallback 不保证更新该列；tag_service.delete_tag 会删除 TaskTag，却不更新关联任务的 updated_at。因此“时间相同”不能证明配置/状态/关系没有变化，last_operated_at 也不是所有写入统一维护的版本。

路径可行性与必须承担的责任
直接比较现有 updated_at本项目当前不可作为唯一并发裁决：同精度碰撞、未覆盖关系/状态变化；即使提升时间精度，也不自然获得唯一或单调保证。检查时间后无条件写入同样有竞态。
重新定义 updated_at 为严格递增并发戳技术上可行，但必须在 DB 原子地保证严格变化、覆盖全部写者并条件更新。简单用当前时间不够；强行 old+1 会将真实墙钟时间与逻辑版本混合，显示时间/排序等消费者须核验。省一个列不等于省掉协议改造，也不能悄悄改变既有字段语义。
无新列：可信基线 + 三方比较 + 事务锁合理替代。MySQL 在短写事务中锁定任务及必要关联/授权实体，读取最新 C，比较并仅写有效差异，完成后释放；关系-only 修改/删除等所有写者遵守相同父任务协调协议。SQLite 采用能在读取后保护后续写入的写事务策略，分别验证其数据库级写竞争与超时。不能用 SQLite 的 with_for_update 假定已有行锁。
无新列：以当前字段值构造原子条件更新标量字段可以用原值作为更新条件；需处理 NULL、文本的数据库比较语义、请求字段范围与受影响行数。关系集合仍要锁或等价原子保护，单条任务 UPDATE 不能自动保护 TaskTag。按 task_id 主键定位后比较字段，不必然破坏索引，但长文本比较和 SQL 复杂度需评估。
独立 edit_revision（正文推荐）职责单一、条件简短，不依赖时钟；代价是新增列与迁移。仍必须覆盖所有相关写者，不能靠新增列自动解决权限或关系并发。

选择依据应是协议复杂度、双后端写竞争和维护成本，不是“专业方案一定要有 version 字段”。无新列方案可满足本问题目标，但需要完整设计和验证；当前 updated_at 原样复用则不能满足。无新列按当前值比较通常不记录 A→B→A 的中间修改历史，若业务要求任何中间修改都使表单失效，需另有可靠版本/历史证据；普通三方比较本身允许当前值恢复为 O 后继续合法保存。

3. 基线、规范化与字段意图

O 是页面打开时的可信原值，R 是提交目标，C 是保存时的当前值，E 是当时可编辑范围。I 为在同一 E 下 O 与 R 的差异；有效差异由 I、C、授权及业务校验共同确定。未出现在 I 的字段不赋值、不重写关联，必须保留 C。

token 使用独立 schema/salt，绑定 actor_user_id、task_id、原始 revision、编辑范围和每个比较单元的基线摘要。URL/body 可能带凭据，不能把原值明文放入签名 token；采用带服务端密钥与字段/主体域分离的 HMAC 摘要，外层再签名。仅 SHA256 不能保护低熵内容被猜测。客户端原值只用于提示；服务端依据已签摘要重算 I。输出长度、类型、字段集合严格验证，不接受未知字段混入 ORM。

签名保护完整性，不是加密、授权或新鲜度；前端已可见的原值不额外写入日志、控制台、localStorage。密钥轮换或 schema 变动使旧表单需要刷新；token 不是幂等键。原值不因校验失败、并发错误或确认回显而改变，只有用户明确重新 GET 才建立新基线。

比较单元可写/缺省与规范化并发粒度与副作用
任务名称Web 只读，以 task_id 定位；篡改拒绝。API 按既有任务名定位，命名协议本批不重设计。不可借 readonly 当服务端保护。
task_keyword当前有写权主体；沿用 trim/长度。Web 缺失必填拒绝，非空字符串。独立单元；只改说明不覆写他人超时、URL、标签或启停。
调度方式与全部时间字段按当前 mode 规则规范化；明确空串/NULL，空 Cron 不等于 *，不推导复杂语法等价；缺字段不悄悄当用户清空。耦合整体比较；切换一次性/Cron 不能拼出两个时点的混合策略。完整候选需再次校验未来时间与调度合法性。
URL + 方法 + Bodytrim、方法大小写、JSON 对象沿用现有契约。Body 文本比较，不改变 JSON 排序/数值语义；GET 的已有 Body 不隐式删除。请求配置作为耦合单元保守比较，防止把别人新 URL 与旧 Body 组合。日志只给字段名和安全摘要。
timeout_sec空为 NULL，整数 1–120；NULL 不等于显式 5。独立单元；并发修改说明时可保留另一方新超时。
scope_type + group_id + 任务标签关系GLOBAL 零关联，GROUP 恰好一有效组；标签按既有 trim/lower 去重集合与命名空间。空标签明确清空，缺标签不能按清空猜测；异常多组/孤立标签拒绝治理。范围/标签绑定作为耦合单元。组切换需当前授权和目标组标签解析。没有关系意图时完全不运行 sync_task_tags/组删除重建，保留当前完整关系。
status 与显式恢复命令普通配置不提交 status 覆盖值；不改变当前启停。恢复必须是显式命令意图，已下线拒绝。配置编辑遇到并发暂停可保留暂停；遇到下线禁止保存。恢复与状态比较使用基线，冲突不隐式重启。
时间、操作人、认证凭据系统维护字段不得客户端绑定；凭据不属于任务表单白名单。真实变化才更新编辑元数据；配置版本不触发用户 Token/认证版本。

共享标签名称属于 Tag 实体元信息，不等于 TaskTag 关系。未编辑标签时只保留当前关系 ID，不能按旧名称重新创建标签；编辑标签时须读取并锁定解析用的当前 Tag，验证名称/命名空间。标签强制删除会改关系，必须参与任务版本协议；标签说明修改不影响任务配置。这样避免把每次公共标签改名都变成对全部任务的无谓重写。

4. 三方比较与原子保存

条件（针对有意图的单元）处理
C=O，且 C≠R候选写为 R。
C=R该单元已等价完成，不重复写入或副作用。
C≠O 且 C≠R冲突，整体拒绝本次需原子完成的编辑；不能部分保存另外几个字段。
无修改意图保持 C，仍校验当前对象权限与业务不变量。
原始基线校验 → 当前授权与可编辑范围核验 → 读 C 与当前 revision
  → 计算 I / 三方比较 → 构造最终候选并完整校验
  → 无有效差异：no_change 或 already_applied，零业务 DML/变更日志/调度操作
  → 有有效差异：按 task_id + 读到的 revision 原子更新所需字段、revision=revision+1
  → 条件命中后，在同一事务内处理真正变化的关系和编辑元数据 → 提交
  → 条件未命中：回滚整个尝试，重新读 C 并重新比较；最多重试一次，仍竞争则返回 conflict
  → 结果不确定：commit_unknown，不自动重复业务写入

CAS 只用于有效变化，不为 no-op 写入版本“抢锁”。关系-only 改变也必须先在同一事务中推进父任务 revision；任意步骤失败回滚关系与父行。MySQL 可辅以短行锁，SQLite 以原子条件更新为裁决，不能认为 with_for_update 在 SQLite 生效。重试必须重新授权/重读，不能盲用旧候选。

标签新建、关系删除、SQLAlchemy 自动 flush 均不能在 CAS 之前偷偷写入；解析目标标签先只读，确认版本获胜后在事务内创建需要的标签，保留既有唯一性冲突处理。发生冲突后不得注册 job 或追加成功变更日志。当前配置日志仍有第二次提交的问题，单列问题④；本批不把外部日志和调度声明成原子事务。

MySQL 保存前读必须是最新事实。锁/条件更新之后事务终态必须明确结束：no_change、already_applied、conflict、校验拒绝、异常均需按所有权释放；不能只靠 HTTP teardown。真实锁验证需在原请求上下文仍存活、清理前用独立连接探测，并包含“故意不结束事务”的反向校准，防止测到框架清理后的假释放。

5. edit_revision 与所有修改者

新增建议列 cron_infos.edit_revision：非空 BIGINT、服务端默认 0；新任务初始 0，已有任务补列后也从 0 开始。它只区分启用协议后的提交，不声称反映迁移前修改次数。每次真正改变任务配置/状态/关联的原子事务推进一次；不把 updated_at 或调度 generation 复用为该语义。按主键定位，revision 不需要单列索引。

本批只加列，不删/迁移/合并旧字段：status 仍表示生命周期，updated_at 仍表示配置编辑时间，scope_type 与关系表仍保持原语义；revision 不替代其中任何字段。采用 business_db_backend 分 SQLite/MySQL 幂等加列与约束检查，空库/存量/重复执行/失败拒启均演练。不支持携带旧写服务的进程与新协议混跑；升级停旧进程、迁移、启动新进程。回退到旧写服务时必须停止对“并发保护有效”的声明。

入口本批必须承担的并发责任
Web 编辑、API 同名 upsert、直接 update_cron统一任务写协议；Web 必带可信基线。API 保留原全目标 upsert 意义，但必须新鲜读取、原子推进版本，保护 Web 不被其绕过。API 没有历史客户端基线，不能宣称 API 调用者间也获得相同旧页面保护；增设 API 条件字段另行设计。
toggle_status、人工下线与补偿写回实际状态变化推进版本；补偿也属于新修改，不得无条件覆写后续状态。至少条件校验“仍是本次写入的版本”，过期则停止覆盖并记录明确结果。这里只保护 DB，并不完成调度恢复设计。
CuBackgroundScheduler / CuGeventScheduler 自动下线和 fallback主路径与异常 fallback 都须按当前版本/状态更新，避免只修主分支。按条件推进任务版本，过期结果不能使后来修改的任务误下线；一次性已开始执行的取消保证仍不在本批。
sync_task_tags、组关系写入、标签强制删除关系与父 revision 同事务。批量影响任务时按 task_id 固定顺序协调；未编辑关系完全不重建。
Tag 改名、ResourceGroup 元信息和删除元信息改名不能让旧页面重新创建旧关系。编辑所依赖的当前实体需受相应行锁/原子条件保护；删除组若改任务 Scope/关系则推进任务版本。P2-0 须搜索实际组删除入口和豁免证据，未完成清单不进入实现。
重新调度/现有对账若只改 JobStore 不影响配置，本批不假造任务版本更新；若路径改变状态则纳入协议。调度器侧的相互覆盖仍由问题③处理。

当前授权还涉及 actor 的角色、启用与业务组绑定。保存锁定主体并读取当前绑定，绑定修改者也必须遵守主体锁或等价条件协议；仅锁现有 UserGroup 行不能防止新关联插入。全局锁顺序需在 P2-0 明确并核对 RBAC 已有写者。不能因目标版本正确就漏掉 actor 已降权的竞态。

6. 前端、失败回显与结果

前端延续问题①的本地 no-op 预检，不向浏览器增加长事务。表单新增唯一 edit_snapshot hidden 字段，检查与其他 visible/hidden 不重名。预检比较需排除 token 与 CSRF 等非业务字段。后端始终以验签后的 O 重算意图，不信任 JS dirty 标志。

合法校验错误/冲突显示保留输入 R，并保留原 token T0；不把 DB 当前值悄悄当新 O。请求仍可对同一基线重试，但不可通过刷新 token 隐式覆盖。非法 token 或权限范围改变只能显式重新加载。重新加载会放弃未保存输入，使用现有 CpConfirm.show 的 body 属性提示；不显示对方不可读范围的值、URL/body 凭据或原始异常。

outcome页面 / 提交行为
no_change / already_applied零变更副作用；留页提示“无需保存”或“目标值已存在，无需重复保存”，不重置原始基线。
conflict“任务已被修改，本次未保存。请重新加载后确认。”保留当前输入，提供重新加载；本次零部分保存、零成功日志/调度。
updated完成有效字段写入后走现有成功行为；不能附带“调度已确认生效”的新承诺。
failed / commit_unknown分别明确未保存与结果待核实；未知不能自动重发。不得把同库 commit 不确定和既有调度失败混成一个“保存失败”。

Ajax 与原生回退语义一致。原生失败可直接渲染输入与 T0，不将含秘密的整份表单置入 URL 或客户端 cookie session；当前安全重定向/CSRF 与防重复提交保留。任何 API 公共字段或语义改变须回到设计补充兼容和发布说明；本稿不新增 API 响应字段。

8. 独立分批、验收与停止条件

批次交付与门槛
P2-0 写协议校准完整配置/关系/状态赋值点与 actor 授权修改清单，固定锁顺序、revision 原子表达式、双后端加列与 CAS 实验；对照已确认规范。发现未参与写者不得开始 P2-1。
P2-1 基线与意图token 精确 schema、绑定、HMAC 无秘密副本、完整单元比较、回显 T0 连续、前端 no-op 兼容。合法表单与坏 token 都有否定用例。
P2-2 原子写入与全部写者当前授权、CAS、有效字段/关系保存；API、状态、系统下线和关系修改参与同协议。P2-1/2 同发布单元，不部署半套并发保护。
P2-3 页面与完整验证两会话浏览器、原生/Ajax回显、MySQL双连接与SQLite写竞态、锁生命周期、第一项回归、迁移和可验证本地环境；修复复盘后交付。
  • 同字段：O=A，乙提交 B，甲提交 D → conflict，DB 保留 B，甲其他字段不部分落库。
  • 无关字段：乙改说明 B，甲只改超时 → 保留 B，仅写超时及必要元数据；组/标签零 DML。
  • 等价完成：乙已设为甲目标 → already_applied，不重复日志/job操作；部分单元已完成而另一单元可写时只写有效变化。
  • 比较后竞态：在 CAS 前让独立连接完成另一次写入，0 行命中后重读重新比较；反复竞争有界返回，不无条件覆盖。
  • 关系：组迁移/标签增删、公共标签重命名/删除、异常多组、actor换组；未编辑关联不被旧完整表单重建。
  • 生命周期：甲编辑中乙暂停/下线、系统自动下线与 fallback、旧补偿写回；暂停不得被默认恢复，下线优先拒绝。
  • 安全与回显：缺/坏/旧 schema、主体不符、当前降权、原生多次错误仍同 T0、无明文秘密副本/错误泄露；重新加载后才换 token。
  • 第一项：按钮/回车无变化零 POST，服务 no-op 零 DML/日志/scheduler；新增 token 不造成永远“有变化”。
  • 后端：SQLite/MySQL 双后端迁移、CAS、独立真实连接释放探针与负向校准；不能只测最终值或 teardown 后的锁。

9. 准确性、合理性、性能与风险

证据说明当前丢失更新真实存在，但不量化线上发生率。版本条件更新与可信三方比较是成熟机制；二者分别解决用户意图和数据库竞态，不能互相替代。比起仅拒绝所有版本变化，本稿允许保留无关修改，代价是比较与写者协议更复杂。

正常请求按 task_id 主键定位，读字段/小型关系集合后在内存比较；新增一个 BIGINT 字段和有效变更时的一次条件写，不做全表 SQL 运算、不引入全局缓存。无意图维持零写；真实变化增加短事务/锁开销。批量标签删除需按其影响任务数量处理，不假设任务总量小；P2-0 应实测影响规模、执行计划和锁等待，不给未测试的性能收益比例。

风险是漏掉写者、原 token 被错误重签、非意图字段仍进入全量 apply、actor/关系并发保护不完整，以及把版本计数误认为调度一致。没有全部写者参与就不能上线声称解决。问题③④⑤仍分别设计；本稿不承诺取消已运行任务，也不把当前 best-effort 日志当强审计。

11. 修复复盘与当前验证状态

  1. 定位：任务编辑页面在他人提交后，旧表单提交可能覆盖其已保存字段。

  3. 测试漏洞：原有测试重视保存后字段，未验证两个独立编辑者的先后提交与零部分写入。
  4. 修复：新增 edit_revision 和绑定主体的签名基线，按字段单元比较并在写入时执行版本条件校验。

12. 后续问题评估（2026-10-30）

按用户要求继续逐项独立设计。建议下一项先研究“暂停任务编辑后先注册再暂停的窗口”（综合背景中的问题⑤）：当前 Web 路径在提交配置后依次调用 register_cron_job 和 pause_job；前者通过 scheduler.add_job(..., replace_existing=True) 注册，未显式传入暂停运行时间。两次调用之间可能存在可触发窗口；不能把已有库实验当作已发生线上误执行。Web 暂停失败会报告“配置已保存，调度更新失败”；旧共享更新路径仍捕获暂停异常并继续记录成功，不可混为相同结果。

独立方案应先核对实际 APScheduler 包装器、持久 JobStore、自定义扫描器和 Web/API 共享写入口，验证创建时指定暂停状态的实际效果；明确已有执行、并发启停、一次性任务和异常返回的边界，设计测试与回滚。暂停窗口收窄不等于解决问题③的跨资源持久恢复，也不等于问题④的业务与审计原子性。若验证发现独立修复无法保证入口一致，则在设计中先阐明依赖，不能据此宣布可直接实施。

问题③仍存在配置已提交而 JobStore 旧、缺失或结果未知的可能；Web 的明确提示改善了结果表述，但未提供持久恢复。问题④中配置已提交后才追加操作日志，日志失败或调度先失败可能缺少对应成功变更记录；应另行决定强审计策略与事务边界。上述为代码分析和既有隔离基线，不代表已观测生产事故或事故发生概率。
