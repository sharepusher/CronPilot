# RBAC 用户编辑差异写入与事务闭环方案专业 Review

日期：2026-10-15 · 评审对象：[RBAC 用户编辑差异写入与事务闭环优化方案 rev.1](../design/RBAC用户编辑差异写入与事务闭环优化方案-2026-10.html) · 评审基线：当前工作区源码 · 结论：**方向通过，实施准入不通过**

**总评：**方案的架构方向、文档结构和风险意识达到专业设计水平，明显优于仅修改 `result.ok` 的局部热修；但 rev.1 仍有 1 个安全阻断项和 7 个高/中优先级契约缺口。建议评级 **B+ / 条件通过**：可作为修订底稿，不可直接确认实施。先形成 rev.2 并重新确认，再进入 U0。

## 1. 评审方法与证据范围

本评审逐项对照以下真实调用链，不以设计文档自证：

- `app/rbac/views.py::users_edit`、`_check_management_scope`、`_users_form_response`；
- `app/rbac/services.py::update_user`、`set_user_groups`、`write_audit_log`、`update_own_profile`；
- `app/templates/redesign/user_form.html` 的业务组与状态表单；
- `app/static/js/common-redesign.js` 的成功 Toast、跳转和刷新分支；
- `app/api/__init__.py` 的用户 Scope 进程内缓存与 TTL 安全网；
- 现有 RBAC、Scope、注册、Ajax 表单和用户编辑测试。

本轮只做设计 Review，没有修改业务实现，也没有把建议视为已确认需求。

## 2. 专业性、准确性与合理性评分

| 维度 | 评分 | 评价 |
| --- | --- | --- |
| 专业性 | 8.3 / 10 | 具备完整问题、根因、目标、范围、分批、验收、风险与页面对比；明确 no-op 不是 ORM 脏检查、提交未知不能自动重试、审计应与事实一致，专业基础扎实。 |
| 准确性 | 7.0 / 10 | 对多次提交、误报成功、用户组已有差异增删、审计独立提交等源码事实判断准确；但全局 Scope 授权、`__ALL__` 回显、资料字段当前校验和前端跳转行为仍有不准确或未冻结处。 |
| 合理性 | 8.0 / 10 | “服务端 change set + 单事务 + 同事务成功审计 + 提交后缓存失效”是合理完成态，单端点垂直切片也有利于控风险；但必须先补安全授权和可实现的 UI/并发契约。 |
| 实施完备度 | 5.5 / 10 | 验收框架充分，但若按 rev.1 直接编码，实施者仍需现场决定权限、停用缘由、审计行数、no-op 页面行为和异常分类，违反“设计先冻结行为”的目标。 |

## 3. 值得保留的专业设计

**以下部分建议原样保留：**

- **问题定位准确：**资料 commit 异常后仍沿用前序成功结果，是明确可复现的误报路径。
- **没有把少写等同于不失败：**方案正确区分风险降低、失败传播和事务原子性。
- **服务端负责 change set：**不信任前端、不依赖 ORM dirty 状态，符合安全与一致性要求。
- **副作用分类合理：**Token、缓存、审计都按真实字段变化触发，no-op 不制造业务审计。
- **不直接复用会 commit 的服务：**提取非提交内部原语、保留现有公开包装器，是兼顾原子性与兼容性的正确重构方向。
- **提交未知语义正确：**不把连接中断简单解释为回滚成功，不自动重试。
- **分批与停止条件清晰：**U0—U3 有逐批证据和停止线，不以最终大包测试替代中间验证。

## 4. Review Findings

[阻断 / 安全] **“目标角色是 admin”被错误当成授予全局 Scope 的充分条件。**

`users_edit` 当前只在 `new_role != 'admin'` 时拒绝 `__ALL__`；模板又会在角色选择为 admin 时显示“全部（全局权限）”。这没有验证操作人自身是否为种子或全局管理员。按组管理员只要拥有多个可管理组、页面未进入单组锁定分支，就可能把 Scope 内目标提升为 `admin + __ALL__`，从而制造新的全局管理员。

rev.1 只写“保留管理 Scope”，没有固定“谁有权授予全局权限”的负向契约，也没有对应测试。这不是一般边界遗漏，而是实现前必须关闭的权限提升面。

**修订要求：**只有 `_actor_bypasses_scope()` 为真时才允许提交 `__ALL__` 或把目标变为全局 admin；按组管理员即使能管理目标，也只能分配自身允许的具体组。新增“多组 Biz Admin 尝试 admin + \_\_ALL\_\_ 必须拒绝”的路由级和浏览器反向测试。

[高] **`__ALL__` 的持久化语义与表单回显没有闭环，no-op 对全局管理员不成立。**

当前 `set_user_groups()` 把 `__ALL__` 规范化为“用户组关系为空”；但 `get_user_group_ids_for_user()` 只返回真实关系 ID，模板只有在列表中显式包含 `__ALL__` 时才选中“全部”。因此非种子全局 admin 的空关系状态不会自动回显为 `__ALL__`，原样提交甚至可能触发“必须选择业务组”。

**修订要求：**先定义双向映射：持久化空关系 + 非种子 admin 的有效全局语义如何转成表单 sentinel；seed admin 空关系如何区分；POST 后如何回显。把 global admin 原样保存纳入 no-op 测试和页面对比。

[高] **停用缘由契约缺失，编辑页与专用停用路径的策略不一致。**

`set_user_active()` 强制要求停用缘由并写入 `status_reason`，但用户编辑页可通过 `update_user()` 直接把状态从 1 改为 0，表单没有缘由字段。rev.1 声称保留停用安全语义，却没有说明是否继续允许这条无缘由路径。

**修订要求：**在以下两种方案中明确选择其一：A）编辑页不再负责停用，状态变更统一走既有专用停用流程；B）编辑页增加必填缘由并与状态、安全字段、审计同事务。两者都会产生页面可见差异，必须更新 Before/After 和端到端步骤。

[高] **no-op 页面契约与现有公共 JavaScript 行为冲突。**

rev.1 展示“未检测到变更，无需保存”Toast，同时写“是否回列表沿用当前成功路径”。但 `common-redesign.js` 在 `errcode=0` 且有 URL 时立即跳转；没有 URL 时又立即刷新当前页面。两种情况都不能保证用户实际看到稳定的 no-op 提示。原生 POST 成功分支则直接 302，也没有持久消息。

**修订要求：**分别冻结 Ajax 和原生 POST：是否停留、是否跳转、消息如何持久显示、是否增加加法字段。若修改公共 JS，需评估全部 `js-ajax-form`；更推荐本页专用、加法式结果标记或明确接受 no-op 与普通成功相同跳转且不承诺可见 Toast。

[高] **成功审计模型改变会影响第二个页面，当前页面对比不完整。**

rev.1 推荐把角色、组和资料变化合并为一条字段名审计。当前角色更新和用户组更新分别调用 `write_audit_log()`，资料更新没有同类成功审计。改为合并记录会改变访问审计页的行数、资源文案和详情内容，属于用户可见变化，不只是用户编辑页内部实现。

**修订要求：**决定是保留现有审计行粒度并在同一事务插入多行，还是改成单条结构化审计。若采用单条，设计已跨两个页面，须补访问审计页 Before/After；同时定义历史记录兼容、action/resource/detail 契约和脱敏字段。

[高] **资料字段“全部前置校验”仍是口号，未冻结实际规则。**

当前管理员编辑路径会把超长 `other` 岗位值静默截断，而自助资料路径会拒绝超长值；管理员编辑对邮箱格式、邮箱长度、花名长度也没有完整服务端校验。rev.1 写“遵守长度约束”和“字段非法零写入”，但没有选择究竟保留静默截断还是改成拒绝，也没有说明管理员可选邮箱/花名与自助资料必填规则不能直接复用。

**修订要求：**增加逐字段的输入、空值、最大长度、格式、规范化、错误文案和历史兼容表；对绕过 HTML 的构造请求写测试。推荐拒绝超长值而非静默截断，但这属于需要明确确认的行为变更。

[中] **事务内重新读取不足以关闭 Scope TOCTOU 和最后管理员并发竞态。**

Scope 当前在路由进入时检查；事务服务若只重新读取目标值而不重新检查操作人的权限和目标组，检查与写入之间仍有时间窗口。类似地，两名管理员并发降权时都可能在计数阶段看到另一名管理员，单纯“一次事务”不必然保护“至少一名启用管理员”不变量。

**修订要求：**在写边界使用同一事务快照重新验证 actor、目标和可分配组；明确最后管理员不变量的串行化方法或将其登记为残余风险。SQLite/MySQL 行为必须分别验证，不能只写“事务内重新读取”。

[中] **缓存失效失败被定义为成功，但安全延迟没有量化和验收。**

当前 API Scope 缓存是进程内缓存并有 TTL 安全网。角色降权、停用或组变化提交成功后，如果当前进程失效失败，或其他 worker 未同步失效，旧 Token 对应的缓存权限可能在 TTL 窗口内继续生效。rev.1 允许业务继续成功是可以讨论的取舍，但“保留现有安全语义”必须同时披露这一残余窗口。

**修订要求：**明确立即撤权还是最终撤权。如果维持现状，验收必须覆盖当前 worker 失效和其他 worker/TTL 的残余风险说明；如果要求立即撤权，需要独立的共享缓存或版本校验设计，不能由本切片暗示已经解决。

[中] **`COMMIT_UNKNOWN` 有名称但缺少可执行判定与核实流程。**

设计没有定义哪些异常进入 `FAILED`、哪些进入 `COMMIT_UNKNOWN`，也没有明确 commit 异常后必须 rollback/清理 Session，或如何使用新事务核实数据库状态。测试若只 mock 一个通用异常，无法证明真实连接中断的两种可能结果。

**修订要求：**建立异常分类表：校验/flush/约束失败、commit 连接丢失、rollback 失败分别如何处理；默认不确定原则；失败 Session 的清理；刷新核实入口；测试分别模拟“服务端未提交”和“服务端已提交但客户端失联”。

## 5. 对 rev.1 核心结论的准确性判定

| 结论 | 判定 | 说明 |
| --- | --- | --- |
| 无变更不调用写服务可减少失败面 | 准确 | 不仅减少用户表 DML，也能减少 commit、审计 INSERT、Token 和缓存副作用。 |
| ORM 同值赋值不等于零写入 | 准确 | 当前路径仍会 commit，并独立写成功审计。 |
| 单事务能消除端点内部的部分提交 | 基本准确 | 前提是所有核心业务变化和成功审计确实共享同一 Session/commit；提交结果未知仍需核实。 |
| 缓存失效失败仍可返回完全成功 | 条件成立 | 只在接受最终撤权和有限陈旧窗口时合理；安全影响必须明示。 |
| 只需一个页面的 Before/After | 不准确 | 审计模型变化会影响访问审计页；若保留审计表现不变才可限定为单页。 |
| 现有 Scope/安全语义可原样保留 | 不充分 | `__ALL__` 授权和停用缘由已有策略缺口，不能不经决策直接复制。 |
| no-op 可用现有成功路径显示专属 Toast | 不准确 | 公共 JS 会立即跳转或刷新；必须补专用交互契约。 |

## 6. 建议的 rev.2 修订顺序

1. **先关闭安全阻断：**固定 actor 授予 `__ALL__` 的资格、可分配组集合和事务内二次 Scope 校验。
2. **冻结领域映射：**补齐 global admin/seed admin/具体组的持久化值、表单值和 change-set 值双向映射。
3. **统一状态策略：**决定编辑页停用是否迁移到专用停用流程，固定 `status_reason`。
4. **冻结字段校验：**对 email、nickname、job\_title、is\_active 给出明确输入与错误矩阵。
5. **冻结输出：**分别定义 Ajax、原生 POST、no-op、已知失败、未知结果的消息与跳转。
6. **冻结审计：**决定单条还是多条，并补第二页面对比或明确保持审计页不变。
7. **冻结并发和缓存残余风险：**给出可验证的 Scope、最后管理员和权限缓存契约。
8. **更新验收：**增加安全反向、全局 admin no-op、停用原因、真实 UI 可见性和未知提交双结果测试。

## 7. 修订后实施准入条件

满足以下条件后，方案可从“条件通过”升级为“允许确认实施”：

- 按组管理员无法创建或编辑出全局管理员，且有多组 actor 的反向用例；
- `__ALL__` 双向映射和 global admin no-op 可证明；
- 停用缘由、字段校验、Ajax/原生响应均无实施时自由裁量；
- 审计页是否变化已明确并满足页面对比规则；
- Scope TOCTOU、最后管理员竞态、缓存陈旧窗口和提交未知均有明确边界与测试；
- rev.2 重新完成 HTML/Markdown、双索引、链接和页面对比门禁，并由用户明确确认。

## 8. 最终结论

rev.1 是一份**专业、方向正确、风险意识较强**的方案，核心架构值得保留；它对“无变更不写库”的价值判断准确，也正确提出了单事务完成态。但它目前更接近高质量架构草案，而不是可以无歧义交给实施者的最终规格。

最关键的问题不是事务代码本身，而是事务开始前仍有未冻结的授权与领域语义。若先编码再补这些决策，极易把现有 Scope 提权面、停用策略分叉和审计/UI 漂移一起固化进新服务。因此本 Review 的专业建议是：**不否定方案，不进入实现；先修订为 rev.2，再重新确认。**
