# RBAC 全局权限授予边界 S0–S5 全过程专业 Review

版本：rev.2 · 初审：2026-10-16 · 最终复核：2026-10-26 · 审查对象：[实施设计 rev.11](../design/RBAC全局权限授予边界加固优化需求-2026-10.html)、实现代码、专项测试、修复复盘、Release Notes、R2-4 浏览器证据与 S5 验收记录

**最终复核结论（2026-10-26）：正式通过，S5 关闭。**S0–S5 安全主链、F-01 批量反馈和 F-02 注册审批读取隔离均已闭环。R2 使用关联表权威查询、数据库当前 actor 和分页前授权谓词；R2-4 以五类真实浏览器角色、旧 Cookie 降权、持久化截图/JSON 和零残留 fixture 完成最终验收。综合评级更新为 **A-（9.3/10）**。独立用户编辑 no-op/单事务不属于本方案完成声明。

## 1. 审查边界与方法

本次 Review 不是重新设计，也不授权追加实现。审查以代码事实为准，逐项对照 S0–S5 的前置条件、停止条件、授权矩阵、测试和交付声明；对安全写入、可见性、事务、响应契约和证据持久性分别判断。已执行静态调用链核对、专项测试复跑、SQL 匹配语义验证、未提交差异检查与文档交叉核对。

- 安全写入链：`users_add/users_edit → validate_user_scope_assignment → create/update/set groups`。
- 审批链：单条/批量路由 → `approve_registration()` → 数据库当前 reviewer 授权。
- 展示链：注册审批列表 Repository 查询、分页、pending 数量及模板批量交互。
- 证据链：设计 rev.8、专项测试、修复复盘、Release Notes、索引状态与本地验收记录。

## 3. 已确认正确的核心结论

**安全目标已经实质达成：**受限 Biz Admin 不能通过新增、编辑、单条审批或批量审批把目标授予全局 Scope；合法 seed/global admin 能力保持。最终写入授权不依赖页面隐藏，也不只信任 Session。

- **S1 纯策略正确：**`user_scope_assignment_denial()` 不读 Session/DB、不产生写副作用，稳定原因码覆盖 actor 权限、全局授予、组越界、目标角色和空组。
- **数据库当前事实正确：**`validate_user_scope_assignment()` 回读 actor 当前角色、活动状态和组，并对读取异常 fail-closed。
- **S2 写前守卫正确：**新增/编辑中的 Scope 拒绝发生在 `create_user()`、`update_user()` 和 `set_user_groups()` 之前；编辑同时校验 target 管理范围。
- **S3 UI 定位正确：**`can_assign_global` 复用后端能力判定；受限 actor 的 HTML 不渲染 `__ALL__`，UI 只是纵深防御。
- **S4 审批写入正确：**单条和批量均逐项调用同一审批服务，服务按 reviewer ID 读取数据库当前授权；越权项保持 pending 且不创建用户。
- **测试隔离与角色建模良好：**专项测试使用内存数据库，明确区分 seed、非种子 global、单组/多组 Biz Admin、operator 和 viewer。

## 4. 阻断正式验收的发现

### F-01 · P1 · 批量审批失败被成功码和立即跳转掩盖

**状态：已关闭（2026-10-19）。**按[B0–B3 独立方案](../design/RBAC注册审批批量反馈真值闭环优化方案-2026-10.html)完成：后端统一全成功/部分失败/全部失败契约，页面仅在全部成功时跳转，失败详情以纯文本持久展示，系统异常以同一 `trace_id` 关联服务端原始日志。浏览器覆盖全部成功、部分成功、全部失败和系统异常；扩展回归 163/163 通过。原始证据保留如下，作为修复前基线。

**证据：**`app/rbac/views.py:1278–1302` 对每项统计成功/失败，但无论全部失败还是部分失败均返回 `web_api_return(code=0, ..., url=...)`；`app/templates/redesign/registration_review.html:213–233` 收到响应后只要有 URL 就立即跳转，不读取 `errcode` 或展示 `errmsg`。专项测试 `test_batch_scoped_admin_partially_approves_only_authorized_scope` 也把 `errcode == 0` 固化为期望。内存库直接复现全部失败时，响应仍为 `errcode=0`、`成功 0 条，失败 1 条`并携带跳转 URL，而数据库正确保持 `pending` 且未创建用户。

**影响：**数据库安全边界没有被绕过，但用户会看不到全部失败或部分失败的详细结果，形成“操作像成功、事实未完成”的反馈风险。这与项目最初治理“误报成功”的目标不一致，也不足以证明设计所称的“保留逐条成功/失败语义”已经在 UI 交付层成立。批量拒绝路由存在相同响应模式，应一并审查。

**修正要求：**为批量结果定义明确契约：全失败必须失败码；部分成功必须返回结构化成功/失败清单并在跳转前可见，或由重定向后的持久提示承载；增加真实浏览器的全部失败、部分成功和全部成功三态测试。

### F-02 · P1 · 注册审批列表存在跨组误展示与旧 Session 可见性

**状态：已关闭（2026-10-26）。**R2-0–R2-4 已完成：数据库当前 actor、申请—组关联表、精确交集/admin 完整子集、分页/count/badge 同源、SQLite/MySQL 性能及五角色浏览器矩阵均通过。旧 Cookie 从全局降为组 1 后立即只见组 1；证据见[R2-4 最终验收](RBAC注册审批R2-4浏览器最终验收与F-02关闭-2026-10-26.html)。以下保留原发现作为修复前基线。

**证据：**`app/repositories/registration_request_repository.py:42–65,75–90` 对逗号分隔的 `group_ids` 使用 `LIKE '%<gid>%'`。因此组 1 会匹配组 10/11/21；本次 SQL 语义复核结果为 `'10' LIKE '%1%' = 1`。`app/rbac/views.py:1166–1182,1221–1224` 又使用 Session 中的组和 bypass 状态筛选列表及计数，而不是数据库当前 actor 事实。

**影响：**写操作仍会被数据库当前事实拒绝，因此不是全局权限写入绕过；但申请用户名、角色、组、理由等可能被范围外管理员看到，待审批数量和分页也可能泄露范围外记录。对于 viewer/operator 申请，分页后的 Python 二次过滤不会纠正数字子串误匹配；actor 被从 global 降为 scoped 后，旧 Session 还可能继续看到全量列表。

**修正要求：**短期使用边界安全的精确 token 条件并统一用于列表与计数；中期将申请与组规范化为关联表。页面可见性读取数据库当前 actor 授权，至少新增“组 1 不匹配组 10”和“数据库降权覆盖旧 Session”的测试。

### F-03 · P1（文档验收） · “拒绝路径零业务副作用”声明范围过宽

**状态：已关闭（2026-10-16 起持续生效）。**父设计 rev.9–rev.11 和索引已统一限定为“Scope 授权拒绝路径零业务写入”，并明确岗位校验、no-op 与单事务属于独立 U0–U3 方案，未纳入 S5 完成声明。

**证据：**设计 §8.3 正确限定“Scope 拒绝在首个写入前”，§8.3 又明确本需求不解决编辑路由多次 commit；但 §12 写成无条件的“拒绝路径零业务副作用”，rev.8 顶部和索引也笼统写“数据库零副作用”。实际 `app/rbac/views.py:799–829` 先调用会各自提交的 `update_user()` 和 `set_user_groups()`，之后才校验岗位；岗位缺失或自定义岗位为空会返回失败，但角色/状态/组可能已经改变。

**影响：**S2 的 Scope 安全拒绝结论仍然成立，但文档会让读者误以为所有表单失败路径都已具备事务原子性。这与独立的[用户编辑差异写入与事务闭环方案](../design/RBAC用户编辑差异写入与事务闭环优化方案-2026-10.html)“待确认、未实施”状态冲突。

**修正要求：**把所有相关表述限定为“Scope 授权拒绝路径零业务写入”；明确岗位、资料、后续提交失败仍属独立 U0–U3 方案范围。在该独立方案实施前，不得宣称编辑端点整体具备零副作用或单事务。

## 9. 最终验收门槛

- 批量全部失败不再返回成功语义，部分失败在 UI 中可见且可追溯；
- 组 1/10 等数字边界不会导致跨组列表、计数或分页泄露；
- 数据库降权后旧 Session 不再获得超出当前授权的审批列表可见性；
- 设计、复盘、Release Notes 和索引统一限定 Scope 拒绝边界；
- 两类角色浏览器证据可从仓库或自动化流程重复获得。

**发布判断：**S0–S5 整体闭环成立；Biz Admin 全局授予阻断、批量反馈真值和审批列表 Scope 展示均已验证。F-01/F-02 关闭不改变 API 返回字段，也不包含独立的用户编辑事务改造。
