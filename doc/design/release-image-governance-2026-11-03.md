# 4.2.0 发布前图片证据治理设计

rev.3 · 2026-11-04 · 状态：用户确认后已实施并完成本批验收。rev.1、rev.2 的评估及阶段数据为历史记录。

## 1. 问题及证据

运行 `.venv-py311/bin/python scripts/check_doc_image_assets.py --check` 返回 1、162 条错误：148 个旧路径 PNG 文件和 14 处非规范图片引用。这是两类计数，不能相加理解为 162 张图片。148 个文件按 SHA-256 去重后为 135 份内容，总计 17,369,877 字节；明细、大小及基线哈希见[只读清单](../qa/evidence/release-image-governance-2026-11-03/inventory.json)。本轮未审阅图片内容，不能宣称无敏感信息。

该检查同时在 `.github/workflows/doc-completeness.yml` 和 tag 触发的 `.github/workflows/release-asset.yml` 中执行，因此阻断文档 CI 和发布资产构建。版本检查仍有 Unreleased 内容，release/release-manifest.json 仍指向 4.1.1；这些是独立发布准备事项。

## 2. 根因与专业评估

历史图片治理设计已经确立内容寻址、来源审查和清单契约；后续 QA 证据继续以旧目录和普通名称入库，导致已跟踪的证据与现有门禁不一致。应先保留审计价值，再按既有规范治理；简单放宽门禁、直接删除截图或批量标记“已审查”都不能证明引用可用或内容安全。

## 3. 建议方案

1. 冻结基线：实施前重算文件清单和哈希，对比本页基线；列出 HTML、Markdown、JSON、脚本、测试及其他文件中对每个旧路径或文件名的引用，并区分可执行引用与历史审计记录。
2. 逐张审查 135 份唯一内容及 PNG 元数据，记录来源、公开使用依据、审查人和结论。发现凭据或其他敏感内容时停止对应项，按已有图片治理规范处理；不得将未审查内容标记为安全或仅凭文件哈希推断内容安全。已有入库历史的敏感内容须另行评估历史及凭据处置。
3. 审查通过且须保留的图片维持原始字节，按 SHA-256 存到 `doc/assets/screenshots/`，相同内容合并并在 manifest 记录所有旧路径及来源。准确更新可执行引用，包括非 HTML/Markdown 引用；历史记录需要保留原路径时明确标识其历史属性，并提供可定位映射。
4. 旧路径仅在新资产存在、引用和证据可达性验证后移除；不覆盖已有未提交修改，不删除无法证明已保留或不再需要的证据。依赖旧目录作为数据集的工具或外部接口须单独核实并迁移；如确需兼容，先设计可验证的兼容方式，不静默断链。
5. 检查图片生成脚本的默认输出位置及其与现有门禁的契约。若存在会重新引入旧路径的受控流程，设计并测试可重复的入库步骤；不将临时隔离测试输出强制写入仓库。

## 4. 范围

范围是上述旧路径图片、对应的证据引用、内容寻址清单及必要的测试和文档；不修改业务代码、数据库、权限策略或发布版本。无产品页面可见变更。不得假设 14 个文档图片引用包含所有证据消费者。

## 5. 分批

1. G0：重新采集清单、引用及来源，逐项审查图片内容与元数据，记录任何待处理敏感项。
2. G1：依据审查结果迁移并去重，逐项核对旧路径到哈希资产的映射，迁移消费方；对无法安全自动迁移的引用单独处理。
3. G2：核验全部已迁移证据、文档、门禁、发布资产边界和防回归；持久化复盘、实际验收结果及未解决项。

## 6. 验收

- 所有保留证据的映射可追溯；未脱敏图片原始 SHA-256 与迁移前一致，去重不造成证据丢失；清单中的来源、公开依据、审查结果和引用真实、完整，不虚报人工审核。
- 对 HTML/Markdown 之外的 JSON、脚本及其他消费者执行路径核对，受影响的浏览器证据在文档中实际加载；历史映射可供旧证据定位。
- `python scripts/check_doc_image_assets.py --check` 通过，图片检查相关测试通过；文档链接、HTML/Markdown 同步、完整性与术语门禁通过，确认不会把 QA 图片带入发布安装包。
- 复盘覆盖定位、根因、测试漏洞、修复、防护测试、同类排查和可执行预防措施；如存在敏感内容或非仓库消费者，记录处置和剩余风险，不能仅凭门禁变绿宣布完成。

## 7. 风险及决策边界

直接迁移可能公开敏感内容，改路径可能破坏 HTML/Markdown 之外的消费者；即使当前文件已在 Git 中，也不能将此视为再次发布前无需审查。证据旧路径删除具有不可逆的工作区风险，应在确认完整映射后谨慎处理；如出现敏感材料、无法确认用途的证据或互不兼容的外部消费方式，应暂停相关项并单独评估。通过本门禁不代表 4.2.0 已完成版本归档、打包演练或最终发布审批。

## 8. 本轮实际验证

图片门禁重跑得到上述 162 条错误；核对了两个 CI 工作流、现有图片治理设计和 release manifest；只计算文件哈希及大小，未对图片内容作安全结论。用户确认前不实施迁移。

## 9. 专业复核（2026-11-03）

**结论：方向可行，补齐迁移和验收细节后可实施；评估本身不是实施确认。**保留原始字节、逐项审查、全路径迁移与不放宽门禁是合理原则。根因中“后续证据继续入库”是基于现状的推断，本轮未逐个回溯提交次序，不应视为已验证的完整历史因果。

1. **P1：证据与消费者覆盖不足。**检查器仅解析文档 HTML 的 img 和 Markdown 图片语法，并检查 PNG 是否在规范目录，不能验证 JSON、脚本、普通链接、旧路径或外部消费者。当前 14 处非规范引用对应 7 个图片路径在 HTML 和 Markdown 中各出现一次；不能把其余旧图片当成无价值或无消费者。建议生成逐旧路径映射和消费者清单，逐项标记引用、用途、哈希、迁移结果和验证方法；外部消费者无法穷举时明确风险，不以搜索零结果证明无人使用。
2. **P1：内容去重不能代替来源审查。**135 个不同哈希对应 148 个旧路径；相同字节也可能有不同来源和证据上下文。每个唯一内容要审查像素和元数据，每个旧路径分别记录来源、用途、公开依据和迁移去向，再建立多对一映射。现有 manifest 的单一 provenance 对象不能自动承载多路径不同来源，应配套可追溯记录，不虚填来源或审核人。
3. **P2：现有门禁和测试不足以验证迁移。**`tests.test_doc_image_assets` 当前仅有 3 条测试，覆盖有效资产、内嵌图和哈希不符；不覆盖本批多路径去重、旧路径映射完整性、非 HTML/Markdown 消费者及证据缺失的拒绝。实施时应增加独立的迁移验收及负向控制：缺一条映射、错哈希、缺资产、引用未更新分别失败；对不属于该检查器契约的消费者单独验证，避免误称已有门禁已覆盖。
4. **P2：发布演练需针对实际候选提交。**本地安装包校验器既排除规范截图目录，也根据 manifest 哈希检查图片字节；须在候选提交上构建并校验，不能仅靠路径白名单推断新资产不会进入归档。版本归档、release manifest 与最终 tag/远端 workflow 是独立事项，不应因图片门禁通过而标记发布就绪。

本轮补充核验：`python -m unittest tests.test_doc_image_assets -v`：3 项通过；按内容哈希比对，135 份旧图与当前规范清单无同哈希项；只检查 PNG 块结构发现 148 个文件均仅含 IHDR、IDAT、IEND，不能因此推断像素内容无敏感信息。脚本中发现与旧图重名的输出文件名；这是生成文件名复用的证据，不等于证明脚本直接读取旧图。当前未做逐图目视审查，也未调查外部消费者。

## 10. 实施进展及生成路径修复复盘

首批 11 个旧路径经原图检查并按原始字节迁移；直接展示的 7 张已更新文档引用，具体映射与审查记录见 [D2 批次](../qa/evidence/release-image-governance-2026-11-03/reviewed-batch-d2.json)及[文档引用批次](../qa/evidence/release-image-governance-2026-11-03/reviewed-batch-referenced.json)。在本阶段图片门禁剩余 137 项，整体尚未通过；不得将本阶段计作完成。

1. **定位：**D1 验证脚本默认将 D1、D2 和超时验证截图写入仓库旧证据目录。
2. **根因：**验证输出目录与历史入库目录绑定，自动验证绕过截图内容审查及内容寻址治理。
3. **测试漏洞：**原集成验证只检查业务结果，未核查输出是否落在仓库文档目录或覆盖旧证据。
4. **修复：**`scripts/verify_cron_edit_d1.py` 每次创建新的系统临时证据目录，D1、D2、超时和 no-op 各自独立子目录，打印路径供后续审查。
5. **防护测试：**隔离 SQLite 浏览器运行 `D1_SKIP_BROWSER=1 VERIFY_D2=1 .venv-py311/bin/python -u scripts/verify_cron_edit_d1.py` 输出临时目录、`D2_VERIFIED` 与 `D1_API_VERIFIED`，退出 0；`.venv-py311/bin/python -m unittest tests.test_qa_image_migration tests.test_doc_image_assets -q` 8 项通过，覆盖映射缺失、错误哈希、图片缺失及篡改、旧文件和旧链接。
6. **同类排查：**D1、D2、timeout 已通过同一临时根目录输出；用户编辑和任务编辑其他浏览器脚本接收调用方指定的输出目录，不能仅凭本次检查认定所有调用方都不会写入仓库。
7. **预防：**`scripts/check_qa_image_migration.py` 对基线清单校验每条旧路径的唯一映射、内容哈希、旧文件及 HTML/Markdown 有效图片链接；通过上述单测复现否定路径。该工具不检查纯文本、JSON 或外部消费者，这些仍须单独核查。文档 CI 和 tag 发布资产工作流均运行该检查。

## 11. 最终验收与治理复盘（2026-11-04）

1. **定位：**图片门禁发现旧目录 PNG 与非规范引用，阻断文档 CI 与标签发布资产检查。
2. **根因：**既有内容寻址规范建立后，浏览器验收截图仍可直接写入旧目录，提交前缺少统一资产迁移和内容审查。
3. **测试漏洞：**旧门禁可发现不规范路径，却没有基于冻结清单证明每张旧截图都被保留，也不能覆盖纯文本或外部消费者；原验收脚本没有隔离输出目录。
4. **修复：**148 条旧路径收敛到 135 份原始字节资产，保留逐路径来源与哈希映射；更新仓库内文档引用并将 D1 系列验证输出改为新建临时目录。审查采用原图检查、缩略总览、PNG 块检查及本机 OCR 辅助；被识别为可疑的 3 份已原图复核，结果为测试数据或设计示例。机器识别不保证发现所有潜在敏感信息，不能证明截图绝对无敏感内容。
5. **防护测试：**`scripts/check_doc_image_assets.py --check` 与 `scripts/check_qa_image_migration.py` 均通过；映射及图片门禁单测 8 项通过；浏览器加载 4 个文档页面的 7 张迁移图片；D1、D2、超时和无变更四组输出均位于同一个新建临时目录。链接、文档完整性、术语及 HTML/Markdown 同步检查通过。
6. **同类排查：**仓库文档中旧文件完整路径和去掉 doc 前缀的文本搜索无匹配；生成脚本的文件名在不同批次复用，调用方自选目录的其他脚本仍需要遵守治理流程；无法穷举仓库外直链与消费者。
7. **预防：**新增 `scripts/check_qa_image_migration.py` 对冻结清单逐条校验映射和内容，且拒绝已知旧文件与 HTML/Markdown 实际链接；`tests/test_qa_image_migration.py` 对缺失、错哈希、缺文件及旧链接做否定控制；文档 CI 和发布资产工作流执行映射校验；D1 验证截图默认落入系统临时目录，需治理后才可入库。旧的仓库外截图直链可能失效，可通过 `doc/assets/screenshots/manifest.json` 的 legacy\_paths 反查。

验收详情：[结构化结果](../qa/evidence/release-image-governance-2026-11-03/validation.json)、[剩余路径审查与映射](../qa/evidence/release-image-governance-2026-11-03/reviewed-batch-remaining.json)。基于隔离工作区快照的本地包演练，两次构建字节相同，301 个文件且资产检查通过；该快照不是正式候选提交，实际候选和远端 tag 流程仍须重新验证。版本归档及 4.2.0 发布清单仍是独立事项。
