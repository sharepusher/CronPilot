传输状态机与 Run Inspector 展示收口

入口：专业 Review 评估 F1–F4 / F6。父语义：失败分类与 HTTP 响应语义。页面对比见 §5。

抢跑说明：工作区已有未提交半成品（exception_failure_info 区分 Connect/Read、run_inspector.html 部分文案分支）。确认本设计后，以本文为唯一准绳重审半成品；不得以「测试已绿」跳过文末验收矩阵。

1. 问题

ID现象用户影响
F1凡请求调用开始后失败（含 ReadTimeout）均写 failed_before_response，页面写「未建立连接」。读超时被误判为根本没连上。
F2actual_request_sent 认 sent|response_received，但终态从不写 sent。布尔与枚举文档脱节；成功才显示「已发送并收到响应」。
F3Presenter 已算 http_status_label，meta 仍渲染 http_status（多为 —）。无响应场景缺少可读说明。
F4模型声明 Unique(run_id,seq)，存量库仅有非唯一索引。新建/存量约束漂移（风险低）。
F6外层 fatal 默认 pre_request/not_started。中段 fatal 可能被标成请求前置。

2. 根因

  • 父设计把超时/连接失败折叠进同一终态 failed_before_response，并配「未建立连接」文案，未区分「连接前失败」与「已发起后无响应」。
  • 枚举含过渡态 sent，但 JobLog 只落终态；Presenter 仍按过渡态判定「已发送」。
  • 模板与 Presenter 字段未做「算了就渲染」门禁。

3. 方案

3.1 推荐：终态枚举拆分 + 展示契约对齐

JobLog.transport_state 终态（写入库）：

值何时写入页面「传输状态」文案
not_started未准备请求目标（请求区不展示传输行，或「未开始」）
prepared已注入参数，尚未调用 _http.get/post已准备，尚未确认发送
client_failed客户端初始化失败（如 assert_hostname TypeError），请求栈未真正发出客户端初始化失败
connect_failedConnectTimeout / ConnectionError / SSLError / TooManyRedirects连接未建立
sent_no_responseReadTimeout 或通用 Timeout（无法证明仅连接阶段）已发起，未收到响应
response_received获得 HTTP response object已发送并收到响应
failed_before_response仅作历史兼容/未知兜底；新写入尽量不用未确认发送

明确不做：不在 JobLog 终态写入过渡值 sent（事件 http.start 的 detail 仍可用 prepared 表示「即将发送」）。文档与模型 doc 同步删除「终态含 sent」表述，或标注「仅事件过程态，不入库终态」。

Presenter 契约：

  • actual_request_sent 仅当 transport_state == 'response_received'（且 admin）为 true → 模板「已发送并收到响应」。
  • 其余态走模板显式分支（上表）；client_failed / unknown_failure（若保留）必须有分支，禁止落入「连接未建立」。
  • meta 行：HTTP <strong>{{ run.summary.http_status_label }}</strong>（关闭 F3）。

分类函数：exception_failure_info(exc) 必须返回三元组 failure_stage / fail_reason / transport_state。映射表：

异常fail_reasontransport_state
ReadTimeouttimeoutsent_no_response
ConnectTimeouttimeoutconnect_failed
Timeout（基类，非上两者）timeoutsent_no_response（保守：不宣称「未连接」）
ConnectionError / SSLError / TooManyRedirectsconnectionconnect_failed
TypeError + assert_hostnameclient_incompatibleclient_failed
其他internal若已 _request_call_started → sent_no_response；否则 prepared 或 client_failed 按能否证明调用边界

cron_do：已发起请求时采用 failure_info['transport_state']；未发起时写 prepared（或 client_failed）。外层 fatal（F6）：若已有 saved_jl/trace 且越过 prepared，写 failure_stage=transport（或 persistence 若异常在写库），禁止默认 pre_request。
