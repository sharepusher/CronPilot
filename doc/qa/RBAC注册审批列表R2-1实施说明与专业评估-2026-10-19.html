RBAC 注册审批列表 R2-1 实施说明与专业评估

日期：2026-10-19 · “R2-11”按上下文解释为 R2-1 · 依据：正式设计 rev.3 · 当前状态：说明与评估，未实施 R2-1

结论：A-（8.9/10），方案边界专业且顺序合理，但实施前必须先解除 RL-05 对 R2-2 的测试耦合，并把导航 badge 纳入同一数据库当前 actor 上下文。修正这两点后，R2-1 可独立、可回滚、可证伪地实施。

1. R2-1 的唯一目标

R2-1 只解决“当前访问者是谁、现在拥有什么读取权限”，不解决“申请的 CSV 组字段如何精确匹配”。Session 只作为 actor ID 的传输载体，数据库当前用户、角色、启用状态和 UserGroup 关系才是授权事实。

Session user_id → 数据库当前 RbacUser → 当前 is_active / role / username → 当前 UserGroup 集合 → 当前是否具有 user:manage → 当前 global 或 scoped(group_ids) → registration_review 列表与页面/导航计数共同消费

2. 为什么必须与 R2-2 分开

批次回答的问题禁止越界
R2-1谁在访问？其数据库当前角色、权限和组集合是什么？不修改 CSV LIKE、admin 子集 SQL、分页算法。
R2-2基于正确 actor，哪些申请行、total、pages 和 badge 应可见？必须经过双后端 DEC，不得回退分页后 Python 过滤。

拆分后，R2-1 失败可定位为 actor 解析/响应契约，R2-2 失败可定位为资源谓词；两种高风险变化不会互相掩盖。

3. 当前代码事实

  • web_session_user_is_valid() 已实时检查用户存在、启用状态、用户名和 auth_version，但不比较数据库当前 role/group_ids。
  • @require_permission('user:manage') 使用 Session role/username，因此角色降权但未 bump auth_version 时仍可能放行。
  • registration_review() 的 bypass、scoped group_ids 和 pending_count 均使用 Session。
  • 侧边栏 _get_pending_reg_count() 也单独使用 Session，并在任何异常时返回 0；若不纳入 R2-1，页面标题和导航 badge 仍可能使用不同 actor。
  • 已有 _load_scope_assignment_actor() 能读取数据库当前用户和组，但它是“授予 Scope”服务的私有实现，直接挪用会混淆读取授权与写入授权语义。

4. 推荐实现

4.1 独立的只读 actor Scope 解析器

在 RBAC 服务层建立专用于“用户管理读取面”的解析器，返回稳定结构，而不是调用 validate_user_scope_assignment() 伪造一个目标角色/目标组。建议契约：

{
  ok: true|false,
  reason: allowed|actor_missing_or_inactive|permission_denied|authorization_check_failed,
  actor_id, role, username, group_ids, bypass
}

解析器必须无写入、无 Session 依赖；数据库异常使用 logger.exception() 保存 traceback，返回稳定 reason，不返回原始异常。

4.2 请求级同源与缓存

同一个 HTTP 请求中，审批列表、标题 pending_count 和侧边栏 badge 必须消费同一份 actor 解析结果，建议放入 Flask 请求级 g 缓存。缓存仅限当前请求，禁止跨请求缓存授权结果。

这样既避免重复读取，也避免同一响应内发生“列表按新权限、badge 按旧 Session”的撕裂。

4.3 响应协议

状态响应日志/Session
会话用户不存在、停用、auth_version 不匹配沿用全局守卫：302 登录页清理 Session。
会话仍称 admin，但数据库当前角色无 user:manage403 通用无权限页不得展示申请；建议记录权限拒绝审计。
actor/组读取异常通用 500原文与 traceback 仅服务端日志；不得伪装为空列表。
数据库当前 global进入全量 Repository 分支不使用 Session 空组判断。
数据库当前 scoped把 DB 当前 group_ids 传给现有 scoped Repository此阶段仍保留现有 CSV 查询缺陷，交由 R2-2。

4.4 导航 badge 的异常边界

主路由 actor 解析异常必须 500；错误页渲染期间的上下文处理器不得再次递归抛出同一异常。推荐复用请求级失败结果：主路由决定 500，错误页导航 badge 安全降为 0，仅作为错误页渲染防护，不得把正常审批页的基础设施故障静默为空。

5. R2-0 测试耦合发现

实施前必须调整：RL-05 当前使用“DB global→组 1，范围外申请为组 10”。R2-1 即使正确拿到 DB 组 1，现有 LIKE '%1%' 仍会命中组 10，因此 RL-05 会继续失败，造成 R2-1 被错误判定未完成。

应将 RL-05 的范围外申请改为组 2，使其只验证 actor 来源：

DB 当前 actor：组 1
旧 Session：global
合法申请：组 1
范围外申请：组 2   ← 不使用组 10
R2-1 后预期：只显示组 1

1/10 子串问题继续由 RL-01、RL-10 和 RL-11 锁定，留到 R2-2 转绿。这不是弱化测试，而是确保每个批次只有一个自变量。

7. 修改范围与停止条件

预计修改：RBAC 服务层 actor 解析、注册审批 GET 路由、pending registration 导航 count、R2-0 测试隔离断言和设计记录。

不得修改：注册申请 Repository 的 LIKE、模型字段、数据库 schema、批量审批写路由、页面列布局与 R2-2 查询 DEC。

  • 若必须修改 CSV 查询才能让 R2-1 测试通过，说明测试仍耦合，立即停止。
  • 若错误页因上下文 badge 再次查询而递归失败，先修请求级失败缓存，不得吞掉主路由 500。
  • 若数据库当前 actor 与列表/badge 使用两次不同解析结果，停止交付。
  • 若 R2-1 使 RL-01/04/10/11 意外变绿，必须确认没有未经授权跨入 R2-2。

9. 结论

建议：先把 RL-05 的范围外组从 10 改为 2，并补充列表标题与侧边栏 badge 同源断言；然后实施独立 actor 解析器和请求级缓存。R2-1 完成时应只新增三条绿色结果（角色降权、组收窄、无权限 403），其余 CSV 精确查询红线继续保留给 R2-2。

10. 实施校准与验收结果

结论：R2-1 已按边界完成。RL-05 的范围外组已由 10 调整为 2，使其只验证 actor 数据源；1/10 精确匹配仍由 R2-2 红线覆盖。生产代码未修改 CSV LIKE、分页算法或页面结构。
  • 13 项 R2 矩阵：9 通过、4 项 R2-2 预期失败、0 error。
  • 相关回归 168/168、路由冒烟 86/86、import smoke 9/9、Ruff 与 diff check 通过。
  • 真实浏览器：global admin 可见 16 条；scoped admin 仅见授权组 1 条；同一已登录账号在数据库角色降为 viewer 后立即得到通用 403，恢复角色后页面恢复。
  • 测试账号角色已恢复为 admin，本地服务保持运行供复验。
