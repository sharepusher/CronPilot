发布工作流 S4 自引用修正设计

日期：2026-10-27 · 状态：已确认并实施 · 承接：发布工作流安全加固 S1–S4 设计。

决策：源码树中的 release/release-manifest.json 不再保存 source_commit；tag→commit 的来源完整性改由构建后生成的 cronpilot-$VERSION.tar.gz.build.json 单独承担。此调整修复可发布性阻断，不降低已实施 S1–S3 的最小权限、输入校验及资产回读保障。

1. 问题

当前 S4 将 source_commit 提交到将被 tag 指向的源码 manifest，同时 workflow 要求它等于该 tag 的 commit SHA。Git commit SHA 包含 tree 内容；修改 manifest 会改变 tree 和 commit SHA。因此该约束在正常、可审计的提交流程中无法满足。历史 v4.1.1 的源码树也不含该后加的 manifest，当前工作流若用于该 tag 会 fail-closed。

2. 根因

manifest.source_commit = A → 创建 commit 得到 B
把 manifest 改为 B → 创建 commit 得到 C
tag 指向 C 时 manifest 仍为 B，故 B ≠ C

根因是把“提交前可评审的发布状态”与“提交后才确定的 Git 对象身份”放入同一版本化文件并要求相等，不是 YAML、jq 或 Release API 的偶发错误。

3. 方案

对象调整后责任校验时点
release/release-manifest.json只保存 version、readiness、release_blockers；用于 tag 前审阅和 tag 后状态门禁。build-validate：版本匹配、ready/published、blockers 为空。
*.tar.gz.build.json构建程序从已 checkout 的 tag commit 生成 source_commit；作为来源绑定证据。publish：回读远端 build report，要求 source_commit == GITHUB_SHA。
workflow删除源码 manifest 与 tag SHA 的相等比较；保留资产回读、checksum、draft 状态与 build report 校验。发布前/后 fail-closed。
不变项：S1 job 权限分离、persist-credentials: false、固定 Action SHA、严格 SemVer、版本化 Release Notes、远端资产 cmp/checksum/来源校验和 draft 后再发布均保持不变。

4. 范围

  • 修改 release/release-manifest.json、scripts/check_version_consistency.py、.github/workflows/release-asset.yml 与相应单元测试。
  • 更新 S1–S4 设计、复盘、评估和索引，明确来源 SHA 属于构建证据而非源码声明。
  • 不改 Release artifact 公共合同，不将 manifest 打包入公开 tarball，不改应用代码、数据库或部署接口。

5. 分批实施

  1. B1：删除 manifest 的 source_commit；将 Python schema 校验改为只检查发布状态字段；workflow 的 readiness 步骤仅验证状态字段。
  2. B2：保留并加强 build report 的 source_commit == GITHUB_SHA 断言；确认它发生在 Release 从 draft 解除前。
  3. B3：补充单测：无 SHA 的 manifest 合法、遗留 SHA 被拒绝或忽略（选择严格 schema）、tag workflow 静态断言不再要求 manifest SHA，且仍要求远端 build report SHA。
  4. B4：执行本地 tag 等价演练（临时 Git 仓库/临时 tag）、专项单测、文档门禁与 YAML 解析；远端 Environment/tag protection 以 GitHub Settings 检查项记录，不能由本地伪造。

6. 验收标准

  • manifest 不包含 source_commit，却能在新建提交和新 tag 的 checkout 中被读取和通过状态校验。
  • 带版本不匹配、非 ready/published 或非空 blockers 的 manifest 均 fail-closed。
  • 发布 workflow 在解除 draft 前仍验证远端下载的 build report 的 source_commit == GITHUB_SHA。
  • tests.test_release_asset、tests.test_version_consistency、check_version_consistency.py --check、文档门禁和 YAML 解析通过。
  • 不声称未执行的 GitHub Actions 远端演练已完成；交付中明确远端 release Environment 与 tag protection 的核验步骤。

7. 风险与回滚

风险缓解回滚
误删来源绑定，降低完整性只删除源码 manifest 的 SHA；保留且测试 build report 的 SHA 绑定与远端回读。若 build report 不含或不能稳定提供 SHA，停止发布，恢复 draft，不解除 Release。
manifest schema 迁移误放行明确 allow-list 字段、负向单测和 tag 等价演练。恢复上一工作流的 draft 状态，禁止发布，修复 schema 后重新运行。
远端环境未配置把 GitHub Environment/tag protection 核验列为发布前人工门槛。不发布；补齐远端设置后重新执行受控发布。

8. 实施与验收结果

  • 已删除源码 manifest 的 source_commit；Python 校验改为严格的三字段 schema，非 object JSON 或遗留 self-referential 字段都会 fail-closed。
  • workflow 的两处 manifest 校验均改为版本、readiness 与空 blockers；远端回读的 build report 仍要求 source_commit == GITHUB_SHA。
  • tests.test_release_asset 与 tests.test_version_consistency 共 16 项通过；新增负向测试覆盖遗留 source_commit、非 object JSON，并直接断言入库 manifest 无该字段。
  • 临时 Git 仓库创建新提交并标记 v4.1.2，从 tag 读取 manifest 后调用 check_release_manifest(..., 'v4.1.2') 返回空错误，证明新 tag 路径不再依赖自引用。
  • 远端 GitHub Environment/tag protection 仍需仓库管理员在 Settings 中核验；本地未声称已执行真实 GitHub Actions。
