# R5：用户编辑字段意图与范围外组保留设计

版本：rev.1.1 · 日期：2026-10-29 · 状态：**用户已明确确认；按设计实施并验证**。R5 为评估发现编号，不新增 OPT 编号。

**核心原则：**只改花名，就只更新花名。表单含某字段不等于用户修改了该字段；服务端必须根据可信的页面原始值判定修改意图。范围外的组不能因页面未展示而被删除。

依据：[管理员 Scope 设计](管理员admin-Scope差异化设计.html) §3.6/§7 明确要求保留范围外组；[父设计](RBAC用户编辑差异写入与单事务收口独立设计-2026-10.html) D1/D5/D7 规定意图、有效差异和授权副作用；[P2 复盘](../postmortem/2026-10-RBAC两项P2组选择与审计契约回退.html) §6.1 登记了 R5 只读复现。[页面对比](#page-compare)。

| 对象/传输 | 认证与责任 | 失败与响应 | 验收 |
| --- | --- | --- | --- |
| GET 原值与表单 | 当前数据库 actor/target Scope 校验。完整目标组用于保护；可编辑投影用于表单意图比较，二者不得混用。 | 不能忠实展示/授权读取失败，不提供可提交缩水表单。 | A 管理员打开 A+B 用户，页面可编辑组初值 A；完整原始绑定仍受保护。 |

## 1. 问题与根因

当前目标完整原值是 A+B，单组管理员的表单只有 A；后端直接比较完整原值与不完整提交值，产生伪组修改。它不是没有做差异判断，而是两侧比较对象不一致。后续全量替换会进一步把范围外 B 当作待删除项。

只在前端过滤、或只在最终写库前补回 B 都不完整：前者可被原生请求绕过，后者仍可能生成伪授权意图，造成无意义冲突、重签 Token、版本递增或错误审计。

## 2. 推荐方案：分别保存和比较三种事实

1. **页面可编辑原值：**管理员当时能编辑的字段/组。A 管理员看到的组原值是 A。
2. **页面请求值：**本次提交的组仍为 A，因此组没有修改意图；花名变了才产生花名意图。
3. **数据库完整当前值：**保存时重新读取并保护 A+B，或期间被合法更改后的最新集合。没有组意图时不执行任何组关系 DML。

```
页面初值：花名=小夏，可编辑组=A
本次输入：花名=Summer，可编辑组=A

修改意图：只有 nickname
本次写入：只有 nickname + 对应成功审计
组 A/B、角色、其他资料：不写
Token/auth_version/Scope 缓存：本次零副作用
```

### 2.1 可信原值的实现方向

推荐保留完整目标组原值，并把“GET 时的编辑范围”一并签名；派生表单比较投影。为避免隐式兼容，已将编辑快照升为 v2，增加 editor\_scope（bypass 布尔值与按组管理员的排序组集合）。全局/种子 bypass 不把所有业务组装进 token，只记录全局模式。旧 v1 编辑页明确刷新，不修改数据库字段或外部 API。

前端的比较基准来自 signed original 的**同一可编辑投影**，服务端也用相同投影计算意图；角色、邮箱、花名、岗位仍使用对应原值。token 原文在失败回显中保持不变，继承 P1。P1 原来“JS original 等于整个 token 对象”的表达需细化为“JS original 等于 token 的表单投影”，不能悄悄修改语义。

editor\_scope 只是证明当时的展示范围，不是授权凭据。服务锁内仍读取当前 actor 能力/Scope；与签名编辑范围不一致时要求刷新，不能用新范围重新解释旧选择。全局角色、资料修改权限仍按现有设计，不能借此扩大授权。

### 2.2 服务端按实际意图执行

- **没有 group\_ids/role 意图：**不计算组替换、不改角色、不重签 Token、不 bump，不因未改字段的陈旧请求值写回其他状态。仍检查当前 actor 可管理目标、账号启用，以及本次资料字段的三方比较。
- **存在可见组修改意图：**只 diff 当前 actor 允许编辑的组。范围外绑定保持；禁止把完整目标组当作“本次新授予组”全部塞进子集校验，也禁止直接绕过校验。新增/删除可见关系必须分别受当前授权约束。
- **存在角色/组授权意图：**仍以完整 role+group\_ids 单元比较原始、当前和逻辑目标；授权并发不一致时拒绝，不拼接两个时点的授权。实际关系 DML 只触及可编辑集合。
- **资料-only 遇到别人的无关变化：**例如他人把外组 B 改成 D，只要当前仍有管理资格，且本次花名没有冲突，应只改花名，保留当前 A+D；不恢复旧 B。若真实调整授权时遇到该并发，则沿用更严格的整个授权单元冲突检查。

空选择、移出唯一可管理组、全局 marker 等不在本方案中顺手开放；沿用现有必选和授权约束。若后续需要“移出本组但保留其他组”，应另明确交互和权限，不从空数组猜测。角色是用户全局字段，其既有授权继续单独校验，不把范围外组保留解释为任意提权许可。

## 3. 示例与正确结果

| 操作 | 结果 |
| --- | --- |
| A 管理员原样保存 A+B 用户 | 无修改意图；正常 JS 0 POST，构造 POST 也零业务写/审计/授权副作用。 |
| A 管理员只改花名 | 只改花名；A+B 不动，不 bump/重签。 |
| A/C 管理员把可编辑组 A 改成 C，目标另有 B | 合法且无并发时变为 C+B；B 不增删。真实组变化才生成授权副作用和 group\_ids 审计。 |
| 仅改花名，期间他人把 B 改成 D | 保留当前 A+D，只更新花名；若失去当前管理资格则拒绝。 |
| 真正改组，期间他人改了角色或完整组 | 整个授权单元检查；非等价并发冲突不覆盖。 |

## 6. 验收

- actor A、target A+B：原样 no-op 和只改花名；后者其他所有标量、UserGroup、Token/auth\_version/缓存均本次零变化，审计仅 nickname。
- actor A/C、target A+B：原样保留 A+B；A→C 只变可编辑关系，保留 B，授权版本一次增加；伪造新组 D 拒绝。
- 原生 POST、JS、锁定 hidden、多选 select、失败回显后再次提交均同样成立；不能只检查 Toast。
- 资料-only 期间外组/无关字段并发，保留当前值；意图字段三方冲突拒绝；真正角色/组变更仍检查完整授权单元。
- actor Scope/角色在 GET 后或写前变化、目标停用/离开交集、组删除：fail-closed，不用新范围解释旧请求。
- 保留 P1、P2 的全部回归，新增外组保留永久测试；86 路由、Ruff、Ajax/导航、UI/颜色与文档门禁。改测试后核对开发 SQLite 表完整。

## 7. 取舍、风险与回滚

**推荐：**以可信表单投影判定用户意图，以当前数据库完整集合保证写入范围。它同时解决“不应变更”和“即使真改也不能误删外组”，不依赖用户理解隐藏字段。

只修前端或只补最终集合不充分；把含外组的所有用户一律禁止编辑会改变现有权限，并阻碍正常资料修改。服务端投影和范围内写入更符合已有设计，但需要同步前后端及调用方，不能只做一行补丁。

风险是快照版本迁移、将外组保留误当新授权、或对并发组变化处理过宽。控制方式是旧页显式刷新、授权与保留分开校验、真正授权变更保持完整单元比较。不扩张空组移出能力；无法证明合法时拒绝。若修复验收失败，停止含外组目标的写入并给出明确提示，不回到缩水全量覆盖。

实施后复盘必须覆盖七项要素；永久防护落在专项单测和现有浏览器 preflight/live 验证，重点断言“只改花名不影响其他字段”，不能只再写一条既有规则。
