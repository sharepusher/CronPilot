三、数据模型

job_log（在 A′ 已有列基础上追加）
  ├─ http_status   INTEGER NULL     ← 已有（b105e47）
  ├─ status        VARCHAR(16)      ← 新增：success | fail | error
  └─ fail_reason   VARCHAR(128)     ← 新增：短枚举/标签，可空

旧数据：status NULL → UI 按 http_status + content 推断展示「—」或「未知」

3.1 status 枚举（已确认草案）

值含义典型场景
success本次回调判定为成功HTTP 2xx 且未命中失败规则
fail已发出 HTTP 请求，但业务/规则判定失败4xx/5xx（配置开启时）、error_keyword 命中
error未得到正常 HTTP 响应超时、连接失败、SSRF 拦截、任务不存在等（content 以「发生严重错误」开头）

3.2 fail_reason 示例（写入时标准化，非用户自由文本）

fail_reason触发条件
http_4xx / http_5xxfail_on_http_4xx_5xx=1 且对应状态码
keyword响应体命中 error_keyword 任一词（不区分大小写）
timeoutrequests 超时（ReadTimeout 等）
connection连接/DNS/SSL 等请求层异常
blocked_urlSSRF / URL 校验未通过（未发起请求）
internal其它未分类异常

多条规则同时命中时：优先写最主要一条（建议顺序：error 类 > http_5xx > http_4xx > keyword）。

四、判定逻辑（cron_do）

请求前 URL/任务校验失败 → status=error, fail_reason=blocked_url|internal, http_status=NULL ↓ requests.get(timeout=120s) 异常 → status=error, fail_reason=timeout|connection|internal ↓ 得到 status_code + body → 写 http_status, content ↓ 若 fail_on_http_4xx_5xx 且 code≥400 → status=fail, fail_reason=http_4xx|http_5xx 否则若 keyword 命中 → status=fail, fail_reason=keyword 否则 → status=success, fail_reason=NULL ↓ 若 status≠success → wechat_info_err（与现有关键词告警合并，避免重复两条）

4.1 配置项（conf.ini / conf.ini.example）

键默认说明
fail_on_http_4xx_5xx11：4xx/5xx 记 fail 并告警；0：仅 keyword/异常算失败（兼容极老行为）
error_keywordfail,error保持现有；命中则 fail（可与 HTTP 规则叠加，告警一次）

5.1 第一行文案规则

status徽章第一行其余部分
success绿色「成功」HTTP {code} · {take_time}s（与 A′ 一致）
fail红色「失败」HTTP {code} 或「—」· 耗时 · 灰色 fail_reason
error橙色「异常」「请求异常」/「未执行回调」· 耗时 · fail_reason
NULL（旧数据）不显示徽章沿用 A′ job_log_status_line 仅按 http_status/content 推断
