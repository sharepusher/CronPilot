# RBAC 用户编辑写前意图缺失 U1 修复复盘

日期：2026-10-28 · 状态：U1 已修复并验证；U2 事务收口待确认 · 路由：`GET/POST /rbac/users/edit`

## 1. Bug 定位

旧编辑流程没有可信的“页面原始值”，POST 后直接调用写服务。即使所有字段没有变化，也会进入数据库更新、提交、审计和缓存失效链路；邮箱空值则被“保留旧邮箱”的兼容表达吞掉，无法表达管理员主动清空邮箱的意图。编辑页还混入了账户停用，绕开专用停用理由流程。

## 2. 根因

读取展示、用户修改意图和数据库当前事实被压成一组 POST 值：系统只能看到“请求值”，不能区分“未改”“主动清空”和“页面停留期间被他人修改”。写服务又用空字符串回退旧值，进一步抹平了邮箱删除语义。状态生命周期与资料编辑没有明确分界。

## 3. 测试漏洞

既有测试主要覆盖成功写入、Scope 拒绝和账号保护，没有断言原样提交时 DML/commit/审计/Token/缓存均为零，也没有快照篡改、actor/target 绑定、组顺序归一化、邮箱清空二次确认及停用字段注入用例。因此“返回成功但发生无意义写入”和“清空被静默忽略”可以长期存在。

## 4. U1 修复

- GET 基于页面实际展示字段生成无状态签名快照，精确绑定 schema 版本、actor、target、资料字段、角色与规范化业务组集合；签名只证明完整性，不替代授权。
- POST 在写事务前验签并做纯规范化，计算“页面原始快照 → 请求值”的 `intent_change_set`；空意图直接返回 `no_change`，不调用现有写服务。
- 原邮箱非空且请求为空时，只有显式确认且理由去空白后为 1～500 字才允许进入后续写边界；缺确认返回 `confirm_required`，空/超长理由返回失败。
- 用户状态在编辑页改为只读，POST 中伪造 `is_active` 不再影响目标状态；停用仍走用户列表专用流程和理由契约。
- 停用目标不能进入编辑流程，转向只读详情；密码、Token、Session、CSRF 和未回显字段均不进入签名载荷。

## 6. 同类排查

已在[编辑与修改业务流程同类一致性风险审计](../qa/编辑与修改业务流程同类一致性风险审计-2026-10-28.html)中登记其他写入口；本轮按用户要求只完成 `/rbac/users/edit`，没有把同类改造扩散到任务、业务组、标签或个人资料流程。现有 Scope 授权基线继续复验，避免把 U1 误当作授权替代物。

## 7. 预防方案

- 把“签名展示快照 → 纯规范化 → intent change set → 空意图短路”固化在 `app/rbac/services.py` 的纯函数和 `tests/test_user_edit_change_set.py`；第三方可执行 `python -m unittest tests.test_user_edit_change_set -v` 重现。
- 编辑表单不得提交账户生命周期字段；`tests/test_user_reactivation.py::TestApproverAdminCopyB4` 和专项路由测试持续断言模板无 `name="is_active"` 且伪造值被忽略。
- U2 必须复用已验签快照，在数据库当前 actor/target 再授权后执行行锁三方比较；禁止把 U1 的客户端意图判断描述为并发控制或事务原子性。

## 8. 后续闭环状态

**U2 已于 2026-10-29 完成事务闭环。**数据库当前授权、行锁三方比较、业务与审计同事务及提交结果未知语义已落地；前端无变更不发 POST、邮箱清空二次确认对话框、审计详情展示和最终 outcome 交互仍属于 U3。U3 完成前不宣称整体方案交付。
