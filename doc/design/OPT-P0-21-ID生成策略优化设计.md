# OPT-P0-21：50-bit 任务 ID 生成器最终优化设计

**状态**：待用户确认　**修订**：2026-09-09　**性质**：方案收敛与纠偏；确认前不修改实现

**关联文档**：[CronPilot 50-bit ID 生成器技术文档](CronPilot-50bit-ID生成器技术文档.html) · [新任务继承旧健康记录 Bug 设计](新任务继承旧健康记录Bug设计.html)

## 0. 决策摘要与边界

**最终推荐**：保留并升级 CronPilot 自己的 50-bit 生成器；增加 12-bit worker，worker 指纹采用稳定哈希后的 `IP + PORT + PID`；生成器只负责 `cron_infos.id`。`job_log.id` 及其他业务表主键继续由数据库自增，所有保存任务 ID 的引用列统一为 BIGINT。

1. **不撤销生成器**：任务 ID 需要避免业务表重建后从小值重新分配并绑定历史残留记录。
2. **必须引入 worker**：当前生产配置已经是 Gunicorn 两个 worker 进程，单部署实例不等于单进程。
3. **不全表推广**：只有任务身份具有跨任务生命周期、调度器和残留引用的业务意义；普通日志行和关联行只需数据库内唯一。
4. **附件隔离**：本设计不采用、改造或评价附件中的独立 Snowflake 脚本；两者没有实现或迁移关系。

## 1. 问题

现有生成器采用 `[38-bit 秒时间戳][12-bit 序列]`，状态只在当前进程内有效。两个 Gunicorn worker 在同一秒首次生成时会得到相同时间戳和序列；同秒重启、PID 复用或时钟回拨也存在重复风险。现有逻辑还把小于上一时间戳的时钟值当成“新秒”处理，会把内部时间倒退。

同时，生成器被扩展到了 `job_log.id`，而 MySQL 中部分任务引用列仍为 `INT`。这把任务身份需求错误扩散到了普通内部行主键，并留下父子字段宽度不一致。

## 2. 根因

1. **部署模型判断错误**：设计按“单实例”推导“单进程”，没有核对实际 Gunicorn `workers=2`。
2. **ID 职责未分层**：任务业务身份和日志行定位被当成同一种 ID 需求。
3. **生成器缺少进程维度**：仅有时间与进程内序列，无法区分同一服务的多个进程。
4. **fork 生命周期未建模**：若 worker 身份在 master 进程预先计算，子进程会继承同一身份与状态。
5. **异常分支不完整**：缺少明确的时钟回拨策略、worker 碰撞边界和数据库最终防线。
6. **验证范围不足**：原测试没有覆盖多进程、fork 后 PID 变化、时钟回拨、序列耗尽和 MySQL 引用列。

## 3. 最终方案

### 3.1 ID 使用范围

| 字段类别 | 最终策略 | 理由 |
| --- | --- | --- |
| `cron_infos.id` | 使用升级后的 50-bit 生成器 | 它是任务在调度、日志、健康、分组、标签和审计链路中的稳定身份；必须降低表重建后复用旧身份的概率 |
| 任务引用列 | 不生成，只保存 `cron_infos.id`；统一 BIGINT | 引用必须与父任务 ID 同宽、同语义 |
| `job_log.id` | 数据库自增；存量值不重编号 | 只承担单表行定位与排序，执行链路身份由 `trace_id` 承担 |
| 其他业务表主键 | 保持数据库自增 | 没有跨表残留重新绑定或跨系统任务身份需求 |

### 3.2 50-bit 位布局

| 字段 | 位数 | 能力 |
| --- | --- | --- |
| 自 2024-09-01 UTC 起的秒数 | 32 | 约 136 年，覆盖到约 2160 年 |
| worker ID | 12 | 4096 个 worker 槽位 |
| 同秒序列 | 6 | 每进程每秒 64 个任务 ID |

`id = (seconds << 18) | (worker_id << 6) | sequence`。最大值仍小于 `2^50`，可以作为 JavaScript 安全整数传输。该容量针对“创建任务”而非“写执行日志”；当前业务不需要每进程每秒创建 64 个以上任务。

### 3.3 worker：稳定哈希 IP + PORT + PID

- 输入指纹为规范化后的 `IP:PORT:PID`。IP 区分主机，PORT 区分同机不同服务实例，PID 区分同一 Gunicorn 实例中的多个进程。
- 使用确定性的稳定摘要算法，再截取低 12 bit。禁止直接使用 Python 内置 `hash()`，因为其结果默认随解释器启动随机化，不利于复现、排障和测试。
- IP 与 PORT 优先读取明确的运行配置；缺省时才从实际监听配置/本机地址推导。配置值必须参与启动日志，便于定位 worker 身份来源。
- PID 和 worker ID 必须在子进程内惰性初始化。每次生成前比较当前 PID 与缓存 PID；发现 PID 变化时重新计算 worker，并清空上一进程继承的时间戳与序列状态。
- 不引入数据库、Redis、文件锁或 worker 租约。该选择接受 12-bit 哈希槽位存在理论碰撞，是基于当前两进程和低频任务创建场景的工程折中，而非数学上的绝对唯一。

**运维边界**：当前默认两进程风险很低；建议单个环境的写任务进程数不超过 16。若未来需要长期运行几十个以上独立写实例，或需要“严格零碰撞”承诺，应另行改为显式分配 worker/租约，而不是继续扩大哈希假设。

### 3.4 为什么仍需要线程锁

模块全局对象已经具备“每进程单例”效果，无需额外实现 Singleton 类；但单例只表示共享一份状态，不表示对状态的复合读写是原子的。生成一个 ID 包含读取时间、判断上一秒、递增序列和写回状态，多线程或并发执行单元可能在这些步骤间交错。因此保留每进程锁，锁只保护本进程的 `last_timestamp` 和 `sequence`，跨进程隔离由 worker ID 负责。

### 3.5 时间回拨与序列耗尽

- 当前秒大于上一秒：切换到新秒，序列归零。
- 当前秒等于上一秒：序列递增。
- 序列达到 63：等待实际时间进入下一秒，不回绕到 0。
- 当前秒小于上一秒：小幅回拨时使用逻辑上的上一秒继续分配序列；若序列耗尽则等待物理时钟追平。超过可配置阈值的回拨直接拒绝生成并记录错误，禁止把内部时间倒退。

### 3.6 防止新任务继承历史残留数据

worker 哈希降低碰撞概率，但不能替代业务完整性检查。任务创建服务在为 `CronInfos` 显式设置候选 ID 后、执行已经核实存在的 `db.session.flush()` 前，检查候选值是否已出现在以下任务身份域：

- `cron_infos.id`
- `job_log.cron_info_id`
- `job_health.cron_info_id`
- `task_groups.task_id`
- `task_tags.task_id`
- 任务类型的 `operation_log.target_id`

发现历史占用时丢弃候选值并重新生成，设置有限重试次数；父表主键唯一约束继续承担并发竞争的最终防线。若最终仍冲突，则回滚事务、记录结构化碰撞日志并安全返回失败，绝不继续创建或绑定残留数据。

### 3.7 模型与类型迁移

- `cron_infos.id` 保留生成器策略；创建服务显式生成候选 ID，以便在写入前完成身份域占用检查。
- `job_log.id` 移除生成器 default，恢复数据库自增；已有 50-bit 日志主键原值保留，不重编号。
- `job_log.cron_info_id`、`job_health.cron_info_id`、`task_groups.task_id`、`task_tags.task_id`、`operation_log.target_id` 在模型和 MySQL 迁移中统一为 BIGINT。
- 迁移过程不得删除或重建业务表；先升级引用列宽度，再启用新位布局。部署窗口暂停所有任务创建写入，避免新旧布局并行。
- 已有 50-bit 任务 ID 全部保留。新布局使用同一纪元但位移更大，不依赖重新编号完成切换。

## 4. 范围

### 4.1 实现范围

- `datas/utils/id_generator.py`：位布局、worker 派生、fork/PID 检测、并发锁、回拨处理。
- `datas/model/cron_infos.py` 与 `app/services/cron_service.py`：任务 ID 的唯一生成入口和身份域占用检查。
- `datas/model/job_log.py`：日志行主键恢复数据库自增。
- 五个任务引用字段的模型与 SQLite/MySQL 双后端迁移。
- 生成器、服务、迁移、多进程和回归测试；同步原技术文档与 Bug 设计。

### 4.2 明确不做

- 不把生成器推广到所有业务表。
- 不引入 worker 注册中心、数据库租约、Redis 或分布式锁。
- 不采用附件 Snowflake 脚本的位布局或代码。
- 不重编号任何已有任务、日志或关联记录。
- 不修改 API 的 ID 字段名称和 JSON 数字类型。

## 6. 验收标准

1. 位布局断言为 32-bit 时间、12-bit worker、6-bit 序列；所有生成值为非负数且小于 `2^50`。
2. 相同 IP/PORT、不同 PID 的两个真实进程在同一秒首个 ID 不同；fork 后子进程不会继承父进程 worker 与序列状态。
3. 相同 `IP:PORT:PID` 的 worker 派生结果跨解释器启动可复现，不依赖 Python 内置随机化哈希。
4. 单进程并发生成无重复；同秒第 65 个请求等待下一秒，不发生序列回绕。
5. 模拟时钟回拨时 ID 不倒退、不重复；超过阈值时明确失败并有结构化日志。
6. 强制制造 worker 槽碰撞和历史残留占用，任务创建要么换号成功，要么事务完整回滚；旧健康、日志、分组和标签不得绑定到新任务。
7. 静态扫描确认生成器只被 `cron_infos`/任务创建服务消费，`job_log.id` 和其他表主键均为数据库生成。
8. MySQL 父任务主键与五个引用列均为 BIGINT；SQLite 和 MySQL 都走通任务创建、日志、健康、分组、标签与操作日志链路。
9. `bash scripts/cronpilot.sh test`、`bash scripts/verify_golden_path.sh`、`python scripts/smoke_routes.py --check` 全部通过。
10. HTML↔Markdown、文档完整性和链接检查通过。

## 7. 风险与回滚

| 风险 | 缓解措施 | 回滚策略 |
| --- | --- | --- |
| 12-bit worker 哈希存在理论碰撞 | 控制写进程规模；任务身份域预检；数据库主键唯一约束；结构化碰撞日志与指标 | 回滚到旧生成器代码但不回滚已生成 ID；若规模增长则另行设计显式 worker 分配 |
| 6-bit 序列限制每进程 64 个任务/秒 | 只用于低频任务创建；溢出等待下一秒 | 不得静默回绕；容量确有变化时重新评审位布局 |
| IP/PORT 推导不一致 | 显式配置优先并输出启动诊断；标准化 IPv4/IPv6 表示 | 恢复上一版本配置并停止新增任务，已有 ID 不受影响 |
| 时钟大幅回拨导致创建失败 | NTP 监控；小幅回拨使用逻辑时间；大幅回拨 fail-closed | 修复系统时钟后恢复写入，不修改既有记录 |
| MySQL ALTER 锁表或引用列遗漏 | 维护窗口执行；按父表/引用链清单逐项断言；双后端迁移分支 | BIGINT 向后兼容旧值，通常无需降回 INT；应用版本可回滚 |

## 8. 本次方案纠偏复盘

1. **Bug 定位**：上一版本文档错误建议撤销 `cron_infos.id` 生成器并改为数据库自增，且将独立附件 Snowflake 脚本的问题混入 CronPilot 生成器结论。
2. **根因**：在用户澄清两个方案无关后，没有锁定“任务 ID 防复用”和“当前实现需多进程 worker”两项前提，仍沿用前一轮候选方案继续推演，造成结论与已确认约束冲突。
3. **测试漏洞**：缺少设计决策一致性检查；未用实际 `gun.py` 的 `workers=2` 反证“单实例即单进程”的假设。
4. **修复**：全文重写为“保留任务生成器 + 引入 worker + 其他主键自增”，并明确附件脚本不属于本设计。
5. **防护测试**：验收项新增真实多进程、fork/PID 变化、哈希槽碰撞和“生成器只用于任务 ID”的静态检查。
6. **同类排查**：实施前全仓搜索 `next_id` 的所有生产调用点和任务 ID 引用列，逐一归类为“生成”“引用”或“无关内部主键”，禁止按表名猜测。
7. **预防方案**：本文件第 0 节新增四条不可互换的决策边界；每次实现批次评审必须执行 `rg -n "不撤销生成器|必须引入 worker|不全表推广|附件隔离" doc/design/OPT-P0-21-ID生成策略优化设计.html`，并将命中四条作为继续实施的前置条件。

## 9. 用户确认点

确认本设计即表示同意：**仅 `cron_infos.id` 使用 32/12/6 的 50-bit 生成器；worker 采用稳定哈希的 IP+PORT+PID；保留进程内锁；其他业务表主键使用数据库自增；五个任务引用列统一 BIGINT；不引入 worker 租约。**

用户明确确认前，不修改业务代码、模型、迁移脚本或测试。
