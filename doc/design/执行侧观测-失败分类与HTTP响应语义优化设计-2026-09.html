失败分类、HTTP 响应与请求状态语义收口

本文针对执行记录 264147763200 暴露的观测语义冲突，定义统一的数据模型、分类规则、页面交互和分批验收方案。它不改变业务成功/失败判定，只修正“失败发生在哪一层、是否收到 HTTP 响应、请求参数是否已准备/已发送”的表达。

1. 问题与根因

实证：该记录的异常是 TypeError: HTTPConnection.__init__() got an unexpected keyword argument 'assert_hostname'。异常发生在本地 HTTP 客户端初始化阶段；没有远端 HTTP 响应，因此 http_status 为空。当前主摘要显示“内部错误”，时间线却把所有 http.error 显示为“连接失败”，两者矛盾。
现象根因影响
连接类问题显示“内部错误”exception_fail_reason 只识别 requests 连接异常，其他异常统一归 internal。无法区分远端连接失败与本地传输栈故障。
时间线显示“连接失败”Presenter 对所有非 Viewer 的 http.error 硬编码该文案。同一运行出现两个失败原因。
HTTP 显示“—”请求未返回 response object，http_status 必然为空；页面未解释“未建立连接”。用户误以为 HTTP 字段被隐藏或丢失。
“实际请求：已注入运行参数”当前以已构造并保存 actual_url 判断，早于真正的 transport 调用。把“参数准备”误表达为“请求已发送”。
正文不完整展示层按角色截断（Viewer 禁止、Operator 200 字符、Admin 2048 字符）。脱敏策略与长度策略混淆，缺少截断提示。

2. 设计目标与非目标

  • 目标：单一失败分类来源；明确请求生命周期；无响应时给出可诊断解释；敏感字段脱敏但不无理由截断。
  • 非目标：不修改任务业务结果判定；不把所有 TypeError 误判成连接失败；不向 Viewer 开放响应正文或凭据。

3. 统一执行状态模型

维度枚举/字段语义

失败阶段pre_request|transport|remote_response|persistence故障发生在哪个处理阶段。

推荐新增 failure_stage、transport_state、response_received；保留现有 status、fail_reason、http_status 兼容 API。事件 detail 使用同一枚举，Presenter 不再自行推断文案。

3.1 JobLog Model 变更（本方案的持久化核心）

本方案不是只改页面文案，必须修改 datas/model/job_log.py 的 JobLog 模型。一次执行的最终摘要由 JobLog 持有，阶段事件只保存过程证据；两者通过同一组语义字段收口。

字段类型/可空语义写入规则
failure_stageVARCHAR(24)，nullablepre_request|transport|remote_response|persistence异常终态写入；HTTP 已返回时为 remote_response。
transport_stateVARCHAR(32)，nullablenot_started|prepared|sent|response_received|failed_before_response由请求生命周期边界写入；不能用 actual_url 推断。
response_receivedBOOLEAN，nullable是否获得 HTTP response object获得响应为 1；异常且无响应为 0。
  • 序列化：JobLog.to_json() 必须同步输出三个字段，避免模型与 API/调试输出不一致。
  • 迁移：scripts/ensure_business_tables.py 为旧库补 nullable 列；有 http_status 的历史记录回填为 remote_response/response_received，无响应异常回填为 transport/failed_before_response，不猜测远端是否收到请求。
  • 兼容：保留 status、fail_reason、http_status、actual_url；旧 API 字段不删除。actual_url 的语义改为“脱敏后的请求目标”，不再表示已发送。
  • 事务：JobLog 终态与三个新字段在同一次业务提交中写入；事件写入仍是 best-effort，失败只把 observability_state 标记为 degraded。

5. 写入与查询流程

根因更正：assert_hostname 在本记录中不是抽象的“依赖版本不兼容”结论，而是 CronPilot 的 _PinnedIPAdapter.init_poolmanager 将 HTTPS 专用 TLS 参数传给 HTTPConnection 的适配器协议使用错误。Batch E 应修正 HTTP/HTTPS 参数分支，并分别验证两种协议。

5.1 HTTP 适配器协议分支修复

修复对象是 app/services/url_security.py::_PinnedIPAdapter，不是更换 requests/urllib3 版本。适配器必须保存 scheme，并按协议初始化连接池：

if scheme == 'https':
    kwargs['assert_hostname'] = original_hostname
    kwargs['server_hostname'] = original_hostname
super().init_poolmanager(...)
协议连接池行为验收断言
HTTP只做固定 IP、Host header 和端口重写；不得传 TLS 专用参数。真实 session.get(http://...) 不再触发 assert_hostname TypeError。
HTTPS固定 IP，同时保留原主机名用于 SNI/证书校验。真实 HTTPS 请求仍完成 TLS 主机名校验；不能因 HTTP 修复而失去 SNI。

兼容策略：保留 make_pinned_session(pinned_ip, original_hostname, scheme) 的现有调用语义，新增 scheme 只影响适配器内部初始化；不改变 SSRF 校验、签名参数、Host header 和 run_id 观测链路。

5.2 HTTP/HTTPS 回归测试矩阵

  1. 单测直接构造 HTTP adapter，断言 init_poolmanager 不包含 assert_hostname/server_hostname。
  2. 单测直接构造 HTTPS adapter，断言两个 TLS 参数使用原始 hostname。
  3. 本地 HTTP callback 集成测试真实调用 pinned session，验证拿到 response 或明确的网络异常，不允许出现客户端初始化 TypeError。
  4. HTTPS 使用可控测试证书/本地 TLS 服务，验证 SNI 与证书主机名仍正确。
  5. 执行详情验收同时检查业务结果、failure_stage、transport_state 和时间线，不只检查页面文字。
创建 JobLog(run_id) → request_prepared(trace/sign 注入) → http.start
→ transport 调用
   ├─ 异常：写 http.error（failure_stage/reason/state）→ 无 HTTP 状态
   └─ response：写 http.complete(status/bytes) → 业务判定
→ db.write_log → 更新 JobLog 摘要与观测状态

actual_url 只记录脱敏后的“准备发送目标”；新增 transport_state 后，页面是否显示“已发送”只由状态驱动。收到响应时才填 http_status 和 response body。

5.4 单次执行的交互顺序

  1. 列表展示最终业务状态；若为异常，用户点击“查看详情”。
  2. 详情页先看顶部摘要：结果、失败阶段、失败原因、HTTP 是否收到响应。
  3. 用户展开“请求”：查看脱敏目标、参数是否准备、传输状态；这里不承诺远端已收到。
  4. 用户展开“时间线”：按 run_id + seq 查看每个阶段，异常节点必须与顶部失败分类一致。
  5. 若 response_received=true，展开“响应”查看 HTTP 状态、响应长度和有权限的正文；否则显示“未获得 HTTP 响应”及错误详情。

7. 实施范围与分批

  1. Batch A：Model 与迁移。修改 JobLog 模型、to_json() 和 ensure_business_tables.py，完成旧数据回填与 schema 验收。
  2. Batch B：分类契约。扩展失败枚举和异常映射；事件与 JobLog 共用分类函数；补齐 TypeError/ConnectionError/Timeout/HTTP 4xx/5xx 测试。
  3. Batch C：传输状态。在请求准备、发送尝试、响应接收边界写入状态；修正 actual_url 文案；无 response 时明确显示“未获得 HTTP 响应”。
  4. Batch D：Presenter/UI。统一 DTO；时间线不再硬编码“连接失败”；增加失败阶段、传输状态、截断提示；按角色验证。
  5. Batch E：依赖问题单独修复。针对 assert_hostname 做 HTTP 客户端依赖兼容性排查，独立设计、测试和发布，不与观测语义改动混合。

8. 验收标准

  • JobLog 模型、to_json()、迁移脚本和数据库实际列结构一致，旧库回填计数可追溯。
  • 同一运行的摘要、时间线、响应区使用同一 fail_reason/failure_stage/transport_state，不得出现“内部错误”与“连接失败”矛盾。
  • 无 response object 的用例显示“未获得 HTTP 响应”，且 http_status 保持 NULL；有 response 的用例显示真实状态码。
  • “参数已注入”不再等同于“已发送”；页面分别展示准备状态和传输状态。
  • Admin 对短于限制的非敏感错误正文完整显示；超限正文必须显示截断标识和原文长度；Viewer/Operator 权限边界保持不变。
  • 执行事件按 run_id 关联，观测写入失败仍显示 degraded，不影响业务结果。
  • 通过定向单测、ruff check、smoke_routes.py --check、UI 契约门禁和浏览器三角色关键路径验证。

9. 风险与回滚

风险控制
新枚举被旧 API/筛选器拒绝保留旧字段值，新增字段向后兼容；先补枚举扩展检查和 API 契约测试。
“已发送”判断被误读只由 transport_state 驱动，并保留“未确认发送”中间态。
错误正文扩大暴露面凭据先脱敏；角色控制；完整内容操作写审计日志并设长度/下载限制。
迁移失败新增 nullable 字段、双写兼容；回滚只关闭新字段读取，不删除旧数据。
决策：批准“分类统一 + 请求生命周期显式化 + 响应语义分层”作为执行侧观测下一阶段设计基线；assert_hostname 依赖兼容性问题另立实现任务，不能用“内部错误”掩盖。
