## 1. Bug 定位

1. **重定向语义：**`app/crons.py` 将两条 HTTP 调用改为 `allow_redirects=False`，但 `evaluate_http_response()` 仅将 4xx/5xx 判失败。3xx 因而成为“未到达目标却成功”的终态。
2. **IPv6 pinning：**`_PinnedIPAdapter.send()` 将 `pinned_ip` 直接拼进 URL netloc；IPv6 地址缺少 RFC 3986 所需方括号。
3. **配置契约：**`_dns_fail_open()` 保留定义和配置读取，但 DNS 失败分支已不调用它；样例配置与 Release Notes 仍称设为 1 会放行。
4. **测试契约：**`tests/test_job_health.py` 仍要求已下线的 50-bit 应用生成 ID；执行日志测试则以裸数字子串判断某条记录是否存在。
5. **Live 操作测试：**`tests/test_cron_ops_integration.py` 仍从旧页面抓取 `data-run-url`/`data-update-url`。Redesign Dashboard 已改为 `$.post(..., {id: cronId, csrf_token: ...})`，因此服务可用时仍跳过 6 项安全与权限验证。
6. **CSRF Live 测试：**`tests/test_csrf_integration.py` 默认使用种子 `admin/changeme`，但本地管理员凭据已变化；测试未验证登录结果，随后把登录页 HTML 当成 JSON，掩盖了真正的认证前置失败。

## 2. 根因（行为层）

**控制面与结果面割裂：**关闭自动跳转是为了确保每次网络连接都受 DNS pinning 保护，但改动只发生在请求参数层，未沿数据流检查 `HTTP status → evaluate_http_response → JobLog`。安全策略改变了协议状态机，却保留了“所有非 4xx/5xx 均成功”的旧业务语义。

**自动跳转的挂载范围被误判：**当前 session 只在初始协议前缀（`http://` 或 `https://`）挂载 adapter。跨协议 Location 会落到 requests 默认 adapter，完全绕过 URL 校验和 pinning；同协议但跨主机的 Location 虽仍命中 adapter，却会被重写为首跳的 pinned IP 与 Host，实际没有访问 Location 主机。两种行为都不符合“安全且语义正确的跳转”。

**地址模型过度简化：**adapter 的 URL 重写将 IP 看作可以直接串联的 hostname 字符串。IPv4 的表示恰好掩盖了问题；代码和测试都没有以地址族作为输入维度，因此新增内部 DNS/AAAA 放行后才成为稳定故障。

**配置门禁只检查可达性：**`test_config_keys` 能证明键进入 `CRON_CONFIG`，却不证明打开该键会走到预期行为分支。配置的“读到”被误当成“生效”。

**迁移后没有删除旧契约：**数据库自增替换应用层 ID 生成器后，测试仍把历史实现细节当作产品契约。HTML 局部更新测试同样把页面字节串当作数据结构，缺乏稳定 DOM 边界。Cron 操作集成测试又把旧 Vue 的 URL data 属性误当成稳定接口，且在找不到属性时 `skipTest`，将真实契约漂移伪装成环境跳过。

## 3. 测试漏洞

- 没有端到端断言“3xx 时最终 handler 是否执行、JobLog 是否失败”。仅测状态判定函数，未覆盖调用方新增的 `allow_redirects`。
- adapter 测试只覆盖 IPv4、端口和协议，未覆盖 IPv6、有端口/无端口以及 DNS 返回 AAAA 的完整链路。
- 配置测试只有静态可达性，没有配置值翻转的行为矩阵。
- 全量测试未在 ID 策略切换提交中作为阻断条件；筛选测试未解析行主键，造成假红。
- Live cron 操作测试未通过真实 Redesign 表单创建作用域内任务，既没有检查创建响应，也没有在服务可用时将任务定位失败视为失败，导致 6 项 CSRF、权限和操作链路测试被旧页面选择器全部跳过。

## 4. 修复方案评估

### 4.1 重定向

**方案 A（推荐立即实施）：**保持 `allow_redirects=False`，将 300–399 映射为 `STATUS_FAIL / redirect_blocked`，记录 Location（脱敏后）但不访问下一跳。优点是安全边界可证明且改动最小；代价是依赖跳转的任务会明确失败而非继续工作。

**方案 B（后续设计后实施）：**手动逐跳处理 Location：用 `urljoin` 解析下一跳，对该 URL 重新执行校验与 DNS 解析，并为每一跳创建新的 pinned session（不得复用首跳 adapter）。它能恢复兼容性，但必须先完成设计确认和 GET/POST 301/302/303/307/308 的完整验收；不能直接恢复 requests 自动跳转。

**方案 C（拒绝）：**重新启用自动跳转。它会再次把后续连接带出 SSRF/DNS pinning 边界。

### 4.1.1 自动重定向的准确行为与签名边界

requests 默认 `allow_redirects=True`。它把 Location 直接替换为下一跳 URL；相对 Location 会用 `urljoin` 展开，而不会自动保留原 GET URL 中的 `cronpilot_trace_id`/`cronpilot_sign` 查询参数。对于 POST，301/302/303 会被 requests 改写为 GET 并清除 body/Content-\*；只有 307/308 保留方法和 body。CronPilot 当前只在首跳注入追踪/签名字段，因此“自动跳转后是否应重新注入、是否应保持 POST”是产品与接收方协议决策，不能让 requests 默认行为替代该决策。

### 4.1.2 当前业务影响证据

以当前配置指向的本地业务库为样本，3 个启用任务均为 GET。`test163` 有 44 次 301、`testgoogle` 有 3 次 301；47 条均记录为 `error / redirect_limit`，两项任务历史成功数均为 0。也就是说，现有 adapter 的重定向兼容已失效，未发现“以前靠自动跳转完成、现在被禁用后才中断”的本地任务。相反，若将当前未提交代码直接合并，47 类调用会在首跳返回 301 后被错误记录为 success，造成执行未发生而告警消失。`test123` 无 3xx 历史记录，最新失败为 `blocked_url`，应按独立 URL 校验问题处理。该证据仅覆盖本地库，部署到其他环境前仍须按同一查询口径盘点。

### 4.2 IPv6 pinning

**推荐：**用 `ipaddress.ip_address()` 判定地址族，IPv6 生成 `[address]` netloc，IPv4 保持原表示；沿用 Host/SNI 原主机名。风险小，但必须覆盖 HTTP/HTTPS、显式端口、域名 A/AAAA 混合解析和 TLS SNI。

### 4.3 DNS fail-open 配置

**推荐：**删除 `_dns_fail_open`、样例键和对外承诺，并在 Release Notes 明确 DNS 失败恒定 fail-closed。重新实现 fail-open 会重新制造无 pinned IP 的发送路径，与本轮安全决策冲突。若需要可用性缓解，应增加 DNS 重试/可观测性，而非放开网络请求。

### 4.4 测试债务

**推荐：**将 ID 测试更新为数据库生成、正数、唯一和单调的行为契约，保留 MySQL BIGINT 关联列测试；将执行日志筛选断言改为解析 `data-id` 或返回的结构化 rows，不再搜索裸数字。两项均为测试修复，不改变生产语义。

## 5. 防护测试（修复批次必须新增）

- 本地 HTTP server：302 返回后断言 destination 未执行，且 JobLog 为 fail / `redirect_blocked`。
- 逐跳设计验收：同协议跨主机、HTTP→HTTPS、HTTPS→HTTP、相对 Location 均断言每跳使用该跳 hostname/IP，而非首跳 adapter；禁止出现默认 adapter。
- 方法/凭据矩阵：GET 与 POST 分别覆盖 301/302/303/307/308，断言最终 method、body、trace/sign 的明确协议结果。
- \_PinnedIPAdapter：IPv6 HTTP/HTTPS、有端口/无端口应产生方括号 netloc；DNS AAAA 返回时执行链路不抛 `InvalidURL`。
- 配置行为矩阵：无论 `url_ssrf_dns_fail_open` 是 0 或 1，DNS 失败都被拒绝；删除该键后配置可达性测试同步更新。
- 全量回归：新 ID 合法性和执行日志筛选应使用结构化身份断言。

## 5.1 实施结果

- **修复：**`evaluate_http_response()` 现将全部 300–399 映射为 `fail / redirect_blocked`，不受 4xx/5xx 兼容开关影响；`cron_do()` 保持首跳请求，记录脱敏后的 Location 摘要，不请求该地址。
- **DNS TOCTOU：**`validate_and_resolve_url()` 不再先走会 DNS 查询的 `validate_trigger_url()`；一次执行内只解析一次，校验和 `make_pinned_session()` 使用同一 IP。环回、链路本地、保留、组播、未指定及 IPv4-mapped IPv6 危险地址全部硬拒绝；混合 A/AAAA 回答亦整体拒绝。
- **开关收口：**`url_ssrf_observe_only=1` 与 `block_private_ip=0` 不再绕过执行期硬拒绝；RFC1918/IPv6 ULA 继续由部署 DNS 决定可达性。README 与样例配置已同步该语义。
- **IPv6：**`_PinnedIPAdapter` 使用 `ipaddress` 判断地址族，对 IPv6 netloc 加方括号，保留端口、Host 和 HTTPS SNI 行为。
- **配置：**已删除 `_dns_fail_open`、运行配置读取、样例配置键及错误承诺；遗留配置值不会改变 DNS fail-closed 行为。
- **测试：**新增/扩展 `tests/test_cron_execution_transport.py` 与 `tests/test_p0_phase_a.py`：断言 resolver 恰一次、首次 IP 被 pin、混合回答 fail-closed、危险地址不创建 session、两个开关均不可绕过；保留 GET/POST × 301/302/303/307/308、IPv6、Tracer、结果展示、ID 与日志筛选测试。
- **Live 操作测试：**`tests/test_cron_ops_integration.py` 现经真实 Redesign 表单取得 CSRF 与业务组、创建唯一作用域任务、从 Dashboard 行定位 task id；断言 Dashboard 操作只传入该 id，并验证无 CSRF 拒绝、有 CSRF 通过、viewer 既无操作入口也被端点拒绝。服务可用时创建或定位失败直接使测试失败。2026-10-12 实测 7 项通过、0 跳过。
- **CSRF 测试账号：**`tests/test_csrf_integration.py` 默认改用专用测试管理员 `admintest`，并在业务请求前断言登录 302 的目标不是登录页；认证失败不再退化为 JSON 解析错误。4 项 CSRF live 测试通过。
- **验收：**宿主环境保持服务运行后，完整套件实际运行 839 项，838 通过、1 跳过；其中 11 项 live HTTP 验证均执行通过。唯一保留项是 `TestIdReuseNoConflict.test_id_reuse_after_delete`，它以 skip 明示 SQLite 重用 ID 时存在孤儿 `TaskGroup` 冲突的历史数据风险，不是环境跳过。`ruff check app/`、文档同步/完整性与差异检查通过。关联 MySQL DDL 方言/SQLite 回放测试已通过；真实 MySQL 临时库演练因本机无 MySQL 客户端未执行。

## 6. 同类排查结论

本次确认同类风险集中在“请求参数改变但响应解释未同步”“网络值按字符串操作”“配置只读不验行为”“迁移后测试未删旧实现细节”四类。ID 关联列升级本身方向正确，但仍须在真实 MySQL 临时库验证 DDL 保留索引、自增和 nullable 语义；这属于合并前验证缺口，不应由 SQLite 方言编译测试替代。

## 7. 预防方案

1. **请求状态机测试：**在 `tests/test_cron_execution_transport.py` 建立“准备→DNS 一次解析→pinning→发送→3xx/响应/异常→JobLog”的端到端矩阵，并在 `scripts/verify_all.sh` 纳入执行。验证：`.venv-py311/bin/python -m unittest tests.test_cron_execution_transport -v`。
2. **地址分类门禁：**在 `tests/test_p0_phase_a.py` 固化未指定地址、IPv4-mapped IPv6、混合 A/AAAA、硬拒绝开关与 IPv4/IPv6 adapter 参数化测试；所有 URL 重写必须经 `ipaddress` 分支。验证：`.venv-py311/bin/python -m unittest tests.test_p0_phase_a -v`。
3. **配置行为契约：**扩展 `tests/test_config_keys.py`，除检查键可达外，为安全相关键登记“0/1 的受测业务效果”；移除配置时删除登记。验证：`.venv-py311/bin/python -m unittest tests.test_config_keys -v`。
4. **迁移契约清单：**在 ID 策略变更的设计验收中列出需删除/重写的测试契约，并把完整 `bash scripts/cronpilot.sh test` 的完成态列为合并门禁。
5. **Live UI 契约：**将 `tests/test_cron_ops_integration.py` 固定为“表单创建 → Dashboard 行定位 → 操作入口 → CSRF 正反路径 → 角色拒绝”的真实 HTTP 链路；只有服务不可达或显式 `SKIP_INTEGRATION=1` 可以跳过。验证：`CRONPILOT_BASE_URL=http://127.0.0.1:5001 .venv-py311/bin/python -m unittest tests.test_cron_ops_integration -v`。
6. **Live 账号前置断言：**`tests/test_csrf_integration.py` 使用专用测试管理员，并在任何业务响应解析前验证登录状态、跳转目标和 CSRF token；禁止依赖种子管理员默认密码。验证：`CRONPILOT_BASE_URL=http://127.0.0.1:5001 .venv-py311/bin/python -m unittest tests.test_csrf_integration -v`。

## 实施顺序与发布裁决

1. **步骤 0：冻结当前 URL 安全变更，不合并、不部署。**原因是现有代码会将 3xx 伪记为成功。此步骤不影响登录、会话或普通页面操作。
2. **步骤 1：最小安全修复（应优先进入正式设计并待确认后实施）。**保持 `allow_redirects=False`；将 300–399 统一写为失败 `redirect_blocked`；记录脱敏后的 Location；修复 IPv6 方括号；删除失效的 fail-open 开关和承诺。验收须覆盖定时触发与管理页“立即执行”，确认首跳 3xx 不会执行目标、也不会显示 success。
3. **步骤 2：处置现有任务数据，而不是自动猜测跳转目标。**由任务负责人逐项确认 `test163` 与 `testgoogle` 的业务目标：若只是验证/测试任务，应下线或修正为可访问的直接触发 URL；若目标服务有稳定规范地址，应由负责人确认后将 `req_url` 改为该直接地址并执行一次受控“立即执行”验收。不能根据历史 301 自动改写 URL，因为跳转可能改变主机、鉴权、方法和请求签名。`test123` 应独立排查 `blocked_url`，不能混入重定向修复。
4. **步骤 3：清理测试债务并恢复完整门禁。**将已废弃的 50-bit ID 断言改为数据库自增行为契约；将日志筛选改为结构化行身份断言；完成项目全量测试与 MySQL 临时库迁移验证。
5. **步骤 4：仅在存在已确认的业务需求时设计“安全逐跳跳转”。**设计必须定义最大跳数、每跳 `urljoin` 解析、每跳 URL 校验/DNS 解析/新 pinned session、GET 与 POST 对 301/302/303/307/308 的明确方法策略、trace/sign 的携带或重签名策略，以及逐跳脱敏审计。该能力是新功能，须另建正式设计并获得用户确认，不能以恢复 requests 默认行为替代。

**发布条件：**步骤 1 与步骤 3 的代码、测试和完整门禁已经通过；步骤 2 的任务 URL 调整须按任务逐项验收，独立于代码合并；步骤 4 不阻塞安全止血。真实 MySQL 临时库演练仍是关联 ID 迁移改动的发布前条件，不应用本次安全修复的测试通过替代。
