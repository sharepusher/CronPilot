日期：2026-09-18 · 状态：已修复并验证（F1）

关联评估：执行侧观测近期提交专业 Review 评估

问题：连接超时、读取超时等异常都被记录为 failed_before_response，Run Inspector 因而把“已发起但未收到响应”误报为“未确认发送”。这会影响值班人员对请求是否离开进程的判断。
结果：失败信息现在同时携带 failure_stage、fail_reason 与 transport_state；连接失败显示“连接未建立”，读取超时显示“已发起，未收到响应”，并保留旧状态兼容展示。

1. Bug 定位

问题位于 app/crons.py 的 HTTP 异常处理和 app/templates/redesign/run_inspector.html 的请求阶段文案。原逻辑只依据 _request_call_started 写入单一的 failed_before_response，无法区分连接阶段与请求已发送后的等待阶段。

2. 根因

异常分类契约只有 fail_reason，传输阶段另由一个布尔值补推；该布尔值表达“调用函数是否开始”，却不能表达“TCP/TLS 是否建立”或“请求字节是否已经发送”。展示层又将该状态直接映射成“未确认发送”，造成运行事实与用户文案不一致。行为层根因是异常到传输状态的映射缺少单一、显式的契约。

3. 测试漏洞

既有测试只验证了异常的失败原因和通用失败记录，没有同时覆盖连接超时、读取超时、连接错误三种传输阶段，也没有断言 Run Inspector 对不同状态给出不同文案。因此测试可以在状态语义错误时仍然全绿。

4. 修复

  • app/services/job_log_outcome.py 新增 exception_failure_info()：ConnectTimeout/ConnectionError 映射为 connect_failed，ReadTimeout/Timeout 映射为 sent_no_response，客户端参数错误映射为 client_failed。
  • app/crons.py 使用上述映射写入 JobLog 与执行追踪事件；未开始调用时仍写入 prepared，避免过度声称请求已经发出。
  • run_inspector.html 为 connect_failed、sent_no_response、历史 failed_before_response 提供独立文案；模型字段说明同步更新。

5. 防护测试

新增/更新 tests/test_job_log_outcome.py 与 tests/test_run_inspector_presenter.py，覆盖连接超时与读取超时的差异、连接错误状态以及 Presenter 透传。验收命令：

  • .venv-py311/bin/python -m unittest tests.test_job_log_outcome tests.test_run_inspector_presenter tests.test_execution_tracer -v（27 条通过）
  • .venv-py311/bin/python scripts/check_ui_contract.py --check（0 违规）
  • .venv-py311/bin/ruff check app/（通过）
  • .venv-py311/bin/python scripts/smoke_routes.py --check（86/86 通过）

6. 同类排查

已检索 failed_before_response、exception_fail_reason 及 transport_state 的生产代码和模板引用。生产路径已改为显式状态映射；历史状态仅保留在展示兼容分支。未发现其他将连接失败直接描述为“已发送”或将读取超时描述为“未发送”的路径。F2（运行时未写入 sent 状态）属于下一项独立修复，未在本批次混入。

7. 预防方案

建立“异常类型 → failure_stage/fail_reason/transport_state → 展示文案”的三列契约表，并将每种状态的正向和否定用例固定在 tests/test_job_log_outcome.py；任何新增网络异常必须先补映射和测试，禁止在 app/crons.py 重新写布尔值推断。评估文档的 B0 契约批次将继续作为 F2 及后续观测修复的入口。第三方可用 §5 命令复现。
