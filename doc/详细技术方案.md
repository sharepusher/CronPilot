## 1. 项目背景与目标

企业在多服务、多环境中分散维护 crontab，存在**不可视、难审计、无法 API 化、集群重复执行**等问题。CronPilot 提供中心化调度台：统一配置周期规则，通过 HTTP 触发既有业务接口，并沉淀执行日志与失败通知。

### 1.1 建设目标

| 编号 | 目标 | 验收标准 |
| --- | --- | --- |
| G1 | 任务统一管理 | Web 列表 CRUD、搜索、启停、批量删除 |
| G2 | Crontab 兼容 | 支持日/周/时/分/秒及 \*/n、列表、区间 |
| G3 | 开放集成 | REST API 增改任务、启停、上传执行明细 |
| G4 | 集群安全 | 多节点部署时同一任务不重复执行 |
| G5 | 故障可达 | 异常/关键词命中推送企微、钉钉、WebHook |

## 5. 模块详细设计

### 5.1 应用工厂 create\_app

```
create_app(config_name)
  ├── app.config ← DevelopmentConfig / ProductionConfig
  ├── logging → datas/logs/info.log (INFO filter), error.log (ERROR)
  ├── db.init_app(app)
  ├── scheduler.app = app; scheduler.init_app(app); scheduler.start()
  ├── register_blueprint(main)
  └── register_blueprint(api, url_prefix='/api')
```

### 5.2 cron\_do 执行逻辑（伪代码）

```
def cron_do(cron_id):
    with app.app_context():
        cif = CronInfos.get(cron_id)
        if not cif or invalid url: write job_log(error); return
        log_id = uuid4()
        sign = MD5(sorted_query_params + api_key)
        t0 = now()
        try:
            resp = GET(cif.req_url, params={log_id, sign}, timeout=120)
            body = resp.text or json
            if any(kw in body.lower() for kw in error_keywords):
                send_alert(task_name, body)
            JobLog.create(cron_id, body, take_time=now-t0, log_id=log_id)
        except Exception as e:
            JobLog.create(error); send_alert(e)
```

### 5.3 Web 与 API 校验复用问题

`main/views.py` 与 `api/views.py` 中 Cron 字段校验逻辑**高度重复**（约 300+ 行 ×2）。技术债务：应抽取 `services/cron_validator.py` 与 `services/cron_service.py`（add\_or\_update、toggle\_status）。

### 5.4 前端 Ajax 契约（Web）

表单 class `js-ajax-form` 提交后期望 JSON：

```
{ "errcode": 0, "errmsg": "操作成功", "url": "/cron_list" }
```

`errcode=1` 时 artDialog 提示错误；`url` 非空则跳转。

## 6. 数据库设计

### 6.1 逻辑 DDL（参考 ORM）

```
CREATE TABLE cron_infos (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  task_name VARCHAR(120) NOT NULL,
  task_keyword VARCHAR(120) DEFAULT '',
  run_date VARCHAR(25) DEFAULT '',
  day_of_week VARCHAR(10) DEFAULT '',
  day VARCHAR(20) DEFAULT '',
  hour VARCHAR(10) DEFAULT '',
  minute VARCHAR(10) DEFAULT '',
  second VARCHAR(10) DEFAULT '',
  req_url VARCHAR(200) DEFAULT '',
  status SMALLINT DEFAULT 1  -- 0停 1跑 -1结束
);

CREATE TABLE job_log (
  id INTEGER PRIMARY KEY,
  log_id VARCHAR(65) NOT NULL DEFAULT '',
  cron_info_id INTEGER NOT NULL,
  content TEXT NOT NULL,
  create_time VARCHAR(25) NOT NULL,
  take_time VARCHAR(25) DEFAULT ''
);
CREATE INDEX ix_job_log_log_id ON job_log(log_id);
CREATE INDEX ix_job_log_cron_info_id ON job_log(cron_info_id);

CREATE TABLE job_log_items (
  id INTEGER PRIMARY KEY,
  log_id VARCHAR(65) NOT NULL,
  content TEXT NOT NULL
);
```

APScheduler 自动维护 `apscheduler_jobs` 表（字段含 id、next\_run\_time、job\_state 等），勿手工修改。

### 6.2 索引与查询模式

| 场景 | 查询 | 索引 |
| --- | --- | --- |
| 任务列表 | task\_name LIKE + ORDER BY status, task\_name | 建议 task\_name 索引（当前无） |
| 单任务日志 | cron\_info\_id = ? ORDER BY id DESC | cron\_info\_id ✓ |
| 全局日志 | JOIN cron\_infos + 时间 between | create\_time 无索引，大数据量需优化 |

## 7. Cron 表达式规范

系统不存储标准 5 段 crontab 字符串，而是**拆字段**存入 cron\_infos，由 APScheduler 组装。

| 字段 | 合法值 | 扩展语法 |
| --- | --- | --- |
| day | 1-31 | `1,15` · `1-5` · `*/3` · `*` |
| day\_of\_week | 0-6 或 mon..sun | 同上；不可同时用 `,` 与 `-` |
| hour | 0-23 | 同上 |
| minute | 0-59 | 同上 |
| second | 0-59 | 同上；is\_dev=1 强制忽略 |

### 7.1 示例

| 业务含义 | 字段配置 |
| --- | --- |
| 每天凌晨 2 点 | hour=2, minute=0 |
| 每月 20 号 9 点 | day=20, hour=9, minute=0 |
| 每 2 小时 | hour=\*/2 |
| 工作日 9、14、16 点 | hour=9,14,16（或 day\_of\_week=mon-fri） |
| 一次性 2026-12-31 23:59 | run\_date=2026-12-31 23:59（date 模式） |

## 9. 回调集成规范（业务方必读）

### 9.1 回调请求格式

| 项 | 值 |
| --- | --- |
| Method | GET |
| Query 追加 | cronpilot\_log\_id, cronpilot\_sign |
| Header | User-Agent: CronPilot |
| Timeout | 120 秒（超时记 job\_log 异常并告警） |

### 9.2 签名验证步骤

1. 读取本次请求全部 query 参数（含 cronpilot\_log\_id，不含 sign）
2. 按参数名字典序升序排列
3. 拼接：`key1=val1&&key2=val2&&...&&api_key={conf.api_key}`（空值参数按源码跳过）
4. MD5(拼接串) 与 cronpilot\_sign 比较

```
// Python 参考（与 get_cronpilot_sign 一致）
def verify(params: dict, api_key: str, sign: str) -> bool:
    keys = sorted(k for k in params if params[k])
    s = "&&".join(f"{k}={params[k]}" for k in keys) + f"&&api_key={api_key}"
    return hashlib.md5(s.encode()).hexdigest() == sign
```

### 9.3 业务方响应建议

- 快速返回：耗时 < 120s，长任务应异步处理 + 调用 add\_log 上报进度
- 避免响应体包含 error\_keyword（默认 "fail"）除非确实失败
- 实现幂等：同一 log\_id 重复回调不应产生副作用
- 验签失败应返回 403 并记录（当前系统仍记 200 响应体）

### 9.4 集成时序（长任务）

```
1. CronPilot → GET 业务 /task?cronpilot_log_id=UUID&sign=...
2. 业务立即返回 {"accepted":true}（<1s）
3. 业务异步执行，每步 POST /api/cron/add_log
4. 最终状态写入 add_log 或让主日志 content 不含 fail 关键词
```

## 13. 安全方案

| 威胁 | 现状 | 加固建议 |
| --- | --- | --- |
| 未授权访问 Web | 单密码 Session | HTTPS、强密码、失败锁定 |
| API 滥用 | access\_token 明文配置 | 环境变量、IP 白名单、速率限制 |
| 伪造回调 | 可选 MD5 签名 | 业务方强制验签 + 时间戳防重放 |
| SQL 注入 | 部分 execute 字符串拼接 | 改为 ORM / 参数化 |
| SSRF | req\_url 任意 | URL 白名单、禁止内网段 |
| 敏感信息泄露 | 体验模式显示密码 | 生产 is\_dev=0 |

## 15. 风险与演进路线

### 15.1 已知风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 依赖版本陈旧 | CVE、Py3.11 上 gevent/Flask-Script 受限 | 按 [依赖升级 RFC](依赖升级RFC.html) 分层：Tier 0 Flask CLI → Tier 1 SA 1.4 渐进 → Tier 2 gevent → Tier 3/4 SA2/Flask2 |
| 多 Scheduler 实例 | 锁失效时重复执行 | 监控 + 单 worker 调度可选方案 |
| GET 回调无 body | 复杂参数受限 | 未来支持 POST + 模板 |
| 无审计日志 | 谁改了任务不可追溯 | 增加 `operation_log`（含操作人、角色/权限快照，见 OPT-P1-09） |

### 15.2 演进路线图

| 阶段 | 内容 | 优先级 |
| --- | --- | --- |
| Phase 1 | 安全加固（SQL 参数化、密码哈希、HTTPS） | P0 |
| Phase 2 | 校验/服务层重构，消除 Web/API 重复 | P1 |
| Phase 3 | Prometheus metrics + 仪表盘 API | P2 |
| Phase 4 | Vue3 管理台、Cron 可视化构建器 | P3 |
| Phase 5 | 可选 POST 回调、任务依赖 DAG | P4 |

### 15.3 依赖升级路线（权威）

详述见 [依赖升级 RFC v1.1](依赖升级RFC.html)。执行序按**耦合从弱到强**，禁止跳级：

| Tier | 内容 | 与 RBAC |
| --- | --- | --- |
| Tier 0 | Flask-Script → `flask db` 原生 CLI | **已交付**；RBAC 建表前置 |
| Tier 1 | SQLAlchemy 1.3 → **1.4**（`Model.query` 已迁移） | 可与 RBAC 并行 |
| 侧车 | requests / urllib3 安全补丁 | 独立 PR |
| Tier 2 | gevent 23.9.1 + greenlet 3.1.1（RFC-2.1 ✓）；gunicorn/APScheduler 待续 | RBAC 稳定后 |
| Tier 3/4 | SA 2.0 → Flask 2.x | 单独立项，禁止与 RBAC 首期并行 |

## 17. RBAC 与多用户技术规格（OPT-P2-10 · v2）

## 16. 与 Plombery 的架构与技术方案对比

**完整版（含页面级交互、代码路径、[§17 可借鉴优化](Plombery深度对比分析.html#s17)）：**
<Plombery深度对比分析.html>

基于 `plombery/docs/architecture.html` 与双项目源码。以下为摘要。

结论先行：

- **CronPilot**：以“**HTTP 回调触发**”为中心的通用定时调度台，适合多语言业务系统的统一触发与审计。
- **Plombery**：以“**Python Pipeline（代码即配置）**”为中心的嵌入式调度框架，强调任务链、运行元数据、实时日志流。

### 16.1 定位与边界（Execution Model）

| 维度 | CronPilot | Plombery |
| --- | --- | --- |
| 执行载体 | 外部系统（回调 URL 的业务服务） | 本进程 Python 代码（`@task` 函数） |
| 任务模型 | “单个任务 = 一个触发器 + 一个 HTTP GET” | “Pipeline = 有序 Task 集合 + 触发器列表 + 可选 Pydantic 输入” |
| 数据流 | 平台不传递任务输出给后续任务（只存日志） | 上游 task 返回值 → 下游 task 第一个位置参数（线性流水线数据流） |
| 面向对象 | 运维视角：任务与触发规则管理 | 开发者视角：把“任务编排”作为 Python 库嵌入应用 |

### 16.2 调度器与并发模型

| 项 | CronPilot | Plombery |
| --- | --- | --- |
| Web 框架 | Flask (WSGI) | FastAPI (ASGI) |
| Scheduler | APScheduler 3.6 + 自定义 BackgroundScheduler | APScheduler 3.11 + AsyncIOScheduler |
| 并发执行 | ThreadPoolExecutor（`max_workers=30`） | AsyncIO（sync 任务用 `asyncio.to_thread`） |
| misfire\_grace\_time | 50s | 60s（文档） |
| coalesce | false（积压不合并） | true（积压合并一次） |
| 水平扩展策略 | 允许多 worker/多节点：文件锁 + Redis 锁协调 | 明确建议单 worker/单副本；多副本会重复触发，需额外分布式锁 |

### 16.3 状态与审计（Run / Log / Output）

| 维度 | CronPilot | Plombery |
| --- | --- | --- |
| 运行状态机 | 任务级：`status ∈ {1,0,-1}`；执行结果主要靠日志文本 | 运行级：`PENDING/RUNNING/COMPLETED/FAILED/CANCELLED`（PipelineRun） |
| 日志 | 以回调响应体为主（TEXT）；另有 job\_log\_items 供业务回传进度 | 结构化 JSONL（`logs.jsonl`）+ WebSocket 实时推送（`logs.{run_id}`） |
| 任务输出 | 平台不保存“业务输出对象”（只保存回调返回内容） | 每个 task 输出落文件：`.data/runs/run_{id}/{task}.json`（DB 存元数据） |
| 实时性 | 无实时流（页面刷新/分页查询） | Socket.IO：run-update、logs 流（UI 实时刷新） |

### 16.4 安全与认证

| 项 | CronPilot | Plombery |
| --- | --- | --- |
| Web 认证 | 单密码（conf.ini login\_pwd）+ Session | 可选 OAuth2（Google/Microsoft）+ Session（Authlib） |
| API 认证 | 可选 access\_token（query/form） | NeedsAuth 依赖注入（启用 auth 时） |
| 执行鉴权 | 回调签名：`cronpilot_sign`（MD5 + api\_key）交由业务验签 | 任务在进程内执行；主要保护 UI/API 与 data 路径访问 |
| SSRF 风险 | 高：req\_url 可配置任意 URL（需加固白名单/禁内网段） | 低：无外部回调执行模型（但仍有外部通知/HTTP 依赖） |

### 16.5 通知与告警

| 维度 | CronPilot | Plombery |
| --- | --- | --- |
| 触发策略 | 异常 + 响应体命中 error\_keyword | 按 PipelineRunStatus 匹配 NotificationRule |
| 通道 | 企业微信 / 钉钉 / WebHook（固定实现） | Apprise（Slack/Email/Discord 等 80+，URL 配置化） |
| 消息内容 | 纯文本 + 时间戳 | 可模板化（邮件 HTML 模板） |

### 16.6 适用场景与选型建议

| 你要解决的问题 | 更适合 | 原因 |
| --- | --- | --- |
| 多语言微服务统一“到点触发业务接口” | CronPilot | HTTP 回调天然跨语言；平台只做调度与审计 |
| Python 脚本/数据管道，想要 UI + 运行元数据 + 实时日志 | Plombery | Pipeline/Task 原生模型 + Socket.IO 实时观测 |
| 需要 DAG 分支/并行/复杂依赖与大规模分布式 | 两者都不理想 | 应考虑 Airflow/Prefect/Dagster 等专业编排器 |

### 16.7 迁移与共存策略（可落地）

#### 方案 A：CronPilot 继续做“触发层”，Plombery 做“执行层（Python 管道）”

- 在 Plombery 暴露一个受保护的 HTTP 端点（如 `/api/pipelines/{id}/run`）
- CronPilot 的任务回调指向该端点，沿用现有 cron 管理与审计
- 优点：保留 CronPilot 对外统一入口；Python 复杂逻辑由 Plombery 管控
- 注意：要处理认证（token/签名）与幂等（按 log\_id 去重）

#### 方案 B：以 Plombery 替代 CronPilot（仅当你主要跑 Python 任务）

- 把每个 req\_url 背后的“业务动作”实现成 Plombery 的 `@task`；多个步骤组成 pipeline
- 用 Plombery trigger 表达 cron；UI 查看 runs + logs
- 限制：部署需严格单 worker/单副本（或额外引入分布式锁/单调度实例）
