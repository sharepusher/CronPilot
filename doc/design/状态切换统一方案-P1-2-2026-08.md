## 1. 问题

任务暂停/恢复的业务逻辑在两个 View 层各实现一份：

| 维度 | Web 端 `main/views.py` L904-936 | API 端 `api/views.py` L510-540 |
| --- | --- | --- |
| 入口 | `POST /update_status` | `POST /api/cron/edit` status 字段 |
| 切换模式 | 仅 toggle（0↔1） | toggle + 指定目标值 |
| 调度器操作 | `scheduler.resume_job / pause_job` | 同 |
| 持久化 | `db.session.add + commit` | 同 |
| 审计日志 | 无条件记录 | 仅 `old != new` 时记录 |

**行为分歧**：Web 端重复点击"暂停"会产生冗余审计记录，API 端不会。两套逻辑独立维护，未来任何规则变更（如加通知、加批量操作）需改两处。

## 2. 根因

1. Web 端最初是唯一入口，toggle 逻辑写在 view 中合理。
2. API 端添加时选择了重写而非提取，因为需求略有不同（支持指定目标值）。
3. 缺少"第二个消费者出现时强制提取到 service 层"的工程纪律。
4. `cron_service.py` 已有 `create_cron`、`update_cron`、`apply_retire`，但 toggle 在 API 端添加时未触发"去 service 层复用"的检查。

## 3. 方案

### 3.1 提取 `cron_service.toggle_status()`

在 `app/services/cron_service.py` 中新增函数：

```
def toggle_status(cron_id, target_status=None):
    """切换或设定任务状态（0=暂停/1=运行）。

    Args:
        cron_id: 任务 ID
        target_status: None=toggle, 0=暂停, 1=恢复

    Returns:
        (ok, msg, old_status, new_status)
        ok=False 时 msg 为错误信息
    """
    cif = db.session.get(CronInfos, cron_id)
    if not cif:
        return False, '项目不存在', None, None
    if cif.status == -1:
        return False, '任务已下线，不能启动或暂停；请新建任务', None, None

    old = cif.status
    if target_status is None:
        new = 1 if old == 0 else 0
    else:
        new = target_status

    if old == new:
        return True, '状态未变', old, new

    if new == 1:
        scheduler.resume_job('cron_%s' % cif.id)
    else:
        scheduler.pause_job('cron_%s' % cif.id)
    cif.status = new
    db.session.add(cif)
    db.session.commit()

    record_operation(
        action='toggle_status',
        target_id=cif.id,
        task_name=cif.task_name or '',
        detail={'status': {'old': old, 'new': new}},
    )
    msg = '已启动' if new == 1 else '已暂停'
    return True, msg, old, new
```

### 3.2 调用方改造

**Web 端**（`main/views.py` `update_status`）：

- 保留权限检查、CSRF、scope 授权
- 替换 toggle + db + scheduler 逻辑为 `toggle_status(id)` 调用
- 根据返回值构造 `web_api_return`

**API 端**（`api/views.py` `cron_edit` 状态切换部分）：

- 保留 API Token 鉴权、scope 检查
- 替换 toggle/指定状态 + db + scheduler 逻辑为 `toggle_status(id, target_status)` 调用
- 根据返回值构造 `api_return`

### 3.3 审计日志行为统一

统一为 `old != new` 时才记录审计日志（API 端当前行为）。Web 端当前无条件记录的行为是一个 minor bug——重复点击不应产生冗余审计记录。

## 4. 范围

### 4.1 改动文件

| 文件 | 改动 |
| --- | --- |
| `app/services/cron_service.py` | 新增 `toggle_status()` 函数（~30 行） |
| `app/main/views.py` | `update_status()` 替换 ~15 行业务逻辑为 service 调用 |
| `app/api/views.py` | `cron_edit()` 中状态切换部分替换 ~20 行为 service 调用 |

### 4.2 不做的事

- 不改变 Web 端和 API 端的入口 URL 或参数格式
- 不改变权限检查、CSRF、scope 逻辑（这些保留在 View 层）
- 不引入新的 API 端点

## 5. 分批

**单批次交付**，改动 3 个文件。

| 步骤 | 动作 | 验收 |

## 7. 风险

| 风险 | 等级 | 应对 |
| --- | --- | --- |
| 调度器 resume/pause 时序变化 | 低 | service 函数保持完全相同的调用顺序（先 scheduler 再 db），无时序变化 |
| 审计日志行为变化 | 低 | Web 端从"无条件记录"变为"状态变化时记录"，行为更合理。如需保留旧行为可配置 |
| 回归面 | 低 | `smoke_routes.py` 覆盖 `/update_status` 和 `/api/cron/edit` |
