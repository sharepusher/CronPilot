1. 总体结论

属于中等到较大范围的跨层改造，不是简单加状态字段，也不需要推翻现有调度器。核心复杂度在原子写入目标记录、全部调度写入口收口、失败后的恢复及新旧版本共存。字段数量和改动行数都不能单独代表风险；当前没有依据给出可靠工时、收益百分比或精确文件总量。

建议以三个问题评估：①每个入口当前在哪里 commit，目标与待应用记录能否同事务？②谁直接写 JobStore，是否存在未登记的旁路？③出现各类中断后，哪些旧行为、页面和客户端契约必须继续成立？本轮只读核查，不复用历史测试当成本轮改造验证。

2. 当前改动地图

现有位置当前边界拟改动与风险
cron_service.create_cron写任务、组、标签并提交后，直接 register_cron_job。首次 commit 前同事务创建变更记录；提交后进入统一应用服务。创建提交未知还涉及请求去重，不能只增加状态记录就宣称不会重复创建。
cron_service._update_cron_with_outcome判断有效调度变化，保存后 apply_edit。有效调度变化时 commit 前记录目标；保留资料-only/no-op 不触碰调度的契约，不能所有编辑都新增调度记录。
cron_edit_concurrency.save_task_editWeb 三方比较、授权、版本 CAS、关系写入及事务所有权自成一条链路。这是独立于共享更新函数的入口，必须在其已有事务内记录目标；不能仅改共享 cron_service 后认为 Web 已覆盖。
cron_status_apply.save_status/apply_status状态保存后直接应用；同值 no-op；签名基线重试。将有效变更关联持久记录；重试定位原变更/尝试，不因同值判断跳过尚未应用的目标。保留明确目标、权限及旧版本拒绝。
retire_cron_by_id/by_task_name、Web /cron_retire先删 Job，再提交；多个“已下线直接成功”分支。改统一提交/移除与清理重试；同步设计已下线执行保护。危险度较高，不能只加日志或只改两行顺序。
reschedule_orphan_task检查缺失后直接 add_job。它是有独立副作用的修复入口，需登记恢复目标，不得绕开统一应用与重试约束。
cron_check、CuBackgroundScheduler/CuGeventScheduler 生命周期启动残留清理直接 remove_job；自动生命周期写下线等。区分业务期望变更与正常执行推进/一次性结束，逐点决定登记、复用或豁免。遗漏则无法宣称全系统统一。
CronInfos、迁移脚本、模型加载已有 status/edit_revision；ensure_business_tables 支持双后端。优先增补新记录结构，保留旧字段语义；新增模型、索引、约束、初始化/升级/回退均验证 SQLite/MySQL。历史任务不能直接回填“已确认应用”。
Web/API、详情/列表、操作及执行日志依赖旧结果信封、签名重试和业务状态。保留旧体验或提供明确兼容映射；新增应用进度不伪造任务执行结果；页面需正式 Before/After，API 字段/头变更需说明。

3. 可复用与必须重构

可复用：build_scheduler_kwargs、job_matches_target、已启动同步接口语义、D1 成功零额外查询、异常有限核实、D2 明确目标/版本绑定、当前权限/Scope/CSRF、现有业务状态和 JobLog。现有测试作为回归基线，不因引入新结构任意放松断言。

必须新增：调度变更与尝试持久记录、集中阶段迁移、事务内记录目标、统一应用领取/结果回写、按记录恢复和用户诊断投影。必须调整：分散的 commit 调用点、直接调度调用及本地返回消息。不能把 operation_log 的 best-effort 成功日志简单改个名字当可靠待办。

4. 事务改动如何验收

  1. 逐入口列出“任务写入＋关系写入＋变更记录”的事务所有权。待应用记录插入失败时，业务变化必须一并回滚；不能先提交任务再补写 PENDING。
  2. 在 commit 之前捕获目标版本与快照；网络或 JobStore 调用放在 commit 之后，业务写锁已释放。调度器独立连接写入不能伪装成同一个业务事务。
  3. 应用领取和结果回写用条件更新目标/尝试编号，主记录投影与尝试明细同事务，不让旧结果覆盖新目标。
  4. 提交未知、应用后结果回写失败分别测试。后者可能仍保留 RUNNING，恢复要核实实际 Job，不以旧阶段值盲目重放。
  5. 业务只读/no-op 路径保持零任务/关系/调度记录 DML；有未完成调度变更时，同值提交如何关联原记录须另定义，不能把“无业务变化”当“调度已同步”。

5. 高风险兼容点

  • edit_revision 不等于调度目标版本：资料、关系变更也会推进当前版本。正式数据设计需说明两种版本如何关联，避免说明编辑使调度恢复记录无故过时，或旧调度目标覆盖新配置。
  • 旧调用旁路：新旧服务或工作进程并存时，旧代码可能写任务/JobStore 而不写变更记录。分批编码可行，但未迁移入口及旧进程须明确标记；不能在混合期称所有变更都可追踪或可恢复。生产启用的版本门槛和写者控制必须在正式设计中确定。
  • 历史数据：旧任务没有新变更记录，表示“未建立确认记录”，不等于未应用或已失败。不得把所有旧任务标 APPLIED，也不应启动时无条件重注册全部任务。
  • 创建去重：配置目标幂等不等于首次创建幂等。提交回执丢失后重复提交可能新增记录；任务名约束、客户端稳定操作标识及唯一性责任需单独核查，不能凭任务名逻辑查询宣称跨并发唯一。
  • 自动生命周期：调度扫描推进 next_run_time 与人工修改不同；一次性任务正常结束也不能被恢复器重新创建。豁免必须有依据，不能把所有 JobStore 内部写都包装为管理操作。
  • 回退：回退应用代码无法撤销已提交的目标/记录。回退前须处理在途尝试、残留目标和旧代码旁路风险，保留新表及证据；不默认删表或重置状态。

6. 建议分批与停止门禁

  1. 第一批：冻结设计与基线。完整写者清单、阶段合法组合、数据职责、原子性、恢复权限、API/页面兼容和崩溃窗口矩阵；读取实际库 API 并 Review 确认。
  2. 第二批：基础结构。模型/双后端迁移/阶段服务及独立故障测试。可以先不改现有运行路径；影子记录仅用于比较，若不与目标同事务则不得称可靠记录。
  3. 第三批：一个垂直入口。选定 D3 或另一个入口，把 Web/API/共享服务、记录、应用、恢复、反馈全部连通，验证失败后可恢复；其他入口的旁路与共享任务影响明确披露。
  4. 第四批：全部管理写入口收口。创建、调度编辑、启停、重注册和后台清理迁移；旧进程退场/启用约束验证后，才宣称全局覆盖。
  5. 第五批：按需求接后台恢复。人工重试与恢复器调用同一服务，先不启用无证明的超时接管；验收失联旧写者和重复恢复边界。

每批有独立门禁和回归结果，不能“先一口气改所有文件，最后只跑单测”。任一入口仍有无记录的有效调度写，就不能把整体标记为完成。

7. 性能成本如何量化

先测当前正常创建/编辑/启停/下线的业务 DML、事务次数、JobStore 读写、连接持有时间与耗时分布，再在同一数据与拓扑下对比。候选机制增加待办写入、领取、结果回写及尝试历史，但精确次数取决于最终协议，不先给虚构百分比。异常与重试单独测，不混入正常成功延迟。

重点指标：正常成功额外 JobStore 查询仍为 0；资料-only 与真正 no-op 新增调度记录为 0；未完成记录按状态/任务/版本索引访问，不做每请求全任务表扫描；新记录的存储增长、主记录/明细查询和连接池耗尽表现可测。低频管理操作更适合优先保证可靠记录，不代表可以忽略开销或允许无界历史/后台扫描。

8. 验证矩阵与交付结论

保留现有 D1/D2/超时、三方编辑、角色/Scope、执行日志、生命周期回归；新增“目标与记录同事务”、全部崩溃窗口、同任务目标更新、签名/记录权限、尝试历史不丢失、历史任务兼容、混合版本、SQLite/MySQL、重启恢复与真实浏览器。原来针对旧内部函数的 Mock 可能需要改注入点，但必须保留实际行为断言，不能只改 Mock 让测试变绿。

当前判断：改造方向合理，现有代码有复用基础；最需要先冻结的是事务记录与目标版本、全部写者覆盖，以及恢复时的并发边界。建议先做正式影响矩阵/设计，不立即修改现有业务实现，也不因为此前 D1/D2 已完成就跳过集成回归。本文没有实现修复、没有修改原库或提交 Git。
