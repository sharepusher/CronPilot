## 1. 问题与影响

注册审批页的批量通过、批量拒绝会逐条执行业务动作，但当前无论成功多少条都返回 `errcode=0` 和跳转 URL。页面 JavaScript 只要收到 URL 就立即跳转，既不读取 `errcode`，也不显示 `errmsg`。

**已复现：**受限管理员批量批准一条无权处理的全局申请时，数据库正确保持 `pending`、不创建用户，但响应是 `{errcode: 0, errmsg: "成功 0 条，失败 1 条…", url: "/rbac/registration_review"}`。用户被立即带回列表，失败原因不可见。

这不是越权写入：已有审批服务仍会按数据库当前授权拒绝。但它违反“用户反馈必须如实反映已提交事实”的基本交互契约，尤其会在部分成功时掩盖未完成项。

## 3. 目标、范围与非范围

### 3.1 目标

- 批量通过和批量拒绝对全成功、部分成功、全失败给出无歧义的 HTTP 与页面反馈。
- 只有所有选中项都成功时，才返回成功码并自动跳转/刷新。
- 存在任意失败时，用户在当前页面可看到成功数、失败数和逐项失败原因；不自动跳转掩盖结果。
- 不改变已有逐项 fail-closed 业务行为、授权规则、CSRF、审计和事务语义。

### 3.2 范围

- `POST /rbac/registration_review/batch_approve` 与 `batch_reject` 的响应契约。
- 注册审批页两个批量按钮的提交、结果展示、刷新交互与无障碍通知。
- 路由、服务结果、模板 DOM、浏览器交互的定向测试与交付证据。

### 3.3 非范围

- 不修改单条通过/拒绝接口，不重写注册审批业务服务。
- 不改变任何审批授权规则；范围外审批仍由既有数据库当前事实守卫拒绝。
- 不解决审批列表的精确组匹配和旧 Session 可见性；该问题另立 R2 方案。
- 不把批量操作改为全有或全无事务：保持已存在的“逐项执行、允许部分成功”业务语义。

## 4. 权威结果契约

沿用项目既有 JSON Envelope：`errcode` 表示“本次批量请求是否完全达成”，`errmsg` 供人读，`data/result` 承载可编程摘要。HTTP 状态仍为 200；鉴权、CSRF 与参数缺失继续沿用现有失败响应。

| 结果 | errcode | url | data.outcome | 页面行为 |
| --- | --- | --- | --- | --- |
| 全部成功 | 0 | 审批列表 URL | `all_success` | 成功 Toast 后跳转刷新；显示“已成功通过/拒绝 N 条”。 |
| 部分成功 | 1 | 空 | `partial_failure` | 当前页显示 warning 结果条；成功项已落库，失败项及原因可见；用户点击“刷新列表”后取得最新状态。 |
| 全部失败 | 1 | 空 | `all_failure` | 当前页显示 error 结果条；列表不自动跳转，用户可直接继续检查或重试。 |

```
{
  "errcode": 1,
  "errmsg": "已通过 1 条，失败 1 条",
  "url": null,
  "data": {
    "operation": "approve",
    "outcome": "partial_failure",
    "success_count": 1,
    "failure_count": 1,
    "failures": [{"id": 42, "msg": "您无权授予全局管理权限"}]
  },
  "result": "与 data 相同"
}
```

**重要语义：**部分成功使用 `errcode=1` 并不表示所有业务动作回滚；它精确表示“选中的所有目标没有全部完成”。`data.outcome` 区分部分与全失败，页面以 warning 而不是 error 呈现部分成功。

## 5. 页面 Before / After

本设计只改变批量操作完成后的反馈区，不改变列表列、筛选、确认弹窗或单条审批交互。

### BEFORE · 部分失败

页面跳转完成

列表重新显示；用户不知道“2 条中哪一条失败、为什么失败”。

批量通过

实际：成功 1 条、失败 1 条，但失败信息已随跳转丢失。

### AFTER · 部分失败

**批量通过未全部完成：**成功 1 条，失败 1 条。申请 #42：您无权授予全局管理权限

刷新列表关闭结果

当前页不自动跳转；用户确认结果后主动刷新，避免掩盖尚未完成的申请。

### AFTER · 全部成功

批量通过成功：已处理 2 条，正在刷新列表…

保留现有快速刷新体验；只有全部成功才自动跳转。

### AFTER · 全部失败

**批量通过未完成：**成功 0 条，失败 2 条。逐项列出失败原因。

不跳转、不伪造成功；原始列表仍可用于检查和重新选择。

## 6. 实施设计

### 6.1 后端：统一批量结果组装

在 `app/rbac/views.py` 提取仅供本模块使用的结果组装函数，输入操作类型、逐项结果，输出上述摘要。两个批量路由必须共同调用它，避免再次产生两个不一致的结果协议。

解析既有 ids / comment
→ 保持当前逐项 approve\_registration / reject\_registration
→ 收集 success\_count 与 failures[{id, msg}]
→ failure\_count == 0：code=0, outcome=all\_success, url=列表 URL
→ success\_count > 0：code=1, outcome=partial\_failure, url=''
→ success\_count == 0：code=1, outcome=all\_failure, url=''
→ web\_api\_return(..., data=summary)

不得改变逐项调用顺序、不得因任一项失败撤销先前已成功的审批、不得把异常原文放入 `msg`。失败消息继续来自既有服务层受控文案。

### 6.1.1 原始异常与 trace\_id 关联

失败分为业务失败与系统异常。“申请不存在”“已处理”“无权授予”等受控业务文案可返回前端，不生成关联号。数据库、驱动或未知程序异常必须使用 `logger.exception()` 记录原始异常与完整 traceback，日志同时记录 32 位十六进制 `trace_id`、操作类型和申请 ID。

```
ERROR ... trace_id=a7c921... operation=approve request_id=42
Traceback ...
DatabaseError: [原始异常仅在服务端日志]
```

客户端对同一失败项仅获得 `{id, msg: "服务器内部错误，请稍后重试", trace_id}`，不返回异常类型、SQL、路径、凭据或 traceback。若异常已在服务层捕获，`trace_id` 必须由服务层生成并随受控结果传递；路由不得二次生成无法对应原始日志的假关联号。本地可从 `datas/logs/local-server.log` 按 `trace_id` 检索；生产环境在实际 systemd/容器日志中使用同一关联号。

### 6.2 前端：结果条优先于导航

在 `registration_review.html` 的批量条之后新增空的页面级结果容器，使用 `aria-live="polite"`；全失败使用 `role="alert"`。页面脚本新增一个只用 `textContent` 写入结果的渲染函数，禁止拼接服务端消息到 `innerHTML`。

- **all\_success：**调用现有 `CpToast.success()`；仅在 `errcode===0 && url` 时跳转。
- **partial\_failure：**调用 `CpToast.warning()`；渲染 warning 结果条和“刷新列表”按钮，不跳转。
- **all\_failure：**调用 `CpToast.error()`；渲染 error 结果条和“关闭结果”按钮，不跳转。
- **网络/非 JSON：**保持现有错误 Toast；两个批量按钮恢复可用，避免被永久禁用。

页面专属样式必须放入 `app/static/css/redesign-pages.css` 的 `.cp-page-reg-review` 作用域，使用既有 `--cp-*` token；模板内不新增超过 3 行的非注释 CSS。

### 6.3 防重复提交与确认框

现有批量批准确认框和批量拒绝输入框保留。两个异步回调在请求开始时禁用相应确认按钮，完成、失败、网络错误后恢复；页面级结果展示不得通过嵌套 form 或 Bootstrap modal 实现。批准仍使用 `CpConfirm.show({body: ...})`，拒绝仍使用现有页面内 `CpModal`。

## 10. 风险、回滚与完成定义

| 风险 | 控制 | 回滚原则 |
| --- | --- | --- |
| 把部分成功当成完整失败，误以为数据库已回滚 | 明确 `outcome` 与成功/失败数量；页面文字写明“成功项已完成”。 | 可回滚结果条样式，但不得恢复固定成功码或自动跳转掩盖失败。 |
| 接口字段影响历史调用方 | 仅修改本页面专用批量端点；保留既有 `errmsg/result/url` 字段，新增 data 摘要。 | 保留 B1 的后端三态契约，前端可暂时降级为不跳转+Toast。 |
| 失败详情被注入页面 | 页面用 `textContent`，服务端只传受控业务文案。 | 不得改用 `innerHTML` 输出错误详情。 |
| 页面成功项状态陈旧 | 部分/全失败不自动跳转，提供显式刷新；全部成功才自动刷新。 | 不得静默刷新并吞掉详情。 |
