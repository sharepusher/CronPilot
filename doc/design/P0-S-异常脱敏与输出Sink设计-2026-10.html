1. 问题与根因

异常文本、请求参数、URL query、JobLog、operation detail、Webhook/IM 和应用日志使用不同路径；任一 catch-all 将 str(e) 写入响应或通知，都可能泄露密码、token、sign、cookie、连接串或内部 URL。

2. 范围与安全目标

目标是单一脱敏策略在所有 sink 生效，默认拒绝原始异常文本出站。覆盖 HTTP JSON/HTML、结构化日志、JobLog、operation detail、Webhook/IM、审计与异常格式化；不改变业务认证或存储模型。

3. 敏感字段与 sink 矩阵

类别必须遮蔽允许保留
凭据password、token、api_key、sign、cookie、Authorization、连接串字段名、长度/是否存在、脱敏占位符
URL/请求体query 中的凭据、完整敏感 body路径、非敏感参数摘要、request_id/execution_trace_id
异常原始 DB/网络/依赖异常文本对用户和通知输出注册 code、安全 message/detail；受控应用日志中的脱敏堆栈

不同 sink 不得使用不同正则自行处理。脱敏函数必须在写入 DB、日志或通知之前运行；展示层屏蔽不是安全边界。

4. 流程与方案

输入/异常上下文 → 统一 sanitizer（递归 dict/list、URL、Header、文本）→ sink adapter → 持久化/发送。若 sanitizer 失败，按 fail-closed 仅输出通用 message、code、request_id/trace，不输出原文，并记录受控基础设施告警。

  • HTTP：catch-all 返回通用文案，不允许 errmsg=str(e) 或 msg=str(e)。
  • JobLog/operation detail：保存已脱敏 detail，不能作为原始请求体或异常文本旁路。
  • Webhook/IM：仅发送安全摘要与关联 ID，不发送堆栈、凭据或原始 URL query。
  • 日志：结构化字段分离；traceback 进入受控日志前同样经 sanitizer。

5. 分批、验收与风险

批次退出条件
S-1字段分类、统一 sanitizer、递归/URL/Header 单测和 fail-closed 测试完成。
S-2HTTP、JobLog、operation detail、日志、Webhook/IM sink 清单逐项接入。
S-3嵌套异常样本在每个 sink 均无明文；静态扫描无 catch-all 原文回传。

风险是过度脱敏损失排障信息；用 code、操作、transport、结果和关联 ID 保留最小可观测性。任何发现泄漏立即停止 detail 输出，仅保留通用 message + 关联 ID。

6. 确认点

确认后先冻结 sink 清单和敏感字段分类；新增凭据数据库字段须另列所有可访问 RBAC 角色及写入前脱敏要求。

7. sink 台账与关闭门槛

静态风险证据：app/main/errors.py 将异常和 traceback 写入日志；app/common/functions.py 的 IM/Webhook 错误路径使用 str(e)；app/crons.py 多处把异常文本/traceback 写入执行与通知路径；app/main/views.py 将异常传入通知辅助函数。以上是待治理的源码证据，不表示每个接收者或保留期已核实。

sink已知来源接收者/保留期强制控制与验收
HTTP JSON / HTML异常 handler、helper、模板与错误处理器实际请求者；缓存/保留由 S-1 核验固定安全文案，原始异常不进入 body/DOM；HTTP 样本测试。
独立审计出口审计写入/序列化/读取入口，S-1 逐函数定位逐角色核验，不能从 operation detail 推定写入前与导出检查，审计读取否定路径。
应用日志errors.py、crons.py运维访问与保留策略须在 S-1 记录脱敏 traceback；嵌套凭据样本不可见。
JobLog / operation detailcrons.py、业务写入点精确 RBAC 角色与保留期须逐路由核验写库前脱敏；页面、导出与 API 均回归。
Webhook / WeChat / DingTalkcommon/functions.py、main/views.py外部服务/群组接收范围须登记只发送 code、安全摘要、关联 ID；不含原文/堆栈/query。

任何 sink 台账缺少代码位置、数据主体、接收者、保留期、控制或测试 ID，都不能进入 S-2。无法确认访问角色时必须标注“待 S-1 核验”，不得假定已有 RBAC 保护。P0-S 是“已发现潜在泄漏路径的安全前置”，其关闭条件是每个已登记 sink 的正反向样本均通过，而不是仅有 sanitizer 单测。

证据等级与安全验收

目前结论限于源码风险路径，尚未证明生产发生泄漏。S-1 台账分别记录静态发现、脱敏样本复现、生产事件证据；没有后两者时不得升级措辞。保证范围是已登记字段/格式和测试样本，任意自由文本无法仅靠正则证明无秘密；对用户/通知优先使用字段白名单和固定摘要。sanitizer 失败的告警只允许固定文本与合法关联号，禁止再格式化原异常或递归调用同一失败链。

S-01：每个 sink 注入嵌套 password/token、URL query、Authorization、Cookie、连接串与异常链，输出不可含测试秘密。S-02：强制 sanitizer 抛错，所有 sink 只出现安全固定摘要。S-03：台账每行具备生产函数、接收者、保留期、控制与测试 ID；HTTP/审计不得遗漏。拟新增 tests/test_error_sink_sanitization.py，命令 python -m unittest tests.test_error_sink_sanitization -v；台账 tests/fixtures/error_sink_registry.json；报告 doc/qa/error-sink-acceptance.html。以上尚未实施执行。
