# 调度器幽灵任务清理设计

**编号**：OPT-P0-20   **版本**：rev.2   **日期**：2026-08-26

**关联**：OPT-P0-18（系统对账安全加固）、`app/crons.py::cron_check()`、`app/services/cron_service.py::retire_cron_by_id()`

## 1. 问题

### 1.1 现象

本地数据库中发现多个"幽灵任务"：`cron_infos.status = -1`（已退休）但对应的 `apscheduler_jobs` 记录仍存在。
具体案例：`cron_9`（testtest）和 `cron_13`（health-live-test）在数据库中 `status=-1`，
但 `apscheduler_jobs` 仍持有这两条 job，服务每次启动都会将它们加载进调度器。

### 1.2 预期

已退休任务（`status = -1`）**不应存在**于 `apscheduler_jobs` 中。
系统应在退休流程和周期对账中保证两库的一致性。

### 1.3 影响

| 影响面 | 描述 |
| --- | --- |
| 资源浪费 | 调度器每次 tick 仍会为幽灵任务计算下次触发时间 |
| 执行噪音 | 若 `cron_do()` 仍能查到 `CronInfos` 记录（status=-1），则可能尝试回调并产生错误日志 |
| 监控干扰 | 孤儿任务计数器不统计 `status=-1` 的任务（`cron_check` 跳过），幽灵任务成为监控盲区 |
| 数据一致性 | 两库状态不一致，管理员查看 `apscheduler_jobs` 时会看到不该存在的条目 |

## 2. 根因

### 2.1 Bug 1：`retire_cron_by_id/by_task_name` 中 `remove_job` 失败被静默吞掉

退休函数的调用顺序为：

apply\_retire(cif, reason) # ① 写 status=-1 到 cron\_infos（内存）
try:
scheduler.remove\_job(...) # ② 从 apscheduler\_jobs 删除
except Exception:
\_log.warning(...) # ③ 异常被吞，仅日志
db.session.commit() # ④ status=-1 持久化

**问题**：步骤 ② 失败时，步骤 ④ 仍然执行。结果：`cron_infos` 中 `status=-1`，
但 `apscheduler_jobs` 中 job 仍在。此后没有任何机制修复这种不一致。

**产生条件**：

- 数据库锁竞争（SQLite 写锁、MySQL 行锁超时）
- APScheduler 内部状态异常（如 JobStore 未初始化完成时就收到 remove\_job 请求）
- 历史 `db.drop_all()` 事件后手工恢复了 `cron_infos` 但未同步清理 `apscheduler_jobs`

### 2.2 Bug 2：`cron_check()` 只检查"正向孤儿"，忽略"反向孤儿"

当前 `cron_check()` 的检查逻辑：

for item in cron\_infos:
if "cron\_{id}" not in apscheduler\_job\_ids:
if item.status == -1:
continue # ← 已退休的跳过（不关心）
orphan\_count += 1 # ← 只统计"活着但不在调度器"的

**遗漏方向**：从未检查"`apscheduler_jobs` 中存在，但 `cron_infos` 中 `status=-1`"的情况——即**反向孤儿/幽灵任务**。

OPT-P0-18 安全加固时，将自动下线改为仅告警，但只加固了"正向"方向，未考虑"反向"方向。

### 2.3 启动时无一致性修复

scheduler.start() # 从 apscheduler\_jobs 加载所有 job（含幽灵）
cron\_check() # 只检查正向孤儿 → 幽灵任务安全通过

应用每次重启都重新加载幽灵任务，形成永久性的不一致。

## 3. 方案

### 3.1 推荐方案 A：双向一致性保障

分两层修复，同时堵住产生入口和发现已有问题。

#### A1. 退休流程加固（堵产生入口）

在 `retire_cron_by_id()` 和 `retire_cron_by_task_name()` 中：

- **先 `remove_job`，后 `apply_retire` + `commit`**——如果 `remove_job` 失败则整个退休操作失败，不会产生不一致
- 如果 `remove_job` 抛出 `JobLookupError`（job 本来就不在调度器中），视为正常（幂等），继续退休流程
- 其他异常向上抛，调用方收到错误信息，管理员可重试

```
def retire_cron_by_id(cron_id, reason):
    err, reason = validate_retire_reason(reason)
    if err:
        return err, None
    cif = db.session.get(CronInfos, cron_id)
    if not cif:
        return '项目不存在', None
    if cif.status == -1:
        return None, cif

    # ── 先从调度器移除（幂等：JobLookupError 视为已移除） ──
    job_key = 'cron_%s' % cif.id
    try:
        scheduler.remove_job(job_key)
    except JobLookupError:
        _log.info('job %s already absent from scheduler', job_key)
    except Exception:
        _log.error('remove_job failed for %s, aborting retire', job_key, exc_info=True)
        return '调度器移除失败，请稍后重试', None

    apply_retire(cif, reason)
    db.session.commit()
    _record_retire(cif)
    return None, cif
```

#### A2. `cron_check()` 增加反向孤儿检测与自动清理

在现有"正向孤儿检测"之后，增加"反向扫描"：

```
# ── 反向扫描：检测幽灵任务（调度器中有，但业务库已退休） ──
cif_map = {item.id: item for item in cifs}
ghost_count = 0
for job_id in job_ids:
    if not job_id.startswith('cron_'):
        continue
    try:
        cron_pk = int(job_id.split('_', 1)[1])
    except (ValueError, IndexError):
        continue
    cif = cif_map.get(cron_pk)
    if cif and cif.status == -1:
        ghost_count += 1
        current_app.logger.warning(
            "ghost job detected: %s (task=%s, status=-1) — removing from scheduler",
            job_id, cif.task_name or '',
        )
        try:
            scheduler.remove_job(job_id)
        except Exception:
            current_app.logger.error("failed to remove ghost job %s", job_id, exc_info=True)
    elif cif is None:
        # job 在 apscheduler 中但 cron_infos 无对应记录 — 仅告警，不自动清理
        # 原因不确定（可能是数据丢失、迁移中断等），需人工排查
        ghost_count += 1
        current_app.logger.warning(
            "stale scheduler entry: %s — no matching cron_infos record, manual action required",
            job_id,
        )
```

**安全性说明**：此清理策略遵循**最小权限原则**：

1. **确定性清理**：只自动清理 `status=-1`（已退休）的幽灵任务——状态明确，无歧义
2. **不确定性仅告警**：`cron_infos` 中无对应记录的调度器残留，原因可能是数据丢失、迁移中断等，**仅记录告警日志**，由管理员人工排查决策
3. 清理方向是"从调度器中删除"——是可逆操作（重新上线任务会重新注册到调度器），不像正向孤儿的 `apply_retire` 那样不可逆
4. 与 OPT-P0-18 的安全原则一致：不确定性场景一律"仅告警 + 人工决策"

### 3.2 备选方案 B：仅日志告警，不自动清理

在 `cron_check()` 中增加反向扫描，但只记录告警日志 + 更新 Prometheus 指标，不执行 `remove_job`。管理员需通过数据库手动清理。

| 维度 | 方案 A（推荐） | 方案 B |
| --- | --- | --- |
| 一致性恢复 | 自动修复，启动后即一致 | 人工处理，窗口期内不一致 |
| 安全性 | 仅清理确定性已退休记录（status=-1）；不确定性残留仅告警 | 完全无风险 |
| 运维成本 | 低（确定性自动清理 + 不确定性人工处理） | 高（所有情况均须人工排查 + SQL 操作） |
| 复杂度 | 中等（需处理 `remove_job` 异常） | 低 |
| 与 P0-18 一致性 | 确定性反向清理 + 不确定性仅告警：严格对齐"不确定场景不自动操作" | 严格"对账不修复" |

**推荐方案 A**：对于 `status=-1` 的幽灵任务，清理是确定性安全的——任务已退休，调度器残留无意义。对于 `cron_infos` 无记录的残留，原因不确定，遵循 P0-18 原则仅告警。两种情况区分处理，兼顾自动化与安全性。

### 4.1 明确不做

- 不修改 `cron_check()` 的正向孤儿处理逻辑（OPT-P0-18 已固化"仅告警"策略）
- 不引入分布式锁或事务协调器（当前 SQLite 单进程场景不需要）
- 不修改 `CuGeventScheduler.py` / `CuBackgroundScheduler.py` 中的 `update_cron_info` 逻辑（自身已有 `remove_job` 调用）
- 不做 `ensure_business_tables.py` 的改动（不是一致性校验的职责范围）

## 7. 风险

| 风险 | 概率 | 影响 | 缓解 |
| --- | --- | --- | --- |
| `remove_job` 在 `cron_check` 中失败 | 低 | 幽灵任务残留到下一轮对账 | 已 try/except 并记录 ERROR 日志；下一轮 cron\_check 会重试 |
| 退休流程变更影响现有 Web/API 退休入口 | 中 | `remove_job` 超时时用户看到"调度器移除失败"错误 | 用户可重试；且幂等（`JobLookupError` 被豁免） |
| 并发：`cron_check` 与手工退休同时操作同一 job | 极低 | `remove_job` 中一方得到 `JobLookupError` | 两侧均已将 `JobLookupError` 视为正常 |

## 附录 A：完整因果链时间线

1. **旧版 `cron_check()`**：发现孤儿任务时直接调用 `apply_retire()`，设置 `status=-1` + 调用 `scheduler.remove_job()`
2. **2026-09 配置错误事件**：`conf.ini` 中 `cron_db_url` 指向 `sqlite:///:memory:`，重启后 JobStore 为空，`cron_check()` 将全部 9 个任务自动下线
3. **OPT-P0-18 安全加固**：移除 `cron_check()` 中的自动下线逻辑，改为仅告警。但只处理了"正向"方向
4. **历史 `db.drop_all()` 事件**：测试脚本意外删除业务表，但 `apscheduler_jobs`（独立 engine）不受影响。后续恢复/重建 `cron_infos` 时未同步清理 `apscheduler_jobs`
5. **持续至今**：每次服务重启，`scheduler.start()` 加载 `apscheduler_jobs` 中的幽灵任务；`cron_check()` 只检查正向孤儿，幽灵任务安全通过
