## 1. 现状、问题与根因

**已核实：**`.github/workflows/unit-tests.yml` 在相关路径的 push/PR 上运行 Python 兼容矩阵及 `unittest discover`；现有 user\_edit\_change\_set、user\_edit\_scope\_projection、user\_edit\_mysql\_guard 均在发现范围内。因此“没有自动回归”并不准确。该 workflow 顶层有 paths 过滤，其 GitHub required 状态未在本轮查询，不能推定已配置。

`scripts/verify_user_edit_group_preflight.py` 已执行真实模板 JS，但只在隔离 DOM 拦截 Ajax，不连接服务；不能替代角色登录、确认和数据库断言。`visual-regression.yml` 负责截图比较，不能代替行为测试。MySQL 工具有专用库保护和业务验证，但[锁释放增强设计](RBAC用户编辑锁释放验收增强设计-2026-10-29.html)仍待确认，其服务返回边界证据缺口不能冒称已补齐。

**根因：**规范、人工 Review、运行入口与合并条件缺少可追踪连接；全量绿测不能展示哪些条款真正被执行，缺失真实环境也可能只得到 skip。方案以检查责任、场景标识和结果证据建立连接，不靠搜索函数名判断正确性。

## 2. 可直接使用的检查单

## 3. 行为回归矩阵：按风险观测，而非按文件名判正确

| 用例组 | 场景与必须断言 | 现有依据 / 待补范围 |
| --- | --- | --- |
| B01 无修改 | 正常页面零 POST；绕过 JS 后零业务 DML/成功审计/授权副作用。 | 现有 no\_change 路由测试 + preflight；完整页面执行接入 G2。 |
| B02 单字段 | 只改花名：仅业务花名和声明的系统元数据变化；关系表零 DML；role/email/Token/auth\_version/cache 不变；审计仅 nickname。 | scope\_projection 的 profile\_only\_no\_relationship\_dml\_or\_auth\_side\_effects。 |
| B03 部分 Scope | actor A / target A+B：原样、只改资料均保留 B；actor A/C 真改 A→C 后 C+B；非法新增及伪造外组删除不能生效。 | 现有 scope\_projection；需补直接伪造外组删除意图的独立负例，不以新增拒绝代替删除边界。 |
| B04 当前授权 | actor 换组/降权、target 停用/离开管理交集：拒绝且无部分写入。 | 现有 change\_set、scope\_projection；专项映射须逐例标明触发时点。 |
| B05 并发 | 同字段冲突不覆盖；无关资料/外组并发保留 C；耦合授权不拼接；重复等价结果不再次 bump/审计。 | 现有两个业务模块；MySQL 层复验真实事务，不把 SQLite 当锁证据。 |
| B06 基线/确认 | 坏/旧 token 拒绝；确认/多次错误回显保持 T0；取消零 POST；完成确认后只清空预期邮箱；字段名唯一。 | 现有 P1 测试；G2 必须跑实际登录、模态确认、原生提交及恢复 JS。 |
| B07 原子性 | 审计 flush 失败业务回滚；commit 异常返回 unknown；不记录凭据，不假报确定失败。 | 现有 change\_set。故障注入仅绑定隔离用例，不加生产开关。 |
| B08 生命周期 | 服务返回后、原上下文清理前，探针验证锁已释放；校准能检出故意省略终态回滚。 | 锁释放增强待确认实施，依源设计验收。旧脚本绿测不计此组完成。 |

这套基线最先覆盖用户编辑。新编辑入口必须声明自己的字段/关系/命令语义并登记适用用例，不能仅运行用户编辑基线就宣称新入口已被验证。不存在关系的入口可对 B03 给出 N/A，不能因此跳过并发/原子性。

## 4. 分层门禁与改动分类

复用现有全量 unittest 兼容矩阵，保持原 job 不变。新增一个 Python 3.11 专项 runner 产生条款级结果，承担少量有意重复以获得稳定诊断；不再复制整个 Python 矩阵。暂不引入复杂通用测试框架、全站端点注册平台或新增运行时依赖。

| 层 | 内容与触发 | 通过条件 |
| --- | --- | --- |
| G0 适用性/契约检查 | 每个 PR、main/master push 都执行；读取 git diff（base→tested SHA）、改名/删除的两侧路径。规则/契约文件变动也触发自身测试。无法分类时保守执行所有相关层或报错，不默认免测。 | 分类报告有效；声明范围与选定层匹配；拟新增 runner 的自测覆盖改名、删除、坏 diff、缺基线、取消/skip 和缺报告。 |
| G1 服务行为 | app/\*\*、datas/\*\*、tests/\*\*、配置/依赖及编辑验证工具改动均执行。仅普通文档变更可 N/A；规范/分类器/映射改动至少执行 G0/G1。固定加载已有三个用户编辑模块，按 B01–B09 登记覆盖，不复制算法。 | 固定模块存在、用例发现数非零、登记用例均执行且无 skip；失败/删除/无法导入阻断。测试数量变化需评审，不用历史固定数量当唯一正确性门禁。 |
| G2 浏览器行为 | app/templates/\*\*、app/static/js/\*\*、样式及用户编辑路由/服务/Scope/policy/context、对应浏览器脚本和测试/依赖变动。包括纯后端影响页面的路径，不能只看模板后缀。 | 实际模板 DOM preflight + 独立测试服务的目标角色登录/正反向/确认/原生回显；网络与 DB 断言全部通过。无浏览器或无样本不 skip。 |
| G3 MySQL 事务 | RBAC services/views/policy/Scope/认证边界、datas 模型/迁移、DB相关配置/依赖、事务测试/专用 MySQL 工具变更。ORM 和 DB 依赖按保守规则升级。 | 专用新空库真实通过业务事务、关系保留与 B08。B08 未实施前本层不得标“全部完成”。非事务普通 CSS/JS 不强制启动 MySQL。 |

分类器是保守的路径触发器，不是语义证明。所有新增/修改编辑行为还必须由作者/Reviewer 检查 C01–C10；新入口的测试映射与分类规则同 PR 修改。示例：只改 user\_form→G1+G2；只改 update\_user\_management→G1+G2+G3；只改说明文档→G0，其他层明确 N/A。

**场景映射契约：**拟新增 `tests/contracts/edit_contract_cases.json`，每项记录稳定 case\_id、适用入口、规范条款、执行层与测试完整标识。runner 必须将实际发现/执行的测试标识与映射逐项核对，禁止仅检索测试名称存在；必测项缺失、重复标识、所属层不符或被 skip 均阻断。该文件不接受人工 pass 值。首次只登记已有用户编辑入口；扩展新入口须补自己的业务断言，不能借基线通过冒称覆盖。

## 5. 稳定的合并检查与防假绿

拟新增 `.github/workflows/edit-contract.yml`，使用 pull\_request、push main/master、workflow\_dispatch；若仓库启用 merge queue，则补 merge\_group 并按该事件的 base/head 计算。workflow 顶层不设 paths 过滤，子 job 根据 G0 结果执行；最终 `Edit contract / required` 必须使用 always 语义收集全部依赖结果。

只有 G0 有效且所有被选层都成功、报告齐全且 tested SHA 与当前 run 一致时才通过；被选层的 skipped/cancelled/failure/空报告一律不通过。不适用层必须有 G0 记录的理由，汇总不能简单把所有 skipped 当 success。整次 workflow 因提交信息或 Actions 平台而没运行，不能生成虚假的汇总成功；required 状态缺失应保持阻断。

GitHub 官方说明：[required workflow 被 paths 过滤跳过时可能保持 Pending](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)。因此不直接把现有带 paths 的 job 改成新的唯一 required。具体规则设置属于外部仓库管理，不从 YAML 存在推定已启用。

PR 清单内容真实与否仍由 Reviewer 判断；结构检查只能发现缺项，无法证明业务语义正确。规范/映射/关键测试被同一 PR 删除或弱化时须重点人工审查，runner 的自测与可审查的固定场景防止无意绕过。具有仓库管理权限者仍可能修改规则或绕过，不能承诺绝对不可绕过。

本期不引入解释自然语言的 PR 清单机器人；检查单完整性与 N/A 真实性由 Reviewer 把关，CI 自动阻断的是分类、映射和真实行为结果。PR 事件保留 head/base 身份，并明确报告被测试的是平台合并引用还是 head；从事件提供的基线计算实际差异，push 首次零 before 等无法取得基线时走保守分支。不得将历史 run 或别的 SHA 的 artifact 当当前证据。

## 6. 测试隔离、执行与结果格式

- **权限：**PR 执行无仓库秘密、GITHUB\_TOKEN contents:read，checkout 不保留写凭据；不使用 pull\_request\_target 执行 PR 代码。fork 首次运行需平台批准时仍视为未完成。依据[GitHub 官方安全说明](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)。
- **服务：**G2 显式设置 CI 临时 SQLite、独立端口、随机测试 secret 和专用测试账号，只清理该 job 自己的资源；不使用 manage 导入开发配置，不调用接管本机5001的黄金路径脚本并行跑 UI。等待明确健康条件，不靠固定 sleep 判通过。
- **MySQL：**job service 使用独立 MySQL 8/InnoDB；每次新建符合现有约束的专用 schema，随机凭据仅传入 job 环境，不打印 URL。验收账号限制在该 schema，允许测试所需 DML/建表、无 DROP；管理权限只用于 disposable 实例准备，结束由 job 生命周期销毁实例。
- **反向校准：**B08 遵循已有增强设计，需单独确认或与本方案明确一并确认后实施；不得把本轮“制定门禁”当作增强设计已确认。正式汇总全部强制前，负向版本必须能被检出。
- **超时/重试：**为 job、进程、网络/锁等待设明确上限；具体值在实施读取源脚本并按首次 CI 运行校准记录。禁止无限等候或业务失败自动重跑到绿；基础设施问题明确失败，可由维护者触发完整新 run。

runner 拟生成固定 JSON：schema\_version、tested\_sha、base\_sha、selected\_tiers、cases（case\_id、test\_id、tier、status、duration、reason）、environment、artifact\_refs。pass/fail 只取 runner 的真实执行结果；文件中不得包含密码、签名载荷、Token 或个人资料。CI 临时 artifact 存截图/JSON/脱敏失败日志（建议保留7天），普通运行产物不 commit。报告生成失败或必需 artifact 未上传视为门禁失败；结果明确记录观测发生在 cleanup 之前。

## 8. 验收标准与风险

1. 修改一个资料字段时，G1 检测到任何额外组DML/Token轮换/认证版本改变必须失败；构造只返回200但DB错的实现也必须失败。
2. 恢复缩水组覆盖、确认回显重签、审计先提交/业务后失败等受控缺陷，应被对应行为测试拒绝；负例只在隔离测试进程或临时副本，不修改生产开关。
3. 按源增强设计，省略终态回滚必须使服务边界探针失败；正确实现恢复后通过。新测试“自己能失败”是门禁上线条件。
4. 文档-only PR 汇总成功且列明 N/A；服务-only PR 不漏跑 G2/G3；缺环境、失败、取消、skip、空报告、报告SHA不符都不能假绿。
5. 外部 required 状态单独验证：一次受控失败 PR 确实不能合并；修正后可合并。未经实际设置/验证只交付可运行workflow，不声称已禁止合并。

**主要风险：**路径规则漏选、同PR弱化测试、浏览器脆弱、真实库成本及外部配置权限。采用保守分类、固定反例、条件等待和独立资源降低风险；人工评审仍负责新入口与语义覆盖。先观察再设 required，避免首次上线阻断全部 PR；上线后基础设施故障应修复门禁或按维护流程记录临时豁免，不能改成 continue-on-error。回退 workflow/required 绑定需维护者显式决定并记录保护缺口。
