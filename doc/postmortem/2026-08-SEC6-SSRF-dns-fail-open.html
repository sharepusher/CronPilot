日期：2026-08-24
严重度：P1 安全
关联编号：SEC-6（Redesign 全面 Review 修复方案 §3.1）
设计文档：Redesign代码全面Review修复方案-2026-08.html

1. Bug 定位

文件：app/services/url_security.py

Layer 1（validate_trigger_url，第 104–109 行）：

except ValueError:
    ips = _resolve_host_ips(hostname)
    if ips is None:
        return True, ''   # ← fail-open: DNS 失败直接放行

Layer 2（validate_and_resolve_url，第 125–128 行）：

ips = _resolve_host_ips(hostname)
if ips is None:
    return True, '', None  # ← fail-open: DNS 失败放行且无 IP pinning

两层 SSRF 防护在 DNS 解析失败（socket.gaierror）时均返回 True，允许请求继续。 这意味着攻击者可以在 DNS 瞬断期间提交指向内网 IP 的恶意域名，绕过 IP 黑名单检查。

2. 根因

层面分析
设计决策原始实现优先考虑「可用性」——DNS 暂时不可用时不影响正常任务调度。这是 SSRF 防护初期（OPT-P0-12）的权衡决策，当时假设内网环境 DNS 稳定
安全建模不足未考虑攻击者主动制造 DNS 故障的场景（如 DNS Rebinding、短 TTL 切换、恶意 DNS 服务器返回 SERVFAIL）
双层都有同一漏洞Layer 2 复制了 Layer 1 的 fail-open 逻辑，未独立审视安全语义
行为层根因OPT-P0-12 实现时无「fail-open vs fail-closed 决策清单」，安全函数的异常路径未被要求单独 review

3. 测试漏洞

原有测试 test_dns_unavailable_returns_none_ip 验证了 DNS 失败时返回 ip=None， 但断言方向是 assertTrue(ok)——即测试本身把 fail-open 作为「正确行为」来验证。 这意味着测试覆盖了该场景但预期值是错误的，反而固化了漏洞。

Layer 1（validate_trigger_url）完全没有 DNS 失败场景的测试用例。

4. 修复

变更描述
_dns_fail_open(cron_config)新增配置读取函数，检查 url_ssrf_dns_fail_open 配置项
_resolve_host_ips(hostname, retries=1)新增 1 次 DNS 重试（间隔 0.5s），减少瞬时 DNS 抖动误拦
validate_trigger_url Layer 1DNS 失败 + dns_fail_open=0 → return False, 'DNS 解析失败...'
validate_and_resolve_url Layer 2DNS 失败 + dns_fail_open=0 → return False, 'DNS 解析失败...', None
conf.ini.example新增 url_ssrf_dns_fail_open=0 配置项（默认 fail-closed）
configs.py（2026-09 补线）把 url_ssrf_dns_fail_open 读入 configs() 返回字典（缺省 '0'），与 block_private_ip / url_ssrf_observe_only 同款写法

4.1 后续修复：逃生开关曾是死键（2026-09-11）

本次交付把配置项写进了 conf.ini.example、设计文档与 Release Notes，但漏了 configs.py： configs() 返回的字典里从来没有 url_ssrf_dns_fail_open 键，而 _dns_fail_open() 只做 (cron_config or {}).get('url_ssrf_dns_fail_open', '0')、 没有 configs('<key>') 兜底，于是运维即使按示例设成 1，运行时读到的仍是默认 0—— 逃生开关完全无效，DNS 抖动环境无法降级。

对照组说明了这个不对称：health_failing_threshold 同样不在 configs() 字典里， 但 get_failing_threshold() 在字典取空时会回落到 configs('health_failing_threshold')， 因此照样生效；api_access_token_required 则是全程走单键读取。 三个键写法各不相同，唯独没有兜底的那个成了死键。

行为层根因：交付验收把「示例文件里有这一项」当成了「配置项可用」， 验证命令写的是 grep 'url_ssrf_dns_fail_open' conf.ini.example—— 这条命令在键完全不生效的情况下依然通过。SEC-6 的 7 个单测则全部直接构造 dict(self.cfg, url_ssrf_dns_fail_open='1') 传入，绕过了 configs() 这一层， 因此测试与 grep 双双为绿。

修复后自证（conf.ini 分别设 0 / 1，对不可解析域名调用 validate_trigger_url）：

1'1'True(True, '')
