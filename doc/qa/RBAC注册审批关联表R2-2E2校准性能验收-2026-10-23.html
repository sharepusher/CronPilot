RBAC 注册审批关联表 R2-2E2 校准性能验收

日期：2026-10-23 · 状态：通过 · 后端：SQLite、MySQL 8.0.46 · 实现：E2-Fix B 管理员集合聚合。

结论：R2-2E2 在校准后的注册审批领域容量下通过。当前安全查询在 MySQL 10k 业务容量、30k 裕量容量及并发 5 场景均满足绝对 SLO；Fix B 消除了原查询的相关子查询退化。100k 保留为非阻断压力诊断，不代表任务域容量。

1. 容量与判定口径

  • 业务容量：10,000 张历史申请；pending 1%/10%；单并发 p95 ≤ 500ms，并发 5 p95 ≤ 1s。
  • 裕量容量：30,000 张历史申请；pending 1%/10%；单并发 p95 ≤ 1s。
  • 压力诊断：100,000 张申请只观察复杂度与容量边界，不再用旧 LIKE 相对倍率单独阻断发布。
  • 计时对象为生产 Repository 的列表 count、20 条 page 与 pending badge；默认全部状态和 pending 筛选分别记录。
  • 旧 LIKE 只在 10k 作为诊断参考；30k 使用 --skip-legacy，避免错误旧查询超时污染安全查询验收。

2. 实现与语义

viewer/operator 分支从 ix_reg_req_groups_group_req 按 actor group 反查申请 ID；admin 分支对申请关联行按 registration_request_id 分组，以 SUM(CASE WHEN group_id NOT IN actor_groups THEN 1 ELSE 0 END)=0 表达非空完整子集。两个角色分支互斥，以 UNION ALL 合并。status/username 使用同一条件构造器下推到两分支，并在最终实体查询保留同值条件。

SQLite 与 MySQL 方言均已实际编译；空 actor group、无关联、非法角色、__ALL__、1/10 边界、admin 部分越权、分页 total 与 badge 均保持 fail-closed。

5. 修复效果

Fix B 前，MySQL 10k、pending 1% 快速档的默认全历史页面在 actor 3/10 组时分别为 1,922.717ms / 5,684.065ms，并伴随不合格计划；pending 页面因状态候选小，仍为 23.973ms / 36.579ms。Fix B 后正式 10/50 的对应全历史 p95 收敛到 111.779ms / 128.380ms，且不再包含相关子查询。

6.2 验收基础设施事件

首次内部冒烟时，测试应用虽将业务 ORM 指向内存 SQLite，但调度器在覆盖发生前已按 conf.ini 连接开发任务库，与运行中的本地服务并发写 apscheduler_jobs，先出现任务 ID 冲突，后检测到 ix_apscheduler_jobs_next_run_time 索引不一致。本轮未改动该未确认范围内的测试工具代码；处置为停止本地开发服务、将数据库备份到 /private/tmp/cronpilot-job-log-before-reindex-20261023.sqlite、仅重建受损索引并以 PRAGMA integrity_check 得到 ok。随后通过环境开关禁用测试调度器，86/86 冒烟通过。该问题不属于 Scope 查询回归，但暴露了冒烟工具隔离缺口，应作为独立设计修复项处理。

7. 七项复盘

  1. Bug 定位：原 E2 把 100k 和旧 LIKE 2×倍率作为唯一发布门槛；校准后又发现容量脚本即使跳过 legacy，仍执行非生产 viewer 包装查询。
  2. 根因：容量模型混淆任务域和注册审批域；基准将“诊断比较语句”与“生产 Repository 语句”耦合，导致旧错误查询或旁路 SQL 超时被误报为安全实现失败。
  3. 测试漏洞：缺少绝对 SLO、pending 分布、默认全部状态、并发 5 及真实 Repository SQL 的独立断言。
  4. 修复：建立 10k/30k/100k 三层模型；Fix B 改为集合聚合；脚本用生产 Repository statement 计时与 EXPLAIN，并允许容量档跳过 legacy。
  5. 防护测试：新增 pending 比例、全历史/pending 双链路、stress mode、skip-legacy、相关子查询计划和并发结果稳定性检查。
  6. 同类排查：列表 total、20 条 page、页面 badge 与导航 badge 共用 Repository；global actor 保持不走 scoped 聚合；未发现其他注册审批读取旁路。
  7. 预防方案：tests/test_registration_scope_benchmark.py 固化数据 manifest 和模式行为；scripts/benchmark_registration_scope.py 的正式结果必须同时输出绝对 p95、生产查询计划、数据层与并发参数，禁止仅凭相对倍率关闭或阻断阶段。

8. 限制与后续

真实数据库验证版本为 MySQL 8.0.46；如发布矩阵仍包含 MySQL 5.7，需在 E3 补跑同一生产 Repository 真值与计划。100k 压力档本轮不作为发布阻断且未重跑 Fix B 正式 10/50。与本查询直接相关的管理员、受限业务管理员、Operator 浏览器正反路径已完成；E2 通过仍不等于 R2-2 全部完成，尚需 E3 其余集成矩阵、冒烟工具隔离缺口的独立设计修复，以及 E4 交付收口。
