# 任务执行链路可观测性：执行侧观测专项评估

范围：仅评估 cron\_do 进入后的运行观测，不含调度注册与对账

**结论：执行侧已达到“工程可用”，尚未达到“生产级完整排障”。**当前能够可靠回答“是否创建了运行实例、执行走到哪些已定义阶段、最终结果是什么、不同角色能看到什么”；但事件上下文仍偏少，观测降级对用户不可见，部分阶段缺少耗时/URL/阈值等诊断字段，事件与父运行记录仅通过 trace\_id 软关联。因此适合工程师排查常见 HTTP 执行失败，不适合仅凭当前时间线完成所有生产事故根因定位。

## 1. 评估对象与事实依据

对照当前代码与测试：`app/crons.py`、`app/services/execution_tracer.py`、`app/services/run_inspector_presenter.py`、`app/templates/redesign/run_inspector.html`、`app/repositories/job_log_repository.py`、`datas/model/job_log_event.py` 及执行观测相关测试。

验证命令：

```
.venv-py311/bin/python -m unittest tests.test_execution_observability_contract tests.test_job_log_outcome tests.test_job_log_display tests.test_job_log_detail_integration tests.test_execution_tracer tests.test_execution_context_executor tests.test_job_log_retention -v
```

**结果：41 条定向测试全部通过。**

## 2. 执行侧实际闭环

**1. 创建父记录**`JobLog.status=pending`

→

**2. 进入执行**`pending → running`

→

**3. 阶段事件**Tracer 按序写入

→

**4. 业务结果**HTTP/异常/安全校验

→

**5. 终态**success/fail/timeout/error

→

**6. 展示**Presenter → Run Inspector

| 能力 | 当前实现 | 判定 |
| --- | --- | --- |
| 父运行记录 | 执行函数前创建 pending；开始后更新 running；结束时写终态。 | 已实现 |
| 事件顺序 | 以 `seq` 和 `offset_ms` 表达顺序与相对时间。 | 已实现 |
| 事件持久化 | 独立连接写入 `job_log_events`，不污染业务事务。 | 已实现 |
| 结果展示 | Presenter 生成模板安全 DTO；模板不读 ORM 原对象和 raw detail。 | 已实现 |
| 角色边界 | viewer/operator/admin 对 URL、响应正文和业务日志差异化脱敏。 | 基本实现 |
| 事件完整性 | 阶段集合稳定，但上下文白名单较小，部分阶段只有固定文案。 | 部分实现 |
| 观测降级可见性 | 写入预算和异常会禁用 Tracer，并增加 Prometheus counter；页面无降级提示。 | 部分实现 |

## 3. 事件契约与诊断价值

| 事件 | 能说明什么 | 当前不足 |
| --- | --- | --- |
| `task.enqueued` | 已进入执行器队列，可见 scheduled\_delay\_ms。 | 不能解释 APScheduler 到执行器之间的全部等待原因。 |
| `task.start` | 业务执行函数已开始。 | 无额外上下文，无法区分线程/进程或执行器实例。 |
| `db.load_cif` | 读取任务配置阶段存在。 | 缺少数据库耗时、读取结果和配置版本。 |
| `ssrf.check` | 安全校验通过或拦截。 | detail 白名单有 block\_type，但缺少安全策略版本/解析耗时。 |
| `http.start` | 发送请求，至少可见 method。 | 缺少脱敏 URL、timeout\_sec、解析/连接阶段信息。 |
| `http.complete` | 拿到 HTTP 状态。 | 缺少响应耗时、响应体大小、重试次数。 |
| `http.timeout/error` | 可区分超时与一般异常。 | 页面不显示 timeout 阈值；异常摘要过于粗，根因需查服务日志。 |
| `db.write_log` | 最终结果已写回业务日志。 | 不能证明所有前置阶段都已成功持久化。 |

## 4. 数据模型与关联完整性

`JobLogEvent` 当前字段包含 `trace_id`、`cron_id`、`seq`、`occurred_at_ms`、`offset_ms`、`duration_ms`、`outcome`、`detail`，并以 `(trace_id, seq)` 唯一约束保证同一 trace 内不重复排序。

| 优点 | 风险/限制 |
| --- | --- |
| 独立表、时间毫秒、序号明确，适合时间线查询。 | 事件没有 `run_id → JobLog.id` 外键，依赖 trace\_id 约定；trace 丢失时无法严格归属父记录。 |
| Tracer 使用独立事务，业务 DB session 不受影响。 | 事件写成功与父记录提交不是同一事务，极端故障可能出现“有事件无父记录”或“父记录有但事件缺失”。 |
| 固定事件上限 16、写入预算 200ms，控制了观测成本。 | 预算触发后剩余阶段静默丢失，当前 UI 不显示“时间线被截断/观测降级”。 |

## 5. 页面、权限与状态语义

入口为 `/job_log_detail`，服务端先按 `log:read` 和资源 scope 授权，再通过 Repository 查询父记录、事件和业务日志，Presenter 生成唯一模板数据形状；展示页面为 `redesign/run_inspector.html`。

| 状态 | 执行侧语义 | 评价 |
| --- | --- | --- |
| pending | 父记录已创建，尚未完成执行；页面显示“已入队 · 最终结果未知”。 | 语义清晰 |
| running | 已开始执行但没有终态；页面显示“执行中 · 最终结果未知”。 | 语义清晰 |
| success/fail/error/timeout | 终态结果。 | 基本完整 |
| suppressed | 并发锁在进入 `cron_do` 前阻止执行，不创建父记录。 | 不误造执行记录 |
| interrupted | 已开始执行后异常终止。 | 当前实现/契约需继续确认是否所有中断路径都能稳定落库 |

脱敏契约已由 Presenter 和测试覆盖：Viewer 隐藏 query value 与响应正文，Operator 可看脱敏 query 和截断正文，Admin 可看业务日志记录。页面不显示原始 detail JSON，这是正确的安全边界。

## 6. 测试覆盖评价

| 已覆盖 | 仍缺测试 |
| --- | --- |
| 事件白名单、序号、毫秒时间、事件预算；Presenter 摘要；三角色 URL/正文/业务日志；pending 页面；列表筛选；保留策略。 | cron\_do 完整集成链路（HTTP 成功/超时/异常产生的完整事件序列）；Tracer 写入失败后的用户可见降级；事件与父记录不一致；中断路径；并发锁“零 JobLog”端到端证明。 |
| 模板禁止 raw detail/ORM 访问，时间线顺序有集成断言。 | 重启后浏览器端四角色正反向验证；大事件量、长期保留和双后端性能验证。 |

## 7. 收口建议与最终判定

1. **P0：补齐执行事件上下文。**至少增加脱敏 URL、timeout\_sec、scheduled\_at/trigger\_source、阶段 duration；同步更新白名单、Presenter 和契约测试。
2. **P0：让观测降级可见。**在运行 DTO 增加 `observability_incomplete` 和原因，页面提示事件可能被预算或数据库错误截断。
3. **P1：强化关联完整性。**评估将 `run_id` 作为事件一等关联键；若保留 trace 关联，至少增加父记录存在性和孤儿事件检测。
4. **P1：补完整集成测试。**覆盖 cron\_do 的成功、SSRF 拦截、HTTP 超时、异常、中断和 Tracer 故障隔离。

**最终判定：**执行侧观测当前完成度约 **75%**。作为“单次运行阶段诊断”可以依赖；作为“任何生产执行事故的充分证据”还不能依赖。当前最重要的不是再增加状态，而是补上下文、降级提示、强关联和真实集成测试。

本专项评估不涉及调度注册、APScheduler JobStore 对账或任务详情页健康模型。
