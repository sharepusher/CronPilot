1. 问题与证据

原库以只读方式执行完整检查返回 row 8 missing from index ix_apscheduler_jobs_next_run_time；quick_check 返回 ok 不代表完整检查通过。该索引属于 apscheduler_jobs 的 next_run_time，表扫描 34 行。服务状态检查显示 5001 和 5860 均未运行，lsof 当时未显示其他持有者；不保证之后无进程接入。不能从该结果判断故障发生时间或根因。

使用 SQLite 在线备份从只读源创建隔离快照，再复制为试验库；仅在试验库重建目标索引。快照检查有同一错误，试验库完整检查为 ok；18 张表的行数与行内容摘要、数据库 schema 摘要均一致。试验摘要、可复现脚本。此比较不证明业务语义或所有过去的数据未丢失，也不是原库修复或长期备份认证。

2. 根因与测试盲区

当前只能定位索引内容与表记录不一致；不能断言是代码、关机、磁盘或本轮测试造成。quick_check 未发现该索引问题，表清单可读也无法证明完整性。恢复后应检查持久化 Job 的语义与应用行为，不能仅凭完整性通过宣布版本就绪。

3. 推荐方案及备选

  1. 确认窗口及库身份：列出并停止所有会读写该数据库的 CronPilot 进程及外部 SQLite 连接，验证停写；检查 journal 模式和 WAL/SHM；记录原库及关联文件状态与指纹。不停止或改写与该库无关的服务。
  2. 先以 SQLite 在线备份创建新的带时间和随机后缀的独立备份，保留未修复版本；备份目录私有权限、绝不覆盖既有备份。校验备份可读性和完整检查结果并计算 SHA256；另外保留原始数据库及必要 sidecar 的一致性证据。备份受保护且不提交仓库。若无法形成可用备份或无法证明停写，停止。
  3. 对备份副本重跑同一试验，比较所有业务表逐行摘要、表结构和完整性；确认只有预期索引异常且修复副本得到 ok。若出现其他问题、内容差异或锁定状态变化，停止并重新评估，不对原库执行。
  4. 通过上述门禁后，仅对目标索引执行 REINDEX；不删除任务、数据库或重建所有索引。随后完整检查、外键检查与全表摘要对比；异常立即停止应用启动并保留原始备份，不能直接覆盖或恢复以免掩盖新写入。
  5. 确认数据检查通过后重启开发服务，验证登录、任务列表、JobStore 日志及任务与 Job 的关联，禁止人为触发真实任务。保持服务供复验并明确说明调度器会按既有配置运行；如用户不希望执行实际调度，则先在隔离预览验证并另行约定恢复方式。

备选为直接替换为备份或重建 JobStore：可能丢失后续任务/执行数据，暂不采用。现有模拟支持定向索引修复，但不构成对原库执行授权。

4. 范围

限当前本地 SQLite 数据库的该索引；不修改应用、生产数据库、MySQL、表数据或字段，不清空历史，不处理其他独立发布阻断。数据库修复涉及用户数据并不可视作纯测试，本稿须明确确认后实施。

5. 分批

  1. R0：用户确认后再次只读检查库与进程，冻结证据并确认所有写者停止。
  2. R1：创建独立备份并核验，在备份副本复演定向修复及对照。
  3. R2：在原库执行经确认的单索引修复，逐项检查并记录结果；失败停机保留备份。
  4. R3：可验证本地环境、审计结果及七要素复盘；业务异常、数据差异或不确定性不得标记成功。

6. 验收

  • 原始备份可读、指纹登记、未覆盖，全部连接和写者已核实；不输出表中记录或凭据。
  • SQLite integrity_check 返回唯一 ok；foreign_key_check 无新增问题；sqlite_master 与所有业务表的行数和全行摘要前后一致。扫描必须绕过被修索引，比较同一静止快照并控制并发。
  • 独立进程重开数据库检查结果；验证 APScheduler 能读取并更新测试用途 JobStore，生产数据只做安全读取与应用既有调度核验；不以 quick_check、表存在或 HTTP 200 代替。
  • 登录 POST、任务列表与目标调度状态核对；若真实任务可能触发，预先明确是否允许启动调度器。固定结果存放 doc/qa/evidence，不包含数据库内容或备份文件。

7. 风险与回滚

重建索引修改用户数据文件，存储故障、隐藏损坏、正在运行的写者或备份不一致可能扩大损失。若检查失败则停止；回退须先确认备份、原库与新写入之间的差异，不能自动覆盖。快照仅为诊断样本，需按实际备份保管策略保存并确认恢复可行。保留文件权限与属主，不改全局 SQLite 设置。

8. 本轮实际验证

只读完整检查与独立副本模拟如第 1 节；上述为设计阶段历史，原库后续修复结果见第 9 节。现有版本一致性、图片资产、全量测试和启停修复的发布收口仍独立存在；本设计不宣称 4.2.0 发布就绪。

9. 修复复盘与验收

  1. 定位：原库 integrity_check 报 row 8 missing from index ix_apscheduler_jobs_next_run_time；表扫描 34 个 Job。quick_check 为 ok。
  2. 根因：可确定该索引与表记录不一致；造成不一致的时间和原因没有证据，不能归因于某次操作、程序或硬件。
  3. 测试漏洞：此前仅以表可见性及 quick_check 等轻量检查作环境信号，未运行能比对索引与表的一次完整检查，因此没有发现该错误。
  4. 修复：用户明确确认后检查读写者与 DELETE journal、创建私有原始文件与 SQLite 在线备份，在备份副本复验，再以独占事务仅重建目标索引；事务内比较通过后提交，独立连接再检查。原库没有被替换，未删除任务记录。备份位于本地 datas/backups/job-log-20261103-uycaovui/，权限仅所有者访问，不纳入版本库；原始备份保留原问题供追溯。
  5. 防护验证：修复前后比较 18 张表全行摘要、schema 和外键检查，结果一致；完整检查从该索引错误变为唯一 ok，foreign_key_check 为零；独立进程重开确认。用户登录前的数据对照结果见修复结果，登录后的正常审计写入不属于该对照。
  6. 同类排查：全库 integrity_check 未再发现其他结构性错误；副本中的 SQLAlchemyJobStore 在暂停调度器状态下读取 34 个 Job，完成一条 Job 更新和读取。副本测试关闭时日志出现对过期 Job 的提交尝试且执行器已关闭；这不是完整调度运行验证，也不能据此证明所有真实任务语义或历史数据完整。
  7. 预防方案：新增只读诊断 doc/qa/evidence/sqlite-jobstore-index-2026-11-03/verify_integrity.py，执行 .venv-py311/bin/python doc/qa/evidence/sqlite-jobstore-index-2026-11-03/verify_integrity.py datas/job_log.sqlite，完整检查或外键异常返回非零；对修复前备份的否定验证退出 1，对修复后原库退出 0。建议备份后、启动调度前执行；它是可复现人工门禁，不冒称已自动加入 CI，也不能替代业务数据备份。
