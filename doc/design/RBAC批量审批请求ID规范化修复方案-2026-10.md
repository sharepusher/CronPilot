## 1. 问题

现有两个批量入口把 `ids` 按逗号拆分后，只要 token 由数字组成便直接加入待处理列表。重复 ID 会被顺序执行两次：第一次改变申请状态，第二次返回“已处理”，最终把一次成功请求误报为部分失败；混入非数字 token 则被静默跳过，响应集合与请求集合不再一一对应。

## 2. 根因

入口把 CSV 解析同时当作“宽容清洗”和“业务校验”，没有形成一个可验证的规范化结果，也没有在逐项调用 `approve_registration()` / `reject_registration()` 前确保输入集合唯一、完整。因此服务层虽能保证第二次不重复写入，却无法使批量摘要表达调用方的原始意图。

## 3. 推荐方案与评估

**推荐 A：严格、保序规范化。**新增私有 View 辅助函数，接收原始 CSV 并返回 `(ids, error)`：

1. 空 token、非 ASCII 十进制整数、零或负数均为非法；
2. 重复正整数为非法；不静默去重，避免调用方误以为所有 token 已被处理；
3. 只有全部 token 有效且唯一时，才进入逐项审批循环；保持首次出现顺序；
4. 两个批量入口共用该函数，返回既有 JSON 错误信封；不调整单项审批、Scope、数据库模式或成功/部分失败三态契约。

该方案以最小改动恢复“输入集合 = 尝试处理集合 = 摘要 total”的可审计关系。相较于“静默保序去重”，严格拒绝能暴露脚本、重放或参数拼接缺陷；相较于继续逐项处理，避免了已经发生状态变化后才报告输入错误。评级维持 P2：正常 UI 无法构造重复复选框，且当前实现不会重复创建用户或越权，但自动化与重放调用会获得不准确结果。

## 5. 分批实施

1. **B0：红线测试。**为通过与拒绝分别覆盖重复 ID、混合非法 token、空 token；断言 `errcode=1`、无申请状态改变、无创建用户。
2. **B1：入口收口。**实现并复用严格解析器；在调用服务前返回受控错误，保留合法请求的原有顺序和响应格式。
3. **B2：验证与复盘。**运行专项注册审批测试、Ruff、路由冒烟；浏览器自动化验证正常多选成功与构造非法请求零写入；写入 7 项复盘和双格式文档同步。

## 6. 验收标准

- `ids=12,12`、`ids=12,abc`、`ids=12,,13` 均返回 JSON 参数错误，且对应申请保持 `pending`。
- `ids=12,13` 保留输入顺序，每个 ID 至多调用一次服务；既有 all-success / partial-failure / all-failure 契约不变。
- 通过和拒绝路由使用同一规则，不存在一侧静默忽略的旁路。
- `.venv-py311/bin/python -m unittest tests.test_registration -v`、`.venv-py311/bin/ruff check app/`、`.venv-py311/bin/python scripts/smoke_routes.py --check` 通过。

## 7. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 既有自动化依赖宽容解析 | 仅非规范请求被拒绝；正常 UI 生成的唯一正整数 CSV 不变。错误消息明确指出修正方式。 |
| 重复检测后才写入造成半完成 | 在进入任何服务调用前完成整串解析与唯一性校验；测试断言零写入。 |
| 两条端点实现漂移 | 抽取共享函数并对 approve / reject 分别建立回归测试。 |
