## 1. 问题与根因

当前 toggle\_status 先提交 DB，再执行 pause/resume，随后写成功日志；这三类事实没有分开。调度调用和成功日志位于同一 try 中，任一异常都尝试把 DB 恢复为旧状态。例如暂停已持久化、随后日志异常，当前代码仍可能把 DB 改回“运行”，与已暂停的 JobStore 相反。现有版本检查和 ORM 条件更新已经限制陈旧覆盖，不能错误描述为完全无并发保护；但 refresh、补偿提交本身的失败仍可能冒泡，且版本一致不能证明调度操作未生效。

另一个入口事实是：两个 Web 调用方已有 newStatus，却只向服务器提交 id，服务器按读取时 DB 值取反。旧页面按钮表达的目标可能与执行动作相反。这里应提交明确目标，无须为低频启停引入新的数据库字段。

## 2. API 假设已读证据

- app/services/cron\_service.py:toggle\_status，app/main/views.py:update\_status，app/api/views.py:cron\_status；datas/model/cron\_infos.py 中 version\_id\_col 与自动版本生成器。
- app/templates/redesign/task\_detail.html:cpToggleTask、dashboard.html:cpToggleStatus。详情使用服务端成功消息；dashboard 成功文案由客户端目标生成，实施时应改读服务端 errmsg，才能正确展示 no-op。
- 已安装 APScheduler schedulers/base.py:pause\_job 调用 modify\_job(next\_run\_time=None)；modify\_job 先更新 JobStore，再派发事件/唤醒，正常返回 Job；resume\_job 有下一次触发时返回 Job，没有下一次触发时移除并返回 None。
- Flask-APScheduler scheduler.py 的 pause\_job/resume\_job 仅转发，丢弃底层返回值；不能把这个封装的 None 直接解释为任务不存在。D2 使用窄适配器调用 scheduler.scheduler.pause\_job/resume\_job 并显式固定 jobstore='default' 取得真实返回，不增加 get\_job 成功验证。已读项目 CuBackgroundScheduler/CuGeventScheduler，当前未覆盖这些方法。
- SQLAlchemyJobStore.update\_job 使用独立 engine.begin 提交；异常可能发生在写入之后。D1 current\_version 与 query\_target 可作为参考，不能不加区分套用重注册逻辑。

## 3. 处理流程

1. 保留路由权限、Scope、CSRF。解析显式目标；旧未传目标仍取反，不自动重试取反请求。已下线禁止恢复，不创建缺失 Job。
2. 目标与 DB 相同：返回明确配置 no-op，零 DML/成功日志/调度调用及额外查询。此分支不是漂移修复；收到此前“待核实”提示后，不能把重复同值请求的 no-op 当成同步已修复。
3. 真实状态变化沿用 ORM 版本条件更新，flush 后、commit 前捕获 task ID、revision、目标状态与完整调度配置快照。StaleDataError 先 rollback，返回“任务已被修改，本次未保存，请刷新确认”；不得自动重试反转目标。普通写前失败安全返回；commit 异常保守提示“状态保存结果待核实，请勿重复提交”，不继续调度。
4. 提交成功后使用独立连接检查本次 revision/status。不同则返回“目标状态已保存，但任务有后续变更，本次未继续操作调度”；不能用旧快照继续调用。调度器未启动直接明确报错，不操作 pending。
5. 只调用现有暂停/恢复，不重新注册、不补写 trigger。真实 Job 返回且非 pending：按同步契约认可成功，不额外 get\_job；然后单独检查 DB 版本，发现后续变更只报告并发事实。成功日志放在调度结果分类之外并按 best-effort 隔离故障；日志异常既不能触发状态恢复或把已确认调用改判失败，也不能冒泡导致请求 500。
6. 底层 resume 正常返回 None 表示无下次触发且任务已移除：明确提示“目标状态已保存，但该调度已无下次触发，未恢复运行”；不冒称已启动，不借此自动下线。返回 pending 或无法证明持久化也不能当成功。底层正常完成后 DB 不可读，提示“调度调用成功，但无法完成并发核验”，不说调度结果未知。
7. 只对不能确定是否已生效的异常执行“新鲜版本 → 一次 JobStore 读取 → 新鲜版本”。调用明确写前拒绝时直接报错；不能仅按异常类名假定未写。确认目标匹配则成功；不匹配则错误；读失败/证据不足则待核实。任一阶段发现后续版本，优先报并发。

## 4. 查询与补偿边界（已确认）

异常时不仅检查 next\_run\_time 是否为空，还要核对 Job ID、执行函数、参数、完整 trigger 与执行策略，确认读取的是本次配置目标；使用 D1 的同源构造/比较能力，保持一次 JobStore 读取。暂停目标要求对应 job 存在且 next\_run\_time=None；恢复目标要求对应 job 存在且具有有效下次时间。已启动调度器从持久化 store 读取；停止态不以 pending 作证明。JobLookupError 可能由并发移除或写后监听引起，不能只凭类名就认定写前失败。

**本批已取消提交后的自动 DB 旧值恢复。**提交成功的 DB 状态保留为目标状态；无法确认实际应用时明确报错，不声称 DB 状态就是当前调度实际状态，也不自动重复调度写。原因是错误发生后无法跨库原子地证明“没有生效且没有后续操作”，再写旧值可能制造另一种不一致。保存事务未提交时仍正常 rollback；这里只取消已提交后的业务补偿。

这是对 AGENTS.md“scheduler 失败时回滚 DB”的旧总则在**启停路径**的显式收窄，与已确认 D1 的事实分层一致；已同步相关规则的启停例外。

增加明确的“核实并重新应用目标”操作，具体见第 10 节。普通同值提交仍不承担恢复职责；缺失 Job 的重新调度入口只处理缺失，不能代替该操作。保留目标但未确认应用时，列表 DB 状态可能与实际调度不同，这是明确报错后的运维边界，不在页面上伪造一个新“同步状态”。暂停也不会终止已开始的任务执行，恢复成功不等于任务已执行。

## 8. 专业评估、性能与风险

准确性：基于当前源代码，区分同步接口、包装返回值、业务是否恢复、后续并发、存储后异常。合理性：沿用低频修改目标，不引入复杂协调系统；Web 明确目标减少陈旧按钮反转。正常路径仍有少量按主键 DB 版本读取，但不为成功增加 JobStore 验证；异常时最多一次有限查询，不做吞吐收益或 SLA 声明。

主要权衡是取消自动补偿后可能留下已保存目标与实际调度不同；本批通过准确报错暴露，而不是自动恢复或隐藏。版本检测不构成 fencing，检查窗口之后仍可能有其他写入；API 未传目标仍是非幂等取反，不能自动重试。本批提供人工触发的核实及恢复；不声称具备自动恢复或持续同步状态展示。

## 10. 已保存目标的核实与恢复（rev.2 补充）

问题：暂停目标已提交但调度未生效时，普通同值请求只会返回 no-op，不能修复实际调度。恢复必须由操作者显式发起，并在页面说明目标、当前观察和结果；不得把普通 no-op 冒称调度已一致。

### 10.1 用户操作

1. 启停结果为不一致或待核实时，显示服务端错误；任务详情提供“核实并重新应用目标”入口。操作者打开详情并发起核实；保留现有权限和 Scope 校验。无需猜测应先启动还是暂停。
2. 服务端读取最新数据库任务与版本、目标状态，以及 JobStore 中对应 Job。查询不可用时提示“无法核实，请稍后重试”，不写入任何一侧。页面展示目标状态和观察结果，并提示暂停不会终止已经开始的执行。
3. 若完整配置和状态已匹配，提示“已核实一致”，不调用 pause/resume，不写任务 DB；特别是恢复目标已运行时，禁止再调用 resume\_job，因为它会重新计算下次执行时间。
4. 若 Job 存在且函数、参数、触发器和执行策略与数据库配置匹配，仅暂停/运行状态不同，则展示当前观察并允许用户直接选择重试明确目标，不要求额外二次确认。重试时提交服务端签名基线和明确目标；服务端重新授权、读取当前版本和 Job 并重新比较。若版本、目标或观察状态变化，停止并要求重新核实；不执行旧目标。
5. 检查仍匹配后，执行一次与数据库目标一致的 pause\_job 或 resume\_job，沿用 D2 同步结果契约。正常返回不再为确认成功额外查询；异常时有限核实一次。调用结束后检查数据库版本；并发发生则报冲突，不能声称最终一致。成功与失败均记录操作人、任务 ID、目标、时间和结果，不记录凭据。

### 10.2 不自动处理的情况

Job 缺失、一次性任务已结束、函数/参数/trigger/策略不匹配、任务下线或身份与 Scope 失效时，禁止通过本操作盲目注册、覆盖或恢复；显示明确原因并引导检查任务和调度记录。特别是 Job 缺失不能视为暂停成功，已经结束的一次性任务不能借重试重新触发。重新注册或修复配置应另按既有入口及其权限/适用条件处理，不能假设既有入口能解决所有情况。

版本检查与调度调用之间仍有竞态窗口；独立数据库和 JobStore 不具备原子 fencing，多个工作进程或旧写入可能在检查后覆盖。该方案降低误操作并报告可观察的冲突，不承诺消除所有并发漂移或保证恰好一次执行；已运行任务和已提交执行无法由暂停撤销。重复请求及多标签页必须使用相同目标、重新读取实际状态：已匹配时零调度写；并发触发仍可能两次调用，应测试该边界，不能以此声称严格幂等或零重复执行。

若已一致：显示“已核实一致”；若无法核实、配置不同或版本变化：显示具体原因并停止。

### 10.4 接口、权限和验收

设计新增 Web 核实 GET /cron\_status\_check?id=… 与显式应用 POST /cron\_status\_apply 两个入口（当前仓库未发现同名路由）；沿用 cron:write、数据库当前用户 Scope、CSRF 和既有 JSON 响应信封。核实只返回当前授权任务的目标、受控状态与版本；不得返回 URL、请求体或凭据。核实响应提供服务端签名基线，绑定操作人、任务 ID、目标、revision 与完整配置/状态的不可逆摘要，不包含 URL、请求体或凭据明文；签名不替代重新授权。POST 必须携带该基线和明确目标，不能使用取反语义；请求非法、缺失版本、权限撤销、目标变化均 fail-closed。旧 API/旧 Web 普通请求契约保持不变；若后续新增公开 API 字段，按仓库要求评估并标注兼容性。

- 真实 SQLite/MySQL JobStore：暂停失败后显式核实并修复；恢复失败后显式修复；确认前后检查独立连接的 DB、版本和 Job。
- 目标已匹配时验证无 pause/resume、无任务 DML、无恢复成功操作日志；特别验证已运行 Job 的 next\_run\_time 未改变。
- Job 不存在、到期一次性、配置不匹配、查询超时、停止状态、无权限、CSRF 失败、目标或版本变化均不写调度；模拟确认后写入前并发和写后异常，记录其有限检测边界。
- 浏览器目标角色验证：失败提示→打开详情→核实→确认→结果；取消零写、权限撤销拒绝、并发重试；截图。既有正常成功零查询、旧接口取反和 D1 测试不得回退。
- 复核实际入口、确认对话框和错误态的 Before/After 与父设计既有详情布局一致；新增权限路由需对齐 Scope。实现、独立预览及发布说明按仓库闭环另行执行。

## 11. 明确目标重试：用户确认后的修订（rev.3）

本节优先于正文 rev.1/rev.2 中与其冲突的“请勿重复提交”、必须二次确认、先核实再由用户确认恢复等表述。暂停异常后用户可稍后点击“重试暂停”；恢复异常后可点击“重试启动”。禁止使用不带目标的取反请求作为重试。

1. 正常调用同步成功：遵循接口契约返回成功，不为了确认成功而读取 JobStore。
2. 调用异常、不能确定结果时，服务端自动查询一次；查询结果仅代表观察时点。如果目标匹配，可报告“当前已观察到目标状态”，但不能证明原操作已最终结束，或保证之后不发生覆盖。若不匹配、缺失、读取失败或不能证明结果稳定，提示“调度结果暂时无法确认，可稍后重试暂停/启动”。查询看见旧状态不得断言原请求最终失败。
3. 重试明确携带原目标和服务端签名基线（任务、操作者、提交后 revision、目标与调度配置摘要）；服务端重新执行当前权限、Scope、CSRF 检查，重读当前任务与版本。目标或 revision 与基线不符、任务下线或权限撤销时返回冲突/拒绝，不允许旧暂停重试覆盖之后的启动。
4. 版本有效时读取持久化 JobStore：Job 缺失、配置或执行策略不匹配、查询不可用均明确报错，不盲目新建或写调度。状态已匹配时返回“当前已暂停/已启动”，不重复调用暂停或恢复；否则调用一次明确目标对应的操作。恢复已有运行任务不得再次调用 resume\_job，以免重新计算下次执行时间。
5. 若写入时或随后仍有异常，允许相同基线再次重试；若数据库已有后续变化，拒绝旧基线。操作后再次检查版本，发现变化时报冲突；这不能防止检查与调度操作之间的竞态，不能保证恰好一次或阻止其他进程迟到的写。

暂停不终止已开始的执行。观察到暂停不保证仍在执行中的旧启动操作不会之后改变状态；只有已知该操作结束或可通过可靠机制消除并发写时才能给出更强保证。未引入锁、持久化操作状态或后台对账，本批不承诺跨进程严格线性化或全局自动收敛。

UI 失败提示为“暂停结果暂时无法确认，可稍后重试暂停”，提供“重试暂停”；启动同理。恢复入口不要求用户判断具体调度状态或经过额外确认，但保留当前权限检查；首次危险操作已有确认，重试只沿用原签名明确目标，不再取反。重试与首次操作均保留现有响应字段，不以旧 API 的无状态取反模拟幂等。

追加验收：首次调用被阻塞或响应超时后，先观察旧状态，再放行原调用；用户稍后重复同目标，验证已达目标零二次调度写；原操作未完成时并发重试应诚实报告可观测结果和边界。另测签名篡改、缺失、跨用户、版本变化/先启动后旧暂停重试、作业缺失、暂停已执行任务及启动重复不能改变 next\_run\_time。真实 SQLite/MySQL、Web/API 权限与 CSRF、目标角色浏览器和 D1 零查询回归均须通过。

## 12. D2 首项修复历史（最终交付见第 13 节）

1. 定位：暂停实际成功后成功日志异常，旧代码把数据库状态回滚，造成两个存储不一致。
2. 根因：成功日志和调度调用放在同一个异常处理范围。
3. 测试漏洞：原测试未在真实 JobStore 暂停成功之后注入日志故障。
4. 修复：将成功日志移出调度异常处理并单独保护；日志故障不改变成功的调度结果。
5. 防护测试：tests/test\_cron\_status\_logging\_d2.py 使用独立 SQLite JobStore 和内存业务库，在真实暂停后注入日志异常，断言 JobStore 与业务库均为暂停且结果成功。
6. 同类排查：恢复也共用该日志处理；真正的调度异常分类、恢复、并发、明确目标及 Web/API 路径仍待实施，不能视为已修复。
7. 预防措施：测试文件固定真实调度成功后日志抛错的反例，执行 .venv-py311/bin/python -m unittest tests.test\_cron\_status\_logging\_d2 -v；变更启停日志时必须运行，防止将日志故障重新纳入业务补偿。

首项修复当时验证：.venv-py311/bin/python -m unittest tests.test\_cron\_status\_logging\_d2 tests.test\_cron\_edit\_concurrency tests.test\_lifecycle\_logging -q：44 项通过；ruff check app/ tests/test\_cron\_status\_logging\_d2.py 通过。仅为部分验证，真实 MySQL、页面与完整 D2 尚未验收；原有调度调用抛异常后补偿逻辑仍存在。

## 13. 最终实施、验收与复盘

实际落点：cron\_status\_apply.py 统一保存、版本核验、启停与重试；cron\_service.toggle\_status 保持四元组；Web /update\_status 接收明确 status，/cron\_status\_apply 验证原签名重试；/cron\_status\_check 读取当前授权目标并签发基线。签名包含 actor/task/revision/target/config（HMAC 调度配置摘要）。当前用户权限在 Web 保存服务再次读取检查。详情和 dashboard 共享 cron-status.js，首次确认后提交明确目标，失败出现直接重试按钮；详情保留“核实并重新应用目标”。

GET 核实入口本身只读 DB 目标和基线，不声称已核实 JobStore；点击入口随后 POST，由服务端读取实际 Job 并按当前目标核实/应用，一次用户操作完成，不增加二次确认。原第 10 节分离观察/确认描述以 rev.3 和此实际流程为准。网络响应丢失时客户端可重新读取当前目标；目标已变化则停止，不以旧按钮取反。已取得失败签名的重试绑定原版本，拒绝后续修改。正常成功不额外读 JobStore，重试在写前读取一次，重试再次异常时允许再观察一次；状态已匹配不重复 resume、不改 next\_run\_time。

API POST /api/cron/status 保持原表单字段与 JSON 信封；失败且 DB 提交已确认时响应头 X-Cron-Status-Retry 提供签名。调用方稍后使用同一任务、明确 status 和同名请求头重试；签名绑定认证 Token 的 HMAC 标识，换 Token/任务/目标或修改签名均拒绝。缺失签名的普通同值请求仍是 DB 配置 no-op，不能作为修复证明。commit 结果未知不签发已提交基线，提示刷新核实。

### 13.2 七项复盘

1. 定位：调度/日志异常混同导致已暂停 Job 与恢复为运行的 DB 不一致；旧目标取反与同值 no-op 阻断恢复。
2. 根因：把异常当作未生效，缺少原目标/版本重试契约，未区分目标存储与实际调度状态。
3. 测试漏洞：只验证一次成功或模拟异常，缺少真实写后异常和“失败之后如何恢复”的端到端断言。
4. 修复：取消提交后旧值补偿；独立分类同步结果与观察；明确目标、签名版本及配置绑定；重试前读实际状态，匹配即不写。
5. 防护测试：tests/test\_cron\_status\_apply\_d2.py、test\_cron\_status\_logging\_d2.py 和 scripts/verify\_cron\_status\_d2.py 的双后端真实端点/浏览器矩阵。
6. 同类排查：Web 详情、dashboard、旧共享四元组、API status 均接入；D1 和超时相关回归通过。下线 D3 未迁移本契约。
7. 预防措施：将“首次失败后重试、重复恢复不改下次时间、后续修改拒绝旧重试”固定在上述测试和脚本中，第三方运行本节命令可重现；日志失败不得落入调度补偿范围。

限制：版本检查不构成跨进程 fencing，无法阻止在检查之后发生的迟到写；不承诺严格只调用一次或任务恰好执行一次。Job 不存在/策略配置不匹配/已过时一次性任务拒绝盲目注册或恢复。长时间中断后查询只代表观察时点。当前测试没有覆盖所有跨进程迟到写、全部跨请求角色撤权竞态和连接池压力，不将这些列为已证明保证。
