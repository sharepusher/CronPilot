# 健康度统计语义优化设计

**编号**：OPT-P1-18   **版本**：rev.1   **日期**：2026-09-03

**关联**：`app/services/job_health_service.py`、`app/repositories/cron_repository.py`、`datas/model/job_health.py`

## 1. 问题

### 1.1 现状

Dashboard 统计卡片「持续异常」和任务列表「健康度」列显示「异常」，但实际包含了**从未成功执行过的新建任务**。用户直觉上认为"还没跑就异常"是不合理的。

### 1.2 真实数据佐证

| ID | 任务名 | 连续失败 | 成功次数 | 健康状态 | 用户预期 |
| --- | --- | --- | --- | --- | --- |
| 10 | test1 | 526 | 0 | failing | 「配置错误」或「从未成功」，不应等同于"曾经正常后变为异常" |
| 11 | test | 3 | 0 | failing | 刚刚越过阈值，且从未成功过 → 更像是"待验证"而非"持续异常" |
| 12 | test2 | 4,687 | 0 | failing | 高频调度 + 持续失败 → 配置错误，不应与真正的"健康退化"混为一谈 |

### 1.3 预期

健康度统计应区分两种根本不同的异常模式：

1. **健康退化**（Degraded）：任务曾经正常运行，后来开始持续失败 — 需要关注，可能是目标服务故障
2. **从未成功**（Never Succeeded）：任务创建后从未成功过 — 更可能是配置错误（URL、参数、权限），需要用户检查配置

## 2. 根因

| 根因 | 描述 |
| --- | --- |
| **健康模型单维度** | `health_status` 仅有 `ok/failing/unknown` 三态，不区分"从未成功"和"曾成功后失败" |
| **统计查询无差异** | `failing_stmt` 对所有 `health_status='failing'` 一视同仁，不检查 `last_success_at` |
| **UI 展示无分层** | 健康度列只有「健康」「异常」「N/A」三种 badge，没有"配置待验证"或"从未成功"的状态 |

## 3. 行业对照

| 系统 | 对"从未成功"的处理 | 对"健康退化"的处理 |
| --- | --- | --- |
| **Kubernetes** | Pod CrashLoopBackOff（明确状态）+ 独立的 `Pending` 状态 | Ready → NotReady + Event 告警 |
| **Airflow** | 首次执行失败 = DAG Run 状态 `failed`，不影响 DAG 的 SLA 判定（需有成功基线） | SLA miss（基于历史成功执行的基线偏离） |
| **Prometheus AlertManager** | `absent()` 函数检测指标是否存在 → 触发「目标不可达」告警，与「指标值异常」分离 | `for: 5m` 持续异常时间窗口触发 |
| **GitHub Actions** | 首次运行失败 → 标记为 failed，但不影响 repo status badge（需有成功 run 基线） | 连续失败 → 显示在 Actions tab，可配置通知 |
| **CronPilot 当前** | ❌ 不区分 — 连续失败 ≥ N 即标记 `failing`，无论是否曾成功 | |

**行业共识**：所有成熟系统都区分「首次/配置问题」和「运行退化」两类异常。前者需要用户**修正配置**，后者需要**排查故障**。混为一谈会导致：①统计膨胀（"异常"数量不反映真实风险）②用户信任下降（"都是异常，那异常=正常"）。

## 4. 方案

### 4.1 核心设计：引入 `never_succeeded` 标志

| 维度 | 当前 | 优化后 |
| --- | --- | --- |
| 健康状态 | `ok` / `failing` / `unknown` | `ok` / `failing` / `unknown`（不变） |
| 是否曾成功 | 间接推断（`last_success_at > 0`） | 显式判断（`last_success_at > 0`）— 无需新增字段 |
| 「持续异常」统计 | `health_status = 'failing'` | `health_status = 'failing' AND last_success_at > 0` |
| UI 健康 badge | 异常 / 健康 / N/A | 异常 / **待验证** / 健康 / N/A |
| Exception Panel | 所有 failing 任务 | 分两组：「健康退化」+「配置待验证」 |

### 4.2 方案对比

#### 方案 A：查询过滤（最小改动）

仅修改统计 SQL，不改 UI badge。

- `failing_stmt` 增加 `WHERE last_success_at > 0`
- Dashboard 卡片「持续异常」只统计曾成功过的任务
- 从未成功的任务仍显示「异常」badge，但不计入卡片数字

**优点**：最小 diff（~5 行 SQL 修改）  
**缺点**：UI 上仍显示"异常"，与统计数字不一致；用户看到 badge 说异常但卡片说 0，会困惑

#### 方案 B：查询 + UI 分层（推荐）

修改统计 SQL + 引入「待验证」badge + Exception Panel 分组。

- 统计层同方案 A
- 健康 badge 增加「待验证」（`failing` 且 `last_success_at = 0`）
- Dashboard 新增「待验证」统计（独立或 sub-text）
- Exception Panel 分两组展示

**优点**：语义清晰；用户一眼区分"配置问题"和"运行故障"；统计与 UI 一致  
**缺点**：改动范围稍大（~8 个文件）；需要新的 badge 样式

#### 方案 C：新增 health\_status 值

在 `health_status` 列中增加 `'never_ok'` 枚举值。

- `update_job_health`：当 `last_success_at = 0` 且失败 ≥ N 时，设为 `'never_ok'` 而非 `'failing'`
- 所有查询按新枚举值分类

**优点**：数据层语义最精确  
**缺点**：schema 变更 + 影响面大（所有引用 `health_status` 的代码都需适配）；与现有 `last_success_at` 字段语义重复

**推荐方案 B**：利用已有的 `last_success_at` 字段（无需 schema 变更），在查询层和 UI 层同时做分层。「待验证」badge 用独立颜色（蓝色/灰蓝色）区别于「异常」（红色）。

### 4.3 方案 B 详细设计

#### 4.3.1 统计查询变更

```
# app/repositories/cron_repository.py

# 「持续异常」— 仅统计曾成功后退化的任务
failing_stmt = (
    select(func.count())
    .select_from(JobHealth)
    .join(CronInfos, CronInfos.id == JobHealth.cron_info_id)
    .where(JobHealth.health_status == HEALTH_FAILING)
    .where(JobHealth.last_success_at > 0)          # ← 新增
    .where(CronInfos.status != -1)
)

# 「待验证」— 从未成功过且持续失败的任务（新增统计）
never_ok_stmt = (
    select(func.count())
    .select_from(JobHealth)
    .join(CronInfos, CronInfos.id == JobHealth.cron_info_id)
    .where(JobHealth.health_status == HEALTH_FAILING)
    .where(JobHealth.last_success_at == 0)          # ← 从未成功
    .where(CronInfos.status != -1)
)
```

#### 4.3.2 健康 badge 渲染逻辑

```
{# app/templates/redesign/_dashboard_rows.html #}

{% if item.status == -1 %}
  <span class="health-badge off">已下线</span>
{% elif h and h.health_status == 'failing' and h.last_success_at and h.last_success_at > 0 %}
  {# 曾经成功过 → 真正的健康退化 #}

  <span class="health-badge ok">健康</span>
{% else %}
  <span class="health-badge unknown">N/A</span>
{% endif %}
```

### 4.4 数据层设计

#### 4.4.1 无需 schema 变更

`job_health` 表已有 `last_success_at`（BigInteger, default=0）。当 `last_success_at = 0` 时表示从未成功。这是一个**已有但未充分利用**的字段。

#### 4.4.2 health\_status 写入逻辑不变

`update_job_health()` 的写入逻辑无需修改。`health_status` 仍然在 `consecutive_failures >= N` 时设为 `'failing'`，读取端根据 `last_success_at` 做分层。这是**写简读分层**的设计模式，避免了对写路径的侵入。

#### 4.4.3 查询层分类逻辑

```
# 真正的健康退化：曾成功后变为 failing
is_degraded = (JobHealth.health_status == 'failing') & (JobHealth.last_success_at > 0)

# 配置待验证：从未成功且 failing
is_never_ok = (JobHealth.health_status == 'failing') & (JobHealth.last_success_at == 0)
```

## 6. 不做

- 不修改 `job_health` schema（复用已有 `last_success_at`）
- 不修改 `update_job_health()` 写逻辑（读端分层，不侵入写路径）
- 不新增 `health_status` 枚举值（避免大面积代码适配）
- 不改变 `health_failing_threshold` 的语义（仍是连续失败次数阈值）

## 8. 验收

| # | 场景 | 期望 |
| --- | --- | --- |
| 1 | 所有任务从未成功 | 「持续异常」= 0；sub-text「N 个待验证」；badge 显示蓝色「待验证」 |
| 2 | 有任务曾成功后变为 failing | 「持续异常」= M（M = 曾成功后 failing 的数量）；「待验证」正确 |
| 3 | 点击筛选「待验证」 | 列表仅显示 `health_status='failing' AND last_success_at=0` 的任务 |
| 4 | 待验证任务首次成功 | badge 从「待验证」变为「健康」；统计更新 |
| 5 | 曾成功任务恢复后再次失败 | badge 从「健康」→「异常」（非「待验证」，因为 `last_success_at > 0`） |

## 9. 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| `last_success_at` 历史数据为 0 | 中：老任务如果 `last_success_at` 从未被写入（创建于 OPT-P2-13 之前），会被误分类为"从未成功" | 检查数据：如果任务有成功的 `job_log` 记录但 `last_success_at=0`，可执行一次修复脚本 |
| 「待验证」长期不处理 | 低：这些任务本来就是配置问题，不处理不影响其他任务 | Exception Panel 中给出"检查任务 URL 和参数"的操作建议 |
