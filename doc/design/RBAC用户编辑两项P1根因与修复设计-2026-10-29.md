## 1. 问题与影响边界

### 1.1 P1-A：签名没有被破解，原始比较基准被服务器替换

数据 snapshot 指字段值集合，不是截图。正常三方比较应使用首次页面 `original`、锁内数据库 `current` 和用户提交的 `requested`。现有服务的比较本身正确；路由在原生 POST 的确认回显中重新生成 original，破坏比较前提。

1. 管理员甲 GET：原邮箱 `old@example.invalid`，签名 token 为 T0。
2. 管理员乙或该用户本人把数据库邮箱改为 `concurrent@example.invalid`。
3. 甲旧表单提交清空邮箱，缺清空确认；回显保留空输入，却携带服务器按当前邮箱生成的 T1。
4. 甲填写理由重提交；后端比较 T1 的 current 邮箱与数据库一致，返回成功并清空。

**影响：**丢失并发更新，且成功审计把实际被删除的新邮箱记录下来，却不能证明管理员看过它。回显本身没有业务写入，危险发生在下一次 POST。该问题不是“所有管理员都能越权”，也不等于常规 JS 弹窗每次都有此问题；已复现的是原生确认回显路径。凡保留旧请求、同时换新基线的后续回显，都属于同源检查范围。

### 1.2 P1-B：验收工具可在错误数据库中删除已有表

`verify(database_url)` 不校验 URL/库名/已有对象，初始化 app 后立即执行 `db.drop_all()` 和 `db.create_all()`。错误连接串只要账户有相应权限，就可能删除已注册在 metadata 的用户、组、审计等表。真实范围取决于该进程已导入的模型；不是仅删除本轮 fixture。

**严重性：**P1-B 的潜在损失比普通测试失败高，可能不可逆；P1-A 损害业务更新与确认的可信性。两项均应在提交前处理。当前没有证据表明生产数据已经受损，本方案不臆测事故已经发生。

## 2. 根因与测试漏洞

| 层次 | P1-A | P1-B |
| --- | --- | --- |
| 直接代码原因 | `users_edit()` 在 GET/POST 分支前统一构造 edit\_ctx；其 token/original 来自 POST 当前 DB。确认失败返回时只传 form\_values，没有覆盖这个新 token。 | verify() 把任意调用者传入的 URL 当成一次性测试库，直接 drop\_all；create\_all 默认还依赖当前全局 metadata。 |
| 建模原因 | 没有把“当前授权/只读对象”“首次原值”“用户请求值”分成三个数据源。回显被当作纯展示，忽略隐藏字段会控制下一次写入。 | 把 fixture 生命周期和数据库生命周期混在一起，用全表清空获得干净基线；脚本名中的 MySQL 不构成后端约束。 |
| 行为原因 | 验证只关注单个响应和最终写服务，未追踪 GET→首次 POST→回显→二次 POST 的原值不变量。 | 只在正确的一次性容器运行脚本，由正确环境掩盖了脚本没有自证隔离；没有给生产式连接串做否定演练。 |
| 既有测试为何漏掉 | `test_native_clear_email_fallback_preserves_form_and_unique_names` 检查文字、保留输入和节点数量，没有提取回显 token 验证它仍是 T0；并发测试直接一次 POST，没有中间回显。 | 没有入口负向测试证明“非法 URL 不连接”“占用库不 DDL”“无 DROP 仍可运行”；成功锁等待演练无法揭示误删。 |

这两项根因不能归结为“粗心”。应增加跨请求不变量、外部资源所有权和否定路径观测，而不是只增加成功用例数量。

## 4. P1-A 推荐方案：冻结一次编辑的原始快照

**R5 后续细化：**已确认的 R5 将签名升为 v2 并加入 editor\_scope；本文“不改 schema/salt”为当时 P1 批次边界。token 在可恢复 POST 中仍不变，JS original 现在等于已验签 token 的表单投影（而非整个载荷），详见[R5 设计 §2.1](R5用户编辑字段意图与范围外组保留设计-2026-10-29.html)。

### 4.1 三份数据各司其职

- **original：**首次 GET 签名载荷；在可恢复 POST 回显中不可替换。服务端验签后的对象是 JS original 表单投影和只读确认邮箱的唯一来源。
- **requested：**独立表单值对象，按白名单恢复输入；不得写回 ORM user 以求回显。规范化成功时使用规范化结果；失败时只在独立展示模型里保留可安全展示的原始文本。
- **current：**只用于当前授权、目标状态和最终写服务比较。不得因为重新读取 DB 就覆盖 original 或未修改字段的表单初值。

### 4.2 路由阶段与响应冻结

1. 先执行既有身份、CSRF、目标存在/停用、自编辑及目标管理 Scope 检查。未授权不回显快照，API 读取异常 fail-closed。
2. GET 通过校验后，按现有字段构建 T0 并渲染；这是新编辑的入口。
3. POST 读取请求 token，调用已存在的 `verify_user_edit_snapshot()` 验签及 actor/target 绑定。通过后，只能将**收到的 token 原文**和 verified snapshot 放入 POST 回显上下文，不能用当前 DB 重新签名。角色/组授予校验继续读当前授权，不因为 token 有效就放行。
4. 输入无效、清空未确认、理由无效、可确定的 flush/保存失败等**可继续填写**响应，保持 T0，恢复表单请求值；POST 回显上下文构造不允许有“缺 original 则从数据库构建”的默认分支。
5. token 缺失、签名/形状/绑定无效：Ajax 返回既有 failed 语义和刷新提示；原生返回**无可提交编辑表单**的失效提示区，只有显式“重新加载编辑页”GET 链接。不把未验签内容塞入 script，也不静默丢弃旧输入后生成可提交新基线。
6. 无法忠实、安全回显的角色/组非法参数，或者当前 Scope 已不足以展示目标时，使用固定错误/禁止响应和显式重新加载入口；不能删除不可见选项后留下可提交的缩水组集合。
7. 已有 CONFLICT/COMMIT\_UNKNOWN 原生 PRG 继续明确提示并重新 GET 数据；这是显式结束旧编辑后的新页面，不是保留旧请求的确认回显。Ajax 继续留页提示刷新，不自动重新发 POST。

**最小必要变化：**路由拆开 GET/POST 的上下文构造，原生失效状态增加不可提交提示；邮箱回退确认加入原始邮箱只读说明。正常编辑、CSRF、原生提交方式、Ajax 公共守卫与提交按钮类型保持原机制。现有 JS 组选择器 P2 是独立发现，本方案不顺手修复。

### 4.3 不变量和数据语义

```
可恢复 POST 响应：
  echoed_token == incoming_verified_token（原文完全相等）
  JS original == decode(echoed_token)
  确认原邮箱 == verified_snapshot.email
  回显输入 == 本次 requested 的可安全展示值
  下一次服务比较仍使用 T0 的 original

业务提交：
  current == original → 应用有效差异
  current == requested → 已等价完成，不重复写
  current 同时不同于 original / requested → 整体冲突
```

不增加确认时数据库锁，也不在页面等待期间持有事务。对“邮箱原来为空、后来被他人新增”的场景，请求仍空表示该字段没有修改意图，不应清掉新值；其他字段有效修改可独立应用，沿用父设计。签名快照没有时间过期，不借本次修复引入 TTL 或 auth\_version 新字段。

## 5. P1-B 推荐方案：无自动删除、专用独占空库、限定建表

### 5.1 入口先拒绝，再连接

1. 仍要求显式传入 `--database-url`，不读 conf.ini、不从环境兜底开发连接。用 SQLAlchemy URL 解析，不做子串判断。
2. 仅接受脚本已使用的 `mysql+pymysql`；SQLite、其他后端/驱动、缺库名、格式损坏直接拒绝。专用库名完整匹配 `^cronpilot_user_edit_verify_[0-9a-f]{12}$`。旧随意库名不再兼容；不提供 --force / --allow-production 豁免。
3. 库名只是误用防线，不能证明数据库所有权。调用方必须使用预建、每次新建的独占 schema，优先放在一次性 MySQL 容器；账户仅能访问该 schema，无全局写权限，不授予 DROP/ALTER/DELETE/TRUNCATE 等无关权限。具体最小 CREATE/索引权限按实际 MySQL 建表结果配置，不以文档猜测替代验证。
4. 错误日志只给固定阶段与后端/安全库名，不输出原始 URL、password、查询参数或未经处理的连接异常文本。`hide_password` 仅处理 URL 密码位置，不能据此认为 query 参数也已脱敏。

### 5.2 数据库准备和失败顺序

1. 连接专用 schema 后先只读核对实际默认 schema 与已验证库名一致，确认可见所有对象；读取失败一律拒绝。
2. 通过 Inspector 分别读取整个 schema 的表名和视图名。**任一对象存在都拒绝**，包括与本轮四表无关的哨兵表；不是只检查是否已有 rbac\_users。库内对象可见性须由专用账户权限和隔离实例保证，不声称检查能识别故意隐藏的对象。
3. **移除 drop\_all，整个脚本不执行 DROP/TRUNCATE 或全表清理。**按固定清单和顺序创建上述四表，`checkfirst=False`。metadata 即使注册额外模型也不能扩大建表集合。
4. 必须等全部建表成功后才插入 fixture。建表失败就停止，保留可能部分建成的空表，不调用清理和重建。MySQL DDL 可能隐式提交，不能靠 rollback 撤销部分 DDL。
5. 同版本脚本误用同一新库并发启动时，固定首个 CREATE 至多让一个实例成功，另一个因表已存在失败并在 fixture 写入前停止；必须有真 MySQL 并发验收。禁止将 checkfirst 改回 True 后复用另一实例已建表。
6. 验收仍执行现有双连接锁等待、更新、冲突及锁释放检查；成功输出保留 `MYSQL_USER_EDIT_U2: OK`，加隔离阶段成功标志。失败退出非零，不输出成功标志。
7. 脚本结束仅关闭本轮 session/连接；成功和失败均保留专用 schema 供排查。下一次使用新 schema；销毁一次性容器/专用库由外层明确生命周期管理，不把清理权限重新放回脚本。

**承诺边界：**这能防止验收脚本自动删除已有业务表，防止占用 schema 被复用。它不是对恶意 DBA 或任意外部进程的数据库安全隔离：前置检查到建表之间外部仍可能建对象，必须结合独占 schema 与受限账户；遇到竞争/残留以停止为准，不自动修复环境。

## 6. 方案合理性、专业性与备选比较

| 问题 | 候选 | 评估 | 决定 |
| --- | --- | --- | --- |
| P1-A | 只给 CONFIRM\_REQUIRED 分支补回 T0 | diff 最小，但理由失败、资料校验失败和事务失败的回显仍可重置基线，根因未收口。 | 不选。 |
| P1-A | 所有失败都丢弃输入并刷新 | 可避免混合新旧值，但恢复成本高，改变既有失败回显契约；并不能代替 token 无效时的明确说明。 | 只用于不可安全继续的失效/越界状态，不作为正常失败策略。 |
| P1-A | 冻结已验签 token，分离三个数据源 | 恢复三方比较前提；覆盖多次回显；不加表/缓存/长事务；保留既有权限与交互。 | **推荐。** |
| P1-A | 服务器缓存快照、加新版本列或跨请求持锁 | 引入跨 worker 状态、迁移或锁时长成本，没有必要；仍需解决回显基线一致性。 | 不选。 |
| P1-B | 只检查库名，再 drop\_all | 带专用名的库也可能已有重要数据；删除能力仍在，不满足不破坏已存在状态。 | 不选。 |
| P1-B | 提示确认 / 加 --force | 自动化易误传或习惯性确认；没有资源隔离的可验证保证。 | 不选。 |
| P1-B | 专用空库、取消删除、四表显式建表、受限账户 | 使误用默认失败，且保留证据。代价是调用方准备新库、失败残留需外层清理；与现有一次性 MySQL 验收方式匹配。 | **推荐。** |
| P1-B | 脚本自动创建/删除数据库或自建容器 | 隔离强，但增加全局权限/Docker 耦合和生命周期复杂度；本次必要目标可由外层准备满足。 | 不在本批加入。 |

**专业性判断：**推荐方案直接对应信任边界和数据生命周期，具备否定路径、失败分类、最小权限、审计一致性、可复现实验与明确停止条件；不依赖“已有测试都绿”。不以没有统计依据的分数或全 A 自评分代替验证。

**合理性判断：**P1-A 主要是路由上下文组织，时间/空间成本与固定字段数量相当，仍只在有意图变更时进入行锁；P1-B 每次多一次 URL 检查和少量元数据查询，远小于启动数据库与锁测试成本。复杂度和用户影响均局限于对应入口；双 P1 可以独立验收和提交。

## 9. 可执行验收矩阵

### 9.1 P1-A：不能只断言页面出现文字

| 编号 | 输入/时序 | 必需断言 |
| --- | --- | --- |
| A-01 | 原值 old → 并发 concurrent → 原生清空缺确认 → 回显 → 合法理由提交 | 中间 token 原文等于 T0；第二次 CONFLICT；DB concurrent；无成功审计、无 auth\_version/Token/缓存副作用。 |
| A-02 | 先回显确认，之后并发更新；或连续两次理由失败后并发更新再提交 | 每一层回显均 T0；二次/三次提交仍冲突，不部分保存。 |
| A-03 | 相同确认流程，无并发 | 合法确认后 SQL NULL，理由 trim 后与一条 user:update 同事务；资料-only 无授权副作用。 |
| A-04 | 邮箱、花名、岗位校验失败 / Scope 参数非法 / 审计 flush 失败 | 能安全继续的分支 token/JS original 保持 T0、请求字段保留、无 ORM dirty 回填；无法忠实回显时不得提供可提交新表单。 |
| A-05 | 缺 token、篡改、未知版本、actor/target 不匹配 | Ajax failed；原生失效提示无 form/token/保存按钮，显式 GET 可重新加载；不能把非法载荷作为 JS/HTML。 |
| A-06 | 当前邮箱已被其他请求清空；原邮箱为空后来被填入 | 前者 ALREADY\_APPLIED、零成功审计；后者无清空意图，不清除新增邮箱。 |
| A-07 | 并发改变花名/岗位，或角色+组授权单元；本人资料更新与管理员编辑交错 | 资料意图字段分别比较，角色/组耦合，任一冲突全拒绝；未动字段不覆盖别人新值。 |
| A-08 | 反复确认期间 actor 降级/离组、目标停用；组被删除 | 当前授权/存在性仍拒绝；原始 token 不成为授权凭证，无越界数据回显。 |
| A-09 | 无 JS 浏览器 POST；JS 正常确认；先 JS 关闭后恢复再确认 | 完整填写→确认→响应/PRG；三动态字段唯一；成功与冲突准确，重新启用 JS 不造成同名 visible/hidden 字段冲突。遇到现有 P2 组问题独立登记，不把它当本 P1 已修复。 |

### 9.2 P1-B：默认拒绝与不破坏

| 编号 | 输入/场景 | 必需断言 |
| --- | --- | --- |
| B-01 | SQLite/其他 backend/缺库名/生产式库名/仅包含而非完整匹配前缀 | 解析拒绝；app/engine/连接/DDL/fixture 调用均为 0；测试不能访问真实业务库。 |
| B-02 | 合法专用名但库中已有用户表、无关 sentinel 表或视图 | 非零退出；零 DDL/fixture DML；完整哨兵对象/行校验值不变。 |
| B-03 | 检查对象失败、连接失败、默认 schema 不一致 | 拒绝，不回退空集合；不写成功标志，日志不含密码/原始 URL。 |

| B-05 | 第二张表建表故障；或同脚本两个进程误用同一空库 | 失败者 fixture DML=0，未删任何表；部分 DDL 留存且重跑拒绝。并发最多一个成功写 fixture，其余非零退出。 |
| B-06 | 无 DROP 权限的专用账户 + 新空 schema | 真 MySQL 完成原有锁等待、更新审计、冲突与锁释放，成功标志保留；结束不自动删除 schema。 |
| B-07 | 合法占用库再次执行 | 拒绝；首次成功结果/审计/fixture 原样保留，调用方使用新库重跑。 |

## 10. 风险、回滚与安全评估

| 风险 | 控制/取舍 |
| --- | --- |
| 反复失败后原值显得陈旧 | 这是保持首次编辑意图所需；显示原邮箱和刷新提示。用户主动重新 GET 才换基线，不能为了减少冲突静默接纳新值。 |
| 旧 token 长期存在 | 沿用父设计无时间过期；每次再授权、锁内比较。密钥变化/格式/绑定失败拒绝；不在本批引入额外超时策略。 |
| 新失效提示使用户输入不能继续提交 | 仅在原始快照无法证明或当前授权不足时停止；显式提示重新加载，与静默换基线相比安全且可解释。 |
| 专用 schema 命名看起来正确但实际含业务数据 | 整库非空拒绝、不 DROP、账户独占，三者缺一不能称为隔离；库名不被描述为安全认证。 |
| DDL 部分成功或进程崩溃遗留 | 保留现场、非零退出、新库重跑；不声称 MySQL DDL 可由回滚完全恢复。清理由外层已知的一次性实例生命周期负责。 |
| 旧脚本调用方依赖重复清空同库 | 这是有意的验收工具兼容性收紧；更新 U2 验收说明，明确每 run 新库。不新增绕过安全守卫开关。 |
| 回滚方式 | P1-A 若需止损，临时禁止原生清空提交并明确提示，不恢复混合基线；P1-B 若新工具不可用，停用该验证入口，不回滚到无条件删表。历史成功审计不重写，生产业务字段不迁移。 |

权限与数据访问仍按父设计：种子/全局管理员及有合法 Scope 的按组管理员可编辑目标；Operator/Viewer 无用户管理权限。邮箱是个人信息，回显只使用原已展示值；密码、完整 Token、Session、CSRF 等不进入 snapshot/detail，不增加审计可见角色。

## 11. 复盘与防再发落点（实施后必须落实）

设计阶段未执行修复；以下为原批准复盘契约，现已由末尾链接的实际七项复盘落实：

1. **定位：**P1-A 路由回显上下文，P1-B verify() 初始化删表；附实际负例输出/浏览器证据。

5. **防护测试：**A-01～A-09、B-01～B-07 中新增实际用例名称、命令、断言和结果。
6. **同类排查：**全仓搜索签名快照回显重建、drop\_all/TRUNCATE 与 raw URL 日志；登记结果，新增范围外问题不夹带实现。
7. **预防：**`tests/test_user_edit_change_set.py` 必须持久化“任意可恢复失败 token 原文不变”矩阵；`tests/test_user_edit_mysql_guard.py` 固化“非法目标零连接、非空目标零 DDL、额外 metadata 不扩表、无 DROP”断言。实际修复复盘落在 `doc/postmortem/`，HTML/MD、两份索引及 Release Notes 同步。
