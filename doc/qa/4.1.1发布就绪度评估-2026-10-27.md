# CronPilot 4.1.1 发布就绪度评估

日期：2026-10-27 · 基线：`main` 的全部未提交工作树 · 对象：拟议 **v4.1.1** · 状态：**版本归档完成前不具备发版条件**

**裁决：**本轮 RBAC Scope 边界、注册审批关联表、数据库当前 actor 与陈旧 Session 防护已经形成有测试、有迁移和有浏览器证据的候选变更。真实 MySQL 迁移演练现已通过；在补齐上一版 `v4.1.0` 的版本归档并使版本门禁全绿前，仍不得创建 `v4.1.1` tag 或发布 Release。

## 1. 范围与版本序列

- 仓库最近 tag 为 `v4.1.0`；拟议版本 `v4.1.1` 在语义版本序列上成立。
- 候选内容：RBAC 用户管理授权授予边界、注册申请—业务组关联表与查询切换、审批拒绝 Scope 授权、审批列表和用户管理的数据库当前 actor、Session 撤销、全局管理员 Scope 回显，以及相应设计、复盘、QA 与浏览器证据。
- 本评估不把“提交候选变更”误写为“发布”；tag、GitHub Release 与公开发布包均不在本轮执行范围。

## 3. 发布阻断项

**B1 · 版本归档不完整：**版本一致性门禁报告路线图缺少 v4.1.0、Release Notes 缺少 v4.1.0 正式章节，且 `[Unreleased]` 仍含 4 个小节和 40 个实质条目。现有 `v4.1.0` tag 与文档状态矛盾，不能在此基础上发布 4.1.1。

**已关闭 · 真实 MySQL 迁移演练：**在自动清理的 MySQL 8 容器中，以旧版 `INT` 主键/关联列创建 7 张目标表后实际调用 `_ensure_id_columns_bigint(backend='mysql')`。9 个目标列均变为 `BIGINT`，三张主键仍为 auto-increment；随后成功插入 `35184372088832` 的高位任务 ID。

## 4. 发版前最小收口顺序

1. 先在隔离真实 MySQL 库复现升级路径，记录主键、关联列、索引、nullable 与 auto-increment schema 断言，并将证据入库。
2. 以已存在的 `v4.1.0` tag 为事实基线，补齐 4.1.0 的 Release Notes 和路线图归档；将后续实质变更保留为 4.1.1 的候选内容。
3. 为 4.1.1 撰写面向用户/运维的英文 Release Notes，清空 Unreleased 的实质内容，并同步 README、路线图、HTML/Markdown 版本索引。
4. 重跑版本一致性、完整测试、黄金路径、MySQL/Docker 发布矩阵与发布包双构建；仅全部通过后才创建 tag 和 GitHub Release。

## 5. 可提交性与风险

**提交建议：**可以将当前所有代码、迁移、测试、设计、复盘、QA 和脱敏浏览器证据作为单一候选提交保存。提交不会声称发版完成，且能固定本次已通过的授权行为与验证证据。

发布风险现集中在版本治理，而不是本次已验证 RBAC 逻辑或历史升级路径。提交后仍须保持 release status 为 blocked，直至 B1 关闭。
