# 为什么需要 run\_id 强关联

决策状态：待确认 · 适用范围：JobLogEvent，后续可扩展至 JobLogItems

**结论：**`trace_id` 适合跨组件检索，`run_id` 适合数据库内的父子数据完整性。二者不是替代关系。执行事件必须以 `run_id → JobLog.id` 作为主关联，以 `trace_id` 作为兼容检索键；新事件要求 run\_id 非空，历史无法唯一回填的事件保留 legacy 标记。

## 1. 当前实现事实

| 事实 | 代码依据 | 含义 |
| --- | --- | --- |
| 每次执行都有一个 JobLog | `cron_do` 调用 `_create_pending_job_log`，并先提交父记录 | `JobLog.id` 天然代表一次执行实例 |
| 事件通过 trace 查询 | `JobLogRepository.events_for_trace_id()` | 当前关联依赖字符串约定 |
| 事件唯一约束是 trace + seq | `JobLogEvent.__table_args__` | 能保证顺序，不保证父记录存在 |
| trace 在 JobLog 中唯一 | `JobLog.trace_id unique=True` | 正常路径可回查，但仍是应用层间接关联 |

## 2. 不做强关联的具体风险

### 2.1 数据库无法证明事件属于哪个运行

现在事件表只有 `trace_id` 和 `cron_id`。数据库可以接受一个不存在于 `job_log` 的 trace，也无法通过外键阻止事件归属错误。应用查询“先按 trace 找父记录，再按 trace 找事件”，属于两次独立查询，不能形成数据库级一致性约束。

### 2.2 trace 是检索上下文，不是稳定的关系键

trace 可能来自 UUID、日志透传或历史数据迁移；它适合在日志平台全文搜索，却不应承担父子表的唯一身份。若 trace 生成失败后重试、人工导入或跨系统复制，字符串键更容易出现缺失、重复或格式不一致。

### 2.3 故障排查会出现“看似完整、实际串线”

并发执行时，若某个事件错误地带入另一次 trace，时间线仍可能按 seq 正常展示，但内容来自另一运行。没有 run\_id 外键，系统无法在写入或查询时发现这种串线。

### 2.4 无法可靠处理孤儿事件和父记录清理

保留策略、备份恢复和历史迁移都需要知道父记录是否存在。只有 run\_id 外键，才能统计孤儿事件、阻止误删父记录或在清理时明确采用 RESTRICT/SET NULL 策略。

## 3. 为什么选择 JobLog.id 作为 run\_id

| 候选 | 评价 |
| --- | --- |
| 继续只用 trace\_id | 不推荐：改动最小，但关系完整性和 SQL join 可靠性不提升。 |
| 新增独立 UUID execution\_id | 可行但成本高：需要父表、事件表、items、API、迁移和所有查询同时引入新身份，且与现有 JobLog.id 重复表达。 |
| **JobLog.id 作为 run\_id** | 推荐：已有不可变主键、创建早于事件、跨页面已有详情 ID，新增列和索引即可形成直接父子关系。 |

这不是把业务日志 ID 误当 trace，而是明确“一个 JobLog 就是一轮执行实例”。`trace_id` 继续保留，因为它承担跨 HTTP、应用日志和指标的检索语义。

## 4. 推荐数据结构

**JobLog**id = run\_id  
trace\_id = cross-system key

→

**JobLogEvent**run\_id FK  
trace\_id 兼容列  
(run\_id, seq) unique

→

**Presenter**按 run\_id 主查  
trace\_id 回退 legacy

→

**Run Inspector**展示父记录 + 时间线

| 字段 | 新数据 | 历史数据 |
| --- | --- | --- |
| `JobLogEvent.run_id` | 非空，值为创建后获得的 JobLog.id | 先按 trace 唯一匹配回填；无法唯一匹配则 NULL |
| `JobLogEvent.trace_id` | 保留并与父记录一致 | 原值不改，继续支持旧查询 |
| 唯一约束 | `(run_id, seq)`；必要时保留旧 trace+seq 约束过渡 | 旧事件按 legacy 查询，不强行猜测 |
| 外键策略 | 同库时 FK → JobLog.id，删除策略 RESTRICT | 回填前不启用强制非空；完成核验后再收紧 |

## 5. 写入与查询方案

### 写入

1. `cron_do` 先执行已验证的 `_create_pending_job_log` 并提交，得到 `saved_jl.id`。
2. 初始化 `ExecutionTracer(run_id=saved_jl.id, trace_id=trace_id, cron_id=cron_id)`。
3. `emit` 使用当前已验证的独立 `with db.engine.begin() as conn`，同时写入 run\_id 和 trace\_id。
4. 如果事件写入失败，不回滚业务 session；父记录的观测状态尽力标记 degraded。

### 查询

```
events = repo.events_for_run_id(run_id)
items = repo.items_for_run_id(run_id)  # 第二阶段；旧数据按 trace 回退
parent = repo.get(JobLog, run_id)
```

页面路由仍可兼容旧的 `trace_id` 入口：先由唯一 trace 找到 JobLog，再切换为 run\_id 查询。新链接统一携带 run\_id；trace\_id 只用于复制、跨系统检索和 legacy 回退。

## 6. 迁移、兼容与回滚

1. 新增 nullable `run_id`、索引和迁移计数，不改变现有事件读取。
2. 离线回填：仅对 trace 在 JobLog 中唯一匹配的事件写 run\_id；输出 matched/ambiguous/orphan 计数。
3. 双写阶段：新事件同时写两列；Repository 优先 run\_id，找不到时按 trace 查询并标记 legacy。
4. 核验通过后，将新写路径的 run\_id 设为非空，并启用 `(run_id, seq)` 唯一约束。
5. 回滚只关闭新查询和新写入列，不删除旧 trace 字段、不删除历史事件；因此可逆。

## 7. 成本与边界

| 成本 | 控制 |
| --- | --- |
| 一次迁移和索引增加 | JobLog.id 已存在，无需新增身份生成器；先 nullable，再收紧。 |
| 写入字段增加 | 一个 BIGINT + 索引；事件已有固定上限和写入预算。 |
| 旧数据不完整 | 不强行回填；legacy 事实透明展示，避免错误归属。 |
| items 仍按 trace | 本期先解决阶段事件；JobLogItems 在第二阶段按同一 run\_id 策略迁移。 |

**最终判断：**run\_id 强关联不是为了增加一个“看起来更专业”的字段，而是把“某次执行的父记录—阶段事件”从应用层字符串约定提升为数据库可验证关系。其增量成本小于引入新 execution\_id，且不破坏现有 trace 检索和历史兼容，是当前执行侧观测最合理的收口方案。

本说明仅解释设计决策，未修改模型、迁移、Repository 或页面实现。
