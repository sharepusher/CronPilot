## 2. 今天核验的新阻断：SQLite用户保存边界

来源为[发布前审查F1](v4.2.0-release-review-2026-10-30.html)，与此前“锁释放测试盲点F1”不是同一项。

1. `user_revoke`：原请求读过授权后，另一独立连接将actor降为viewer并提交，原请求仍返回updated并保存。
2. `user_conflict`：原请求读过目标后，另一独立连接保存concurrent-value，原请求仍返回updated，最终request-value覆盖新值。

两项今天均observed=true，属于产品保存边界问题。串行处理的七状态页面测试不涵盖该内部交错；MySQL锁结论不能替代SQLite原子保护。[今天的原始结果](evidence/next-steps-2026-11-02/rbac-sqlite-races.json)。

使用既有隔离诊断函数，数据库仅位于TemporaryDirectory并自动清理，未连接datas开发库。整个旧脚本因任务模块移除了scheduler属性而退出1，任务那一例本轮没有结论；随后只执行仍可运行的两个用户用例，未修旧脚本。

```
.venv-py311/bin/python -c "import runpy,json; m=runpy.run_path('doc/qa/evidence/v4.2.0-review-2026-10-30/sqlite_authorization_race.py'); print(json.dumps([m['run_case'](c) for c in ('user_revoke','user_conflict')],indent=2))"
两项：independent_commit=true, outcome=updated, stored_value=request-value, observed=true
```

## 3. 建议执行顺序与完成条件

1. **第一优先：SQLite保存边界专项设计。**核对实际驱动的事务启动、授权读取、三方比较和写入边界，同时盘点任务保存同类入口。论证SQLite适用的最小原子保护方案，明确连接所有权、忙错误/等待预算、回滚和提交未知处理，与MySQL分开说明。先正式设计并经Review确认，再实现。本页不预选事务API或擅自降低隔离级别。完成条件：独立连接交错不能在撤权后继续写入，不能静默覆盖同字段新值；正常保存及MySQL、no-op、范围外组、审计和结果语义不退化；有七项复盘。
2. **第二优先：最终基线审查与提交清单。**在修复后的同一工作区检查RBAC、任务、启停、API和迁移交叉影响。逐项登记设计/批准范围、代码、测试、证据和限制；纳入未跟踪Python/JS/HTML/MD/图片/JSON。完成条件：最终基线相关回归、双后端、目标角色页面与文档门禁都有本轮证据，提交边界清楚。仅用户要求时commit，本轮不git add。
3. **第三优先：发布收口。**今天术语、版本门禁仍退出1。开发阶段保留Unreleased合理，发布前必须归档正式版本；同步Release Notes、README、路线图及索引，补备份、停止旧写入者、版本列迁移/验证和回滚/混跑边界。审阅失效历史复现脚本，不能将无法执行解释为问题已修复。完成条件：发布门禁通过、升级步骤与风险明确。tag/push/Release须用户明确指令。
4. **后续治理：事务所有权清单，再按证据优化。**沿用[规范评估§4–5](数据库事务与锁使用规范及当前实现评估-2026-10-29.html)，盘点update\_user/set\_user\_groups/set\_user\_active等真实调用方、事务所有者、审计原子性和锁顺序，再核对MySQL索引/EXPLAIN、等待预算与热点。有实证才优化锁，不一次重构全站。
5. **自动门禁另批确认。**[编辑契约门禁设计](../design/编辑契约检查单与行为回归门禁设计-2026-10-29.html)仍待确认。接入前对齐已经完成的专项状态及本次SQLite反例；CI工具上线不等于远端required检查已启用，也不能替代第一优先的产品修复。
