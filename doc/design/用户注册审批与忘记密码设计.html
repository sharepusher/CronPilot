用户注册审批与忘记密码设计

编号：OPT-P1-10 · 日期：2026-08-03 · 状态：Batch 1–4 已交付

一、问题

当前系统存在两个用户体验缺陷：

  1. 新用户无法自助申请加入：所有用户必须由 admin 手动创建（/rbac/users_add），潜在用户需线下联系 admin，效率低。
  2. 忘记密码无引导：登录页（/rbac/login）无任何密码恢复提示，用户不知如何处理。

二、根因

系统初期以 admin 单点管控为核心设计，未设计自助注册流程和密码恢复引导。登录页仅有用户名 + 密码输入，无辅助入口。

三、方案

3.1 注册审批流（方案 A）

3.1.1 业务流程

[登录页] → 点击「注册账号」
    → [注册申请表单] → 填写邮箱/密码/角色/业务组/缘由 → [提交]
        → 系统创建 pending 申请记录
        → 跳转登录页，提示「申请已提交，审批通过后使用注册账号密码登录」

[登录页] → 用户尝试登录（pending 状态）
    → 系统识别该用户名有 pending 申请 → 显示「您的注册申请正在审核中，请耐心等待。」
    → 系统识别该用户名有 rejected 申请 → 显示「申请已被拒绝。原因：xxx」+ 重新申请链接

[管理端] → admin 导航「注册审批」
    → 查看待审批列表 → [批准] 或 [拒绝]
    → 批准：自动创建 rbac_users + user_groups + API Token，用户可立即登录
    → 拒绝：标记 rejected + 备注原因，用户可重新申请

3.1.2 用户名规则

注册时填写完整公司邮箱地址，系统自动提取 @ 前部分作为用户名。邮箱地址保存到 rbac_users.email 字段（新增列），供后续通知等扩展使用。

3.1.3 注册申请表单字段

字段必填规则
公司邮箱✅格式校验（含 @）；自动提取前缀作为用户名；唯一性校验（用户名不可重复）
密码✅用户自设（非默认 changeme），至少 6 位
确认密码✅二次确认，须与密码一致
申请角色✅下拉：operator / viewer / admin（admin 选中时显示引导提示但允许提交；审批时校验审批者范围）
目标业务组✅多选下拉，列出所有已有业务组（至少选 1 个）
申请缘由✅文本域，最长 500 字符

3.1.4 审批权限

审批者类型可见范围
种子 admin（username='admin'）所有申请
__ALL__ 管理员 admin所有申请
组管理员 admin仅 group_ids 与自己组有交集的申请

3.1.5 审批通过后动作

  • 自动创建 rbac_users 记录（使用申请时的密码哈希 + 邮箱）
  • 绑定 user_groups（根据申请的 group_ids）
  • 自动签发 API Token（复用 _auto_issue_token()）
  • 不设 must_reset_password（密码已是用户自设）
  • 写审计日志：action='user:register_approve'

3.1.6 Admin 角色注册（已更新）

admin 角色可通过注册流程申请，但审批时有额外的范围约束：

  • 注册表单中 admin 选项可见，选中后显示引导提示：「管理员角色申请将由系统管理员审批，审批周期可能较长。」（但不禁用提交按钮）
  • 审批时校验审批者的业务组范围 ≥ 申请者请求的业务组（_check_admin_approval_scope()）
  • 种子 admin 和拥有「全部」业务组的管理员可审批任何 admin 申请
  • 按组管理员若业务组范围不覆盖申请者的请求组，则在审批列表中不可见该申请

3.1.7 停用不可恢复与重新注册（已补充）

用户一旦被停用（is_active=0），不可通过任何路径恢复启用（"停用不可恢复"策略）。如需使用系统，必须：

  • 通过注册流程重新申请（同一邮箱/用户名可重新提交）
  • 或由管理员在用户管理中重新创建

技术实现：

  • set_user_active()：拒绝 is_active=1 请求
  • update_user()：检查 is_active == 0 的用户不可被改为 is_active=1
  • users_set_active() 视图：在入口处拦截 is_active=1（纵深防御）
  • 编辑页 UI：停用用户显示「已停用（不可恢复）」文本，无恢复按钮

重新注册流程：

  • submit_registration() 仅检查 is_active=1 用户的用户名冲突 → 已停用用户名可重新申请
  • approve_registration() 审批通过时自动删除同名已停用旧记录（释放 UNIQUE 约束），再创建新用户
  • create_user()（管理员手动创建）同理：仅检查启用用户，自动替换停用旧记录
  • 审批页面提示「⚠ 曾被停用」（当待审批用户名存在已停用记录时）

3.1.8 Admin 角色审批权限（已补充）

审批者类型可审批 admin 角色申请？条件
种子 admin✅无条件
__ALL__ 管理员 admin✅无条件
组管理员 admin✅（有条件）审批者业务组 ⊇ 申请者请求的业务组
operator / viewer❌无 user:manage 权限

3.1.9 防恶意注册

威胁防护措施
批量提交（Bot）同一 username pending 状态仅允许 1 条；CSRF Token 校验
数据库膨胀pending 申请 30 天未审批自动标记 expired；启动时清理
用户名抢注rejected/expired 的 username 释放，可重新申请
信息泄露登录时仅 username 精确匹配且有 pending/rejected 记录时才提示注册状态

3.1.10 性能评估

维度分析风险
表规模rbac_registration_requests 预估几十到几百条（内部系统）极低
登录时额外查询仅在「用户名不存在」时才查注册表（WHERE username=? AND status IN ('pending','rejected')）极低
审批列表查询admin 分页查询，有 status + create_time 索引极低
业务组列表复用已有 list_resource_groups()极低

3.2 忘记密码（方案 B：纯提示）

  • 登录页新增「忘记密码？」链接
  • 点击后展示独立提示页面：「请联系您所在业务组的管理员重置密码。如不确定管理员是谁，请联系系统管理员。」
  • 不实现邮件重置（零外部依赖）

3.3 注册进度查询

采用登录时自动提示方案（参考 GitLab Self-Managed / Discourse / Keycloak）：

  • 用户用 pending 账号尝试登录 → 系统自动显示审核状态
  • 无需独立查询页面，登录页本身即为进度查询入口
  • 优势：零额外入口、交互最自然、信息泄露面小

六、审计日志

注册与审批全流程纳入审计日志（rbac_audit_logs），确保可追溯：

事件actionresourceactor (user_id / username)status
提交注册申请user:register_apply申请的用户名user_id=0, username='anonymous'（申请者无账号）allow

  • AUDIT_ACTION_LABELS 中新增中文标签映射：'user:register_apply': '注册申请'、'user:register_approve': '审批通过'、'user:register_reject': '审批拒绝'、'user:register_expire': '注册过期'。

8注册时选 admin 角色提示框出现，提交按钮禁用
9注册已存在的用户名（邮箱前缀重复）提示「用户名已存在」
10组 admin 审批页面仅看到自己组相关的申请
11拒绝一个申请（带原因）→ 用该用户名登录显示「申请已被拒绝。原因：xxx」+ 重新申请链接
