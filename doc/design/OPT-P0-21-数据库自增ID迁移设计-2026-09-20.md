# OPT-P0-21：数据库自增 ID 迁移设计

日期：2026-09-20 · 状态：**待用户确认** · 前置：v4.0.0 后深度 Review、用户澄清“id\_generator 不应继续使用”

## 1. 问题与目标

当前代码仍在 `cron_infos`、`job_log`、`job_log_events` 模型中设置 `default=next_id`，`execution_tracer.py` 还直接写入 `next_id()`。目标是统一由数据库生成这三类业务主键，生产路径不再依赖 `datas/utils/id_generator.py`，优先保证新写入的唯一性、事务性、可观测性和结果准确性。历史数据只做必要的完整性校验，不为低价值历史形态引入复杂兼容层。

## 2. 根因与现状证据

- 应用层生成器只有进程内锁，不能提供 Gunicorn 多 worker 的全局唯一性；时钟回拨也未形成跨进程契约。
- 当前 SQLite 库的 `cron_infos.id`、`job_log.id` 是 `INTEGER PRIMARY KEY`，但 `job_log_events.id` 是 `BIGINT PRIMARY KEY`；三者都由应用层默认值填充，不能把“模型写成 BigInteger”误认为已启用数据库自增。
- 现有收敛设计已要求至少 `job_log.id` 恢复数据库自增；本设计将范围扩展为所有业务主键，消除用户目标与实现分叉。

## 3. 方案

### 3.1 主键策略

移除全部生产代码对 `next_id` 的 import、模型 default 和显式赋值。SQLAlchemy 模型使用数据库自增语义；新建记录不提供 `id`，flush/insert 后读取数据库返回的 ID。历史数据不主动重编号；若现有数据无法满足目标 schema，则迁移前明确失败并停止，不做静默截断或隐式兼容。

### 3.2 后端实现契约

| 后端 | 实现 | 验收 |
| --- | --- | --- |
| SQLite | 需要将主键列建成 SQLite 的 INTEGER rowid 主键；对现有 `BIGINT PRIMARY KEY` 表采用受控重建，复制全部列、索引、约束和数据，再原子替换。 | 重启/迁移幂等；最大历史 ID 后插入得到更大 ID；进程重启后仍唯一。 |
| MySQL | 主键保持 BIGINT，声明 `AUTO_INCREMENT`；迁移前读取最大 ID，保证自增起点大于存量最大值。 | 空库、仅旧小 ID、含 50-bit 历史 ID 三种数据集均能插入并回读 ID。 |

### 3.3 引用列语义审计

新写入链路只要求引用列与当前任务主键类型一致，并在业务边界完成存在性/范围校验。历史引用不做无条件扩容；迁移前执行一次最大值与孤儿引用检查，发现超出目标范围或无法证明完整性即拒绝迁移，由发布方先清理或备份处理。禁止静默截断。

### 3.4 迁移事务与回滚

1. 迁移前做最小快照并记录行数、最大 ID、孤儿引用和约束清单；不满足目标范围立即失败。
2. 先创建临时表并复制数据，校验主键唯一、非空、约束和关键引用。
3. 在明确停写窗口内切换表名；切换失败保留原表并回滚。SQLite 重建按后端分支实现。
4. 在独立验收事务中插入并回读新记录 ID，确认失败时业务事务和观测事务均不产生半写入；重复运行必须幂等。

## 4. 范围

**包含：**三张主键模型、ExecutionTracer 写入、SQLite/MySQL 建表与最小迁移脚本、关键引用的范围校验、模型/仓储/并发测试、ID 生成器死代码审计和设计文档。

**不包含：**历史 ID 重编号、历史引用全面扩容、业务 URL/API ID 格式改造、删除历史数据、在本轮保留 worker 位继续扩展生成器。

## 5. 分批实施

1. **Batch A 契约与盘点：**冻结三张表目标 schema，确认当前数据满足非空、唯一、范围和引用不变量。
2. **Batch B 模型写路径：**移除 next\_id 生产调用，改为 ORM/Core insert 的数据库回填；补 flush 后 ID 与失败回滚测试。
3. **Batch C SQLite：**在停写窗口重建必要表，验证 rowid 自增、约束和重复迁移。
4. **Batch D MySQL：**验证 BIGINT/AUTO\_INCREMENT、起点和并发插入；不做额外历史兼容层。
5. **Batch E 回归与发布：**全量测试、双后端、并发、重启、异常路径和发布文档收口。

## 6. 验收标准

- `rg "from datas.utils.id_generator|next_id\(" app datas --glob '*.py'` 不存在生产写路径。
- SQLite/MySQL 均通过空库和当前支持的数据集迁移测试；超范围/孤儿引用必须拒绝迁移，不能静默成功。
- 两进程/多线程同时插入三类记录不产生主键冲突；应用重启后仍由数据库分配唯一 ID。
- 创建、更新、失败回滚、观测事件写入和重试路径的 ID/状态一致。
- 运行 Ruff、模型序列化测试、关键路由冒烟、全量测试和版本/文档门禁；未创建 4.1.0 tag 直至全部通过。

## 7. 风险与回滚

| 风险 | 控制 | 回滚 |
| --- | --- | --- |
| SQLite 重建遗漏约束/索引 | 目标 schema 断言与迁移后关键查询 | 事务失败保留原表，恢复快照 |
| 当前数据不满足目标范围 | 迁移前检查并 fail-closed | 停止发布，先处理数据 |
| 并发写入造成状态分裂 | 停写窗口、事务边界和并发测试 | 回滚迁移，不上线半成品 |
| 数据库自增起点错误 | 迁移前设置并验证 sequence/AUTO\_INCREMENT | 停止发布，修正起点后重跑幂等迁移 |

确认本设计后，才允许实施 Batch B；确认前不得删除 `id_generator.py` 或修改生产模型。
