1. 问题、根因与目标

1.1 问题

管理平台并非纯 REST 前后端分离系统：页面首次加载、导航和部分表单仍由服务端渲染（SSR）完成，另有 jQuery Ajax、直接 fetch/XHR 和公开 /api/* JSON API 并存。前端请求方式、错误处理、request_id、权限/CSRF 语义和文档出口因此分散，新增交互容易走出未登记的 JSON 路径。

1.2 已确认根因

  • 历史上以 SSR 为主，局部功能逐步加入 Ajax；没有管理端 JSON API 的统一命名空间、资源边界和迁移顺序。
  • 公开 API 面向外部调用方，管理端面向浏览器 Session 与现有 RBAC/CSRF；两者认证模型不同，不能因路径相似而混用。
  • 前端没有一个覆盖 jQuery、fetch 和 XHR 的稳定请求客户端，因此无法可靠落实“每次异步请求有唯一 request_id、失败可统一呈现”的契约。

1.3 目标

在保留 SSR 页面和既有业务行为的前提下，逐领域建立受 Session、CSRF、RBAC 与 scope 保护的管理端 REST/JSON 层；让管理页面的数据读取与写入能够渐进式使用该层，并使每一个 JSON 请求具备已确认的 X-Request-Id 可观测性。目标不是一次性 SPA 重写，更不是改变公开 API 的认证或兼容承诺。

2. 方案与架构边界

核心决策：新增独立的管理端 JSON 命名空间（建议在路由盘点后确定为 /manage/api/v1 或等价受限前缀），只供已登录的管理平台浏览器调用；继续使用现有 Session、CSRF、require_permission 与 scope 规则。公开 /api/* 继续面向外部调用方，不复用其 Token 鉴权、权限假设或错误兼容策略。每个管理 JSON endpoint 属于 P0-A-lite 的显式 request_id 登记范围。
请求类别认证与安全边界request_id 规则迁移策略
公开业务 API既有对外 Token/scope 合约调用方必填；合法值可重复并原样回传不因管理端演进而改认证、路径或 body
管理端 JSON API既有浏览器 Session + CSRF + RBAC/scope浏览器客户端每次请求生成 UUID v4；服务端必填校验并回传逐领域加入，不复用公开 API handler
SSR 文档导航与原生 form既有服务端渲染、Session/CSRF不适用 P0-A-lite Header 契约在对应领域完成切换前保留；不强迫改造成 JSON
scheduler/后台任务内部执行上下文既有 cronpilot_trace_id，每次 UUID v4不纳入 HTTP 管理 API

2.1 管理端 JSON 合约

  • 资源与动词按 REST 语义命名；写操作仅使用对应 HTTP 动词，不以新增“页面 POST 端点”充当长期 API。
  • 请求/响应 body、错误信封和字段验证以 P0-A2 统一契约为前置；禁止某个页面自行发明 JSON 形状。
  • 每个端点必须显式声明所需权限与 scope 检查；先进行角色权限校验，再进行资源 scope 校验，不能因 Session 已登录而省略。
  • 管理端浏览器客户端只能经共享 cpRequest（名称待实现设计确认）发送 JSON；该客户端负责 CSRF、X-Request-Id、超时、非 JSON 响应保护与统一错误映射。禁止新页面直接散写 fetch/XHR/jQuery 请求。
  • 管理端 API 文档必须有受控可发现位置；若使用 OpenAPI，必须明确“仅管理端 Session 调用”、CSRF 与权限前提，不能把管理端 API 误写成外部 Token API。

3. 范围与非范围

纳入不纳入
路由/前端请求盘点；显式 JSON 端点登记；管理端 API 基础层；共享浏览器请求客户端；任务、RBAC、日志等领域的逐批垂直迁移；接口文档、回归和浏览器验收。一次性 SPA 重写；移除 SSR；把管理端 Session API 改为外部 Token API；重写公开 /api/*；改变数据库模型；以“统一 API”为名放松 CSRF、RBAC 或 scope；未验证即删除旧路由。

4. 分批计划

阶段交付退出条件
M0：盘点与基线按页面、路由、请求方式、权限、CSRF、scope、当前 JSON 形状、SSR 回退和测试覆盖建立清单；将“管理 JSON required / SSR excluded”写入路由登记。所有现有 Ajax/fetch/XHR 与目标领域路由均被分类；未分类项不得进入迁移。
M1：管理端 API 基础层确定命名空间、P0-A2 错误信封接入、Session/CSRF/RBAC/scope 顺序、OpenAPI/文档策略和共享 cpRequest 边界。一个只读端点和一个写端点完成正向/未登录/CSRF/无权限/scope 反向测试，且 request_id、错误信封和审计符合 P0。
M2：首个垂直领域选择风险可控且已有 P0 失败闭环的单一领域（建议从任务编辑或用户编辑二选一，确认后再定）；同批交付 endpoint、服务边界、前端调用、SSR 回退与页面对比。目标角色浏览器完成读取、校验失败、写入失败、成功与无权限路径；旧行为有基线对照，SSR 回退可用。
M3：按领域扩展按“任务 → RBAC → 日志/审计”等独立批次迁移，每批只迁移一个资源组，并冻结兼容样本。每批 API 文档、权限/scope、CSRF、request_id、错误状态、路由烟测和浏览器正反向验证全部通过。
M4：收敛与弃用为已完成领域标记旧 Ajax 端点弃用；在观测期后移除重复客户端代码或旧端点。存在替代端点、迁移说明、调用方清零证据、至少一个发布周期的回归记录及明确的删除确认；不得仅凭代码“看似未引用”删除。

5. 页面 Before / After（首个垂直领域的交互边界）

这是交互架构对比，不替代具体页面的视觉设计。M2 选择具体领域后，必须在该领域子设计中补充真实页面的逐字段 Before/After。

BEFORE · 混合页面自带请求逻辑

任务编辑页（SSR + 页面内 Ajax）
浏览器 GET → 服务端渲染页面

保存按钮 → 页面各自 $.ajax / fetch

Header、错误分支、CSRF 处理随页面而异

失败 → 可能直接 Toast 或依赖旧 JSON 字段

保留 SSR，但客户端调用分散，难以统一验证与演进。

AFTER · SSR 壳 + 受控管理 JSON API

任务编辑页（SSR 保留）
浏览器 GET → 服务端继续渲染页面

保存按钮 → cpRequest → 管理端 JSON endpoint

自动发送 CSRF 与每次唯一 UUID v4 X-Request-Id

失败 → P0-A2 错误信封统一映射字段/全局错误；响应 Header 可关联日志

页面布局和导航不被强制改成 SPA；失败时可按批准的 SSR 回退路径恢复。

6. 验收与风险

6.1 每批必须验收

  • 接口：合法 request_id 原样回传；缺失/非法 400 且零业务副作用；P0-A2 JSON 兼容快照通过。
  • 安全：未登录、CSRF 缺失/失效、无权限、跨 scope 资源操作分别被拒绝；不得用公开 API Token 规则替代管理端 Session 规则。
  • 浏览器：用目标角色完成成功和失败路径，验证 UUID v4 Header、字段/全局错误、无权限拒绝与 SSR 回退；按仓库规范保留截图证据。
  • 兼容：既有 SSR 路由保持可访问；迁移前后页面内容、跳转和表单防重复提交均有对照；运行路由烟测与相关专项测试。
  • 文档：端点、权限、scope、CSRF、request_id、错误码和弃用状态与实现同步；若 API body 字段变化，按仓库规则标注 API Breaking Change。

6.2 主要风险及控制

风险控制措施
把公开 Token API 与管理 Session API 混用，造成权限越界独立 Blueprint/命名空间；每端点审查认证、权限和 scope；目标角色正反向浏览器测试。
迁移中删掉 SSR 导致页面或书签失效垂直迁移且保留 SSR；M4 前不得删除旧路径；以调用方清零与观测期作为删除门槛。
共享客户端遗漏 CSRF/request_id 或页面绕过只允许登记的共享客户端；静态搜索 direct fetch/XHR/jQuery 调用并建立门禁；浏览器网络断言覆盖三种历史调用方式。
错误信封与旧页面成功/失败语义不一致M1 依赖 P0-A2 兼容快照；每个垂直领域先锁定基线，再迁移一条路径。
范围膨胀为 SPA 重写每批一个资源组；任何状态管理、路由框架或页面视觉重构另立设计并提供 Before/After。

7. 后续确认点

确认本方案后，先执行 M0 路由与前端请求盘点，再由用户选择 M2 的首个垂直领域。M0 的清单和 M2 的具体 API/页面设计须分别评审确认；在此之前，不实施任何管理端 API 化代码。
