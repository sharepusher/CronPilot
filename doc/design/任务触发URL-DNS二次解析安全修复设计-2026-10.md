## 1. 问题

`validate_and_resolve_url()` 先调用 `validate_trigger_url()`。后者对首次 DNS 结果逐一过滤环回、链路本地、保留和组播地址；前者随后再次调用 `_resolve_host_ips()`，却直接选择第二次结果。`cron_do()` 将这个结果传给 `make_pinned_session()`，成为实际连接地址。

攻击者可控制同一主机的 DNS 序列：首次解析返回公网地址以通过校验，第二次解析返回 `127.0.0.1`、`169.254.169.254` 或其他禁止地址。所谓 pinning 因而固定到了未验证的地址，形成 DNS rebinding / TOCTOU 绕过。

## 2. 根因

同一业务动作被拆为“校验时解析”与“执行前解析”两个独立 DNS 读取，安全判定没有随数据携带到执行层。代码注释虽声明要消除 TOCTOU，但当前实现重新打开了窗口。问题不在私网允许策略：RFC1918 与 IPv6 ULA 的访问是已确认的部署 DNS 区域功能，禁止集合仅包含环回、链路本地、保留和组播。

## 3. 推荐方案与完整安全契约

**推荐方案：单次解析、同源校验、原样 pin。**在**一次 `cron_do()` 调用**内，将 URL 语法/主机/allow-host 检查与 DNS 解析合并为一个内部结果；域名仅查询一次，结果不可再被 DNS 读取替换。该结果逐一经过地址分类；任一回答属于硬禁止集合即拒绝整个请求。仅当全部回答合格时，按确定顺序选择一个 IP，并将该 IP 原样传给 `make_pinned_session()`。任务新增/编辑时的表单校验可在其独立请求中解析 DNS；它不是执行期授权结果，不能被执行期复用或替代。

**硬禁止集合（执行期不可绕过）：**IPv4/IPv6 环回、链路本地、保留、组播、未指定地址（`0.0.0.0`、`::`），以及 IPv4-mapped IPv6 归一化后命中上述集合的地址。DNS 失败、空回答或不合法回答同样拒绝。若 A/AAAA 回答混合了可用地址和硬禁止地址，仍拒绝整个请求；不得“挑一个看似安全的地址”继续执行。

**兼容开关的精确定义：**`url_ssrf_observe_only` 可保留用于配置录入期观测/审计，但**不得**使执行期的硬禁止地址或 DNS 失败放行；执行期必须记录 `ssrf.check=blocked`，且不得创建 HTTP session。`block_private_ip=0` 也不得关闭上述硬禁止基线；该名称与“RFC1918/ULA 允许”的既有契约存在歧义，应在本批次的 README/配置说明中标为兼容开关并说明它不降低硬禁止集合。若未来确有完全关闭 SSRF 防护的需求，必须另行设计、显式风险确认并以 API/审计能力约束，不能隐含在该开关中。

**允许区域：**RFC1918 与 IPv6 ULA 本身不是硬禁止对象；其可达性仍由部署网络、DNS 和既有 RBAC 决定。`validate_and_resolve_url()` 不再先调用会执行 DNS 查询的 `validate_trigger_url()` 后再次解析，而是消费唯一解析结果。`cron_do()` 只接受非空且已验证的 `resolved_ip` 创建 pinned session。

**专业性：**该方案把“授权判定的对象”和“实际连接的对象”绑定为同一个不可变结果，消除同一次执行中 check/use 之间的 DNS 状态变化，符合 SSRF 防护的 TOCTOU 最小化原则。它维持公开返回形状与调用点，不引入 DNS 缓存、CIDR 配置、RBAC 或新依赖，因而是最小且可回归验证的修复。

## 4. 备选方案与取舍

| 方案 | 评价 | 结论 |
| --- | --- | --- |
| 第二次解析后重复过滤 | 可阻断已知禁止地址，但仍保留两次 DNS 读取与难以审计的“哪次才是授权来源”；DNS 答案变化会造成不必要的结果漂移。 | 不推荐。 |
| 仅复用首次解析结果 | 最小化 TOCTOU；让校验和连接共享同一 IP。需要重构内部辅助函数，避免公开 API 语义被破坏。 | **推荐。** |
| 完全禁止私网/ULA | 能缩小攻击面，但违反已确认的企业内网服务访问功能，且会破坏内部 DNS 用户。 | 拒绝。 |
| 新增应用侧 CIDR/hostname 白名单 | 可以形成更严格的多租户策略，但改变现有部署 DNS 信任模型，涉及配置、权限、审计和运维迁移。 | 不属于本 P0 最小修复；另行设计。 |

## 5. 范围

**包含：**`app/services/url_security.py` 的单次 DNS 解析/验证结果流；`tests/test_p0_phase_a.py` 的序列 DNS 与允许区域回归；README 和索引的网络区域说明同步。

**不包含：**不改变 RFC1918/ULA 可达性；不新增 CIDR 白名单；不改任务 URL 数据、RBAC、请求签名、重定向策略、数据库 schema 或前端页面。

## 6. 分批实施

1. **A：解析结果收口。**抽取内部“校验并解析一次”的辅助路径；域名每次执行只查询一次，IP 字面量不查询 DNS。地址分类须包含未指定地址和 IPv4-mapped IPv6 归一化；任一硬禁止回答均拒绝。退出条件：公开函数返回形状不变，执行层仅拿到已验证 IP。
2. **B：执行期硬拒绝。**将 `url_ssrf_observe_only` 与 `block_private_ip=0` 限定为不能绕过执行期硬禁止基线；被拦截时不得构造 `requests.Session`，必须写 `ssrf.check=blocked` 和 JobLog。
3. **C：安全矩阵测试。**以 mock 顺序返回和执行链 spy 覆盖“公网→环回/链路本地/保留/组播/未指定地址”，断言 resolver 调用恰一次、第二个返回值不可影响连接、`make_pinned_session()` 接收首次已验证 IP，且阻断路径的 GET/POST 均为零次。同时覆盖混合 A/AAAA、IPv4-mapped IPv6、RFC1918、ULA、内部 DNS、DNS 失败及开关不可绕过硬拒绝。
4. **D：文档同步与回归。**将 README/示例配置调整为“允许私网/ULA；危险地址硬拒绝；兼容开关不关闭硬拒绝；`url_allow_hosts` 是可选主机限制”。运行完整安全与调度回归，并更新审查/复盘状态。

## 7. 验收

- `.venv-py311/bin/python -m unittest tests.test_p0_phase_a tests.test_cron_execution_transport -v`：DNS 序列测试必须断言单次执行中 resolver 调用**恰一次**；`make_pinned_session()` 的 IP 必须等于该次通过校验的 IP，绝不能使用第二个 DNS 返回值。
- 对 `127.0.0.1`、`169.254.169.254`、`0.0.0.0`、`::`、组播、保留地址和 IPv4-mapped IPv6 分别断言：任务失败、`ssrf.check=blocked`、HTTP GET/POST 调用次数为零；即使 `url_ssrf_observe_only=1` 或 `block_private_ip=0` 亦然。
- 混合 A/AAAA 回答中包含任一硬禁止地址必须失败；只有全部合格时才按确定顺序 pin。私网字面量、内部 DNS 的 RFC1918、IPv6 ULA 用例仍通过，证明业务功能没有被误回滚。
- DNS 失败、空回答和无效回答均 fail-closed，且不存在普通 `requests` 回退路径。
- `.venv-py311/bin/ruff check app/`、`git diff --check`、`.venv-py311/bin/python scripts/html_docs_to_markdown.py --check`、`.venv-py311/bin/python scripts/check_doc_completeness.py --check` 通过。
- 重启本地服务后，以具备 `cron:write` 的测试账号走“立即执行”：正常内部目标成功；危险 DNS 夹具被拒绝且未出现 HTTP 发送事件。

## 8. 风险与回滚

单次解析的主要风险是 DNS 在极短时间内发生合法轮换时仍使用首次地址；这正是 pinning 的安全目的，且请求生命周期通常远短于 DNS 运维切换窗口。兼容风险在于历史部署可能将 `url_ssrf_observe_only=1` 或 `block_private_ip=0` 当作完全放行；v2 明确不再允许其绕过硬禁止集合，属于必要的安全收紧，须在 RELEASE\_NOTES 标明。若出现兼容问题，应修复 DNS/服务发现或在未来独立设计受控重试，不能恢复二次未经验证解析或重新引入隐式放行。回滚仅限本修复批次，不得改变私网/ULA 允许契约。

**实施结果：**已按 A→D 实施。定向安全/传输测试覆盖单次解析、首次 pinning、硬拒绝与零 HTTP session；完整测试、Ruff 与文档同步结果见复盘。真实浏览器验收仍受当前宿主环境端口监听限制，须在可监听环境复验。
