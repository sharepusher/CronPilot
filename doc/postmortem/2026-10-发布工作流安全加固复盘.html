发布工作流安全加固复盘

日期：2026-10-27 · 范围：Security Review S1–S4 · 结果：代码、脚本、CI 和测试已完成；远端 GitHub workflow 尚未在本地伪造为已运行。

1. Bug 定位

发布 job 原先在 .github/workflows/release-asset.yml 同时持有 contents: write、checkout 持久化凭据并执行 tagged commit 代码；tag 输入、Release Notes fallback 和上传后资产内容也缺少强绑定。S4 初版又将 manifest 内的 source_commit 要求为自身所在 tag commit，造成发布门禁自引用。

2. 根因

构建与发布处于同一信任域，版本号被当作普通字符串流入发布路径，发布说明状态依赖自然语言，上传验证只确认名称而没有回读内容与来源 commit。S4 的根因是混淆“tag 前可评审的状态声明”和“tag 后才确定的 Git 对象身份”：把后者写入前者会改变 commit 自身。

3. 测试漏洞

既有测试覆盖发布包和说明结构，但没有覆盖恶意 tag、tag 模式禁止 [Unreleased] fallback、checkout token 隔离、远端资产回读或 structured readiness；也没有创建新提交/新 tag 来验证 manifest 位于被校验源码树时的行为。

4. 修复

  • S1：构建/发布拆 job，构建只读，checkout 不持久化凭据，Actions 固定 SHA，发布 job 使用受保护环境。
  • S2：严格 numeric SemVer、显式 tag 检查、tag 模式禁止 fallback。
  • S3：上传后回读并比较归档、checksum、build report，验证 SHA 和 source_commit。
  • S4：manifest 严格只保存版本、readiness、空 blockers；来源 commit 只由构建后生成的 build report 记录并在解除 draft 前校验，移除自引用。

5. 防护测试

tests.test_release_asset 与 tests.test_version_consistency 共 16 项通过，其中包含遗留 manifest source_commit、非 object JSON 的拒绝用例和入库 manifest 无该字段的契约；临时 Git 仓库的新提交/新 v4.1.2 tag 读取 manifest 并通过状态检查；历史 v4.1.1 tag 270 文件重建和发布包校验通过；Ruff、版本、文档完整性与链接门禁通过。

6. 同类排查

检查了 tag workflow、版本一致性脚本、Release Notes 提取器、发布包构建/校验脚本及现有发布资产测试。所有 source_commit 使用点均归入 build report 的来源证明，不再出现在版本化 manifest。远端 GitHub environment、tag protection 和实际 Release 状态仍需在真实 workflow 中核验。

7. 预防方案

在 scripts/check_version_consistency.py 为 manifest 固化精确 allow-list schema，并在 tests/test_version_consistency.py 拒绝遗留自引用字段；在 tests/test_release_asset.py 断言只有远端 build report 承担 source_commit == GITHUB_SHA。每次变更发布身份契约时，使用临时 Git 仓库创建新提交和新 tag 运行状态门禁，禁止只对当前工作树或历史 tag 做静态检查。可复现命令：.venv-py311/bin/python -m unittest tests.test_release_asset tests.test_version_consistency -v。
