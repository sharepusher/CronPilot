# 统一错误处理 P0 设计契约修订复盘

日期：2026-09-21 · 范围：[统一错误处理 P0 实施计划](../design/统一错误处理P0实施计划-2026-09.html) 的设计修订；未改动应用实现。

## 1. Bug 定位

原设计第 10.2 节同时规定首期 API 采用 400/403/409/5xx，第 12.3 节又规定首期保留历史 HTTP 200 + `errcode` 语义；第 3 节将 commit 后的 scheduler 失败笼统写成“补偿/回滚”。此外，入口清单以手工枚举替代可验证覆盖，页面对比只有文字表。

## 2. 根因

设计把“最终目标的 REST 语义”与“首期兼容迁移”写在同一层，没有指定优先级；把数据库事务 rollback 的概念错误外推到已提交 DB 与 scheduler 的跨资源副作用；审阅范围以公共 JSON helper 为中心，而非以实际路由、异常处理器和副作用调用点为中心。

## 3. 测试漏洞

原验收矩阵没有要求同一端点同时断言旧 HTTP 状态与新字段，未注入“commit 成功后 scheduler 失败”及“scheduler 成功后同步标记写入失败”，也没有由扫描器验证 POST 写入口完整性。因此即使公共 helper 测试全绿，仍可能发生 API 语义漂移、假 rollback 或漏改入口。

## 4. 修复

设计 rev.3 明确首期为加法兼容：保留现有端点 HTTP 行为和旧字段，将状态码迁移拆为单独的 API Breaking Change；定义 `UNKNOWN/PENDING/READY/SYNC_FAILED` 最终一致性状态机、执行器门禁与幂等对账；加入 APIFlask、CSRF、鉴权、HTML handler 的入口表；以可审阅的 Before/After 页面线框替代文字表，并为每批增加冻结基线、先写失败测试、验证、停止条件与发布降级顺序。

## 5. 防护测试

后续 P0-A/P0-D 必须实现并运行：兼容 HTTP + JSON 信封契约测试、trace 输入与 Header 测试、敏感值输出 sink 脱敏测试、scheduler 双失败序列与 PENDING/FAILED 执行器门禁测试，以及 AST 路由扫描覆盖门禁。每项对应设计第 6、7 节的退出条件。

## 6. 同类排查

同类风险存在于所有“兼容期新增字段 + 未来语义迁移”的设计：不得把两个阶段的响应语义混写；所有跨 DB/队列/scheduler 的设计必须把补偿描述为新的持久化动作，不得称已提交状态可 rollback。实现前还须核对 APIFlask error processor、Blueprint handler 和装饰器等非 helper 入口。

## 7. 预防方案

在 `doc/design/统一错误处理P0实施计划-2026-09.html` 第 2、4、6、7 节固化可验证门禁：首期兼容决议、跨资源状态机、AST 入口清单、双失败序列、每批停止条件与发布降级顺序。第三方可通过 `rg -n -e '首期只增加字段' -e 'PENDING' -e 'AST 路由扫描' -e '停止条件' doc/design/统一错误处理P0实施计划-2026-09.html` 复核设计存在性；实现阶段通过设计指定的路由扫描和集成测试验证行为，避免再依赖人工记忆。
