## 1. 文档说明

**目的：**为开发、运维、集成方提供 CronPilot 的结构性视图，说明模块边界、运行时拓扑、数据流向及扩展点。

**读者：**后端工程师、SRE、架构师、需对接回调的业务研发。

**范围：**应用层（`app/`）、数据层（`datas/`）、配置与容器化部署；不包含业务回调服务内部实现。

| 术语 | 含义 |
| --- | --- |
| 调度 Job | APScheduler 中 id 为 `cron_{cron_infos.id}` 的持久化任务 |
| 回调 | 触发时对 `req_url` 发起的 HTTP GET |
| 双库 | `cron_db_url`（JobStore）与 `cron_job_log_db_url`（业务 ORM） |
| 体验版 | `is_dev=1`，禁用秒级字段 |

## 2. 架构目标与约束

### 2.1 设计目标

| 目标 | 架构手段 | 源码体现 |
| --- | --- | --- |
| Crontab 语义兼容 | 字段级 Cron + APScheduler cron trigger | `views.py` 校验 + `scheduler.add_job` |
| 可视化运维 | SSR Web + Session 鉴权 | `main/views.py`、templates |
| 自动化集成 | REST API + access\_token | `api/views.py` |
| 水平扩展 | Redis 任务互斥 + 文件锁拉取 Job | `single_task`、`CuBackgroundScheduler` |
| 故障可感知 | 关键词检测 + 三通道推送 | `crons.cron_do`、`send_text` |
| 低部署成本 | Docker + Supervisor + 默认 SQLite | Dockerfile、docker-compose |

### 2.2 约束条件

- 回调仅支持 **GET**，超时固定 **120s**（`requests.get(..., timeout=120)`）
- 集群模式要求 MySQL JobStore + Redis，SQLite 仅适合单机
- 每 Gunicorn worker 独立启动完整 Scheduler（非集中式 Master）
- Web 鉴权为单密码 Session，无 RBAC

```
                                         │
              ┌──────────────────────────┼──────────────────────────┐
              │                          │                          │
```

系统在生态中的角色是 **调度编排中枢（Orchestrator）**：不执行业务逻辑，只负责按时间表触发 HTTP 调用并审计结果。

## 4. 容器架构（Level 2）

```
┌──────────────────────────────── Docker Host / 物理机 ────────────────────────────────┐
│  Supervisor (nodaemon)                                                                │
│    └── docker_start.sh                                                                │
│          ├── flask db migrate / upgrade  (首次初始化 migrations)                      │
│          └── gunicorn -c docker_gun.py manage:app                                     │
│                ├── Worker 1 (gevent) ──► Flask App + APScheduler Instance             │
│                ├── Worker 2 ...                                                       │
│                └── Worker N (docker: 4, gun.py本地: 2)                                │
│                                                                                       │
│  每个 Worker 进程内：                                                                  │
│  ┌─────────────────────────────────────────────────────────────────────────────────┐ │
│  │  WSGI Layer: Flask Application (create_app)                                      │ │
│  │    ├── Blueprint: main  (/, Web UI)                                              │ │
│  │    ├── Blueprint: api   (/api, JSON API)                                         │ │
│  │    ├── SQLAlchemy ORM  → cron_job_log_db                                         │ │
│  │    └── Flask-APScheduler → CuBackgroundScheduler                                 │ │
│  │              ├── SQLAlchemyJobStore → cron_db (apscheduler_jobs)               │ │
│  │              ├── ThreadPoolExecutor (max_workers=30)                             │ │
│  │              └── portalocker(scheduler.lock) 进程间互斥拉取 due jobs             │ │
│  └─────────────────────────────────────────────────────────────────────────────────┘ │
│                                                                                       │
│  文件系统：datas/logs/{info,error,server}.log  |  scheduler.lock  |  caches/         │
└───────────────────────────────────────────────────────────────────────────────────────┘
```

### 4.1 运行时双进程模型说明

**重要：**Gunicorn 多 worker 意味着同一主机存在 **N 个 APScheduler 实例**。它们通过 `scheduler.lock`（portalocker 非阻塞排他锁）保证**同一时刻仅一个进程**执行 `_process_jobs()` 拉取到期任务；任务执行函数 `cron_do` 在集群模式下再由 Redis `@single_task` 保证跨节点互斥。

### 5.2 Web 管理端调用链（与 APScheduler 的关系）

**结论：**管理页面（任务添加/编辑、执行时间、启停、删除等）**不会**由浏览器直接调用 APScheduler 或 Flask-APScheduler 接口。前端仅通过 HTML 表单 / Ajax 请求 Flask 的 `main` 蓝图路由；服务端在 `cron_service` 或 `main/views.py` 内完成校验、写 `cron_infos`，再调用 `scheduler.add_job` / `pause_job` / `resume_job` / `remove_job`。

```
┌─────────────── 浏览器（jQuery + common.js）────────────────────────────┐
│  cron_add.html / cron_edit.html  →  js-ajax-form  →  POST Flask 路由    │
│  cron_list.html  →  js-ajax-dialog-btn / js-ajax-delete  →  GET 路由     │
│  ❌ 无 apscheduler SDK；❌ 不请求 /api/cron（管理 UI 走 main，不走 api）   │
└───────────────────────────────┬────────────────────────────────────────┘
                                ▼
┌─────────────── Flask 表现层（app/main/views.py）────────────────────────┐
│  /cron_add  /cron_edit  /update_status  /cron_del  /cron_list  …         │
└───────────────────────────────┬────────────────────────────────────────┘
                                ▼
┌─────────────── 服务层（app/services/）──────────────────────────────────┐
│  cron_validator.validate_cron_form  — Web/API 共用校验（执行时间字段等）   │
│  cron_service.add_cron_web / edit_cron_web / create_cron / update_cron   │
│       → INSERT/UPDATE cron_infos  → register_cron_job()                  │
└───────────────────────────────┬────────────────────────────────────────┘
                                ▼
┌─────────────── 调度层（进程内 Flask-APScheduler，非 HTTP）────────────────┐
│  scheduler.add_job('cron_{id}', cron_do, trigger=date|cron, …)           │
│  scheduler.pause_job / resume_job / remove_job                           │
│  持久化 → apscheduler_jobs（SQLAlchemyJobStore）                          │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 管理页操作对照表

| 管理页操作 | 前端请求 | Flask 路由 | 服务/逻辑 | APScheduler（服务端） |
| --- | --- | --- | --- | --- |
| 添加任务（含执行时间） | `POST` 表单 Ajax | `/cron_add` | `add_cron_web` → `create_cron` | `add_job` |
| 编辑任务 / 改时间 | `POST` 表单 Ajax | `/cron_edit` | `edit_cron_web` → `update_cron` | `add_job(replace_existing)` |
| 启动 / 暂停 | `GET` Ajax 对话框 | `/update_status` | `main/views.py` | `resume_job` / `pause_job` |
| 下线（生命周期终点） | `GET` / `POST` | `/cron_retire` | 写 `status=-1`；保留行与日志 | `remove_job` |
| 任务列表 / 执行记录 | `GET` 页面 | `/cron_list`、`/job_log_*` | ORM 分页查询 | 无（只读 DB） |

**无删除：**禁止人工删除任务与执行流水。暂停 ≠ 下线。权威设计见 [任务生命周期与无删除](任务生命周期与无删除设计.html)。

**操作审计（现状）：**管理写操作**不落库操作记录**（P1 规划见 [OPT-P1-09](产品优化需求-借鉴Plombery.html#opt-p1-09)）。审计 action 用 `retire_cron`，不用 `delete_cron`。

外部系统集成走 **REST API**（`/api/cron`、`/api/cron/status`），同样经 `cron_service` 写库后由服务端注册调度，**亦非**直连 APScheduler。详见 [技术方案与前端设计](技术方案与前端设计.html) 第 6 节 API 规范。

### 6.4 管理操作审计（P1 规划 · OPT-P1-09）

**现状：**无 `operation_log` 表；添加/编辑/启停/删除仅改 `cron_infos` 与 APScheduler，不写审计行。执行侧仅有 `job_log`（回调 HTTP 结果）与可选 `job_log_items`（业务 `add_log` 进度）。

| 记录类型 | 表 | 记录什么 | 现状 |
| --- | --- | --- | --- |
| 任务执行 | `job_log` | 到点 GET 回调的响应、耗时、UUID | ✅ 已有，管理端「任务执行记录」 |
| 执行进度 | `job_log_items` | 业务 `POST /api/cron/add_log` | ✅ 已有 |
| 配置变更审计 | `operation_log`（规划） | 添加/编辑/删任务、启停、API 改配置 | ❌ 未实现 |
| 服务端异常 | `datas/logs/error.log` | 未捕获异常栈 | ✅ 有，非结构化、非按任务检索 |

#### 表结构草案（`cron_job_log_db`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER PK | 自增 |
| `create_time` | VARCHAR(25) | 与 `job_log` 一致，本地时间字符串 |
| `action` | VARCHAR(32) | `create_cron` `update_cron` `delete_cron` `toggle_status` `batch_delete_cron` `delete_job_log` … |
| `channel` | VARCHAR(8) | `web` | `api` | `system` |
| **操作人（预留多用户 / RBAC，P1 建列、P2 接账号体系）** | | |
| `operator_type` | VARCHAR(16) | `user` | `api_client` | `system` | `legacy_admin`（单密码过渡期） |
| `operator_id` | VARCHAR(64) | 稳定主体 ID：未来 `users.id`；API 为 client/token 哈希；legacy 为 session 哈希；system 为空 |
| `operator_name` | VARCHAR(120) | 展示名快照：用户名、邮箱、`API集成`、`系统`、`管理员`（删用户后仍可读） |
| `operator_roles_json` | TEXT | 操作时角色快照 JSON 数组，如 `["admin"]`、`["operator","viewer"]` |
| `operator_permissions_json` | TEXT | 操作时权限码快照，如 `["cron:read","cron:write","cron:retire"]`；全权限可 `["*"]` |
| **请求与目标** | | |
| `client_ip` | VARCHAR(45) | 可选，取自 `X-Forwarded-For` / `remote_addr` |
| `target_type` | VARCHAR(16) | `cron` | `job_log` |
| `target_id` | INTEGER | `cron_infos.id` 或 `job_log.id`；删除后仍可凭 `task_name` 检索 |
| `task_name` | VARCHAR(120) | 冗余，便于删任务后查询 |
| `detail_json` | TEXT | 变更摘要 JSON，如 `{"hour":{"old":"9","new":"10"}}` |
| `result` | VARCHAR(8) | `ok` | `fail` |
| `error_msg` | VARCHAR(255) | 失败时简短原因 |

#### 写入点（服务层统一）

```
app/services/operation_log_service.record_operation(...)
  ↑ 由 cron_service / main/views / api/views 在 commit 成功后调用
  覆盖：create_cron · update_cron · delete · toggle_status · API upsert/status
```

#### 管理页「操作记录」

- 路由：`GET /operation_log_list`（需 `@login_required`）
- 筛选：任务名、`action`、**操作人**、**角色**、时间范围、`channel`
- 列表列：时间、操作、**操作人**、**角色**、任务名、渠道、结果、详情（展开 `detail_json` / 权限快照）
- 导航：与「任务执行记录」并列，勿与 `job_log` 混为一页
- 保留：配置项 `operation_log_counts`，超限按 id 删最旧（同 `job_log_counts`）

### 6.2 存储分离策略

| 数据源 | 配置项 | 内容 | 访问方式 |
| --- | --- | --- | --- |
| 调度库 | cron\_db\_url | apscheduler\_jobs、下次触发时间 | APScheduler SQLAlchemyJobStore |

### 6.5 管理操作审计详细设计（OPT-P1-09）

#### 6.5.1 设计目标与边界

| 要记录 | 不记录 |
| --- | --- |
| 任务配置的增删改、启停（Web + API） | 到点 HTTP 回调执行（已有 `job_log`） |
| 操作时间、渠道、结果、字段级 diff | 登录成功/失败（首批可不做，避免噪音） |
| **操作人**、**角色与权限快照**（操作时态） | 只读查询（列表、看执行记录） |
| 删任务后的历史（靠冗余 `task_name`） | — |

#### 6.5.2 时序：写入时机

```
Browser/API     views/cron_service      DB                 operation_log_service
     │                  │                   │                         │
     │──写任务请求──────►│──validate────────►│                         │
     │                  │──INSERT/UPDATE───►│ cron_infos              │
     │                  │──scheduler.*──────►│ apscheduler_jobs        │
     │                  │──commit──────────►│                         │
     │                  │──record_operation─┼────────────────────────►│ INSERT
     │◄──响应───────────│                   │                         │
     │                  │  ※ 审计失败仅打 error.log，不回滚业务事务      │
```

#### 6.5.4 detail\_json 约定

| action | detail\_json 示例 |
| --- | --- |
| `create_cron` | `{"task_name":"daily","hour":"9","minute":"0","req_url":"https://..."}` |
| `update_cron` | `{"hour":{"old":"9","new":"10"},"req_url":{"old":"...","new":"..."}}` |
| `toggle_status` | `{"status":{"old":0,"new":1}}` |
| `delete_cron` | `{"snapshot":{"task_name":"...","hour":"9",...}}` 删除前最后一屏配置 |
| `batch_delete_cron` | `{"ids":[1,2,3],"task_names":["a","b","c"]}` |

#### 6.5.5 操作人、角色与权限快照

**原则：**审计行保存**操作当时**的主体与授权态，不存 live 外键到当前用户表（用户删改角色后历史仍可读）。P2 接入 `users` / RBAC 后，`operator_id` 对齐用户主键即可。

| 来源 | channel | operator\_type | operator\_id / name | roles / permissions（快照） |
| --- | --- | --- | --- | --- |

### 6.6 P2 多用户与 RBAC（OPT-P2-10 · v4）

权威文档：[RBAC架构设计方案 v4](RBAC架构设计方案.html)（设计稿 · 待确认实施）。

#### 6.6.1 设计目标

| 目标 | 说明 |
| --- | --- |
| 多用户 | 单表 `rbac_users`（username + role）；复用 `hash_password` |
| RBAC | 三角色；`@require_permission` 替换 `@login_required`（仅装饰器，函数体不动） |
| 可审计 | `rbac_audit_logs` 记 RBAC 事件；P1 `operation_log` 记业务变更，共用 Session `user_id`/`role` |
| 可回退 | `rbac_enable=0`（默认）与现网逐字节一致 |

#### 6.6.2 数据模型

| 表 | 要点 |
| --- | --- |
| `rbac_users` | `username` UNIQUE · `password_hash` · `role`（viewer/operator/admin）· `is_active` |
| `rbac_audit_logs` | `user_id` · `action` · `resource` · `status` allow/deny |
| `operation_log` | P1 业务审计（见 §6.5）；RBAC 启用后 `operator_*` 来自 Session |

#### 6.6.3 三角色权限

| role | permissions |
| --- | --- |
| `viewer` | `cron:read` `log:read` |
| `operator` | viewer + `cron:write` |
| `admin` | operator + `cron:retire` `user:manage` `audit:read` |

策略常量：`app/rbac/policy.py` → `ROLE_PERMISSIONS`。

#### 6.6.4 Session 与鉴权

```
rbac_enable=0（默认）
  check_pass → session[is_login]=True
  require_permission → 仅校验 is_login（等同旧 login_required）

rbac_enable=1
  check_pass → is_login + role (+ user_id/username)
  require_permission → has_permission(role, perm) 或 403/redirect
  API /api/* → access_token 不变（独立轨道）
```

#### 6.6.5 模块与路由

| 路径 | 职责 |
| --- | --- |
| `app/rbac/policy.py` | `ROLE_PERMISSIONS`、`has_permission` |
| `app/rbac/decorators.py` | `require_permission` |
| `app/rbac/services.py` | 用户 CRUD、`write_audit_log`、`get_rbac_enabled` |
| `app/rbac/views.py` | `/rbac/users`、`/rbac/audit-logs` |
| `app/main/views.py` | 替换装饰器（见 RBAC 文档 §3.4） |

#### 6.6.6 迁移

1. `flask --app manage:app db migrate` / `db upgrade`（Flask-Migrate；**Tier 0** 退役 Flask-Script，见 [依赖升级 RFC](依赖升级RFC.html)）。
2. 种子：可选将 `login_pwd` 导入为首条 `admin` 用户。
3. `conf.ini` 设 `rbac_enable=1` 并重启。

#### 6.6.7 验收标准

- `rbac_enable=0`：P0 单测全绿，行为与现网一致。
- `viewer` 不可写任务；`operator` 不可删任务。
- `admin` 可管理 `/rbac/users`。
- API `access_token` 未破坏。

### 8.1 两层互斥的设计 rationale

| 层级 | 机制 | 解决的问题 |
| --- | --- | --- |
| L1 进程间 | portalocker + scheduler.lock | 同机多 Gunicorn worker 重复 poll due jobs |
| L2 节点间 | Redis SET NX EX + @single\_task | 多机同时执行同一 cron\_do |

局限：非强一致 Leader 选举；Redis 锁 TTL 120s 内进程崩溃可能导致短暂空窗或重复（取决于崩溃时机）。生产环境建议监控 Redis 与调度延迟。

## 15. RBAC 与安全子系统架构（OPT-P2-10 · v4）

完整方案见 **[RBAC 详细设计 v4](RBAC架构设计方案.html)** · 实施见 **[RBAC 落地路线](RBAC落地路线.html)**。v1.1 中间件/JWT/四角色**已废弃**。数据模型摘要见 [§6.6](#rbac-detail)。

**v4 核心：**Flask `@require_permission` + `app/rbac/` Blueprint；`app_context_processor` 注入 `has_perm`；`/rbac/login` 渐进多用户；`make_has_perm` 防 N+1；三角色；`rbac_enable=0|1`；API `access_token` 独立不变。

### 15.1 子系统定位

| 职责 | 不负责 |
| --- | --- |
| Web Session 登录后按角色拦截管理端路由 | 改造 `/api/*` 的 `access_token` 契约 |
| `rbac_users` 多账号、`/rbac/users` 管理 | 企业 SSO（远期 OAuth 另项） |
| `rbac_audit_logs` 记 RBAC 事件与拒绝 | 替代 P1 `operation_log` 业务审计 |

### 15.2 逻辑架构

```

                      │
main/views ──► @require_permission(perm) ──► policy.has_permission(role, perm)
                      │ deny ──► rbac_audit_logs + redirect/web_api_return
                      ▼ ok
                 原 handler（函数体不变）

app/rbac/ Blueprint ──► /rbac/users, /rbac/audit-logs

api/views ──► access_token（不变，与 Web RBAC 分离）
```

### 15.3 模块规划

| 模块 | 职责 |

### 15.8 与 operation\_log 集成

P1 `operation_log` 记录 cron 业务变更；RBAC 启用后从 Session 取 `user_id`、`username`、`role` 写入 `operator_*`。RBAC 自身事件写 `rbac_audit_logs`。

### 15.9 依赖升级排期（与 RBAC）

RBAC **不依赖** Flask 2 / gevent 升级。权威路线：[依赖升级 RFC](依赖升级RFC.html) — Tier 0 `flask db` → Tier 1 SA 1.4 渐进 → Tier 2 gevent → Tier 3/4 代际；RBAC 在 Tier 0 后可与 Tier 1 并行。

### 15.10 ADR-06（修订）

| 决策 | 理由 |
| --- | --- |
| 应用内三角色 + 单表用户 | 轻量、贴合 Flask 装饰器习惯、最小 diff |
| 装饰器而非全局中间件 | 与现有 `@login_required` 模式一致；可逐路由迁移 |
| API token 与 Web RBAC 分离 | 不破坏外部 `access_token` 集成 |

## 12. 架构决策记录（ADR）

| ID | 决策 | 理由 | 代价 |
| --- | --- | --- | --- |
| ADR-01 | 选用 APScheduler 而非 Celery Beat | 轻量、内嵌 Flask、Crontab 语义直接 | 多 worker 需自研锁 |
| ADR-02 | HTTP GET 回调而非 Agent 拉取 | 集成简单，防火墙友好 | 无请求体、幂等需业务保证 |

| ADR-06 | 应用内 RBAC + 审计权限快照 | 轻量部署、与 operation\_log 契合 | 大企业需 SSO；见 [§15](#rbac-arch) |

```
CronPilot                          Plombery
────────────────────────────────────────────────────────────
表现  Jinja2 + jQuery (SSR)              React 19 SPA + TanStack Query
接口  Flask main (HTML) + api (JSON)     FastAPI REST /api + Socket.IO /ws
领域  CronInfos + cron_do(HTTP)          Pipeline/Task/Trigger + executor.run
调度  CuBackgroundScheduler + ThreadPool  AsyncIOScheduler + async run()
数据  cron_infos / job_log (DB)          pipeline_runs (DB) + .data/runs/ (FS)
横切  conf.ini / 企微钉钉 / Redis锁       Settings yaml / Apprise / contextvars
```

### 13.3 前后端交互架构

| 维度 | CronPilot | Plombery |
| --- | --- | --- |
| 交互模式 | 多页 SSR；表单 POST → JSON `{errcode,errmsg,url}`（`js-ajax-form`） | SPA；REST JSON + HTTP 状态码；422 字段级错误 |
| 任务配置 UI | Web 动态 CRUD `cron_infos` | 代码 `register_pipeline`；UI 仅展示与手动 Run |
| 运行观测 UI | 日志表 + iframe 明细；无 Run 状态机页面 | RunsList + WS `run-update`；LogViewer + WS `logs.{id}` |
| 认证流 | 单密码 Session | OAuth2 Session（可关闭） |

### 13.4 调度与执行架构

| 项 | CronPilot | Plombery |
| --- | --- | --- |
| Job 函数 | `cron_do` → HTTP 客户端 | `run` → 循环 `_execute_task` |
| 拓扑 | 1 Job : 1 URL | 1 Trigger : 1 Pipeline : N Task（线性） |
| 成功语义 | 响应体 + error\_keyword；无 COMPLETED 状态 | Task 异常 → PipelineRun FAILED |
| coalesce | false | true |
| 多副本 | 文件锁 + Redis 锁（设计支持集群） | 文档禁止多 worker；无内置分布式锁 |

### 13.5 数据架构对照

| 数据 | CronPilot | Plombery |
| --- | --- | --- |
| 定义持久化 | DB 表（可 API 改） | 代码内存注册 |
| 运行记录 | `job_log`（回调响应 TEXT） | `pipeline_runs` + `tasks_run[]` |
| 大对象 | 塞进 content 字段 | 文件系统 `task.json`、`logs.jsonl` |
| 双存储 | JobStore DB + 业务 DB | SQLite 元数据 + .data 产物 |

### 13.6 部署拓扑对照

#### CronPilot

- Supervisor → Gunicorn gevent (N workers)
- 集群：共享 MySQL JobStore + Redis
- 无需 WebSocket 代理

#### Plombery

- Nginx TLS + Uvicorn workers=1
- 必须代理 `/ws` WebSocket
- 单卷：db + .data

### 13.7 ADR 级对照（为何选型不同）

| 决策点 | CronPilot 选择 | Plombery 选择 |
| --- | --- | --- |
| 执行位置 | ADR-02 HTTP 回调 | 进程内 Python（Library-first） |
| UI 技术 | ADR-04 SSR 简化部署 | SPA 内嵌包（单进程交付） |
| 扩展方式 | DB/API 动态任务 | 代码注册 Pipeline |
| 水平扩展 | ADR-05 双锁 | 单实例；扩展靠外置调度或未来 Redis 锁 |
| 可观测 | 日志表 + 关键词告警 | 双存储 + WS 实时 + Apprise 状态告警 |

### 13.8 架构层选型建议

| 架构诉求 | 更合适 |
| --- | --- |
| 异构微服务统一 Cron 入口、调度与业务解耦 | CronPilot |
| Python 数据管道、要强 Run 状态机与实时日志 | Plombery |
| 既要统一调度台又要 Python 多步管道 | CronPilot 触发 → Plombery `POST /api/pipelines/{id}/run` |

## 14. 可借鉴的架构优化方向

完整论证见 [产品优化需求（详版 PRD）](产品优化需求-借鉴Plombery.html)；
对比文档 [§17](Plombery深度对比分析.html#s17) 含差距总览与路线图。此处仅列架构层要点。

### 14.1 守正：必须保留

- HTTP GET 回调 + 跨语言；Web/API 动态 `cron_infos`
- 双锁集群、秒级 Cron、签名与 add\_log

### 14.2 出奇：优先借鉴（不改变执行模型）

| 领域 | 借鉴 Plombery | 架构落点 |
| --- | --- | --- |
| 可观测 | Run 状态机 + 结构化日志 | `job_log.status`、SSE、`/metrics` |
| 契约 | REST + OpenAPI + 422 | 统一 envelope、校验服务层 |
| 存储 | DB 元数据 + 文件大对象 | 超大响应落盘 |
| 安全 | OAuth 可选 | SSRF 白名单 + 密码哈希（P0） |
| 工程 | pytest + 新 Python | SQL 参数化、CI |

### 14.3 不借鉴

进程内 Pipeline、代码唯一任务定义、强制单 worker、全量 React 重写 —— 均会削弱 CronPilot 现有定位。
