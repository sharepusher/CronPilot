1. 问题与证据

P1：最终包 07dddb3 的 app/templates/redesign/_exec_logs_pagination.html 被改写。源码 Jinja parse 通过；包内 parse 报 TemplateSyntaxError：Encountered unknown tag 'endif'，期待 endfor。execution_logs.html 在 page_data.items 非空时 include 该模板，所以有记录的执行日志页及复用该模板的 AJAX 会失败；不是只在超过一页时发生。空库黄金路径没有进入此分支。

失败附件已隔离到 /private/tmp/cronpilot-v420-blocked-07dddb3，不应上传。既有 check_release_asset.py 仍退出 0，说明当前独立资产检查未覆盖 Jinja 可解析性/运行时字节完整性。

2. 根因

已读 scripts/build_release_asset.py:21–26、114–147、180–200：rewrite_links 仅按 .html/.md/.htm 扩展名挑选，运行时 app/templates/*.html 也进入文档重写。HTML_LINK_RE 在双引号 href 内遇到 keywords.get('task_name') 的单引号提前截断；query-only URL 的空 path 又被 resolved_repo_target 解释为模板父目录，public_url 将其换成 GitHub tree 链接，删除原 Jinja if 前缀却保留 endif，导致语法损坏。发布包与源码测试输入不是同一个制品。

3. 方案

  1. 给文档链接重写增加明确路径边界：只处理根级发布 Markdown 和 doc/ 下已选的文档；app/、frontend/、scripts/ 等运行时文件原字节保留，不凭后缀判定文档身份。根级文档和 doc/ 仓库外链接重写继续保留。
  2. 对 query-only/空 path 的文档链接返回无需重写；其语义是当前文档查询，不是父目录链接。保留外链、锚点及合法文档路径的现有行为。
  3. 为 tests/test_release_asset.py 增加真实 Jinja 分页模板及包含引号、查询参数的夹具，构建后断言 app 文件字节与 Git blob 相同；对实际包模板做 Jinja parse/render，并断言 href 保持 ?page=... 与筛选参数。保留确定性和文档链接重写原回归。
