## 原评审结论（针对修订前基线）

专业性：架构方向合理，版本、范围与分批意识已建立，但仍偏原则性方案。准确性：核心 Request ID 和 ContextVar 方向正确，存在响应字段事实错误、证据强度夸大与状态机失败分支缺口。完整性：拆分未实现语义等价迁移，关键 P0 问题失去明确归属，不能认定为完整可执行规格。结构与链接门禁通过仅能证明文档形式完整，不能证明设计正确。

优先级标识：下文“高”表示阻断相关实现，“中”表示需在设计冻结前修正；不与产品功能 P0/P1 编号混用。C-0、B-0 中已明确声明的调研事项属于正常待决策项，不将其单纯计为错误。

## R1 高：失败仍成功的原始 P0 问题失去独立归属

证据：总览历史 §1.1 和 §6 原先覆盖用户编辑失败；app/rbac/views.py:749–805 中 update\_user/set\_user\_groups 后，资料 commit 异常仅记录日志与 rollback，最终仍把此前 result['ok'] 交给 \_users\_form\_response。新 P0-C 只明确任务调度切片，P1-A2 只适配信封，均未明确承接该缺陷。统一输出对象不会自动修复错误成功判定。

建议：为普通数据库写入失败闭环保留明确 P0 工作项，定义用户编辑切片、部分提交语义、响应与审计结果。验收：注入资料 commit 失败，JSON 和原生 form 均不得返回成功，并如实断言此前操作是否已经持久化。

## R2 高：唯一权威子方案丢失原已确定契约

证据：总览 §2.1.1 原有两种协议 400 精确 body、安全 UUID 生成与每次重试新 ID、五个 scheduler 日志上下文字段、唯一约束冲突识别和 JobLog 成功后才记录 cron.start。A-lite rev.2 只保留 code、泛化 reset 和“trace 唯一冲突测试”，同时总览 §1–12 被降为历史。子方案不存在等价的完整规格，实施人员仍必须依赖已失去权威的旧章节。

建议：逐条迁移确认过的约束，建立“旧条款→子方案条款→验收用例”映射；若改变条款，标为决策变更。验收：只阅读子方案即可确定精确响应、ID 分配和所有上下文恢复行为。补充人工同步执行与跨线程执行的传播边界。

## R3 高：JSON 兼容基线存在可直接验证的事实错误

证据：P1-A2 §8 将 url 写为“可选”，将 data 条件描述为“非空”。datas/utils/json.py:13–23 无条件构造 url（缺参为 null），data 的判断是 is not None，因此空字符串、空列表、0、False 都会被输出。api\_return 也不能与 json\_response 的 HTTP status 参数机制混为一谈。

建议：修正为 url 始终存在、data 仅 None 时省略；为每个出口列出字段存在性、类型、空值和默认/调用点状态。验收至少覆盖 None、空字符串、空列表、0、False，不能只测普通成功和异常。

## R4 高：A2/B 的关联号与表单适用范围未闭合

证据：A2 §3 已列 trace\_id 为 v1 字段，§8 却把名称、取值和缺失语义留待冻结；入口流程要求“已验证 request\_id”。A-lite 又豁免双模式 POST，A2 排除原生分支，而 B 明确包括普通 form 并展示 trace。各自合理的局部边界拼接后，没有解释这些豁免分支的关联号从何而来。

建议：明确 required JSON 的 body 关联号是否等于 Header request\_id；为双模式 JSON、普通 form、协议 400 和网络无响应分别规定字段省略/展示策略。普通 form 回显可独立于信封实现。不得未经确认自动生成替代 request\_id。

## R5 高：C 的失败状态写回仍假定数据库可写

证据：C §2 将所有 failure 简化为 DB commit(SYNC\_FAILED)。当第一次 commit 未完成、提交结果不确定或数据库持续不可用时，该路径不成立；scheduler 已应用但 READY 写回失败时，也未必能记录 SYNC\_FAILED。此为文档状态转换缺口，不是对调度库 API 的假设。

建议：区分期望尚未持久化、PENDING 已持久化、scheduler 已应用但确认失败、旧 generation 过期。SYNC\_FAILED 写入为有条件尽力操作，失败时不得伪称落库；对账须能从持久化 PENDING/UNKNOWN 和实际调度状态恢复。C-0 冻结时明确 generation 的原子获取和对账并发所有权。验收覆盖两次写库连续失败与提交结果不确定。

## R6 中：安全台账未覆盖自身声明范围，生产泄漏表述证据不足

证据：S §2/§5 声明 HTTP JSON/HTML、审计等全部出口，§7 初始台账仅列应用日志、JobLog/operation detail、通知，缺 HTTP 与独立审计项。源码存在 str(e)/traceback 直接输出能证明泄漏风险路径，不能单凭静态检查证明“已知生产泄漏”。

建议：区分已发现风险路径、样本复现、生产事件三个证据级别；补齐每个 sink 的生产点/接收者/策略/用例。未知接收者和保留期可作为 S-1 明确交付物；脱敏只声明对已定义字段与测试样本的保证，不能宣称任意文本绝无秘密。fail-closed 告警路径也须避免再次格式化原异常。

## R7 中：B 示意图与规则矛盾，超时后的重试语义缺失

证据：B §2 同屏展示字段错误与全局错误，正文却要求两者互斥；§3 统一“关闭/重试”且把超时、断网归入失败，但响应未收到不能证明写入未发生。A-lite 明确 request\_id 不是幂等键。

建议：分开字段校验失败、已确认业务失败、提交结果未知三种示例；未知结果提示先核实状态，禁止默认自动重试写操作。B-0 已声明必须补真实页面，是正确门禁，但当前示意图不能算页面设计验收通过。

## R8 中：前置契约矩阵与可执行验收缺失

证据：五份子方案均从顶部版本表直接进入问题章节；.cursor/rules/cronpilot-documentation.mdc 要求相关设计在正文前提供交付契约矩阵。已有分类表/sink 表不含全部规定维度。各子方案目前主要写“测试通过”，没有具体测试文件/命令或登记完成后的产物位置。

建议：各子方案提供适用维度矩阵，不适用项明确说明；将现有可运行验证与拟新增测试分开，给出用例 ID、触发输入、期望响应/副作用、产物与退出条件。不得将未编写测试列为已通过。

## R9 中：文档修订采用追加方式，旧结论仍在正文竞争

证据：总览保留“P0-A-lite 的唯一准绳”“整体 P0 关闭”等历史规范措辞，五份子方案追加 rev.2 补充而未完整整合；A2/B 正文仍出现 P0-A2/P0-B。保留旧文件路径本身合理，并不等同于优先级错误，但正文与索引应该统一。

建议：将历史内容折叠为明确非规范附录，现行条款在正文单处定义；P1 名称同步所有现行引用；总览重新定义当前 P0 关闭集合，避免把 P1 信封/UI 混入。文件旧路径可继续兼容，无需强制重命名。

- P1-A2：拆分方向合理；先纠正事实基线，再冻结字段和适用范围。
- P0-S：优先处理实际风险合理；当前属于安全治理方案，台账尚未冻结。
- P1-B：P1 定级合理；只可进入 B-0 页面级设计，不可直接实施 UI。
- P0-C：标为 C-0 待详设是诚实边界；先完成失败状态机，再冻结迁移与并发机制。

建议按 R1/R2 恢复范围和契约，R3/R4 修正接口，R5 完善状态机，R6/R7 补齐安全和交互，最后 R8/R9 整体验收。无需推翻全部方案，也不能以增加“待确认”字样替代解决已知矛盾。

## 核验方法与限制

已直接阅读六份文档及 json helper、请求 hook、用户编辑、任务执行、日志上下文、Redis 锁与项目规范相关源码。本轮为静态设计评审，未触发写业务数据、未运行故障注入、未验证生产部署；有关并发恢复是设计推导，不宣称运行时已验证。

ContextVar Token 由 set 返回并由 reset 恢复之前值、同一 Token 不可重复 reset，与 [Python 官方文档](https://docs.python.org/3/library/contextvars.html)一致。项目 Python 3.8–3.11 应继续使用 try/finally，不能采用 3.14 新增的 Token 上下文管理器语法。
