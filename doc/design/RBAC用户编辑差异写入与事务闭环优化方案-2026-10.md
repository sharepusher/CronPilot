## 1. 执行结论

推荐把“无变更不写库”与“失败不得误报成功”作为同一个垂直切片实施，但分成可独立验证的批次。最终状态不是依赖 ORM 自动少发几条 SQL，而是由服务端显式决定：先校验并规范化全部输入，再计算字段级 change set；change set 为空时零业务写入，有变化时只应用差异，并把本端点涉及的用户、用户组、安全字段和成功审计收口到一个事务。

该方案同时降低两类风险：一是减少无意义的事务、审计写入、Token 轮换和缓存失效；二是消除当前“前序阶段已经提交，资料阶段失败后仍返回成功”的错误反馈。减少写入只能降低故障概率，单事务和准确失败传播才负责保证最终语义。

## 2. 当前事实与证据

| 位置 | 当前行为 | 风险 |
| --- | --- | --- |
| `app/rbac/views.py::users_edit` | 依次调用 `update_user()`、`set_user_groups()`，最后直接赋值资料字段并再次提交。 | 一次请求形成多个提交边界。 |
| `app/rbac/services.py::update_user` | 角色/状态赋值后无条件提交；成功后再写审计并失效缓存。 | 同值可能不生成用户表 UPDATE，但仍进入提交、审计写入和缓存失效。 |
| `app/rbac/services.py::set_user_groups` | 关系行已按集合差异增删，只有集合变化才轮换 Token；但无变化时仍提交、写审计并失效缓存。 | 已有局部差异化，但没有端到端 no-op。 |
| `app/rbac/views.py` 资料提交异常分支 | 只记录日志并 rollback，没有把此前的成功 `result` 改为失败。 | Ajax 可能得到 `errcode=0`，普通 POST 可能按成功路径跳转。 |
| `app/rbac/services.py::write_audit_log` | 审计函数自行提交，并吞掉审计异常。 | 业务提交与成功审计不是同一原子边界；无变化也会尝试写审计。 |
| `app/static/js/common-redesign.js` | `errcode=0` 显示成功 Toast 并按 `url` 跳转。 | 后端误判会被前端忠实放大为“保存成功”。 |

**ORM 边界：**SQLAlchemy 通常不会为同值标量赋值生成实际 UPDATE，但应用仍会执行 `commit()`；而当前成功审计会产生真实 INSERT。因此“数据库可能没有更新用户行”不能证明“本次请求没有写库”。

## 3. 问题与根因

### 3.1 用户可见问题

- 资料提交失败后仍可能显示“保存成功”并跳转，页面反馈与数据库事实不一致。
- 用户未修改任何信息时仍被告知“保存成功”，审计中也可能出现没有状态变化的更新记录。
- 用户只修改一个资料字段时，角色和用户组阶段仍被调用，扩大故障面。

### 3.2 工程根因

- 路由承担跨服务编排，但每个服务自行提交，缺少请求级 Unit of Work。
- 没有服务端规范化快照和 change set，是否变化被隐式交给 ORM 或各阶段自行判断。
- 资料提交异常只做 rollback，没有更新最终 outcome。
- 审计写入既不与业务同事务，也不能表达 no-op、部分完成和未知结果。
- 现有测试覆盖正常编辑和安全拒绝，但没有断言无变更零写入、提交失败不得成功、审计与缓存副作用次数。

## 4. 目标、范围与非范围

### 4.1 目标

1. 所有字段在首次业务写入前完成校验和规范化。
2. 服务端生成可测试的字段级 change set；无变化时零业务写入。
3. 有变化时只修改必要字段和关系行，不触发无关副作用。
4. `/rbac/users/edit` 的核心业务状态和成功审计使用一个事务、一次提交。
5. 只有提交结果确认成功才返回成功；异常与未知结果均禁止成功跳转。
6. 保留现有 RBAC、Scope、CSRF、停用策略、Token 安全语义及响应兼容形状。

### 4.2 修改范围

- `app/rbac/views.py`：将编辑路由收口为取参、鉴权上下文、调用事务服务和适配响应。
- `app/rbac/services.py`：增加用户编辑输入规范化、change set、非提交内部原语和单事务编排；保留现有公开函数对其他调用方的既有契约。
- `app/templates/redesign/user_form.html`：仅在确有必要时补充 no-op/未知结果的页面级提示挂点，不改变字段布局。
- `tests/test_user_edit_write_failure.py`：新增垂直失败与差异写入测试；复用内存数据库，禁止导入 `manage`。

### 4.3 明确不做

- 不改所有 RBAC 写入口，不把本方案扩大为全站事务框架。
- 不改变外部 API、不提前实施 P1 JSON 错误信封或 Request ID 协议。
- 不新增数据库字段，不在本批引入乐观锁版本列。
- 不改变邮箱清空规则、停用不可恢复策略、业务组权限模型或 Token 生命周期策略。
- 不把“没有业务变化”记录成 `user:update`；如未来有合规要求记录 no-op 尝试，须另定义独立审计动作。

## 5. 输入规范化与 change set 契约

change set 必须在服务端、同一份数据库当前状态上计算。比较前先把输入转换为稳定的领域值，避免空值、类型和顺序制造伪变化。

| 字段 | 规范化 | 相等判定 | 副作用 |
| --- | --- | --- | --- |
| role | 沿用现有合法角色校验。 | 规范化字符串相等。 | 真实变化时重新评估最后一名管理员保护；可能影响 Scope 缓存。 |
| is\_active | 只接受可解释为 0/1 的现有表单值。 | 整数状态相等。 | 仅 1→0 时递增 `auth_version`、清除 Token；同值不得重复执行。 |
| group\_ids | 验证 `__ALL__` 与具体组互斥；具体 ID 转整数、去重、忽略顺序，并确认均存在。 | 规范化后的语义集合相等；全局选择按现有“无绑定行”持久化语义比较。 | 仅集合变化时增删差异关系、按现有策略轮换 Token并失效 Scope 缓存。 |
| email | trim；本方案保留空输入沿用原值的当前语义。 | 规范化结果与持久化值比较。 | 仅资料字段变化；审计不记录原始邮箱值。 |
| nickname | trim；空值规范化为 `None`。 | 将持久化空值统一后比较。 | 仅资料字段变化。 |
| job\_title | 复用既有选项；`other` 必须有自定义值并遵守长度约束。 | 规范化编码相等。 | 仅资料字段变化。 |

内部结果至少表达四种状态：`CHANGED`、`NO_CHANGE`、`FAILED`、`COMMIT_UNKNOWN`。这些是服务内部语义，不要求本批改变公共 JSON Envelope。

| 状态 | 数据库事实 | 对外结果 | 允许跳转 |
| --- | --- | --- | --- |
| CHANGED | 单次提交确认成功。 | 保存成功。 | 是。 |
| NO\_CHANGE | 未执行业务提交、业务审计或缓存失效。 | 未检测到变更，无需保存。 | Ajax 保持兼容成功语义；是否回列表沿用当前表单成功路径。 |
| FAILED | 校验失败或提交前确定失败，未提交业务变化。 | 明确字段错误或“保存失败，请修正后重试”。 | 否。 |
| COMMIT\_UNKNOWN | 提交期间连接级异常，应用无法证明数据库最终选择。 | 保存结果无法确认，请刷新核实当前信息。 | 否；不得自动重试。 |

## 6. 推荐架构与事务边界

### 6.1 路由只负责请求编排

POST /rbac/users/edit
→ 权限 / Scope / CSRF / 禁止自编辑
→ 解析请求值
→ 调用“用户编辑事务服务”
→ 在事务上下文读取当前用户与用户组
→ 校验、规范化、计算 change set
→ change set 为空：直接 NO\_CHANGE
→ 应用必要字段和关系差异
→ 将成功审计加入同一 Session
→ 单次 commit
→ commit 成功后按 change set 失效必要缓存
→ 现有 \_users\_form\_response 适配 Ajax / 原生 POST

### 6.2 复用规则而不复用提交

不建议让新事务服务继续调用当前会自行提交的 `update_user()` 和 `set_user_groups()`。实施时应把其中的校验和状态变更提取为“不提交”的内部原语，现有公开函数仍以薄包装方式提交，以保持其他调用方行为；新编辑事务服务直接组合内部原语并拥有唯一提交权。内部原语名称属于实现细节，确认后以最小 diff 落地。

### 6.3 审计、Token 与缓存

- **成功审计：**只记录发生变化的字段名、目标用户 ID、操作人和结果；不记录密码、Token、邮箱、花名或岗位的原始值。审计对象与业务变更同 Session、同一次提交。
- **no-op：**不写 `user:update`。HTTP 访问日志仍可证明请求发生，但不能冒充业务状态变更。
- **Token：**只在现有安全策略要求的真实状态转换时处理；同组、同状态提交不得轮换或清除 Token。
- **缓存：**只在角色、状态或组发生变化且提交成功后失效；资料字段单独变化不失效 Scope 缓存。缓存失效失败不回滚已经提交的数据库事务，但必须记录基础设施错误。

### 6.4 并发语义

本批不新增版本字段，继续保留当前“后提交者覆盖前值”的并发模型。为了避免用路由早先读取的陈旧对象作 no-op 判断，事务服务必须以事务内重新取得的持久化状态构建 before 快照。若后续出现真实并发覆盖需求，再独立设计乐观锁；本批不得宣称已解决所有并发编辑。

## 9. 验收矩阵

| 场景 | 数据库断言 | 响应与页面断言 | 副作用断言 |
| --- | --- | --- | --- |
| 所有字段无变化 | 用户行和关系行不变；零业务提交。 | `errcode=0`，文案为“未检测到变更，无需保存”；不得显示“已更新”。 | 无业务审计、无 Token 变化、无缓存失效。 |
| 仅修改 nickname | 只改变 nickname；一次提交。 | 保存成功。 | 一条事实审计；不轮换 Token、不失效 Scope 缓存。 |
| 仅修改用户组 | 只增删关系差异；一次提交。 | 保存成功。 | 按现有策略轮换 Token；一次缓存失效；审计只标记 groups。 |
| 用户组仅顺序或重复不同 | 规范化集合相等，零业务提交。 | NO\_CHANGE。 | 无关系重建、无 Token 变化。 |
| 停用启用用户 | 状态 1→0，与 auth\_version/Token 安全变化在同一提交。 | 保存成功；种子 admin、自停用、最后管理员保护仍拒绝。 | 提交后缓存失效；审计不含 Token。 |
| 岗位或组校验失败 | 任何字段均不写入。 | 字段错误；Ajax/原生均不成功跳转。 | 无成功审计、无缓存失效。 |
| 提交前确定失败 | 整体回滚，无持久化变化。 | 失败且停留在表单。 | 日志脱敏；不得写成功审计。 |
| 提交期间连接级异常 | 应用不伪造最终状态。 | COMMIT\_UNKNOWN；不跳转、不自动重试，提示刷新核实。 | 不得补写可能与事实冲突的成功审计。 |
| 缓存失效失败 | 数据库已成功提交。 | 业务结果保持成功；不得假装回滚。 | 记录基础设施错误，后续请求通过缓存 TTL/既有机制恢复；实现前确认当前缓存机制。 |

## 11. 风险、降级与回滚

| 风险 | 控制措施 | 回滚注意 |
| --- | --- | --- |
| 提取内部原语时改变其他调用方语义 | 公开 `update_user()`/`set_user_groups()` 契约测试保持；新事务编排只服务本端点。 | 可回滚新编排并恢复原路由，但不得恢复误报成功；至少保留错误传播热修。 |
| no-op 判断错误，漏掉真实变化 | 字段级规范化矩阵、单字段参数化测试、数据库最终值断言。 | 临时禁用 no-op 短路可恢复保守写入，但失败闭环必须保留。 |
| 全局选择与空关系语义混淆 | 按现有 `__ALL__` 校验和“无绑定行”持久化语义做专门测试；不引入新 Scope 模型。 | 发现歧义即停止 U1，不迁移数据。 |
| 成功审计同事务导致审计表故障阻断编辑 | 这是安全敏感写入的预期 fail-closed；测试审计失败整体回滚并返回通用错误。 | 不得通过吞掉审计异常恢复可用性；需独立评审降级策略。 |
| 连接中断后的重复提交 | COMMIT\_UNKNOWN 禁止自动重试，提示刷新核实；不把 Request ID 当幂等键。 | 代码回滚不能撤销已经可能提交的数据，必须先核实状态。 |
| 页面提示回归 | 保持现有字段布局、Ajax 表单和防重复提交；浏览器覆盖正常、no-op、失败三态。 | 可单独回滚提示层，但后端不得重新返回假成功。 |

## 12. 备选方案与取舍

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 只在资料 commit 异常时把 `result.ok` 改为 false | 改动最小，立即消除最明显误报。 | 仍有多次提交、无变化写审计、部分完成和无关副作用。 | 可作为紧急热修下限，不能作为本优化的完成态。 |
| 仅依赖 SQLAlchemy 脏检查 | 无需新增比较代码。 | 不能跳过 commit、审计 INSERT、缓存失效；不能表达字段级 change set。 | 拒绝。 |
| 由前端只发送变化字段 | 请求体更小。 | 可绕过、状态可能过期、不能作为安全或一致性依据。 | 可作未来体验优化，服务端仍必须独立判断。 |
| 服务端 change set，但保留三个 commit | 减少无关阶段，改动中等。 | 多字段编辑仍可能部分完成。 | 作为 U1 过渡，不是最终关闭条件。 |
| 服务端 change set + 单事务 + 同事务成功审计 | 无变化零写入；有变化一次提交；反馈与事实最一致。 | 需要提取非提交内部原语并加强测试。 | **推荐完成态。** |

## 13. 完成定义与确认项

只有同时满足以下条件，才能把本方案标记为已实施：

- no-op 场景经测试证明零业务提交、零成功审计、零 Token 变化、零缓存失效；
- 真实变化只触发必要字段和副作用，并由单次业务提交完成；
- 已知失败和提交未知均不显示成功、不跳转、不自动重试；
- 既有 RBAC、Scope、CSRF、停用与最后管理员保护无回退；
- 自动化、路由冒烟和真实浏览器正反向路径全部通过；
- 完成修复复盘、HTML/Markdown 同步、索引登记和可验证本地环境交付。
