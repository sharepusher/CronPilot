## 3. 待评估问题（7 项）

### 3.1 B-13：`/api/auth/token` 无暴力破解限制

**位置**：`app/api/views.py:67-106`

**现状**：Web 登录通过 `app/rbac/login_limiter.py` 的 `check_login_limit()` + `record_login_failure()` 实现 IP+用户名级锁定（5 次失败后锁 15 分钟）。`/api/auth/token` 端点无此限制。

**准确性评估**：准确。代码中确认无任何调用 `check_login_limit` 或等效逻辑。

**必要性：建议修复（P1）**。CronPilot 作为内部工具，API 端点通常在内网。但如果暴露到公网（如通过 Nginx 代理），此端点可被用于凭据爆破。修复成本极低（复用现有 limiter，约 5 行代码），风险收益比高。

### 3.2 B-14：`updated_from/to` 字符串与 BIGINT 比较

**位置**：`app/api/views.py:186-188`

```
    if updated_from:
        filters.append(CronInfos.updated_at >= updated_from)    # updated_from 是字符串
    if updated_to:
        filters.append(CronInfos.updated_at <= updated_to)      # updated_at 是 BigInteger
```

**准确性评估**：准确但影响有限。`CronInfos.updated_at` 确实是 `BigInteger`（百毫秒纪元值）。SQLite 的弱类型系统会隐式转换，通常能工作。但语义不正确——用户传入 `"2026-08-28 10:00:00"` 会被当作字符串与整数比较。

**必要性：降为 P2，非紧急**。该参数在实际调用中使用频率低，且 SQLite 的隐式转换使大多数场景能工作。正确修复是用 `str_to_hms()` 解析后比较，加上输入格式校验。可在下一次 API 接口优化时顺手处理。

### 3.3 B-15：API 创建任务无 scope/group 参数，所有新任务为 GLOBAL

**位置**：`app/api/views.py:539-559`；`app/services/cron_service.py:146-167`

**现状**：`CronUpsertIn` schema 无 `scope_type` 和 `group_id` 字段。`upsert_cron_by_task_name()` 创建新任务时不设置 scope，默认为 GLOBAL。Web UI 的 `cron_add` 视图通过 `_apply_scope_from_form()` 强制分配组。

**准确性评估**：准确。确认 API 创建路径不经过 scope 分配逻辑。

**必要性：建议修复（P1），但需设计讨论**。这是一个功能缺失而非 bug——API 设计初期未考虑 scope 概念（RBAC v4 后才引入）。修复涉及 schema 扩展、默认值策略（用户所在组 vs 必填参数）、向后兼容。建议作为独立 OPT 条目规划，而非紧急修复。

### 3.4 B-16：`tag_suggest` 接受任意 `group_id` 无 scope 校验

**位置**：`app/main/views.py:1086-1093`

```
@main.route('/api/tags/suggest')
@require_permission('cron:read')
def tag_suggest():
    prefix = (request.args.get('q') or '').strip()
    raw_gid = request.args.get('group_id', '').strip()
    group_id = int(raw_gid) if raw_gid and raw_gid.isdigit() else None
    tags = suggest_tags(prefix=prefix, limit=20, group_id=group_id)
    return jsonify(tags)
```

**准确性评估**：准确但低风险。用户可通过传入非自身组的 `group_id` 获取该组的标签名称列表。标签名称是低敏感数据（通常是技术分类标签）。

**必要性：降为 P2**。标签名称不是敏感信息，泄露不会造成业务损失。但从权限完整性角度，加一行 scope 校验是好习惯。可顺手修复。

### 3.5 Q-1：API Token 支持 query string 传递（日志/Referer 泄露）

**位置**：`app/api/__init__.py:49`

```
    return request.values.get('access_token', '')
```

**准确性评估**：准确。`_extract_bearer_token()` 先检查 `Authorization: Bearer` header，若无则回退到 query string `access_token` 参数。

**必要性：降为 P2，长期废弃**。Query string token 会出现在：① 服务端 access log ② 浏览器历史记录 ③ HTTP Referer header。CronPilot 的 API 通常由自动化脚本调用（非浏览器），且为内部工具，实际泄露风险有限。建议在 RELEASE\_NOTES 中标注 deprecated，未来大版本移除。

### 3.6 Q-2：LIKE 查询未转义 `%` / `_` 通配符

**位置**：`app/api/views.py:154`；`app/main/views.py:214,747` 等

```
    filters.append(CronInfos.task_name.like('%%%s%%' % keyword))
```

**准确性评估**：准确但非安全问题。这**不是 SQL 注入**（SQLAlchemy 参数化处理）。但用户输入 `%` 或 `_` 会匹配超出预期的结果。

**必要性：P2，低优先级**。功能行为上用户搜索 `%` 会返回所有任务，这是一个 UX 问题而非安全问题。在内部工具中用户不太可能故意利用这点。可在 API 接口优化时统一添加 `escape_like()` 工具函数。

### 3.7 鉴权降级：`api_access_token` 未配置时全放行

**位置**：`app/api/__init__.py:76-78, 97-99`

```
    if not api_access_token and not token:
        request._api_scope = {'role': 'admin'}    # 无 token 配置且无请求 token → admin
        return None
    ...
    if not api_access_token:
        request._api_scope = {'role': 'admin'}    # 无 token 配置但有不匹配的 token → admin
        return None
```

**准确性评估**：准确，已知设计决策。这是向后兼容行为，在 R1 附录 D 中已深入分析。

**必要性：无需修复**。这是有意的向后兼容设计（代码注释第 60 行明确说明）。管理员可通过设置 `api_access_token_required=1` 或配置 `api_access_token` 启用严格鉴权。默认行为适合内部开发/测试场景。如果将来 CronPilot 支持公网部署，可改为默认拒绝。
