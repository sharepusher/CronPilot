1. 问题与根因

已确认 commit 返回后，SQLAlchemy 默认过期 ORM 属性；save_status 对原 task 再调用 status_config 生成 context 摘要，可能在隐式 SELECT 时异常，而该语句位于 try 边界之外。隔离复现显示 DB 已是运行、异常逃逸、调度调用 0 且 context 为空。该证据是服务级故障注入，不证明全部生产异常路径。

2. 已读实现与决策

  • cron_status_apply.py：提交前已有六个调度字段快照、目标、revision 与 task name；提交后 context 构造再次访问 task。status_config 使用这六字段、排序 JSON 与当前 secret 的 HMAC；正常同目标无重试在写前返回。
  • app/main/views.py::update_status：失败且 context 非空时签发 actor 绑定令牌；GET 重试基线使用 status_config。app/api/views.py::cron_status 将同一 context 与调用凭据摘要签名到响应头。
  • cron_edit_apply.py::check_version：通过独立连接核对 DB 当前 revision/status，读取故障转换为 EditWriteError；不得把这个必要的提交后并发核验一并删除或笼统禁止所有 SELECT。

3. 推荐方案

  1. 提取共享的配置摘要计算，使既有 status_config(task) 和保存路径从同一六字段规范计算摘要；保证字段顺序、空值处理、JSON 默认编码、密钥和 HMAC 结果与现有 token 完全一致。调用者、签名 salt、schema 和现有令牌继续兼容。
  2. 保存或明确目标重试前，从已取得的同一调度快照计算摘要，保存为请求内普通字符串；保证此步发生在业务 commit 前且在受控错误边界内。快照、revision 和目标须属于同次决定，禁止 commit 后通过 ORM task 再读取来构造 context。
  3. commit 确定返回后才用上述不可变原始值填充 context，随后沿用 apply_status 的独立版本核验、同步应用及有限观察。commit 抛异常时不填 context、不调用调度或成功日志；无 context 的内部调用保持兼容。若摘要计算或读取在 commit 前失败，回滚并返回既有安全失败，不向调用方暴露异常文本。
  4. 保留 D2 的 no-op、签名令牌、缺失 Job、陈旧版本拒绝及调度不确定处理。业务已提交后不回滚旧状态，不用新值冒充旧快照，也不声称数据库和调度器跨库原子。

备选为仅在提交后增加异常捕获：可避免未处理异常，但已保存状态缺少可靠的重试摘要，仍可能留下状态与调度不一致；因此不作为首选。单纯关闭 expire_on_commit 会改变应用全局会话语义，亦不采用。

4. 范围与边界

实现修改 app/services/cron_status_apply.py、app/main/views.py 的启停路由及对应测试；必要的可复验隔离测试工具、文档和复盘按批次补齐。Web/API 返回结构、模板、静态资源、数据库结构、用户授权规则、成功审计既有 best-effort 语义不变。本设计无前端可见改动，不需页面 Before/After；实际浏览器交互仍须验证。启停读前异常、全量六失败、图片资产、版本归档与 Docker 发布包不由本项自动关闭；如发现须扩大接口或 UI 行为，应先修订本稿并重新确认。

6. 验收矩阵与命令

  • 真提交后拒绝对同一 ORM 对象触发读取，同时允许 check_version 的独立连接读取：摘要不再触发隐式 SELECT；正常应用仍成功且目标和 Job 一致。另单独令独立版本查询失败，断言受控失败、数据库已保存、不冒称调度成功，签名重试上下文绑定正确。
  • 在提交前摘要计算失败：明确无业务提交、无调度及成功日志，安全错误；在 commit 前/后分别注入 commit 异常，断言均不生成重试上下文、不调度，独立连接核对实际状态，不能断言两者必然相同。
  • 实际 Web 与 API 成功/调度异常场景：校验令牌包含正确 actor、task、revision、target、config；旧实现产生的同配置令牌仍有效，改配置/版本、改 actor/target、伪造均拒绝；同目标重试不重复 resume。context=None 也需覆盖。
  • SQLite/MySQL 独立库、真实 JobStore 与 Operator 浏览器确认→失败→重试；明确角色反向、CSRF、令牌泄露与敏感日志检查，覆盖启动与暂停。对防护作负向变异：恢复提交后读取须使测试失败；令牌摘要改变须被兼容性测试发现。

7. 风险与回滚

摘要算法变动可能让旧令牌失效；以逐字段空值、Unicode、定时模式及现有令牌兼容测试阻断。快照与后续变化之间仍存在跨库窗口，现有版本核验只能有限检测，不承诺分布式串行。回滚应一起回退摘要实现和新增调用，保留已有业务数据；不得以恢复旧 DB 状态补偿未知调度。

8. 设计阶段核验

本稿基于当前工作区读取上述源代码与既有 D2 验收；故障注入的已保存状态及异常见原记录。此前全量 1146 项、6 失败、12 跳过，发布图片资产 162 项错误和版本归档问题仍存在。以上为 rev.1 的设计阶段历史；确认后结果见第 9 节。

9. 实施复盘与最终验收

  1. 定位：提交后服务使用过期 task 生成摘要可能触发 SELECT；Web 错误响应中的 actor.id 也可能在提交后触发 SELECT。两处均可能绕过受控响应。修复前实测。
  2. 根因：跨事务边界继续持有 ORM 实体，而提交使属性过期；错误路径缺少在提交前冻结恢复令牌所需普通值。
  3. 测试漏洞：旧用例覆盖调度异常但未禁止提交后 ORM 加载，故未覆盖成功提交、读取失败和重试令牌生成的组合。
  4. 修复：摘要从提交前六字段快照计算并复用；Web 在提交前保存 actor ID；提交阶段异常包括 StaleDataError 保守判为结果待核实。旧摘要格式、令牌字段、权限与响应结构不变。
  5. 防护测试：tests/test_status_postcommit_snapshot.py 覆盖提交后 ORM 加载拒绝、真实 Job 启停、Web/API 错误令牌、旧摘要一致性、摘要失败、提交前及已提交后异常、提交期版本异常和独立版本读取故障。最终相关回归 40 项通过；关键路由 86/86、Ruff 通过。旧探针修复后结果显示提交成功、无过期读取、调度调用一次；旧探针替换了调度调用，不单独证明实际 Job 状态。
  6. 同类排查：Web 路由确有同源 actor 隐式读取并一同处理；API 路由提交后使用已计算的凭据摘要而非 ORM 对象。独立连接版本检查保留；执行态调度与数据库仍非跨库原子。
  7. 预防方案：新增提交后禁止 ORM 列加载的服务、Web 与 API 测试，并覆盖旧摘要兼容和提交结果未知。落点 tests/test_status_postcommit_snapshot.py，执行 .venv-py311/bin/python -m unittest tests.test_status_postcommit_snapshot -v；恢复任一旧的提交后对象读取会触发失败。
