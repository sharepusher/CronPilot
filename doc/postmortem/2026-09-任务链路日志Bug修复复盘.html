日期：2026-09-07  |  触发来源：设计文档专业评审（自查） |  修复文件：app/crons.py、datas/model/job_log.py、tests/test_lifecycle_logging.py

Bug 1 — 内层 except 路径 _actual_url NameError

严重程度：HIGH — 异常处理器本身崩溃，掩盖真实错误，日志丢失

1. Bug 定位

app/crons.py，内层 except Exception as e: 路径（约 line 387）引用了 _actual_url，该变量在 try 块内部的 if req_method == 'GET': ... else: ... 分支中赋值（约 line 288）。若以下任一代码在赋值前抛出异常，_actual_url 为未定义状态：

  • get_cronpilot_sign(parmas, api_key=api_key) 抛出异常
  • URL 参数字典推导式（{d.split('=')[0]: d.split('=')[1] for d in ps}）在 URL 含无 = 参数时抛 IndexError

此时 except 处理器引用 _actual_url 触发 NameError，进而导致外层 except Exception as e: 接管，记录的错误信息是 name '_actual_url' is not defined，而非原始异常内容。

2. 根因

新增 actual_url 追踪字段时，代码在"成功路径"和"异常路径"两个 _save_job_log 调用点均引用了 _actual_url，但仅在 try 块内某分支赋值，未在块外提供初始值。这是一个典型的"变量作用域与控制流不匹配"问题：变量赋值被嵌套在条件语句内，而引用点在异常退出路径上。

3. 测试漏洞

原有测试（test_lifecycle_logging.py）只测试了"任务不存在"路径（cron_do(99999)），此时流程在 DB 查询后提前 return，不会进入内层 try 块，所以 _actual_url 从未被触及。没有任何测试模拟"进入内层 try 后提前异常退出"的场景。

4. 修复

# app/crons.py — 在内层 try: 块前添加 1 行初始化
started_at = utc_now_hms()
_actual_url = None  # 提前初始化：防止 try 内赋值前抛异常时 except 引用未定义变量
try:
    api_key = CRON_CONFIG.get('api_key') or ''

5. 防护测试

tests/test_lifecycle_logging.py::TestActualUrlNameErrorGuard::test_actual_url_initialized_before_try：静态解析 crons.py，断言 _actual_url = None 行号 < 紧随其后的 try: 行号。

6. 同类排查

在 crons.py 的所有其他 except 路径中检查变量引用：started_at（在 url_ok 分支外初始化为 None）、task_name（在 try 外初始化为 None）、resolved_ip（在 SSRF 校验返回，try 外可见）、timeout_sec（在 url_ok 分支内赋值，内层 try 外可见）。仅 _actual_url 有此问题。

7. 预防方案

规范新增（落地位置：AGENTS.md + .cursor/rules/cronpilot-backend.mdc）：

凡在 except 处理器中引用的变量，若其赋值点在 try 块内部（而非块外），必须在 try 之前提供默认值初始化（var = None）。自检命令： 
python3 -c "
import ast, sys
with open('app/crons.py') as f: src = f.read()
tree = ast.parse(src)
# 检查 Try 节点的 handlers 中是否引用了仅在 body 中定义的名称
print('AST parse OK — manual review required for variable scope in try/except')

Bug 2 — actual_url 存储明文 cronpilot_sign（E-1 安全缺陷）

严重程度：MEDIUM — log:read 角色（含 Operator）可读取签名值，可伪造认证请求

1. Bug 定位

app/crons.py line ~288 构建 _actual_url（GET 场景）：

_actual_url = req_url + _sep + _urlencode({'cronpilot_trace_id': trace_id, 'cronpilot_sign': cronpilot_sign})

随后在 _save_job_log(..., actual_url=_actual_url, ...) 中将完整 URL（含明文签名）写入 job_log.actual_url 列。详情页路由 job_log_detail 使用 @require_permission('log:read')，而 Operator 角色拥有 log:read，因此所有 Operator 均可在执行详情页读取 cronpilot_sign。

2. 根因

设计文档安全审查节声明"job_log 表仅管理员可访问"，此描述与实际权限模型（log:read 包含 Operator 角色）不一致。文档作者将"受权限保护"等价于"仅管理员可访问"，未交叉核验 RBAC 矩阵。设计审查时没有测试"以 Operator 角色访问详情页"。

3. 测试漏洞

原有测试不包含"以 Operator 角色访问执行详情页，验证 actual_url 不含签名"的集成测试。签名泄露是只有在有意测试"最小权限用户可见范围"时才能发现的缺陷。

4. 修复

# app/crons.py — 两个 _save_job_log 调用点（HTTP 成功路径 + HTTP 异常路径）
import re
# ...
actual_url=re.sub(r'(cronpilot_sign=)[^&]+', r'\1***', _actual_url) if _actual_url else None,

脱敏结果示例：https://example.com/cb?trace_id=abc&cronpilot_sign=***

日志文件中的 cron.http_sending 事件记录 req_url（原始 URL，无签名），不受影响。

5. 防护测试

tests/test_lifecycle_logging.py::TestActualUrlSignMasking（5 个用例）：

  • test_sign_is_masked_in_get_url：确认签名值不出现在 masked URL 中
  • test_sign_masked_when_not_last_param：签名在中间参数时也被正确脱敏
  • test_none_url_passes_through：None 输入安全处理
  • test_post_url_unchanged：POST URL 无签名，脱敏无副作用
  • test_actual_url_field_masking_logic_matches_crons_py：静态断言 crons.py 中存在相同的 re.sub 模式

6. 同类排查

全仓库搜索其他可能暴露 cronpilot_sign 的位置：

  • cron.http_sending 日志（GAP-3）：记录 req_url（无签名）✅
  • API 响应：job_log_detail 视图直接返回 jl.actual_url（现已脱敏）✅
  • Prometheus metrics：不记录 URL ✅
  • cron.http_ok/http_error 日志：只记录 http_status ✅

7. 预防方案

规范新增（落地位置：.cursor/rules/cronpilot-backend.mdc）：

凡新增含认证凭据（sign/token/key）的字段到数据库模型，必须在设计文档"安全审查"节逐一列出可访问该字段的所有 RBAC 角色（非仅写"受保护"），并明确是否需要脱敏存储。自检命令： 
grep -rn "cronpilot_sign" app/ | grep -v "re.sub\|test_\|#" | grep -v "get_cronpilot_sign\|parmas\|cronpilot_sign'\]\|cronpilot_sign\"\]"
输出不应包含将 cronpilot_sign 值写入持久存储的代码路径。

Bug 3 — JobLog.to_json() 引用不存在的字段

严重程度：LOW（当前无调用方，但任何未来调用者立即触发 AttributeError）

1. Bug 定位

datas/model/job_log.py，to_json() 方法，引用了三个不存在于 JobLog 模型的属性：self.job_id、self.remark、self.traces。

2. 根因

历史遗留：to_json() 方法在模型演进（Phase A ORM 迁移）过程中这些字段被移除，但方法本身未同步更新。新增字段（trigger_source、actual_url 等）同样未加入 to_json()，进一步体现该方法已与模型脱离同步。

3. 测试漏洞

无任何测试调用 JobLog.to_json()，因此 AttributeError 从未被触发。模型字段变更时没有"调用 to_json() 验证无异常"的保护测试。

4. 修复

# datas/model/job_log.py — 删除三个无效字段引用
def to_json(self):
    return {
        'id': self.id,
        'content': self.content,
        'status': self.status,
        'create_time': self.create_time,
    }

5. 防护测试

tests/test_lifecycle_logging.py::TestToJsonNoAttributeError::test_to_json_does_not_raise：实际创建并查询一条 JobLog 记录，调用 to_json() 断言不抛异常，并验证结果不含已删除的字段名。

6. 同类排查

检查同仓库其他模型的 to_json() / to_dict() 方法：

  • datas/model/cron_infos.py：无 to_json() 方法，通过视图层字段访问 ✅
  • datas/model/job_health.py：无 to_json() 方法 ✅

仅 JobLog.to_json() 存在此问题。

7. 预防方案

测试门禁（落地位置：tests/test_lifecycle_logging.py，已加入）：每次模型字段变更后，TestToJsonNoAttributeError 会在内存数据库上实际调用 to_json()，确保字段引用有效。

规范新增（落地位置：.cursor/rules/cronpilot-backend.mdc）：

凡从模型中删除字段，必须搜索 to_json()/to_dict() 等序列化方法并同步移除对应字段。自检命令： 
grep -rn "to_json\|to_dict" datas/model/ app/ --include="*.py"

Bug 4 — 术语改名切断历史日志的「未执行触发」识别（2026-09-11 追加）

严重程度：MEDIUM（不影响新数据，但已入库的历史 job_log 全部丢失分类）

1. Bug 定位

app/services/job_log_display.py::job_log_status_line() 与 app/services/job_log_outcome.py::pre_request_outcome()，两处的前缀判断随术语统一从 '回调URL安全校验未通过' 单向改成 '触发URL安全校验未通过'，未保留旧前缀。

而该文案是 持久化数据：app/crons.py 把它写进 job_log.content 列。改名前入库的所有记录仍是旧文案，改名后：

  • 列表/详情页第一行从「未执行触发」掉成 —（落到兜底分支）
  • pre_request_outcome() 不再返回 ('error', 'blocked_url')，SSRF 拦截记录在失败原因统计里归类错误

2. 根因

术语统一是按「搜索旧词 → 替换成新词」的方式做的，替换动作对「这个字符串是代码内部常量」还是「这个字符串是数据库里的历史值」不做区分。判定函数读的是 DB 里的 content，属于后者，本应是「新增识别分支」而不是「替换识别分支」。行为层原因：改名时没有一步问「这个字符串有没有已入库的副本」，而全仓 grep 的结果里代码常量与数据值长得一模一样，不会自己提示这个差别。

3. 测试漏洞

tests/test_job_log_display.py::test_status_from_error_content 与 tests/test_job_log_outcome.py::test_pre_request_blocked 本应发现它，但两条断言的输入字符串在同一轮里被一起改成了新文案——测试和实现被同一次替换改成互相自洽，因此仍然全绿。测试用的是「当前会产生的文案」，没有任何一条用「历史已入库的文案」作输入。

4. 修复

# app/services/job_log_outcome.py — 新增共享常量，两处判定共用
# 术语统一前写入的历史 job_log 仍存着旧文案，识别须同时兼容两种前缀
BLOCKED_URL_PREFIXES = ('触发URL安全校验未通过', '回调URL安全校验未通过')

def pre_request_outcome(content):
    ...
    if text.startswith(BLOCKED_URL_PREFIXES):
        return STATUS_ERROR, 'blocked_url'

# app/services/job_log_display.py — 从 job_log_outcome 导入同一常量
if text.startswith(BLOCKED_URL_PREFIXES) or text in (...):
    return '未执行触发', 'muted'

写入端（app/crons.py）不动，新数据仍只写新文案；旧前缀只用于识别。

5. 防护测试

  • tests/test_job_log_display.py::test_status_from_legacy_blocked_url_wording：以 '回调URL安全校验未通过: http://127.0.0.1/x' 为输入，断言 ('未执行触发', 'muted')
  • tests/test_job_log_outcome.py::test_pre_request_blocked_legacy_wording：以 '回调URL安全校验未通过: x' 为输入，断言 (STATUS_ERROR, 'blocked_url')

两条用例的输入固定为旧文案，后续任何单向替换都会让它们变红。

6. 同类排查

把术语改名涉及的所有「被判定的字符串」逐个查了写入端与判定端是否隔着数据库：

  • '定时任务不存在' / '请求链接不存在' / '请求链接有误，请检查一下' / '发生严重错误'：本轮术语替换未触及，判定端与写入端文案仍一致 ✅
  • fail_reason 取值（blocked_url / timeout / keyword / internal）：英文常量，术语替换不涉及 ✅
  • trigger_source 取值（schedule / manual）：英文常量 ✅

结论：只有「URL安全校验未通过」这一条中文文案同时是入库值与判定依据，其余判定依据都不是中文持久化文案。

7. 预防方案

规范新增（落地位置：.cursor/rules/cronpilot-backend.mdc「术语/文案变更」节 + AGENTS.md）：

凡修改会被 startswith / == / in 判定的中文文案，必须先确认该文案是否被写入数据库列（job_log.content、operation_log 等）。若是，判定端只能新增旧文案分支，禁止单向替换；且防护测试的输入必须使用旧文案。 
# 自检：判定端出现中文字面量时，反查写入端是否入库
grep -rn "startswith('[^']*[一-龥]" app/services/ app/main/ | cat

验证命令：python -m unittest tests.test_job_log_display tests.test_job_log_outcome -v（15 条，含 2 条旧文案用例）

附：设计决策错误 D-2 — next_run_time 方案不可靠（2026-09-07 追加）

定位：doc/design/任务执行链路可观测性增强方案.html D-2 建议 scheduler.get_job('cron_{id}').next_run_time，但 CuGeventScheduler.py:125-127 显示 next_run_time 在 submit_job() 后立即同步更新为下次时间，函数执行期间已是下一周期值。

根因：设计时未 Read 调度器实现文件，对 APScheduler 的 next_run_time 更新时机做了错误假设。

修复（R1）：D-2 改为 EVENT_JOB_SUBMITTED 监听器方案，捕获 evt.scheduled_run_times[-1]；三字段语义分离。

修复（R2，2026-09-08）：EVENT_JOB_SUBMITTED 方案被发现存在 gevent 竞态：_process_jobs() 中 executor.submit_job() spawn greenlet 后，后续 DB I/O 会触发 gevent yield，任务 greenlet 在 _dispatch_event() 执行前已进入 @single_task，导致 _sched_times 读取为空。改为在 submit_job() 前通过 per-job FIFO 队列（deque）写入计划时间，消除竞态。同时修复：coalesce=False 时多 run_times 仅存最后一个的问题。

预防：设计文档引用具体 Python API 时，必须先 Read 相关实现文件验证假设；在 AGENTS.md 设计先行节追加"API 实现验证"要求。涉及并发/事件监听方案时，必须画出完整时序图并标注 yield 点。
