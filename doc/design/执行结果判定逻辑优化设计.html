执行结果判定逻辑优化设计

日期：2026-08-27   状态：待确认

1. 问题

用户反馈：HTTP 200 的请求在执行记录中被标记为"失败"，详情页"错误"字段显示 keyword，开始/结束时间为空。

  • 误判原因：conf.ini 中 error_keyword=fail,error 对所有任务的响应体做子字符串匹配。绝大多数 JSON API（如 {"error_code": 0, "msg": "success"}）都包含 error 字样，导致 HTTP 200 也被判定为失败。
  • 可读性差：失败原因码（keyword、http_4xx、http_5xx、timeout、connection、internal、blocked_url）直接展示给用户，用户无法理解含义。
  • 不可定制：error_keyword 是全局配置，所有任务共用同一套关键词，无法按任务差异化。

2. 根因

问题根因
HTTP 200 被判失败keyword_matched() 做全文子字符串匹配（any(kw in text for kw in keywords)），不理解 JSON 结构；默认关键词 fail,error 太宽泛
错误显示 "keyword"模板直接输出 jl.fail_reason 原始码，未做人类可读映射
开始/结束时间为空started_at/finished_at 字段是后续版本添加的；早期记录不含这两个字段

3. 方案

3.1 判定链重构（核心改动）

当前判定链（evaluate_http_response）：

HTTP 5xx → fail (http_5xx)
HTTP 4xx → fail (http_4xx)      ← 受 fail_on_http_4xx_5xx 控制
响应体含 error_keyword → fail (keyword)
其他 → success

新判定链：

HTTP 5xx → fail (http_5xx)
HTTP 4xx → fail (http_4xx)      ← 受 fail_on_http_4xx_5xx 控制
响应体关键词匹配 → fail (keyword:实际匹配词)  ← 增强：记录实际匹配到的关键词
其他 → success

关键改进：

  1. 默认值改为空：conf.ini.example 中 error_keyword=（空，不启用）。当前 fail,error 太宽泛，对绝大多数用户造成困扰。
  2. fail_reason 记录实际匹配词：fail_reason 从 'keyword' 改为 'keyword:error'（冒号后为实际匹配到的关键词），方便排查。
  3. 注释增强：conf.ini.example 中加入配置说明和示例。

3.2 UI 可读性改进

新增 fail_reason → 人类可读文案映射（类似 operation_action_label）：

fail_reason 码显示文案
http_4xxHTTP 客户端错误 (4xx)
http_5xxHTTP 服务端错误 (5xx)
keyword（旧格式）响应体关键词匹配
keyword:xxx（新格式）响应体包含关键词「xxx」
timeout请求超时
connection连接失败
internal内部错误
blocked_urlURL 安全拦截

实现方式：新增 Jinja2 filter fail_reason_label，模板中 {{ jl.fail_reason|fail_reason_label }}。

3.3 方案对比（未来可选扩展，本轮不做）

扩展方向描述复杂度
每任务 error_keyword 覆盖在 cron_infos 增加字段，允许单任务自定义关键词高（DB 迁移 + 表单 UI）
JSON 路径匹配支持 $.errcode != 0 等 JSONPath 表达式高（新依赖 + 表达式引擎）
正则匹配error_keyword 支持正则而非纯子串中（安全风险：ReDoS）

本轮聚焦 3.1 + 3.2，投入产出比最高。

4. 范围

不改：

  • 数据库模型 — fail_reason 字段仍为字符串，兼容旧格式
  • 用户现有的 conf.ini — 只改 example 文件的默认值，不主动修改用户配置
  • HTTP 状态码判定逻辑 — 4xx/5xx 判定不变

5. 分批

  1. B1：job_log_outcome.py 改造 + 测试（纯后端，可独立验收）
  2. B2：fail_reason_label filter + 模板更新（UI 层，B1 通过后进行）
  3. B3：conf.ini.example 默认值 + 注释更新

6. 验收

  1. 单元测试：error_keyword=fail,error 时，{"error_code": 0} → fail + fail_reason='keyword:error'
  2. 单元测试：error_keyword=（空）时，{"error_code": 0} → success
  3. 单元测试：error_keyword=FATAL 时，"all ok" → success
  4. 模板验证：执行记录详情页显示"响应体包含关键词「error」"而非裸码 keyword
  5. 兼容性：旧 fail_reason='keyword' 记录仍能正确显示为"响应体关键词匹配"
  6. python scripts/smoke_routes.py --check — 路由冒烟

7. 风险

  • 低：fail_reason 格式从 keyword 变为 keyword:xxx，新旧格式在同一数据库共存，filter 需同时处理两种格式
  • 用户配置：不主动修改用户 conf.ini，但可建议用户将 error_keyword 清空或改为更精确的关键词
  • 向后兼容：已有 fail_reason='keyword' 的历史记录不受影响，filter 向后兼容

附：追踪码文案优化

问题：执行记录详情中 trace_id 字段的中文翻译「追踪码」不够专业，技术用户更习惯直接看 Trace ID。

方案：全局将「追踪码」替换为「Trace ID」。

文件改动
app/templates/redesign/run_inspector.htmllabel "追踪码" → "Trace ID"
app/templates/job_log_all_list.html表头 <th>追踪码</th> → <th>Trace ID</th>
app/templates/job_log_list.html同上
app/templates/job_log_detail.html"追踪码:" → "Trace ID:"
app/api/schemas.pydescription 中 "追踪码" → "Trace ID"
scripts/smoke_routes.py断言字符串同步
tests/test_job_log_detail_integration.py断言字符串同步

不改：数据库字段名 trace_id、Python 变量名、路由参数 — 保持不变。

验收：python scripts/smoke_routes.py --check + 浏览器执行记录详情页确认标签为 "Trace ID"。

8. 用户当前问题的即时建议

在方案实施之前，用户可以直接修改 conf.ini：

# 方式一：清空关键词（仅靠 HTTP 状态码判定）
error_keyword=

# 方式二：使用更精确的关键词（避免误判）
error_keyword=FATAL,Exception,traceback

修改后需重启 CronPilot 生效。
