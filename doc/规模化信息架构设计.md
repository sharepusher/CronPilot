## 一、问题、双维目标与设计原则

#### 维度 A · 任务运营

对象：`cron_infos`。痛点：上百任务扁平平铺、跨 Scope 检索疲劳、启停路径长。解药：Scope 锚点、状态/健康快筛、行内操作。

#### 维度 B · 日志可观测

对象：`job_log`（Run）。痛点：秒级任务几何膨胀淹没低频失败。解药：任务级健康聚合 → 再下钻 Run；全局流失败优先。

| 原则 | 含义 |
| --- | --- |
| Exception First（可调制） | 运维默认放大异常；开发角色并陈「进 L2」与「最近成功」 |
| 隐藏无关、放大异常 | 过滤与聚合优先于加宽表、加翻页 |
| 配置 ≠ 健康 ≠ Run | L2 管配置生命周期；Health 管聚合；L3 管单次执行事实 |
| 预计算健康 | 列表/首页读 `job_health`，禁止每次扫全量日志算连续失败 |
| 风格一门 | 全程 SimpleBoot / 现有 badge·dialog，禁止 L1 单独大屏视觉 |
| Scope 只收窄不放大 | UI 二次过滤永远是 `build_scope_filter_clause` 可见集的子集 |

## 二、已拍板结论（讨论收束）

1. 采纳 **L1/L2/L3 心智**；B0 **同页合体**（L1 指标条挂 `cron_list`），不一次开三个门户。
2. L1 按 `admin` / `operator` / `viewer` **模块权重调制**；不新增 developer 角色。
3. L3 = 现有 `job_log` + 详情 / add\_log；**不新建 Execution 表**；文案逐步改为「执行记录 / 运行实例」。
4. 健康表名 **`job_health`**（勿用 `rbac_*`）；B0 窄字段；失败与状态翻转同步写，连续成功节流。
5. 保留一级「执行记录」Tab；失败优先筛选与 OPT-P1-01c 对齐（可同波或紧随）。
6. L2 Scope：权限与查询参数仍按 Scope UX 矩阵；**B0 列表落地**为两段式工具栏内「业务组」下拉（统一替代侧栏/Pill 占位，见 §5.1 密度收拢），避免信息叠加撑高行高。
7. 首期**不做** Facet Filter、Saved View、独立 `/dashboard`、Redis、完整 health\_score / 24h 比率。
8. 连续失败默认阈值 **N=3**（实现时允许 `conf.ini` 覆盖，默认 3）。

| --- | --- | --- |

### 5.1 列表密度收拢（信息叠加治理）

多租户标签 + 健康信号 + RBAC 提示叠进宽行后会「垂直炸开」。B0 落地约束（不换 Bootstrap 3 / SimpleBoot）：

- **健康圆点静默**：连续失败 ≥N 显示红底 `×N`；未达阈值橙点；最近成功绿点（无「成功」文案）；尚无执行**不渲染**指示（勿写「未跑」）。
- **双行内聚**：任务名加粗一行（悬停可见 `title=ID`）；Scope / 备注 / last\_run / URL 淡灰缩字号共占第二行；**无 ID 列**。
- **两段式工具栏**：左 = 连续失败 / 今日失败 / 全部 / 运行中 / 已暂停 + 业务组下拉 + 搜索；右 = 唯一主行动「+ 新建任务」（需 `cron:write`）。
- **Metric 分轨**：工具栏「连续失败」(`health=failing`) / 「今日失败」(`health=today_fail`)；四格 Metric 条与待处理榜**暂隐**（可恢复）。
- **操作列色义**：有权限 — 运行记录 info / 立即执行 success / 启停·编辑·下线在「更多 ▾」；无下线权 — 灰色项 + `js-retire-denied` 前端拦截提示。
- **操作列平铺**：运行记录 / 启停 / 编辑 / 下线（含 `js-retire-denied`），不折叠进「更多」。
- 表格使用 `table-condensed`；列收为 任务 / 周期 / 状态 / 操作；导航文案为「任务中心」。

## 六、job\_health 数据模型与写路径

### 6.1 表结构（B0）

```
job_health
  cron_info_id          INTEGER PK  -- FK cron_infos.id
  last_run_at           VARCHAR(25) -- 最近一次触发完成时间
  last_run_status       VARCHAR(16) -- success|fail|error|null
  last_run_log_id       VARCHAR(65) -- 可选，便于直达 L3
  last_success_at       VARCHAR(25)
  last_fail_at          VARCHAR(25)
  consecutive_failures  INTEGER NOT NULL DEFAULT 0
  health_status         VARCHAR(16) -- ok|failing|unknown
  updated_at            VARCHAR(25)
```

B2+
`failure_rate_24h` / `avg_duration_ms` / `health_score` 批算或物化；非 B0。

### 6.2 什么是 N？为什么需要 N？（连续失败阈值）

**N** = 判定任务进入「连续失败 / failing」所需的**最近连续失败（或异常）次数**。

每次任务跑完会记一次结果（success / fail / error）。字段 `consecutive_failures` 记录「当前连续失败了几次」：

- 本次失败/异常 → 计数 +1
- 本次成功 → 计数清零

当 `consecutive_failures >= N` 时，将该任务标为 `health_status=failing`，并出现在「连续失败」Metric / 快筛里。

| 例子（N=3） | 连续失败计数 | 是否进入「连续失败」榜 |
| --- | --- | --- |
| 偶发一次网络失败，下次成功 | 1 → 0 | 否（短暂抖动，不打扰） |
| 连续失败 2 次后又成功 | 2 → 0 | 否 |
| 连续失败 3 次仍未恢复 | 3 | **是**（需要人处理） |

**为什么不设 N=1：**秒级/分钟级任务偶发超时很常见，N=1 会让异常榜长期刷屏，运维疲劳。  
**为什么推荐 N=3：**兼顾「别太敏感」与「别拖太久才看见」；业界熔断/告警常用「连续 K 次」而非「单次」。  
**配置：**默认 `N=3`；`conf.ini` 项 `health_failing_threshold`（正整数，缺省 3）。

| health\_status | 规则（B0） |
| --- | --- |
| `failing` | `consecutive_failures >= N` |
| `ok` | 最近一次为 success，且连续失败计数为 0 |
| `unknown` | 从未执行或尚无有效 outcome |

注意：任务「运行中/已暂停」是 `cron_infos.status` 生命周期，与 `health_status` 正交；列表两列或两套快筛共存。行内仍可展示 `consecutive_failures`（即使尚未 ≥N），便于观察趋势。

### 6.3 写路径（防行锁）

```
cron_do 完成并写入 job_log 后 → update_job_health(cron_id, outcome, log_id, at):
  if outcome in (fail, error):
      consecutive_failures += 1
      last_fail_at / last_run_* / last_run_log_id 更新
      health_status = failing if consecutive_failures >= N else ok|failing(按阈值)
      与 job_log 同事务同步提交（失败必须实时可见）
  if outcome == success:
      if consecutive_failures > 0 or last_run_status != 'success':
          # 翻转：同步清零并标记 ok
          consecutive_failures = 0; last_success_at=...; health_status=ok
      else:
          # 连续成功：节流写 last_run_at（如间隔>=10s 才 UPDATE），或跳过
          pass
```

**隐阱：**秒级任务禁止「每次 SUCCESS 都 UPDATE」。日志裁剪（`job_log_counts`）后**禁止**靠残缺日志重算连续失败——以 `job_health` 为准。
首期不引入 Redis；多 worker 热点任务若观测到锁争用，再单独立项依赖评审。

### 6.4 读路径

- L1 Metric / 异常榜：对可见 `cron_info_id` 集 join/filter `job_health.health_status='failing'`
- L2 行内：left join `job_health` 展示 last\_run / consecutive\_failures
- 聚合必须先注入 Scope（防 L1 见 B 组任务 → L2 403）

| **S4** L1 合体 | 列表顶 Metric；健康快筛；行内 last\_run / consecutive\_failures；admin 可无完整角色调制（留给 B1） | `cron_list.html` · 聚合查询（读 health 表） | 1–1.5 |
| **S5** 验证 | `cronpilot.sh test` · golden path · 三角色会话路径 · `restart` 后 curl/浏览器断言新标记 | 脚本 + 手工清单 | 0.5–1 |
| **S6** 闭环 | RELEASE\_NOTES · 交付状态标已交付 · 设计稿状态更新 · `html_docs_to_markdown --check` · 用户要求时再 commit | `doc/` · `RELEASE_NOTES.md` | 0.5 |
| **B0.5** 可选 | OPT-P1-01c：全局执行记录 `status` 失败筛选 | `job_log_all_list` + P1 小步设计 | +0.5–1 |

合计粗估（单人、不含旁路）：约 **5～8 人日**；捆 P1-01c 则约 **6～9 人日**。

### 11.3 每周节奏建议（示例）

| 日历 | 目标 |
| --- | --- |
| 第 1 段（1～2 天） | G0 确认 → S1+S2 合入（健康表可跑、失败可见于 DB） |
| 第 2 段（2～3 天） | S3+S4 管理端可见（Scope + Metric）；每日 `restart` 验收 |
| 第 3 段（1～2 天） | S5+S6；可选 B0.5；发布说明与路线图同步 |

### 11.4 完成定义（DoD）

- admin：工具栏业务组切换 + 连续失败快筛可用；Metric 数字与可见 Scope 一致；行内「更多」可编辑/下线
- operator（1/2 组）：同构工具栏；越权 group\_id 被拒；无空洞侧栏
- viewer：只读路径完整；无写入口泄露
- 秒级任务连续成功不导致 health 行锁告警（节流生效，可用测试或压测说明）
- 文档闭环与 `--check` 绿；无「只改代码不更交付状态」

**本阶段明确不做：**独立 `/dashboard`、Facet/Saved View、Redis、health\_score、新建 Execution 表、Tags、P1-03/04（除非另开确认）。
