以下为 rev.1 历史评估，受上述最新决策约束

评估结论与优先级

下一项优先处理提交后复审 R1：SQLite 中任务编辑与启停的在途撤权竞态。它是权限边界 P1，优先于启停提交后读取异常及版本归档。两条路径需分别修复与验收；只修其中一条不能关闭 R1。

证据与影响

任务编辑：已存独立进程证据显示 DELETE/WAL 下，读取 actor 后另一进程提交降权，旧请求仍返回 updated。见历史任务探针结果；本轮未重跑该探针。该证据证明服务层窗口，不代表完整 HTTP 攻击链或 MySQL 同样成立。

启停：本轮执行 .venv-py311/bin/python doc/qa/evidence/commit-review-2026-11-03/status_authorization_race.py，退出 0；独立连接降权已提交，actor 已为 viewer，保存仍成功，状态变为运行，隔离调度器真实 Job 恢复。隔离调度器全局暂停，未触发真实任务。此探针证明服务层交错，尚非真实撤权入口与双 HTTP 链路验证。

同轮执行 .venv-py311/bin/python doc/qa/evidence/commit-review-2026-11-03/status_postcommit_read.py：提交成功后注入读取失败，RuntimeError 逃逸，状态已写入且调度未调用。这是独立 R2，不应与撤权问题混称为同一修复。

根因与代码边界

cron_edit_concurrency.save_task_edit 和 cron_status_apply.save_status 使用 FOR UPDATE 读取当前主体；SQLite 不提供等效行锁，任务版本条件也不追踪 actor 的角色或组变化。启停先读取任务再读取 actor；写入前需要同库受保护的当前任务、主体和 scope 事实。API 和内部调用允许无 actor_id，不能把 Web Session 授权假定为 API Token 的授权，也不能仅用 Web 探针宣称覆盖全部调用方。

建议方案与实施顺序

  1. 先 Review 已存在的SQLite 任务编辑正式设计。它提出同 Session 局部写者保护、锁外 URL 校验、重新进入后重读授权与重算；记录最多保护轮次、错误语义、关系写和提交后调度边界。该设计明确不覆盖启停，仍待确认。
  2. 确认后按设计先执行源指纹冻结与 DELETE/WAL 反例重现，再分批实现并验证真实撤权入口和正反竞争顺序。确认该设计不等于批准启停方案。
  3. 为启停另出正式设计：逐一评估 Web actor、API Token scope 和内部调用的事务所有权；保护当前授权与条件写直到业务提交，明确同目标与签名重试语义。提交后 scheduler 是外部副作用，不能声称受数据库锁覆盖，也不能用未验证的回滚补偿已提交事实。启停提交后读取异常需在该设计中明确是否同批处理，未经确认不实施。

验收与风险

任务编辑依既有设计逐项验证撤权先提交、保存先保护、URL 校验间隙撤权、同字段冲突、不同字段合并、锁释放、关系写、真实角色 HTTP/浏览器与 MySQL 回归；不得将内存顺序测试当成真实竞争。启停必须另列真实撤权入口、双连接 DELETE/WAL、Web/API 各授权范围、版本与 Job 事实及失败清理矩阵。提交后副作用和独立日志的可靠性仍是单独边界。

本轮是评估，不改业务代码或测试；此前术语与基线修复仍为未提交工作区内容。全量最近一次为 1146 项、6 失败、12 跳过，见上轮验收；本轮未重跑全量，不能宣称发布就绪。
