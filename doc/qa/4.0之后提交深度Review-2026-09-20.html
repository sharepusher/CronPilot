v4.0.0 之后提交深度 Review

日期：2026-09-20 · 范围：v4.0.0..700ec94 · 方法：提交链路审阅、Bugbot 正确性检查、实现与设计/发布计划交叉核验。

1. 结论

不建议发布 4.1.0，也不建议将当前范围标为可合并完成。 已确认 3 个 P1 正确性缺陷：两个会造成主键冲突，一个会使启用 DNS pinning 的公网 IPv6 任务必然失败。执行侧观测的 R3/R4/R6/R7 仍是已登记但未关闭的发布阻断/观察项；发布计划还保留一处 R2 状态漂移。

2. 已确认问题

ID级别位置证据与影响修复方向
CR-1P1datas/utils/id_generator.py:18-45生成器只使用进程内线程锁和序列，但 gun.py 配置 workers=2。两个 worker 在同一秒首次生成都会得到相同 (timestamp << 12) | 0，可导致 cron_infos 或 job_log 主键写入冲突。使用数据库/跨进程原子序列，或加入稳定的 worker/node 位；补多进程并发唯一性测试。
CR-2P1datas/utils/id_generator.py:33-44时钟从 T 回拨到 T-1 时，代码重置序列并生成较小 ID；时钟回到 T 后会再次生成此前的 T+序列 0，导致重复主键。钳制 ts >= last_ts；序列耗尽时等待超过 last_ts；补回拨及溢出组合测试。

3. 测试覆盖审计

现有 tests/test_id_generator.py 覆盖同进程线程并发、顺序和单秒溢出；tests/test_p0_phase_a.py 覆盖 IPv4 pinning。两组共 44 项现有检查均无法覆盖多进程、时钟回拨或 IPv6 URL 构造，故“全绿”不能证明上述 P1 风险已消除。

4. 方案与实现一致性

  • 执行侧观测：执行侧观测优化完成后全面Review 已正确列出 R3（外层异常阶段）、R4（状态枚举门禁）、R6（唯一约束迁移）和 R7（混合事件 fallback）未关闭；这些项仍不应被 Release Notes 或路线图暗示为完成。
  • 发布计划漂移：4.1.0发布前变更梳理与文档收敛 已在结论中标记 R2 已关闭，但发布顺序仍写“R2 关闭且门禁全绿后”。这不改变运行行为，却会误导发布操作者；应改为以 R3/R4/R6/R7 和本报告 CR-1～CR-3 为准。
  • 设计覆盖缺口：OPT-P0-21 的 50-bit ID 设计只承诺线程安全，未对 Gunicorn 多 worker 与时钟回拨给出唯一性契约；SSRF/DNS pinning 设计未把 IPv6 URL 语法作为验收项。修复前应先补充这两份设计的边界、回滚与验收矩阵。

5. 建议修复顺序

  1. 先处理 CR-1/CR-2：这是持久化主键正确性问题，设计需明确跨进程 ID 分配方案与迁移兼容。
  2. 处理 CR-3：修复 IPv6 bracket，补 IPv4/IPv6、带端口和 HTTP/HTTPS 测试。
  3. 再处理执行观测 R3/R4/R6/R7，并更新 4.1.0 发布计划的阻断清单。
  4. 完成后重新运行全量测试、ID 专项多进程测试、IPv6 请求构造测试、迁移双后端测试与发布门禁。
