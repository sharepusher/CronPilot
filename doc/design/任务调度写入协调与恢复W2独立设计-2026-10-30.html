1. 问题与已验证事实

数据库中的任务配置和业务状态与 APScheduler 的 JobStore 分开写入。若较旧的调度操作在较新的恢复操作之后写入，就可能覆盖新的调度状态。W0 在隔离 SQLite 和 MySQL JobStore 使用两个全局暂停的独立调度器验证了“后恢复、旧暂停晚到”会被覆盖；故障注入亦证明调用报错时 JobStore 可能已经写入。实验为确定顺序的机制验证，未证明生产事故、跨进程同时执行表现或故障发生率。

当前 cron_edit_concurrency.py 和 cron_service.py 在业务提交后另行操作 scheduler；toggle_status 对已提交状态在失败时尝试版本约束补偿。cron_check 主要检查 job ID，不能证明 trigger 与暂停状态匹配。W1 已跳过非调度字段编辑时的不必要调度调用，规则改变和启停乱序仍未闭环。

2. 目标、边界与一致性承诺

  • 期望配置及版本持久化，状态准确区分：尚未验证、待应用、已确认及应用失败/未知；具体字段和值域不是本稿已确认的数据库结构。
  • 为同一任务的所有调度写入建立可验证的顺序约束；禁止较早状态在较新状态已确认后再次覆盖。若平台只能提供最终纠正而不能阻止短暂旧写，必须明确这种窗口、影响和用户是否接受，不能宣称强顺序。
  • 可恢复：进程崩溃、提交或应用回执丢失、调度项缺失或错误时可识别并按最新期望重新核对；恢复依赖业务库、JobStore 和执行者最终可用，不能承诺固定收敛时间。
  • 不能撤销已经进入执行器的任务和已经发出的 HTTP；权限、Scope、敏感信息不因同步设计被放宽。绕过协议的直接 DB/JobStore 修改不在保证内，必须通过运维权限及监控显式约束。

3. 字段和状态语义：候选而非迁移定稿

edit_revision任务编辑与关系的并发版本，包括非调度变更；不具备 JobStore fencing。沿用；评估是否能参与同步快照定位，不直接替代下项。

4. 候选架构和停止条件

候选 A 是单一调度应用者 + 持久期望 + 对账：Web/API 只提交期望及待处理证据，由被约束的应用者读取最新期望并更新 JobStore，再读回实际 trigger/参数/状态；同一任务按版本记录结果。前提是其他调度写者全部改道或被强制禁止，进程退出和新旧版本切换必须阻止旧写者重叠。现有配置开关只是启停本进程调度器，不证明独占写入；故障转移和旧进程恢复仍必须设计。

候选 B 是所有写者使用共享协调协议：每次写 JobStore 前取得同任务跨进程所有权、读取当前期望并应用。必须验证锁的持有、超时、连接断开和旧持有者恢复；普通 Redis TTL 租约、DB 事务版本回写、进程内锁或本机文件锁都不自动提供 JobStore fencing。若锁可过期且旧写仍能落地，本候选不能声称旧写绝不覆盖。不能证明所有写者共享同一协议时停止。

候选 C 是仅检测版本并周期性修正：可作为受限部署的漂移检测/恢复候选，但旧写可能短暂改变调度项甚至触发任务；不满足强顺序，是否可接受需明确业务决策。调度暂停不代表已在途执行被取消。C-0 以可实施性、运行风险和已有部署为依据比较 A/B/C，不预选数据库锁或新中间件。

5. 期望、应用、读回及故障流程（候选）

验证当前授权和字段意图
→ 同一业务事务写入配置与待同步期望（若本次涉及调度）
→ 提交结果确定后，由受约束写者应用最新期望
→ 读回实际调度规则、状态和必要参数
→ 仅对仍是当前期望的版本记录确认
→ 后续异常或漂移由对账重新核验

DB 提交失败时不应用新期望；提交结果未知时不能盲目应用或假设失败。JobStore 写入前失败与写入后回执丢失不能混同：先读取实际状态和最新期望，有限重试；避免旧版本通过条件写回标记新版本成功。待同步、失败、结果未知的前端/API 文案、是否允许继续编辑以及审计责任须在 C-1 单独定义。即使读回成功，后续非协议写者仍可能制造漂移。

8. 分批与停止门槛

  1. C-0 只读与隔离实验：冻结环境拓扑、实际支持的 DB/JobStore 组合、全部写者、W0 证据、单/多进程互斥与锁失效实验；只在随机隔离数据库和测试任务运行，不更改现有数据。形成可实施架构决策、字段独立语义和双后端迁移草案。这个阶段不授权业务实现。
  2. C-1 独立设计 Review：冻结一致性保证和运维约束，写出准确字段/状态转换、API 兼容、页面对比、可恢复操作与回滚；不能强制阻止旧写又不能接受旧写影响时停止。
  3. C-2 迁移与垂直切片：仅在 C-1 再次确认后执行。存量同步状态标未知，升级必须停旧写者并验证启动条件；迁移和回退均需 SQLite/MySQL 验收。单一编辑切片不得宣称所有入口全局安全。
  4. C-3 所有写者与恢复：逐入口迁移和独立回归，隔离新旧进程混跑；故障对账和目标角色浏览器通过后才评估完整交付。

9. 验收矩阵

  • 两进程/连接可控栅栏：暂停→恢复和恢复→暂停，较旧应用在较新操作之后恢复；分别验证 DB、实际 JobStore 和确认记录，不用仅检查返回值代替。
  • 应用者持锁时暂停、锁超时、连接断开、进程崩溃和旧进程恢复；必须验证过期持有者不能造成未声明的旧写，或验证明确接受的恢复窗口及告警。
  • DB commit 前失败、commit 后回执未知、JobStore 已写但回执未知、确认写回失败、JobStore 缺失和重启；每一步校验落库事实和最终读回，不能使用虚假的成功/失败状态。
  • SQLite/MySQL 空库、存量未知、重复迁移、故障回滚、权限受限和线上升级隔离；验证任务量、索引执行计划和对账扫描范围，不预设负载或收益。
  • Web/API 所有涉及任务生命周期入口和角色权限正反测试；已有在途执行、过期一次性任务、无调度变化保存；浏览器检查实际故障提示。

10. 风险、回退与未完成事项

引入持久状态和协调增加数据库写入、等待和可用性依赖；调度规模、争用、吞吐及恢复时间均未测，C-0 应在隔离环境按代表性数据量测量，不虚构百分比。回退须先停所有新旧写进程并备份，评估未同步任务、异常状态及重复触发风险；不能直接回退后宣称原保证仍有效。原开发 SQLite 完整性异常为独立问题，本稿不授权修改该数据库。

本轮仅核对现有代码与 W0 证据；没有真实多进程、故障转移、C-0 迁移实验或 W2 实现，不把本稿标为已完成。

11. C-0 校准进展（2026-10-30）

执行 .venv-py311/bin/python scripts/verify_w2_lock_calibration.py；使用独立子进程、随机创建并自动删除的 MySQL 库和临时 SQLite 文件，不读取或修改原开发库。完整结果：锁校准 JSON。

  • SQLite 独立数据库中，第一进程持有 BEGIN IMMEDIATE 时第二连接写事务被拒绝；回滚后可写，强制结束持有进程后也可写。该结果只证明此单文件写锁场景，不证明 SQLite 行锁或跨数据库 JobStore 防旧写。
  • MySQL 中持有 GET_LOCK 的连接存活时另一连接无法获得同名锁；终止测试进程自己持有的测试连接后，另一连接成功获取锁并恢复 job，旧进程随后使用另一条 JobStore 连接仍能把它覆盖成暂停。该确定性交错使用两个 OS 进程，不代表自动测试实际网络分区或线上复现。
  • 首次实验主断言已达到，但测试进程清理被故意断开的连接时抛出预期断连异常，导致整体未通过；脚本仅对断连码 2006/2013 的清理做针对性处理，再重跑通过。隔离库在失败及成功路径均由 finally 清理。

现状核对：gun.py 默认两个 gevent worker；CRONPILOT_SCHEDULER_ENABLED 仅控制本进程调度器启动；自定义调度器使用的 scheduler.lock 位于本地扫描路径，不能推出 Web/API 写 JobStore 被全局串行。single_task 用于被装饰任务执行，且仅在配置启用时使用 Redis，并不是这些 Web/API 调度写入口的统一锁。当前下线路径先移除 JobStore 项再提交业务状态；这与编辑/启停的事务顺序不同，需按故障矩阵分别分析。

阶段结论：排除“仅凭 MySQL 连接锁本身即可阻止失联旧进程写外部 JobStore”的安全假设；SQLite 文件级互斥也不能自动覆盖独立 JobStore。尚未完成真实跨主机分区/恢复、Redis 租约续期与失效、所有入口运行时覆盖、候选迁移和性能测试。当前不选定互斥机制、不声称 W2 全局顺序、也不进入业务实现。

同库自阻塞实验：临时 SQLite 同文件中，SQLAlchemyJobStore 使用自己的引擎连接；业务连接持有 BEGIN IMMEDIATE 时，调度器 add_job 在独立连接上因数据库锁定失败，释放业务锁后相同写入成功。该测试的 JobStore 连接超时固定 0.2 秒，只说明所测同文件连接组合不能简单持有业务写锁并同步等待 JobStore 写；不外推为所有数据库或所有部署都会死锁。结果记入上述 JSON。

部署边界补充：仓库 gun.py 默认两个 worker，docker-compose.yml 未显式设置调度进程单所有者；开关与配置描述不是故障切换时的排他证明。用户现有实例使用何种多机/多容器部署与流量、业务库/JobStore 是否同库尚未验证；候选决策必须涵盖支持的拓扑并可验证地拒绝不支持的部署。现有 single_task 中 Redis 锁默认 TTL 两分钟，只包被装饰的执行函数，不能据此推断对所有编辑/启停写者生效。

12. 单主机单所有者候选的可行性实验

命令：.venv-py311/bin/python scripts/verify_w2_single_owner.py。使用 spawn 创建独立 OS 进程、临时本地文件、真实 SQLAlchemyJobStore 和 CuBackgroundScheduler，所有扫描器全局暂停，未执行任何业务任务。结果见 实验 JSON。

  • 所有者打开同一锁文件并持有全生命周期排他锁；第二进程在访问 JobStore 前获取失败并退出，原进程仍能检查其暂停 job。
  • 确认原进程 terminate 且 join 后不再存活，再启动接管进程；持久任务仍暂停，接管进程明确恢复后可读到运行目标；正常退出再启动后持久状态保持。
  • 测试期间不删除或替换锁文件，不使用 TTL。该实验未测试 SIGSTOP、不同容器挂载、NFS、不同操作系统、多主机分区或真实 job 执行。

建议收窄的首个可实施部署范围：单主机、同一受控本地文件系统上的唯一调度应用/扫描进程；Web/API 多 worker 仅写业务期望，不直接写 JobStore；接管必须证明旧进程退出，不能仅凭心跳超时。旧进程存活但无响应时停止自动接管，牺牲暂时可用性而不冒称已有跨主机 fencing。该范围仍需用户确认，不能假定用户部署满足。

实现前必须补齐：全部调度写入口改道与启动拒绝规则；旧版本进程/运维脚本无法绕过的部署约束；应用者启动、暂停、退出、心跳告警和离线期间请求语义；业务期望记录与确认/读回故障的字段及双后端迁移；同一进程的后台线程、调度扫描与应用请求对同一 job 的内部串行及锁顺序。独占进程不等于内部所有操作天然顺序一致，不以本实验当成完整 C-0 通过。

跨主机自动接管：本地文件锁不能覆盖此需求，不能作为相同设计的一个配置开关启用；如有此部署要求，须另行验证所有者撤销、存储层条件写或可靠 fencing 与数据访问权限，且不能用普通租约代替证明。尚未选择该方案，也未实施。
