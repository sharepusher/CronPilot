# 注册审批结果状态显示设计

**状态**：待确认  |  **日期**：2026-08-28  |  **关联**：OPT-P1-10 注册审批

## 1. 问题

**P1. 已审批状态不可辨** — 已通过 / 已拒绝（无原因）/ 已过期的注册申请，操作列统一显示 `—`，管理员无法直观判断审批结果。

**P2. 审批决策信息不足** — 审批者做决定时，表格仅展示基本信息（用户名/花名/邮箱/岗位），缺少关键审批依据：

- **申请角色**（role）— viewer / operator / admin 权限差异巨大，直接影响审批标准
- **申请业务组**（group\_ids）— 决定用户可访问的资源范围
- **申请原因**（reason）— 申请者自述的使用目的

这些字段在模型 `RbacRegistrationRequest` 中已有，但审批页面未展示。

## 2. 根因

**P1**：操作列 Jinja 条件分支仅处理了 `pending` 和 `rejected + review_comment`，其余状态 fallback 到 `—`。

**P2**：注册审批页面直接复用了简化表格，未设计展开详情机制。视图函数未传递 `group_name_map`，模板无组名解析能力。

## 3. 参考与交互方案对比

### 3a. 详情展示方式三方案对比

| 维度 | A. "详情"按钮展开行 | B. 独立详情页 | C. 点击整行展开 |
| --- | --- | --- | --- |
| **信息密度** | 高 — 列表+详情同视口 | 低 — 离开列表上下文 | 高 — 同 A |
| **操作效率** | 中 — 需精准点击按钮 | 低 — 页面跳转+返回 | 高 — 点击面积大 |
| **批量审阅** | 好 — 逐行展开对比 | 差 — 频繁跳转 | 好 — 但展开收起频繁触发 |
| **误触风险** | 低 — 按钮意图明确 | 无 | **高** — 选文本/点复选框/点操作按钮均可能误触 |
| **与复选框兼容** | 好 — 互不干扰 | 好 | **差** — 点击行内复选框同时触发展开 |
| **移动端** | 中 — 小按钮 | 好 — 独立页面天然适配 | 好 — 整行可点 |
| **实现复杂度** | 低 — 纯前端 toggle | 高 — 需新路由+模板 | 中 — 需排除内部元素点击冒泡 |
| **无障碍 a11y** | 好 — 按钮有明确 role | 好 — 标准导航 | 差 — 行点击需额外 ARIA |
| **行业参考** | Jira Backlog、GitHub PR | 企业 OA 审批 | Notion 数据库行 |

**选择方案 A（按钮展开行）**：

1. **批量审阅场景** — 注册审批需逐条审阅多条申请，频繁页面跳转的方案 B 效率最低
2. **避免交互冲突** — P1 批量操作引入了复选框，方案 C 的整行点击与复选框、操作按钮严重冲突（需对每个行内交互元素做 `event.stopPropagation()`，维护成本高且易遗漏）
3. **信息量适中** — 注册详情仅 6-8 个字段，展开行完全够用，无需独立页面
4. **一致性** — 操作列已有"通过/拒绝"按钮，追加"详情"按钮符合用户心智模型

### 3b. ID 列分析

**结论：移除 ID 主列**，在展开详情行中以辅助信息形式展示。

| 维度 | 分析 |
| --- | --- |
| 用户价值 | ID 为自增数据库主键，对审批人无业务语义；审批关注点是「谁/什么角色/什么时候」 |
| 行业参考 | GitHub PR 列表不展示数据库 ID；Jira 展示人类可读 issue key（`PROJ-123`），非主键 |
| 空间成本 | ID 列占 ~60px 宽度，在 8 列表格中属低价值消耗 |
| 批量操作替代 | 复选框 `value` 已承载 ID 传递，用户无需感知 |
| 排序替代 | 「申请时间」列天然提供时序；「用户名」已满足唯一标识（`pending_username` UNIQUE） |
| 调试需求 | 在展开详情行中显示 `申请编号: #6`（灰色辅助文字），仅排查时可见 |

## 4. 方案

### 4a. 状态标签（P1）

操作列按 `req.status` 显示彩色标签，复用已有 `pg-audit-badge-*` CSS 类（`redesign-pages.css` L1628–1632）：

| 状态 | 当前 | 改后 | CSS 类 |
| --- | --- | --- | --- |
| `pending` | 通过 / 拒绝按钮 | **不变**（保持按钮） | — |
| `approved` | `—` | 已通过 | `pg-audit-badge-ok` |
| `rejected` | 原因文本 / `—` | 已拒绝 + 原因 | `pg-audit-badge-fail` |
| `expired` | `—` | 已过期 | `pg-audit-badge-muted` |

### 4b. 展开行详情（P2）

#### 交互方式

操作列末尾增加详情按钮（所有状态均有），点击后 toggle 展开当前行下方的详情行。再次点击收起。同一时间可展开多行。

#### 详情行字段清单（与个人资料页对照）

| 字段 | 来源 | 展示方式 | 个人资料页对照 |
| --- | --- | --- | --- |
| **申请角色** | `req.role` | 角色标签：viewer / operator / admin | 个人资料页「角色」行 |
| **申请业务组** | `req.group_ids` → 通过 `group_name_map` 解析 | 组名标签列表：技术组运维组；若为 `__ALL__` 显示「全部业务组」 | 个人资料页「所属业务组」行 |
| **申请原因** | `req.reason` | 完整文本（最长 500 字符，模型约束） | 无（注册表单独有字段） |
| **审批状态** | `req.status` | 彩色标签（同 4a） | — |
| **审批人** | `req.reviewer_id` → 通过 `reviewer_map` 解析用户名 | 仅已处理申请显示，如：「admin」 | — |
| **审批时间** | `req.update_time` | 仅已处理申请显示，格式同申请时间 | — |
| **拒绝原因** | `req.review_comment` | 仅 rejected 状态显示，完整文本 | — |

#### 详情行布局

采用 2 列 Grid 布局（与个人资料页 `pf-info-list` 的 `<dl>` 结构对齐），左蓝色边框标识展开区域：

```
┌─────────────────────────────────────────────────────────────┐
│ 申请角色                      申请业务组                  │
│ [operator]                    [技术组] [运维组]            │
│                                                             │
│ 申请原因                      审批状态                    │
│ 需要管理定时任务，负责数据…      [待审批]                    │
│                                                             │
│ 审批人                        审批时间                    │
│ —                               —                           │
└─────────────────────────────────────────────────────────────┘
```

#### 后端数据准备

视图函数 `registration_review()` 需新增两个上下文变量：

| 变量 | 来源 | 说明 |
| --- | --- | --- |
| `group_name_map` | `ResourceGroup` 全表查询 | `{group_id: group_name}`，用于 `req.group_ids` → 组名解析 |
| `reviewer_map` | 页面内 `reviewer_id` 集合 → `RbacUser` 查询 | `{user_id: username}`，用于审批人展示 |

模板中 `group_ids` 解析逻辑（Jinja）：

```
{% set gids = req.group_ids.strip() %}
{% if gids == '__ALL__' %}
  全部业务组
{% elif gids %}
  {% for gid in gids.split(',') %}
    {% if gid.strip() %}
      {{ group_name_map.get(gid.strip()|int, '组#' + gid.strip()) }}
    {% endif %}
  {% endfor %}
{% else %}
  未指定
{% endif %}
```

#### JS 交互

纯 jQuery toggle，无 AJAX：

```
$(document).on('click', '.rr-expand-btn', function() {
    var $row = $(this).closest('tr').next('.rr-detail-row');
    $row.toggle();
    $(this).text($row.is(':visible') ? '收起' : '详情');
});
```

## 5c. 展开行详情重设计

**状态**：待确认  |  替换原 4b 设计中的 2 列 Grid 平铺布局

### 问题诊断

| # | 问题 | 严重性 | 说明 |
| --- | --- | --- | --- |
| D1 | **信息平铺无分组** | 高 | 申请信息（角色/组/原因）与审批信息（审批人/时间/拒绝原因）混在同一个 2 列 grid 中，无语义分组，认知负担高 |
| D2 | **视觉层次扁平** | 高 | 所有 label 同样式（11px / muted），所有 value 同样式（13px / ink），无重点突出 |
| D3 | **空间利用低效** | 中 | `padding: 12px 16px` + `gap: 10px 24px` 在宽表格中过于紧凑；2 列 grid 对短值浪费空间，对长文本（申请原因 500 字）又不够 |
| D4 | **左蓝边框语义模糊** | 中 | `border-left: 3px solid signal` 在表格行中突兀，更像"侧边标记"而非"展开详情区" |
| D5 | **状态字段冗余** | 低 | 主行操作列已有状态标签（已通过/已拒绝），展开行重复显示审批状态 |
| D6 | **字段数量动态跳变** | 低 | pending 4 字段、approved 6 字段、rejected 7 字段，展开行高度差异大 |

## 5d. 信息架构重组

**核心问题**：审批决策关键信息（角色 + 业务组）被藏在展开行中，管理员需"展开每一行"才能做决策。  
**解决思路**：将高决策权重字段提升到主行，使列表本身成为"决策面板"。

## 6. 与个人资料页模板的关系

| 维度 | 个人资料页 (`user_profile.html`) | 审批展开行 (本次设计) | 复用关系 |
| --- | --- | --- | --- |
| 数据来源 | `RbacUser` 对象 | `RbacRegistrationRequest` 对象 | 不同模型，字段名不完全相同 |
| 角色字段 | `user.role` | `req.role` | 相同语义，复用 `role_display_name()` 函数 |
| 业务组 | `user_groups_display`（已拼接文本） | `req.group_ids`（逗号分隔 ID 字符串） | 需独立解析（模板内 group\_name\_map lookup） |
| 岗位类型 | `user.job_title` + `job_title_choices` 枚举 | `req.job_title` + 同枚举 | 已在主表格显示，展开行**不重复** |
| 邮箱/花名 | `user.email` / `user.nickname` | `req.email` / `req.nickname` | 已在主表格显示，展开行**不重复** |
| 申请原因 | 无此字段 | `req.reason` | 注册申请独有 |
| 审批信息 | 无 | `req.reviewer_id` / `req.update_time` / `req.review_comment` | 注册申请独有 |

**结论**：展开行与个人资料页**字段有重叠但不适合直接复用模板**。原因：① 数据模型不同（`RbacUser` vs `RbacRegistrationRequest`）；② 展开行需要嵌入 `<tr>` 中，与卡片布局不兼容；③ 展开行只展示主表格**未包含的补充字段**，避免信息重复。但**视觉语言对齐**：标签颜色、字号、间距参照个人资料页的 `pf-info-item` 风格。

### 6b. 审批通过后的数据流转

审批通过后，`approve_registration()`（`app/rbac/services.py` L961–1033）执行以下流程：

| 步骤 | 操作 | 数据映射 |
| --- | --- | --- |
| 1 | 校验申请状态为 `pending` | — |
| 2 | 检查用户名冲突（启用用户） | 若冲突 → 自动拒绝并写 `review_comment='用户名已被占用'` |
| 3 | 删除同名已停用旧用户（释放 UNIQUE） | — |
| 4 | **创建 `RbacUser`** | 见下方字段映射表 |
| 5 | 绑定业务组 | `req.group_ids` → 逐个写入 `UserGroup(user_id, group_id)`；`__ALL__` 不写行 |
| 6 | 更新申请状态 | `req.status='approved'`、`req.reviewer_id`、`req.update_time` |
| 7 | 自动签发 API Token | `_auto_issue_token(user)` |
| 8 | 审计日志 | `action='user:register_approve'` |

#### 字段映射：注册申请 → 用户记录

| `RbacRegistrationRequest` | → | `RbacUser` | 同步方式 |
| --- | --- | --- | --- |
| `req.username` | → | `user.username` | 直接复制 |
| `req.password_hash` | → | `user.password_hash` | 直接复制（哈希值，非明文） |
| `req.email` | → | `user.email` | 直接复制 |
| `req.role` | → | `user.role` | 直接复制 |
| `req.job_title` | → | `user.job_title` | 直接复制（含 `other:xxx` 格式） |
| `req.nickname` | → | `user.nickname` | 直接复制 |
| `req.group_ids` | → | `UserGroup` 关联表 | 拆分逗号 → 逐行写入 |
| `req.reason` | → | **不同步** | 申请原因仅保留在注册申请表中，不迁入用户表 |

**关键说明**：审批通过后，用户的所有基础信息（用户名、密码、邮箱、角色、岗位、花名、业务组）**一次性同步**到 `RbacUser` + `UserGroup`。此后用户可在「个人资料」页面自行修改花名、邮箱、岗位，但**角色和业务组**只能由管理员在「用户管理」页面修改。注册申请记录（`RbacRegistrationRequest`）作为审计痕迹**永久保留**，不会删除。

## 7. 并发审批安全分析

多管理员可能同时审批同一条注册申请。以下分析现有防护机制及各并发场景的处理结果。

### 7a. 现有双层防护

| 层级 | 机制 | 位置 | 作用 |
| --- | --- | --- | --- |
| **第 1 层 — 应用层** | `if req.status != 'pending': return` | `services.py` L969–970 | 先提交者改状态为 approved/rejected，后到者读到非 pending 直接返回"该申请已处理" |
| **第 2 层 — 数据库层** | `pending_username` UNIQUE 约束 | `rbac_registration_request.py` L39–44 | 审批通过后 `pending_username` 设为 NULL，同时创建 `RbacUser`。UNIQUE 约束防止两个 pending 请求使用同一用户名 |

### 7b. 并发场景矩阵

| 场景 | Admin A | Admin B | 结果 | 安全？ |
| --- | --- | --- | --- | --- |
| **同时通过** | approve(#6) | approve(#6) | 先提交者成功创建用户；后到者 `status != 'pending'` 返回"已处理" | ✓ |
| **一通过一拒绝** | approve(#6) | reject(#6) | 同上，先提交者生效，后到者看到已处理 | ✓ |
| **极端竞态** （flush 前并发） | approve(#6) 执行中 尚未 commit | approve(#6) 读取 status 仍为 pending | 两者都通过 status 检查 → 均执行 `db.session.add(user)` → 先 commit 成功，后 commit 触发 `username` UNIQUE IntegrityError → except 分支 rollback | ✓ |
| **批量+单条并发** | batch\_approve([5,6]) | approve(#6) | 逐条调用 `approve_registration()`，#6 只有一方成功，另一方返回"已处理"，不影响 #5 | ✓ |

### 7c. 用户体验优化建议

| # | 问题 | 建议 | 优先级 |
| --- | --- | --- | --- |
| 1 | Admin B 页面仍显示"通过/拒绝"按钮（页面加载时 status 还是 pending） | AJAX 返回"已处理"后，JS 动态将该行按钮替换为状态标签，而非仅弹 toast | P2（可后续迭代） |
| 2 | SQLite 写锁粒度较粗（WAL 模式），高并发写入性能受限 | SQLite 部署规模下无需优化；若迁移 MySQL/PostgreSQL 可考虑添加 `version` 列乐观锁 | P3（远期） |

**结论**：当前应用层检查 + 数据库 UNIQUE 约束的双层防护已覆盖所有可预见并发场景。SQLite 的写事务天然串行化进一步降低了竞态风险。

1. **Batch 1 — 状态标签**（纯模板改动）：修改操作列 `{% if %}` 条件分支 → restart → curl 验收
2. **Batch 2 — 展开行详情**：① views.py 增加 `group_name_map` + `reviewer_map`；② 模板增加展开行 HTML；③ JS toggle 逻辑；④ CSS 样式 → restart → 浏览器验收展开交互
3. **Batch 3 — 搜索**（P1）：① views.py 增加 `search_username` 查询逻辑；② 模板增加搜索框 + 清除按钮 → restart → 验收搜索 + 分页保持
4. **Batch 4 — 批量操作**（P1）：① views.py 新增 `batch_approve` / `batch_reject` 路由；② 模板增加复选框 + 批量操作栏；③ JS 全选/联动/AJAX 提交 → restart → 浏览器验收批量流程

## 12. P2 UX 优化方案

基于审批列表数据展示合理性分析，提出以下 3 项 UX 优化建议。

### 12a. 默认筛选改为"待审批" 已评估 · 不采纳

**决策**：保持默认"全部"视图。理由：① CronPilot 审批频次较低，管理员进入审批页面时通常也需要参考历史审批记录（先例、通过率）；② 已有筛选按钮供用户自行过滤 pending；③ 配合 12c badge 数字，管理员入页即可感知待审批数量，无需改变默认视图。

#### 行业对标

| 产品 | 默认视图 | 可切换全部？ |
| --- | --- | --- |
| GitHub Issues / PR | `is:open`（待处理） | Yes |
| Jira Board | Sprint 当前列 | Yes（Backlog） |
| GitLab Merge Requests | `Open` | Yes |
| Slack Workflow | 待处理 tab | Yes（已处理 tab） |
| AWS IAM Access Requests | Pending | Yes（History） |

**结论**：6/6 审批类产品默认展示"待处理"视图。

#### 信噪比分析

假设运行 6 个月的系统（50 个注册申请）：pending 0–3 条、approved ~40 条、rejected ~7 条、expired ~3 条。默认"全部"时信噪比约 6%，审批人需在 50 条中寻找 3 条可操作项。

#### 实现方式对比

| 方式 | 实现 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 后端默认（推荐）** | `views.py` 中无 status 参数时默认 `pending` | 首次加载即为 pending，URL 干净 | "全部"需显式传空 status |
| B. 前端重定向 | JS `location.replace('?status=pending')` | 不改后端 | 额外跳转、页面闪烁 |
| C. 视觉引导 | "待审批" chip 加 badge 数字 | 无行为变更 | 首次仍看到全部 |

**推荐方案 A**：后端默认 `status=pending`，"全部"按钮显式传 `status=` 空值，与 GitHub/Jira 实现方式一致。

### 12c. 标题旁待审批数量 badge 已实施

#### 行业对标

| 产品 | 位置 | 格式 |
| --- | --- | --- |
| GitHub | Issues tab | `Issues (23)` |
| Jira | Board 标题 | `Sprint 45 · 7 issues` |
| GitLab | MR tab | `Merge Requests (5)` |

#### 实现

- `views.py`：`pending_count = repo.count_by_status('pending')`（额外 1 次 COUNT 查询，< 1000 行表无性能风险）
- 模板：`<h1>注册审批{% if pending_count %} <span class="pg-badge-count">{{ pending_count }}</span>{% endif %}</h1>`
- CSS：`.pg-badge-count` — 圆角蓝色小标签，参照侧边栏 badge 样式

**优先级**：P2 — 不影响核心功能，提升审批效率感知。

#### 性能评估

| 场景 | 数据量 | 预期耗时（SQLite WAL） | 预期耗时（MySQL InnoDB） |
| --- | --- | --- | --- |
| 小型部署（1-2 年） | < 500 行 | < 0.1ms | < 0.1ms |
| 中型部署（3-5 年） | 500 - 5,000 行 | < 0.5ms | < 0.3ms |
| 大型部署（5+ 年） | 5,000 - 50,000 行 | < 2ms | < 1ms |
| 极端场景 | 100,000+ 行 | < 5ms | < 2ms |

**分析**：`COUNT(*) WHERE status='pending'` 命中 `status` 索引（`index=True`），pending 行通常 < 10 条，索引扫描 O(log n + k)。新增 1 次 COUNT 查询（页面原有 4 次 → 5 次），增量耗时 < 0.5ms，用户无感知。

**按组管理员路径**：`get_pending_count_by_groups()` 使用 `LIKE '%gid%'` 匹配组交集，无法使用索引。但因 pending 行极少（< 10 条），即使逐行字符串匹配也在亚毫秒级完成。`LIKE` 误匹配（`'%1%'` 匹配 `'15'`）是既有架构债（`group_ids` 逗号分隔存储方案），非 badge 引入的新问题，修复应作为独立的数据模型重构。

**结论**：性能风险极低，不建议添加缓存（引入额外复杂度不值得，缓存失效逻辑反而增加 bug 面）。

#### 实施详情

- `views.py`：利用已有 `repo.get_pending_count_all()` / `repo.get_pending_count_by_groups()`，传 `pending_count` 到模板
- 模板：`<h1>注册审批{% if pending_count %} <span class="pg-badge-count">{{ pending_count }}</span>{% endif %}</h1>`
- CSS：`.pg-badge-count` 使用 `var(--cp-signal-bg)` / `var(--cp-signal)`，圆角蓝底标签

### 12d. 审批列表数据展示合理性结论

**全量历史展示（当前方案）合理**：

1. **审计追溯**：审批记录是操作日志的组成部分，管理员需回溯"谁批了谁"
2. **状态总览**：一眼看到审批通过率、拒绝原因分布
3. **行业惯例**：GitHub PR、Jira Issue 不默认隐藏已处理项

**种子 admin 不会出现在审批列表**：种子 admin 通过 `conf.ini` 初始化创建，从未提交注册申请。`rbac_registration_requests` 表仅记录通过注册页面 (`/rbac/register`) 提交的申请。

**Self-approve 风险不存在**：申请人在被审批前没有 `user_id`（账号未创建），无法作为审批人操作自己的申请。

### 12e. 三项 UX 优化协同关系与实施决策

#### 最终决策

| 项 | 决策 | 理由 |
| --- | --- | --- |
| 12a 默认筛选 | 不采纳 | 保持默认"全部"：① 审批频次低，管理员需参考历史先例；② 已有筛选按钮自助过滤；③ badge 已提供待办感知 |
| 12b 已处理行淡化 | 待决策 | 默认"全部"视图下淡化价值更高（视觉层次引导）；可与 12c 独立实施 |
| 12c badge | 已实施 | 标题旁蓝色圆角 badge 显示 pending 数量；性能评估极低风险 |

#### 协同关系（更新后）

```
12c (badge 数字) ✅ 已实施
       │
       ↓ 入页即感知待办量
       │
12b (淡化显示) ⏳ 待决策
       │ 默认"全部"视图下价值更高
       │ （视觉层次引导可操作行）

12a (默认筛选) ✗ 不采纳
       保持默认"全部" + 自助筛选
```

**关键变化**：12a 不采纳后，12b 的价值提升 — 默认"全部"视图下，管理员需要在混合列表中识别可操作项，行级灰化成为主要的视觉引导手段。

### 12f. 专业性评审补充项

#### 12a 补充：首次访问 vs 回访区分

新管理员首次进入审批页面时可能需要查看全部历史以了解审批惯例和先例。当前方案 A（后端默认 pending）对此场景的处理：管理员可随时点击"全部"切换到完整视图。此为标准 UX 模式（GitHub/Jira 均如此），新用户学习成本为一次点击，可接受。

#### 12b 补充：暗色主题交互与视觉 Demo

**暗色主题风险**：`var(--cp-surface-2)` 在暗色主题下为深灰（`#2a2a3c`），`var(--cp-text-muted)` 为浅灰（`#8B9198`）。已处理行在暗色下的灰化对比度低于亮色主题。建议实施时需 dark mode 下截图验证，确保灰化行与正常行仍有可辨识的视觉差异。

**与展开行蓝色边框的交互**：灰化行展开后，展开行使用左蓝色边框（`border-left: 3px solid var(--cp-signal)`）已提供了足够的视觉区分。但需验证灰化行内的状态标签颜色（如绿色"已通过"）是否被 `color: var(--cp-text-muted)` 覆盖 — `.pg-audit-badge-ok` 使用了自身 `color` 属性，应不受行级 `color` 影响（CSS specificity）。

#### 12c 补充：badge 更新时机与侧边栏扩展

**更新时机**：badge 数字在页面加载时由后端渲染。审批通过/拒绝后页面刷新，badge 自动更新。如需无刷新更新（AJAX 审批后即时减数），需额外 JS 逻辑（P3 可选，当前可暂不实现）。

**侧边栏扩展**：更高频可见的 badge 位置是侧边栏"注册审批"导航项。但侧边栏 badge 需额外的全局查询（每次页面加载都执行 COUNT），当前阶段仅在审批页标题显示更合适。侧边栏 badge 可作为后续独立优化。

**badge=0 时的 UX**：方案中 `{% if pending_count %}` 使 pending=0 时不显示 badge — 这是正确的"零态"处理（"没有待审批"不需要任何视觉指示器），与 GitHub Issues tab 行为一致。

## 13. 风险

- **低风险**：模板条件分支 + 展开行 toggle，不改核心审批逻辑
- **后端查询**：`group_name_map` 和 `reviewer_map` 各一次查询，数据量极小（业务组 < 20，审批人 < 10）
- **搜索性能**：`LIKE '%keyword%'` 在 < 1000 行注册申请表上无性能风险；后续若数据增长可加索引
- **批量操作并发**：每条独立调用 `approve_registration()`，`pending_username` UNIQUE 约束保证并发安全；单条失败不影响其余（逐条执行 + 汇总结果）
- **回退**：Git revert 单 commit（Batch 3/4 的路由新增可独立回退）

### 13b. 复盘：pending 用户登录被限流锁定

**问题**：pending 用户每次尝试登录都被 `record_login_failure()` 计为失败，5 次后触发 IP 锁定（15 分钟），之后 `check_login_limit()` 直接返回锁定消息，用户无法看到「注册审核中」提示。

**根因**：`check_registration_status()` 位于认证失败分支的最后一步，在 `record_login_failure()` 和 `check_login_limit()` 之后。pending 用户的状态查询被错误地纳入安全限流统计。

**修复**：将 `check_registration_status()` 前移到 CSRF 校验之后、限流检查之前。pending/rejected 用户直接返回注册状态，不进入认证和限流流程。

**架构约束**：登录视图的执行顺序必须为：  
① CSRF 校验 → ② **注册状态前置检查**（pending/rejected 直接返回） → ③ 限流检查 → ④ 认证 → ⑤ 失败记录  
验证命令：`grep -n 'check_registration_status\|check_login_limit\|authenticate_user' app/rbac/views.py | head -5`（注册检查行号 < 限流行号 < 认证行号）。
