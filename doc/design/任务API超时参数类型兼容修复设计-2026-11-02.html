1. 问题与业务影响

新 API 请求提供合法 timeout_sec=5 时，Schema 将值转换为整数 5，normalize_cron_form 对该值调用 .strip()，在正常输入上抛出 AttributeError。上轮隔离端点验证观察到 500；本轮重新执行真实 Schema→normalize 链路也复现异常，未重新启动端点宣称复测 HTTP。D1 的端点验收没有传该可选字段，因此不能证明超时字段路径健康。

该错误发生在任务查找、提交和调度之前，当前受影响请求通常不能完成保存。它是输入类型契约不兼容，与调度器是否返回成功无关。优先关闭这个小范围、确定性问题，再推进 D2，可避免后续验收继续绕过已知失败字段。

2. 根因与已读代码

  • app/api/schemas.py：CronUpsertIn.timeout_sec 为 Integer，默认 None，范围 1–120。
  • app/api/views.py：crons 接收 Schema 的 form_data，传给共享 upsert；旧 crons_legacy 使用 request.values.to_dict()。
  • app/services/cron_service.py：upsert 先 normalize_cron_form，后校验，两个阶段都必须接受已规范化或已反序列化的数据。
  • app/services/cron_validator.py：timeout_sec_raw = (datas.get('timeout_sec') or '').strip() 假定输入都是字符串；or 也会把数值 0 当缺失。

根因是跨入口共享校验器没有明确支持字符串与已转换整数两种输入，并非 Schema 的 Integer 定义错误。建议保留正确的 Schema/OpenAPI 类型，在共享规范化边界兼容两种来源。

3. 方案与字段语义

  1. 在 normalize_cron_form 的 timeout_sec 分支先区分类型，再去空白、解析和检查范围；不对任意对象直接 str() 后强行接纳。
  2. 缺失/None → None；字符串 trim 后为空 → None；非空整数字符串按现有 int 解析规则得到整数；int 原样进入范围检查；bool 必须先于 int 拒绝。浮点、集合等其他类型返回“必须是整数”。
  3. 范围统一为 1–120，0、负数及大于 120 拒绝，不把 0 当成默认值；成功输出只允许 int 或 None。
  4. 不修改 CronUpsertIn、公开字段、数据库结构、超时执行逻辑、无变更判定或调度调用策略；保持 Web/旧路径清空表示使用默认超时的既有语义。
  5. 同时测试再次验证 int/None 的路径，避免首次规范化通过、第二次校验又失败。异常原文仍只留在服务端。

4. 范围与明确不包含

计划实现仅限共享 timeout_sec 规范化分支及对应测试/验收脚本。新旧 API、Web 通过共享入口受益；不改变 API 协议字段，不新增依赖或迁移。无页面布局、模板、按钮或交互修改，因此不需要新增页面 Before/After。任务启停 D2、下线 D3、原 SQLite 索引异常均独立处理。

7. 风险、性能与专业评估

改动局限于内存中的单字段类型判断、trim、整数转换和范围比较，不新增查询、锁、连接、缓存或调度操作。没有实测性能收益，也不需要增加缓存。主要兼容风险是将不合法数值 0 从误当缺失改为明确拒绝；它与已声明的 1–120 契约一致，必须通过旧入口反例验证。新 API 空字符串仍由 Schema 先拒绝，不混淆不同入口的缺省规则。

准确性依据是当前实现与可重现异常；合理性在于修共享边界而保留正确的 Integer Schema；专业性通过同源输入、输出类型、失败零副作用和真实端点回归保证。完成该独立修复后，再为 D2 的“启停异常不能盲目回滚”提交单独设计确认。

11. 七项修复复盘

  1. Bug 定位：合法超时参数经新 API Schema 转成 int 后，进入共享字符串处理分支，抛 AttributeError。
  2. 根因：共享规范化沿用了 Web 字符串输入假设，没有按实际调用边界检查反序列化类型；or 回落还把整数 0 误当缺失。
  3. 测试漏洞：多数校验用例输入字符串；D1 端点验证绕过了已知失败的可选字段，没有把此字段加入稳定回归矩阵。
  4. 修复：先检查 int/str/None，拒绝 bool/其他类型；仅字符串去空白，显式 None 判定后转换与范围校验。
  5. 防护测试：tests/test_cron_timeout_types.py 覆盖实际 Schema 输出、重复规范化、缺省、边界和非法类型；scripts/verify_cron_timeout.py 观察真实请求、DML、调度调用和目标角色页面。
  6. 同类排查：确认现代/旧 API、Web 与共享服务消费链；保持模型/执行器 int/None 契约，无其他字段类型转换或数据迁移。权限反例从误选的全局任务改为其他业务组任务，测试遵守既有全局可见规则，没有改权限策略。
  7. 预防方案：在 D1 harness 的真实 API 请求中永久携带 timeout_sec='5'，不能再靠省略字段使端点回归通过；新增实际 Schema→共享规范化回归与双后端专项。第三方可执行第 10 节命令复现验证，检查 result.json 的零 DML/零调度断言。
