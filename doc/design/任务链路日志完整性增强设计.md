# CronPilot 任务链路日志完整性增强 — 技术设计方案

**状态**：待审阅（已有实现需回溯审查） · **作者**：AI Agent · **日期**：2026-09-07

---

## 一、问题

### 1.1 现状

CronPilot 的**结果层**日志设计完善（`job_log` 表 + Prometheus metrics + 健康聚合），但**过程层**日志存在系统性盲区：

- `cron_do` 被 APScheduler 触发后，在生成 `trace_id` 和开始业务逻辑之间没有任何日志输出
- HTTP 触发请求发出前没有日志，当目标服务 hang 时日志出现长时间空白
- 任务创建和 Scheduler 注册成功路径只写 DB 审计表，不进应用日志文件
- 日志详情页硬编码触发方式为"定时调度"，无法区分手动/定时/一次性
- 详情页不展示实际发出的完整 URL、DNS pinning IP、调度延迟等运维排查关键信息

### 1.2 影响

| 场景 | 现状 | 影响 |
| --- | --- | --- |
| 任务触发后数据库超时 | 日志中无"开始执行"标记 | 无法区分"未触发" vs "卡在 DB" vs "卡在 HTTP" |
| 触发目标 hang 50s | 触发后日志空白直到超时异常 | 无法确认"请求是否已发出" |
| 用户点"立即执行" | 详情页显示"定时调度" | 与实际操作不符，误导运维判断 |
| DNS 解析到内网 IP | 详情页不展示 resolved\_ip | SSRF 审计和网络排查困难 |
| APScheduler 积压 | 只有 Prometheus metric，详情页不展示 | 逐条排查时需跨系统查看 |

## 二、根因

1. **历史演进遗留**：`cron_do` 最初设计时只关注"结果写入"，未设计中间状态可观测性。后续迭代（SSRF 防护、Prometheus、健康聚合）逐层叠加但未回补过程日志。
2. **详情页未与模型同步演进**：`job_log` 模型多次加列（`http_status`、`status`、`started_at` 等），但详情页的"触发方式"字段始终硬编码，未随模型增长而参数化。
3. **应用日志 vs 审计日志边界不清**：`operation_log` 表有完整审计，但运维对"日志文件/ELK"的查询依赖未被覆盖。

## 三、方案

### 3.1 总体架构

按三层增强：**应用日志**（写日志文件/ELK）→ **数据模型**（job\_log 表新增列）→ **详情页展示**（模板读取新列并渲染）。

### 3.2 应用日志增强（4 个 GAP）

| GAP | P1/P2/P3 | 位置 | 日志内容 | 设计考量 |
| --- | --- | --- | --- | --- |
| GAP-2 | P1 | `cron_do()` 入口（`trace_id` 生成后） | `logger.info("cron_do start", extra={event:"cron.start", cron_id, trace_id, trigger_source})` | 位于 `try` 块之前，确保即使后续 DB 查询超时也有起点标记。  使用 `current_app.logger`（Flask 日志，走 `_CronPilotJsonFormatter`）而非模块级 `logging`。  `trigger_source` 来自函数参数默认值 `'schedule'`。 |
| GAP-3 | P1 | `cron_do()` 中 `_http.get/post` 前 | `logger.info("sending trigger request", extra={event:"cron.http_sending", url, method, resolved_ip, timeout_sec})` | 记录 `req_url`（不含注入参数的原始 URL），避免 sign 泄露到日志。  `resolved_ip` 来自 SSRF 校验阶段的 DNS 解析结果。 |
| GAP-1a | P2 | `create_cron()` 成功后 | `_log.info("task created: cron_%s (%s)", cif.id, cif.task_name, extra={event:"cron.created"})` | 使用模块级 `_log`（`logging.getLogger(__name__)`），因为 `cron_service` 不在请求上下文中。 |
| GAP-1b | P2 | `register_cron_job()` 成功后 | `_log.info("scheduler registered: cron_%s trigger=%s", ...)` | 记录 trigger 类型和调度参数（排除 `func`/`args`），便于排查"创建了但未调度"。 |
| GAP-4f | P3 | `toggle_status()` 中 `resume_job/pause_job` 成功后 | `_log.info("scheduler resumed/paused: cron_%s", ...)` | 成功路径记录；失败路径已有 `logger.error`。 |

**设计决策 D-1：日志级别统一为 INFO**  
所有成功路径日志使用 `INFO`。异常/失败路径保持 `WARNING`/`ERROR`。  
**理由**：生产环境日志级别通常设为 INFO，过程日志必须在此级别可见。

**设计决策 D-2：GAP-3 日志记录原始 URL 而非 actual\_url**  
`cron.http_sending` 事件中 `url` 字段为 `req_url`（不含 `cronpilot_sign`）。  
**理由**：签名值属于敏感信息，不应写入日志文件。`actual_url` 含签名仅存入 `job_log` 表。

### 3.3 数据模型增强（4 个新列）

| 列名 | 类型 | Nullable | 用途 | 写入时机 |
| --- | --- | --- | --- | --- |
| `trigger_source` | `VARCHAR(16)` | 是 | 触发来源：`schedule` / `manual` / `one_shot` | `_save_job_log()` 全部 7 个调用点 |
| `actual_url` | `TEXT` | 是 | 实际发出的完整 URL（GET 含注入参数，POST 为原始 URL） | 仅 HTTP 成功/异常路径（2 个调用点） |
| `resolved_ip` | `VARCHAR(45)` | 是 | DNS pinning 解析到的 IP（IPv4 最长 15 / IPv6 最长 45） | 仅 HTTP 成功/异常路径（2 个调用点） |
| `trigger_delay_ms` | `INTEGER` | 是 | APScheduler enqueue → cron\_do 入口的时间差（毫秒） | 全部 7 个调用点 |

**设计决策 D-3：全部 Nullable，旧数据零迁移**  
4 个新列均为 `NULL` 默认，不需要回填历史数据。  
**理由**：`job_log` 表可能有百万级历史记录，`ALTER TABLE ADD COLUMN` 在 SQLite 上是 O(1) 操作（不重写数据页），但 `UPDATE` 回填不可接受。详情页对 `NULL` 值使用 `{% if %}` 条件渲染。

**设计决策 D-4：actual\_url 在 POST 场景记录原始 URL**  
POST 方法时 `trace_id`/`sign` 注入到 JSON body 而非 query string，因此 `actual_url` = `req_url`。  
**理由**：真实请求 URL 不变，参数在 body 中。避免混淆。

**审查发现 R-1：trigger\_delay\_ms 对手动执行语义不准确**  
`_ctx_enqueue_time` 由 `@single_task()` 装饰器在 `cron_do` 入口设置，`t0` 在 `cron_do` 函数体内设置。
对于手动执行（`cron_run_now` → `cron_do(id, trigger_source='manual')`），两者间隔仅微秒级，`trigger_delay_ms` 无实际意义。  
**建议**：在手动执行路径下将 `trigger_delay_ms` 设为 `None`，或在详情页标注"仅定时调度有意义"。  
**当前实现**：未处理此边界，手动执行也会记录一个近零的延迟值。影响为低——显示值为 0ms，不会误导。

**审查发现 R-2：cron\_do 函数签名变更的兼容性**  
`cron_do(cron_id, trigger_source='schedule')` 新增了第二个参数。APScheduler 调用时只传 `args=[cron_id]`，依赖默认值 `'schedule'`——这是安全的。  
但如果未来有任何地方以 `cron_do(cron_id, 'schedule')` 位置参数方式调用，则 `trigger_source` 无法与 `@single_task` 的装饰器参数区分。  
**当前状态**：全仓库只有 2 个调用点（APScheduler `args=[cron_id]` + `cron_run_now` 关键字参数），安全。

### 3.4 详情页展示增强

| 展示项 | 来源 | 条件渲染 | 位置 |
| --- | --- | --- | --- |
| 触发方式（动态） | `jl.trigger_source` → 中文标签映射 | 始终展示（NULL 回退为"定时调度"） | 时间线区 + 元数据区 |
| 调度规则 | `format_cron_expression(cif)` 或 `humanize_schedule(cif)` | `{% if schedule_display %}` | 元数据区 |
| 实际请求 URL | `jl.actual_url` | `{% if jl.actual_url %}` | 请求区（配置 URL 下方） |
| DNS Pinning IP | `jl.resolved_ip` | `{% if jl.resolved_ip %}` | 请求区 |
| 调度延迟 | `jl.trigger_delay_ms` | `{% if jl.trigger_delay_ms is not none and jl.trigger_delay_ms >= 0 %}` | 元数据区 |

### 3.5 cron\_do 函数签名

```
# 变更前
def cron_do(cron_id):

# 变更后
def cron_do(cron_id, trigger_source='schedule'):
    """
    trigger_source 枚举值:
      - 'schedule': APScheduler cron/date/interval 触发（默认）
      - 'manual':   用户点击"立即执行"
      - 'one_shot': 一次性任务（run_date 触发，CuBackgroundScheduler 自动退休）
    """
```

**调用方变更**：  
`cron_run_now` 视图：`cron_do(int(id), trigger_source='manual')`  
APScheduler：`scheduler.add_job(..., args=[cron_id])`（依赖默认值 `'schedule'`，无需改动）  
**注**：一次性任务（`run_date`）目前仍使用默认 `'schedule'`。若要区分，需在 `register_cron_job` 中传入 `args=[cron_id, 'one_shot']` 而非通过关键字参数。此改动属 P3，本轮不做。

### 4.2 明确不做

- **一次性任务自动标记 `one_shot`**：需在 APScheduler `add_job` 的 `args` 中传入，涉及 `register_cron_job` → `CuBackgroundScheduler._process_jobs` 链路改动，范围偏大
- **APScheduler misfire/next\_run\_time 元数据**：需从 `apscheduler_jobs` 表反序列化 trigger 对象，依赖 APScheduler 内部 API，稳定性风险高
- **actual\_url 存储完整 POST body**：JSON body 可能包含敏感业务数据，不应冗余存储在 `job_log`
- **日志级别动态调整**：P3 场景，当前 INFO 固定即可
- **trigger\_delay\_ms 手动执行特殊处理**：影响低，0ms 不会误导，留作后续优化

## 七、风险

| 风险 | 概率 | 影响 | 缓解 |
| --- | --- | --- | --- |
| `cron_do` 签名变更破坏 APScheduler 调用 | 低 | 高 | `trigger_source` 有默认值 `'schedule'`；APScheduler 使用 `args=[cron_id]` 位置参数仅传第一个 |
| 日志量增长 | 中 | 低 | 每次执行增加 2 条 INFO（≈200 字节/条），对于秒级触发的高频任务约 17MB/天，在 TimedRotatingFileHandler 7 天周期内可控 |
| `actual_url` 存储 TEXT 影响 DB 体积 | 中 | 低 | URL 通常 <500 字节；仅 HTTP 路径写入，预检失败路径为 NULL |
| 旧 `to_json()` 方法引用不存在的属性 | 已确认 | 低 | 预存问题（`self.job_id`, `self.remark`, `self.traces`）。本轮不改——属于 `to_json` 死代码，无调用方 |

**安全审查：actual\_url 含 cronpilot\_sign（已修复 · 2026-09-07）**  
`actual_url` 在 GET 场景原始 URL 包含 `cronpilot_sign` 值。该签名基于 `api_key`（`conf.ini`），泄露可能导致请求伪造。  
**原缓解声明（已废弃）**：原文称"`job_log` 表仅管理员可访问"——**此描述不准确**，详情页路由使用 `@require_permission('log:read')`，Operator 角色亦可访问。  
**实际修复**：`crons.py` 在写入 `_save_job_log` 前通过 `re.sub(r'(cronpilot_sign=)[^&]+', r'\1***', _actual_url)` 脱敏，DB 中 `actual_url` 存储形如 `...&cronpilot_sign=***`，日志文件中的 `cron.http_sending` 事件同样不含签名值。

## 九、优化评估总结（2026-09-07）

**总体结论：有条件通过**  
该方案在可观测性目标、分层设计和兼容性策略上方向正确，具备明确的运维价值与落地必要性。  
在推进发布前，建议优先修正 2 项关键偏差（见 E-1 / E-2），以确保安全边界描述与指标语义与实际实现一致。

### 9.1 合理性评估

- **必要性高**：当前过程层日志盲区会直接抬高故障定位成本，补齐“开始执行/发包前/触发来源”链路具备高收益。
- **方案分层合理**：应用日志 + `job_log` 扩展 + 详情页渲染形成观测闭环，改动边界清晰。
- **兼容策略合理**：新增列全部 Nullable、历史数据零回填，符合大表低风险演进原则。
- **验收路径完整**：自动化与手动验收步骤齐全，可支撑发布前回归。

### 9.4 同期发现的额外 Bug（已修复 · 2026-09-07）

**BUG-FIX-1：内层 except 路径 \_actual\_url NameError**  
`crons.py` 内层 `try:` 块中，若签名计算或 URL 参数解析在 `_actual_url` 赋值前抛异常，`except` 处理器引用 `_actual_url` 会触发 `NameError`，掩盖真实错误且日志丢失。  
**修复**：在 `try:` 块前添加 `_actual_url = None` 初始化（1 行）。防护测试：`TestActualUrlNameErrorGuard`。

**BUG-FIX-2：JobLog.to\_json() 引用不存在的字段**  
`to_json()` 方法引用了 `self.job_id`、`self.remark`、`self.traces`（均不存在于模型），任何调用者都会触发 `AttributeError`。  
**修复**：删除三个无效字段引用，保留有效字段（id / content / status / create\_time）。防护测试：`TestToJsonNoAttributeError`。
