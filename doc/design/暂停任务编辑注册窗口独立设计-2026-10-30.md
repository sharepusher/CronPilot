## 1. 问题、示例与证据

一个任务当前已暂停。管理员只修改任务说明并保存后，当前 Web 服务先提交数据库，调用 register\_cron\_job 替换调度项，再调用 pause\_job。第一次调用到第二次调用之间，替换后的任务可能具有下一执行时间；如果调度器正好扫描到期任务，可能被提交执行。此前真实 APScheduler MemoryJobStore 实验验证过省略 next\_run\_time 与显式 None 的差异，但没有向真实目标发出请求；不是生产事故或发生频率证据。

代码依据：`app/services/cron_edit_concurrency.py` 在提交后先 register 再 pause，暂停失败返回 saved\_scheduler\_error；`app/services/cron_service.py` 的共享 update\_cron\_with\_outcome 也先注册再暂停，但暂停异常仅记录 warning 后继续。当前 create\_cron 为运行状态注册；reschedule\_orphan\_task 使用单独 add\_job，不能仅因名称类似就假设其暂停语义正确，须作为关联入口审计。`cron_check` 主要比对 job ID、扫描 ghost，不能证明 trigger 和暂停状态一致。

## 2. 根因与边界

目标状态与调度注册分为两次操作，第一步未指定暂停。两操作不可视为一个不可中断动作；暂停失败或进程退出时，第二步可能未发生。问题还受到数据库提交与 JobStore 操作不同步、编辑和启停交错、不同进程并行写 JobStore 的影响。

**准确边界：**直接注册为暂停仅消除这次注册主动制造的可运行窗口。它不能撤销已提交到执行器的任务、已开始的 HTTP 请求、已有调度项在替换前的触发；也不能阻止并发启停或两次编辑的调度操作以相反顺序到达，不能保证崩溃恢复或最终一致。

## 3. 方案：有效变化驱动调度副作用

Web 必须根据写事务内经原始基线、当前 DB 值和用户输入三方比较后的**实际有效变化**判断，而不是仅凭提交的字段或页面 dirty 标志；共享/API 入口须依据各自的完整目标、缺省语义和保存前后实际值计算同等有效变化，不能假装 API 有 Web 原始基线。最终状态明确为暂停或运行，已下线拒绝编辑。只有调度规则或明确运行目标有有效变化时，才需要更新 JobStore。

| 有效变化 | DB 与调度器处理 |
| --- | --- |
| 说明 task\_keyword、组 scope/group、标签 | 按现有授权与差异保存数据库；不注册、不修改、不暂停/恢复调度项。 |
| 触发 URL、请求方式/内容、timeout | 保存数据库；不改调度项。cron\_do 运行时按任务 ID 查询这些字段；已读取旧值的执行仍可能使用旧配置，不承诺影响执行中的请求。 |
| run\_date、day\_of\_week、day、hour、minute、second | 使用已有规范化规则比较有效调度单元，不自行推导 cron 表达式等价。真实变化则需同步新 trigger；目标暂停时全程不得由本次操作产生可运行状态。 |
| 明确恢复命令 | 数据库状态实际从暂停变为运行才产生运行目标变化；结合是否同时修改 trigger 明确执行一次适当的调度应用。已运行且规则未变的等价恢复不应重复应用。 |
| 没有任何有效变化 | 零任务写入、零调度操作及零成功变更日志；前端预检不替代服务端判断。 |
| 调度无关变更时 JobStore 已缺失或错误 | 不因普通编辑隐式创建或修复；发现与恢复另设计。调度器不可用本身不能让与其无关的配置修改因调度调用失败。 |

多个变化一起提交时，先判断是否包含有效调度/状态变化；只存在无关变化即不调用调度器，混合变化则在 DB 成功后按最终目标应用一次。配置提交后的调度失败不等于 DB 回滚；并发启停、旧操作后到达及持久恢复不是 edit\_revision 单独能解决的问题。

## 3.1 调度规则变化时：候选方案与实现证据

**A 修改已有调度项：**保留现有 job，通过底层 APScheduler 的单次 modify\_job 一并设置新 trigger 与 `next_run_time=None`。已读底层 `schedulers/base.py:modify_job`：同一 jobstore 锁中执行属性修改及一次 update\_job；但项目对外使用的 Flask-APScheduler `scheduler.py:modify_job` 一旦 changes 含 trigger，会先执行 reschedule\_job，再执行 modify\_job，而底层 reschedule\_job 会计算非空下一时间。因此**不能直接使用当前包装器的 modify\_job(trigger=..., next\_run\_time=None) 声称单次原子暂停更新**。调用底层私有对象或增加封装的稳定性、锁和兼容性须实验及专门评审，不预先授权绕过包装器。job 不存在时必须处理 JobLookupError，不得静默视作已更新。

**B 暂停替换注册：**按已核实的 add\_job(..., replace\_existing=True, next\_run\_time=None) 以暂停状态替换；已读 Flask 包装器和 APScheduler 源码确认 None 会保留为暂停，缺省才计算首次时间。此操作可能改变 job 元信息、下一运行时机或持久状态，必须在实际 JobStore 实验；缺失 job 时它会创建新 job，是否允许这种隐式修复须另定，不在本稿假装已经确认。两种方法均不能撤销已进入执行器的任务，也不能独立解决跨进程并发写入和结果未知。

**决策门槛：**W0 对 A/B 做同样的 SQLite/MySQL SQLAlchemyJobStore、实际自定义扫描器、cron/date trigger、暂停后重启、显式恢复、原 job 缺失、持久化故障与并发交错实验；按正确性、对现有 job 的影响、维护性和调用接口稳定性选型，并记录代码/API依据。当前不预选实现、不宣称任一候选已验证；结果影响方案时修订文档并再次等待用户明确确认。

rev.3 决议：A/B 均未解决外部写入顺序，W0 已触发停止条件。先实施经用户另行确认的调度无关有效变化纵向切片；涉及规则或运行目标的应用暂不从候选中挑一种直接实施，先完成第 10 节协调设计及验证。

## 7. 风险、性能及回退

调度无关编辑将避免不必要的 JobStore 写入和可能的暂停调用，但不承诺吞吐收益；实际性能未测量。多进程/并发写者、错误回执、时间到期与已有执行是主要边界。

回退代码前先停止相关新旧写进程，按部署的 JobStore 和 DB 备份策略检查任务状态并记录；旧逻辑恢复后窗口随之恢复。已提交配置或已执行请求不能自动撤销。问题③持久恢复和问题④审计强原子性另行设计。

## 9. W0 实验进展（2026-10-30）

用户确认后运行 `.venv-py311/bin/python scripts/verify_paused_jobstore_w0.py`；使用本项目 CuBackgroundScheduler、SQLAlchemyJobStore、临时 SQLite 文件及新建随机 MySQL 测试库，全部调度器全局暂停、不执行 job，结束清理隔离库。结果见 [机器可读证据](../qa/evidence/paused-jobstore-w0-2026-10-30/result.json)。

- SQLite 与 MySQL 均观察到：cron/date 暂停任务以显式 next\_run\_time=None 替换后保持暂停，重启保持暂停，明确恢复后下一时间非空。
- Flask 包装器 modify\_job(trigger=..., next\_run\_time=None) 触发两个修改事件：先可运行，再暂停；底层单次 modify\_job 在该实验下保持暂停；缺失 job 返回 JobLookupError。底层调用是否适合作为稳定生产接口仍未选型。
- 故障注入将 JobStore update 完成后抛异常，重读确认新 trigger 已保存：调用异常不能推断操作未生效。
- 两个独立调度器共享同一 JobStore，旧暂停操作在另一个调度器恢复之后写入，结果恢复被覆盖。该实验真实验证了指定的顺序交错，未引入业务 DB 状态或同时线程竞争，也不等同于生产发生率。

**停止条件触发：**并发启停与调度应用可能乱序，单靠直接暂停替换或底层单次修改无法提供与数据库状态一致的完整保证。W0 尚未完成：运行中扫描栅栏、跨进程竞争、所有写入口及 API 错误返回仍需校准；必须明确本批保证范围与协调方案，修订设计并再次确认后才能实施。既有第 8 节“尚未运行双后端实验”为 rev.2 初稿历史状态，以本节为准。

## 10. 并发写入协调：待独立设计的约束

**典型交错：**甲编辑基于“暂停”生成调度操作 A；乙随后恢复任务并应用运行操作 B；如果 A 晚于 B 到达 JobStore，最终调度项会被旧 A 再次暂停。反向交错也可能让旧运行操作晚于暂停到达。数据库 edit\_revision 可保护业务行，但 JobStore 没有用它作为写入条件，不能单靠数据库比较保证旧调度操作不落地。

**推荐设计方向：**与 [P0-C 任务调度最终一致性设计](P0-C-任务调度最终一致性设计-2026-10.html) 对齐：数据库记录期望状态和可核验同步状态，所有会写相同 job 的入口接受同一套跨进程协调；所有权期间读取最新期望、应用、读取实际状态并按期望版本条件记录结果，异常或崩溃后由受控对账恢复。这是待验证方向，不代表现有代码已有持久状态、串行器或恢复服务，也不得把 READY 当作永久不漂移的保证。

**关键限制：**仅在调用前后检查版本、使用进程内锁或仅依靠本机 scheduler.lock 无法阻止不同进程或机器中的过期 JobStore 写入；锁超时或进程暂停后恢复时，普通租约不自动具备 fencing 能力。若 JobStore 不接受版本条件写，必须证明不会存在重叠的旧写者，或以可恢复对账纠正，并说明收敛前风险；不能用 DB 条件回写冒充阻止外部写入。

**必须覆盖的写者：**Web/API 编辑与创建、启停、手动下线、孤儿重调度、自定义调度器一次性/异常下线、启动/周期对账及可能的直接工具；逐一标明是否写 JobStore、业务状态与锁顺序，无法统一的入口不得宣称全局协调。当前 `scheduler.lock` 位于调度扫描路径，只能说明该路径存在本地文件锁，未证明覆盖所有 Web/API 写者或跨主机共享。

**故障与停止条件：**DB commit 不确定时不盲目应用；JobStore 应用成功但响应丢失时读回实际值，不能重复假设未写；等待锁超时或持有者崩溃时明确失败或待核实，不能伪报同步成功。必须验证 SQLite/MySQL、锁释放、双进程真实交错、崩溃/锁失效、重启读回与对账、已有执行不可撤销；若部署拓扑和写者无法强制遵循协议，则 W2 保持停止。

## 11. W1 实施记录与复盘（2026-10-30）

1. 定位：Web 与共享更新对任意真实变更均重注册调度项，说明、URL 等修改也引入暂停窗口与 JobStore 失败风险。
2. 根因：以“任务有变化”而非“调度规则或运行目标有变化”决定调度副作用；执行时从 DB 加载的字段未与 trigger 字段分开。
3. 测试漏洞：原测试将说明修改后调用调度器视为期望，缺少真实非调度变化、调度器不可用和调度规则变化的成对反例。
4. 修复：Web 基于三方比较后的 effective 单元判断；共享/API 在模型赋值前比较规范化调度字段和有效恢复意图。其他变化保留原验证、写库和日志流程；调度相关变化保持既有路径。
5. 防护：`tests.test_cron_edit_concurrency` 与 `tests.test_cron_edit_noop` 验证说明、URL、请求、超时、标签、组及混合/恢复变化、调度器不可用和 API 共享路径；真实浏览器隔离库结果见 [验收结果](../qa/evidence/task-edit-w1-2026-10-30/result.json)。
6. 同类排查：Web 与 API/共享路径均纳入；创建、启停、下线、孤儿重调度及调度相关编辑属于其他语义，本批未改，W2 仍需统一协调。
7. 预防：将字段级与混合变化测试纳入 unittest discover；浏览器验收脚本同时检查数据库保存及不存在的 job 不被隐式创建。命令：`python -m unittest tests.test_cron_edit_noop tests.test_cron_edit_concurrency tests.test_cron_edit_status -q`。
