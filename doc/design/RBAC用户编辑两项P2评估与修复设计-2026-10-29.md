## 1. 结论与风险分级

**P2-A 是实际功能缺陷：**具体组原样保存会多发请求；全局 admin 只改为具体组时却被误判 no-op，权限收窄意图没有提交。后端没有授予超范围权限，但管理员以为操作未变化/无法保存，已有全局授权会继续保留，因此应优先修复。

**P2-B 是解析契约与审计展示可信度问题：**代码和现有测试允许 partial，但父 D6c 明确禁止部分猜测渲染。当前自动转义仍在，未发现由此造成的 XSS 或读权限绕过；不据此升级为 P1 或声称历史审计被篡改。P2-B 在 P2-A 后独立验收。

## 2. P2-A 根因、证据与影响

HTML 的 `name="group_ids"` 在 select 上，`selected` 在 option 上。当前 `[name="group_ids"]:selected` 要求同一节点同时满足两者，所以读不到多选框的 option；只有锁定业务组的 hidden 分支可能正确。读到的组集合反复变成空数组，比较与真正序列化的请求脱节。

```
真实 Chrome + 当前模板脚本 + common-redesign.js，隔离 DOM 实测：
specific_noop          → POST=1，本应 0
global_to_specific     → POST=0，误提示“未检测到变更”，本应 1
global_missing_selection → POST=0，误判等价于全局，本应交服务校验
global_noop            → POST=0，此例碰巧正确
```

**同源边界：**即使只改成正确 option 选择器，如果仍把“没有选项”归一化为空数组，就无法区分它和明确选中 `__ALL__` 的全局语义。当前后端对非种子 admin 的无组选项会拒绝；前端不应提前把非法输入伪装成合法 no-op。不是为新增规则，而是恢复既有 D3/Scope 契约。

**测试为何漏掉：**静态字符串用例只证明 preflight 存在；后端 no-op 测试绕过了真实 DOM；若浏览器只用单组锁定 hidden 或全局原样保存，两者均绕开失败分支。必须同时覆盖 select/hidden 与空/全局/具体集合。

## 3. P2-A 推荐方案

1. 保留现有表单和 marker，不增加字段。读取当前表单中**启用且参与提交**的 `select[name="group_ids"]` 的 `.val()` 数组；无 select 时读取锁定 `input[type="hidden"][name="group_ids"]`。两种来源按现有 DOM 互斥，遇到多来源/多 select 不做 no-op 优化。
2. 读取结果分成 **合法全局、合法具体组、不可可靠比较**。只有显式且唯一的 `__ALL__`、角色为 admin，才映射成全局规范值 []。具体组转为整数、去重、升序；不可把非法字符串用 parseInt 部分解析，也不可静默忽略坏值后再比较。
3. 无选择、混合 marker、空/非法 ID、表单来源冲突均标为“不可可靠比较”，不得调用本地 no-op 短路。原请求仍照常序列化，服务端返回既有错误；不在客户端猜授权或修正选择。种子目标空组特例交回后端判断，宁可多一次无副作用请求，也不扩大前端特权推断。
4. 只在全部待比较字段可可靠归一化、且与原始快照相等时，阻止 POST 并提示无变化。有效组变化让公共 Ajax 正常提交；本地辅助状态不增加到请求 payload。
5. 邮箱确认、原生 POST、P1 token 回显、服务端差异/Scope/事务不变。修复后应以真实后端检查授权变更仅 bump 一次、Token 重签、成功审计 1 行；重复 no-op 无上述副作用。

具体整数转换可使用既有 ES5 能力和严格字符串检查，不依赖当前旧 jQuery 环境没有的现代接口；本次不升级 jQuery、不重构公共 Ajax、不引入前端框架。选择器可达性已通过模板实际节点核对。

## 4. P2-B 根因与运行证据

`format_user_update_audit_detail()` 先忽略未知 changes 键，继续渲染已知键，再标 partial；未验证顶层键集合。版本用 `== 1` 比较，Python 中 True 与 1 相等；值函数把 int 转成 str，所以错误邮箱数值被展示成“42”。测试又明确期待 partial，与实现自洽而偏离父设计。

```
当前解析器直接运行：
已知 nickname + future_field → partial，继续展示 nickname
合法 v1 + 顶层 future_metadata → ok
schema_version=true         → ok
email.before=42             → ok，展示字符串“42”
```

已读取 writer 的实际建模：顶层为 schema\_version/changes，仅邮箱清空时写 reason；role 是字符串，group\_ids 是排序整数列表，资料值是字符串或 null。以上异常不是当前合法 writer 应生成的数据。禁止为“兼容未知未来结构”继续猜测它们的语义。

## 5. P2-B 推荐方案：恢复整条 v1 验证

| 层次 | 冻结规则 | 失败行为 |
| --- | --- | --- |
| 历史空详情 | 仅 DB None/空字符串视为 legacy；不将任意 falsy 类型一概当空详情。 | legacy 保持原通用 resource 展示。 |
| 顶层对象与版本 | 必须 JSON object；schema\_version 类型必须恰为 int，值为 1。bool/float/string 不能冒充版本 1。未知整数版本为 unsupported。 | 错误类型 invalid；未知整数版本 unsupported。两者 changes=[]、reason=None。 |
| 顶层键 | 必有 schema\_version、changes；可选 reason。无其他键，不能把未知顶层元数据静默忽略。 | 整条 invalid，不尝试展示已知片段。 |
| changes | 非空 object，键严格属于 email/nickname/job\_title/role/group\_ids；每项恰有 before、after。 | 未知或缺/多键均整条 invalid；移除 partial 展示路径。 |
| 资料值 | email/nickname/job\_title 只允许字符串或 null，禁止整数/布尔/容器自动转字符串。保留现有空值语义化展示与自动转义。 | 任一字段类型错误，整条 invalid。审计读取不重新执行邮箱格式或岗位枚举等当前业务表单校验，避免把历史合法变更误判。 |
| 授权值 | role 前后值只允许字符串；group\_ids 前后值为去重、升序整数列表，排除 bool。不把 form marker 字符串当 DB 审计值。 | 类型/结构错误整条 invalid。不重新用当前角色枚举否定历史文本；不凭空补未记录的 role 来解释组范围。 |
| reason | 仅 email 非 null→null 时存在，且 trim 后 1–500 字；该变化缺 reason 也非法。非清空事件带 reason 与当前 v1 writer 契约不符。 | 整条 invalid；不显示理由或部分字段。有效理由继续普通 Jinja 自动转义，不使用 safe/innerHTML。 |

**渲染：**合法整条 v1 才返回 ok；其余使用已有 legacy/invalid/unsupported。模板只在 ok 显示变化和理由；保留原六列表格的基础事件，invalid/unsupported 使用已有固定提示。数据库原 detail、审计保留期、action 命名、查询和 RBAC 不变；不做历史数据清洗、不新增审计 schema\_version=2。

**扩展边界：**未来需要新字段时先定义新版本与 reader 分支，再升级 writer；不能在固定 v1 中加入任意键并要求旧 reader 猜测。若未来业务选择“部分兼容”，必须另行修改 D6c 并获确认，本次不选择它。

## 6. 方案取舍与专业性

| 候选 | 优点 | 不足/判断 |
| --- | --- | --- |
| 仅修 option 选择器 | diff 最小。 | 不能区分“无选择”与显式全局；仍可能伪 no-op，未完整解决语义缺口。 |
| 取消全部前端 no-op | 避免吞掉真实变更。 | 违背父设计“正常 no-op 零 POST”的收益；只可作为临时止损，不是推荐最终方案。 |
| 正确读取 + 可比较状态 | 保持有效集合归一化，非法输入交服务端；不改 payload 或权限。 | **P2-A 推荐。**增加少量状态分支，有浏览器矩阵可验证，复杂度与风险匹配。 |
| 修改父 D6c 接受 partial | 贴合当前代码，未来字段可局部展示。 | 改变已确认的整体解释契约，可能被误认为完整审计；本轮没有新产品理由支持这种变更。 |
| 严格 v1 整条验证、固定回退 | 与父设计一致，易测试、可解释；异常记录不影响整页。 | **P2-B 推荐。**异常/未来数据的详细字段会隐藏，但原记录完整保留、通用事件仍可查，是明确取舍。 |
| 新增 JSON schema 依赖/通用解析框架 | 可集中表达复杂 schema。 | 仅固定五字段，现有纯函数足够；增加依赖与全局抽象不合算。 |

**专业性：**区分客户端交互优化与服务端授权、完整审计事件与不可靠字段片段；异常既不误显成功，也不冒称攻击。冻结了失败路径、历史保留、兼容边界和独立批次，而不以“当前单测全绿”证明契约正确。

**合理性：**P2-A 是少量 DOM 读取和固定字段比较；P2-B 是已有 JSON 解析后的 schema 检查，不增加 DB 查询；有效记录只遍历五个字段及已有组列表。实际成本主要是补浏览器矩阵，远低于改权限模型、引入新依赖或迁移数据。

## 9. 验收矩阵

### 9.1 P2-A：必须是真实 DOM 与 POST 观测

| 场景 | 预期 |
| --- | --- |
| 锁定单组 hidden、具体组单/多选原样提交、选择顺序变化 | 合法 no-op 0 POST；DB/审计/版本/Token/缓存零副作用。 |
| 全局 admin 原样 \_\_ALL\_\_ | 0 POST；空数组只来自明确 marker。 |
| 全局→具体、具体→全局、具体集合增加/移除 | 1 POST；与后端真实请求一致；权限仅一次 bump、Token 重签、成功审计一次；再次原样 0 POST。 |
| 全局 admin 清空全部选择、混合 marker、非法 ID/来源冲突 | 不得提示合法 no-op；原请求进服务端校验，非法输入零业务变化。种子空 Scope 既有特例由服务端决定。 |
| Viewer/Operator 角色选全局、按组管理员企图授予越界/全局 | 既有角色/Scope 拒绝仍成立，不因前端比较扩大权限。 |
| 邮箱清空确认取消、理由无效、成功、原生回退恢复 JS | 与组读取同时运行不回归 P1；确认字段唯一，原 token 连续。键盘兼容不凭模拟声称全部真实输入行为已覆盖。 |

## 10. 风险、回滚与防再发

- 严格 reader 会隐藏过去被宽松解析的异常细节；保留原事件和原始 DB，不迁移不删除。若合法 writer 样本被拒绝，停止 B 批次并修正 schema 判断，不能直接放回 partial。
- 客户端“不可比较”多发一次请求属于有意保守退让，不把它当客户端权限拒绝；后端已有校验负责错误。
- 前端若需紧急止损，可暂不做本地 no-op 优化，不能恢复吞掉真实授权变化；这会偏离零 POST 指标，必须明确记录。
- reader 回滚只能退回基础 resource 展示，而非无声恢复未知结构的部分解释。已生成审计和 P1 修复不回滚。
- 永久预防：在浏览器用例冻结 select/hidden/全局/无选择的 POST 数量与请求集合；在 tests/test\_user\_edit\_change\_set.py 冻结整条错误原子回退及真实 writer 兼容性。每个新增 detail 版本必须同时提供 writer+reader+异常矩阵。
- 实施后的七项复盘须覆盖定位、行为根因、测试漏洞、修复、实际防护用例、同类排查和新增预防措施；不能把本设计预期当成已修复结果。
