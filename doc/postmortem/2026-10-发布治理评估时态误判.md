# 发布治理评估时态误判复盘

日期：2026-10-27 · 范围：QA 评估文档，不涉及业务代码或已发布 tag。

## 1. Bug 定位

`doc/qa/当前项目全面专业性Bugbot评估-2026-10-27.html` 初稿将早先“4.1.1 发布就绪度评估”中的历史阻断写成当前 P1 风险，未先验证当前 tag 与版本门禁。

## 2. 根因

评估将一份时点性 QA 结论当作当前事实，未先建立“tag → README/路线图 → Release Notes → 自动门禁”的最新证据链。

## 3. 测试漏洞

文档完整性/链接门禁只验证注册与可达性，不验证 QA 文本中的状态断言是否与当前 Git 状态一致。

## 4. 修复

已重新执行 `check_version_consistency.py --check` 并核实 `v4.1.0`、`v4.1.1` 注释 tag；评估已改为“结构闭环、文案存在 P2 时态问题”。

## 5. 防护测试

本次直接证据为 22 个 tag 的版本一致性门禁通过；后续评估必须在结论前记录该命令的输出。

## 6. 同类排查

同一 4.1.1 Release Notes 节仍有一条“发布 4.1.0 前完成 MySQL 演练”的过期 blocker 文案；它不影响结构化版本门禁，但会误导人工阅读。

## 7. 预防方案

在 `scripts/check_version_consistency.py` 增加已发布版本语义检查：对每个已发布版本节扫描指向更早已发布版本的 “before publishing vX.Y.Z” blocker 文案；配套单元测试置于 `tests/test_check_version_consistency.py`。在该门禁落地前，任何“当前发布阻断”评估须先列出 tag 和该脚本的当次输出。

```
.venv-py311/bin/python scripts/check_version_consistency.py --check
# ✓ 版本一致性检查通过（22 个 tag，全部在 README/路线图/RELEASE_NOTES 中找到）。
```
