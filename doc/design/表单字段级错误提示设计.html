表单字段级错误提示设计

版本 rev.6 · 2026-09-01 · 编号 OPT-P1-14

1. 问题

1.1 用户痛点

当前 Redesign 表单（以任务新建/编辑页为主）的验证错误反馈采用全局 Toast + 字段高亮模式：

  • 错误文案：CpToast 固定在视口右上角（position: fixed; top: 16px; right: 16px），4 秒后自动消失
  • 字段高亮：出错字段添加 tf-field-error（红色边框 + 标签变红）或 tf-section-error（仅标签变红）
  • 滚动定位：scrollIntoView({ behavior: 'smooth', block: 'center' })

核心缺陷：错误文案（"任务名称不能为空"）出现在视口右上角，出错字段在表单中部或底部。用户必须「向上看 Toast → 记住错误内容 → 向下看高亮字段 → 理解并修正」，视觉路径断裂。

1.2 格式塔心理学：接近性原则（Law of Proximity）

「空间上相近的元素被感知为同一组」——错误说明文案应与引发错误的输入控件紧密相邻，而非分散在页面不同区域。当前设计违反了这一基本原则。

缺失：表单页面（非模态框）没有字段旁内联错误文案机制。

2. 根因

  1. 历史架构：v1 使用 jQuery alert() 报错，Redesign 升级为 Toast 是进步但未走完最后一步
  2. 通用框架缺少字段级文案规范：common-redesign.js 的 AJAX handler 只处理 field 键用于高亮，不处理消息文案的就近显示
  3. 后端契约未区分：web_api_return(code=1, msg=err, data={'field': field}) 中 msg 同时用于 Toast 文案和（缺失的）字段级文案

3. 业界模式对比

模式 代表 机制 优点 缺点 适合场景
A · 字段下方内联文案 Material Design、Ant Design、Bootstrap 5、GitHub 在 input 下方显示红色小字 空间关联最强；持久可见；无遮挡；业界最通用 可能导致布局偏移（可通过预留空间解决） 表单页（CronPilot 主战场）
B · 全局 Toast Slack、部分后台管理系统 固定位置弹出通知 实现简单；不影响布局 视觉路径断裂；自动消失后信息丢失 非表单操作（删除确认、权限变更等）
C · Summary + Inline 双层 W3C WCAG 推荐、gov.uk 页面顶部错误摘要 + 字段旁内联 最佳无障碍；适合超长表单 实现复杂；CronPilot 表单字段数 ≤15，性价比低 超长表单 / 政务/无障碍要求高
D · Tooltip/Popover 部分 jQuery 插件 字段旁浮动气泡 不影响布局 可被遮挡；移动端体验差；不够持久 不推荐

4. 方案：A · 字段下方内联文案（推荐）

4.1 设计原则

  1. 就近显示：错误文案紧跟在出错字段的 input/select 下方，替代 hint 位置
  2. 保留 Toast 作为降级：当后端未返回 field 键时（通用错误），仍用 Toast 全局提示
  3. 互斥显示：有 field 时 → 内联文案 + 高亮 + 滚动，不再 Toast；无 field 时 → 仅 Toast
  4. 自动清除：用户修改出错字段内容时，自动清除该字段的错误状态和文案，恢复原始 hint
  5. Section 处理：对 cron_div 等区段，错误文案使用 insertAfter(label) 插入在区段标签与子字段网格之间
  6. 无障碍：.tf-error-msg 添加 role="alert" 属性，使屏幕阅读器自动朗读错误信息（WCAG 最佳实践，参考 React Hook Form / Formik）
  7. 禁用原生校验：凡启用 .tf-error-msg 内联文案的表单，必须添加 novalidate 属性。JS 中 checkValidity/reportValidity 对 novalidate 表单自动跳过。原因：浏览器原生校验气泡（如「请填写此字段」）样式不可控，与自定义内联文案冲突

4.1.1 Hint 隐藏与恢复策略

错误文案与 hint 不能同时显示（视觉混乱）。策略：

  1. 显示错误时：找到 .tf-hint 元素，style.display = 'none' 隐藏，同时在该位置插入 .tf-error-msg
  2. 清除错误时：移除 .tf-error-msg DOM 元素，恢复 .tf-hint 的 display
  3. Section 容器（如 cron_div）：无直属 .tf-hint，.tf-error-msg 直接 insertAfter 于 .tf-label 后

4.1.2 Section 插入位置

对于 #cron_div 等区段容器，DOM 结构为：

<div id="cron_div" data-field="cron_div">
  <label class="tf-label">Cron 表达式 *</label>
  <!-- ← .tf-error-msg 插入此处 -->
  <div class="tf-cron-grid">...子字段...</div>
</div>

JS 实现须使用 $el.find('> .tf-label').after(errorMsg)，而非简单 append。

4.2 交互流程

用户提交表单
  └→ 后端返回 { errcode: 1, errmsg: "Cron 表达式不能全部为空", data: { field: "cron_div" } }
      └→ JS 收到响应
          ├→ 有 field key?
          │   ├→ YES: ① 清除所有旧错误状态
          │   │       ② 找到 [data-field] 或 #id 元素
          │   │       ③ 添加 tf-field-error / tf-section-error
          │   │       ④ 在目标元素内插入/更新 .tf-error-msg 内联文案
          │   │       ⑤ scrollIntoView
          │   │       ⑥ 不弹 Toast
          │   └→ NO:  ① CpToast.error(errmsg)（保持现有行为）
          └→ 用户修改该字段 → input 事件 → 清除该字段的 error 状态 + 移除 .tf-error-msg

5.2 不做什么

  • 不修改后端 API 契约：web_api_return(code, msg, data={'field': ...}) 保持不变
  • 不改模态框错误显示：模态框（tags、retire、deactivate）已有各自的 .tg-err / .cp-modal-err 机制，本轮不统一
  • 不新增模板 DOM：.tf-error-msg 由 JS 动态创建/销毁，不需要在模板中预埋
  • 不改 HTML5 原生校验：checkValidity() / reportValidity() 保持，内联文案仅处理 AJAX 服务端校验

8. 风险

风险影响缓解
内联文案导致布局偏移 低：.tf-error-msg 高度约 20px，偏移可接受 使用 min-height 预留可选；当前表单间距足够
其他 js-ajax-form 表单（非 task_form）受影响 低：目前只有 task_form 有 data-field 标注；其他表单走 Toast 降级 逻辑为「有 field → 找元素 → 找到才插入；找不到 → Toast 降级」
CpToast.success 被误取消 中：成功提示消失 仅在 errcode !== 0 && field 时取消 Toast；success 路径不变
Vue CronFormValidator 冲突 中：#cron-form-validator 已有 .cron-field-inline-error（URL/JSON 客户端校验），服务端返回 field=cron_div 时可能出现双重错误信息 Vue 仅处理 URL/JSON 客户端校验；cron 格式由后端校验。两者字段不重叠（Vue 管 URL/JSON 格式，后端管 cron 表达式非空/格式），不会同时触发
scrollIntoView + fadeIn 时序 低：先插入 DOM 再触发 scrollIntoView 时，fadeIn 动画可能在滚动完成前开始，用户短暂看到空位置 CSS fadeIn 仅 0.15s，肉眼几乎不可察；且 .tf-error-msg 在 DOM 中已有文本内容，仅透明度过渡

10. Phase 2 — 全 RBAC 表单覆盖设计

10.1 问题

Phase 1 仅覆盖了 task_form.html，审计中识别的其余 7 张 A 类表单仍使用全局 Toast 反馈字段级校验错误。用户在修改密码、管理用户/组、下线任务、停用用户、编辑个人资料时，仍面临「错误文案与出错字段空间分离」的体验问题。

10.2 方案概览

基于 Phase 1 已验证的内联文案架构，将覆盖范围扩展到全部 RBAC 表单。核心工作分为四层：

① 基础设施提升：CSS 共享化

变更原因风险评估
.tf-error-msg 从 redesign-pages.css（.cp-page-task-form 作用域下）移入 redesign-components.css（全局） Phase 1 样式限定在 task-form 页面作用域下，其他页面的 .tf-error-msg 无样式。按 CSS 归属决策树，跨页面复用的 UI 组件应放在 redesign-components.css 低风险：选择器特异性降低（从 .cp-page-task-form .tf-error-msg 降为 .tf-error-msg），但该类仅由 JS 动态创建，无意外匹配可能

② 基础设施提升：JS hint 选择器泛化

变更原因风险评估
hint 选择器从 .tf-hint 改为 [class*="-hint"]（CSS attribute 选择器通配） 各 RBAC 页面使用不同前缀：cr-hint（cron_retire）、pw-hint（password）、uf-hint（user_form）、gf-hint（group_form）、usa-hint（set_active）。统一查找避免逐页定制 低风险：[class*="-hint"] 匹配所有含 -hint 的类。审计确认无误匹配（如 kbd-hint 在非表单区域，不包含在 [data-field] 容器内）
task_form.html 的 input 事件 hint 恢复从 classList.contains('tf-hint') 改为正则 /\b\w+-hint\b/ 一致性：与 common-redesign.js 的泛化逻辑对齐 极低：仅影响清除时的 hint 恢复识别，正则语义等价于原有判断

③ 后端 field key 返回

Phase 1 中 task_form 的后端已返回 data.field。Phase 2 需要为 RBAC 表单补充：

表单后端策略field key 映射规则合理性分析
cron_retire 在视图层 views.py 直接 data={'field': 'reason'} 该表单仅一个输入字段（reason），无歧义 合理：最小 diff，不改服务层
users_set_active 视图层根据错误消息关键词（'缘由'）匹配 → field='reason' 该表单仅一个输入字段 合理：关键词匹配可靠（服务层只有两个含「缘由」的错误消息）

11. Phase 3 — 认证页内联错误覆盖设计

11.1 问题

Phase 1 / Phase 2 已将管理端全部 RBAC 表单升级为「字段旁内联文案」错误反馈。但三个认证页面（login.html、register.html、complete_profile.html）仍使用 HTML5 原生校验气泡（required 属性 → 浏览器「请填写此字段」气泡），与系统整体体验风格不一致。

用户感知：在管理端内修改密码、编辑用户等操作已获得友好的红色内联提示，但回到登录页/注册页却看到浏览器默认的蓝白气泡，体验断裂。

11.2 现状分析

页面提交方式字段数当前空字段处理当前服务端错误处理
login.html 原生 POST（非 AJAX） 2（username, password） HTML5 required → 浏览器原生气泡 服务端 redirect → auth-msg-err banner（表单下方）
register.html 原生 POST（模态确认后 form.submit()） 7（email, nickname, job_title, password, confirm_password, role, group_ids, reason） JS checkValidity() + reportValidity() → 浏览器原生气泡 服务端 redirect → SSR 渲染 auth-msg-err banner（表单上方）
complete_profile.html 原生 POST 1~3（动态，仅缺失字段可编辑） HTML5 required → 浏览器原生气泡 服务端 redirect → auth-msg-err banner（表单上方）

11.3 根因

  1. Phase 2 审计时降级为 B+：认证页的 auth-msg-err banner 距表单近（≤50px），审计时认为改造收益低。但忽略了前端空字段校验仍使用原生气泡的问题（B+ 评估仅关注了服务端错误 banner，未关注前端即时校验）
  2. 认证页独立于 common-redesign.js：认证页不继承 _base.html，没有加载 Phase 1/2 的 AJAX form handler，需要在页面内 inline script 中实现验证逻辑
  3. 前后端校验架构差异：管理端表单使用 AJAX 提交 → 后端返回 field key → 前端就近显示。认证页使用原生 POST → 后端 redirect → SSR 渲染错误。两种架构的内联错误实现方式不同

11.4 方案

核心策略：前端即时校验 + SSR 服务端错误保持

认证页无需改为 AJAX 提交。方案分两层：

  1. 前端即时校验（本 Phase 实现）：在 submit 事件中用 JS 检查空字段，使用与管理端一致的红色内联文案（auth-error-msg），替代浏览器原生气泡
  2. 服务端错误 banner 保持：auth-msg-err banner 仅处理服务端校验（凭证错误、用户名冲突等），距表单近且语义为"表单整体错误"（如"用户名或密码有误"），保持不变

设计原则

#原则说明
P1样式一致使用 auth-error-msg class（与管理端 .tf-error-msg 视觉等价，颜色/字号/图标一致），添加到 redesign-auth.css
P2禁用原生校验所有 auth 表单添加 novalidate，移除 required / maxlength 约束属性
P3hint 互斥显示错误时隐藏 auth-hint，清除时恢复
P4自动清除input/change 事件自动清除该字段的错误状态
P5无障碍role="alert" + aria-live="polite"
P6不改提交方式认证页继续使用原生 POST，不引入 AJAX

11.8 JS 工具函数（三页面共用，inline 定义）

由于认证页不加载 common-redesign.js，每个页面 inline script 中定义以下两个函数：

function showAuthError(fieldName, msg) {
  clearAuthError(fieldName);
  var wrap = document.querySelector('[data-field="' + fieldName + '"]');
  if (!wrap) return;
  wrap.classList.add('auth-field-error');
  var hint = wrap.querySelector('.auth-hint');
  if (hint) hint.style.display = 'none';
  var errEl = document.createElement('div');
  errEl.className = 'auth-error-msg';
  errEl.setAttribute('role', 'alert');
  errEl.textContent = msg;
  var insertAfter = wrap.querySelector('.auth-input, .auth-select, .auth-textarea, .input-with-toggle');
  if (insertAfter) insertAfter.parentNode.insertBefore(errEl, insertAfter.nextSibling);
  else wrap.appendChild(errEl);
}

function clearAuthError(fieldName) {
  var wrap = document.querySelector('[data-field="' + fieldName + '"]');
  if (!wrap) return;
  wrap.classList.remove('auth-field-error');
  var err = wrap.querySelector('.auth-error-msg');
  if (err) err.remove();
  var hint = wrap.querySelector('.auth-hint');
  if (hint) hint.style.display = '';
}

function clearAllAuthErrors() {
  document.querySelectorAll('.auth-field-error').forEach(function(el) {
    el.classList.remove('auth-field-error');
  });
  document.querySelectorAll('.auth-error-msg').forEach(function(el) { el.remove(); });
  document.querySelectorAll('.auth-hint[style]').forEach(function(el) { el.style.display = ''; });
}

备选：可提取为 auth-validation.js（约 40 行），通过 <script src> 引入，避免三页面重复。但认证页加载频率低且脚本量极小，inline 更简单。

5注册页 → 不填任何字段 → 点击「提交申请」第一个空字段（email）显示内联错误 + 滚动到该字段
6注册页 → 填完所有字段 → 点击「提交申请」模态确认弹出（行为不变）
7注册页 → 模态确认后服务端返回错误（如邮箱已存在）SSR banner 显示错误（保持现有行为）
8补全信息页 → 不填花名 → 提交花名字段下方内联错误
9所有页面 → 无浏览器原生校验气泡出现✓ 全部被 novalidate 抑制

11.12 风险

风险影响缓解
前端校验被绕过（DevTools 禁用 JS） 低：服务端仍有完整校验，无安全风险 前端校验仅为 UX 优化，不替代后端
注册页校验逻辑与服务端不一致 中：前端认为合法但服务端拒绝，此时降级为 SSR banner 显示 前端校验尽量对齐服务端规则（非空/格式），但 uniqueness 检查仅服务端可做
移除 required 后，表单可能提交空值到服务端 低：服务端 authenticate_user / submit_registration 已有完整空值校验 JS 前端校验作为第一道防线，服务端校验为最终保障
三页面 inline 重复工具函数 低：约 30 行重复代码 可选：后续提取为 auth-validation.js，但当前影响可控

11.13 Phase 2 审计分类修正

Phase 2 审计（§9.2 ③）将认证页 SSR Banner 降级为 B+（基本合理）。本 Phase 3 修正评估：

  • SSR Banner（服务端错误）：维持 B+ 评价，不改。理由：banner 距表单近，语义为整体错误
  • HTML5 原生气泡（前端空值校验）：从 B+ 升级为 A（需修复）。理由：浏览器原生气泡样式不可控，与系统整体内联错误风格严重不一致，是用户直接可感知的体验断裂
