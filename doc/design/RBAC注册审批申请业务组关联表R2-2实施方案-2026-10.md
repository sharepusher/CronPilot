## 1. 问题与目标

现有 `rbac_registration_requests.group_ids` 用逗号字符串保存集合，Repository 使用子串 `LIKE` 查询；View 又在分页后过滤 admin 越界申请。结果是组 1 可能命中组 10，admin 完整子集无法进入数据库谓词，items、total、pages 和 pending badge 可能不一致。

R2-2 的目标是新增规范化关联表作为 scoped actor 的权威资源查询来源，在数据库分页前准确表达：

- viewer/operator：申请组与 actor 当前组存在精确交集。
- admin：申请组是 actor 当前组的非空完整子集。
- `__ALL__`：仅数据库当前 global actor 可见。
- 无关联、非法或迁移不完整数据：scoped actor 下 fail-closed。
- 列表、total、pages、页面计数与侧边栏 badge 使用同一授权谓词。

## 2. 根因

1. CSV 把集合语义压缩成字符串，token 相等和集合包含无法由当前 LIKE 准确表达。
2. Repository 只实现“可能有交集”，角色相关的 admin 子集被推迟到 View。
3. 分页组件在 Python 过滤前已经计算 count 和 offset，后置删除无法修正 total/pages。
4. pending count 复制了一套 LIKE 条件，没有单一权威 scoped query。

## 3. 方案决策

**已选 DEC：**新增 `rbac_registration_request_groups` 关联表。原 CSV 字段本轮保留，用于兼容旧版本、页面展示和可回滚；scoped 读取授权改用关联表。禁止继续扩展 CSV 方言 SQL，禁止全量加载后 Python 分页。

### 3.1 表结构

```
rbac_registration_request_groups
  id          INTEGER primary key
  registration_request_id  INTEGER not null
  group_id    INTEGER not null

  UNIQUE(registration_request_id, group_id)
  INDEX(group_id, registration_request_id)
```

`registration_request_id` 明确指向 `rbac_registration_requests.id`，类型与当前申请主键保持一致；`group_id` 与资源组主键一致。唯一约束保证集合去重，反向复合索引支持“actor 组 → 申请”交集查询。仓库虽在审批服务、日志和测试局部变量中使用 `request_id` 表示注册申请，但 HTTP 层也有独立 request\_id 协议；数据库 schema 采用完整资源名可消除长期歧义。

**直译：**`registration_request_id` = “注册申请单编号”，不是“网络请求编号”。例如父表中注册申请单 #42 申请组 1、2，关联表保存两行：`(registration_request_id=42, group_id=1)` 和 `(registration_request_id=42, group_id=2)`。之所以保留 request，是因为现有父实体和父表已经正式命名为 `RbacRegistrationRequest` / `rbac_registration_requests`；关联列必须明确镜像父资源，而不是另造不一致的 `registration_id`。

为保证 SQLite/MySQL 行为一致并遵循仓库现有关联表模式，R2-2 首批不依赖数据库物理外键级联；完整性由同事务写入、启动迁移校验、孤儿门禁和删除入口显式清理保证。后续如引入物理外键，必须独立设计并完成存量孤儿清理。

### 3.2 `__ALL__` 表达

`__ALL__` 不伪造为特殊 group\_id。全局申请继续由父表 CSV 的精确值 `__ALL__` 表达，关联表保持零行；scoped 查询天然不可见，global actor 继续走全量分支。普通有效申请必须至少有一条关联行。

### 3.3 字段语义逐项分析

| 原状态 | 独立语义 | 关联表表达 | 迁移决定 |
| --- | --- | --- | --- |
| 整数 CSV，如 `1,2` | 无序业务组集合。 | 两条关联行。 | 全量解析成功且组存在时原子回填。 |
| `__ALL__` | admin 全局申请，不等于空集合。 | 零关联行；由父字段保留全局标记。 | 只允许 role=admin；混合值非法。 |
| 空串/NULL | 不满足当前注册契约；属于历史非法状态。 | 零关联行。 | scoped 不可见；global 可见以便治理，不自动猜测。 |
| 重复，如 `1,1` | 集合语义等价于组 1，顺序/次数无业务意义。 | 唯一的一条组 1 关联。 | 安全去重并记录规范化计数。 |
| 空白，如 `1, 2` | 可无损规范为整数集合。 | 组 1、2 两行。 | trim 后回填并记录规范化计数。 |
| 非整数、≤0、混合 `__ALL__` | 无法等价表达的非法状态。 | 零关联行。 | 整条申请拒绝部分回填，scoped fail-closed。 |
| 引用不存在的组 | 悬空授权，不能视为有效组。 | 零关联行。 | 整条申请不回填；新写入必须先验证组存在。 |

**删除结论：**本轮不删除、重命名或改变 `group_ids` 字段。因 `__ALL__`、非法历史状态和展示兼容尚依赖它，关联表尚不能完全替代其全部独立语义。

## 4. 权威查询设计

### 4.1 global actor

数据库当前 seed/global admin 继续使用全量申请查询；R2-2 不改变其合法可见能力。

### 4.2 viewer/operator 申请

必须存在一条关联行，其 group\_id 属于 actor 当前 group\_ids。该 EXISTS 条件在 count、分页和 badge 前生效。

### 4.3 admin 申请

必须同时满足：至少一条关联行；不存在任何 group\_id 不属于 actor 当前组的关联行；父字段不为 `__ALL__`。这准确表达“非空完整子集”。

### 4.4 单一查询来源

```
database-current actor
  → authoritative scoped predicate
  → optional status / username filters
  → count + limit/offset
  → items / total / pages

pending badge = same scoped predicate + status='pending'
```

Repository 提供一个内部权威 scoped statement 构造入口；列表分页与 pending count 只能复用它。View 中现有 `page_data.items` admin 后过滤必须删除。

## 5. 写入与事务设计

### 5.1 注册申请目标 Scope 规范化器

该组件只回答“这张注册申请单申请了什么权限范围”，建议命名为 `normalize_registration_requested_scope`。它不是 R2-1 的当前管理员 actor Scope 解析器，也不读取 Session、不判断管理员是否有权审批、不执行数据库写入。

```
输入：申请角色 + 表单 group_ids 或历史 CSV + 当前有效资源组集合
输出之一：
  global                         # 合法 admin + __ALL__
  concrete_groups = {1, 2}       # 合法、去重后的具体组集合
  invalid(reason_code)           # 空、非法、混合 __ALL__、悬空组等
```

新申请、历史回填和审批前复核必须调用同一规则，避免同一个 `"1, 2"` 在三个阶段被解释成不同结果。真正的页面可见性由“R2-1 当前 actor 结果”与“关联表中的申请目标组”组合判断。

### 5.2 原子写入与审批复核

1. 注册服务先完成角色、`__ALL__`、整数格式、正数、去重及所有资源组存在性校验。
2. 创建申请父记录并取得 `registration_request_id`。
3. 具体组申请在同一数据库事务内写入关联行；`__ALL__` 不写关联行。
4. 父记录或任一关联行写入失败时整体 rollback，返回现有通用失败信息；异常原文仅写服务端日志。
5. 批准前再次核对 CSV、关联集合和当前资源组；非法历史申请或两种存储不一致时安全拒绝本项、零用户/组写入，并由既有批量三态协议返回失败原因。
6. 批准、拒绝和过期只改变申请状态，不删除关联行，保证历史列表仍可按原申请 Scope 查询。

CSV 与关联行由同一个服务函数根据同一规范化集合生成，禁止调用方分别拼接。新版本回滚到旧代码时，CSV 仍完整，因此读取兼容；关联表作为附加数据保留。

## 6. 双后端迁移与回填

### 6.1 建表

新增模型并由 `db.create_all()` 创建新表；迁移脚本显式导入模型、把新表加入关键表断言，并检查唯一约束/两个查询方向的索引。SQLite/MySQL 使用相同逻辑结构，不使用单后端专属 SQL 作为业务查询前提。

### 6.2 幂等回填

1. 启动脚本检测表和迁移标记。
2. 只读扫描父申请并分类：global、有效具体组、可规范化、非法。
3. 对每个有效具体组申请，按完整集合原子替换关联行；任何 token 非法或组不存在则整条零写入。
4. 在同一 DML 事务完成同步、对账和迁移标记；数据库异常必须使启动失败，不得带半回填表启动新查询。
5. 在 R2-2D 切换权威读源前，重复启动仍以旧 CSV 为权威源做差异同步并再次对账；这样覆盖 B→C 分批部署间新增申请。集合未变化时零 DML，唯一约束作为最后防线。

### 6.3 对账不变量

- 有效具体组申请：关联集合等于规范化 CSV 集合。
- 合法 `__ALL__`：关联数为 0。
- 非法申请：关联数为 0，且出现在迁移报告。
- 不存在孤儿 `registration_request_id`；不存在重复的 `registration_request_id/group_id`。
- 回填前后父申请行数、状态、密码摘要及审计字段完全不变。

## 10. 测试与验收矩阵

- 精确 token：actor 1 不见申请 10；actor 10 不见申请 1。
- viewer/operator：交集可见，无交集不可见。
- admin：合法单组/多组子集可见；部分越权和完全越权不可见。
- global：seed/global admin 保持全量；scoped 不见 `__ALL__`。
- 异常数据：空、非整数、≤0、混合全局、重复、空白、悬空组按冻结策略处理。
- 分页：21 条合法+5 条越权时 total=21、pages=2、第二页 1 条。
- 筛选：status/username 只能缩小授权集合，使用不含 1/10 碰撞的独立样本。
- 一致性：列表标题、页脚 total、pages、页面 pending count、导航 badge 同源。
- 事务：父写失败、关联写失败、commit 失败均无父/子半成品。
- 审批防护：非法历史值、CSV/关联集合不一致、关联组已删除时，单项和批量审批均安全失败且无用户/用户组写入。
- 迁移：首次、重复、故障重试、非法数据、空库、存量库、SQLite、真实 MySQL。
- 回滚：新版本产生的申请由旧版 CSV 查询仍可读取，新增表不影响旧版启动。

### 10.1 性能门槛

## 14. R2-2E 集成加固与最终交付设计（E1/E2/E3/E4 已实施）

### 14.1 审批前一致性门禁

父申请加锁后、任何用户或用户组写入前，读取当前有效资源组并调用同一个注册申请目标 Scope 规范化器；随后读取该申请全部关联行。合法 global 必须是 `admin + __ALL__ + 零关联`；合法 concrete 必须满足规范化 CSV 集合与关联集合完全相等，且不存在重复关联；非法 CSV、关联缺失/多余、引用已不存在资源组均返回受控业务失败，申请保持 pending，零用户、零用户组、零审批状态副作用。批准实际使用门禁返回的已验证集合，禁止随后再次独立解析 CSV。单项与批量批准均复用 `approve_registration()`，批量继续使用既有 all\_success / partial\_failure / all\_failure 真值协议。拒绝操作仍允许处理异常申请，作为治理出口。

### 14.2 切读后的启动语义

当前启动函数仍会在每次启动时以 CSV 重建关联表，这只适用于切读前。R2-2E 新增独立切读标记：首次运行新版本时在一个事务内完成最后一次 CSV→关联同步、全量对账并写入标记；标记存在后，启动流程只计算期望集合并核对实际集合，发现缺失、多余、孤儿或非法新增关系立即阻止启动，禁止自动删除或重建关联行。这样 CSV 保留回滚兼容和一致性校验价值，但不会在关联表成为授权读源后反向覆盖它。旧版本回滚后再前滚若产生漂移，新版本应 fail-closed，并按运维对账流程修复，不能静默猜测。

### 14.3 分段实施顺序

1. **E1 正确性：**实现审批一致性 helper、审批使用已验证集合、切读标记和 verify-only 启动对账；补单项/批量零副作用测试。
2. **E2 数据库与性能：**在隔离库生成至少 100,000 张申请、平均 3 个组，分别记录旧 LIKE 与新关联查询的预热后 p95；列表+count 不超过旧查询 2 倍，global 回归不超过 20%，EXPLAIN 必须命中双向索引。SQLite 与真实 MySQL 使用同一数据模型和验收脚本；MySQL 方言编译只算静态门禁，不能替代真实执行。

## 16. R2-2E2 数据库与性能验收详细设计（待确认）

### 16.1 目标与非目标

E2 只回答三个问题：关联查询是否在真实 SQLite 和真实 MySQL 上返回相同授权结果；100,000 张申请和约 300,000 条关联行下性能是否达标；查询计划是否使用预期索引。不改页面、权限语义、审批协议、CSV 字段或开发数据库。

### 16.2 隔离环境与数据集

- 新增可重复的性能验收脚本，只接受显式的隔离数据库 URL；如 URL 指向当前开发库或未包含专用验收库名，立即拒绝。
- SQLite 使用临时文件；MySQL 使用临时隔离容器/数据库，不复用项目 `docker-compose.yml` 的 SQLite 服务。容器版本、SQL mode、字符集、数据库版本和硬件摘要必须写入结果。
- 固定随机种子生成 100,000 张申请、至少 100 个业务组、平均 3 条关联；角色、pending 状态、global 申请和具体组数量按固定比例输出到 manifest。夹具直接写入惰性密码摘要，禁止计时期间做密码哈希。
- 数据分为两个逻辑样本：“等价性能样本”使旧 LIKE 与新谓词的结果数量一致，用于相对性能比较；“冲突正确性样本”显式包含组 1/10、admin 部分越权和 `__ALL__`，只验证新查询真值，不把错误 LIKE 的额外行当成性能优势或劣势。

### 16.3 计时口径

每个后端在同一数据集上先执行 10 次不计时预热，再独立执行至少 50 次并记录 p50/p95/max。每轮校验返回行集或 count，禁止只计时不验真值。分别记录：

1. 分页 total count SQL；
2. 20 条首页 page SQL；
3. pending badge count SQL；
4. Repository 端到端“分页 count + page”；
5. 页面数据读取组合“分页 count + page + pending count”。

scoped 查询的等价样本以组数为 1、3、10 三档执行，并覆盖 viewer/operator 交集和 admin 完整子集。global 路径不使用关联谓词，单独作为非回归基线。

### 16.4 验收阈值与 EXPLAIN

- 在等价样本、同机器、同连接池和同预热条件下，新 scoped 页面组合 p95 不得超过旧 LIKE 基线 2 倍；五个分项指标同时报告，不得用组合值掩盖单项异常。
- global 路径 p95 相对同脚本的无关联基线回归不超过 20%。若基线过小导致比率失真，同时报告绝对差值，不单凭百分比下结论。
- SQLite 保存 `EXPLAIN QUERY PLAN`；MySQL 5.7/8.x 共用 `EXPLAIN FORMAT=JSON`，MySQL 8.0.18+ 可额外保存 `EXPLAIN ANALYZE`。关联子查询不得对整张关联表使用 `ALL` 全扫；实际 `key` 必须是申请领先的唯一索引 `uq_reg_req_groups_req_group` 或组领先的 `ix_reg_req_groups_group_req`。“双向索引”指不同查询形状均有可用索引，不强求单条 SQL 同时使用两个索引。

### 16.5 执行顺序与证据

1. 静态门禁：确认模型约束、两个索引及 SQLite/MySQL SQL 编译。
2. 在临时 SQLite 库建表、批量加载、对账、运行真值矩阵、EXPLAIN 和性能基准。
3. 在真实 MySQL 服务重复同一 manifest，执行空库建表、存量迁移/重试、切读 verify-only、真值矩阵、EXPLAIN 和性能基准。
4. 脚本输出机读 JSON 和人读 Markdown，包含环境、manifest 校验和、每次耗时、分位数、查询计划、行集/count 断言及 PASS/FAIL；凭据落到 `doc/qa/` 并生成同名 Markdown。
5. 清理临时数据库/容器，重启开发服务并重新实际登录，证明本地开发数据未被验收污染。

### 16.6 停止条件与后续

- 真实 MySQL 不可用、双后端真值不同、数据集不守恒、关联表全扫或任一阻断性阈值超标时，E2 立即停止并报告，不得宣称通过。
- 性能失败时不得恢复不安全 LIKE；先交付计划与耗时证据，如需改动谓词或索引，作为 E2-Fix 设计修订再请用户确认，不在基准过程中静默调参。
- E2 通过后只能标记“数据库与性能验收完成”；仍需经过 E3 集成和 E4 交付后才能宣称 R2-2 完成。

## 17. R2-2E2-Fix A：角色分支查询复盘（已回滚）

### 17.1 问题与根因

在 100,004 张申请、295,006 条关联行的隔离 SQLite 实测中，10 组 scoped 场景的旧/new 分页 count+page p95 分别为 44.515ms/98.762ms，比例 2.219×。实际 MySQL 8 在第一个组 1 真值 count 即持续执行超过 7 分钟；`EXPLAIN FORMAT=JSON` 显示父表 `access_type=ALL`、预估扫描 98,930 行，但关联表三个子查询均命中 request-led 覆盖索引。根因是单个 `OR` 谓词将 viewer/operator 的“按 group 查结果”与 admin 的“完整子集”合并为相关父表扫描，不是关联表索引缺失。

### 17.2 实施结果

实施以角色互斥的两条 ID 查询使用 `UNION ALL` 合并；viewer/operator 从 `group_id` 反向索引开始，admin 保留 `EXISTS + NOT EXISTS` 完整子集判定。为避免一个申请同时命中多个 actor group 时的一对多行倍增，普通角色分支在 ID 投影内去重；这不是跨角色或权限语义去重。

隔离 SQLite 10,004 父申请 / 29,506 关联行、1 次预热 / 2 次计时的结果为：组 1 为 2.037×、组 3 为 4.267×、组 10 为 3.948×，均未通过 2× 阈值。计划显示普通角色分支使用 `ix_reg_req_groups_group_req`，但 admin 分支仍为 `SCAN rbac_registration_requests` 并对每个候选执行相关关联查询。按 §16.6 已回滚该实现，不进入 MySQL 或完整 100k 计时。

### 17.3 七项复盘

1. **Bug 定位：**E2-Fix A 将 OR 拆分后，admin 分支仍在 SQLite 计划中扫描父表，三档样本均超性能门槛。
2. **根因：**“完整子集”以相关 `EXISTS + NOT EXISTS` 写在每个 admin 父行上；分支拆分只优化了普通角色，未把管理员判定改成集合运算。
3. **测试漏洞：**原候选设计只要求关联索引可用，未把 admin 分支“不得父表扫描”列为单独门禁，也未先用小样本证明总组合比可过线。
4. **修复：**未保留未达标代码，已恢复已验证的单谓词实现；下一版改为集合聚合设计，见 §18。
5. **防护测试：**基准脚本保留三档 p95、结果真值和 SQLite/MySQL 计划输出；实施 §18 时新增 admin 分支计划断言与 1/3/10 组阈值回归。
6. **同类排查：**普通角色关联反查已证明索引有效；剩余热点只在 admin 完整子集条件，列表 count、页面 count 和 badge 均受影响。
7. **预防方案：**在 `tests/test_registration_scope_benchmark.py` 增加“admin 分支不得出现父表全扫”的计划结构测试，并在脚本 result 中分别报告两分支计划；第三方可运行 §16.5 的命令复现。

## 18. R2-2E2-Fix B：管理员集合聚合设计（待确认）

### 18.1 方案

保持 viewer/operator 的 group-driven ID 分支不变。将 admin 的“存在关联且不存在 actor 范围外关联”改为**单次关联表集合聚合**：从申请关联行 join 父申请，限定 `role='admin'` 和 `group_ids != '__ALL__'`，按 `registration_request_id` 分组，并以条件聚合断言范围外 group 数为 0。内连接天然保证至少存在一条关联，条件聚合精确表达“非空完整子集”。两个角色分支继续互斥，以 `UNION ALL` 合并。

### 18.2 正确性与风险控制

- 关联表唯一约束确保每个申请/组只计一次；admin 分支按申请 ID 聚合，无需外层 `DISTINCT`。
- `__ALL__` 仍被父字段精确排除；零关联、非法角色和空 actor group 都不产出 ID，保持 fail-closed。空 actor group 在构造 SQL 前直接返回 false，禁止生成空 `NOT IN`。
- status/username 仍只能缩小授权结果；实现时由同一父表筛选构造器等价下推至两个 ID 分支，避免 UNION 派生表先计算全量 ID 后才筛选。最终实体查询保留同值条件作为结果契约校验。
- 聚合使用已安装 SQLAlchemy 2.0.36 的 `case((condition, 1), else_=0)` 与 `func.sum(...)`；2026-10-23 已读取函数签名并实际编译 SQLite/MySQL SQL，均生成 `HAVING sum(CASE WHEN group_id NOT IN (...) THEN 1 ELSE 0 END) = 0`。
- 查询从关联行集合而非每行相关子查询计算；可能扫描 admin 关联候选，但消除父表×相关子查询的乘积。是否需要额外父表 role/status 索引，必须由新 EXPLAIN 和完整 100k 实测决定。

### 18.3 验收与回滚

先执行 SQLite 小样本计划/真值门禁，再执行 §16 相同的 100k、10/50 基准，最后执行真实 MySQL；每一步均要求 viewer/operator 使用反向索引、admin 不出现相关父表全扫、1/3/10 组 p95 全部不超过 2×。任一失败立即恢复当前单谓词实现，不修改关联表或 CSV，不降级为 LIKE。

### 18.4 专业 Review 结论

**结论：有条件通过设计评审，具备进入受控实施的专业性，但性能收益仍是待验证假设。**准确性方面，内连接保证非空、按申请 ID 分组保证逐申请判定、范围外计数为零等价于“申请组是 actor 组的完整子集”；角色互斥使 `UNION ALL` 不产生跨分支重复。合理性方面，方案直接消除 MySQL 已证实的逐父行相关子查询，不改变表结构、授权语义或回滚数据，变更半径可控。

性能方向为正，但不能预先承诺达标：聚合会把复杂度转为 admin 关联候选的集合扫描，并可能在 MySQL 产生 UNION 派生表物化、在 SQLite 产生临时分组 B-tree；actor 组越多，`IN/NOT IN` 比较和普通角色分支去重成本也会增加。10k、1 次预热/2 次计时仅用于快速否决，不构成通过证据；正式结论必须来自 100k、10/50 和真实 MySQL。

现有“相对旧 LIKE 不超过 2×”可作为回归门槛，但旧 LIKE 不能表达 admin 完整子集，且基线过小时倍率易失真。正式报告必须同时给出绝对 p50/p95/max、超时次数、返回基数、两分支独立 EXPLAIN 以及 Repository 的 count+page+badge 总耗时；30 秒会话超时只是安全熔断，不是性能目标。测试数据还须分别覆盖 admin 占比、每申请关联数和 actor 组数的低/中/高档，避免只在当前均匀分布上得出结论。

因此本方案的专业性和语义准确性评价为高，工程合理性为高，方向性性能可信度为中高，量化性能可信度在真实双后端验收前仅为中等。未通过 §18.3 前不得宣称 E2 或 R2-2 完成。

## 19. R2-2E2 领域容量模型校准（待确认）

### 19.1 偏差确认

原 E2 将 100k 注册申请直接作为发布阻断规模，缺少领域依据。CronPilot 数量最大的实体预期是定时任务；注册申请受人员规模约束，管理员、操作人员及其他用户总量预期不超过万，注册和审批不会持续高并发。100k 可用于暴露渐进复杂度和长期历史风险，但不能替代真实业务容量，也不应仅凭相对倍率否决绝对耗时可接受的方案。

低审批并发会降低数据库吞吐、锁和连接池压力，但不会消除单次默认“全部状态”列表对历史申请执行精确 count 的延迟；当前路由未指定 status 时确实查询全部历史，pending badge 则只查询 pending。因此仍需容量验证，但应按注册审批领域建模。

### 19.2 三层数据与并发模型

- **业务容量层：**10,000 张历史申请，pending 分别取 1% 与 10% 两档，角色与每申请组数按真实约束分布；并发 1 为主、并发 5 为短时峰值。此层是发布阻断门槛。
- **裕量容量层：**30,000 张历史申请，用于覆盖拒绝后重申请、停用后重新激活及多年历史累积；仍按低并发执行。此层不应出现超时或数量级退化。
- **压力诊断层：**100,000 张申请和约 300,000 条关联继续保留，用于观察复杂度、执行计划和容量边界；不再以“相对旧 LIKE 2×”单独阻断发布，但查询超时、权限真值错误或异常全表乘积仍必须报告。

### 19.3 校准后的验收判定

- 业务容量层以绝对延迟为主：Repository 的 `count + page + pending badge` 单并发 p95 建议不超过 500ms、max 不超过 1s；并发 5 p95 建议不超过 1s。该 SLO 是本轮待确认值，不以 30 秒安全超时代替。
- 裕量容量层组合 p95 建议不超过 1s、max 不超过 2s；不得出现数据库查询超时。
- 相对旧 LIKE 的倍率降为诊断指标；旧 LIKE 不能表达 admin 完整子集，不能作为唯一等价性能标准。
- 默认全部状态列表、pending 筛选列表、pending badge 必须分别计时；不得用 pending 的小集合成绩代替默认历史列表。
- 若当前精确单谓词在真实 MySQL 的 10k/30k 层通过绝对 SLO，则不实施 Fix B，保留 100k 容量限制记录；若任一发布阻断层不通过，再实施 §18 并用同一模型复验。

### 19.4 缓存结论

在人员规模不超过万且审批低并发的前提下，引入权限结果缓存的收益进一步降低，而版本化失效、跨进程一致性和过期授权风险不变。本轮不引入应用内存或 Redis 权限缓存；只有数据库正确查询在业务容量层仍不满足 SLO，且 Fix B 也无法达标时，才另立缓存设计。

### 19.5 实施结果

当前单谓词在真实 MySQL 10k 的默认全历史列表未通过：actor 3/10 组快速档分别为 1,922.717ms / 5,684.065ms，因此触发 §18 Fix B。Fix B 实施后，MySQL 10k 正式 10/50 最差 p95 为 128.380ms；30k、pending 10% 正式 10/50 最差为 378.184ms；10k、pending 10%、并发 5 的 50 个请求样本最差为 188.870ms。SQLite 10k/30k、pending 1%/10% 四档全部通过。完整证据见 [E2 校准性能验收](../qa/RBAC注册审批关联表R2-2E2校准性能验收-2026-10-23.html)。
