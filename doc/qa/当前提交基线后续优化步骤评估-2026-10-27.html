当前提交基线后续优化步骤评估

日期：2026-10-27 · 基线：main / 8e3a1b0 加当前未提交工作树 · 类型：后续优先级与实施门禁评估 · 状态：评估完成，不授权新增实现

推荐结论：下一步不是直接进入新的 RBAC 或产品功能，而是先把当前已经实施但尚未提交的“发布工作流安全加固 S1–S4 + S4 自引用修正”完成本地收口并形成一个原子提交；随后核验 GitHub release Environment 与 tag protection。完成这两项后，下一项产品正确性工作才是重新 Review 并确认 /rbac/users/edit 差异写入与单事务方案的 U0。

发布资产边界已提交8e3a1b0 build: enforce release asset boundary，且 main == origin/main。源码归档与部署包边界已有正式基线。

2. 下一步唯一优先项：发布治理批次收口

2.1 为什么优先

  • 当前工作树直接修改 tag 触发的发布工作流和 contents: write 权限边界，风险高于普通业务功能。
  • 继续叠加 RBAC U0 会把 CI/Release 风险与数据库事务风险混在同一工作区，降低 Review、回滚和归责能力。
  • S4 修正已经实施并通过专项测试，当前最经济的动作是完成一致性复核和原子提交，而不是另起功能。

2.2 提交前完成定义

  1. 确认设计、复盘、评估、Release Notes 与 manifest 均采用同一三字段语义，不再把源码 manifest 绑定自身 commit。
  2. 运行 release/version 专项、版本一致性、Release Notes 精确版本提取、YAML 解析、文档同步/完整性/链接和 git diff --check。
  3. 复核 workflow：构建 job 只读且不持久化凭据；publish job 单独获得写权限；Release 保持 draft，远端资产回读、checksum 与 build report 来源校验完成后才发布。
  4. 将代码、测试、manifest、设计、复盘和索引作为一个可审计原子提交；不夹带应用业务代码。
当前成熟度：本地技术结论为 A- / 可进入最终提交复核。已知本地阻断项为 0；远端 Environment/tag protection 尚未核验，因此不能宣称端到端发布治理全部完成。

3. 提交后的第二步：远端治理核验

检查期望停止条件
GitHub Environment release存在；设置必要审批者及允许部署分支/tag。未配置时不得声称 publish job 有人工门禁。
tag protection / ruleset限制 v*.*.* tag 创建与更新主体，禁止随意改写已发布 tag。信任根未收紧时，不进行真实新版本发布演练。
受控远端演练验证 build-validate 无写权限、publish 等待 Environment、资产回读一致后解除 draft。任一资产、来源、Release 状态或权限断言失败，保留 draft 并停止。

远端演练会创建或触发外部发布状态，必须另行明确授权；本评估不自动创建 tag、Release 或修改 GitHub Settings。

4. 后续产品正确性优先项：RBAC 用户编辑 U0

发布治理闭环后，建议回到 RBAC 用户编辑差异写入与事务闭环方案。其业务价值高于路线图中的一般功能项，因为当前编辑链仍存在多次提交、后置校验失败可能留下部分写入，以及无变化也写库/写审计的风险。

  1. 先校准设计：对照已提交的 Scope 授权边界、用户重新启用、auth_version 和缓存失效语义，确认 rev.1 没有被近期实现改变。
  2. 再次明确确认：该方案仍是“待确认，未实施”；不得因旧讨论或本次评估直接开工。
  3. 只实施 U0：冻结 no-op、单字段、组变更、提交失败和未知结果的 before/after 契约；不得在 U0 修改生产代码。
  4. U0 通过后再分批 U1–U3：change set → 单事务服务 → 路由/UI/审计与浏览器交付。

5. 暂不推荐的方向

  • Tier 3c / Flask 3 / 默认 Python 3.12+：权威依赖 RFC 已明确搁置，不应重新开启。
  • OPT-P1-03 等一般功能：价值存在，但优先级低于当前发布供应链闭环和用户编辑事务正确性。
  • 继续扩展 R2：F-02 已关闭；除非出现新证据，不应把新问题继续挂在已完成批次下。
  • 未清理工作树时启动新方案：会破坏原子提交、回滚边界和 Review 准确性。

6. 建议执行顺序

P0  当前发布治理工作树最终复核 → 原子提交
P1  GitHub Environment + tag protection 核验 → 经授权的受控远端演练
P2  RBAC 用户编辑方案基线校准 → 用户再次确认
P3  只实施 U0 红线/基线测试 → Review 后再进入 U1

7. 风险与边界

  • 当前本地服务未运行；这不阻断纯 release-workflow 提交，但开始 RBAC U0 或 UI 验收前必须恢复服务并验证登录 POST。
  • release-manifest.json 当前描述 v4.1.1；下一版本发布前必须在被 tag 的提交中更新版本和 readiness，禁止复用旧 manifest。
  • 本地 --tag v4.1.1 通过只证明当前工作树的契约一致；不能证明历史 v4.1.1 tag 自身包含新增 workflow/manifest，也不应重写历史 tag。
  • 本评估只排序和定义门禁，不授权 commit、push、GitHub Settings 修改、tag 或 Release 操作。

8. 最终判断

下一步：先完成并提交当前发布工作流安全加固批次。提交后先核验远端发布信任根；两者完成后，再把 RBAC 用户编辑差异写入方案升级为当前产品正确性主线，并从 U0 开始。该顺序在专业性、风险隔离、可回滚性和投入产出比上均优于直接进入新功能。
