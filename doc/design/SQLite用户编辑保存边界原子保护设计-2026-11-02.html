SQLite 用户编辑保存边界原子保护设计

版本：rev.1.1 · 日期：2026-11-02 · 状态：用户授权评估后实施；S0–S3已执行，RBAC专项通过；全量基线6失败与任务子项仍开放。

承接：下一步方案评估、优先级梳理。问题标识：发布前审查的SQLite保存边界发现；与已关闭的“锁释放验收盲点”分开。

推荐决策：只在有真实用户编辑意图的顶层保存服务内，为SQLite建立局部即时写事务，在同一物理连接、同一事务中重新读取当前授权、当前目标/关系、三方比较和写入审计；MySQL保持现有行锁。采用明确串行顺序、有界竞争处理，不改全站事务配置，不引入版本列、分布式锁或自动业务重试。

1. 问题、根因与证据边界

现有update_user_management先结束路由读事务，再用with_for_update读取actor/target及组关系，随后授权、比较、写入并提交。SQLite方言不生成该行锁子句；当前sqlite3默认控制方式下，Session逻辑事务不等于读操作已处于持续保护后续写入的物理事务。

本日已有两个独立连接反例：actor被降为viewer并提交后，旧请求仍保存；目标花名已被另一个连接更新后，旧请求仍覆盖。原始证据。它们证明当前服务边界不足，不直接代表所有部署的完整HTTP攻击链；本设计补真实入口对照。

设计阶段已在内存库核对：Python 3.11.4、SQLAlchemy 2.0.36、SQLite 3.51.2；普通SELECT后Session事务活跃而DBAPI事务为false。局部BEGIN IMMEDIATE后DBAPI事务为true，Session rollback后为false；busy_timeout临时置0后可恢复原5000ms。此为API可行性诊断，未执行修复后的并发验收，不证明已修复。

2. 范围、责任与现有调用方盘点

  • 本批修改：app/rbac/services.py::update_user_management；拟新增app/services/sqlite_write_boundary.py（只负责取得局部保护及恢复连接参数，不拥有业务commit）；内存守卫tests/test_user_edit_sqlite_boundary.py；隔离集成CLI scripts/verify_user_edit_sqlite_boundary.py；验收、复盘、Release Notes、依赖RFC和索引。
  • 应用调用方：全仓搜索显示update_user_management只有app/rbac/views.py::users_edit调用；路由在服务前做用户读取、Scope早期校验、验签、规范化、邮箱确认与意图判定。合法进入服务的路径没有业务DML；前置拒绝可能另写拒绝审计，但随后直接返回，不调用保存服务。
  • 事务归属：该服务是独立请求的顶层写边界，允许结束调用方可丢弃的只读事务，负责业务flush/commit/rollback及同库成功审计；不是可嵌套helper。签名T0和请求规范化值是普通数据，入口rollback后仍保留，不从已过期ORM对象重建基线。
  • 禁止组合调用：待提交ORM new/dirty/deleted在任何服务内数据库操作前拒绝；原生SQL待写事务同样禁止，不能以这三个集合为空宣称没有原生写入。通过真实users_edit调用链计数证明其无前置DML，并要求将来新增调用方重新提供此证据。误用时不擅自提交或清理未知归属的工作，由调用者承担清理；正常请求的终态释放契约不变。
  • 竞争写入口：角色资料变更经同一用户编辑服务；停用经views.users_set_active→set_user_active；set_user_groups仍是独立服务；update_user与set_user_groups未发现当前app调用方，但保留脚本/测试可达边界。_replace_user_groups_in_session由其他RBAC业务事务调用。本批不重构这些入口；同一SQLite文件的实际DML必须遵守数据库写者排他，但其自身读取/审计正确性不因此自动成立。
  • 任务保存：save_task_edit应用调用方为main.cron_edit；已有版本条件写入，但锁内validate_cron_form会执行URL/DNS校验。当前旧任务反例接口失效。本批只重新核验任务边界、记录当前结果，不直接接入局部保护；若仍有缺口，另补任务专项设计并确认后修改，不能借RBAC修复宣布任务问题关闭。
  • 不修改：数据库字段、迁移、API信封、权限策略、隔离级别、全局engine事件、生产配置键、CI规则和调度器。无前端模板、CSS/JS、布局或提示文案变化，沿用现有FAILED/CONFLICT/COMMIT_UNKNOWN呈现，故不新增Before/After页面稿；仍执行角色浏览器回归。若需要新增可见提示，先补设计对比再确认。

3. 正确性契约：按串行顺序判断

  1. 撤权先提交：撤权事务先完成，保存随后取得保护；保存必须读取新角色/状态/组并拒绝，零业务DML、零成功审计、零授权副作用。
  2. 保存先取得保护：保存先在数据库取得写者资格，再读当前授权。后来的撤权写入不能穿入该决策区间；它可等待或明确忙失败。保存可先成功，撤权可在释放后重新发起并随后成功；不能因撤权请求已开始就判保存越权。
  3. 目标并发先提交：当前值与原值、请求值均不同时返回CONFLICT并保留新值；当前值已等于全部请求值返回ALREADY_APPLIED，不再写审计或递增认证版本。
  4. 无关字段与部分Scope：保留未编辑字段当前值及外组B；actor A/C、target A+B只改资料时关系零DML；真实组变更只改可编辑投影，但角色与完整组仍作为耦合授权单元并发校验。
  5. 短事务与终态：用户停留、GET、无意图POST、未确认清空、纯参数失败不取得写保护；锁内只执行必要本地校验、随机值生成和DB操作。所有正常未提交终态在服务返回前结束事务，不能靠teardown。成功仍是业务与成功审计一次提交。

“取得保护”以真实BEGIN成功和物理事务状态判定；不是取得Python进程锁、进入函数或Session.in_transaction变true。保护覆盖全部当前事实读取至业务事务结束；接口成功返回后可能有合法后续写入，不能要求目标永远不再变化。

4. 备选分析与选择

  • 继续只用FOR UPDATE：SQLite不生成该子句，无法解决当前缺口。
  • 只加目标版本/CAS：可检测目标变动，但不自动保护actor角色、停用状态、组关系和资源组存在性；需要更大协议与迁移，本批不采用。
  • 全局修改SQLite事务启动：影响所有读写、调度及其他服务，回归面大，不作为最小修复。
  • 仅进程互斥：不能覆盖多个worker/容器或其他SQLite写连接，不采用。
  • 局部BEGIN IMMEDIATE（推荐）：在被保护的保存服务读授权前先占有SQLite写者资格，同库其他写者不能在读取与提交之间插入。代价是数据库级写竞争，不能称为行级锁或零成本。仅SQLite分支生效，MySQL继续原行锁流程。

5. 连接与事务详细方案

5.1 入口顺序与helper责任

取得本请求concrete Session，核对顶层调用契约
完成无DB的参数/意图校验
结束路由可丢弃的读事务（原有入口rollback，纳入异常处理）
根据实际模型bind判断后端
  MySQL：不发SQLite SQL，沿用当前行锁事务
  SQLite：在该Session将用于RbacUser写入的连接建立即时写事务
保护内重新读取actor、target、关系、资源组
校验当前授权 → 三方比较 → 仅写有效差异 → 同事务审计
  非提交终态：rollback → 观察锁释放 → 返回
  成功：一次commit → 已有必要缓存处理 → 返回
  异常：按发生阶段分类，清理失败保留原异常链

helper不创建独立engine/session，不借出另一条连接做BEGIN，也不调用commit。使用concrete Session的模型bind连接；RbacUser、UserGroup、ResourceGroup、RbacAuditLog目前均无bind_key，设计要求运行时确认其engine一致。多bind或非支持后端不得静默降级为“无保护成功”。

当前API可采用s.connection(bind_arguments={'mapper': RbacUser})取得实际写入连接，并用connection.exec_driver_sql('BEGIN IMMEDIATE')发送固定SQL。这些调用已读本地SA/FSA实现并做内存验证；不通过新独立connection.begin或Session.begin嵌套已有逻辑事务。BEGIN前若底层已存在真实事务，视为入口/驱动模式不符，拒绝继续并记录诊断，不擅自commit或再套BEGIN。

5.2 写者资格获取采用立即返回策略

本批低频管理操作采用保护获取失败立即返回既有FAILED，不在业务层自动重试，避免SQLite驱动长等待占用Web执行单元。仅在发送BEGIN的极短窗口，将该连接busy_timeout暂置0：

  1. 从同一连接读取原PRAGMA busy_timeout；返回值必须是有效非负整数。
  2. 固定SQL临时置0，执行一次BEGIN IMMEDIATE；无论成功或异常，立即恢复原值。
  3. 只有BEGIN成功且原值恢复成功才进入授权读取和业务DML。原值拼入恢复SQL前限定整数范围，不接受用户输入。
  4. BEGIN遇SQLITE_BUSY时还未执行保护内读取/写入，清理后返回现有“保存失败”；不把所有OperationalError都认作忙，不以英文异常字符串判定。Python缺少sqlite_errorcode时按未知基础设施错误保守失败并保留日志，不猜成功。
  5. 若PRAGMA恢复失败、连接断开或清理失败，使用已核实的Session.invalidate淘汰不安全连接；不得将修改过的连接无声归池。记录原异常及清理异常，但对用户只给通用错误。

临时0仅控制保护获取，不修改全局engine/配置；保护成功后恢复原等待策略。DELETE模式下提交仍可能因其他长读者忙失败，不能声称BEGIN成功就绝不再忙。后续SQL/commit沿用部署连接的有限等待预算；日志与验收记录实际值，本机诊断原值为5000ms，不能把它写成所有部署保证。已有超长等待配置需在实施环境评估，不能擅自改生产参数。

5.3 异常分类与释放

  • 入口rollback、参数恢复、BEGIN、授权读取、比较或flush失败发生在commit尝试前：返回FAILED（业务冲突仍返回CONFLICT），必须回滚/失效连接，无部分业务与成功审计。
  • COMMIT调用开始后抛错：继续沿用COMMIT_UNKNOWN，不自动重试或推断必定未提交；授权尝试后的缓存处理保持现有策略。真实commit-before/after对照必须继续成立。
  • rollback再次抛错：不覆盖原阶段诊断，尽力invalidate。不能把清理失败变为成功，也不能错误重用该连接。
  • 正常rollback后DBAPI事务为false；独立竞争者应能取得写者资格。观察在原上下文清理前完成，不用ORM查询重新开始事务来“证明已清理”。

本方案只保证该受保护服务的决策原子性。其他写服务可能在保护外读取旧值再于释放后写入，其自身一致性仍需单独审计；不据本次数据库排他推定全仓写协议已统一。

7. 并发验收设计与隔离例外

7.1 先校准尺子，再测业务

废除“原线程在SQL监听内同步执行并等待竞争写入”的修复验收方式。竞争者与保存者使用独立执行单元、独立Flask上下文、独立engine/物理连接，推荐spawn进程防止继承Session。控制端只通过事件/屏障协调，不持有被测连接；事件只传run_id、case_id、阶段和固定结果，不传凭据。

  1. 保存方A取得即时写事务并发出已取得保护事件，暂停在测试进程绑定的准确读取点；竞争方B用独立连接、零等待尝试写，必须得到真正的SQLITE_BUSY且未提交。
  2. 控制端看到B结果后释放A，A应能完成而非互等；A结束后B在新的事务中再次尝试应成功。第二次是控制端显式动作，不是应用自动重试。
  3. 反向次序由B先真实提交，A再获取保护并读取，断言撤权拒绝、同字段冲突或等价完成。全部阶段必须有命中和提交证据。
  4. 等待使用条件和事件，默认每阶段10秒、每例45秒为测试预算；超时、未命中、进程异常、零用例、skip、缺报告都失败。不能用睡固定时长或“线程还活着”证明阻塞。

仅隔离测试进程使用精确Session/engine监听或局部wrapper标记阶段；不新增生产请求参数、环境故障开关或人工构造成功响应。

7.2 数据库隔离的明确设计例外

已随本次评估后实施授权确认的窄例外：普通tests/*单元测试仍严格使用sqlite:///:memory:；新增独立集成CLI可在自己创建的TemporaryDirectory中使用专用SQLite文件，以实际验证DELETE/WAL、文件写者排他及多连接行为。这是“所有测试只用内存”规则的本专项例外，本次仅适用于该集成工具，不修改或推广该仓库规则。

CLI不接受任意数据库URL或已有目录；仅在新临时目录建表，逐连接核验绝对路径与run_id哨兵，无manage导入，不连datas/job_log.sqlite。连接、进程、SQLite文件和WAL/SHM最后统一清理，脱敏JSON/截图写到用户指定的新空输出目录；拒绝复用含旧结果的输出目录。既有单连接内存浏览器工具不能承担并发证明。

覆盖DELETE与WAL；未能设置/核验指定模式必须失败，不能以默认模式代替。至少一组真实HTTP/浏览器交错使用两个独立测试服务实例共享该专用文件，各自使用实际认证/Scope/CSRF与模板；不复用串行内存Harness的全局锁去制造假的并发测试。

7.3 必测矩阵

  1. 撤权先提交：角色降权、actor停用、actor换组、目标停用/离开交集；真实当前权限拒绝，业务及成功审计零变化。
  2. 保存先取得保护：竞争actor/target/组写入不能插入；A先完成、B随后合法提交或明确忙失败；不是要求A无条件失败。
  3. 目标同字段新值先提交：CONFLICT；相同目标先提交：ALREADY_APPLIED；未编辑字段/范围外组新值保留。
  4. 正常资料-only、邮箱清空确认和授权变更：有效差异、单次业务/审计commit、认证版本/Token/缓存各按既有语义；种子admin不可停用、最后管理员约束保持。
  5. no-op、坏快照、缺确认/理由与参数错误：不取得即时事务；坏/缺键Session版本仍fail-closed，测试Fixture不得绕过真实鉴权。
  6. BEGIN忙、事务意外已开启、PRAGMA读取/恢复失败、flush失败、rollback失败、连接失效：正确分阶段，锁/连接不泄漏，不返回原异常文本。
  7. commit前/后异常：前者无持久化、后者可能已持久化，均COMMIT_UNKNOWN且无自动POST重放；保留当前七状态页面/原生POST语义。
  8. 参数恢复与池复用：成功/忙/普通异常后，下一次借出连接的busy_timeout为原值；恢复失败的连接必须淘汰。内存测试对淘汰用守卫验证，临时文件集成验证真实连接丢弃和数据完整。
  9. MySQL：同连接原行锁、冲突/已完成/失败终态释放，A+B范围外组保留；无SQLite专用SQL，无隔离/配置修改。

每例观测事务阶段、实际竞争错误码、网络POST次数、目标资料/关系、成功审计、认证版本和缓存调用；凭据仅内存比较并输出变化布尔值。前置登录和竞争准备事务与被测提交分别计数。

8. 分批实施与逐批退出条件

  1. S0 基线与工具校准：记录HEAD、已跟踪差异、未跟踪清单和相关文件SHA256；核对调用链、物理后端/驱动模式。先实现内存API守卫及独立竞争执行器，证明有保护/无保护对照能区分，暂不改业务。工具自身卡死、没有真正竞争、同连接、假busy或数据路径不明则停止。
  2. S1 最小RBAC修复：新增局部保护helper，仅接入update_user_management；将入口rollback及获取/清理纳入异常阶段处理。逐例通过撤权前后、同字段、正常/no-op、同事务审计和参数恢复守卫，再进入S2。不得顺手重构其他RBAC写服务或任务服务。
  3. S2 多后端与入口验收：运行临时SQLite DELETE/WAL、实际HTTP/目标角色页面、七状态和原生回退、真实MySQL回归。任务旧复现先按当前接口重新建立有效诊断，记录已证明/未证明；如发现任务缺口，另补任务方案确认后修，不将其计作本批已关闭。
  4. S3 复盘与交付：固化七项复盘及可执行预防，记录原始证据和限制，更新源评估/设计、Release Notes、依赖RFC、双索引及快速命令。只关闭有新验收证据的RBAC子项；发布前审查的任务子项不连带关闭。用户要求时再commit，不自动tag/push/发布。

10. 风险、限制与回退

  • 数据库级写者排他会影响其他目标与同文件日志写入；保护获取立即失败可能增加忙响应。限定真实有意图的短事务、记录耗时/失败阶段，不承诺零成本；不得持锁做HTTP/DNS或等用户。本RBAC锁内随机Token生成是本地操作。
  • 参数临时修改是连接级行为，必须在业务读取前恢复；恢复不了则失效连接。不能因为pool默认会rollback就假定PRAGMA会自行还原。
  • 当前机制针对已核验的原生sqlite3事务模式；其他连接事件或自动事务模式导致BEGIN前已物理开启时拒绝继续，S0核验不能省略。未来支持新模式另补兼容方案，不走无保护fallback。
  • 不新增字段，无数据迁移。撤回代码会重新暴露已知缺口，不能将不安全旧版本当作等价安全回退；紧急情况下可临时限制相关编辑入口，须按发布维护流程明确决定，不在本批自动加开关。
  • 该保护不等于全仓授权写入、任务调度、外部缓存或跨库审计原子性；SQLite不同文件/多个业务bind也不在该单事务保证内。任务和其他写入口继续按独立证据列风险。
