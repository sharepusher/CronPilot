# 集成测试分层策略（2026-09）

状态：待确认

## 1. 问题

### 1.1 现状

CronPilot 当前有 659 个单元测试，全部使用 `sqlite:///:memory:` 内存数据库。
这一约束源自 2026-08 一次真实事故——测试代码通过 `from manage import db`
绑定到开发数据库 `datas/job_log.sqlite`，`tearDown` 中的
`db.drop_all()` 删除了全部 11 张业务表，导致服务全站 500。

事故后项目规范强制要求所有测试使用内存数据库。这解决了隔离问题，但引入了新的盲区。

### 1.2 in-memory SQLite 的盲区

| # | 盲区 | 根因 | 实际案例 |
| --- | --- | --- | --- |
| 1 | ID 复用场景 | 内存库每次 `create_all` 后 ID 从 1 开始，永远不会复用； 真实 SQLite 不用 AUTOINCREMENT 时删除行后 ID 会被复用 | 2026-09 IntegrityError 事件：调试产生的 test 任务被清理后 SQLite 复用了旧 ID，撞上 `task_groups` 残留记录 |
| 2 | 跨表约束残留 | 内存库无历史数据，UNIQUE 约束永远不会因残留记录而冲突 | 同上——`task_groups (task_id, group_id)` UNIQUE 冲突 |
| 3 | ensure\_business\_tables 补列逻辑 | 内存库每次 `create_all` 建全表，ALTER TABLE ADD COLUMN 逻辑从未被实际测试 | 生产升级时若补列 SQL 有语法错误，单元测试无法发现 |
| 4 | scope 持久化全链路 | 单元测试只验证 helper 函数（如 `_apply_api_scope`）， 不验证 HTTP POST → validate → normalize → create → DB 行的完整链路 | R7 评估发现 B-15 API scope 注入后经 `validate_cron_form` 丢失——单元测试通过但功能实际不可用 |
| 5 | 并发/WAL 行为 | 内存库是单连接，无 WAL 模式、锁等待、busy timeout 等行为 | scheduler 与 web 请求并发写入时的锁竞争在内存中不可复现 |

### 1.3 与预期差距

正常服务的测试应该能在真实数据库引擎上运行。CronPilot 的约束是 SQLite（文件型，无独立服务进程），
测试隔离的核心诉求是**不能连开发库**，而不是**不能用真实 SQLite**。

## 2. 根因

2026-08 事故后的规范将"使用真实数据库"和"连接开发库"混为一谈，一刀切为 in-memory only。
这是合理的应急措施，但未后续补充"隔离的真实数据库测试"这一层。

根本原因：**测试分层策略缺失**——只有"快速单元"和"依赖运行服务的集成"两个极端，
缺少"进程内 + 真实数据库"的中间层。

## 3. 方案：三层测试架构

### 3.1 保留现有层级

| 层级 | 数据库 | 数量 | 变更 |
| --- | --- | --- | --- |
| L1 单元测试 | `sqlite:///:memory:` | 659 | **保持不变**——快速、隔离，覆盖函数逻辑和权限矩阵 |
| L3 HTTP 集成测试 | 对运行中服务 | 11 | **保持不变**——auto-detect :5001/:5860 |
| L4 冒烟/E2E | smoke\_routes / verify\_\*.sh | 86+ | **保持不变** |

### 3.2 新增 L2：持久化集成测试

**核心思路**：使用 `tempfile.mkstemp(suffix='.sqlite')` 创建临时 SQLite 文件，
测试在该文件上运行，结束后删除。既测到真实 SQLite 行为，又完全隔离不碰开发库。

#### 基础设施：`tests/integration_base.py`

```
import os
import tempfile
import unittest

from app import create_app, db

class PersistentDBTestCase(unittest.TestCase):
    """使用临时 SQLite 文件的集成测试基类。

    每个测试类创建一个独立的 .sqlite 文件，测试结束后自动删除。
    相比 in-memory：
      - 测试到真实的 ID 分配/复用行为
      - 测试到跨表约束的持久化效果
      - 测试到 ensure_business_tables 的补列逻辑
    相比连开发库：
      - 完全隔离，不会误伤 datas/job_log.sqlite
    """

    @classmethod
    def setUpClass(cls):
        cls._db_fd, cls._db_path = tempfile.mkstemp(suffix='.sqlite')
        app = create_app('testing')
        app.config['SQLALCHEMY_DATABASE_URI'] = f'sqlite:///{cls._db_path}'
        app.config['TESTING'] = True
        app.config['WTF_CSRF_ENABLED'] = False
        cls.app = app
        with app.app_context():
            db.create_all()
            cls._seed_data()

    @classmethod
    def tearDownClass(cls):
        with cls.app.app_context():
            db.session.remove()
        os.close(cls._db_fd)
        os.unlink(cls._db_path)

    @classmethod
    def _seed_data(cls):
        """子类覆写以添加种子数据。"""
        pass
```

#### 测试文件 1：`tests/test_cron_persistence.py`

覆盖以下场景：

| # | 场景 | 验证内容 |
| --- | --- | --- |
| 1 | 创建 GROUP 任务 | `cron_infos.scope_type='GROUP'` + `task_groups` 行存在 |
| 2 | 创建 GLOBAL 任务 | `scope_type='GLOBAL'` + 无 `task_groups` 行 |
| 3 | 更新任务组归属 | 旧 `task_groups` 被 DELETE，新行正确写入 |
| 4 | 删除任务后 ID 复用 | 新建任务的 `task_groups` 不与残留冲突  （**复现 2026-09 IntegrityError 场景**） |
| 5 | 下线（retire）任务 | `status=-1` + `retire_reason` 持久化 |

#### 测试文件 2：`tests/test_api_scope_e2e.py`

覆盖以下场景（正好补 B-15 scope 持久化盲区）：

| # | 场景 | 验证内容 |
| --- | --- | --- |
| 1 | 全局 token POST `/api/cron` | DB 中 `scope_type='GLOBAL'`，无 `task_groups` |
| 2 | 单组 operator token POST `/api/cron` | DB 中 `scope_type='GROUP'` + `task_groups.group_id` 正确 |
| 3 | 多组 operator 指定 `group_name` | 正确关联到指定组 |
| 4 | 多组 operator 不指定 `group_name` | 返回错误（需指定组） |
| 5 | operator 指定外部组 | 返回 403 |

### 3.3 CI 集成

L2 测试使用临时文件，**无需运行中的服务**，可以直接加入 CI 的 `unittest discover`：

```
# 文件名以 test_ 开头，unittest discover 自动发现
# 无需修改 .github/workflows/unit-tests.yml
# L2 测试自带 setUpClass/tearDownClass，与 L1 测试共存
```

如需区分层级（比如 CI 只跑 L1，本地跑 L1+L2）：

```
# 环境变量控制
SKIP_PERSISTENT_DB_TESTS=1 python -m unittest discover -s tests -p "test_*.py" -v
```

## 7. 风险

| 风险 | 缓解 |
| --- | --- |
| 临时文件残留（测试异常退出时 `tearDownClass` 未执行） | `tempfile.mkstemp` 创建在系统临时目录，OS 定期清理； 另可在 CI 中加 `find /tmp -name '*.sqlite' -mmin +60 -delete` |
| SQLite 文件 I/O 使测试变慢 | SQLite 临时文件性能接近 in-memory（OS page cache）， 5 个新测试增量 < 2 秒 |
| Batch 2 测试先于 B-15 修复，会产生测试失败 | 先实施 Batch 1，Batch 2 与 B-15 修复同步实施 |

## 8. L2.5 MySQL 容器测试层（后续专题）

**背景**：CronPilot 生产环境通常使用 MySQL，而 L2 测试使用临时 SQLite 文件。
SQLite L2 覆盖了 ~80% 的 service 层逻辑（后端无关的 ORM 行为），
但以下 MySQL 特有场景需要额外的 L2.5 层来覆盖。

### 8.1 SQLite 与 MySQL 的关键差异

| 差异 | SQLite | MySQL | 影响 |
| --- | --- | --- | --- |
| ID 分配 | `INTEGER PRIMARY KEY` 无 AUTOINCREMENT 时复用已删除 ID | `AUTO_INCREMENT` 不复用（除非 TRUNCATE） | ID 复用引发的 IntegrityError 仅在 SQLite 出现 |
| 事务隔离 | 默认 SERIALIZABLE（文件锁） | 默认 REPEATABLE READ（行锁） | 并发写入行为不同 |
| 字符串比较 | 大小写敏感 | 取决于 collation（utf8\_general\_ci 不敏感） | 用户名/任务名查重结果可能不同 |
| ALTER TABLE | 不支持 DROP COLUMN / MODIFY | 完整支持 | ensure\_business\_tables 补列逻辑差异 |
| FK 约束 | 默认关闭 | 默认启用 | orphan 记录清理行为不同 |

### 8.2 方案：Docker Compose 测试服务

```
# docker-compose.test.yml
services:
  mysql-test:
    image: mysql:8
    environment:
      MYSQL_DATABASE: cronpilot_test
      MYSQL_ROOT_PASSWORD: test
    ports:
      - "3307:3306"
    tmpfs:
      - /var/lib/mysql  # 内存文件系统加速
```

#### 测试基类扩展

```
@unittest.skipUnless(
    os.environ.get('CRONPILOT_MYSQL_TEST_URI'),
    'CRONPILOT_MYSQL_TEST_URI not set — skip MySQL tests'
)
class MySQLTestCase(unittest.TestCase):
    """MySQL-specific integration tests.

    启动方式：
      docker compose -f docker-compose.test.yml up -d
      CRONPILOT_MYSQL_TEST_URI='mysql+pymysql://root:test@127.0.0.1:3307/cronpilot_test' \
        python -m unittest tests.test_mysql_persistence -v
    """
    @classmethod
    def setUpClass(cls):
        app = create_app('testing')
        app.config['SQLALCHEMY_DATABASE_URI'] = os.environ['CRONPILOT_MYSQL_TEST_URI']
        cls.app = app
        with app.app_context():
            db.create_all()
```

### 8.4 优先级与依赖

- **前置**：L2 SQLite 测试（Batch 1/2）已完成
