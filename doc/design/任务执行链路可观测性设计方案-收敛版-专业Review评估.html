任务执行链路可观测性收敛版专业 Review 评估

评估对象：专业 Review · 基准：收敛版设计 rev.5 · 日期：2026-09-15

结论：原 Review 有价值，但不能原样作为实施门槛。其评审基准为 rev.2，仍包含已被后续决策否定的“锁竞争形成一次执行记录”及“自动清理为既定策略”的假设。rev.5 已确认并写死界面、threadpool、调度抑制与审计保留边界；原 Review 中仍有效的意见已纳入实施约束。

一、逐项结论

原 Review 意见结论依据与处理
B1：双栏与列表→详情冲突采纳设计 §〇 和两个 Demo 均承诺保持既有列表→详情整页跳转，但 §5.5 残留“桌面双栏”。这是范围冲突，确认前必须统一为整页跳转；双栏另立 UI 设计。
B2：计划时间只能从 executor 提交边界取得部分采纳禁止以 next_run_time 反推、以本次 run_times 注入 ContextVar 的结论正确。当前本期运行基线是 BackgroundScheduler + threadpool，因此不能把保留但未启用的 Gevent 路径强行扩为同批交付；应明确 threadpool 是本期范围，Gevent 仅在未来启用时需补等价适配与测试。
B3：清理不级联且可能裁剪活跃记录重写处理该意见正确识别了现有自动物理删除路径，但 rev.4 已明确取消自动删除：任务仅下线，JobLog、items 与 events 均为保留的生产审计证据。实施项改为取消 cron_del_job_log() 裁剪和父记录删除入口，并测试任务下线后历史记录仍可读；不实现新的级联删除。
M1：pending/running 已有常量，展示文案需对齐采纳现有展示为“待执行 / 执行中”。设计中的 pending 是“父记录已创建但尚未进入业务函数”，应避免“待执行”被理解成尚未被调度；建议改为“已入队”，并补展示/筛选回归。
M2：锁失败应终态化并返回父记录 ID不采纳rev.3 已明确：锁未获取时 cron_do 根本未开始，是调度抑制而非执行结果，不得创建父记录、事件或详情。保持当前 single_task() 的直接返回语义；手动执行沿用既有“正在执行中”反馈即可。
M3：未覆盖 APS max_instances采纳该抑制发生在进入 cron_do 前，和锁竞争同属非执行。应在非目标明确：本期不产品化 APS max_instances 抑制；仅依赖调度器日志/指标，避免用户误以为所有未执行都可在执行记录中查询。
M4：不得复用 trigger_delay_ms已满足，补强设计当前将 scheduled_delay_ms 放在 task.enqueued.detail，未复用旧列；应再增加一条验收断言，确保旧列语义保持“装饰器入口到函数体”的开销。
M5：新增状态的消费面未写全前提失效rev.3 不新增任何状态值，且 API 已接受既有 pending/running。不需要“新增枚举”清单；B0 应改为既有状态写入、显示、健康度与历史兼容检查。
M6：Tracer 应新增配置键与熔断阈值可选优化事件写入预算、失败隔离和熔断是必要契约；但不必在第一期新增可配置项。若新增配置键，必须满足 configs() 可达性门禁；否则使用代码内保守常量并由测试锁定行为。
M7：Batch 1–4 与 B0–B6 双轨编号采纳属于文档可执行性问题。应标明 B0–B6 为唯一权威分批，或移除前置摘要表，避免实施、验收和 Review 引用错批次。

二、原 Review 的事实偏差

  • 评审对象标注为 rev.2，而当前基准为 rev.4；原文中关于锁竞争产生执行状态、事件和详情的多处推论已过期。
  • “Gevent 两条路径同批覆盖”超出已确认的 threadpool 第一阶段范围。保留代码不等于当前产品配置与本期交付范围。
  • “Demo 不是生产 CSS 同源”已不成立：两个 Demo 直接加载生产的 console-theme.css 与 Redesign CSS；通过 /docs/ 打开时切换至 /static/css/ 路径。

三、进入实施前仍需完成的设计修订

  1. 已确认：删除 §5.5 的桌面双栏描述，保持列表→独立详情页。
  2. 已确认：本期在 threadpool 提交边界以本次 run_times[-1] 写入 ContextVar；worker 结束 reset；手动触发为 NULL；不使用 next_run_time；Gevent 不在本期。
  3. 已确认：取消按数量裁剪和父记录删除入口；任务下线后所有历史执行证据仍可读；不新增归档、清理、容量监控或备份功能。
  4. 已确认：APS max_instances 与锁竞争均只记录调度器/应用日志及指标，不产生执行记录。待实现时补齐 pending 展示文案、B0–B6 编号与旧 trigger_delay_ms 语义保护测试。
实施判断：页面、调度上下文、调度抑制和审计保留的产品决策已确认。待对 pending 文案、分批编号和旧列语义保护完成文档收口后，可进入实施确认；锁竞争或 max_instances 不产生执行记录、任务与执行证据不自动物理删除这两项 rev.5 决策应保持不变。
