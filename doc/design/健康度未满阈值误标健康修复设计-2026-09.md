# 健康度未满阈值误标「健康」修复设计

UX / 健康模型
已实施  
**日期**：2026-09-16 · rev.1（实施）  
**状态**：用户确认方案 A 后已实施 · 未满阈值失败 →「有失败」  
**实证**：任务 `testgoogle` 执行 1 次 `error`，
`consecutive_failures=1`，原 `health_status=ok` → 列表误显「健康」  
**关联**：
[OPT-P1-18 健康度统计语义（待验证 vs 退化）](健康度统计语义优化设计.html) ·
写路径 `app/services/job_health_service.py` ·
复盘 [2026-09-健康度未满阈值误标健康](../postmortem/2026-09-健康度未满阈值误标健康.html)

**用户表述：**
新任务执行不到 3 次（未达持续异常阈值）时，不能把已有失败瞎标成「健康」。

## 1. 问题

- 「健康」在用户语义 = **最近运行正常 / 当前可靠**。
- 实现语义 = `consecutive_failures < N`（默认 N=3）→ 写 `health_status=ok` → UI「健康」。
- 结果：新任务第 1～2 次失败仍显示「健康」，与最近执行列的失败矛盾，严重误导。

**矩阵（现状）：**

| 连续失败 | 写入 health\_status | 列表 badge | 用户感受 |
| --- | --- | --- | --- |
| 0（成功后） | ok | 健康 | 正确 |
| 1～N−1 | **ok** | **健康** | **错误**（testgoogle） |
| ≥ N | failing | 异常 | 正确（持续异常） |
| 从未跑 | 无行 / unknown | N/A | 正确 |

## 2. 根因

```
# job_health_service.update_job_health — 失败分支
row.consecutive_failures += 1
row.health_status = HEALTH_FAILING if consecutive_failures >= n else HEALTH_OK
# ↑ 未满阈值故意写 ok，模板把 ok 一律渲染为「健康」
```

「持续异常」阈值（≥N 才进异常面板 / 持续异常统计）与「是否可称健康」被绑死在同一枚举上。
未满 N 的失败被塞进 `ok`，展示层无第三态。

## 3. 方案

### 3.1 推荐方案 A：未满阈值失败 → 写 `unknown` + UI「有失败」

> **「健康」**仅当连续失败 = 0（可靠基线）。  
> **「有失败」**：1 ≤ 连续失败 < N（琥珀色，观察中，未达持续异常）。  
> **「异常」**：连续失败 ≥ N（与现网持续异常一致）。  
> **「N/A」**：从未执行（无 health 行，或 consecutive=0 且无 last\_run）。

**写路径变更：**

```
if outcome in FAIL/ERROR/TIMEOUT:
    consecutive_failures += 1
    if consecutive_failures >= n:
        health_status = failing
    else:
        health_status = unknown   # 原为 ok ← 本轮关键
elif outcome == SUCCESS:
    consecutive_failures = 0
    health_status = ok
```

**展示变更（dashboard 健康列 / 详情健康卡）：**

```
failing → 异常
ok → 健康
unknown 且 consecutive_failures > 0 → 有失败（新）
其它 unknown / 无记录 → N/A
```

**不做（本轮）：**

- 不改 N 默认值（仍为 3）；不把「一次失败」直接升为「异常 / 持续异常」。
- 不实现 OPT-P1-18「待验证」全套（从未成功 + failing 分层）；可后续叠加。
- 不改「持续异常」统计口径（仍 ≥3 或 health\_status=failing）。

### 3.2 备选

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| **A · 推荐** | 写 unknown + UI「有失败」 | 最小语义修正；持续异常阈值保留；历史 1～2 次失败行需回填或读侧兜底 |
| B | 仅改模板：ok 且 consecutive>0 →「有失败」 | 不改写库也能修展示；但库内仍写 ok，API/导出语义脏 |
| C | N=1，一次失败即异常 | 过噪；与「持续异常」产品定位冲突 |
| D | 新增枚举 `watching` | 更清晰，但枚举扩展面大；本轮不必 |

**历史数据：**
已存在 `health_status=ok AND consecutive_failures>0` 的行（如 testgoogle）。
方案 A 实施时须：① 写路径改正；② 展示层兜底（ok 且 consecutive>0 也显示「有失败」）；
③ 可选一次性 SQL/ensure 脚本把这类行改为 `unknown`（推荐，小脚本）。

### 3.3 交互契约

| 项 | 约定 |
| --- | --- |
| 可见文案 | 新增 badge「有失败」；「健康」「异常」「N/A」保留 |
| 颜色 | 有失败用既有 warn / overdue 琥珀色 token（`var(--cp-warn)`），禁止硬编码色 |
| 筛选 | 本轮不新增「有失败」筛选 chip（可后续）；「异常」仍只匹配 failing |
| 详情页 | 健康卡与列表同语义 |

## 4. 范围

| 路径 | 改动 |
| --- | --- |
| `job_health_service.py` | 失败且 <N → `unknown`；单测断言 |
| `_dashboard_rows.html` / 详情健康展示 | 「有失败」分支 + 历史 ok+consecutive>0 兜底 |
| CSS（pages / components） | `.health-badge.watching` 或复用 warn |
| 可选迁移 | 校正历史 ok+consecutive>0 → unknown |
| 测试 | 1 次失败 ≠ 健康；3 次仍异常；成功后回健康 |

## 5. 分批

| 批次 | 内容 | 验收 |
| --- | --- | --- |
| B1 | 写路径 + 单测（含修正既有「1 次失败仍 ok」用例） | unittest 绿 |
| B2 | 模板/CSS + 历史兜底 +（可选）数据校正 | testgoogle 显示「有失败」 |
| B3 | restart 浏览器自证 | 截图 / curl 断言 |

## 6. 验收

1. 新建任务失败 1 次 → badge「有失败」，不得「健康」
2. 再失败至 3 次 →「异常」，进入持续异常口径
3. 随后成功 1 次 →「健康」，consecutive=0
4. 存量 testgoogle：列表为「有失败」（兜底或迁移后）

## 7. 风险

- 依赖「ok ≡ 健康」的外部脚本：未满阈值失败不再是 ok —— 属预期纠正。
- 与 OPT-P1-18：「有失败」是未满 N；「待验证」是已满 N 且从未成功。文案勿混用。
- 回滚：恢复写 ok + 去掉「有失败」分支。
