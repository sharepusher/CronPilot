# 执行链路可观测性：页面改造对比

严格复用现有 Redesign shell、令牌与组件语义；本方案是在既有页面上增量改造，不新增独立控制台。

**范围结论：**不新增导航、不新增“链路中心”页面、不新增 events API。用户仍沿用“执行记录 → 详情”与“任务详情 → 最近执行 → 详情”两条既有路径。

## 涉及页面与入口

3 个既有页面 / 2 个既有详情入口

**执行记录**`/job_log_list` 与 `/job_log_all_list`。补充状态筛选和短链路摘要。

**任务详情**`/task_detail_v2` 的“最近执行”。从二元点扩展到完整状态语义。

**Run Inspector**`/job_log_detail`，仍是唯一详情页。在保留原区块的前提下新增时间线。

## A. 执行记录列表

侧栏“执行记录” / 任务详情“查看全部”

现状：结果列表AS-IS

筛选和状态仅围绕终态；仅凭结果文本难以判断链路停在何处。

| # | 返回内容 | 耗时 | 结果 |
| --- | --- | --- | --- |
| 10481 | 请求超时 | 5.0s | ● 超时 |
| 10480 | — | — | ● 未知 |

改造后：执行入口TO-BE

保留表格结构；状态表达完整，摘要说明详情页能回答什么。

| # | 链路摘要 | 耗时 | 结果 |
| --- | --- | --- | --- |
| 10481 | HTTP 已发出 · 等待 5s 后超时 | 5.0s | ● 超时 |
| 10480 | 请求已发出 · 最终结果未知 | — | ◎ 执行中 |

变化：列表仍用于筛选和定位；点击既有“详情”入口后才阅读完整链路。

## B. 任务详情的最近执行

任务详情右侧“最近执行”卡片

现状：二元状态点AS-IS

- 10:32:00● 成功1.2s
- 10:27:00● 失败5.0s
- 10:25:11● 失败—

问题：执行中记录可能被二元展示误读为失败。

改造后：状态机语义TO-BE

- 10:32:00● 成功1.2s
- 10:27:00● 超时5.0s
- 10:25:11◎ 执行中—

变化：终态失败与未完成记录按真实语义显示；锁竞争不会创建此处的执行记录，详情跳转 URL 不变。

## C. Run Inspector 执行详情

执行记录“详情” / 最近执行项

现状：终态详情平铺AS-IS

执行 #10481⏱ 超时5 分钟前

HTTP **—**耗时 **5.0s**失败原因 **请求超时**

请求

POST https://api.example.com/v1/orders/trigger

响应

无响应内容

问题：不知道请求前经过哪些步骤、请求何时发出，也难以查看未终态记录。

改造后：先链路、后下钻TO-BE

执行 #10481⏱ 超时5 分钟前

计划延迟 **18ms**HTTP **—**耗时 **5.0s**触发方式 **定时调度**

执行链路 新增 · 系统事件 + 业务日志

- **任务入队**T+0ms · 计划时间 → 实际进入 18ms
- **安全校验**T+20ms · DNS Pinning 校验通过
- **发起 HTTP 请求**T+24ms · POST /v1/orders/trigger
- **请求超时**T+5.00s · 等待超过任务配置阈值

响应 / 诊断

请求在 5s 超时阈值内未返回响应。

变化：请求、响应、业务日志、元数据均保留；时间线成为首要诊断区，详情只消费 Presenter 的角色化 DTO。
