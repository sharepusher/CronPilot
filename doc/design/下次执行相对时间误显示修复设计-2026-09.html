下次执行相对时间误显示修复设计

Bug 已实施
日期：2026-09-16
状态：方案 A 已确认并实施（CronTrigger 同源）
影响面：任务中心「下次执行」列、任务详情「下次执行」、逾期判定、format_cron_expression

一句话问题： 当任务只填了「小时」字段（分钟留空）时，调度器按「该小时的第 0 分」触发， 但页面把空分钟当成 *（每分钟），于是「下次执行」长期显示 in <1 min， 与真实调度、与同页「调度策略」人话文案互相矛盾。

0. 问题表述（澄清版）

0.1 用户看到什么

  • 任务中心列表里，新建任务与旧任务的「下次执行」列经常都是 in <1 min（或偶发 in 1 min）。
  • 同页「调度策略」人话却写着类似 「每 2 小时 的第 0 分」——语义上应在约 1～2 小时后，而不是 1 分钟内。
  • 易被误判为：调度器卡死、时钟错误、或「所有任务马上要跑」。

0.2 实际发生了什么（事实）

  • 调度本身往往是对的：注册进 APScheduler 时，空的 minute 字段不会传入 CronTrigger；库会把更细粒度字段默认成 0，因此 hour=*/2 实际是「每 2 小时的整点」。
  • 坏的是展示层与逾期层的「伪 crontab」拼装：多处把空字段写成 Unix cron 的 *，得到 * */2 * * *（偶小时内每分钟一发），相对时间自然永远 < 60s。

0.3 什么情况会中招 / 不会中招

配置形态是否误显示说明
只填 hour（如 */2），minute 空 会（高发） 真实：0 */2 * * *；展示：* */2 * * *
只填 minute（如 */2），hour 空 通常不会系统性误导 真实与展示均为「每 2 分钟」；靠近触发点时出现 in <1 min 是正确的相对时间
minute 与 hour 都显式填写 一般不会 两边语义一致
一次性 run_date 走另一分支 本 bug 主路径是周期 cron 字段

本地 2026-09-16 抽样：活跃任务 test123 / testgoogle 为「空 minute + hour=*/2」；newtest123 为「minute=*/2」。前两者稳定误报 <1min；第三者在触发点附近也会显示 <1min，属正常。

1.2 同一任务三套口径对照（2026-09-16 实测）

口径空 minute + hour=*/2minute=*/2

1.3 APScheduler 默认规则（库行为，非猜测）

APScheduler 3.x CronTrigger.__init__（字段顺序 year→…→hour→minute→second）：

  • 未传入的粗粒度字段 → *
  • 一旦某个字段被显式传入，其后更细粒度且未传入的字段 → 使用 DEFAULT_VALUES（其中 minute=0、second=0）
# 等价实验
CronTrigger(hour='*/2')
# → hour=*/2, minute=0, second=0   （下次整点）

CronTrigger(minute='*', hour='*/2')
# → 偶小时内每分钟触发   （与错误展示表达式同形）

CronPilot 注册路径 build_scheduler_kwargs()：仅把非空的 day/hour/minute/… 放进 kwargs → 正好踩中「省略 minute → 默认 0」这条规则。

2. 根因（深度）

2.1 直接根因：两套「空字段」语义

路径空 minute 的含义代码位置
调度注册 省略字段 → APScheduler 默认 0 app/services/cron_service.py · build_scheduler_kwargs
下次执行 / 逾期 or '*' → Unix cron「每分钟」 app/services/dashboard_service.py · compute_next_runs / compute_overdue_map
任务详情下次执行 同上 cif.minute or '*' app/main/views.py 任务详情分支
表达式展示 同上 → 显示 * */2 … format_cron_expression
人话展示 空 minute 已按 0 处理 humanize_schedule（小时级分支）

因此不是「相对时间格式化函数写错了」：_format_relative_time(sec<60) → 'in <1 min' 本身正确；错在喂给它的 next_dt 来自错误 crontab。

2.2 结构性根因

  1. 缺少「有效调度字段」单一事实源：注册用 kwargs 省略语义，展示/预测用「空=星号」语义，无人强制对齐。
  2. Unix crontab 习惯被误套到 APScheduler 局部字段模型：表单五格各自可空；空格在 APScheduler 里 ≠ crontab 里的 *。
  3. 表单 hint 强化误解：分钟 placeholder 为 *，用户以为「不填=每分钟通配」；而小时填 */2、分钟不填时，产品人话与调度却按「第 0 分」执行——三方（用户心智 / 调度 / 下次执行）只有调度与人话碰巧一致，下次执行与表达式展示站在用户心智一侧却与调度相反。
  4. 测试只覆盖「显式填全」或「仅 minute」场景：无「只填 hour、minute 空」的 next_run 断言，故长期潜伏。

2.3 次生影响：逾期判定也被拉歪

compute_overdue_map 用同一错误表达式估算 interval：

  • 错误：* */2 * * * → interval ≈ 60s，阈值 max(120, 600)=600s
  • 正确：0 */2 * * * → interval ≈ 7200s，阈值 max(14400, 600)=14400s

结果：只填小时的任务更容易被标成「逾期」，与「下次执行永远 <1min」同一根因。

4. 方案

4.1 目标语义（产品契约）

「下次执行 / 表达式展示 / 逾期间隔」必须与 该任务实际注册进 APScheduler 的 Trigger 一致。
不以 Unix crontab「空格=星号」习惯覆盖 APScheduler 局部字段默认值。

4.2 备选方案

方案做法优点缺点取舍
A · CronTrigger 同源（推荐） 复用 build_scheduler_kwargs 构造 kwargs， 用 CronTrigger(**kwargs).get_next_fire_time(None, now) 算下次； 表达式展示从 Trigger 字段（含默认值）格式化。 与调度器行为零漂移；覆盖 hour/day/dow 等组合默认 展示层依赖 APScheduler；需注意 timezone 与 naive/aware 推荐
B · 手写「空→0」规则 若 hour/day/dow 非空且 minute 空 → minute='0'；再喂 croniter 改动面小、不引 Trigger 需复刻 APScheduler 级联默认，易再漂移（second/day 等） 不推荐作长期方案
C · 表单强制写库 minute=0 保存时把空 minute 落成 '0'；迁移历史数据 DB 自描述 不修展示算法则历史空值仍错；改变用户「空」与「0」的存储约定；需迁移 可作增强，不能单独替代 A
D · 改调度语义去迁就展示 注册时显式传 minute='*' — 改变真实触发频率（每分钟），破坏现网「每 N 小时整点」行为 禁止

8. 风险

  • 相对时间文案突变：修复后 hour-only 任务从「<1min」变为「in 1h」等，属预期纠正；需在 RELEASE 用用户语言说明「展示与真实调度对齐」，避免被当成调度变慢。
  • 逾期数量变化：阈值变大后，部分误标逾期会消失——属纠正，不是功能回退。
  • timezone / DST：CronTrigger 带 tz；须在 helper 内统一，避免 aware/naive 相减异常（单测覆盖）。
  • 回滚：仅展示/逾期计算，回滚共享函数调用即可；无 DB 迁移则回滚成本低。

9. 沟通备忘（为何初版表述不清）

  • 不宜说「所有任务 next 都坏了」——高频 minute 任务靠近触发点时 <1min 是对的。
  • 不宜说「调度坏了」——用户若只看执行记录间隔，hour-only 任务仍按约 2 小时跑。
  • 准确说法：「空分钟字段在展示层被当成每分钟，与调度器默认第 0 分不一致，导致下次执行相对时间被压到 <1min。」
