1. 问题

当前注册审批列表对按组管理员使用逗号字符串上的 LIKE '%gid%' 判断组交集，并从 Session 读取角色、全局状态和组集合。两个行为组合后会造成组号子串碰撞和降权后旧 Session 继续扩大读取范围。

问题当前事实影响
组号子串碰撞组 1 使用 LIKE '%1%'，会命中 10、11、21。范围外申请、用户名、角色、业务组、原因等信息可能被展示。
旧 Session 扩权读取_actor_bypasses_scope() 和 scoped 列表均读取 Session 的 role/group_ids；角色降权和组收窄不会同步刷新现有 Session。数据库已从 global 降为 scoped，或当前组集合已收窄后，旧会话仍可能看到全量或旧组申请。停用用户已由全局会话有效性守卫拦截，不属于该未修缺口。
分页后过滤admin 申请在数据库分页后再由 Python 删除不满足子集覆盖的行。页面行数、total、页数和待审批 badge 可能不一致或出现空页。
列表与计数口径分裂列表存在 admin 二次过滤，pending count 没有同等过滤。用户看到的待审批数量大于真实可见/可处理数量。
安全定性：这是 P1 读取隔离与信息机密性问题，不是当前的写入越权。审批写操作已有数据库当前事实守卫，但“最后写不进去”不能抵消“先看到了范围外申请”的泄露风险。

2. 根因与已验证实现事实

  • RbacRegistrationRequest.group_ids 是 String(255)，承载空串、单个 ID、逗号 ID 列表或 __ALL__，不是关系型组关联。
  • RegistrationRequestRepository.paginate_by_groups() 与 get_pending_count_by_groups() 均使用无分隔符边界的模糊匹配。
  • registration_review() 使用 Session 判断 bypass 和 actor 组集合；写授权已有 _load_scope_assignment_actor() 从数据库读取当前用户、启用状态与组关系，但读取列表未复用这一安全语义。
  • admin 申请的“请求组必须是 actor 当前组的子集”发生在分页完成后，因此无法修正 SQL 的 total/count/page。

3. 目标、范围与非范围

3.1 目标

  • 组 1 绝不匹配组 10/11/21；每个 ID 必须按完整 token 判断。
  • 列表读取仅信任 Session 中的 actor ID，角色、启用状态、组关系从数据库当前事实解析；失败时 fail-closed。
  • 列表 items、total、页数、筛选、搜索和 pending badge 使用同一授权谓词。
  • admin 申请要求完整子集覆盖；viewer/operator 申请按精确组交集展示；__ALL__ 仅数据库当前全局 actor 可见。
  • 分页前完成授权过滤，不再修改 page_data.items 掩盖查询错误。

3.2 范围

  • GET /rbac/registration_review 的 actor 解析、列表查询、计数和分页。
  • 注册申请 Repository 的 scoped 查询及其 SQLite/MySQL 兼容实现。
  • 角色降权和组关系收窄后的旧 Session 读取立即收敛；停用后的既有会话失效行为作为防回退基线。
  • Repository、路由、浏览器正反路径和文档证据。

3.3 非范围

  • 不改变 F-01 已完成的批量审批三态反馈。
  • 不改变审批写入策略、用户新增/编辑授权或 Session 全局撤销机制。
  • R2 短期闭环不强制迁移字段；关联表规范化作为独立后续演进，实施前须另行设计字段语义、双后端迁移和回滚。

6. 推荐实现设计

6.1 数据库当前 actor 上下文

新增或复用一个无副作用的只读 actor Scope 解析器。Session 仅提供 user_id，解析器从数据库读取用户存在性、启用状态、角色、用户名与当前组关系，再计算是否 bypass。不得使用 Session 的 role/group_ids 作为查询授权事实。

Session actor user_id → DB 当前用户存在且 active → DB 当前 role / username / UserGroup → 当前是否拥有 user:manage → global / scoped(group_ids) / denied → 读取异常一律 denied，并记录服务端异常

6.2 查询级精确 Scope

短期在保留字符串字段的前提下，必须按完整 token 匹配而不是子串匹配，并明确验证 SQLite/MySQL 等价性。实现形式由 R2-1 代码阶段在双后端能力核验后确定；本设计不凭印象锁定未经验证的 SQL 函数。

  • viewer/operator：申请组集合与 actor 组集合存在精确交集。
  • admin：申请组集合必须为 actor 组集合的非空子集。
  • __ALL__：只进入 global actor 查询。
  • 空串、非法 token、重复 token：scoped actor 下 fail-closed；不得因为解析异常扩大可见性。

6.2.1 R2-2 前置技术决策（DEC）

进入 R2-2 编码前必须形成并记录一个可复核的查询 DEC，在以下方向中作出明确选择：双后端精确 token 表达式、规范化派生查询，或申请—业务组关联表。DEC 必须给出 viewer/operator 精确交集、admin 完整子集、__ALL__、空/非法 token 的 SQLite/MySQL 等价样例和性能基线。

升级条件：如果 CSV 方案不能在 SQLite/MySQL 上以可审计且性能可接受的方式实现 admin 完整子集，禁止退回分页后 Python 过滤；必须升级为关联表设计，并重新完成字段语义、双后端迁移、回滚和用户确认。

6.3 列表、count 与分页同源

Repository 应以一个权威 scoped 查询为源，分页 total 与 pending count 复用同一授权谓词，仅额外叠加状态或用户名条件。删除 View 中分页后的 page_data.items 过滤。任何优化都不得让 count 使用比列表更宽的条件。

6.4 中期规范化方向

关联表是消除字符串查询债务的长期正确方向，但不是本轮短期安全闭环的隐含动作。若后续迁移，必须先逐字段回答 group_ids 的空串、__ALL__、顺序、重复和历史非法值语义是否被新结构等价表达，并设计 SQLite/MySQL 双后端迁移与回滚。

10. 风险与控制

风险控制回滚原则
过度收紧导致合法申请不可见R2-0 同时固定交集正向、admin 子集正向及 global 正向。可回滚查询优化，不得恢复 Session 授权或无边界 LIKE。
列表修了但 count 未修每个负向用例同时断言行、total、pages、badge。共享谓词未统一前不得交付。
数据库读取故障造成 500固定通用 HTTP 500 + 服务端 traceback，禁止异常原文返回；不得伪装为“暂无申请”。不得以 Session 放行或空列表作为可用性降级。
字符串精确查询性能下降用明确数据量基线测量；中期规划关联表与索引。性能优化不能牺牲精确授权。
SQLite/MySQL 行为分叉实现前验证两端表达式与大小写/空值行为；迁移/SQL 按后端分支。任一后端未证明则停止 R2-2。

11. 完成定义

只有组号精确匹配、数据库当前 actor、查询级 admin 子集、列表/count/page 同源、角色降权与组收窄的旧 Session 收敛、302/403/500 外部契约和五类角色浏览器矩阵全部成立，才能关闭 F-02。R2-0 完成只代表风险被测试稳定捕获，不代表问题已修复。

完成判定：上述条件均已由 R2-0–R2-4 的自动化、双后端性能和真实浏览器证据证明，详见 R2-4 最终验收。F-02 于 2026-10-26 关闭。
