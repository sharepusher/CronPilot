1. 问题与根因

D1 实施前，DB 提交与调度写入分离，Web 有提交后调度异常提示，共享/API 更新仍可能吞掉暂停异常。需要对可检测的冲突与失败明确报错。此前设计把正常接口返回也视作需要核实，增加查询依赖并可能把随后合法修改误判为前一次接口失败；现改为遵守接口的实际同步/暂存契约。

2. 已核实的接口语义

已读取本机 Flask-APScheduler scheduler.py:add_job、APScheduler schedulers/base.py:add_job/_real_add_job、SQLAlchemyJobStore.add_job/update_job。调度器已启动时，SQLAlchemyJobStore 在其 engine.begin 内完成写入，再返回；正常返回可按该契约视为调度写成功，无须再查一次。

调度器停止时 add_job 可仅加入 pending 列表，正常返回不代表持久化完成；这是接口状态语义，不是接口失信。需要调度更新的编辑路径应先确认已启动，未启动明确报错，不把 pending 当同步成功；并发停止也须验证实际返回/异常，不假设状态检查构成锁。需要封装保证时由窄适配器检查返回的 pending 属性，仍不额外查询 JobStore。

底层正常返回后，项目封装的日志、监听器、唤醒等后续步骤也可能异常；这种异常不直接证明存储失败。已完成的 W0 隔离实验验证“JobStore 写后抛异常”可发生，属于异常核实依据，不是正常返回也要查询的理由。

3. 推荐流程

  1. 执行原有授权、输入校验、Web 三方比较与 ORM 版本条件写。保存前冲突回滚，提示“任务已被修改，本次未保存，请重新加载后确认”，不操作调度器。
  2. flush 成功后、commit 前捕获本次 revision、调度目标和状态。commit 结果未知时提示“保存结果待核实，请勿重复提交”，不盲目调度；确定失败沿既有失败契约处理。
  3. 无调度有效变化时保持 W1：不调用调度器，也不查询 JobStore。
  4. 需调度应用时，以新鲜 DB 视图核对本次 revision 和状态。发现后续修改，停止旧应用，提示“配置已保存，但任务随后发生变更，本次未继续更新调度，请刷新核实”。
  5. 按已核实同步接口应用目标。正常返回即按接口契约记录调度调用成功，不调用 get_job 验证。之后的新鲜 DB 版本检查仅识别后续并发变更，不验证调度接口是否成功。
  6. 确定未生效的失败直接明确报错；不能确定是否已生效的异常，才进入第 5 节查询核实。不得自动重发调度写或无条件恢复旧配置。
  7. 应用后发现 DB 版本变化，明确报告“配置已保存，但任务有后续变更，请刷新核实”；这是并发变更结果，不声称先前调度接口失败。DB 并发检查不可读时提示“配置已保存、调度调用成功，但无法完成并发核验”，不得误称调度结果未知。

4. 结果判定与异常分类

事实结果
保存前冲突错误；本次未保存，保留 R/T0。
配置提交未知错误；保存结果待核实，不调度。
调度接口同步正常返回，版本检查无冲突成功；JobStore 查询次数为 0。
已观察到后续 DB 版本并发变更错误；明确配置已保存，不用查询到目标相同来掩盖版本变化。
有充分证据证明本次应用尚未写入就失败错误；配置已保存，调度更新失败。无需额外查询证明。
不确定异常，查询后版本有效且目标匹配成功；内部保留异常已核实记录。确认当前目标达成，不证明由本次调用独自造成。
不确定异常，查询明确不匹配错误；配置已保存，当前调度与目标不一致。
不确定异常且查询失败或证据不足错误；配置已保存，调度结果待核实。

分类必须基于失败阶段和接口证据，不能只看异常类名；例如网络断连、写入后的事件处理/日志异常可能已经应用，任意 OperationalError 也不能一概视为确定未写。设计无法证明确定未写的异常，保守进入有限查询分支；不能把全部异常都当成失败。

5. 仅异常时的查询确认

按新鲜 DB 版本 → 已启动目标 JobStore 中的 get_job → 新鲜 DB 版本核验；期间观测到版本不同优先报告并发变更。DB 不可读则不能确认本次目标，提示相应核验失败，不透传原异常。查询只做一次有限核实，不增加轮询、常驻对账或自动重复写入。

读取固定注册 store 的任务：核对 ID、func_ref、任务参数/kwargs、完整 trigger 及暂停/运行状态；cron 使用与现有 build_scheduler_kwargs 同源的默认与 timezone，比较全部有效字段和行为属性；date 比较实际时刻。不能只看 job ID、trigger 总字符串或 next_run_time。涉及执行策略的默认期望必须读实际配置，不能猜常量。

查询已启动调度器时从 JobStore lookup；停止时可能只有 pending，不能证明持久化。未来任务缺失可判不匹配；已到期一次性任务可能正常完成后被移除，不能仅凭缺失认定写入失败，缺少生命周期证据则待核实。不建立操作表，不能用目标匹配证明操作归属。

6. 事务、更新接口与兼容

保持 Web 保存事务所有权；共享/API 辅助核验采用独立只读连接，不 rollback/commit/flush 调用者待写事务。既有隔离 双后端实验 证明 identity map 可能旧而独立读取可见最新提交。正常路径仍有少量主键 DB 版本读取，它们用于冲突检测，不是 JobStore 二次验证。

D1 已为 register_cron_job 增加编辑调用方显式暂停目标参数：暂停时单次 add_job(..., replace_existing=True, next_run_time=None)，不再先创建运行态后 pause。创建/其他未传参数的入口保持兼容。保留现有编辑在真实调度变化时创建缺失 job 的 replace 语义，不在说明等编辑中顺手修复。W0 已验证该参数行为，D1 又完成真实 JobStore 回归。

共享服务成功保持模型或既有 tuple 返回；已引入 EditWriteError 窄内部失败类型供 upsert 映射到既有错误二元组，两条 API 保持 errcode/errmsg 信封。Web 沿用现有错误分支并按“未保存/已保存/并发核验失败”校准标题和安全正文，原生回退保留原始基线。未知异常不能直接 str(e) 返回。

9. 风险、性能与评估

正常路径不新增 JobStore 查询，避免不必要故障依赖；版本检查增加少量按主键 DB 读取。异常时一次查询与必要连接恢复有额外成本，超时和连接池耗尽必须验收，不给未经测量的收益或 SLA。查询后仍可能发生后续修改，API 无客户端旧基线；本方案承诺检测到的冲突报错，不承诺检测所有未来漂移或消除旧写。

评估：准确性上遵守已启动调度器的同步契约，并明确停止/pending 例外；合理性上符合低频修改与明确错误目标；专业性上将接口结果、并发版本和 DB 提交事实分开。D1 在本批已验证范围内通过：停止/pending、版本冲突、异常目标比较及两个 API、Web Ajax/原生均有回归证据。已用容量为 1、无溢出的真实 QueuePool 占满连接，验证获取连接超时的安全报错及零调度写；未做持续吞吐压力测量，不承诺性能 SLA。回退恢复旧漏报边界，已提交数据不能靠回退撤销；原开发库索引异常不在本批授权修复范围。

范围外发现：现代 /api/cron 显式传 timeout_sec=5 时，Schema 输出 int，而 cron_validator.normalize_cron_form 对其执行 .strip()，可触发既有 500；本批端点验收未传该可选字段，不掩盖该问题，也未擅自扩大修复范围。该问题已于 2026-11-02 经用户授权按独立设计修复，最新专项和 D1 端点回归显式携带此字段通过；以上描述保留为 D1 当时的验收边界。D1 保持原生成功返回既有 JSON 契约，新增错误页显示安全提示；不宣称原生成功已改为重定向。
