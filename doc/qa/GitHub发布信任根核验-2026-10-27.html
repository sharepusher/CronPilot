3. 核心风险分析

3.1 远端仍使用旧 workflow（P0）

本地提交完成不等于远端生效。在 061f73f 进入默认分支前，新 tag 仍会使用旧 workflow：构建、验证和发布共享写 token，缺少严格 tag 校验、Environment 隔离和远端资产内容比对。因此“当前不创建新 tag”是必须的停止条件。

3.2 分支与标签信任根未加固（P0）

发布 workflow 来自被 tag 指向的 Git 提交。当 main 无保护且无 ruleset 时，应用内的最小权限设计仍可被后续直接提交改写。只修 workflow 而不保护 workflow 的代码来源，不能形成完整供应链边界。

3.3 Environment 名称存在不等于审批存在（P0 核验）

GitHub 官方文档说明：workflow 引用不存在的 Environment 时，GitHub 会自动创建同名 Environment；普通 workflow 自动创建的 Environment 默认没有保护规则或 secrets。所以必须在首次 tag 演练前由管理员显式确认审批者和允许的部署分支/tag。

4. 建议的安全执行顺序

  1. 先配置远端保护：为 main 创建活动 branch ruleset，至少禁止 force push/删除并要求 PR；为 v*.*.* 创建活动 tag ruleset，限制创建、更新和删除主体。
  2. 显式配置 release Environment：设置 required reviewers，部署来源只允许受保护的发布 tag；不依赖 workflow 首次运行隐式创建。
  3. 收紧 Actions 仓库默认值：默认 GITHUB_TOKEN 只读；关闭 Actions 创建/批准 PR；保留 workflow 内 publish Job 的显式最小 contents: write。
  4. 通过 PR 纳入 061f73f：不在未保护 main 上直接 push 作为正常发布流程的范例。
  5. 再做受控演练：用新版本 tag 验证 build Job 无写权、publish Job 等待审批、资产回读后才解除 draft。该步会产生外部状态，须另行明确授权。
