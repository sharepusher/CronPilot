# 下一步方案合理性、专业性与准确性评估

**结论：方向合理，事实依据基本准确，作为排期建议条件通过；尚不能作为可直接实施的修复设计或发布批准。**SQLite保存边界优先于一般治理与发布是合理的；需补并发胜负规则、测试执行模型、最小事务依赖盘点和最终基线绑定。

**后续状态（2026-11-02）：**RBAC用户编辑保存边界已按批准设计修复并专项验收；任务保存独立诊断仍复现同类问题，全量基线6项失败仍在。见[最新专项验收](SQLite用户编辑原子保护验收-2026-11-02.html)。下文为历史发现与当时状态，不代表整体问题已关闭。

## 1. 准确性：哪些结论有证据

- **RBAC两条服务边界反例成立：**此前本日执行的[独立连接证据](evidence/next-steps-2026-11-02/rbac-sqlite-races.json)显示user\_revoke和user\_conflict均observed=true；本轮重新读取同一代码，未把它们扩张为所有部署和所有角色的漏洞。直接服务调用证明原子保护缺口，尚不等于完整HTTP攻击链已验证。正式验收应增加真实授权修改入口对照。
- **机制依据已核实：**本轮内存诊断中，执行SELECT后SQLAlchemy逻辑事务活跃，但底层sqlite3连接未维持显式事务；SQLite方言编译with\_for\_update后无FOR UPDATE子句。该结果与当前用户服务“先读用户、再读组、后比较写入”的代码一致。它不是SQLite数据库本身不支持事务的证明。
- **环境范围：**本轮诊断使用Python 3.11.4、SQLite 3.51.2及仓库现有SQLAlchemy；诊断来自内存测试工厂，不代替线上配置、WAL模式和所有支持的Python版本核验。实际部署的连接事件/驱动配置仍需在正式设计中检查。
- **历史验收边界准确：**锁释放测试证明服务终态与测试灵敏性；串行七状态页面测试证明结果和界面，不证明服务内部独立连接交错安全。不能因新增发现抹掉旧验收价值，也不能用旧绿测否定新问题。
- **任务分支未重新证实：**旧完整复现因scheduler属性不存在失败；此前方案明确没有对任务那一例给出当前结论，这点专业且必要。后续只能标“待重新核验”，不能并入当前已复现范围。
- **发布门禁需区分时态：**上一步本日术语和版本检查退出1有命令证据；Unreleased在开发期合理，尚未归档是发布前置工作，不是当前产品功能缺陷。本文未重复执行那两项检查。

## 2. 合理性：优先级与范围

先阻止越权窗口和同字段覆盖，再做最终验收、提交和发布，风险排序正确。把全仓重构、CI治理、锁热点优化放在后续，避免扩大修复面，也合理。方案没有因SQLite差异直接提出迁移数据库、关闭SQLite或引入分布式锁，取舍适度。

但“全部所有权盘点都放到后续”需要细化：受影响服务的调用方、入口rollback会结束什么、是否已有DML、同库授权修改入口以及提交所有权，必须在本次设计之前先做最小盘点。只有全仓治理可以后置。否则无法安全确定事务保护从哪里开始。

术语校准、失效脚本界定和升级说明可与方案论证并行准备；最终业务验收依赖修复完成。正式版本归档应在发布范围确定后做，不应为消除版本检查提示提前虚构发布状态。

## 3. 必须补强：并发正确性的判据

原文“不能在撤权后继续写入”过于绝对，应改为明确的串行顺序契约：

1. **撤权先完成：**授权变更先提交，保存请求随后进入其原子决策边界，应读取新权限并拒绝，不写业务或成功审计。
2. **保存先取得正确保护：**保存先建立涵盖当前授权、比较与写入的保护，竞争撤权必须等待或按明确策略返回忙；保存可以按旧的有效权限先完成，撤权随后完成。这是合法顺序，不能仅因撤权请求已经发起就要求保存失败。
3. **同字段并发：**保存决策前已经提交的新值必须被保留，并按三方比较返回冲突或等价完成；保护建立后的竞争写入不能从中间穿过。后续合法操作不应被错误禁止。
4. **不同字段与重放：**保留无关字段/范围外组，重复等价结果不增加成功审计或认证副作用；新保护不得把原本可合并的变更一律改成冲突。

这里保护的是可定义的原子决策与写入，不是承诺用户点击与所有撤权请求之间的绝对先后。该契约须在正式设计中冻结，实施与测试使用同一判据。

## 4. 必须补强：复现脚本不能直接当修复验收

现有脚本通过before\_cursor\_execute同步调用另一个连接的写入，原请求必须等它返回。这适合证明目前“竞争写入能插入”的缺口；如果修复后原请求正确持有写入保护，竞争写入会等待原请求释放，而原线程又在等待竞争写入，形成测试调度上的相互等待。

因此不能把observed=true简单改成false，也不能把任意锁超时/OperationalError当作修复成功。正式验收应使用独立执行单元、同步屏障和有界时间预算，分别观测“竞争方已尝试、尚未提交”“保护方可继续完成”“随后提交或明确忙错误”，最终校验实际顺序及两侧持久化事实。错误码、提交阶段和锁释放也要分别核验。

单元测试继续使用内存SQLite。文件锁、DELETE/WAL及独立连接集成诊断若需要临时文件，正式设计必须明确其独立工具边界、专用目录和清理责任，并就仓库“测试只用内存”规则的适用范围说明并取得明确确认；不得借此接触开发库。共享单连接内存测试不能替代文件级行为证据。

## 5. 专业性：正式设计应交付的最小内容

1. **问题与根因：**保留两条当前服务反例，核验真实Web路径；任务保存单独补证据，不以已失效的脚本作当前结论。
2. **事务所有权：**列出受影响服务调用方、路由读事务、原生SQL与ORM待写入、提交/回滚归属、失败清理；保护须在依赖当前权限/当前值的读取前建立。
3. **备选取舍：**比较SQLite适用的局部事务保护与条件写入等方案是否能覆盖授权、关系和审计。只有目标行版本条件不足以自动保护actor权限。评估数据库级写竞争对不同目标编辑的影响，不机械照抄MySQL行锁。
4. **异常及兼容：**区分事务进入时忙、写入前失败、提交结果未知，明确等待预算；自动重试须完整重做授权和比较，不能盲重试未知提交。不直接照抄新Python版本才支持的连接参数，不擅自修改全站隔离和生产超时。
5. **分批与验收：**先在隔离环境校准竞争观察方法；再最小修复已证实的RBAC路径；任务路径依据自身证据决定批次。覆盖撤权前后、目标同字段/不同字段、关系范围、无变化、等价完成、忙错误、回滚和未知提交；MySQL回归与角色浏览器各有边界。
6. **基线与交付：**修复前就保存HEAD、差异与未跟踪清单及必要内容指纹，避免混合工作区漂移；当前HEAD本身不能标识未提交内容。最终证据绑定相同内容基线，提交拆分需遵守实际依赖，不以文件夹机械拆分。先后端修复再做最终整体验收，保留升级和回滚方案。
