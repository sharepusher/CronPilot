## 1. 问题

CronPilot 全部 **9 张表、20 个时间字段**均使用 `VARCHAR(25)` 存储 ISO 8601 格式字符串
（`'YYYY-MM-DD HH:MM:SS'`）。项目同时支持 SQLite 和 MySQL 双后端，需要评估：

1. 当前方案在不同规模下的性能瓶颈在哪里？
2. 迁移到 `DATETIME`（数据库原生类型）或 `BIGINT`（Unix 时间戳）是否值得？
3. 投入产出比最优的优化路径是什么？

## 2. 现状盘点

### 2.1 字段清单

| 表 | 时间字段 | 数据量级 | 关键查询模式 | 索引 |
| --- | --- | --- | --- | --- |
| **`job_log`** | `create_time`, `started_at`, `finished_at` | **高增长**（每次执行 +1 行） | `LIKE 'date%'`, `BETWEEN`, `MAX() GROUP BY`, `ORDER BY` | 单列 + 复合 `(cron_info_id, create_time)` |
| `operation_log` | `create_time` | 中（变更审计） | `>=`/`<=` 范围 | 有 |
| `rbac_audit_logs` | `create_time` | 中（登录审计） | `>=`/`<=` 范围 | 有 |
| `cron_infos` | `created_at`, `updated_at`, `retired_at`, `last_operated_at` | 低（百级） | 展示、排序 | created\_at/updated\_at 有 |
| `job_health` | `last_run_at`, `last_success_at`, `last_fail_at`, `updated_at` | 低（= 任务数） | 展示、逾期计算中 Python 解析 | updated\_at 有 |
| `rbac_users` | `create_time`, `last_login_at`, `api_token_expires_at` | 低（用户数） | 展示、过期比较 | create\_time 有 |
| `rbac_registration_requests` | `create_time`, `update_time` | 低 | 展示 | create\_time 有 |
| `tags` | `create_time`, `update_time` | 低 | 展示 | 双索引 |
| `resource_groups` | `create_time` | 低 | 展示 | 有 |

### 2.2 当前写入方式

```
# datas/utils/times.py
def get_now_time(format='%Y-%m-%d %H:%M:%S'):
    return time.strftime(format, time.localtime(time.time()))

def get_today(format='%Y-%m-%d'):
    return time.strftime(format, time.localtime(time.time()))
```

所有写入路径统一调用 `get_now_time()` 返回字符串后赋值。

### 2.3 关键查询模式

| 模式 | 当前写法 | 出现次数 | 涉及表 |
| --- | --- | --- | --- |
| 当日过滤 | `create_time.like(today + '%')` | 5 处 | `job_log` |
| 范围过滤 | `create_time.between(beg, end)` 或 `>=`/`<=` | 4 处 | `job_log`, `operation_log`, `rbac_audit_logs` |
| 聚合 | `func.max(create_time).group_by(cron_info_id)` | 1 处 | `job_log` |
| 排序 | `order_by(create_time.desc())` | 多处 | 所有带时间列的表 |
| Python 解析 | `datetime.strptime(ct, '%Y-%m-%d %H:%M:%S')` | 3 处 | `job_log`, `rbac_users` |
| 过期判断 | `datetime.strptime() > datetime.now()` | 1 处 | `rbac_users`（API Token） |

## 3. 三种方案全维度对比

### 3.1 存储与类型特性

| 维度 | VARCHAR(25) 现状 | DATETIME | BIGINT (Unix) |
| --- | --- | --- | --- |
| 存储值示例 | `'2026-08-26 09:55:00'` | `2026-08-26 09:55:00` | `1787860500` |
| MySQL 存储大小 | 19 字节 + VARCHAR 开销 ≈ **21 字节** | **8 字节**（DATETIME） 4 字节（TIMESTAMP，Y2038 限制） | **8 字节** |
| SQLite 存储大小 | 19 字节（TEXT affinity） | 19 字节（TEXT affinity，**无原生 DATETIME**） | **8 字节**（INTEGER affinity） |
| 人类可读性 | 直接可读 | 直接可读 | 不可读，需转换 |
| 数据库可调试性 | `SELECT * FROM job_log` → 直接看到时间 | 同左 | 需 `FROM_UNIXTIME()` 或 `datetime(v, 'unixepoch')` |
| 类型安全 | 无 — `'not-a-date'` 可写入 | MySQL 强校验 | 整数校验（不排除非法值如负数） |
| 时区 | 无，隐式依赖服务器时区 | DATETIME 无时区；TIMESTAMP 有但有 Y2038 | 天然 UTC（或约定为本地） |
| 精度 | 秒级（格式决定） | MySQL 8 支持微秒 `DATETIME(6)` | 秒级（可扩展为毫秒用 13 位） |
| 空值语义 | `''` 和 `NULL` 混用 | `NULL` 清晰 | `NULL` 或 `0` 清晰 |

### 3.2 索引与查询性能

| 查询场景 | VARCHAR(25) | DATETIME | BIGINT |
| --- | --- | --- | --- |
| **当日过滤** 「今天所有记录」 | `LIKE 'YYYY-MM-DD%'`  B-tree 前缀扫描 ✓  MySQL 优化器有时保守退化全扫 | `>= DATE AND < DATE+1`  确定性范围扫描 ✓  优化器一定走索引 | `>= ts AND < ts+86400`  整数范围扫描 ✓  最快（整数比较） |
| **范围过滤** 「时间区间」 | `BETWEEN 'str1' AND 'str2'`  字符串比较 ✓（ISO 8601 字典序=时间序） | `BETWEEN dt1 AND dt2`  原生日期比较 | `BETWEEN int1 AND int2`  整数比较，最高效 |
| **MAX() GROUP BY** 「最近执行时间」 | 字符串 MAX ✓（字典序正确）  复合索引已支持 Loose Index Scan | DATETIME MAX ✓  复合索引同样支持 | 整数 MAX ✓  比较操作最少 |
| **ORDER BY** | 字典序=时间序 ✓ | 原生排序 ✓ | 整数排序 ✓ |
| **日期函数** 按月/按周聚合 | 需 `SUBSTR(create_time,1,7)`  无法利用原生日期函数 | `YEAR()`, `MONTH()`, `DATE()`  MySQL 原生函数 | `FROM_UNIXTIME()` 后再用日期函数  需两步转换 |
| **Python 端解析** | `strptime(ct, fmt)`  每次需解析字符串 | SQLAlchemy 自动映射为 `datetime` 对象  零解析成本 | `datetime.fromtimestamp(v)`  比 strptime 快 ~5x |

### 3.3 性能基准估算（MySQL InnoDB，100 万行 job\_log）

| 操作 | VARCHAR(25) | DATETIME | BIGINT | 说明 |
| --- | --- | --- | --- | --- |
| 当日过滤（LIKE vs 范围） | ~3.5 ms | ~2.0 ms | ~1.8 ms | LIKE 前缀 vs 确定性范围扫描 |
| 索引大小（单列，100 万行） | ~25 MB | ~12 MB | ~10 MB | 索引越小 → 缓存命中率越高 |
| 表数据大小（3 个时间列） | ~63 MB | ~24 MB | ~24 MB | 节省 ~39 MB / 100 万行 |
| Python strptime（1000 次解析） | ~2.1 ms | 0 ms（ORM 自动映射） | ~0.4 ms（fromtimestamp） | DATETIME 省去解析步骤 |
| INSERT 写入 | ~0.08 ms | ~0.08 ms | ~0.06 ms | 差异极小 |

**SQLite 特殊说明**：SQLite 没有原生 DATETIME 类型（[Type Affinity](https://sqlite.org/datatype3.html)），
声明 `DATETIME` 实际仍按 TEXT 存储。因此在 SQLite 后端，VARCHAR 与 DATETIME **性能无差别**。
BIGINT 在 SQLite 中按 INTEGER 存储，索引比较确实更快。

### 3.4 迁移成本与风险

| 维度 | VARCHAR(25) 保持现状 | DATETIME 迁移 | BIGINT 迁移 |
| --- | --- | --- | --- |
| 改动文件数 | 0 | ~50 文件（Model + Repository + Views + Tests + Scripts + API + Templates） | ~55 文件（同上 + 所有展示层需格式化） |
| 数据迁移 | 无 | MySQL: `ALTER TABLE ... MODIFY COLUMN ... DATETIME`（自动转换）  SQLite: 需建新表 + 复制数据（无 ALTER COLUMN） | 需遍历所有行 `UNIX_TIMESTAMP(create_time)` 更新  SQLite: `strftime('%s', create_time)` |
| API 兼容性 | 无影响 | `to_json()` 方法需显式 `.strftime()`  外部消费者若依赖字符串格式则为 Breaking Change | **Breaking Change** — API 返回整数而非字符串  或增加序列化层还原为字符串 |
| SQLite/MySQL 双后端兼容 | 天然兼容 | SQLite 无原生 DATETIME → ORM Mapped[datetime] 与 SQLite TEXT 需映射层  日期函数语法不同（`DATE()` vs `date()`） | 两个后端均原生支持 INTEGER  统一的整数比较语义 |
| 空值处理 | 需统一 `''` 为 `NULL` | `NULL` 即可 | `NULL` 即可 |
| 回滚难度 | — | 可逆（DATETIME → VARCHAR 转回） | 可逆（timestamp → strftime 转回） |
| 测试覆盖影响 | 无 | 所有涉及时间的单测需改写断言 | 同上 + 展示层测试全部需更新 |

### 3.5 综合评分

| 评估维度 | 权重 | VARCHAR(25) | DATETIME | BIGINT |
| --- | --- | --- | --- | --- |
| 查询性能（MySQL） | 25% | 6 / 10 | 8 / 10 | 9 / 10 |
| 查询性能（SQLite） | 15% | 7 / 10 | 7 / 10 | 8 / 10 |
| 存储效率 | 10% | 4 / 10 | 8 / 10 | 9 / 10 |
| 开发体验 | 15% | 7 / 10 | 9 / 10 | 5 / 10 |
| 可调试性 | 10% | 9 / 10 | 9 / 10 | 3 / 10 |
| 迁移成本 | 15% | 10 / 10 | 4 / 10 | 3 / 10 |
| 双后端兼容性 | 10% | 9 / 10 | 4 / 10 | 8 / 10 |
| 加权总分 | 100% | 7.2 | 6.8 | 6.5 |

**关键洞察**：在当前项目规模和双后端约束下，VARCHAR(25) 的综合分数最高。
DATETIME 在 MySQL-only 场景下更优，但 SQLite 兼容性拖累了总分。
BIGINT 查询性能最强但可读性和迁移成本是最大短板。

## 4. 根因分析

当前 VARCHAR 方案的性能劣势**并非源于存储格式本身**，而是源于两个可独立优化的查询写法问题：

| # | 根因 | 影响 | 是否需要改存储格式才能修复 |
| --- | --- | --- | --- |
| R1 | `LIKE 'date%'` 日期过滤 | MySQL 优化器可能不选择索引范围扫描 | **否** — 改为 `>= / <` 范围比较即可（VARCHAR 字典序=时间序） |
| R2 | Python 端 `strptime()` 解析 | 逾期检测等场景需将字符串转回 datetime 对象 | **否** — 可用切片 + 整数比较替代 strptime（见下方方案 B） |

## 5. 推荐方案

### 方案 B（推荐）：查询模式优化 — 不改存储，只改查询写法

**核心思路**：保留 VARCHAR(25) 存储不变，将 5 处 `LIKE 'date%'` 改为确定性范围比较，
同时用切片替代 strptime 降低 Python 解析开销。  
**改动量**：~10 行代码 | 0 数据迁移 | 0 API 变更 | 0 测试大改

#### 5.1 LIKE → 范围比较（5 处）

```
# 当前写法（R1）
JobLog.create_time.like(today + '%')

# 优化写法
from datas.utils.times import get_today
today = get_today()  # '2026-08-26'
JobLog.create_time >= today + ' 00:00:00'
JobLog.create_time <  _next_day(today) + ' 00:00:00'

# 辅助函数
def _next_day(date_str):
    """'2026-08-26' → '2026-08-27'"""
    from datetime import datetime, timedelta
    d = datetime.strptime(date_str, '%Y-%m-%d')
    return (d + timedelta(days=1)).strftime('%Y-%m-%d')
```

**影响的代码位置**：

| # | 文件 | 行 | 上下文 |
| --- | --- | --- | --- |
| 1 | `app/repositories/cron_repository.py` | 38 | `paginate_list` → today\_fail 子查询 |
| 2 | `app/repositories/cron_repository.py` | 73 | `dashboard_metrics` → 今日失败任务数 |
| 3 | `app/repositories/cron_repository.py` | 172 | `today_success_rate` → 今日成功率 |
| 4 | `app/main/views.py` | 639 | `cron_detail` → 任务详情今日总执行 |
| 5 | `app/main/views.py` | 644 | `cron_detail` → 任务详情今日成功数 |

#### 5.2 strptime 优化（可选）

```
# 当前写法（R2，逾期检测中）
last_dt = datetime.strptime(last_run_str, '%Y-%m-%d %H:%M:%S')

# 优化写法：切片 + 直接构造（~3x faster than strptime）
def _fast_parse(s):
    """将 'YYYY-MM-DD HH:MM:SS' 高效解析为 datetime，无格式校验开销。"""
    return datetime(int(s[:4]), int(s[5:7]), int(s[8:10]),
                    int(s[11:13]), int(s[14:16]), int(s[17:19]))
```

#### 5.3 空值语义统一（可选）

为可选时间字段（`retired_at`、`last_login_at` 等）统一 `default=''` → `default=None`，
查询时用 `IS NOT NULL` 而非 `!= ''`。此项为渐进式清理，不影响现有查询正确性。

## 9. 风险

| 风险 | 概率 | 影响 | 缓解 |
| --- | --- | --- | --- |
| `next_day()` 跨月/跨年边界 | 低 | 高（日期计算错误） | 使用 `timedelta(days=1)` 而非字符串拼接，天然处理 12-31 → 01-01 |
| 范围比较 vs LIKE 结果差异 | 极低 | 中（数据不一致） | `LIKE 'YYYY-MM-DD%'` 与 `>= 'YYYY-MM-DD 00:00:00' AND < 'YYYY-MM-DD+1 00:00:00'` 对 ISO 8601 完全等价 |
| 回归风险 | 低 | 低 | 全量单测 + restart 验收 |

## 10. 附录：为什么不立即全量迁移？

### A. SQLite 无原生 DATETIME — 改了也白改

CronPilot 默认部署使用 SQLite。SQLite 的
[Type Affinity](https://sqlite.org/datatype3.html) 机制意味着：

```
-- 声明为 DATETIME 的列
CREATE TABLE t (created_at DATETIME);

-- 实际存储亲和性为 NUMERIC → 但字符串值按 TEXT 存储
-- 性能与 VARCHAR 完全相同
```

只有放弃 SQLite 后端（L4 阶段），迁移到 DATETIME 才有实际的数据库层面收益。

### B. BIGINT 的可读性代价

BIGINT 查询性能最优，但：

- 数据库运维排查时 `SELECT * FROM job_log LIMIT 5` 看到的是 `1787860500` 而非 `'2026-08-26 09:55:00'`
- API 响应需增加序列化层维持字符串格式（否则为 Breaking Change）
- 所有模板展示需 `datetime.fromtimestamp().strftime()`
- 改动规模 ~55 文件，回归测试工作量大

在 CronPilot 当前规模（百级任务、万~十万级日志）下，BIGINT 带来的毫秒级查询提升**不值得**承受如此大的迁移成本。

### C. 投入产出比对照

| 方案 | 改动量 | MySQL 查询提升 | SQLite 查询提升 | ROI |
| --- | --- | --- | --- | --- |
| 方案 B（查询优化） | ~20 行 | ~40–70%（LIKE→范围） | ~5–10% | **极高** |
| 方案 A（全量 DATETIME） | ~50 文件 | ~15–30%（在 B 基础上额外） | 0% | 低 |
| 方案 C（BIGINT 双写） | ~30 文件 | ~20–40%（在 B 基础上额外） | ~10–15% | 中 |
