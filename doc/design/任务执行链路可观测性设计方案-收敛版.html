CronPilot 任务执行链路可观测性设计方案（收敛版）

实施中 · 日期：2026-09-15（rev.6 trace_id 唯一性契约）· 范围：同步 HTTP 定时触发链路

本稿结论：CronPilot 是“调度触发 → 同步 HTTP 请求 → 写入结果”的管理系统。本方案只为 cron_do 增加可追溯的执行事件和执行中父记录；不把它扩展为分布式工作流系统，不新增 owner、lease、heartbeat，也不自动把遗留记录猜测为 interrupted。任务采用下线而非物理删除；执行日志、业务日志与链路事件均为保留的生产审计证据，不自动物理删除。

一、问题、根因与目标

1.1 当前事实

当前 cron_do 在 app/crons.py 中同步执行 URL 校验、DNS 解析、HTTP 请求和结果写入。HTTP 调用使用任务级 timeout_sec；正常执行在收到响应或超时后结束。_save_job_log() 只在终态创建一条 JobLog，因此中间阶段不可见。

阶段现状排查缺口
调度提交现有 trigger_delay_ms 仅表示装饰器内部开销无法得知计划时间到实际开始的延迟
配置读取与 SSRF/DNS仅保留最终错误文本或 resolved IP无法定位预检耗时和拦截原因
HTTP 请求保留结果和总耗时无法判断请求是否已发出、何时超时或发生连接异常
结果写入仅有终态记录进程退出时，已发生的步骤对产品不可见

1.2 改造前后对比（评审基线）

用户排查动作改造前：Run Inspector改造后：Run Inspector本次新增的产品价值
判断任务是否真正开始只在终态后有 JobLog；开始前异常没有可查看记录触发时即创建 pending 父记录，进入业务链路即转 running即使未终态化，也有执行身份和已写步骤可追溯
定位慢在哪里只有总耗时，无法区分调度等待、预检和 HTTP 等待摘要展示计划延迟；时间线展示关键阶段的相对时间与耗时无需翻应用日志即可先判断瓶颈所在阶段
判断 HTTP 是否发出失败时依赖最终文案推测http.start、http.complete/http.timeout/http.error 明确表达区分预检阻断、连接异常、请求超时和服务端响应失败
查看运行中或异常退出的记录无终态即无产品化详情保留 pending/running 及已写事件，并明确“最终结果未知”不伪造失败结论，同时保留现场证据
按角色查看诊断详情页面直接依赖模型字段，敏感信息边界难以统一服务端 Presenter 先裁剪为角色化 DTO，模板只渲染 DTO请求体、响应与异常详情有可验证的最小可见原则

页面变化一览：改造前是“摘要 → 原始请求/响应 → 业务日志”的平铺详情；改造后是“摘要（状态、调度延迟）→ 执行链路时间线 → 按需展开的请求/响应/业务日志 → 元数据”。原有信息不被时间线替代，而是被组织为先概览、后下钻的诊断路径。

1.3 根因

现有模型是“单点终态写入”：执行身份 trace_id、日志行和结果都在 cron_do 后段才落库；Run Inspector 又以 JobLog 为入口。因此，任何发生在最终写入前的异常都缺少产品可访问的执行记录。

1.4 目标与非目标

目标非目标
显示一次同步触发中的关键阶段、耗时和安全处理结果拆分 HTTP connect/TTFB/transfer 等底层网络阶段
进程异常退出后保留已写事件和未完成父记录自动判定进程死亡或自动恢复 interrupted
为定时、一次性和手动触发提供一致的执行身份引入 owner/lease/heartbeat、锁续租或工作流编排
在角色权限下安全展示事件详情新增公开 events 查询 API 或透传原始 detail JSON

二、范围与运行边界

仅观测 cron_do。 cron_check、cron_del_job_log、cron_del_operation_log、cron_check_db_sleep 等维护任务继续使用原有 @single_task()，不创建业务 JobLog，不写 job_log_events。

现有 Redis 仅是 single_task() 在 is_single != '1' 时使用的可选互斥锁。默认 is_single=1 不连接 Redis。它防止同一任务被重复开始执行；本方案不增加 Redis 依赖，也不改变其 TTL/续租语义。

如果进程被 kill -9、OOM Killer、主机断电或解释器崩溃，代码无法更新终态。父记录保持 pending 或 running，页面显示“执行未完成，最终结果未知”。这不是 error，也不是本批次自动转换的 interrupted。

保留策略：任务只允许下线，不做物理删除；JobLog、JobLogItems 与新增 job_log_events 均不按数量、时间或任务状态自动物理删除。现有 cron_del_job_log() / job_log_counts 自动裁剪属于待取消的存量机制，不得在本方案中继续沿用或扩展。未来如需归档或清除，必须另立数据保留与审计设计，经明确确认后实施。

调度抑制边界：Redis 锁未获取和 APScheduler max_instances 限制均发生在 cron_do 之前，本期只记录调度器/应用日志与指标，不创建执行记录、事件或详情入口。容量边界：本期不新增归档、清理、容量监控或备份功能；永久保留后的容量与备份由既有数据库运维流程负责。

三、总体方案

3.1 执行父记录与事件流

APScheduler / 手动触发
        │
        ▼
@single_task(observe_execution=True)       # 仅 cron_do
  ├─ [仅集群配置] 先获取现有 Redis 锁
  │    └─ 未获取 → 直接返回（不创建 trace / JobLog / event）
  ├─ 获准进入执行路径后：创建 trace_id + JobLog(status=pending)
  ├─ 写 task.enqueued
  ├─ status: pending → running；写 task.start
  └─ cron_do 使用同一 trace_id / tracer
       ├─ db.load_cif
       ├─ ssrf.check
       ├─ http.start → http.complete / http.timeout / http.error
       ├─ 更新既有 JobLog 为 success / fail / timeout / error
       └─ 写 db.write_log、health.update（成功时）

复用已有 JobLog 作为执行父记录，不新增 job_runs 表。这样执行记录列表、业务日志 job_log_items 和 Run Inspector 都继续以同一个 trace_id 关联；父记录及其关联证据长期保留，不纳入自动清理路径。

3.2 状态机

pending
   │
   ├──已捕获的入口异常──────────► error
   ▼
running
   ├──同步请求成功──────────────► success
   ├──HTTP/业务判定失败─────────► fail
   ├──requests 超时─────────────► timeout
   └──已捕获的其他异常──────────► error

进程级异常：保留 pending/running，不自动改写终态。
状态含义健康度
pending父记录创建，尚未进入业务函数不参与统计
running已开始同步业务链路不参与统计
successHTTP 与业务判定成功成功
failHTTP 已返回，但状态码或关键字判定失败失败
timeout同步 HTTP 请求超时失败
error当前进程捕获到的确定性异常失败
终态约束：success、fail、timeout、error 不可再次转换。finalize 必须使用“当前状态仍为 pending/running”的条件更新，避免覆盖已完成记录。若 finalize 本身失败，不伪造新的终态，记录应用日志和指标。
锁竞争边界：single_task() 未取得可选 Redis 互斥锁时，cron_do 没有开始执行；这属于调度抑制，不是一次执行的结果。因此仅保留应用日志/指标，不创建 JobLog、trace_id 或 job_log_events，也不影响健康度、执行列表和详情页。

3.3 装饰器契约

def single_task(observe_execution=False):
    # False：保持当前互斥和调用语义
    # True ：仅供 cron_do 使用，创建父记录、Tracer，并注入 _trace_ctx
    ...

@single_task(observe_execution=True)
def cron_do(cron_id, trigger_source='schedule', _trace_ctx=None):
    # 只消费装饰器提供的 trace_id / tracer；不重复创建
    ...

定时、一次性和手动执行都必须经过这一专用路径。维护任务不得因通用装饰器无条件注入 _trace_ctx 而改变签名或失败。

四、数据与事件契约

4.1 数据模型

新增 job_log_events，一条事件对应当前执行链路中的一个已发生步骤。新增 job_log_items.occurred_at_ms，用于将业务回传日志与系统事件以服务端接收时间稳定排序。

job_log_events
  id              BIGINT PK
  trace_id        VARCHAR(65) NOT NULL
  cron_id         INTEGER NOT NULL
  seq             INTEGER NOT NULL
  event_type      VARCHAR(48) NOT NULL
  occurred_at_ms  BIGINT NOT NULL       # UTC 墙钟毫秒
  offset_ms       INTEGER NOT NULL      # 本执行 monotonic 相对毫秒
  duration_ms     INTEGER NULL
  outcome         VARCHAR(16) NOT NULL  # ok/fail/blocked/timeout
  detail          TEXT NOT NULL          # 已脱敏的事件专属 JSON
  UNIQUE(trace_id, seq)

JobLog 复用既有 status、trace_id、started_at、finished_at。trace_id 使用 uuid1 生成，并有父记录唯一约束；历史空值/重复值在建索引前回填，父记录写入遇到冲突时最多重新生成两次。UNIQUE(trace_id, seq) 只保证同次执行内事件顺序唯一。本批次不新增状态值：执行状态仅使用既有 pending、running、success、fail、timeout、error；也不为进程级异常增加自动判定状态。

历史 trace_id 迁移安全边界：若同一旧 trace_id 被多个 JobLog 父记录共用，且 job_log_items 或 job_log_events 已存在引用，则原始归属不可推断。迁移脚本必须在改写父记录前 fail-closed，保留原数据并要求人工制定映射；不得把依赖记录批量重指向任意新父记录。没有依赖记录时，才允许仅为重复父记录生成新的 uuid1 并建立唯一索引。

4.2 事件类型

事件时机detail（仅专属字段）
task.enqueued观测装饰器入口scheduled_delay_ms、trigger_source、scheduled_at
task.start进入 cron_do 前无
db.load_cif读取任务配置后无
ssrf.checkURL 校验后block_type、block_detail（拦截时）
http.start请求发出前method、脱敏后的 url
http.complete收到 HTTP 响应http_status、必要时 resp_snippet
http.timeout捕获超时timeout_sec
http.error捕获非超时请求异常exc_type、exc_detail
db.write_log父记录终态更新后status

outcome 与 duration_ms 是顶层列，禁止在 detail 中重复存储。事件写入失败不改变业务终态；事件序号可有空洞，UI 只按单调递增排序，不将空洞解释为链路缺失。

4.3 时间语义

  • scheduled_delay_ms：计划触发时间到装饰器入口；手动执行为 NULL。
  • offset_ms：同一次执行内的相对顺序和耗时展示，使用 time.monotonic()。
  • occurred_at_ms：服务端记录事件或收到业务日志的 UTC 毫秒时间。
  • 系统事件与业务回传日志只保证按 (occurred_at_ms, source_priority, seq_or_id) 稳定排序，不承诺跨网络来源的因果顺序。

真实调度延迟不得用 APScheduler 的下一次 next_run_time 反推。第一期只覆盖生产当前的 BackgroundScheduler + threadpool：在 executor 提交边界从本次 run_times[-1] 取计划时间，以 ContextVar 一对一传入 worker，并在 worker 复用前 reset。手动执行不经 Executor，因此自然得到 NULL；Gevent 变体不属于本期范围，未来启用时另补等价适配与测试。

五、安全、可靠性与展示

5.1 事务隔离与写入预算

ExecutionTracer 禁止使用业务 db.session。它使用独立 Engine 与独立事务，写入失败只回滚自身事务，不能污染结果写入或健康度更新。实现必须按 SQLite 文件库、SQLite 内存测试库与 MySQL 分别选择兼容的连接池参数；不得把同一组 pool_size/max_overflow/pool_timeout 盲目用于所有 SQLite URL。

性能契约：Tracer 提供“故障隔离”，不承诺零阻塞。实现需设置后端短等待、每次执行的累计写入预算和失败熔断；验收必须在 SQLite 锁竞争及 MySQL 池耗尽场景测试实际 p100，不得仅以空闲库结果宣称无影响。

5.2 脱敏与 RBAC

所有事件 detail 在写库前经过字段白名单、结构化拆分、URL 凭据掩码和 UTF-8 安全截断。actual_url 与 http.start.url 必须复用同一 redact_url() 规则，至少掩码 sign/token/key/secret/password/auth 等参数名。

Run Inspector 必须通过 Presenter 输出角色化 DTO；模板不得直接读取 JobLog、CronInfos 或原始 event.detail。Viewer 不可见请求体、完整响应和异常详情；Operator 获取有限诊断文本；Biz Admin 与 Seed Admin 按既有权限获得完整但已入库脱敏的数据。第一阶段不新增 events API。

5.3 未完成记录展示

pending/running 的详情页仍展示已写事件，并提示“执行中”或“执行未完成，最终结果未知”。所有状态的父记录、events 与 items 都是生产审计证据：本期及既定策略均不自动裁剪、级联删除或因任务下线而删除。

5.4 Run Inspector UI 设计契约

现有页面包含执行摘要、请求、响应、业务日志和元数据区块。目标态保留这些信息层级，并在摘要下方新增“执行链路”作为首要诊断区块；时间线不是替代请求/响应正文，而是帮助用户先定位阶段，再按需查看原有详情。

区域现有内容目标态与可见变更

5.5 时间线、详情与交互规范

元素设计要求
时间线顺序按 occurred_at_ms ASC, source_priority ASC, seq ASC, id ASC 排序；source_priority 固定为系统事件先于同毫秒的业务日志。排序只保证呈现稳定，不以事件序号是否连续判断链路完整性。
事件行固定展示阶段名、相对时间、阶段耗时、结果语义和摘要；摘要必须是 Presenter 已裁剪文本。系统事件标记“系统”，业务日志标记“业务日志”，避免把业务回传误读为调度器动作。
详情区请求、响应/诊断、业务日志全文以折叠区块呈现。默认优先展开与当前终态相关的一个区块：timeout 展开诊断，fail/error 展开失败摘要，success 全部折叠。空值统一呈现为“—”，不显示 JSON null、空字符串或原始异常对象。

5.6 Redesign 前端契约

6.1 实施前门禁与交付原则

  1. 先冻结契约，后改执行路径。先为状态机、事件排序、脱敏和 Presenter 字段写单元测试；每一批只提交可独立验收的最小闭环，禁止“模型已落库但页面仍直接读原始字段”。
  2. 保持向后兼容与审计保留。既有 job_log 可继续被查询，但不再自动清理；新字段、job_log_events 和 job_log_items.occurred_at_ms 均允许历史记录为空。列表和详情对历史记录显示“—”，不补写伪事件。
  3. 事务和失败隔离优先。业务 db.session 与事件写入不可共用；Tracer、事件表或 Presenter 发生故障时，既有 HTTP 执行与终态写入仍必须工作。
  4. 每批完成定义。代码、SQLite/MySQL 迁移、正反向测试、文档同步和对应浏览器验收均通过后，才进入下一批；不在未确认设计上提前写业务实现。

七、验收与风险

7.1 必测场景

  • 定时触发有 scheduled_delay_ms；手动触发为 NULL；一次性触发有计划时间。
  • 单机模式不写锁事件；集群配置锁未获取时不产生父记录、事件、HTTP 或健康度变更。
  • SSRF 拦截、HTTP 4xx/5xx、超时、连接异常分别产生正确事件和终态。
  • 进程级异常后父记录保持 pending/running；不自动写 error 或 interrupted。
  • 事件写库失败不导致 db.session 无效，且预算/熔断生效。
  • 四种角色在浏览器中查看同一执行记录，敏感字段边界与 DTO 矩阵一致。

7.2 主要风险与缓解

风险缓解
即时事件写入增加 DB 压力独立 Engine、短等待、累计预算、熔断、TRACE_LEVEL；以目标后端实测决定默认级别
pending/running 长期遗留本期明确展示为“结果未知”，不作错误推断；未来自动恢复另立设计
状态扩展遗漏消费者同步更新 outcome、display、filter、health、Repository、API 白名单和测试；API 枚举变化写入 Release Notes
事件详情泄露凭据或网络信息写库前脱敏、Presenter 白名单、四角色浏览器反向验证

八、进入实施的确认项

  1. 确认本期只处理同步 HTTP 执行链路，不实现多实例存活判定和自动 interrupted。
  2. 确认复用 JobLog 作为执行父记录，不新增 job_runs。
  3. 确认仅 cron_do 使用 @single_task(observe_execution=True)。
  4. 确认事件详情按入库前脱敏、Presenter DTO、无新增 events API 的安全边界实施。
