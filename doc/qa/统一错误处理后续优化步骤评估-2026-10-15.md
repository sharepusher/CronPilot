# 统一错误处理后续优化步骤评估

日期：2026-10-15 · 类型：代码与设计现状评估 · 基线：[统一错误处理治理路线图 rev.15](../design/统一错误处理P0实施计划-2026-09.html) 及五份独立子方案

**结论：**方案拆分和风险识别已基本正确，但应用代码尚未进入这些方案的实施阶段。后续不应按总路线图批量开工；应先修复“确认状态与实施证据漂移”，再按“P0-D 数据正确性 → P0-S 安全输出 → P0-A-lite 协议 → P0-C 仅 C-0 → P1-A2 → P1-B”推进。

## 1. 当前代码事实

| 领域 | 当前实现 | 评估 |
| --- | --- | --- |
| HTTP request\_id | `app/__init__.py` 对全部请求接受任意 `X-Request-Id` 或生成 UUID，并写入 `g.trace_id`/`_ctx_trace_id`；没有 endpoint 分类、UUID v4 校验、响应 Header、ContextVar token reset 或机器登记。 | P0-A-lite 尚未实施；现有代码只能算可复用基线。 |
| 错误信封 | `json_response/api_return/web_api_return` 仍是 `errcode/errmsg/data/result/url`；APIFlask error processor 仍是独立旧形状。 | P1-A2 尚未实施，且不应提前于 P0-S。 |
| 数据库写入闭环 | `users_edit` 的资料 commit 异常只 rollback/log，仍可能沿用此前 `result['ok']=true`。 | 可复现的当前正确性缺陷，P0-D 是最优先代码切片。 |
| 输出脱敏 | `app/common/functions.py`、`app/main/views.py` 等仍有 `str(e)`、traceback 进入日志/通知链路。 | 存在静态泄漏风险；尚无生产泄漏证据，P0-S 必须先做 sink 台账。 |
| scheduler 一致性 | create/update 是 DB commit 后 scheduler apply；retire 是 scheduler remove 后 DB commit；toggle 用第二次 commit 补写旧状态。模型没有 generation/sync-state/fingerprint 字段。 | 风险真实但改造面最大；当前只适合 C-0 发现和冻结，不应直接建表或改状态机。 |

## 2. 设计现状与关键缺口

- 总览 rev.15 写明 P0-A-lite 核心契约已经用户确认，但 P0-A-lite 子方案 rev.3 仍标记“待确认，未授权实施”。实施授权的单一事实来源不一致，是当前第一个治理阻断项。
- P0-D 已定位真实 bug，但 D-0 阶段矩阵、真实页面 Before/After 和专项测试尚未产生。
- P0-S 方案足够作为 S-1 调研输入，但 `tests/fixtures/error_sink_registry.json` 与专项测试不存在。
- P0-A-lite 的 machine registry、调用方扫描、OpenAPI/代理证据与专项测试不存在；“无外部调用方”不能仅由仓库代码证明，实施前还须用部署配置、访问日志或明确业务确认佐证。
- P0-C 已正确降级为 C-0，但 generation 原子递增、条件写回、锁所有权、双后端迁移和实际 trigger 指纹仍未冻结。

## 3. 推荐执行顺序

| 顺序 | 工作 | 进入条件 | 完成/停止条件 |
| --- | --- | --- | --- |
| 0 | **治理冻结**：统一父/子方案状态；建立确认记录；冻结当前路由、响应、commit 和 sink 基线。 | 只读扫描可执行。 | 各子方案只有一个权威状态；任何“已确认”均可指向明确确认记录。状态不一致时禁止写实现。 |
| 1 | **P0-D D-0 → D-1**：先完成用户编辑阶段矩阵和失败注入测试，再修复误报成功。 | P0-D 页面级 Before/After、Ajax/原生响应事实和部分提交语义确认。 | 资料 commit 失败最终必为失败；不虚假声称整体 rollback；成功、权限、CSRF 基线不变。若无法区分提交结果，停止并先补核实路径。 |
| 2 | **P0-S S-1 → 窄 S-2**：生成 sink 台账，优先治理通知、HTTP 与业务持久化中的原始异常文本。 | 每个 sink 已登记代码位置、数据主体、接收者、保留期、控制和测试 ID。 | 嵌套凭据及 sanitizer 自身失败均 fail-closed。台账不完整时不得批量替换异常处理。 |
| 3 | **P0-A-lite A1 → A3**：机器登记、调用方原子改造、双 ID/ContextVar、代理缓存验证。 | 父/子确认状态统一；外部调用方事实已核实；机器登记人工签核。 | 协议 400 零业务副作用；required/exempt 真值表、OpenAPI、真实代理、旧标签页和整版回滚演练通过。任一调用方未登记即停止发布。 |
| 4 | **P0-C 仅 C-0**：枚举全部配置修改者、scheduler 实际状态、锁与迁移约束，形成正式详设。 | P0-D 已明确 DB 失败语义；现状扫描不写 schema。 | generation、条件写回、指纹、UNKNOWN 对账、SQLite/MySQL 迁移和并发模型全部确认后，才能申请 C-1 实施。 |
| 5 | **P1-A2**：兼容 JSON 信封与错误码注册表。 | P0-A-lite、P0-S 完成；旧响应快照已冻结。 | 旧字段和业务 HTTP 状态无漂移；所有 JSON 出口覆盖。 |
| 6 | **P1-B**：按真实页面逐页迁移错误交互。 | P1-A2 完成；每页 B-0 基线和页面对比单独确认。 | 字段错误、已确认失败、结果未知三种交互互斥；浏览器正反向和无障碍验证通过。 |

## 4. 为什么调整总览中的优先顺序

P0-D 是当前已由代码直接证明的用户可感知错误，改动可限制在单一垂直切片；P0-S 有明确静态风险，但应先盘点再治理；P0-A-lite 是跨全部 JSON 调用方的协议变更，影响面显著大于前两项，且仍缺外部调用方证据。P0-C 涉及数据库迁移和并发状态机，应保持 C-0 调研边界。P1-A2/P1-B 主要提升一致性和体验，不应阻塞当前 P0 正确性与安全修复。

## 5. 每个实施批次的统一门禁

1. 明确子方案已确认，禁止用父总览替代确认。
2. 先增加可失败的专项测试和不可变兼容快照，再改实现。
3. 一次只做一个垂直切片；发现新范围即回到设计，不边实现边扩面。
4. 运行专项测试、Ruff、路由烟测；UI/权限变化必须 restart 后用目标角色浏览器验证正向与反向路径并截图。
5. 若发生修复，完成 7 项复盘、HTML/Markdown/索引同步和 Release Notes（用户可感知时），最后再 commit。

## 6. 本次验证证据

`python scripts/smoke_routes.py --check`：86/86 路由通过。

任务持久化、编辑状态与日志格式专项：10 项运行通过，1 项既有场景跳过；存在一条 SQLAlchemy identity-map warning，和本计划无直接因果关系。

设计中计划的 `test_request_id_contract.py`、`test_error_sink_sanitization.py`、`test_user_edit_write_failure.py`、`test_scheduler_consistency.py` 及 sink registry 均不存在。

文档门禁：297 份 HTML 已注册、无断链；HTML/Markdown 同步和 pending-sync 检查通过。

## 7. 最终判断

当前最合理的下一动作不是实现统一错误信封，而是完成“治理冻结 + P0-D D-0”。在 P0-D 首切片关闭之前，不建议启动 P1-A2/P1-B；在外部调用方与机器登记未冻结之前，不建议启动 P0-A-lite 原子发布；在 C-0 未形成正式并发详设之前，禁止新增 scheduler 状态字段或迁移。
