# 编辑与修改业务流程同类一致性风险审计

日期：2026-10-28 · 审计范围：RBAC 管理面、个人资料、业务组、标签、任务编辑、状态/凭据操作、注册审批 · 状态：**事实审计完成，未修改生产代码**

**总结论：有同类问题，而且分成两族。**任务编辑、个人资料、业务组和标签存在“页面原值可能陈旧、无差异仍写库或产生副作用、成功语义不能区分”的编辑型问题；密码重置、Token、停用和注册审批本身是明确动作，不应套用 `NO_CHANGE`，但存在“业务提交成功后，审计再用第二次提交”的原子性问题。两族问题应共享原则，不应强行共享一套实现。

**最高优先级对象是任务编辑，而不是继续横向修改所有 RBAC 表单。**`update_cron()` 即使内容未变，也会更新时间/操作人、删除并重建任务组与标签关联、提交数据库、重新注册调度任务并另行写操作日志。它同时放大数据库写入、调度器副作用、误导日志和并发覆盖风险。

## 1. 审计判定标准

本审计没有只搜索函数名，而是按以下五个可验证风险判定：

1. **无差异写入：**请求值与页面/数据库原值相同，仍执行 UPDATE、关系表重建、Token/缓存/调度器副作用。
2. **陈旧页面覆盖：**GET 展示数据后，POST 直接用整表单覆盖数据库，没有原始快照、版本号或三方比较。
3. **业务与审计分裂：**业务先 commit，审计函数内部再次 commit；第二次失败时页面仍显示成功但审计缺失。
4. **成功语义失真：**未发生有效变化仍返回“保存/修改成功”并生成变更日志。
5. **副作用非幂等：**无差异或并发请求仍重置凭据、失效缓存、重建调度状态或改写关联表。

其中 1、2、4 适用于“编辑表单”；密码重置、Token 签发、停用等命令型操作只适用 3、5，不能因为每次都会改变状态就误判为 no-op 缺陷。

## 2. 逐入口事实与风险矩阵

| 业务入口 | 当前代码事实 | 与用户编辑问题的关系 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| **任务编辑** `/cron_edit` `update_cron()` | 全量表单写回；无 change set；写 `updated_at`/最近操作人；删除并重建 `task_groups`、`task_tags`；先业务 commit，再注册调度器，再由 `record_operation()` 独立 commit。 | 五类风险全部存在，并额外带调度器外部副作用。POST 前重新读取当前行并不能防止旧表单覆盖，因为请求仍携带 GET 时的旧字段全集。 | P0 | **最典型、影响最大的同类问题。**应作为用户编辑之后的下一份独立设计。 |
| **个人资料编辑** `/rbac/profile` `update_own_profile()` | 规范化后无条件给 email/nickname/job\_title 赋值并 commit；没有 no-op 结果；没有页面原始快照或并发检测；没有变更审计。 | 与用户编辑的资料字段几乎同源，但当前邮箱不能为空，因此不存在“清空邮箱二次确认”分支。 | P1 | 需差异写入、并发保护和个人资料审计；可复用字段规范化与审计 JSON 契约，不能照搬管理员授权字段。 |
| **业务组编辑** `/rbac/groups/edit` `update_resource_group()` | 名称/描述只要在请求中出现就赋值；无差异仍 commit；随后 `write_audit_log()` 再次 commit；无页面版本或原值校验。 | 同时存在 no-op、陈旧覆盖、误导审计和双事务。 | P1 | 同类问题成立，但字段少、并发低，可在统一写入契约稳定后迁移。 |
| **标签编辑** `/rbac/tags/<id>/update` `update_tag()` | 只要传入名称或说明就把 `changed` 设为真，即使规范化值完全相同也更新时间并 commit；无原始快照；无审计记录。 | 存在 no-op 和陈旧覆盖；不是“双事务审计”，而是**完全缺少编辑审计**。 | P1 | 问题成立，但修复重点是精确 change set + 是否应纳入管理审计，而不是改造现有审计事务。 |
| **用户组绑定兼容服务** `set_user_groups()` | 仅组集合变化时重签 Token，但无差异仍 commit、写 `user:update` 审计并失效缓存。当前生产路由未直接调用，主要由测试/兼容路径使用。 | 与用户编辑的组差异问题同源，但不是当前主页面写路径。 | P2 | 不应单独抢先修；在用户编辑 U0 中确认保留、收口或废弃，避免两套用户组写服务继续漂移。 |
| **启停任务/停用用户** `toggle_status()` `set_user_active()` | 两者已有“当前状态等于目标状态则直接返回”的幂等分支；真实变化后日志/审计仍是第二次 commit。任务启停还依赖调度器补偿写回。 | no-op 已正确处理；只剩审计原子性、并发命令与外部副作用一致性，不能宣称与编辑表单完全相同。 | P1 | 保留现有幂等语义；另立“命令执行与审计/调度一致性”设计。 |

## 3. 为什么这些问题过去容易被忽略

- 现有测试集中验证“能否成功修改”和最终字段值，几乎没有断言“完全相同的输入必须零 SQL 写入、零副作用、零审计”。
- `write_audit_log()` 与 `record_operation()` 都把异常吞掉并回滚自己的事务，主流程因此保持成功，常规成功用例观察不到审计丢失。
- 页面 POST 时再次 `get()` 当前对象容易造成“已读取最新值”的错觉；但服务随后用旧页面提交的完整字段覆盖它，仍会发生 lost update。
- 任务编辑的关系表全量重建和调度器重注册被封装在服务层，页面看起来只是一次“保存”，真实副作用远大于普通 UPDATE。

## 4. 不应采用的横向修复方式

**不能一次性把当前用户编辑方案复制到所有入口。**字段语义、并发强度和副作用不同：任务编辑需要处理 DB 与调度器的一致性；凭据操作需要事件审计而不是字段前后值；标签当前没有审计；注册审批已经有行锁和状态机。强行抽象会把尚未验证的契约扩散到大范围生产路径。

- 不能只在前端比较字段：API、重复请求和并发变化仍会绕过。
- 不能只给所有函数加 `with_for_update()`：无差异请求不应先拿锁，且跨用户思考时间绝不能持有事务。
- 不能简单删除审计函数内部 commit：许多旧调用方依赖它自提交，直接改动会造成“看似执行、实际随请求回滚”。
- 不能把密码/Token 的“每次都变化”当成无效写入；这是命令语义，只应保证确认、幂等键（如需要）和审计完整性。

## 11. 历史最终建议（2026-10-28）

**下一步仍应先完成当前用户编辑 M0，而不是立即横向开改。**M0 验收通过后，下一份正式设计应是“任务编辑差异写入、并发保护、调度副作用与操作日志一致性”，因为它是同类问题中业务影响、性能浪费和运行风险最高的入口。密码/Token 的审计原子性作为独立 M2，不与任务编辑混在同一批实现。
