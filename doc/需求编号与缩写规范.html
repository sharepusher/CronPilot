需求编号与缩写规范

OPT / Tier / Phase / DEC 四轨并存时的书写与解读约定

状态：已生效 · 2026-07-20

一句话：「P1」「Tier 1」「D1」不是同一套编号。 对外与路线图须写带前缀的全称；简称仅在同页已定义后可用。
权威落点：本页 · 交付状态与路线图 · 依赖升级 RFC（OPT-P2-11）· 仓库 .cursor/rules/cronpilot-project.mdc。

一、四条轨道（必须分清）

轨道正式写法含义权威出处
产品优先级 优先级 P0 / P1 / P2 安全 → 可观测 → 增强；描述一类工作的先后，不是单条需求 ID 产品 PRD
功能需求 OPT-P1-03 OPT + 优先级 + 序号；单条可交付需求 PRD · 交付状态 §二
依赖大阶段 Tier 0～4（属 OPT-P2-11） Flask / SQLAlchemy / gevent 等依赖升级分层 依赖升级 RFC
ORM / 框架子阶段 Phase A/B/C、Phase D0～D3 Tier 3/4 下的实施切片（分页、Repo、AST、pin、Mapped、Docker） RFC · Phase D0
RFC 决策 DEC-008 依赖 RFC 内的决策记录编号 依赖升级 RFC §决策表
生命周期专项 LIFECYCLE-2 任务元数据 / 下线可追溯等 生命周期设计

二、书写强制格式

场景正确禁止 / 避免
路线图、RELEASE、聊天标题 OPT-P1-03（执行详情页） 单独用「P1-03」「P1」指该需求
依赖子阶段 Phase D3（OPT-P2-11 · Framework Generation · Docker 矩阵） 跨文档仅写「D3」且无归属
依赖大阶段 Tier 3b（OPT-P2-11 · 迁移重放） 与 OPT 序号混称（如「做完 Tier1 再做 P1」不说明轨道）
同页二次提及 首次全称后可用 Phase D3 / OPT-P1-03 首次就裸写 D1 / P1

推荐句式

下一依赖动作：Phase D3（OPT-P2-11 · Framework Generation · Docker / pip show 矩阵）
下一功能项：OPT-P1-03（独立执行详情页）——设计待确认
依赖大阶段：Tier 2（OPT-P2-11）已随 v0.2.0 交付

三、易混别名（历史）

写法易误解为实际
Phase A（P0）· v0.1.0 发行用语 现行 ORM Phase A 产品优先级 P0 安全包（SQL/密码/SSRF 等）；≠ Phase A Query Contract
Phase A · Query Contract 产品 P0 OPT-P2-11 下 ORM 子阶段（分页硬门）
B1（DEC-008） UI 设计 B1 Flask 2.3 + SA2 同窗方案；UI 稿另有 B1，须写「DEC-008 B1」或「UI B1」
A′ / B1（管理端 UI） Tier / Phase 仅 UI 设计稿内部方案代号
口头「P1」 OPT-P1-xx 仅「优先级 P1」；单条需求必须带 OPT-
不强制 bulk 改写历史 Release Notes / 旧设计稿正文中的简称； 新文档与路线图「建议实施顺序」须遵守本规范。读旧文时以本表「易混别名」为准。

四、与交付状态的对应

  • §二 功能优化（OPT-*） — 产品功能轨
  • §三 依赖升级（OPT-P2-11 · Tier / Phase） — 依赖与 ORM/框架子阶段
  • §五 建议顺序 — 每条须含 OPT-… 或 Phase …（OPT-P2-11） 或 Tier …
