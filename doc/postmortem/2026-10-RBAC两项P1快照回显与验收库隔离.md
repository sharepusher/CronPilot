# RBAC 两项 P1：快照回显与验收库隔离修复复盘

日期：2026-10-29 · 版本：rev.1 · 状态：两项 P1 已修复并验证；独立 P2 未关闭 · 设计已获用户明确确认

| 版本 | 日期 | 变更 |
| --- | --- | --- |
| rev.1 | 2026-10-29 | 记录两项 P1 的实际修复、永久防护测试、MySQL 和浏览器证据；不处理独立 P2。 |

## 1. Bug 定位

**P1-A：**`app/rbac/views.py::users_edit` 曾在 GET/POST 分支前重建 token。原生清空确认保留旧输入却更换 original，使并发新邮箱可被二次提交清空。**P1-B：**`scripts/verify_user_edit_transaction_mysql.py::verify` 曾无校验执行 drop\_all，有误删调用方数据库表的风险。本轮没有证据表明真实业务库已遭误删。

## 2. 根因

P1-A 将原始基线、当前授权/数据库对象和请求输入放进一个通用回显上下文；把回显当成纯展示，忽略 hidden token 会影响下一次写入。P1-B 把“在正确临时容器运行”当成脚本自身隔离，把数据库清空当成 fixture 初始化，缺少资源所有权和默认拒绝边界。

## 3. 测试漏洞

旧原生回显测试仅检查提示、保留输入与字段数量，没有检查多次失败响应中的 token 原文连续性；服务并发测试没有中间确认回显。MySQL 原测试只证明正确环境的锁等待，没有覆盖非法 URL、无关占用表/视图、metadata 扩大、部分 DDL 或同库竞争。

实施期间一条 Scope 测试先因缺 token 被新守卫拒绝；已为其补真实 GET token，使它仍断言原有全局授予拒绝和业务零变化，没有降低权限断言。浏览器 harness 的必填理由和 Scope 302 拒绝行为按现有产品契约执行，未通过修改产品代码适配错误测试预期。

## 4. 修复

- 仅 GET 创建签名基线；POST 验签后复用收到的 token 原文，回显的 JS original 也来自 verified snapshot。
- 可恢复失败以独立 form\_values 保留请求字段，不污染 ORM User；非法 token/无法安全回显的 Scope 参数不提供可提交新表单，只提供显式重新加载入口。
- 原生邮箱确认展示已验签原邮箱；恢复 JS 后，动态 hidden 理由独占 name，移除原生 textarea 的同名字段，避免后端取得旧理由。
- 脚本连接前只接受明确专用 mysql+pymysql URL；连接后检查默认库、所有表和视图；不 DROP/TRUNCATE，限定四表，checkfirst=False，全部建表成功后才写 fixture。
- 脚本错误只返回固定诊断，不回显连接串/密码。成功、失败都保留 schema；连接资源关闭，外层管理一次性实例。管理员角色和资料编辑权限沿用现有设计。

## 5. 防护测试与实证

永久命令：

```
.venv-py311/bin/python -m unittest tests.test_user_edit_change_set tests.test_user_edit_mysql_guard -v
.venv-py311/bin/python -m unittest tests.test_rbac_global_scope_assignment.TestGlobalScopeAssignmentRouteGuard.test_native_edit_global_scope_denial_has_no_business_side_effect -v
```

- 专项 43 项通过：含 10 项新增回显/并发/权限测试与 9 项 MySQL 守卫测试。核心断言是 echo token == 首次 token，而非重新解码后“看起来有效”。
- 真实 MySQL 8 独立容器：专用账户只有 SELECT/INSERT/UPDATE/CREATE/INDEX，无 DROP。成功执行原锁等待/审计/冲突/锁释放；四表白名单排除了额外 metadata；非空无关表/视图哨兵 42 保持；重复执行拒绝；两个实例同步越过检查后只有一个成功；注入第二表 DDL 失败后首表零行保留、重跑拒绝。
- 浏览器证据与联合回归：见下方最终验收结果。

## 6. 同类排查

`rg -n 'drop_all\(|TRUNCATE|sign_.*snapshot|edit_snapshot_token=' scripts/ app/ --glob '*.py'`：用户编辑签名只在 GET 分支；POST 赋值来自 incoming\_token。脚本 drop\_all 残余只在 `scripts/smoke_routes.py`，其 fixture 为独立内存测试数据库，与本次接受外部 URL 的工具不同，未扩改。两项独立 P2（业务组 JS 选择器、未知审计字段 partial 策略）仍未修复，不宣称整批无剩余问题。

## 7. 预防方案

- `tests/test_user_edit_change_set.py`：固化原生确认、空/超长理由、资料校验失败、写失败的 token 原文不变；缺失/篡改/版本/绑定失败不得产生可提交新基线；新增授权耦合、旧空邮箱并发新增及 actor 降权负例。
- `tests/test_user_edit_mysql_guard.py`：非法目标零 app/连接、占用目标零 DDL、检查错误拒绝、只建四表且 checkfirst=False、fixture 前失败、异常脱敏和 AST 禁止 drop/drop\_all/TRUNCATE。上述第一条永久命令可由第三方重现。
- 真实 MySQL 演练必须包含非空哨兵与并发占用；仅成功锁等待不构成脚本隔离验收。失败保留现场，不能通过清空原库重试。
- 浏览器回归必须覆盖原生与 JS 两种路径，隐藏字段与可见字段同名要检查实际 POST 参数；不能以 DOM 字符串存在代替按钮点击。

## 8. 最终验收结果

- 联合回归 223/223，318.156 秒；专项 43/43；86 条路由全部通过。
- Ruff（app 与改动脚本/测试）、UI 契约、路由完整性、颜色审计通过；开发 SQLite 业务表完整。
- 真实 Chrome 目标账号 POST 登录：global/scoped 原生确认的 T0 连续、并发冲突、非法 token 无可提交表单；scoped 越组重定向拒绝；正常 JS 清空成功；恢复 JS 之后实际 POST 中 confirm\_clear\_email/email\_clear\_reason 各一个；Operator/Viewer 用户管理 403。结果六项全 true。
- MySQL 六项隔离/并发/DDL/保留检查全 true；成功锁释放分别 5.0ms、9.0ms，成功审计均 1 行。专用 MySQL 8 账户用 mysql\_native\_password 适配现有客户端，无新增依赖；未改变业务数据库认证配置。
- 本地 restart 后 daemon 进程未持续存活，使用持久前台会话继续运行；登录 GET 200，已执行真实浏览器 POST 登录，服务保持可复验。
- 复盘门禁有 41 条已有历史 Release 引用告警（非本次新增复盘）；本次复盘已引用，未将历史告警冒称全绿。磁盘短暂不足导致一次截图失败，已重试完成全部证据；只请求清理本轮临时 MySQL 容器，无操作已有容器。

## 9. 本地复验

服务入口：`http://127.0.0.1:5001/rbac/login`。专用本地验收账号 `p1_review_global`（全局业务管理员）、`p1_review_scoped`（组 A 管理员）、`p1_review_target`（组 A Viewer）、`p1_review_operator`。密码统一 `P1Review!2026`，仅为本地隔离 fixture，非真实用户凭据。账号及专用组暂保留，供用户复验；未清理为零。

1. 管理员登录 → 用户管理搜索 `p1_review_target` → 查看 → 编辑。正常 JS 清空邮箱，应先弹出理由确认。
2. 禁用该页 JS，重新加载编辑页，清空邮箱并保存；应出现原生确认和“本次确认原邮箱”，原始 token 保持。
3. 另一个浏览器以目标本人登录，先在个人资料页改邮箱；原生确认继续填写理由并保存，应显示冲突且保留本人新邮箱。
4. 组 A 管理员访问组 B 目标应重定向用户列表；Operator/Viewer 访问用户管理应为 403。
