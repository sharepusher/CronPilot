# Dashboard 统计卡片文案优化设计

版本 rev.3 · 2026-09-02 · 编号 OPT-P1-17

## 1. 问题

### 1.1 用户反馈

Dashboard 显示「9 个任务持续异常」「9 个任务异常」但「今日失败次数 0」，用户困惑：异常任务从哪里来？既然今天失败为 0，为什么还有 9 个异常？

### 1.2 根因分析

| 问题 | 描述 |
| --- | --- |
| **时间维度不可见** | 「异常任务」和「持续异常」基于 `job_health` 表的累积状态（自上次成功执行以来的连续失败），不受日期约束；「今日失败次数」基于 `job_log` 当日记录。两者时间维度完全不同，但 UI 文案未做任何区分，用户默认以为都是「今天」的数据。 |
| **卡片 1 和卡片 2 语义重叠** | 「异常任务」= `health_status == 'failing'`；「持续异常」= `consecutive_failures >= 3`。当阈值为默认 3 时，两者数值必然相同（health\_status 在 consecutive\_failures >= threshold 时设为 'failing'），展示两次造成信息冗余。 |
| **术语冗余** | 顶栏 stat-line 用「持续异常」「今日告警」；卡片用「异常任务」「持续异常」「今日失败次数」— 三种近义词混用。 |

## 2. 方案 推荐

### 2.1 合并卡片 1 和卡片 2

将「异常任务」和「持续异常」合并为一张卡片，消除冗余。使用 `consecutive_failing`（count\_consecutive\_failing 查询）作为唯一数据源，因为它直接反映连续失败计数且查询语义更清晰。

### 2.2 增强 sub-text 说明时间维度

每张卡片的 sub-text 明确标注数据的时间范围，消除用户对「今天」vs「累积」的混淆。

### 2.3 新增一张有意义的卡片替代被合并的卡片

用「今日成功率」替代被合并的位置，提供正向指标，平衡 Dashboard 的"告警焦虑"。

### 2.4 已下线任务统计口径（rev.4 更新）

**决策变更（rev.4）**：所有健康/性能指标统一排除已下线任务（`CronInfos.status != -1`）。原因：已下线任务不再参与调度，其历史健康数据不应影响当前仪表盘的运营判断。

| 指标 | 是否包含已下线 | 实现 |
| --- | --- | --- |
| 任务总数 `total` | **包含**（全部状态） | `SELECT COUNT(*) FROM cron_infos`，不过滤 status（展示系统中所有任务的总数，含下线与暂停） |
| 持续异常 `consecutive_failing` | **不包含**（rev.4 变更） | `job_health JOIN cron_infos WHERE consecutive_failures >= 3 AND cron_infos.status != -1` |
| 逾期未执行 `overdue_count` | **不包含** | `WHERE status == 1` 仅统计运行中任务（原有逻辑，无需变更） |
| 今日失败 `today_fail_runs` | **不包含**（rev.4 变更） | `job_log JOIN cron_infos WHERE ... AND cron_infos.status != -1` |
| 今日总执行 `today_total_runs` | **不包含**（rev.4 变更） | `job_log JOIN cron_infos WHERE ... AND cron_infos.status != -1` |
| 今日成功率 `today_success_rate` | **不包含**（rev.4 变更） | 分子分母 SQL 均添加 `cron_infos.status != -1` |
| 异常任务数 `failing` | **不包含**（rev.4 变更） | `job_health JOIN cron_infos WHERE health_status = 'failing' AND cron_infos.status != -1` |

**设计决策（rev.4 更新）**：所有健康与性能指标统一排除已下线任务。已下线任务不再参与调度，其历史执行/失败记录不应影响当前仪表盘的运营判断。仅「任务总数 `total`」保留全部状态，作为系统资产的总览计数。变更范围：`app/repositories/cron_repository.py` 中 7 条查询语句添加 `.where(CronInfos.status != -1)`。

### 2.5 「逾期未执行」判定逻辑说明

**用户疑问**：如果今日没有执行，岂不是所有任务都逾期了？

**答案**：不是。逾期判定基于 `cron 调度间隔 × 2`，不是简单的"今天有没有执行"。示例：

| 任务 | 调度间隔 | 逾期阈值 | 上次执行 | 是否逾期 |
| --- | --- | --- | --- | --- |
| 日报汇总 | 每日 8:00 | 48 小时 | 昨天 8:00 | 否（距今 < 48h） |
| 实时监控 | 每 5 分钟 | 10 分钟 | 30 分钟前 | **是**（距今 > 10min） |
| 周报 | 每周一 9:00 | 14 天 | 上周一 9:00 | 否（距今 < 14d） |

sub-text 调整为「距上次执行超 `max(间隔×2, 10min)`」，更准确传达实际逻辑。

### 2.5 今日无执行时的显示策略

**用户疑问**：今日没有执行数据时，「今日失败 0」和「今日成功率 100%」是否误导？

**答案**：是的。「0 失败」暗示「检查过了，没有失败」；「100% 成功率」暗示「所有执行都成功」。但实际可能是今天还没有任何执行。

**解决方案**：后端返回 `today_total_runs`（今日总执行次数），前端根据此值区分显示：

| 场景 | today\_total\_runs | 今日失败 显示 | 今日成功率 显示 |
| --- | --- | --- | --- |
| 有执行且无失败 | > 0 | `0` | `100%` |
| 有执行且有失败 | > 0 | `N` | `X%` |
| 今日无执行 | 0 | `—` | `—` |

sub-text 在无执行时显示「今日尚无执行记录」，避免「0」的歧义。

**后端改动**：`metrics()` 新增 `today_total_runs` 字段（已有的 `today_fail_stmt` 改为统计全量，再分别过滤 fail/success）；`today_success_rate()` 在 total=0 时返回 `None` 而非 `100.0`。

### 2.6 卡片排序策略

**原则**：相关指标相邻，形成两组「信息对」，用户一眼扫完一组即可理解该维度的完整状况。

| 位置 | 组 | 指标 | 逻辑 |
| --- | --- | --- | --- |
| 卡片 1 | 健康组（累积/实时） | 持续异常 | 累积健康状态 |
| 卡片 2 | 逾期未执行 | 实时快照 |
| 卡片 3 | 今日组（当日） | 今日成功率 | 正向指标 |
| 卡片 4 | 今日失败 | 反向指标 |

### 2.7 变更明细

| 位置 | 当前 | 优化后 | 理由 |
| --- | --- | --- | --- |
| 卡片 1 | 异常任务 · `metrics.failing` · "需要立即关注" | **持续异常** · `consecutive_failing` · "≥N 次连续失败，直到恢复" | 保留核心健康指标，sub-text 说明「持续」语义 |
| 卡片 2 | 持续异常 · `consecutive_failing` · "≥3 次连续失败即标记" | **逾期未执行** · `overdue_count` · "距上次执行超 max(间隔×2, 10min)" | 与持续异常同属健康组，相邻展示 |
| 卡片 3 | 逾期未执行 · `overdue_count` · "超过 2 倍调度间隔" | **今日成功率** · `today_success_rate`% 或 `—` · "今日已执行 N 次" 或 "今日尚无执行记录" | 正向指标 + 无执行时显示 `—` 避免误导 |
| 卡片 4 | 今日失败次数 · `today_fail_runs` · "N 个任务 · 成功率 X%" | **今日失败** · `today_fail_runs` 或 `—` · "0:00 以来" 或 "今日尚无执行记录" | 明确时间范围；无执行时显示 `—` |
| 顶栏 stat-line | `N` 个任务 · `M` 持续异常 · `K` 逾期 · `J` 今日告警 | `N` 个任务 · `M` 持续异常 · `K` 逾期 · `J` 今日失败 或 `—` | 统一术语 + 无执行时显示 `—` |

### 2.8 四卡片时间维度一览

| 组 | 卡片 | 时间维度 | 计算方式 | 清除条件 |
| --- | --- | --- | --- | --- |
| 健康组 | 持续异常 | **累积（无时间边界）** | `job_health.consecutive_failures >= 3` | 任务成功执行一次 → consecutive\_failures 归零 → 自动消失 |
| 逾期未执行 | **实时快照** | `now - last_exec > max(interval × 2, 600s)` | 任务执行一次（无论成败）→ last\_exec 更新 → 自动消失 |
| 今日组 | 今日成功率 | **当日（0:00 至今）** | 今日成功次数 / 今日总执行次数 × 100% | 每日 0:00 自动重置 |
| 今日失败 | **当日（0:00 至今）** | `job_log` 中今日 fail/error/timeout 记录数 | 每日 0:00 自动重置 |

**关键用户认知**：「持续异常 9 + 今日失败 0」含义是：有 9 个任务在此前累积了 ≥3 次连续失败（可能是昨天或更早），今天它们尚未执行（或未失败），所以今日失败为 0，但它们的累积异常状态尚未被清除。

## 3. 范围

### 3.1 改动文件

| 文件 | 改动内容 |
| --- | --- |
| `app/repositories/cron_repository.py` | `metrics()` 新增 `today_total_runs` 字段；`today_success_rate()` total=0 时返回 `None` |
| `app/main/views.py` | AJAX 响应中传递 `today_total_runs` |
| `app/templates/redesign/dashboard.html` | 4 张卡片文案 + stat-line 文案 + AJAX 刷新 JS + 无执行时 `—` 显示逻辑 |

### 3.2 不做什么

- **不改健康判定规则**：`health_failing_threshold` 默认 3 保持不变
- **不改逾期判定规则**：`max(interval×2, 600s)` 保持不变
- **不新增 tooltip 组件**：仅通过 sub-text 自然语言解释，不引入额外 JS

## 4. 分批

| 批次 | 内容 | 验收 |

## 5. 验收

| # | 场景 | 期望 |
| --- | --- | --- |
| 1 | Dashboard 加载（有执行数据） | 4 张卡片：持续异常 / 今日成功率 X% / 逾期未执行 / 今日失败 N |
| 2 | Dashboard 加载（无执行数据） | 今日成功率 → `—` + "今日尚无执行记录"；今日失败 → `—` + "今日尚无执行记录" |
| 3 | stat-line 文案 | 「N 个任务 · M 持续异常 · K 逾期 · J 今日失败」（无执行时 J → `—`） |
| 4 | AJAX 筛选切换 | stat-line 和卡片数值正确刷新，不出现旧文案 |
| 5 | 有失败场景 | 「今日成功率 X%」 + 「今日失败 N」 + sub-text 显示执行总次数 |
| 6 | 0 失败场景 | 「今日成功率 100%」 + 「今日失败 0」 + 「持续异常 N」含义无矛盾 |

## 6. 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 合并卡片后丢失 `metrics.failing` 展示 | 低：`failing` 和 `consecutive_failing` 在默认阈值下数值相同；Exception Panel 已展示具体失败任务列表 | Exception Panel 补偿了卡片信息丢失 |
| `today_success_rate` 返回 `None` 需要前端兼容 | 中：AJAX 刷新和模板渲染都需处理 None 值 | 模板中用 `{% if today_success_rate is not none %}` 条件渲染；JS 中检查 `stats.today_success_rate === null` |
