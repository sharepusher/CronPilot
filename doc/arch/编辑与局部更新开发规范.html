编辑与局部更新开发规范

版本：v1.0 · 日期：2026-10-29 · 状态：开发规范已落库；无运行时或 CI 行为变更。适用于编辑表单、资源局部更新、关联集合编辑及相关服务和验收。本文的“必须/禁止”为 CronPilot 项目要求；“建议”允许在正式设计中说明替代方案。

总原则：只更新被明确请求、当前有权修改、通过并发检查且确实发生变化的数据；未编辑、不可编辑和范围外数据必须受到保护。可读、可编辑、可授予是三种不同权限，不能互相推导。本规范不改变现有管理员权限；具体权利继续以已批准的业务设计为准。

1. 官方实践及项目推导边界

以下是公开可核对的工程资料，不代表这些企业所有系统使用同一实现，也不是对 CronPilot 的官方背书。来源结论与项目决策分开标注；核对日期为本文日期。

来源来源支持的原则CronPilot 的采用方式与边界
Google AIP-134 Update、AIP-161 Field masks支持局部更新；字段掩码表达更新路径，未选路径不应随请求改变。AIP 的 Update 还将一般资源更新与其他副作用区分。采用“更新字段集合”概念；传统 POST 表单可由可信原值计算意图，无需为规范而迁移为 gRPC/FieldMask。掩码表达范围，不证明字段实际变过或调用者有权。角色变化所需认证失效仍由本项目安全契约约束。
Google AIP-154 Resource freshness；Microsoft API implementation / optimistic concurrency使用资源版本/ETag 验证客户端看到的状态；Microsoft 指出版本条件检查与写入必须原子执行，内存检查后无条件保存仍有竞态。本项目用户编辑采用可信原值三方比较与写事务内校验。它解决类似并发问题，但不是实现了 HTTP ETag。整资源 ETag 可更保守地拒绝无关并发，不可误称其不专业。新 API 可在设计中选择原子版本条件更新。
AWS Builders’ Library：Making retries safe with idempotent APIs用调用方请求标识识别同一操作的重试，并使标识记录和业务变更原子；相同标识、不同意图不能当作相同操作。普通目标状态编辑先保证等价请求不重复生效；支付、发送、创建等命令如需重试，另设计操作键、参数绑定和保留期限。签名编辑 token 不承担操作去重键职责。
AWS Transactional outbox pattern本地数据库与外部消息双写可出现不一致；outbox 把发送意图与业务状态写在同一事务，后续可靠投递。本库成功审计直接与业务同事务。仅当引入外部事件、邮件等可靠副作用时评估 outbox；本轮不引入队列，不声称 DB commit 能使任意远端操作原子化，也不声称 outbox 天然 exactly-once。
OWASP Authorization、Mass Assignment服务端校验每次请求的权限、默认拒绝；使用专用输入对象和字段白名单限制可写属性。字段白名单与对象/操作授权分别执行；禁止把整个请求自动绑定 ORM。禁用控件、隐藏字段和签名均不能替代当前授权。OWASP 是安全社区，不将其写成某家企业标准。

2. 统一模型：四类事实、两层差异

  • 原始值 O：用户打开编辑页时的可信基线；由签名或服务端存储保证完整性，绑定对象及编辑者。snapshot 是数据集合，不是截图。
  • 可编辑范围 E：字段白名单、可管理集合及允许的操作。比较两侧必须是同一 E 下的规范化值；只读展示值不等于可写输入。
  • 请求值 R：用户提交的规范化输入，或带明确字段集合的局部更新请求。字段在 payload 出现，不等于用户修改了它。
  • 当前值 C：写入时重新读取并受事务/并发条件保护的数据库事实；决定当前权限、冲突及实际写入。

意图差异回答“用户请求改什么”；有效差异回答“授权和并发检查后，本次真正改变什么”。审计、Token 轮换、认证版本和缓存处理必须依有效差异，不能仅依字段出现或意图非空。

“只改一个字段”指业务字段的修改边界；更新时间、操作者等系统维护元数据可按已声明契约随真实修改更新，不得借此改变无关业务字段。无真实修改时是否更新访问元数据，应与业务写入和成功变更审计分开定义。

可信基线与编辑范围→ 规范化与意图→ 当前授权与并发校验→ 有效差异→ 业务与审计原子提交→ 已设计的副作用与结果

3. 必须执行的更新契约

EDIT-01：声明字段语义，禁止全量盲写

设计必须逐字段定义可写主体、可读范围、规范化、缺失/null/空串/空集合语义及副作用；输入字段须白名单解析。局部更新中“未选择该字段”表示不更新；显式清空须符合业务约定。完整 HTML 表单缺失其必需字段时可以拒绝，不能机械套用 PATCH 的省略语义。JSON Merge Patch 的 null 有删除含义，不可无设计地套给合法可空字段。

集合若为数学集合，才可排序去重；有序数组、可重复项不能按组 ID 集合规则处理。空组不应默认解释成全局，必须存在明确业务表示和授权。

EDIT-02：意图必须来自同一编辑范围

传统表单在同一可信投影内比较 O 与 R；局部 API 可用明确更新字段集合表示意图。服务端必须重新验证字段和范围，不能信任 JS 给出的 dirty 标志或客户端自行上传的原始值。未知字段应按接口契约拒绝或安全忽略，不能悄悄绑定到实体；当前带版本签名基线采用精确 schema 校验。

EDIT-03：范围外关系必须保留

可见子集不能作为完整关联集合替换。若仅允许编辑 E 内成员，则无并发冲突时完整目标等于“受保护的 E 外绑定 + 合法请求的 E 内绑定”。每次新增/删除分别校验当前权限；已有外部绑定是保留状态，不是本次新授权。对完整授权单元仍须做并发校验，不能为了保留外部关系而跳过授权或随意拼接两个时点的数据。

管理员只管理 A；目标属于 A+B；表单原值 A，提交 A：没有组修改。
只把花名“小夏”改为“Summer”：仅更新花名及对应成功审计。
管理员管理 A/C；目标 A+B；合法改 A→C：目标 C+B，保留 B。
只改花名期间他人把外部 B 改为 D：有权且花名无冲突时，保留当前 A+D。
真正改组期间他人改变完整授权：按授权单元并发策略拒绝不兼容覆盖。

EDIT-04：保存前使用当前权限

对象、字段与关系操作权限必须在服务端依据当前可信事实检查；需要消除授权检查到写入的竞态时，在事务边界锁定或使用等价原子机制。当前用户停用、降权、退出管理交集应拒绝。编辑范围变化时，本项目签名表单要求刷新，不能用新范围重新解释旧表单。跨请求 Session 缓存只可按已批准的失效/版本策略使用。

EDIT-05：并发检查必须与写入原子结合

必须在正式设计中选择版本条件更新、三方比较或其他可验证策略，并说明比较粒度。独立资料字段可以逐字段处理；角色与组等耦合权限必须作为整体检查。本规范不强制所有业务采用同一粒度。

针对有修改意图的独立字段行为
C 等于请求目标 R已等价完成，不重复写入及副作用。
C 等于原始值 O，且 C 与 R 不同允许写入 R。
C 既不是 O，也不是 R冲突，整体拒绝本次需原子完成的编辑。
该字段没有修改意图不写回；保留 C，仍执行当前对象权限及必要业务不变量检查。

整资源 ETag 方案可以拒绝更多并发，三方比较方案则须明确定义可合并边界；两者都不能先在事务外检查，再无条件覆盖。SQLite 逻辑通过不能证明 MySQL 行锁语义。

EDIT-06：确认和错误回显不能重新建立原值

合法可恢复 POST 的确认、校验失败和重试必须保留原始编辑基线，用户输入另存，不把 DB 当前值冒充原值。必须显式重新 GET/刷新才能建立新基线。旧版本/坏签名/主体失配应拒绝继续编辑。签名保护完整性，不提供保密性、当前新鲜度或授权；不可读取的数据不应因“已经签名”而泄露给客户端，可选择服务端保存基线。

二次确认用于表达清空等高影响行为的意愿，不能代替权限、并发和服务端校验。原因应按业务约定验证且不含秘密；确认取消零业务 POST。原生与 Ajax 路径应具备相同安全契约。

EDIT-07：业务与成功审计同事务

同库业务变更与成功审计必须一次原子提交。任何字段冲突或审计写失败不得留下部分业务结果。审计只记录实际 before/after 和必要原因，不记录密码、Token 或 Session 内容。拒绝审计、HTTP 访问日志和安全日志可以独立存在；“no-op 零成功变更审计”不等于禁止记录请求访问或攻击。

事务所有权必须明确：服务拥有写事务时须在返回终态前结束；外层拥有事务时须明确由外层承担完成责任。禁止隐式依赖框架 teardown 才释放锁。该规则是设计与验收要求，不是对所有现有路径已完成验证的声明。

EDIT-08：副作用必须有触发条件和可靠性边界

仅改花名不应重签 Token、递增认证版本或变更组；真正授权变化按既有安全契约执行必要失效动作。无变化、已等价应用、冲突均不得重复触发成功副作用。对 COMMIT_UNKNOWN，不可假设事务必然未提交；按既有设计进行结果核对和必要的保守缓存失效，不盲目重放。

跨进程缓存失效、事件和邮件不因本地 commit 自动可靠。新需求必须单独设计 outbox/CDC/可重试投递及消费幂等；本项目当前 worker 的 best-effort 缓存失效不等同于全局可靠通知。

EDIT-09：目标状态编辑与业务命令分别定义幂等

对“设置为某值”可通过有效差异与等价完成保护重复提交；禁用按钮只改善体验，不是服务幂等保证。“增加一次额度”“发送通知”“创建实例”不能用参数相同就判重复，需另设计操作标识、请求参数绑定、保留期限、原子记录与结果查询。角色切换/凭据重置/上下线等行为是否拆为专用命令，由业务设计确定，不往通用资料保存中暗加。

EDIT-10：响应必须区分结果而非统一“成功”

至少区分实际更新、无修改意图、已等价完成、冲突、确定失败与提交结果未知。确认尚未完成是非终态。表单可以沿用业务 outcome 和 PRG，API 可以采用相应 HTTP/领域错误；Google 的 ABORTED 与 HTTP If-Match 的 412 不是同一套响应约定，禁止无迁移设计改现有接口。

4. 测试与 Review 的最低矩阵

场景必须观测的断言
无修改；直接绕过前端提交正常 JS 零 POST；服务端零业务 DML、零成功变更审计、零授权副作用；当前权限仍有效才可响应。
仅改一个资料字段字段级 DB 差异、关系表零 DML、其他标量/Token/认证版本不变；成功审计只有有效字段。

确认、输入失败、多次原生回显、恢复 JS基线 token 保持；原值投影不漂移；字段名唯一；完整交互与正反向角色路径截图。
审计失败、提交结果未知、重复/延迟请求审计和业务一致；未知结果明确提示；不按“报错”等同“肯定未提交”；命令幂等契约单独覆盖。

6. 设计评审与交付检查单

可直接填写的 C01–C10 检查单、行为用例映射和拟实施 CI 门禁见检查单与行为门禁设计 §2。该 CI 设计待确认；现有 unittest discovery 已覆盖专项测试，不能将其误写为完全没有自动回归。

  1. 设计阶段：列字段语义、可读/可写/可授予范围、集合替换/增减语义、并发比较粒度及副作用矩阵；已有页面可见变更仍先提供 Before/After。
  2. 实现阶段：入口白名单规范化，服务执行当前授权及原子并发检查，写入与成功审计单事务；基线、请求和当前状态分别保存。
  3. 验收阶段：按第4节选出适用场景并说明不适用原因；浏览器测正反向、数据库测实际差异、真实后端测事务语义，不能用静态规则声称行为已证明。
  4. 交付阶段：同步设计/复盘/索引和可复验环境；如要新增协议、字段、DB结构或 CI 门禁，先走独立设计确认。本规范自身不授权这些运行时变更。

7. 适用、采用与风险

问题与根因：通用“保存表单”容易混淆 payload、用户意图、当前权限与实际变更；全量回写和覆盖式关系保存会放大到越权、丢失更新与错误审计。本文用统一模型和可执行断言解决认知分歧。
