# 发布工作流安全加固未提交变更专业评估

日期：2026-10-27 · 范围：当前未提交的发布治理、安全工作流、版本检查、测试与配套文档 · 审查方式：静态代码、工作流数据流、Git 对象语义及已执行专项验证复核。

**总裁决：不建议按当前状态合并或用于下一次新版本发布。** S1/S2/S3 的安全方向和大部分实现均专业、准确且明显优于原方案；但 S4 的 `source_commit` 自引用契约在未来 tag 上不可构造，发布 job 会安全地失败。因此当前结论为“安全设计大体正确，但可发布性不通过”；先修正该 P1 阻断项后再合并。

## 1. 变更全景与总体评分

| 维度 | 评级 | 依据 |
| --- | --- | --- |
| 安全架构 | A- | 构建/发布权限拆分、只读 checkout、Action SHA 固定和 draft→校验→发布的状态机符合最小权限与供应链隔离原则。 |
| 正确性/可发布性 | C（阻断） | 版本化清单要求记录自身所在 commit 的 SHA，形成 Git commit 内容哈希的自引用；新 tag 无法满足该等式。 |
| 健壮性 | B+ | 严格 tag 校验、拒绝 `Unreleased` fallback、回读三类 Release asset 并比较内容，失败均为 fail-closed。 |
| 测试与可维护性 | B | 已有脚本单测和工作流静态断言；但尚无能暴露未来 tag 自引用失败的集成测试，也没有真实 GitHub 环境演练证据。 |
| 文档治理 | A- | 设计、复盘、QA、索引和 HTML↔Markdown 同步齐备；需把 S4 的 commit 绑定模型订正为非自引用模型。 |

## 2. 关键阻断项：`source_commit` 的自引用不可满足（P1）

**定位：**`release/release-manifest.json` 写入 `source_commit`；`.github/workflows/release-asset.yml` 同时用 `git rev-parse "$GITHUB_REF_NAME^{commit}"` 和 `jq` 强制二者相等；`scripts/check_version_consistency.py` 也将该字段设为 tag 发布前置条件。

**根因：**Git commit ID 是包含 tree 内容、父提交、作者时间和提交信息的对象哈希。若将“本 commit 的 SHA”写入清单后再提交，tree 内容改变，commit SHA 也随之改变；把新 SHA 再写回会继续改变 SHA。除非求解不可行的哈希固定点，无法让版本化文件的值等于包含它的 commit ID。

```
提交前 manifest.source_commit = A
创建 commit 得到 SHA = B（B 的内容包含 A）
把清单改为 B 后重新创建 commit 得到 SHA = C（C 的内容包含 B）
因此 B ≠ C，工作流要求的 source_commit == C 永远不能常规满足。
```

**影响：**当前清单能通过 `v4.1.1` 的检查，仅因为它被在该历史 tag 之后新增，并手工填入旧 tag SHA；下一次版本要把更新后的清单纳入待 tag 提交时，`build-validate` 会在“Verify structured release readiness”阶段失败。这是安全失败（不会误发），但会阻断发布。

**合理修正：**从提交进仓的 manifest 删除 `source_commit`，仅保留可在 tag 前人工评审的 `version`、`readiness`、`release_blockers`。tag→commit 绑定应继续由 workflow 的 `git rev-parse` 与构建产物 `.build.json` 的 `source_commit` 进行验证；后者由构建过程在已确定的 tag commit 上生成，因而不存在自引用。若必须持久化清单 SHA，应在 tag 创建后生成并作为 Release artifact/attestation 保存，而不是放入被该 tag 指向的源码 tree。

## 3. 其余方案的专业性与准确性

| 变更 | 专业评估 | 结论 |
| --- | --- | --- |
| S1：`build-validate` 只读、`publish` 单独 `contents: write`，checkout 不持久化凭据 | 准确。把不可信 tag 代码执行面与写 Release 权限隔开，显著缩小 token 可达面；job 级最小权限比仅在步骤中隐藏 token 更可靠。 | 应保留。 |
| Action 固定到完整 SHA | 准确。避免 tag 可变造成的第三方 Action 供应链漂移；所用 checkout/setup-python/upload/download 都被固定。 | 应保留，并建立 SHA 更新维护流程。 |
| S2：严格 `vX.Y.Z` 与 versioned Release Notes | 准确。workflow glob 只能做候选筛选，运行时正则和 `--require-version-section` 才是实际信任边界；拒绝 Unreleased fallback 合理。 | 应保留。 |
| S3：draft 后下载回读、`cmp`、sha256 和 build report commit 校验 | 准确且强度适中。它证明远端 Release 三个用户交付资产与本轮构建输出一致，校验通过前不会解除 draft。 | 应保留。 |
| 旧的英文 blocker 正则 | 实现对声明的“已知短语防回归”是准确的，但不是自然语言语义分析，也不应继续被描述成通用发布治理保证。 | 保留为兼容性 lint；以结构化字段承担状态判断。 |

## 4. 条件、测试缺口与发布前门槛

- **GitHub 环境不是代码保证：**`environment: release` 只有在仓库 Settings 中实际创建并配置审批者/部署分支策略时才提供人工关卡；未配置通常会失败或失去预期治理，需在远端完成一次管理员核验。
- **tag 保护仍是信任根：**该方案降低“被触发代码拿到写 token”的风险，但不能阻止有 tag 创建权限的主体指向恶意 commit。需为发布 tag 配置保护规则并限制创建者。
- **测试缺口：**当前单测验证 manifest 格式，却未建模“清单位于被验证 commit 内”的 Git 语义。修正 S4 后应添加测试，断言源码 manifest 不再含 `source_commit`，并用临时 Git 仓库跑一次“提交→打新 tag→workflow 等价检查”。
- **远端演练：**本地脚本、YAML 解析、历史 v4.1.1 归档重建和专项单测已验证；尚未在 GitHub Actions 真实执行，因此不能宣称远端 Environment、token scope、Release API 已端到端通过。

## 5. 建议的合并顺序

1. **P1，先修 S4：**解除 manifest 与自身 commit SHA 的耦合，保留产物 build report 的 tag commit 校验。
2. **P1，补回归：**增加无 `source_commit` 的 schema/CLI 测试和临时 Git tag 演练；更新设计、复盘和说明，避免传播错误契约。
3. **P2，远端治理核验：**配置并实际检查 `release` Environment、tag protection、最小审批人；以受控测试 tag 或 dry-run 工作流留证。
4. **P2，PR 早反馈：**对 manifest JSON schema 和 blocker/readiness 做常规 CI 检查；tag 时仅做 tag/version 与产物来源的最终绑定。


以上通过只证明当前工作树与历史 `v4.1.1` 的静态/本地契约相容，不能证明未来 tag 的自引用契约可构造，也不替代 GitHub Actions 的真实运行验证。

## 7. 对本评估结论的反向复核（2026-10-27）

**结论：原结论总体准确、定级合理，且有一项需要更精确地表述。** 反向检查了 tag checkout 语义、历史 tag 内容和工作流校验顺序：`git show v4.1.1:release/release-manifest.json` 返回退出码 128，说明该清单不在 `v4.1.1` 被指向的源码树中；而 workflow 在 checkout tag 后立即读取该路径。因此若将当前 workflow 应用于历史 tag，也会在读取/校验清单时 fail-closed。该事实使“当前实现不能直接支持一次真实发布”比原结论更明确。

| 原结论 | 复核裁决 | 校准说明 |
| --- | --- | --- |
| S1–S3 专业、准确，应保留 | **成立** | 权限分层、凭据隔离、tag 输入拒绝和发布后回读的控制点与数据流一致，无相互抵消的实现。 |
| S4 是 P1 发布阻断 | **成立，且证据增强** | 未来 tag 的自引用无法通过常规可重复的 Git 提交流程构造；既有 v4.1.1 tag 又不含清单，证明现有历史发布也不能被该工作流直接重跑。 |
| “不可满足” | **应收敛措辞** | 工程结论应为“没有可审计、可重复、实际可用的构造流程”，而非宣称数学上绝对不存在任意哈希固定点。对 SHA-1 Git commit 而言，穷举这类固定点不构成可接受的发布机制，故不影响 P1 定级。 |
| 当前工作树可与 v4.1.1 静态契约相容 | **需明确局限** | 本地 `--tag v4.1.1` 通过仅因当前未提交工作树额外带有 manifest；它不等价于 GitHub 在 `v4.1.1` checkout 上会通过。 |

**最终专业判断：**“不应直接合并或用于下一次发布”是保守且准确的结论；建议的修正方向（从源码 manifest 移除 tag commit SHA，继续用构建后生成的 build report 绑定 tag commit）仍是最小、合理且不降低 S1–S3 安全收益的方案。

## 8. 实施后状态（2026-10-27）

**P1 已关闭。**经用户确认的 [S4 自引用修正设计](../design/发布工作流S4自引用修正设计-2026-10.html)已实施：manifest 现在严格只含 `version`、`readiness`、`release_blockers`；workflow 继续只以远端回读 build report 的 `source_commit == GITHUB_SHA` 证明 tag 来源。16 项发布专项测试、Ruff、版本一致性、YAML 解析和文档门禁均通过，并已在临时 Git 仓库创建新提交/新 tag 演练状态清单可被正常读取。远端 GitHub Environment、tag protection 和真实 Release API 流程仍为需管理员执行的外部核验项。
