P0-1 二次 DNS 解析可退化为未 pin 的请求

问题分析

运行时链路先调用 validate_trigger_url()，该函数对域名做一次 DNS 校验；随后 validate_and_resolve_url() 再解析一次，以得到用于连接的目标 IP。第二次解析在 app/services/url_security.py:160-165 只寻找“第一个公网 IP”，若 DNS 响应已全部变成环回、私网或保留地址，函数错误地返回 (True, '', None)。app/crons.py:409-412 将 resolved_ip is None 解释为“无需 pin”，回退到普通 requests。因此，名称校验成功与实际 TCP 连接之间仍有 TOCTOU 窗口。

攻击者只需控制一个任务可访问域名的权威 DNS：第一次查询回答公网地址，通过保存/执行校验；第二次查询回答 127.0.0.1、RFC1918 私网、链路本地或云元数据地址。调度器会按第二次答案发起真实连接。默认 url_ssrf_dns_fail_open=0 不会阻止该路径，因为这里不是 DNS 失败，而是“解析成功但结果全部不安全”。

问题影响

  • 机密性：可读取运行机器或内网服务返回内容；任务响应会进入执行日志，拥有日志读取权限的角色可能看到被带回的数据。
  • 完整性：可向内部仅信任本机/内网来源的 HTTP 服务发起 GET 或 POST；POST 会附带任务配置的请求体及 CronPilot 追踪参数。
  • 可用性：可利用慢速内网端点耗尽调度线程和连接资源，影响其他任务。
  • 攻击条件：攻击者需具备创建或编辑可执行任务的权限，或能控制已配置任务域名的 DNS。该条件低于“控制服务器”，因此属于高风险 SSRF。

复现证据

在无网络、无数据库条件下将两次 _resolve_host_ips() mock 为 ['93.184.216.34'] 和 ['127.0.0.1']，validate_and_resolve_url('http://example.com/', cfg) 返回 (True, '', None)。随后调用路径确定选择普通 requests。

解决方案对比评估

方案做法安全性兼容性/复杂度结论
A. 二次解析必须产生 pinned IP无论解析到公网还是内网，只要返回可连接地址就返回该地址；空结果或 DNS 异常拒绝，不再返回 True, None。消除“允许但无连接证据”的状态，同时不阻断合法内网。改动小，区域边界依赖部署的内外网 DNS 隔离。推荐立即实施。
B. 应用维护域名/CIDR 清单为内网域名和内网网段增加显式配置。应用侧边界更强，但会增加配置和运维负担。复杂度高，且不符合当前部署前提。不采用。
C. 保留无 pin 回退当二次解析结果异常时使用默认 requests。继续保留 TOCTOU/SSRF 风险。表面兼容性最高。不可接受。

策略校正（最终决议）：不要求用户配置内网域名或内网 CIDR。系统按部署的 DNS 分区识别目标：内网域名由内部 DNS 解析到内网地址，外网域名由公网 DNS 解析到公网地址。应用层只负责解析一次、固定解析结果并建立 pinned 连接；解析失败、空结果或环回/链路本地/保留地址拒绝。该方案依赖部署契约“内网域名不经过公网 DNS，公网 DNS 不返回私网地址”，不再重复维护一份应用侧网络清单。

内网访问的正确识别与放行

业务上应支持两种合法内网入口：① 内网域名，例如公司 DNS 将 service.corp.example 解析到 RFC1918 地址；② 直接填写内网 IP。不能要求内网目标必须返回公网 IP，也不能仅因地址属于私网就拒绝。建议采用以下确定性判定顺序：

  1. 直接 IP：内网 IP 和公网 IP 均允许；环回、链路本地、保留和组播地址拒绝。
  2. 域名：使用系统 DNS 解析全部 A/AAAA 结果，内网解析结果和公网解析结果均可访问，不做应用侧域名清单判断。
  3. 连接阶段：无论目标区域，都使用具体解析 IP 建立 pinned 连接，Host/SNI 保留原域名。

验收覆盖：内部域名→私网 IP、直接内网 IP、外部域名→公网 IP、环回/链路本地拒绝，以及 IPv4/IPv6 双栈。DNS 分区隔离作为部署前置条件。

验收标准

  • 二次解析从公网变为私网、全部私网、空结果、DNS 异常时均不得调用 requests。
  • 每一次允许运行时请求都具备非空 resolved_ip，并由 pinned adapter 发出。
  • 回归覆盖 IPv4、IPv6、混合 A/AAAA、loopback、RFC1918、link-local 与云元数据范围。

P0-2 跨协议重定向绕过 DNS pinning

问题分析

make_pinned_session() 在 app/services/url_security.py:206-209 仅为原始协议挂载 _PinnedIPAdapter。requests 默认自动跟随 301/302/303/307/308。若初始任务是 http://public.example，该 session 只保护 http://；服务端返回 Location: https://127.0.0.1/internal 后，requests 会选择默认 HTTPS adapter。此跳既不经过 validate_and_resolve_url()，也不复用初始 pinned IP。

该缺陷与 P0-1 独立：攻击者不需要 DNS 变化，只要控制一个允许访问的公网 HTTP 服务，就能用重定向把调度器导向私网、环回或云元数据地址。相同问题也存在于 HTTPS 跳转至 HTTP，及跨主机重定向。

问题影响

  • SSRF 防护完全失效：首跳通过校验后，后续跳转的目标没有 host allowlist、私网地址、DNS 或 pinning 检查。
  • 凭据与参数风险：GET 路径添加的 cronpilot_trace_id/cronpilot_sign 会参与 requests 的重定向行为；POST 在 301/302/303 情况下还可能被改写为 GET，导致任务语义与审计记录不一致。
  • 协议降级：跨协议跳转可能让原本 HTTPS 任务落到 HTTP，降低传输保护。

复现证据

模拟 http://example.com/ 首跳返回 302 Location: https://127.0.0.1/internal，记录 adapter 调用序列为 _PinnedIPAdapter → HTTPAdapter。第二跳使用 requests 默认 adapter，已离开保护链。

解决方案对比评估

方案做法安全性兼容性/复杂度结论
A. 禁止全部重定向请求传 allow_redirects=False，将 3xx 作为任务失败。最强、最易证明，但无法保留合法跳转。改动小，会影响依赖跳转的既有任务。可作为紧急止血，不是最终产品策略。
B. 逐跳解析并 pin关闭自动跳转，手动处理 Location；每跳重新解析并 pin，限制跳数。支持内网和外网正常跳转，避免解析后漂移。需要处理相对 URL、307/308 方法语义；跨区域安全性依赖 DNS 分区契约。推荐最终方案。
C. 禁止全部重定向将 3xx 作为任务失败。最容易证明安全，但会影响合法内网服务跳转。实现简单，兼容性较差。当前止血方案。

推荐方案：关闭 requests 自动跳转，逐跳重新解析并 pin；当前先将 3xx 作为失败，后续在确认 DNS 分区契约后实现同区域逐跳跳转。每一跳保留原始 Host/SNI 语义。

验收标准

  • HTTP→HTTPS、HTTPS→HTTP、跨主机、相对 Location、环回、链路本地和 IPv6 Location 都覆盖。
  • 当前所有 3xx 不产生后续网络调用。
  • 未来恢复跳转时，每跳都重新解析并 pin，不能只复用首跳结果。
  • 301/302/303/307/308 对 GET/POST 的方法、body、追踪参数和日志语义均有断言。

P1-1 SQLite 事件表切换失败会留下空业务表

位置：scripts/ensure_business_tables.py:269-300。流程先把旧表改名，创建新表并复制，再删除旧表，最后重建索引。SQLite DDL 不会按代码假设自动回滚；若索引创建失败，当前名称的 job_log_events 为空，而原数据留在 job_log_events__id_switch_old。下一次启动直接因临时表存在抛错，不能自动恢复。

复现：对 CREATE INDEX 注入异常后，查询得到新表空、临时表仍含原行。修复建议：将恢复逻辑做成可重入状态机：完成复制和验证后再切换名称；失败时恢复原表名；对临时表执行一致性校验与自动恢复，且用文件备份验证恢复路径。

P1-2 公网 IPv6 目标无法请求

位置：app/services/url_security.py:181-188。Pinned adapter 将 IPv6 直接拼入 netloc，如 2001:db8::1:443，未使用方括号，requests/urllib3 解析为非法 URL。

复现：以 IPv6 pinned IP 调用 adapter 得到 InvalidURL。修复建议：重写 netloc 时为 IPv6 使用 [addr]:port，增加 HTTP/HTTPS 与有/无端口用例。

P1-3 MySQL 自增主键与关联列类型不一致（已修复）

位置：datas/model/cron_infos.py:12-16、datas/model/job_log.py:25-27、datas/model/task_group.py:17、datas/model/job_log_event.py:21、scripts/ensure_business_tables.py:1210-1230。迁移将任务主键提升为 BIGINT AUTO_INCREMENT，但 job_log.cron_info_id、task_groups.task_id、task_tags.task_id、job_health.cron_info_id、job_log_events.cron_id 与 operation_log.target_id 仍为 MySQL INT。当前 SQLite 数据库最大任务 ID 已是 263,765,630,976，超过有符号 INT 范围；MySQL 上新的关联写入会溢出。

修复结果：ORM 已将所有任务 ID 引用列统一为 MySQL BIGINT（SQLite 仍使用兼容的 INTEGER）；启动迁移同步升级 job_log、job_health、job_log_events、task_groups、task_tags、operation_log 的关联列。迁移异常现在直接 fail-closed。专项测试验证所有引用列编译为 MySQL BIGINT，并覆盖数据库自增 ID 回归。

P1-4 MySQL 主键 DDL 失败仅记录 WARN 后继续启动

位置：scripts/ensure_business_tables.py:1225-1235。ALTER 异常被打印为 WARN，函数不抛出，启动脚本继续报告就绪。应用模型已省略应用层 ID，schema 未实际切换时会在首个写入才失败，错误被延后且难以诊断。

修复建议：关键 ID schema 不满足目标时 fail-closed，使启动失败；记录后端、表、列、实际类型和修复命令。为 MySQL DDL 失败增加断言测试。
