RBAC 注册审批 R2-3 集成与同类排查实施方案

版本：rev.2 · 日期：2026-10-26 · 状态：R2-3 已完成 · 父方案：Scope 精确化方案 rev.18 · 前序：R2-2 已完成 · 验收：R2-3 QA

实施结论：已完成只读入口审计、集成测试和路由门禁；未发现注册审批读取旁路或口径分裂，因此未触发 R2-3B 生产修复。新增一条 HTTP 级筛选/第二页/badge 联动防回归测试。

1. 问题与目标

R2-2 已将注册审批的 scoped 读取切换为申请—业务组关联表，并让列表与 pending badge 复用 Repository 的授权集合。但“主路径已修复”不等于“没有旁路”：状态筛选、用户名搜索、翻页、模板渲染、导航 badge，或其他注册审批读取入口，仍可能复制旧 CSV Scope 逻辑或绕开数据库当前 actor。

R2-3 的目标不是重写授权策略，而是建立一份可重复的集成证据：每个可见计数和页面行都来自同一 actor Scope 与同一授权查询，且仓库中不存在未纳入审查的注册审批读取旁路。

2. 已核对的实现事实与根因假设

  • app/rbac/views.py::registration_review 是审批列表的 GET 入口；它通过 current_registration_actor_scope() 获取数据库当前 actor，并调用 paginate_all() 或 paginate_by_groups()。
  • app/rbac/__init__.py::_get_pending_reg_count 是导航 badge 的入口；它使用同一 actor Scope，再调用 get_pending_count_all() 或 get_pending_count_by_groups()。
  • RegistrationRequestRepository._scoped_request_ids() 当前承载 scoped actor 的唯一 ID 集合；状态和用户名条件被下推至该集合，分页和 pending count 分别复用它。
准确性边界：以上是对当前调用图的只读核对，不构成“无遗漏”的结论。R2-3 必须用全仓扫描、负向集成测试和渲染断言把该假设证实或证伪。

3. 范围与非范围

纳入明确不纳入
审批列表 GET、状态/用户名筛选、分页 total/pages、页面 pending 数和侧边栏 badge；注册审批模型的所有读取调用方；与此字段相关的逗号 Scope 查询静态审查。审批通过/拒绝写入协议、批量反馈真值协议、关联表结构、性能阈值、用户编辑授权、任务/审计日志的既有 Scope 语义。发现它们的独立风险时只记录并另建设计，不在 R2-3 顺带修改。

4. 页面 Before / After

不改变页面布局：仍为“选择、用户名、申请角色、申请业务组、岗位、申请时间、操作”七列。变化是将可见性与所有数量指标的同源关系验证为可回归契约。

Before：未证明的集成状态

组 1 管理员在“全部”页看到 1 条，但切换“待审批”、搜索或翻页后，total、页码或侧边栏 badge 可能重新包含组 10 / 全局申请。

After：同源可验证状态

组 1 管理员在所有状态、用户名搜索和页码组合下，行、total、pages、页面 pending 数及侧边栏 badge 都只统计授权 ID 集合；任何筛选仅缩小集合，不能扩权。

5. 执行步骤

  1. 只读调用图审计：以 RbacRegistrationRequest、RegistrationRequestRepository、registration_review、group_ids 和旧 token/LIKE 模式为关键词全仓扫描；逐项记录“授权读取 / 写入校验 / 无关历史字段”。
  2. Repository 集成矩阵：在内存 SQLite fixture 生成组 1、组 10、组 1+10、全局和非法/零关联申请；对 viewer/operator 与 scoped admin 分别断言 items、total、pages 和 pending count。
  3. 路由渲染矩阵：使用数据库当前 actor 而非伪造 session role/group，遍历 status（全部、pending、approved、rejected、expired）、用户名命中/未命中和至少两页数据；断言 HTML 行、分页文本和页面 pending 数不越权。
  4. 导航同源矩阵：在相同请求上下文调用 context processor，断言 pending_reg_count 与 Repository pending count 及列表 pending 筛选相等；actor 不存在、停用、无权限或 Scope 读取异常必须保持 0/302/403/500 的既有外部契约，不得泄露异常文本。
  5. 同类排查结论：对每一个旧 CSV Scope 查询判断是否服务于注册审批可见性。属于本功能的旁路必须纳入修复；其他领域只登记证据、风险和独立需求。

6. 验收矩阵

场景关键断言

组 1 actor 与组 1、组 1+10 的普通角色申请精确交集可见；筛选仅缩小可见集合。

降权、收窄、停用、读取异常沿用 R2-1 外部契约：403、302 或通用 500；不使用 Session role/group 回退授权。

7. 风险、停止条件与缺陷处置

  • 发现任何注册审批读取旁路、列表与 badge 口径不等、筛选扩权、分页不一致或原始异常泄露时，停止标记完成；先输出定位、影响和最小修复设计，等待用户确认。
  • 扫描到其他领域的 CSV Scope 查询不自动修改，避免把注册审批修复扩大为跨模块重构。
  • 测试 fixture 必须使用内存 SQLite，不得导入 manage.app/db；浏览器验收数据必须与本地开发数据隔离或可追溯清理。
  • R2-3 不允许以“全量测试通过”替代针对性证明；缺少 HTML 行、total、pages、页面 count 和导航 badge 的联动断言即视为未验收。

8. 分批与完成定义

  1. R2-3A 审计与测试：只做扫描、补齐测试、运行验证；无缺陷则不改生产代码。
  2. R2-3B 最小修复（条件触发）：仅在 A 发现审批读取旁路或口径差异时，针对单一根因形成增补设计、等待确认后实施。
  3. R2-3C 集成验收：运行 Repository/路由/RBAC/CSRF/侧边栏、路由冒烟、Ruff 与文档门禁，形成 QA 记录。

完成定义：调用图不存在未解释的注册审批读取入口；验收矩阵全绿；所有筛选/分页/badge 同源；不存在需修复的同类旁路。达到后才能进入 R2-4 浏览器五角色最终矩阵和 F-02 关闭评审。

9. 实施结果（2026-10-26）

调用图与静态扫描确认列表入口仅为 registration_review、导航 badge 入口仅为 _get_pending_reg_count；注册申请可见性不存在旧 CSV LIKE 查询。新增 HTTP 防护测试覆盖 status、username、第二页、total 与两处 badge 的集合一致性。Scope 专项 65 项、注册与侧边栏 92 项、路由冒烟 86/86 和测试 Ruff 均通过。完整命令和审计边界见 R2-3 QA。
