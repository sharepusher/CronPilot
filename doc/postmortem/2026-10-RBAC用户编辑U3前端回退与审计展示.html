RBAC 用户编辑 U3 前端回退与审计展示修复复盘

日期：2026-10-29 · 状态：已修复并验证

1. Bug 定位

U3 实施前，公共 Ajax 对“成功但无跳转 URL”的响应会自动刷新页面，使 NO_CHANGE/ALREADY_APPLIED 无法稳定留页；U2 已写入的 JSON v1 审计 detail 未被访问审计页面消费。实施复核还发现，无 JavaScript 回退在管理员已确认清空但提交空理由后会隐藏理由输入区。

2. 根因

公共提交器把“无 URL”统一解释为刷新，没有结果真值的 opt-in 分支；访问审计只展示 resource 文案，未建立版本化 detail 解析边界；服务器回退的显示条件错误地只绑定 CONFIRM_REQUIRED，没有覆盖“确认存在但理由校验失败”的 FAILED。

3. 测试漏洞

此前测试集中在服务端事务和最终数据库值，没有运行真实按钮点击、输入型对话框取消/空理由、原生 POST 二次失败回显、显式 outcome 留页，以及损坏/未知审计结构的浏览器矩阵。

4. 修复

公共 Ajax 新增可取消 preflight 和显式 outcome 事件；用户编辑页实现五字段 no-op 比较和邮箱清空 CpModal。原生回退在所有邮箱清空确认失败场景持续显示理由区并保留输入。审计服务把 JSON v1 转为纯文本 ViewModel，模板自动转义展示，异常结构使用固定文案降级。

5. 防护测试

tests/test_user_edit_change_set.py 现有 24 项专项契约，包含实际 form 节点字段唯一性、原生回退、PRG、解析回退和 XSS 转义。真实浏览器进一步覆盖 no-op、清空取消/空理由/成功、并发冲突、正常审计及三类异常 detail。

6. 同类排查

公共 Ajax 的新行为只在响应显式携带 data.outcome 时生效，其他 Ajax 表单仍走原跳转/刷新规则；运行全仓库 Ajax 守卫和 111 项相关回归未发现漂移。审计解析只作用于 user:update，历史空 detail 保持原展示。

7. 预防方案

  • 在 tests/test_user_edit_change_set.py 固化“真实 user-edit form DOM 内确认字段各只有一个”的断言，禁止用整页字符串计数代替 DOM 范围。
  • 在 app/static/js/common-redesign.js 保持 outcome opt-in：只有服务端显式返回 outcome 才允许覆盖公共成功刷新语义；tests.test_ajax_form_guard 持续回归所有 Ajax 表单。
  • 审计 detail 新版本必须先扩展 format_user_update_audit_detail() 的版本分支和损坏数据测试，模板禁止直接 json.loads、innerHTML 或 |safe。
  • 输入型确认必须同时验证 JavaScript 正常路径和原生 POST 降级路径；理由为空、超长或重试时都要保持可继续操作。
