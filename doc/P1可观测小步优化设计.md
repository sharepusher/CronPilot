# P1 可观测小步优化设计

OPT-P1-01 follow-up：列表失败筛选 · 徽章/HTTP 展示统一

状态：Draft v1 · 待确认 · 2026-06-24

**定位：**在 [OPT-P1-01/02（已交付）](P1可观测优化设计.html) 之上做**小 diff UI + 查询**，不碰 `cron_do` 判定逻辑、不新增列、不改 API 协议。与 [P1-03/04](P1执行详情与立即执行设计.html) 可并行，但本方案更小、可先做。

## 一、要解决的问题

| 现象 | 根因 | 用户影响 |
| --- | --- | --- |
| 同一条记录：绿色「成功」徽章 + 红色/橙色 HTTP 行 | `_job_log_result_cell` 同时渲染 `job_log_badge(status)` 与 `job_log_status_line(http_status)`，两套独立着色规则 | 误以为「运行记录」与「执行记录」结论不一致 |
| HTTP 200 + body 含 `error` → 徽章「失败」但 HTTP 行绿色 200 | `error_keyword` 判 fail，HTTP 码仍为 2xx | 合理但易误解；需文案统一 |
| 执行记录页无法「只看失败」 | [P1-01/02](P1可观测优化设计.html) §十 明确本期不做筛选 | 排障时要翻页找失败行 |
| 旧数据 `status IS NULL` | 升级前 job\_log 无 status 列值 | 仅 HTTP 行推断，无徽章 |

## 三、PR-A · 徽章与 HTTP 行统一（推荐方案 U1）

### 3.1 原则

- **有 `status` 时**：以 status 为**唯一权威**；HTTP 码仅作补充信息，色调跟 status 走。
- **无 `status`（旧数据）**：沿用 A′ `job_log_status_line` 推断，不显示徽章。
- 第二行仍为 `content` 摘要（120 字），不变。

### 3.2 新函数 `job_log_summary_line(jl)`

放在 `app/services/job_log_display.py`，返回 `(badge_text, badge_tone, headline, headline_tone, extras)` 或结构化 dict，供 macro 与详情页共用。

| status | 徽章 | 第一行 headline（示例） | 色调 |
| --- | --- | --- | --- |
| `success` | 成功 | `HTTP 200` · 0.85s | 绿 |
| `fail` + http | 失败 | `HTTP 502` · 1.2s · `http_5xx` | 红（HTTP 行不再单独标绿） |
| `fail` + keyword + HTTP 200 | 失败 | `HTTP 200` · 0.3s · `keyword` | 红（明确「HTTP 成功但规则判失败」） |
| `error` | 异常 | 请求异常 · 120s · `timeout`（或无 HTTP 时「未执行回调」） | 橙 |
| NULL | （无） | 沿用现 `job_log_status_line` | A′ 规则 |

### 3.3 线框（统一后）

失败 **HTTP 200** · 0.31s · `keyword`

{"ok":false,"error":"something"}…

---

成功 **HTTP 200** · 0.85s

{"ok":true}…

### 3.4 触点文件

| 文件 | 变更 |
| --- | --- |
| `app/services/job_log_display.py` | 新增 `job_log_summary_line(jl)`；保留 `job_log_status_line` 供旧数据回退 |
| `app/templates/_job_log_result_cell.html` | 改为只调 summary；删除双轨 badge+line 分支 |
| `app/templates/job_log_detail.html` | 同上，标题行与列表一致 |
| `tests/test_job_log_display.py` | 覆盖：200+keyword fail、502 fail、timeout error、status NULL 回退 |

## 四、PR-B · 执行记录「结果筛选」

### 4.1 范围（仅 Web 列表，不做 API）

| 页面 | 路由 | 是否加筛选 |
| --- | --- | --- |
| 任务执行记录（全局） | `/job_log_all_list` | **是**（主场景） |
| 单任务运行记录（iframe） | `/job_log_list?id=` | **是**（同组件，query 透传） |

### 4.2 查询参数 `outcome`

| 值 | SQL 条件 | UI 文案 |
| --- | --- | --- |
| （空）全部 | 无额外 filter | 全部 |
| `success` | `JobLog.status == 'success'` | 仅成功 |
| `fail` | `JobLog.status == 'fail'` | 仅失败 |
| `error` | `JobLog.status == 'error'` | 仅异常 |
| `not_success` | `JobLog.status.in_(('fail','error'))` | 非成功（推荐默认「排障」快捷项） |
| `unknown` | `JobLog.status.is_(None)` | 未知（旧数据） |

与现有 `task_name`、时间范围筛选 **AND** 组合；分页参数 `page` 保持。

### 4.3 UI（高级查询区追加）

高级查询：任务名称 [\_\_\_\_] 开始 [\_\_\_\_] -- 结束 [\_\_\_\_]
结果 [(全部 ▼)] [仅非成功] …
[搜索] [重置]

实现：在 `job_log_all_list.html` 的 `well form-search` 增加 `<select name="outcome">`；重置链保留 query。

### 4.4 索引策略（本次仍不加索引）

与 P1-01 §六 一致：默认部署 job\_log 量级下 `WHERE status=?` + `ORDER BY id DESC` 可接受。若单库 >50 万行且筛选变慢，follow-up 评估 `(status, id)` 或 `(cron_info_id, status, id)`（须 EXPLAIN）。

### 4.5 触点文件

| 文件 | 变更 |
| --- | --- |
| `app/main/views.py` | `job_log_all_list`、`job_log_list` 解析 `outcome` 追加 filter |
| `app/templates/job_log_all_list.html` | select + 选中态 |
| `app/templates/job_log_list.html` | 可选：iframe 内简易 select（或仅全局页） |
| `app/templates/admin_page.html` | 分页链接保留 `outcome` query（若 paginate 宏支持 keywords 已透传则可能无需改） |
| `tests/test_job_log_display.py` 或新 `tests/test_job_log_list_filter.py` | mock session 验证 filter 组合 |
