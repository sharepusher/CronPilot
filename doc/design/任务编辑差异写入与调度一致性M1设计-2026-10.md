## 1. 五项问题：证据、根因与准确性

复现命令：`.venv-py311/bin/python scripts/verify_cron_edit_baseline.py`，结果为 5/5 缺陷场景复现，退出码 0。使用真实 ORM/服务/关系同步、内存 SQLite，调度调用及故障由 mock 注入。退出码 0 表示缺陷证据断言成立，绝不是修复验收通过。

| 问题 | 已经证明的事实 | 准确性与影响边界 | 根因 / 修复方向 |
| --- | --- | --- | --- |
| ① 无变化仍写入 | 相同字段、组和标签提交产生任务 UPDATE、组 DELETE/INSERT、标签 DELETE/INSERT、日志 INSERT，共 6 条 DML、两次提交，调度注册/暂停各一次。 | 高置信。6 条只适用于该单组单标签暂停任务样例，不能写成所有任务固定成本；同秒更新时间偶尔不变也不等于无副作用。增加写入与锁机会，不代表已经观测到数据库写失败。 | 服务没有有效差异集；元数据和关联重建无条件执行。前端预检加服务端权威 no-op，关系集合增量更新。 |
| ② 旧表单覆盖 | 另一个事务先写 concurrent-new，服务重新读取后，旧表单把字段恢复为 original。 | 高置信。顺序提交已证明 lost update；无需高并发。没有测量线上发生率；行锁本身不能识别用户看到的旧值。 | 表单携带完整旧值，服务缺展示基线/条件更新。三方比较与原子版本条件共同防护。 |
| ③ 调度注册失败后配置已保存 | 业务 commit 后注入注册异常，后续 rollback 无法撤销保存，日志为 0。 | 故障处理缺口高置信；实际 job 可能旧、缺失，或调用已应用但响应丢失，不能只凭抛异常判断。HTTP 错误形态尚未做端到端注入，不能声称已验证前端必为某种状态码。 | 跨资源操作没有持久化同步意图和恢复证据；业务事务不包含 JobStore。持久化期望、明确待同步与未知结果，由对账恢复。 |
| ④ 日志失败仍返回 | 第二次提交失败被 record\_operation 捕获；任务已修改，日志为 0，服务正常返回。Web 正常返回分支固定“修改成功”。 | 高置信，但应称“配置成功、审计不完整”，不是配置未保存却说成功。现有日志本来采用 best-effort；转为强审计是明确的可靠性策略变更。 | 日志自提交且吞异常；配置与审计没有原子性。增加不自提交的日志追加内核，当前入口迁移，保留旧包装器。 |
| ⑤ 暂停失败仍视为成功 | 注册后的暂停异常仅 warning；DB status=0，服务正常返回并有成功日志。 | 失败吞掉高置信。补充真实 APScheduler 内存实验：替换暂停 job 未传 next\_run\_time 会得到非空执行时间；显式 None 则暂停。没有向真实任务发 HTTP，不能声称已观测误执行。 | 先创建可运行 job 再暂停存在窗口；暂停异常不影响结果。以目标暂停状态直接创建 job，并将应用结果纳入响应和恢复。 |

优先级：③⑤属于运行安全优先项，②涉及配置完整性，④涉及审计可靠性，①主要是正确性与可避免的副作用。五项均应治理，但不能仅因一次故障注入就认定为线上事故或统一赋予相同严重等级。

## 2. 已核验的代码与 API 依据

- `app/main/views.py:cron_edit` / `_apply_scope_from_form`：Web 取参、Scope 赋值、固定成功响应；当前依赖 Session 的授权数据不能直接复制为新写边界。
- `app/services/cron_service.py:apply_normalized_to_model/update_cron/edit_cron_web/upsert_cron_by_task_name`：Web 与 API 共用写服务；apply 无条件覆盖字段、时间；commit → register → pause → record\_operation。
- `app/services/tag_service.py:sync_task_tags`：先删除全部任务标签；查找/创建标签使用嵌套事务。改造须保留标签并发去重，避免误删其他任务共享 Tag。
- `app/services/operation_log_service.py:snapshot_cron/record_operation`：快照缺 timeout\_sec 和 tags，group\_id 不是当前模型列；日志内部 commit/rollback。现有快照不能直接用作新完整基线。
- `app/__init__.py` 实际使用 CuBackgroundScheduler；`app/CuBackgroundScheduler.py` 覆写调度扫描并在一次性结束/异常时直接更新任务下线，属于必须协调的额外写入口。
- 本地安装的 Flask-APScheduler `scheduler.py:add_job` 转发参数；APScheduler `schedulers/base.py:add_job/_real_add_job` 在 next\_run\_time 未提供时计算下一时点，提供 None 时保持暂停；`pause_job` 本质是修改该值。
- `app/crons.py:cron_check` 当前对账检查 ID 存在性和 ghost；不证明 trigger 或暂停状态匹配。`cron_do` 以 cron\_id 从 DB 读取请求参数，因此仅 URL/body/timeout 的变化通常无需重建 job，但已开始的执行仍可能使用旧读取值。

真实库隔离实验输出：`initial_paused=True; replace_without_next_run_time_is_active=True; replace_explicit_none_is_paused=True`。使用独立 BackgroundScheduler、MemoryJobStore，调度器全局暂停，未运行任务，完成后关闭。生产 JobStore 和自定义扫描器还需 M1-0 补充实验；库实验不能代替它们。

## 3. 范围与设计决策

目标：无变化零业务写入和调度调用；旧页面不静默覆盖；配置与变更日志同成败；暂停任务注册时即为暂停；调度失败可知、可恢复。配置数据库是期望状态源，JobStore 是实际调度状态，两者不声称一个事务提交。

共享写服务必须提供 Web/API 适配；全部调度修改者纳入清单后才能发布完整调度收敛能力。包括新增、API upsert、编辑、启停、下线、手动重新调度、启动/周期对账、一次性任务结束和执行器异常下线。逐点定义迁移或禁止并行写入条件，不能仅改编辑后宣布全局一致。

任务名在页面是只读且描述为不可修改，新 Web 服务须验证不可变，不把 readonly 当安全校验。业务组迁移保持单组模型：GLOBAL 零关联，GROUP 恰好一条有效关联。无法表示的历史多组任务须提示治理，不选第一个后静默删除。密码、Token 和其他 RBAC 编辑不在本设计内。

## 4. 字段规范化、基线与差异集

| 字段组 | 规则 | 副作用 |
| --- | --- | --- |
| task\_keyword | 沿用 trim/长度校验，真正不同才更新。 | 配置日志；无需重注册 job。 |
| run\_date、day\_of\_week、day、hour、minute、second | 规范化只采用已验证校验器；模式决定有效字段。不得擅自把空值等价于 \*；本轮不新增 Cron 语法等价推导。一次性过期值即使 no-op 也须明确区分“原配置未改”与“请求重新安排”，不绕过有效变更校验。 | 有效调度改变才产生 scheduler\_generation。 |
| req\_url、req\_method、req\_body、timeout\_sec | 沿用 URL/SSRF、方法、JSON 对象及超时校验；body 保留现有文本语义，不未经确认自动改 JSON 排序/数值。NULL 超时与显式 5 不强行等价。 | DB 读取驱动；无需单纯因此重注册 job。日志保护 URL query 和 body 中秘密值。 |
| scope\_type、group\_id、tags | Scope 与组必须作为整体；标签按现有大小写去重规则比较，保留规范展示值；组切换需重新解析目标组标签，不能跨组复用 tag\_id。组集合与标签关系按实际增删，不删整表再重建。 | 范围变更重验授权；关系增量写；通常无需重注册。 |
| status / resume\_after\_save | 状态不是普通隐藏字段；恢复是明确命令意图。默认保持当前暂停，已下线拒绝；恢复可单独造成有效变化。 | 改变运行目标才发调度同步；no-op 不隐含修复调度漂移。 |

GET 读取后结束请求事务，不跨用户编辑时间持锁。前端使用显示基线预检，只有明显无变化时阻止 POST；不确定时提交服务端裁决。服务端以 O（原始展示）、C（当前 DB）、R（提交目标）判定意图 I 与有效差异 E。对用户有意修改的字段：C=O 才写入，C=R 视为已完成，其他为冲突。对未修改字段保持 C，不把旧表单全量覆盖回去。相互依赖的 Scope/组/标签、调度模式/时间字段按整体比较，避免不合法混合。提交前对最终候选整体重新校验。

快照 token 绑定 actor、task\_id、schema 和字段基线；不能包含 URL/body 的明文副本。建议对字段规范化值做带服务端密钥的 HMAC，再签名元数据，可比较 O 与 R/C 的摘要；普通 SHA256 会泄露低熵秘密的可猜测摘要。token 无效/旧结构要求重新加载。前端原值 JSON 必须安全序列化，禁止重复写入控制台、持久缓存或日志。密钥轮换导致旧表单失效属明确兼容行为。

写入采用原子条件版本检查，避免比较之后再次竞态；MySQL 可短事务锁当前行，SQLite 使用条件版本更新并验证影响行数，不假设 with\_for\_update 生效。关系修改、版本更新和日志必须在同一事务；版本条件不匹配则整体回滚重读并返回冲突。所有任务配置写者都须推进 edit\_version；上线前完整赋值点搜索。时间戳不是可靠版本号。

没有意图的 no\_change 和当前已等价的 already\_applied 均不写业务、不增加编辑版本、不追加成功变更日志、不触发调度。并发重读必要时允许短读事务，不把“零写入”误称整个请求绝无数据库事务。

## 5. 配置变更与日志同事务

新增“构建/追加操作日志但不提交”的内核，追加失败向调用方传播，由配置事务共同回滚。保留现有 record\_operation 自提交包装器供未迁移入口使用，不能直接删内部 commit。配置字段与关联真实差异构建同一份日志；补齐 timeout、组和标签，不用现有不完整 snapshot 兜底。

记录 actor、task、operation\_id、有效变化、配置版本和“配置已持久化”的结果；调度应用结果另记同步事件并关联。配置日志成功不再被解释为“调度全部成功”。这与 P0-C 草案把成功 operation log 绑定 READY 的定义不同：本文选择保存即审计，避免 PENDING 期间配置变化无证据；最终调度成功事件只在确认 READY 后记录。实施前须同步修订父草案并经 Review，避免两套成功定义。

审计强原子性的代价是日志库失败时配置保存也失败，这是有意选择。用户可见普通资料前后值；URL/body 只记录字段已变化与脱敏摘要，不复制完整凭据。日志权限消费点须按当前角色逐项核验，不能因名称叫“操作日志”就认定仅管理员可见。沿用既有 operation\_log 保留策略，本轮不暗中承诺永久留存；任务变更审计若要永久保留须单独冻结保留规则和存储容量。

## 6. 调度应用与恢复设计

### 6.1 最小暂停修复

目标暂停任务以 `scheduler.add_job(..., next_run_time=None, replace_existing=True)` 直接创建暂停 job，消除注册后再暂停的两调用窗口。该参数行为已由本地库源码与内存实验确认；非暂停路径不传 None。必须覆盖真实 JobStore、一次性、周期任务和启动状态。此法不撤销已入执行队列或已发出的 HTTP，也不能替代一致性恢复。

### 6.2 持久化期望与调度状态

采用 DB 持久化同步意图，而非内存缓存/仅请求内重试。配置保存事务同时记录最新期望 generation、目标启停与 PENDING；后台应用者读取已提交最新期望。无需为每次读取引入外部缓存，避免重启丢失恢复证据。仅元信息变化且 scheduler 状态无需变化时，不生成新的调度操作；既有 PENDING 仍按旧意图恢复，不能伪置 READY。

| 建议字段 / 结构 | 独立语义与约束 |
| --- | --- |
| cron\_infos.edit\_version | 所有配置/状态写者参与的单调版本；用于 CAS，和时间戳、调度版本不同。 |
| 任务同步记录：task\_id 唯一、desired\_generation、applied\_generation | 最新调度目标与最后已证明应用版本；applied 可空，不能以 0 代表证明。按 task\_id 存当前恢复状态，不重复保存敏感 URL/body。 |
| sync\_state、operation\_id、error\_code、retry\_count、next\_retry\_at、updated\_at | UNKNOWN / PENDING / READY / SYNC\_FAILED；安全故障码而非原始异常；指数退避有上限，到达重试门槛后保留失败等待人工，不能删除证据。 |
| scheduler 配置指纹 | 只针对 trigger、时区、目标状态、任务入口和参数；不得把 next\_run\_time 当完整指纹。周期自然推进不构成漂移。 |

以上是待机制验证的逻辑结构：加列/独立表二选一由 M1-0 最终迁移演练冻结，本稿推荐独立同步记录以隔离高频重试写与配置版本，但不因此把已有 status/Scope 字段移走。当前不删除/合并字段；若后续调整须逐字段证明语义等价。已有任务从 UNKNOWN 起，禁止批量标 READY。SQLite/MySQL 的默认、索引、回填、重复执行和旧进程兼容必须实测。

### 6.3 应用所有权与并发

generation 条件写回只能防止旧操作伪报 READY，不能阻止旧操作实际覆盖 JobStore。因此不能仅写“加版本号和 Redis TTL 锁即可”。本设计推荐首期由唯一的调度所有者顺序处理应用队列，Web/API 只提交期望，既有直接 scheduler 写者逐项迁移。所有者选择、部署启动校验和接管必须可执行验证；旧实例确认停止后才接管，不以租约超时即证明旧实例已停止。

若当前多进程/多主机拓扑无法强制唯一所有者，则 M1-3 暂不具备上线条件，须先在 P0-C C-0 冻结跨进程 fencing 与 JobStore 访问约束；禁止以进程内 mutex 或现有两分钟无续租执行锁冒充分布式写保护。无需在 M1-1/2 一开始就为尚未确认的规模引入新锁基础设施。

应用者以最新 generation 构建 job，暂停直接 None；应用后读取 job 的 trigger/入口/参数/目标状态核对，再条件写回 applied\_generation 和 READY。对账发现新 generation 时继续处理最新期望，旧回调不能覆盖新状态。进程崩溃后从持久化 PENDING/FAILED 恢复。实际 job 已存在但 trigger 陈旧也要恢复，不只处理缺失 job。

APScheduler 单独持久化并非跨库原子事务。尚未收敛的窗口内旧 trigger 可能仍触发；若产品要求“保存后绝不按旧计划触发”，需要执行侧 generation 检查并协调提交栅栏，作为 P0-C 的额外强保证，当前方案不冒称已经提供。执行开始后或 HTTP 已发出不能撤销。

### 6.4 失败阶段与准确响应

| 故障 | 事实与处理 |
| --- | --- |
| 业务/日志 flush 失败 | 共同回滚；不触发 scheduler，返回失败。 |
| 业务 commit 结果未知 | 返回 commit\_unknown；禁止自动重提整份修改。用 operation\_id 重读配置日志/版本核实；若 PENDING 已落库，后台仅按已提交状态恢复。 |
| 配置已提交，应用未完成或失败 | 返回 saved\_pending / saved\_sync\_failed，显示“配置已保存，调度尚未确认生效”；保留持久化恢复记录，不再称配置回滚。 |
| 应用成功，READY 写回失败/未知 | 保持待核实，不假定失败标记一定落库；重连后对实际 job 与期望核对，避免盲目重建一次性任务。 |
| 旧 generation 回写 | 影响 0 行即过期，不覆写当前状态；后台读取最新目标。 |
| READY 后漂移 | 定期低频校验实际结构；只对不一致目标修复。一次性已执行结束、已下线状态必须协调，不能把完成任务重新激活。 |

不承诺跨 DB/JobStore 恰好一次执行；重试是“应用最新目标”的幂等操作，不是重放业务编辑。外部应用失败不能通过写回旧配置来假装恢复成功，因为这可能覆盖别人后续提交。

## 9. 验收矩阵

- 无变化：原值、标签重排/重复、空值、GET/POST Body 与超时差异规范化；SQL 监听断言零业务 DML，零日志、零 job 调用，元数据不变。
- 真实变化：单字段、组迁移、标签增删、仅请求参数变化、Cron 变化；不变关系不写，不必要的 job 不重建；任务名篡改写前拒绝。
- 并发：旧页面/新 DB、两请求比较后交错、Web/API、编辑/启停、编辑/下线、一次性完成；冲突不覆盖，未改字段保留当前值。
- 事务：业务 flush、日志 flush、提交确定失败/未知；未知结果按 operation\_id 查询；业务和日志原子，scheduler 不消费未提交意图。
- 调度：真实库 + 同类持久 JobStore，暂停注册立即 None，注册异常、响应丢失、应用后 READY 失败、应用者崩溃/接管、旧 generation、同名旧 trigger、一次性过期/完成、重试上限。
- 安全：当前 actor 降权、Scope 变化、组被删除、CSRF、伪快照、未知 schema、只读字段；日志/JSON/快照不得泄露 body、签名或 Token。
- 迁移：SQLite/MySQL 空库/存量/重复迁移、UNKNOWN 不伪 READY、新旧进程混跑拦截；所有版本赋值点审计。
- UI：Operator 完整提交/留页/故障恢复/截图，Viewer 与 Admin 能力反向验证；回车、无 JS、双击；只测 JSON 不算页面验收。

保留基线复现工具为历史取证；未来修复后以新增正向契约测试验收，不为让旧缺陷断言保持全绿而回退实现。拟新增 tests/test\_cron\_edit\_change\_set.py、test\_cron\_edit\_concurrency.py、test\_scheduler\_sync.py 和真实 JobStore 工具，当前尚未创建或声称通过。

## 10. 性能、合理性与专业性评估

**准确性：**五项核心结论有真实服务与 SQL 证据；调度暂停参数补有真实库实验。生产调度异常概率、多进程接管、HTTP 实际故障返回未实测，明确保留门禁。不能用现有 2 条暂停测试替代整个方案证明。

**合理性：**差异比较在单任务小集合内存完成，不需全表计算或全局缓存。正常请求按 task\_id/唯一键读写；关系计算 O(g+t)，GROUP 任务 g=1。调度不变时避免不必要 job 重建；真实变化新增审计和版本条件是必要成本。失败恢复需要持久状态，因为内存缓存无法承担断电恢复。

**性能：**当前未采集任务总量、编辑速率和故障率，不沿用未经核验的固定行数。实施前只读采集 count 与索引；待处理查询按 sync\_state/next\_retry\_at/task\_id 联合索引有界批取，禁止每轮扫描所有配置。同步状态不能引发全列表 N+1；只批量关联当前页。真实修改的总 commit 不保证减少，因为调度回写是另一资源证明步骤；no-op 消除的是基线中的整套副作用。不得给未经压测的收益比例。

**专业性：**方案区分编辑意图、并发、数据库事务、跨资源恢复和 UI 真值；采用标准 CAS、同事务审计、持久化恢复与状态读回。generation 不冒充外部 fencing，暂停状态不冒充已撤销执行。推荐分批合理，但 M1-3 复杂度显著高于普通表单优化，必须以部署可强制和全部写者覆盖作为上线条件。

**备选方案：**仅前端比较无法阻止绕过与并发；只加行锁不能识别旧表单；scheduler 失败后回滚旧配置会覆盖后续修改且无法撤销已发请求；每次重建 job 会扰动暂停/下次时间；仅内存队列丢失崩溃证据。短期可先交付 M1-1/2 关闭①②④及⑤窗口，但③完整恢复要到 M1-3/4，阶段报告必须如实保留。

## 11. 风险与实施前确认事项

- 新增后台所有权是部署行为变化，须核实当前启动方式、主机数及共享 JobStore，不得直接假定单机。
- 旧调用方共享 update\_cron，需适配返回结构，不扩大为所有动作一起重写；未迁移包装器保留行为。
- 父 P0-C 日志成功语义与本文选择不同，须同轮校准；本稿不声称自动覆盖父草案。
- 现行“scheduler 失败回滚 DB”规范应精确解释为必要时独立补偿事务；已 commit 不可普通 rollback。任务编辑采用保留期望并恢复调度，实施前同步修正规范以免执行冲突。
- 本文不做物理字段删除；不在设计阶段写生产迁移/功能代码，不更改真实任务。新增 API/outcome、同步所有权及审计强原子性须经用户确认。
