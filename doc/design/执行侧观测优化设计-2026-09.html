任务执行链路可观测性：执行侧观测优化设计

本方案只优化已经进入 cron_do 的执行实例观测，不改变任务调度、业务结果判定和权限模型。目标是让一条运行记录可以被准确关联、完整解释，并在观测降级时主动告知使用者。

设计决策摘要：以 JobLog.id 作为执行实例的稳定 run_id；trace_id 继续承担跨组件检索。所有新事件写入 run_id，旧数据通过 trace 回填兼容。事件 detail 继续白名单化，但补齐 URL（脱敏）、超时阈值、计划时间和阶段耗时。Tracer 预算耗尽或写入失败时，把“观测不完整”写入父记录并在 Run Inspector 顶部展示。

非目标：不改 APScheduler 注册/对账；不新增工作流编排；不把锁竞争或 APS max_instances 抑制伪造为执行记录；不改变 pending/running/success/fail/timeout/error 既有业务结果语义。

3. 目标架构与数据契约

3.1 运行时写入时序

  1. 执行开始前创建 JobLog，其自增 ID 即本次 run_id；生成 trace_id 并写入父记录。
  2. Tracer 初始化时绑定 run_id、trace_id、cron_id，每次 emit 写一条事件。
  3. 事件写入使用已验证的独立连接事务（当前实现为 with db.engine.begin() as conn），不参与业务 session 回滚。
  4. 业务结束时 finalize 父记录；若 Tracer 被熔断，尽力把父记录标记为 observability_state=degraded，并保存原因。
  5. 查询时以 run_id 为主、trace_id 为兼容回退；Presenter 合并阶段事件与业务日志记录，按事件时间排序。

3.2 字段设计

对象新增/调整字段语义
JobLogobservability_state：healthy/degraded/unknown
observability_drop_reason：event_budget/database_error/write_budget		本次运行的观测完整性摘要，不改变业务 status
JobLogEventrun_id（新运行必填，历史可空）
schema_version（默认 1）		稳定指向父运行；支持未来事件契约演进
JobLogEvent.detail保持 JSON 字符串，但扩大白名单仅存脱敏、可展示的结构化上下文，禁止原始异常和凭据

迁移语义：trace_id 仍有独立语义（跨服务检索），不能删除；run_id 表达父执行实例，二者不等价。历史事件先按 trace 找唯一 JobLog 回填；无法唯一匹配的保留 run_id=NULL 并在查询中标记 legacy，不得强行猜测。

Detail 白名单由 Tracer 定义，Presenter 的 summary keys 必须是其子集；新增事件或字段必须同时更新契约测试，禁止模板直接读取 detail。

5. 观测降级与异常隔离

场景系统行为用户可见结果
事件数达到上限停止继续写事件；父记录尽力写 degraded/event_budget；指标计数顶部显示“观测不完整：事件数量达到上限”，业务 status 不变
事件写入数据库异常不影响业务 session；停止本次 Tracer；父记录尽力写 degraded/database_error显示“阶段事件写入失败，以下时间线可能不完整”
单条 detail 不符合白名单丢弃未授权键，保留事件和允许字段正常显示摘要，不显示原始异常
父记录 finalize 失败记录服务端错误和指标；不伪造 success运行状态保持未知/异常，提示联系运维

交互规则

  1. 列表页结果徽章继续表示业务执行状态；增加小型“观测不完整”标识，不替换业务状态。
  2. Run Inspector 顶部先显示运行状态与观测状态，再显示时间线；时间线摘要永远来自 Presenter DTO。
  3. 时间线与业务日志记录按 occurred_at/created_at 合并排序；同一时间使用事件 seq 稳定排序。
  4. Viewer 隐藏 query value、响应正文和业务日志记录；Operator 看到脱敏 URL 与截断正文；Admin 仍不能看到原始 detail JSON。

7. 实施分批与范围控制

批次内容完成标志
B1 数据与迁移JobLog 观测状态；JobLogEvent.run_id/schema_version；历史回填脚本与双后端 SQL。新旧数据可查询，无法唯一回填的 legacy 可识别。
B2 采集契约扩展 Tracer 白名单；在 cron_do 已验证阶段补上下文和 duration；降级标记。成功、SSRF、超时、异常、写入失败均有契约测试。
B3 查询与 PresenterRepository 按 run_id 优先；合并事件/业务日志；DTO 增加 observability 字段。模板无 ORM/raw detail；角色矩阵通过。
B4 页面交互列表观测徽章；Run Inspector 顶部降级提示、丰富时间线和统一排序。Before/After 关键路径浏览器验证。
B5 验收与运营重启、四角色、双后端、事件预算/容量压测、指标与清理策略。验收命令和结果落库，才可标记完成。

8. 验收标准

  • 每条新事件均可通过 run_id 查到唯一父 JobLog；trace_id 仍可用于跨组件搜索。
  • HTTP 事件展示脱敏目标、timeout_sec、状态码和阶段耗时；任何角色不见原始异常 detail。
  • 事件预算耗尽、数据库写入异常时，业务结果不被改变，Run Inspector 明确显示观测不完整。
  • 业务日志记录计数使用“条”，并与阶段时间线可按时间关联。
  • pending/running 的最终结果未知语义保持；锁竞争和 APS max_instances 不创建虚假执行记录。
  • 测试覆盖父记录与事件不一致、legacy 回退、四角色、HTTP 超时/异常、中断和 Tracer 故障隔离；浏览器完成列表→详情→检查器路径。

9. 风险与回滚

风险控制/回滚
迁移回填误关联历史事件只回填 trace 唯一匹配；不唯一保持 legacy；迁移可重复执行并有计数校验。
事件字段增加导致写入开销保持事件上限和预算；新增字段只写短值；压测超过阈值自动降级。
观测状态被误读成业务失败独立徽章与独立字段；文案固定“观测不完整”，不改变 status。
敏感数据进入 detail写入白名单 + Presenter 子集测试 + 脱敏 URL 测试；发现违规可关闭新增字段而不影响旧事件。
确认点：本方案只优化执行侧观测。请确认四项核心决策：run_id=JobLog.id 强关联、观测状态与业务 status 分离、事件与业务日志统一时间线、Tracer 降级必须在页面显式可见。确认后再进入实现设计和开发。

依据的现有 API 行为已在写入方案前核对：ExecutionTracer.emit 使用独立 db.engine.begin() 写入；Repository 已按 trace_id 查询事件/业务日志；Run Inspector 通过 Presenter DTO 渲染。
