统一人工操作错误处理设计（历史草案，已拆分）

版本：2026-09 · 状态：不再作为实施依据 · 本文保留用于决策溯源。

权威替代：P0-A2 JSON 错误信封、P0-S 异常脱敏与输出 Sink、P0-B 错误交互与表单回显、P0-C 任务调度最终一致性 以及 P0-A-lite Request ID。原文包含已被后续契约替代的错误对象与 trace 表述，禁止据此实现。

1. 问题与目标

当前不同页面对异常的处理不一致：部分只写日志不提示，部分只返回通用失败，部分把底层异常吞掉。操作人无法判断失败原因，也无法向开发人员提供可关联的排查线索。

目标是建立统一闭环：异常必记录、失败必提示、原因可理解、详情可关联、敏感信息不泄露。

2. 根因分析

  • 业务层、路由层和模板层各自处理异常，没有统一错误契约。
  • Ajax 与普通 POST 的返回形态不同，前端没有统一错误渲染器。
  • 日志缺少稳定的 trace_id、操作上下文和错误阶段。
  • 直接返回 str(e) 会泄露 SQL、路径、凭据或内部拓扑。

3. 设计方案

3.1 后端错误契约

{"ok": false, "code": "TASK_UPDATE_FAILED", "message": "任务状态更新失败", "detail": "数据库写入失败：字段类型不匹配", "trace_id": "..."}

message 是操作人可读文案；detail 是脱敏后的排查详情；完整 traceback 只进入服务端日志。

3.2 日志契约

所有人工操作异常使用统一 logger，至少记录 trace_id、用户 ID/角色、动作、目标资源、请求路径、错误阶段、异常类型、脱敏参数摘要和完整 traceback。写入失败时必须回滚并记录原始异常。

3.3 前端呈现

Ajax 失败统一调用错误弹窗；普通表单失败返回原页面并弹窗，保留已填写字段。弹窗显示失败标题、原因、trace_id，并提供复制详情；权限、校验、网络、数据库和未知异常使用不同提示。

3.4 脱敏边界

前端不得显示密码、Token、签名、Cookie、连接串和完整请求体。日志允许保留完整堆栈，但凭据字段必须在写日志前脱敏。

4. Before/After 页面行为对比

场景BEFOREAFTER
Ajax 写入失败按钮无反馈或仅返回空 JSON统一失败弹窗：原因 + trace_id + 复制详情
普通表单失败刷新后丢失输入，原因不明确返回原页面，保留输入并弹窗提示
数据库异常可能吞异常或仅记录 WARN事务回滚、错误日志、明确失败响应
未知异常用户只看到“失败”或 500显示安全详情，服务端保留完整 traceback

5. 实施范围

覆盖任务新增/编辑/启停/退役/手工执行、日志操作、标签、分组、用户、权限、Token、审计和配置等所有人工写入路径。只读页面的加载错误也复用同一错误码和 trace_id 机制。

6. 分批计划

  1. B1 契约层：新增错误码、响应序列化器、trace_id 注入和脱敏工具。
  2. B2 前端层：统一 Ajax/普通表单错误弹窗，覆盖网络异常、JSON 解析失败和超时。
  3. B3 业务层：按模块迁移任务、RBAC、标签/分组和 Token 操作，删除静默吞异常。
  4. B4 验收层：建立成功、校验、权限、数据库、网络和未知异常矩阵，完成浏览器关键路径验证。

7. 验收标准

  • 每个人工写入失败都同时产生错误日志和前端提示。
  • 每个错误响应包含稳定 code 与 trace_id。
  • 日志包含完整 traceback；前端详情经过脱敏。
  • 数据库失败必回滚，禁止继续执行后续业务。
  • Ajax、普通表单、超时、权限拒绝和未知异常均有自动化测试。
  • 浏览器验证覆盖至少一个任务操作、一个 RBAC 操作和一个标签/分组操作。

8. 风险与取舍

  • 统一错误契约会改变部分 API 错误响应，需要检查调用方兼容性。
  • 过度暴露 detail 会产生信息泄露，因此采用“前端脱敏详情、日志完整堆栈”的非对称策略。
  • 弹窗不能替代日志；没有 trace_id 的错误不得标记为已完成。

9. 设计决策

采用“统一错误契约 + 统一日志 + 统一弹窗 + 分批迁移”方案。禁止各页面自行拼装异常文案，禁止 catch-all 后静默返回成功，禁止将原始异常文本未经脱敏直接返回浏览器。
