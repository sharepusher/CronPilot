**建议结论：**局部 SQLite 即时写事务可填补当前授权读取到业务提交的窗口；但任务编辑包含 DNS、版本重试、关系写入、提交后调度及独立日志，不能直接复制用户编辑函数。推荐“受保护读取与规划 → 必要时释放后校验URL → 重新保护并重算 → 短事务写入 → 提交后调度”。SQLite 写者保护期间禁止DNS与scheduler调用；当前URL的本次校验结果不能被拿去写另一URL。

## 1. 问题、根因与证据强度

save\_task\_edit已具备当前授权重读、签名原值、六个业务单元三方比较及ORM版本CAS。但在SQLite上，with\_for\_update不提供预期行锁；当前驱动SELECT不一定建立持续物理读事务。actor读取后另一连接提交降权，旧请求仍可写入任务；任务行CAS只检查任务版本，授权变更未必推进任务版本，因此不能替代授权保护。

直接证据沿用本日已落库[task\_probes](../qa/evidence/sqlite-user-boundary-2026-11-02/sqlite/results.json)：DELETE与WAL均出现竞争降权committed、actor\_role=viewer、旧请求outcome=updated、值requested。该探针在独立进程替代URL校验以避DNS；权限/比较/写入是真实服务。**它证明服务层授权窗口；本轮未重跑，也不等同当前已验证HTTP攻击链。**实现前S0须按冻结源码重新复现，并补实际撤权入口。

测试漏洞：test\_current\_actor\_downgrade\_rejects\_stale\_form是保存前先撤权的串行用例；test\_mapper\_cas\_detects\_write\_after\_read证明任务行版本，不保护actor；同线程事件处理函数等待竞争者提交在修复后可能形成测试自锁。故新增独立进程调度、反向变异校准和同上下文释放观察。

## 3. 范围、字段意图与兼容性

计划修改生产文件仅cron\_edit\_concurrency.py和cron\_validator.py；复用sqlite\_write\_boundary.py而不修改其用户服务行为。允许在前者提取内部只读规划函数和SQLite协调函数，避免两套授权/比较规则；若确需另拆文件，应在同批列明纯搬迁和调用点。新增任务专项内存测试、独立文件集成工具、QA/复盘及规范要求的命令登记。**无前端可见变更**：模板、CSS/JS、布局、文案、字段及结果类型沿用当前契约，免页面Before/After；真实页面仍要端到端验收。

API任务编辑、启停、下线、任务创建、批量任务、调度器回补路径均不纳入新保存协议；实施时静态盘点相关写入口并记录剩余项，不代表它们已有等价保护。无全站engine事件、默认隔离级别、busy\_timeout配置、journal模式、依赖或数据库结构变更；不修改全量6项既有失败。

## 4. 备选及推荐取舍

- **仅任务版本CAS：**不足；actor撤权和组关联变化不必推进该版本。
- **仅条件UPDATE加actor谓词：**单条业务行可校验，但scope/标签关系、缺失关系、整单比较及异常清理需重新设计多条协议，本次改动面更大。
- **所有请求全局BEGIN或全站改事务模式：**影响GET、日志与其他服务，不选。
- **全程BEGIN IMMEDIATE并保持现有完整校验：**正确性方向可行，但DNS可能长时间占数据库写者资格，不选。
- **推荐局部物理保护+锁外URL校验+重新保护重算：**复用已有helper与CAS；显式增加至多两次URL校验和至多三轮保护。额外实现复杂度由规划函数复用、状态计数和变异测试约束。MySQL原有锁/校验顺序保留，本批不顺带治理其DNS锁持有成本。

## 5. 推荐算法与证明义务

### 5.1 事务所有权与最初清理

服务仅接受独立请求、无待写ORM工作的Session；入口守卫先于任何rollback，不得丢弃调用方写入。已flush或原生SQL待写不一定出现在dirty集合，仍由禁止组合调用契约约束，不能声称已自动识别。签名校验及入口只读事务rollback统一纳入主异常边界；记录清理异常并invalidate，清理不成功即停止。禁止仅依赖teardown。

每次SQLite保护前Session必须已成功结束上轮事务；复用begin\_sqlite\_write\_boundary，完整模型集为RbacUser、UserGroup、CronInfos、TaskGroup、TaskTag、Tag、ResourceGroup。配置与请求取本次不可变副本；同bind必须是同一物理业务库。多bind/其他后端不做静默降级。已有helper执行BEGIN前发现物理事务已开始时拒绝，不能嵌套BEGIN或用SAVEPOINT代替全库写者保护。

### 5.2 三轮上限、锁内重算与URL校验凭据

1. **进入保护：**每轮重新取得同Session物理保护，恢复原busy\_timeout后才读业务。保持未编辑字段保留C、scope整体比较及当前actor授权；使用新读取值重建计划。所有轮次沿用最初O和R，禁止自动接受新基线。
2. **先处理终态：**无效主体、无权限、下线、冲突、非法输入直接清理返回；no\_change/already\_applied在保护内确定后释放，无DNS、无DML、无成功日志、无scheduler。
3. **需写且没有可用URL校验结果：**只复制候选标量，不修改任何ORM属性、不flush；成功rollback释放保护，再执行原有validate\_trigger\_url校验精确candidate.req\_url与本请求固定策略。失败返回既有failed/req\_url，不写DB。校验期间当前Session不得重新读业务或开启事务。
4. **校验结果只在本次请求内有效：**以完整归一化URL（包括路径/query）和固定策略为匹配条件；既不持久化也不跨请求缓存，不记录URL明文。策略输入冻结为当前config副本，涵盖实际消费url\_allow\_hosts、block\_private\_ip、url\_ssrf\_observe\_only；不凭配置名称推断其他键已被消费。再次保护后，重新查actor/目标/关系、授权、三方比较；只有最终候选精确匹配时才允许复用校验成功。角色/组/状态变化仍须拒绝，校验成功不是授权凭据。
5. **最终本地校验：**提取计划新增的纯函数validate\_cron\_form\_local（当前尚不存在），从现有validate\_cron\_form原样拆出normalize与get\_now\_time比较；完整validate\_cron\_form仍调用它再校验URL，原签名、返回结构和默认行为不变。SQLite写前调用local，重验候选与当前时间；不得在锁内调用完整校验。API及MySQL原有完整校验继续使用同一纯逻辑。
6. **写入：**只有最终匹配并通过全部本地校验的轮次才能设置ORM属性、stamp操作者、推进edit\_revision、flush CAS、scope关系DML与标签SAVEPOINT，再commit。每次请求最多一次确定成功的业务commit；不得在URL校验轮次写入关系或成功日志。

预算定义：SQLite全请求最多**3次保护进入尝试、2次锁外URL校验、1次StaleData重新规划**，共享预算而非相乘循环。BEGIN忙立即failed，不自动重试；保护成功后因URL变动需要重验可以消耗下一轮，预算耗尽返回既有conflict消息、零本次写入。一次无关字段并发（含另一人改URL、本请求只改说明）应在预算内重新校验新URL并合并；持续改变可拒绝，不声称无界追赶。StaleData仅commit调用前、成功清理且仍有总轮次预算时允许一次，必须重读重算；MySQL保持原两次StaleData尝试，不增加SQLite循环。任何commit开始后的异常均不重试。

```
伪流程（语义设计，非可直接粘贴实现）
clean-owner guard → 主错误边界：校验原token；结束入口只读事务
SQLite：至多3轮
  BEGIN IMMEDIATE → 当前actor/task/全部关系 → 授权与三方规划
  终态？→ 清理并返回
  最终URL未按固定策略校验？
    复制候选 → rollback确认释放 → URL校验（上限2次）→ 成功后下一轮
  纯校验/时间重验 → 赋值 → 版本flush → 关系DML → commit
MySQL：原行锁/完整校验/两次StaleData语义；不发送SQLite SQL
确定commit成功 → 按有效差异apply_edit → 沿用独立record_operation → updated
```

**安全证明：**允许写入的最后一轮，从当前授权读到业务提交持续持有同库写者资格；另一写者不能在中间提交撤权/关系变化。释放锁作DNS的轮次没有业务修改；重新进入后旧授权与旧candidate均作废。CAS仍作为防御层；URL校验绑定最终写入的URL且执行前独立DNS防护保持不变。保存前DNS检查并不保证未来解析不变。

## 6. 并发胜负与异常结果

- **撤权/停用/换组先提交：**最终受保护读看见新事实，拒绝，业务版本/关系/成功日志不变。
- **最后一轮保存先取得保护：**竞争撤权等待或明确忙；保存可合法完成，释放后撤权再执行。不能用“撤权请求已发起”断言保存必须失败。
- **DNS释放期间发生变更：**竞争写可以成功；保存重入必须重新授权与比较，不能因为此前拿过锁而沿用旧事实。
- **同单元先改：**conflict整单拒绝；不同单元先改：保留C并合并；目标已等价：already\_applied；未表达恢复不得覆盖暂停/运行状态。

| 故障阶段 | 返回与持久化 | 清理/重试 |
| --- | --- | --- |
| 签名/入口rollback/BEGIN/恢复timeout/URL失败/纯校验 | failed，固定安全错误；无本次业务DML与调度；签名缺失保持reload\_required | 主try覆盖所有清理；恢复失败淘汰连接；不以任意OperationalError当“已阻止竞争” |
| flush、标签SAVEPOINT、关系DML失败 | commit前failed；StaleData可按共享预算重算，耗尽conflict | rollback\_or\_invalidate；清理失败禁止继续；独立连接确认无残留 |
| 设置attempting\_commit之后commit抛异常 | commit\_unknown；分别核验异常发生前后真实DB事实；不能宣称未提交 | 清理但绝不自动重试、注册job或写成功日志；StaleData若发生在该阶段同样保守处理 |
| 确定commit成功后调度失败/版本变更 | saved\_scheduler\_error既有结果；已提交业务不倒回 | 沿用apply\_edit有限检查；不引入伪补偿/分布式事务；仅schedule/status有效变化调用 |
| 独立OperationLog写失败 | 保留当前updated语义，业务不回滚 | 日志记录错误，失败独立事务须结束；本批不承诺可靠投递 |

## 7. 日志、调度和规范边界的显式决策

**重要差异：**RBAC用户编辑成功审计在业务事务；任务OperationLog当前是提交后独立事务，且调度失败提前返回时不会写该成功日志。本设计明确请求本专项保留这一既有边界，作为EDIT-07“业务/成功审计同事务”的局部现状豁免，不将其宣传成已合规。若验收目标必须包括强审计，则须改选同事务日志或outbox并更新设计后再确认；不得在实施中悄悄扩大。

暂不选同事务日志：record\_operation内含独立commit并吞异常，直接移到锁内会破坏事务所有权；拆成可靠事务日志影响更多调用方。暂不选outbox：涉及表、投递、重放和运维，不是关闭当前授权窗口必需。后续强审计应独立设计。当前窄范围可批准，但不能据此关闭整站审计/调度一致性问题。

本设计保护到业务提交为止。提交后的apply\_edit仍可能与新版本交错，其版本检查存在窗口，不能视作线性化scheduler协议。保留已有结果核验，单列后续评估；不把新业务锁保持到scheduler完成，也不为消除错误强行重注册旧目标。未注册时钟变更与纯说明变更两类均需独立观察。

时间戳、版本、组/标签关系都无字段迁移；API返回无字段增删，不需新增API Breaking Change标记。若实施发现必须改结构或结果类型，须先更新设计再确认。无新增凭据列；复用摘要token不包含URL/body明文。

## 9. 验收矩阵与计划命令

以下是**待实施的验收要求**，不是本轮绿色结果。单元库只用sqlite:///:memory:；真实文件竞争及MySQL分别使用owned临时文件/独占专用库。任何mock DNS用例只能证明事务调度，另设实际校验分支和一次真浏览器无mock提交，不得把DNS旁路当完整安全验收。

1. **物理/API守卫：**同Session连接、7模型同bind、helper前零授权读取；timeout恢复先于读；BEGIN真实忙失败、恢复失败淘汰、rollback失败无掩盖；MySQL无SQLite SQL；待写ORM拒绝不丢工作；原生写契约单独说明。
2. **授权竞争：**role降级、停用、actor换组、task移出可见组、下线，各覆盖竞争先提交/最终保存先保护/DNS间隙提交；正常忙失败后显式新请求可成功。actor合法旧role先提交不是漏洞。
3. **比较与关系：**同字段冲突整单零写、不同字段保留、scope耦合、tag改名/删除、关系异常、等价、no-op、重复token、显式恢复；新标签SAVEPOINT失败主事务回滚；提交版本只增一次。
4. **URL与预算：**DNS时零物理事务/零待写，竞争者能写；URL被另一人改动后旧校验不可用；新URL重新校验后合并其他单元；连续URL变化超过预算conflict；DNS失败无写；同URL仍重验当前授权；DNS期间run\_date过期写前拒绝；3轮/2校验/1Stale上限逐项断言，BEGIN忙和未知提交零重试。
5. **异常事实：**入口/保护/flush/关系/commit之前与之后/清理双失败；独立连接查DB、版本、关系；未知提交两个事实分支均不得scheduler/成功日志；敏感异常原文不回前端。
6. **副作用：**非schedule/status零scheduler调用；确定提交成功后apply\_edit一次；调度失败、pending、调度前后新版本、OperationLog故障分别验；日志独立性按§7豁免准确展示。
7. **灵敏性校准：**隔离进程暂时绕过BEGIN、跳过DNS后授权重读、把URL匹配改恒真、遗漏终态rollback四类变异，验证器必须检测；变异只能在工具进程或源码副本，禁止改开发服务。关闭原上下文前探针验证释放，再做teardown对照。
8. **Web与MySQL：**真实Operator保存及Viewer/外组拒绝；第二账号通过真实RBAC入口撤权、第二Operator通过真实表单改任务；双实例共享专用业务库/固定同一secret、独立Session。DELETE/WAL均覆盖先撤权、保存先保护、DNS间隙撤权、同字段冲突与不同字段合并；Ajax及原生POST至少各一条完整链。MySQL保持FOR UPDATE及现有竞争语义，原提交后调度继续可用。

## 10. 性能、隔离、风险与回滚

锁成本是SQLite数据库级写者资格，包含不同任务/其他模块写竞争。BEGIN只临时零等待，取得保护后恢复原timeout，不声称整次保存零等待；DELETE模式commit可能受读者影响。DNS虽不再占写事务，resolver自身无硬期限；不在本批虚构硬请求超时、取消线程或新配置开关。

每轮增加actor/关系重读，最大三轮；TaskGroup/UserGroup/TaskTag已有按主体id索引，Tag按id或name/group查询。实际关系量与SQL耗时尚未量测，不能据此判定性能已通过。S3记录1/10/100标签的锁持有时长、总耗时、轮次、busy比例及同条件旧实现对照；如业务上限更低则用实际允许上限。硬性通过项为无网络/调度调用发生在锁内、循环有界、终态释放；延迟数值作为测量结果而非设计拍脑袋门槛，异常增长必须说明并阻止性能合格声明。

**临时文件窄例外待随设计确认：**普通unittest仍仅内存库；计划新增独立CLI为验证文件锁可使用自身TemporaryDirectory下的SQLite DELETE/WAL文件。必须校验路径归属、run\_id标记、拒绝任意数据库URL，输出目录须空，结束dispose并清理自身DB/WAL/SHM；不清理调用方目录，不接触开发库。此为本专项新授权范围，不能默认沿用上一批用户编辑工具例外。双HTTP/scheduler验收的JobStore也只用该拥有目录；浏览器账号由工具创建，密码不进仓库或HTTP证据。

发布回滚为撤销本批代码与文档状态，无迁移可逆负担；回退会重新暴露原授权窗口，不能当安全降级。遇无法确定的数据库/清理错误应拒绝本次保存，保留日志调查，不降级绕过BEGIN。多进程部署各进程均须运行同版本，混合旧写协议不作为已保证场景。

## 12. 官方依据与API版本边界

本轮在线核对[SQLite事务](https://www.sqlite.org/lang_transaction.html)：IMMEDIATE提前申请写事务，竞争写者可致BUSY，COMMIT亦可受读者阻塞。[SQLite隔离](https://www.sqlite.org/isolation.html)说明写者串行及journal差异；不因此声称所有读者被BEGIN阻塞。[SQLAlchemy sqlite3事务说明](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#legacy-transaction-mode-with-the-sqlite3-driver)支持区分逻辑与物理事务；在线版本可能高于仓库，具体API以本地2.0.36实现与现有helper为准，不使用Python3.12的autocommit参数。此处是基于官方机制与当前代码的工程推导，没有宣称任何大厂给CronPilot做过认证。
