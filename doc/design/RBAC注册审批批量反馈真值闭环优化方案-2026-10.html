1. 问题与影响

注册审批页的批量通过、批量拒绝会逐条执行业务动作，但当前无论成功多少条都返回 errcode=0 和跳转 URL。页面 JavaScript 只要收到 URL 就立即跳转，既不读取 errcode，也不显示 errmsg。

已复现：受限管理员批量批准一条无权处理的全局申请时，数据库正确保持 pending、不创建用户，但响应是 {errcode: 0, errmsg: "成功 0 条，失败 1 条…", url: "/rbac/registration_review"}。用户被立即带回列表，失败原因不可见。

这不是越权写入：已有审批服务仍会按数据库当前授权拒绝。但它违反“用户反馈必须如实反映已提交事实”的基本交互契约，尤其会在部分成功时掩盖未完成项。

2. 根因与已验证实现事实

位置事实结论
app/rbac/views.py::registration_batch_approve逐项调用 approve_registration()，收集 ok_count/fail_msgs 后固定 code=0。数据库逐项结果正确，但 HTTP 结果没有区分全成、部分失败、全失败。
registration_batch_reject采用同样的固定成功码和 URL 模式。同源问题必须一起修，不得只修“批量通过”。
registration_review.html两个批量 $.post() 回调遇 URL 即跳转。即使后端文字包含失败项，页面也不会向用户展示。
datas.utils.json.json_responsedata 同时映射到历史字段 result，可安全承载结构化摘要。无需改变全局 JSON 信封。
redesign-toast.js已有 CpToast.success/error/warning；消息使用 textContent 写入。可复用现有安全提示能力，不引入第三方组件。

3. 目标、范围与非范围

3.1 目标

  • 批量通过和批量拒绝对全成功、部分成功、全失败给出无歧义的 HTTP 与页面反馈。
  • 只有所有选中项都成功时，才返回成功码并自动跳转/刷新。
  • 存在任意失败时，用户在当前页面可看到成功数、失败数和逐项失败原因；不自动跳转掩盖结果。
  • 不改变已有逐项 fail-closed 业务行为、授权规则、CSRF、审计和事务语义。

3.2 范围

  • POST /rbac/registration_review/batch_approve 与 batch_reject 的响应契约。
  • 注册审批页两个批量按钮的提交、结果展示、刷新交互与无障碍通知。
  • 路由、服务结果、模板 DOM、浏览器交互的定向测试与交付证据。

3.3 非范围

  • 不修改单条通过/拒绝接口，不重写注册审批业务服务。
  • 不改变任何审批授权规则；范围外审批仍由既有数据库当前事实守卫拒绝。
  • 不解决审批列表的精确组匹配和旧 Session 可见性；该问题另立 R2 方案。
  • 不把批量操作改为全有或全无事务：保持已存在的“逐项执行、允许部分成功”业务语义。

4. 权威结果契约

6. 实施设计

6.1 后端：统一批量结果组装

在 app/rbac/views.py 提取仅供本模块使用的结果组装函数，输入操作类型、逐项结果，输出上述摘要。两个批量路由必须共同调用它，避免再次产生两个不一致的结果协议。

解析既有 ids / comment → 保持当前逐项 approve_registration / reject_registration → 收集 success_count 与 failures[{id, msg}] → failure_count == 0：code=0, outcome=all_success, url=列表 URL → success_count > 0：code=1, outcome=partial_failure, url='' → success_count == 0：code=1, outcome=all_failure, url='' → web_api_return(..., data=summary)

不得改变逐项调用顺序、不得因任一项失败撤销先前已成功的审批、不得把异常原文放入 msg。失败消息继续来自既有服务层受控文案。

6.1.1 原始异常与 trace_id 关联

失败分为业务失败与系统异常。“申请不存在”“已处理”“无权授予”等受控业务文案可返回前端，不生成关联号。数据库、驱动或未知程序异常必须使用 logger.exception() 记录原始异常与完整 traceback，日志同时记录 32 位十六进制 trace_id、操作类型和申请 ID。

ERROR ... trace_id=a7c921... operation=approve request_id=42
Traceback ...
DatabaseError: [原始异常仅在服务端日志]

客户端对同一失败项仅获得 {id, msg: "服务器内部错误，请稍后重试", trace_id}，不返回异常类型、SQL、路径、凭据或 traceback。若异常已在服务层捕获，trace_id 必须由服务层生成并随受控结果传递；路由不得二次生成无法对应原始日志的假关联号。本地可从 datas/logs/local-server.log 按 trace_id 检索；生产环境在实际 systemd/容器日志中使用同一关联号。

6.2 前端：结果条优先于导航

在 registration_review.html 的批量条之后新增空的页面级结果容器，使用 aria-live="polite"；全失败使用 role="alert"。页面脚本新增一个只用 textContent 写入结果的渲染函数，禁止拼接服务端消息到 innerHTML。

  • all_success：调用现有 CpToast.success()；仅在 errcode===0 && url 时跳转。
  • partial_failure：调用 CpToast.warning()；渲染 warning 结果条和“刷新列表”按钮，不跳转。
  • all_failure：调用 CpToast.error()；渲染 error 结果条和“关闭结果”按钮，不跳转。
  • 网络/非 JSON：保持现有错误 Toast；两个批量按钮恢复可用，避免被永久禁用。

页面专属样式必须放入 app/static/css/redesign-pages.css 的 .cp-page-reg-review 作用域，使用既有 --cp-* token；模板内不新增超过 3 行的非注释 CSS。

6.3 防重复提交与确认框

现有批量批准确认框和批量拒绝输入框保留。两个异步回调在请求开始时禁用相应确认按钮，完成、失败、网络错误后恢复；页面级结果展示不得通过嵌套 form 或 Bootstrap modal 实现。批准仍使用 CpConfirm.show({body: ...})，拒绝仍使用现有页面内 CpModal。

10. 风险、回滚与完成定义

风险控制回滚原则
把部分成功当成完整失败，误以为数据库已回滚明确 outcome 与成功/失败数量；页面文字写明“成功项已完成”。可回滚结果条样式，但不得恢复固定成功码或自动跳转掩盖失败。
接口字段影响历史调用方仅修改本页面专用批量端点；保留既有 errmsg/result/url 字段，新增 data 摘要。保留 B1 的后端三态契约，前端可暂时降级为不跳转+Toast。
失败详情被注入页面页面用 textContent，服务端只传受控业务文案。不得改用 innerHTML 输出错误详情。
页面成功项状态陈旧部分/全失败不自动跳转，提供显式刷新；全部成功才自动刷新。不得静默刷新并吞掉详情。

完成定义（已达成）：两个批量端点和页面均满足三态契约；所有失败信息在用户离开当前页前可见；接口摘要与数据库逐项状态一致；全成功体验不回退；可重复自动化证据、浏览器矩阵、复盘、Release Notes、HTML/Markdown 和索引已同步。父方案 F-01 于 B3 关闭；父方案整体仍受 F-02 阻断，不得据此宣称 S0–S5 已全部关闭。
