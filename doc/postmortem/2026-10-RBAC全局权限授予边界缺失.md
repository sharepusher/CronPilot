# RBAC 全局权限授予边界缺失修复复盘

日期：2026-10-16 · 范围：S0–S5（新增、编辑、前端最小暴露、注册审批与最终交付） · 状态：实现与写入安全验证完成；独立 Review 条件通过，S5 待 P1 收口后验收

## 1. Bug 定位

`POST /rbac/users/add` 与 `POST /rbac/users/edit` 只检查目标角色能否使用 `__ALL__`，没有在业务写入前检查当前操作人是否有权授予全局 Scope。单组或多组 Biz Admin 因拥有 `user:manage`，可构造 `role=admin&group_ids=__ALL__`，创建或修改为无组关系的全局管理员；多组 Biz Admin 还可提交自身范围外的具体组。

## 2. 根因

- **授权对象混淆：**原逻辑验证的是 target 角色与目标组参数是否合法，却把“target 可以是 admin”误当成“actor 可以授予全局权限”。
- **页面约束代替写边界：**锁定组只在路由中覆盖部分表单值；多组管理员仍可看到全局选项，直接 POST 更不受前端约束。
- **授权事实来源不稳定：**既有管理范围检查主要依赖 Session 组集合，不能证明写入时 actor 的数据库当前角色、活动状态和组关系仍然有效。

## 3. 测试漏洞

- 已有用例覆盖“非 admin target 不得使用 `__ALL__`”和种子 admin 的合法路径，没有覆盖“受限 admin actor 授予 admin target 全局 Scope”的负向矩阵。
- 缺少 Ajax/原生 POST、单组/多组 actor、新增/编辑、范围外具体组、陈旧 Session 与拒绝零副作用的组合测试。
- `tests/test_registration.py` 的一个独立 fixture 未导入注册申请模型，单文件执行时可能以缺表异常污染诊断；S0 已补齐模型注册。
- S3 首轮页面测试用裸 `value="__ALL__"` 判断 DOM，误命中页面脚本中的 `querySelector` 字符串而产生 4 个假失败；这说明“源码包含字符串”不等于“实际渲染了 option”。
- S4 发现审批仅对 admin 目标检查 Scope，范围外 viewer/operator 申请可被直接 POST 批准；审批者能力又取自 Session，数据库已降权时仍可能批准全局申请。
- 重新启用测试用例只伪造审批人 Session、数据库没有对应有效用户，旧实现因此未真正覆盖数据库授权事实；S4 将夹具改为真实审批人。

## 4. 修复

- `app/rbac/policy.py` 新增无 Session、无数据库、无写副作用的授予矩阵：只有种子/当前全局 admin 可授予 `admin + __ALL__`；按组 admin 只能授予当前数据库组集合的子集。
- `app/rbac/services.py` 统一规范化 `__ALL__`、具体组与非法参数，并从数据库读取 actor 当前角色、活动状态和组关系；编辑 POST 还以数据库当前关系校验 actor 是否仍可管理 target。
- `app/rbac/views.py` 在新增/编辑的第一个业务副作用前调用统一校验，拒绝后不进入 `create_user()`、`update_user()` 或组关系写入；合法结果只使用服务层返回的规范化 Scope。
- 拒绝审计使用稳定原因码，detail 仅记录入口、原因和目标 ID；审计本身异常时记录受保护错误，主请求仍拒绝，禁止 fail-open。
- S3 由同一数据库当前校验派生页面 `can_assign_global`；受限管理员的 HTML 不渲染 `option[value="__ALL__"]`，并明确提示只能分配当前管理组。全局/种子管理员仍保留合法选项；模板脚本在该 option 缺席时安全返回。
- 页面测试断言收紧为真实标签前缀 `<option value="__ALL__"`，既排除脚本字符串误命中，也保留浏览器 DOM 查询作为第二层证据。
- S4 将单条与批量审批的 reviewer ID 显式传入服务层，并对 admin、operator、viewer 全部调用 `validate_user_scope_assignment()`；Session 只定位用户 ID，最终角色、状态和组范围从数据库读取。

## 6. 同类排查

S2–S4 已检查用户新增、编辑、停用用户同名覆盖、单条审批、批量审批、Ajax/原生响应及页面正反暴露。生产调用方已逐项归类：新增、编辑、单条审批、批量审批均已守卫；事务内组替换为受信任私有函数；未发现其他生产写入调用点。写入授权全部回读数据库。后续独立 Review 发现列表展示使用 Session 和字符串模糊匹配会造成可见性残余风险，已列为 S5 验收前收口项。

## 7. 预防方案

1. **可执行安全矩阵：**保留 `tests/test_rbac_global_scope_assignment.py` 作为独立门禁；任何用户 Scope 写入口变更必须运行该模块，并要求受限 actor 的直接 POST、零业务副作用和审计故障用例同时通过。
2. **单一写边界：**新增或修改用户 Scope 的生产入口必须调用 `validate_user_scope_assignment()`，禁止重新在 view 中仅按 target role 判断。复核命令：`rg -n "create_user\(|update_user\(|set_user_groups\(|approve_registration\(" app/`；调用方分类与最终验收已写入设计 rev.8。
3. **数据库事实优先：**最终授权只允许 Session 提供 actor ID，角色、活动状态、actor 组和 target 管理范围必须在写入边界回读数据库；陈旧 Session 防护由专项测试固定。
4. **交付门禁：**涉及 RBAC 授权语义的三文件及以上变更，除单测外必须运行 86 路由冒烟，并用受限和允许两种真实角色执行浏览器正反路径；证据写回设计文档与本复盘。
5. **DOM 断言精度：**服务端渲染可见性测试必须匹配实际 HTML 标签或解析 DOM，禁止用可能同时存在于 JS/CSS 的裸属性字符串判断元素存在；落地位置为 `TestGlobalScopeAssignmentPageExposure`。
