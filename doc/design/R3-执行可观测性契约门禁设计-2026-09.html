R3 · 执行可观测性契约门禁与 Tracer / Presenter 对齐设计

已实施 工程门禁 · 无 UI 大改 收敛版 B0 收尾 · B2 尾巴

入口： 问题 根因 方案 页面对比 范围 分批 验收 风险

一句话：R1/R2 已修好列表与详情产品面，但 Tracer 写库白名单与 Presenter 摘要规则仍是两份手写表，缺集中合同测试。本轮只加可 CI 的契约门禁并补齐映射表文档化断言，不改页面布局、不标已交付。

1. 问题

  1. 双表漂移风险：写路径 execution_tracer._DETAIL_KEYS 与展示路径 run_inspector_presenter._event_summary / _EVENT_LABELS 独立维护。新增 event_type 或 detail 键时，容易出现「库里有字段、页面无摘要」或「摘要读了未白名单键」。
  2. B0 未收口：收敛版要求新增 tests/test_execution_observability_contract.py 冻结状态机/脱敏/未完成语义/锁边界；现有断言散落在 R1/R2 测试中，无单一合同入口，R2 安全约束易被后续热修改回。
  3. 写库仍含敏感键：Tracer 允许 exc_detail 入库（故障诊断用）；展示已禁原文。若有人再次把 raw detail 拼进模板，仅靠人工 Review 不够。

不是：用户再改一遍详情页布局；也不是本轮做四角色浏览器发布（属 R4/B6）。

2. 根因

层事实
结构B2 先落地 Tracer 白名单；B4/R2 另写 Presenter 摘要，无共享「事件类型登记表」或双向断言。
测试R2 否定了 HTML raw JSON，但未断言「每个 Tracer 事件类型都有标签」「summary 只用到 _DETAIL_KEYS 内的键」。
流程收敛版 B0「先冻结契约」在热修接线时被跳过；产品面先行，合同文件未建。

3. 方案（推荐）

3.1 单一合同测试模块（核心）

新增 tests/test_execution_observability_contract.py，作为可观测性的 B0 合同入口。至少覆盖：

契约组断言要点
C1 事件登记_EVENT_LABELS 的 key ⊇ Tracer 实际 emit 的事件类型集合（从代码/测试夹具枚举：task.enqueued、task.start、db.load_cif、ssrf.check、http.*、db.write_log）
C2 写↔展对齐对每个有 summary 规则的 event_type：解析样例 detail 后，summary 字符串不得包含 exc_detail / block_detail / 任意非白名单键的字面值；允许使用的键 ⊆ _DETAIL_KEYS[event_type]（无登记则 summary 必须恒为空串）
C3 展示硬禁模板 run_inspector.html 静态禁止：event.detail、ri-timeline-detail、jl.、cif.；Presenter 行 dict 不得含 detail 键
C4 角色矩阵冒烟复用/薄封装 R2：viewer/operator/admin 对同一 fixture，URL/正文/业务日志可见性符合 R2 矩阵（可 import 已有断言函数，避免复制逻辑）
C5 状态过滤pending/running 不落入 not_success；in_progress ∈ KNOWN_OUTCOMES（锁 R1，防回退）
C6 锁未获取若已有「锁未获取不建父记录」测试，合同文件 import 或文档引用其用例名；本轮不重写调度实现，仅保证合同清单列出并 CI 跑到

3.2 轻量代码整理（最小 diff）

  • 在 execution_tracer.py 与 run_inspector_presenter.py 顶部注释交叉引用对方模块与合同测试路径。
  • 推荐：将 Presenter 中「summary 可读键」显式声明为常量（如 _SUMMARY_KEYS），合同测试断言 _SUMMARY_KEYS[t] ⊆ _DETAIL_KEYS.get(t, set())。不强制合并两个模块为一个文件（避免循环依赖）。
  • 禁止为「对齐」而扩大 Tracer 写入面（不新增可写敏感键）。
# 合同关系（示意）
Tracer._DETAIL_KEYS[event_type]  ⊇  Presenter 可读键
Presenter._EVENT_LABELS          ⊇  运行时 emit 的 event_type
页面 HTML                        ⊥  raw detail / exc_detail 原文

3.3 交互契约

无新路由、无新 API、无模板结构变更（R3-A）。若确认纳入下方「可选 R3-B」，才允许任务详情近期执行文案微调。

4. 页面对比

本轮默认范围：无前端可见变更。R3-A 仅测试与常量对齐，不改管理端 HTML/CSS 可见效果，故不强制 Before/After 画面。自检：实现 diff 不得出现 app/templates/、app/static/css/ 的产品向改动（注释交叉引用除外）。

可选 R3-B（需你在确认时显式点名才做）：任务详情「最近执行」将纯色点扩展为与列表一致的超时/失败区分或短文案。若纳入，必须另补内嵌 Before/After（复用 .td-recent-runs），并单独分批验收。

5. 范围

做不做
  • tests/test_execution_observability_contract.py（C1–C6）
  • Presenter 可选 _SUMMARY_KEYS 常量 + 交叉注释
  • 必要时把 R2 重复断言改为合同模块调用（去重，行为不变）

  • 扩大 Tracer detail 写入键；删减 exc_detail 入库（另立脱敏设计）
  • 四角色浏览器全矩阵、双后端压测、标「可观测性已交付」（R4/B6）
  • 未确认的 R3-B 任务详情 UI

8. 风险

  • 过严导致假红：emit 集合若含仅日志、不进时间线的类型，登记表需同步；以代码实测 emit 列表为准，不凭记忆。
  • 重复测试变脆：合同模块应组合现有断言，避免三处复制角色矩阵。
  • 误以为可交付：R3 绿 ≠ B6；RELEASE 只写「工程门禁」，不写「功能已交付」。
