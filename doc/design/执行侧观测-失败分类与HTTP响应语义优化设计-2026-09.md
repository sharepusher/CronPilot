# 失败分类、HTTP 响应与请求状态语义收口

本文针对执行记录 `264147763200` 暴露的观测语义冲突，定义统一的数据模型、分类规则、页面交互和分批验收方案。它不改变业务成功/失败判定，只修正“失败发生在哪一层、是否收到 HTTP 响应、请求参数是否已准备/已发送”的表达。

## 1. 问题与根因

**实证：**该记录的异常是 `TypeError: HTTPConnection.__init__() got an unexpected keyword argument 'assert_hostname'`。异常发生在本地 HTTP 客户端初始化阶段；没有远端 HTTP 响应，因此 `http_status` 为空。当前主摘要显示“内部错误”，时间线却把所有 `http.error` 显示为“连接失败”，两者矛盾。

| 现象 | 根因 | 影响 |
| --- | --- | --- |
| 连接类问题显示“内部错误” | `exception_fail_reason` 只识别 requests 连接异常，其他异常统一归 `internal`。 | 无法区分远端连接失败与本地传输栈故障。 |
| 时间线显示“连接失败” | Presenter 对所有非 Viewer 的 `http.error` 硬编码该文案。 | 同一运行出现两个失败原因。 |
| HTTP 显示“—” | 请求未返回 response object，`http_status` 必然为空；页面未解释“未建立连接”。 | 用户误以为 HTTP 字段被隐藏或丢失。 |
| “实际请求：已注入运行参数” | 当前以已构造并保存 `actual_url` 判断，早于真正的 transport 调用。 | 把“参数准备”误表达为“请求已发送”。 |
| 正文不完整 | 展示层按角色截断（Viewer 禁止、Operator 200 字符、Admin 2048 字符）。 | 脱敏策略与长度策略混淆，缺少截断提示。 |

## 2. 设计目标与非目标

- 目标：单一失败分类来源；明确请求生命周期；无响应时给出可诊断解释；敏感字段脱敏但不无理由截断。
- 非目标：不修改任务业务结果判定；不把所有 TypeError 误判成连接失败；不向 Viewer 开放响应正文或凭据。

## 3. 统一执行状态模型

| 维度 | 枚举/字段 | 语义 |
| --- | --- | --- |
| 业务结果 | `success|fail|timeout|error|pending|running` | 任务最终是否符合业务规则。 |
| 失败阶段 | `pre_request|transport|remote_response|persistence` | 故障发生在哪个处理阶段。 |
| 失败原因 | `connection|timeout|client_incompatible|http_4xx|http_5xx|keyword|internal|blocked_url` | 可操作的最小诊断分类。 |
| HTTP 交互 | `not_started|prepared|sent|response_received|failed_before_response` | 请求是否准备、发送、收到响应。 |
| 观测完整性 | `healthy|degraded|unknown` | 仅表示观测事件是否完整，不代表业务成功。 |

推荐新增 `failure_stage`、`transport_state`、`response_received`；保留现有 `status`、`fail_reason`、`http_status` 兼容 API。事件 detail 使用同一枚举，Presenter 不再自行推断文案。

## 4. 分类规则

| 异常/结果 | failure\_stage | fail\_reason | transport\_state | 页面文案 |
| --- | --- | --- | --- | --- |
| DNS、TCP refused、ConnectionError | transport | connection | failed\_before\_response | 连接建立失败 |
| 连接或读取超时 | transport | timeout | failed\_before\_response | 请求超时 |
| `assert_hostname` 等客户端 API 不兼容 | transport | client\_incompatible | failed\_before\_response | HTTP 客户端初始化失败 |
| 收到 4xx/5xx | remote\_response | http\_4xx/http\_5xx | response\_received | 远端返回 HTTP 4xx/5xx |
| 收到 2xx 但命中业务关键词 | remote\_response | keyword | response\_received | 响应内容命中失败规则 |
| 无法归类的程序异常 | transport 或 persistence | internal | 按实际阶段记录 | 系统内部异常 |

## 5. 写入与查询流程

```
创建 JobLog(run_id) → request_prepared(trace/sign 注入) → http.start
→ transport 调用
   ├─ 异常：写 http.error（failure_stage/reason/state）→ 无 HTTP 状态
   └─ response：写 http.complete(status/bytes) → 业务判定
→ db.write_log → 更新 JobLog 摘要与观测状态
```

`actual_url` 只记录脱敏后的“准备发送目标”；新增 `transport_state` 后，页面是否显示“已发送”只由状态驱动。收到响应时才填 `http_status` 和 response body。

### 5.1 数据落点与页面入口

| 信息 | 存储位置 | 写入时机 | 页面位置 |
| --- | --- | --- | --- |
| 执行结果、失败阶段、失败原因 | `job_log` | 执行结束或异常捕获时 | Run Inspector 顶部“结果”摘要 |
| 参数准备与传输状态 | `job_log_events`：`request.prepared`、`http.start`、`http.error`、`http.complete` | 各阶段边界即时写入 | Run Inspector“时间线”与“请求”区 |
| HTTP 状态码与响应长度 | `job_log.http_status`、`http.complete.detail` | 收到 response object 后 | Run Inspector“响应”区 |
| 异常详情 | `job_log.content`（脱敏后）及 `http.error.detail` | 异常捕获时 | Run Inspector“错误详情”折叠区 |

用户入口保持现有执行记录列表：点击某条记录的“查看详情”进入 `/job_log_detail/<run_id>`（旧 trace 链接先解析父记录再转 run\_id）。不新增独立的“观测中心”页面，避免与执行记录形成两个事实源。

### 5.2 单次执行的交互顺序

1. 列表展示最终业务状态；若为异常，用户点击“查看详情”。
2. 详情页先看顶部摘要：结果、失败阶段、失败原因、HTTP 是否收到响应。
3. 用户展开“请求”：查看脱敏目标、参数是否准备、传输状态；这里不承诺远端已收到。
4. 用户展开“时间线”：按 `run_id + seq` 查看每个阶段，异常节点必须与顶部失败分类一致。
5. 若 `response_received=true`，展开“响应”查看 HTTP 状态、响应长度和有权限的正文；否则显示“未获得 HTTP 响应”及错误详情。

Run Inspector 仍是执行观测的唯一详情入口。顶部摘要、请求、响应、时间线必须引用同一 DTO；用户不需要在多个页面拼接信息。

### 6.1 场景验收对比

| 场景 | 顶部摘要 | 请求/响应区 | 时间线末节点 |
| --- | --- | --- | --- |
| DNS/TCP 连接失败 | 传输层 · 连接建立失败 | 传输状态：连接失败；HTTP：未获得响应 | `http.error · 连接建立失败` |
| 本地客户端 API 不兼容 | 传输层 · HTTP 客户端初始化失败 | 参数已准备；未确认发送；HTTP：未获得响应 | `http.error · HTTP 客户端初始化失败` |
| 远端返回 500 | 远端响应 · HTTP 5xx | 传输状态：已收到响应；HTTP 500；显示响应正文 | `http.complete · HTTP 500` |
| 观测事件写入失败 | 业务结果照常显示；右上角“观测不完整” | 业务响应仍可见；时间线标注缺失阶段 | 最后可写入节点标记 degraded |

## 7. 实施范围与分批

1. **Batch A：分类契约。**扩展失败枚举和异常映射；事件与 JobLog 共用分类函数；补齐 TypeError/ConnectionError/Timeout/HTTP 4xx/5xx 测试。
2. **Batch B：传输状态。**在请求准备、发送尝试、响应接收边界写入状态；修正 actual\_url 文案；无 response 时明确显示“未获得 HTTP 响应”。
3. **Batch C：Presenter/UI。**统一 DTO；时间线不再硬编码“连接失败”；增加失败阶段、传输状态、截断提示；按角色验证。
4. **Batch D：依赖问题单独修复。**针对 `assert_hostname` 做 HTTP 客户端依赖兼容性排查，独立设计、测试和发布，不与观测语义改动混合。

## 8. 验收标准

- 同一运行的摘要、时间线、响应区使用同一 `fail_reason/failure_stage/transport_state`，不得出现“内部错误”与“连接失败”矛盾。
- 无 response object 的用例显示“未获得 HTTP 响应”，且 `http_status` 保持 NULL；有 response 的用例显示真实状态码。
- “参数已注入”不再等同于“已发送”；页面分别展示准备状态和传输状态。
- Admin 对短于限制的非敏感错误正文完整显示；超限正文必须显示截断标识和原文长度；Viewer/Operator 权限边界保持不变。
- 执行事件按 `run_id` 关联，观测写入失败仍显示 degraded，不影响业务结果。
- 通过定向单测、`ruff check`、`smoke_routes.py --check`、UI 契约门禁和浏览器三角色关键路径验证。

## 9. 风险与回滚

| 风险 | 控制 |
| --- | --- |
| 新枚举被旧 API/筛选器拒绝 | 保留旧字段值，新增字段向后兼容；先补枚举扩展检查和 API 契约测试。 |
| “已发送”判断被误读 | 只由 transport\_state 驱动，并保留“未确认发送”中间态。 |
| 错误正文扩大暴露面 | 凭据先脱敏；角色控制；完整内容操作写审计日志并设长度/下载限制。 |
| 迁移失败 | 新增 nullable 字段、双写兼容；回滚只关闭新字段读取，不删除旧数据。 |

**决策：**批准“分类统一 + 请求生命周期显式化 + 响应语义分层”作为执行侧观测下一阶段设计基线；`assert_hostname` 依赖兼容性问题另立实现任务，不能用“内部错误”掩盖。
