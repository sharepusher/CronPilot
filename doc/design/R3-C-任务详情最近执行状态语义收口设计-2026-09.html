R3-C · 任务详情「最近执行」状态语义收口设计

待确认 UX · 任务详情 收敛版 B5 · 短设计
日期：2026-09-17 · UI 对照： 页面对比 Demo §B · 父：收敛版 B5 · 前序：R3

入口： 问题 根因 方案 页面对比 范围 分批 验收 风险

一句话：把任务详情「最近执行」改成与 页面对比 Demo §B 「改造后」一致：● 成功 / ● 超时 / ◎ 执行中；数据用 job_log_badge，并补 time_short。

1. 问题

现网「最近执行」用手写三元 class，把 timeout/error 画成失败红点；执行中也可能被误读为失败。列表侧（R1）已用 job_log_badge，此处未对齐。另：视图未传 time_short，时间列常空。

2. 根因

层事实
模板未用 job_log_badge，手写 ok / running / pending / else→fail。
CSS.td-rr-status 仅 8px 圆点，无「●/◎ + 文案」形态。
视图recent_runs 未写 time_short / status_label / status_tone。

3. 方案

改造后的可见效果以 Demo §B TO-BE 为准（见下节页面对比，与父 Demo 同画面）。

  • 数据：label, tone = job_log_badge(status)；写入 status_label、status_tone、time_short。
  • 模板：每行渲染 时间 | ●/◎ + 文案 | 耗时（与 Demo 一致）；点击仍进 /job_log_detail。
  • CSS：.td-rr-status 改为行内状态文案（同 Demo .demo-status）；行布局 1fr auto auto。
  • 不做：不新卡片、不塞时间线；列表 / Run Inspector 不在本批。

4. 页面对比（Before / After）

下列画面与 任务执行链路可观测性-页面对比Demo.html §B 任务详情的最近执行相同（AS-IS / TO-BE 原文照录）。

现状：二元状态点 AS-IS
  • 10:32:00● 成功1.2s
  • 10:27:00● 失败5.0s
  • 10:25:11● 失败—

问题：执行中记录可能被二元展示误读为失败。

改造后：状态机语义 TO-BE
  • 10:32:00● 成功1.2s
  • 10:27:00● 超时5.0s
  • 10:25:11◎ 执行中—

变化：终态失败与未完成记录按真实语义显示；锁竞争不会创建此处的执行记录，详情跳转 URL 不变。

5. 范围

做不做
  • views.py：recent_runs 补 badge 字段 + time_short
  • task_detail.html + redesign-pages.css：对齐 Demo §B 行形态
  • 测试：超时行见「● 超时」、执行中见「◎ 执行中」
  • 执行记录列表（R1）、Run Inspector（R2）、R4 交付标注

6. 分批

子批内容可独立验收

7. 验收

  1. 打开任务详情「最近执行」：可见 ● 超时、◎ 执行中（有对应数据时），形态与 Demo §B TO-BE 一致。
  2. bash scripts/cronpilot.sh restart --daemon 后 curl/浏览器断言文案；单测覆盖 badge 映射。
  3. audit_hardcoded_colors.py --check、check_ui_contract.py --check（若触模板）。

8. 风险

窄卡上「● 超时」比纯圆点略宽；用 nowrap + 现有卡片宽度即可。其它 status（失败/异常/已入队）用同一 ●/◎ + badge 规则扩展。
