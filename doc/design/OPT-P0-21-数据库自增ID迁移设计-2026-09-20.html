OPT-P0-21：数据库自增 ID 写入机制切换设计

日期：2026-09-20 · 状态：待用户确认 · 前置：v4.0.0 后深度 Review、用户澄清“id_generator 不应继续使用”

1. 问题与目标

当前代码仍在 cron_infos、job_log、job_log_events 模型中设置 default=next_id，execution_tracer.py 还直接写入 next_id()。目标是将后续新写入统一切换为数据库生成主键，生产路径不再依赖 datas/utils/id_generator.py，优先保证新写入的唯一性、事务性、可观测性和结果准确性。现有表、历史数据和历史 ID 原样保留，不做数据搬迁、重编号或清洗。

2. 根因与现状证据

  • 应用层生成器只有进程内锁，不能提供 Gunicorn 多 worker 的全局唯一性；时钟回拨也未形成跨进程契约。
  • 当前 SQLite 库的 cron_infos.id、job_log.id 是 INTEGER PRIMARY KEY，但 job_log_events.id 是 BIGINT PRIMARY KEY；三者都由应用层默认值填充，不能把“模型写成 BigInteger”误认为已启用数据库自增。
  • 现有收敛设计已要求至少 job_log.id 恢复数据库自增；本设计将范围扩展为所有业务主键，消除用户目标与实现分叉。

3. 方案

3.1 主键策略

移除全部生产代码对 next_id 的 import、模型 default 和显式赋值。SQLAlchemy 模型使用数据库自增语义；新建记录不提供 id，flush/insert 后读取数据库返回的 ID。既有表结构只做必要的自增属性调整，不复制、不删除、不改写历史行；数据库自增起点必须设置为当前最大 ID 加一。

3.2 后端实现契约

后端实现验收
SQLite需要将主键列建成 SQLite 的 INTEGER rowid 主键；对现有 BIGINT PRIMARY KEY 表采用受控重建，复制全部列、索引、约束和数据，再原子替换。重启/迁移幂等；最大历史 ID 后插入得到更大 ID；进程重启后仍唯一。
MySQL主键保持 BIGINT，声明 AUTO_INCREMENT；迁移前读取最大 ID，保证自增起点大于存量最大值。空库、仅旧小 ID、含 50-bit 历史 ID 三种数据集均能插入并回读 ID。

3.3 引用列语义审计

引用列不做历史数据迁移或批量改写。新写入链路继续使用现有列类型，并在业务边界完成存在性/范围校验；若数据库当前列类型无法容纳未来自增值，应先做结构变更而不改写历史行。禁止静默截断。

3.4 迁移事务与回滚

  1. 切换前记录每张表当前最大 ID、现有约束和自增状态，必要时做数据库备份；不改写历史行。
  2. 仅执行目标 schema 所需的 DDL：为新记录启用自增，并将起点设为当前最大 ID 加一。
  3. 在明确停写窗口内执行 DDL；失败时回滚 DDL 或恢复备份，不进行临时表数据复制。
  4. 在独立验收事务中插入并回读新记录 ID，确认新 ID 大于切换前最大值；重复执行必须幂等。

4. 范围

包含：三张主键模型、ExecutionTracer 写入、SQLite/MySQL 自增属性切换、当前最大 ID 起点校正、模型/仓储/并发测试、ID 生成器死代码审计和设计文档。

不包含：历史数据迁移、历史 ID 重编号、历史引用批量改写、业务 URL/API ID 格式改造、删除历史数据、在本轮保留 worker 位继续扩展生成器。

5. 分批实施

  1. Batch A 契约与盘点：读取三张表当前最大 ID、现有 schema 和自增状态，不修改数据。
  2. Batch B 模型写路径：移除 next_id 生产调用，改为 ORM/Core insert 的数据库回填；补 flush 后 ID 与失败回滚测试。
  3. Batch C SQLite：仅调整必要的主键自增属性；若 SQLite 物理限制必须重建，要求逐行复制且行值完全一致，禁止业务数据改写。
  4. Batch D MySQL：验证 BIGINT/AUTO_INCREMENT 起点大于当前最大值和并发插入。
  5. Batch E 回归与发布：全量测试、双后端、并发、重启、异常路径和发布文档收口。

6. 验收标准

  • rg "from datas.utils.id_generator|next_id\(" app datas --glob '*.py' 不存在生产写路径。
  • 切换前后每张表的行数、历史主键集合、历史列值和引用关系完全一致；禁止任何历史行变化。
  • SQLite/MySQL 新插入记录的 ID 均大于切换前最大值，且重复执行切换不会产生重复或跳回。
  • 两进程/多线程同时插入三类记录不产生主键冲突；应用重启后仍由数据库分配唯一 ID。
  • 创建、更新、失败回滚、观测事件写入和重试路径的 ID/状态一致。
  • 运行 Ruff、模型序列化测试、关键路由冒烟、全量测试和版本/文档门禁；未创建 4.1.0 tag 直至全部通过。

7. 风险与回滚

风险控制回滚
SQLite 重建遗漏约束/索引目标 schema 断言与迁移后关键查询事务失败保留原表，恢复快照
当前数据不满足目标范围迁移前检查并 fail-closed停止发布，先处理数据
并发写入造成状态分裂停写窗口、事务边界和并发测试回滚迁移，不上线半成品
数据库自增起点错误迁移前设置并验证 sequence/AUTO_INCREMENT停止发布，修正起点后重跑幂等迁移

确认本设计后，才允许实施 Batch B；确认前不得删除 id_generator.py 或修改生产模型。
