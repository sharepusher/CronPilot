## 0. 先从官方工程实践判断该怎么测

**先回答用户的问题：**要判断当前代码有没有锁释放问题，应在隔离MySQL中原样运行当前服务；它返回以后，先别让框架结束请求，再由第二个独立连接申请同一记录的写锁。能拿到，说明被测路径在这个边界已释放该记录的冲突锁；拿不到且确认仍由原连接持有，才是当前路径存在问题的证据。

以下来自厂商官方文档或工程团队公开文章；它们不是各公司统一强制标准，也没有现成的CronPilot专用方案。右侧是针对本项目的工程推导，不能当作厂商直接背书。

| 公开来源 | 来源支持的实践 | 对当前问题的适用结论 |
| --- | --- | --- |
| Oracle/MySQL：[Locking Reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html) | FOR UPDATE取得的锁随事务提交或回滚释放；其他事务申请同一冲突行锁会等待。 | 用第二个真实事务申请同一条现存记录的锁作行为证据；普通SELECT或最终业务值不能代替。 |
| Microsoft：[Choosing a testing strategy](https://learn.microsoft.com/en-us/ef/core/testing/choosing-a-testing-strategy) | 替代数据库上通过的测试不保证真实数据库系统行为；真实资源测试还需解决隔离。 | 该文面向EF Core；迁移到本项目的原则是使用专用MySQL/InnoDB验证锁，SQLite仅测快速逻辑，不连接生产数据。 |

**对现有方案的裁定：**真实MySQL、独立连接、先观察后清理和故障对照具有充分工程依据；不需要引入完整变异测试平台、线上故障注入或全站事务重构。实施顺序应是先用最小实验判明当前实现，再将有效实验固化为回归。

### 0.1 三组实验就能说清楚怎样验证

A和B表示两个独立数据库连接；下列全部使用新建专用测试库。给B设置有界锁等待，申请精确存在记录的FOR UPDATE锁。每次申请结束后，B都显式回滚自己的探针事务。

1. **先确认这把“检测尺”有效。**A明确锁住目标记录且不提交；B申请同一记录必须被阻塞并得到预期1205。A回滚后，B必须能获得。若前后都能获得或都不能获得，先处理测试连接/事务/环境问题，不能判断业务服务。
2. **测当前代码原样运行。**制造一个真实用户编辑冲突，让当前update\_user\_management返回CONFLICT；A对应的请求/应用上下文暂不退出、不额外回滚、不关闭Session。此时B申请同一目标记录。若成功且命中目标行，该冲突路径的目标行锁释放通过；若1205且确认阻塞者是A，则该服务返回边界未释放；若连接/权限报错，结论是验证未完成。然后才清理A。
3. **最后测测试能否发现错误。**仅在隔离测试进程省略A的终态rollback，其余步骤与实验2相同；B应无法获得锁。若这个错误版本仍通过，说明测试还不可信。恢复回滚后应通过。这一步不改变对“当前原样实现”的观测结果。

实验2首先回答“现在有没有问题”；实验1和3回答“这个判断方法可信吗”。先做CONFLICT的最小闭环，再扩展到ALREADY\_APPLIED和锁后FAILED；只做一个场景通过，不能宣称所有返回路径都通过。§5列出了完整矩阵。

### 0.2 结果该如何解读

- **原样实现中B能获得：**当前被测路径、被测记录在服务返回时未残留冲突行锁。
- **原样实现中B等到1205，确认A是阻塞者：**证明该路径的服务边界清理有问题；若退出A上下文后才成功，则框架在兜底。
- **只有退出A上下文后才探测且B成功：**仅证明请求清理后的状态；这就是旧脚本证据不足的原因。
- **省略回滚的错误版本也通过：**说明验收仍有盲点，不等于当前原样代码有锁泄漏。
- **错误来自连接、权限、空记录或非预期数据库错误：**验证未完成，不应归为产品通过或产品锁泄漏。

**rev.1.1设计阶段事实边界：**当时只完成SQLite生命周期对照，尚未执行真实MySQL三实验。rev.1.2已按批准方案完成三实验及终态矩阵，受测正常路径通过、错误变异均被识别，详§11；不将测试盲点误称为已发生的生产锁泄漏。

## 1. 问题：测试观察的是哪个时刻

父设计 D8 与 U2 要求锁内未提交终态在**服务返回前**明确结束事务。当前 `scripts/verify_user_edit_transaction_mysql.py:175–197` 调用服务后退出 request context，才启动第二连接的锁探针。两者测量边界不同：

```
设计要求：服务返回 → 立即观察（原上下文仍存活） → 最后清理
现有脚本：服务返回 → request/app context 退出并自动清理 → 才观察
```

后一个顺序只能证明“请求清理以后没有挡住这条目标行锁”，无法确定是业务服务 rollback，还是框架清理补做了回滚。即使历史 MySQL 记录为通过，也不能倒推服务边界已被独立验收。

当前脚本 `verify()` 走普通 CLI 时，在此处没有包住整段的外层 app context；`app.test_request_context()` 会建立并在退出时移除相应 app context。不能泛化为“任意 request context 退出都会移除已有外层 app context”，实际取决于上下文嵌套。

## 2. 根因、证据与结论准确性

### 2.1 已读取的真实清理链

1. Flask `ctx.py::RequestContext.pop`：本 request context 若创建过 app context，退出时调用其 pop。
2. Flask `AppContext.pop`：执行 appcontext teardown。
3. Flask-SQLAlchemy `extension.py::init_app`：注册 `_teardown_session`；该处理器执行 `self.session.remove()`。
4. SQLAlchemy `orm/scoping.py::scoped_session.remove`：先 close 当前 Session，再清空 registry；文档明确事务资源会回滚。
5. SQLAlchemy `orm/session.py::_close_impl` 与 `SessionTransaction.close`：结束当前事务并释放持有的连接资源。

当前环境已核实为 Flask 2.3.3、Flask-SQLAlchemy 3.1.1、SQLAlchemy 2.0.36、PyMySQL 1.1.2。上述源码来自当前 .venv-py311，不以其他框架版本的印象替代。

InnoDB 的 FOR UPDATE 锁随事务提交或回滚释放；默认锁等待超时通常只回滚等待语句，因此探针自身在超时后也必须显式结束事务。依据：[MySQL 8.0 Locking Reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)、[InnoDB Error Handling](https://dev.mysql.com/doc/refman/8.0/en/innodb-error-handling.html)。

### 2.2 本轮正常/变异对照

使用现有 `TestUserEditChangeSet` 的内存 SQLite fixture：原始花名为 old，先提交 concurrent，再请求 requested，稳定触发 CONFLICT。仅在诊断进程中 patch 当例 concrete Session 的 rollback，正常组执行两次；变异组执行入口首次回滚、故意跳过冲突分支第二次回滚。未修改仓库实现文件。

| 观察 | 正常实现 | 省略终态回滚 |
| --- | --- | --- |
| outcome | conflict | conflict |
| 服务返回后、上下文退出前 in\_transaction | false | true |
| 上下文退出后 in\_transaction | false | false |
| 最终存储花名 | concurrent | concurrent |

[完整诊断输出](../qa/evidence/rbac-lock-release-2026-10-29/sqlite-lifecycle.json)。这个结果直接证明 Session 生命周期掩盖了差异；SQLite 不提供此处所需的 MySQL 行锁语义，因此**不能声称已经运行“省略回滚时 MySQL 探针仍绿”的物理锁实验**。该 MySQL 因果链有源码与 InnoDB 事务语义依据，但真实控制实验仍是实施验收项。

现有服务的资料/授权 CONFLICT、ALREADY\_APPLIED、锁后 FAILED 均有显式 rollback，本轮没有发现生产锁泄漏。正常 Web teardown 仍是有效的最终资源保护；本问题是该保护掩盖服务自身回归，不是框架清理错误。

### 2.3 为何会形成盲点

测试将“完整请求结束后资源释放”与“服务自己在返回前释放资源”当成同一个不变量；fixture 清理被放在了观察之前。用例还只测试正确实现，没有证明把关键 rollback 删除后它会变红。行为层根因是选择了容易观察的最终干净状态，没有控制观察点之前可能代劳的框架行为。

## 3. 对原建议的合理性和专业性评估

| 原建议/备选 | 专业判断 | 取舍 |
| --- | --- | --- |
| 把探针移进原 context | 必要且方向正确，单独实施仍不完整。 | 若探针复用 writer 连接、查询不存在的行、使用普通 SELECT 或自动提交语义不当，仍可能假通过。 |
| 只 assert rollback 被调用 | 适合辅助观测，不能作为主要验收。 | 服务入口已有一次 rollback；次数或字符串断言不能证明终态执行。将来等价的事务上下文退出也可能合法。 |
| 只 assert Session.in\_transaction() 为 false | 适合非提交终态的快速守卫，不能替代 MySQL。 | 它描述 ORM 逻辑事务，不直接证明数据库行锁与连接独立性；UPDATED 还可能因 commit 后 ORM 读取启动新的只读事务，不能机械套用于所有结果。 |
| 用 Performance Schema 作为主要判据 | 可诊断，当前不优先。 | 引入额外权限与 MySQL 版本依赖；独立连接锁定同一行即可验证本契约。 |
| 依赖 NOWAIT 或 SKIP LOCKED | 本方案不采用。 | NOWAIT 会增加版本/错误码分支；SKIP LOCKED 可能跳过目标，若不验行数就假通过。沿用现有有界锁等待更小。 |
| 立即改生产事务框架 | 缺乏必要性。 | 当前服务已有正确 rollback，先增强测试敏感性；如果新验收发现真实缺陷，再另行设计修复。 |

**结论：**采用“同上下文观察 + 真实独立连接 + 校准/变异 + 业务零副作用断言”专业且适度。优先级是保护已有事务契约，既不夸大生产风险，也不以测试绿色替代测试有效性。

## 4. 推荐方案与可验证不变量

### 4.1 保留原上下文，观察后才清理

每个场景使用独立 fixture 和 concrete Session。服务返回后先取其内存事务状态，再执行 probe；两者完成之前不得退出原 request/app context，不得 close/remove/额外 rollback/commit，也不得通过 writer ORM 查询业务事实。查询 ORM 可能 autobegin 干扰观察。持久化验证放在探针结束之后，用独立连接或新上下文完成。

```
预留 probe 连接、设置会话级等待超时
建立 writer request/app context，准备并提交 fixture
绑定当例 concrete Session 的只读观察器
调用 update_user_management
记录服务结果与当前 Session 内存事务状态
在原 context 内通过 probe 请求同一已存在行的 FOR UPDATE 锁
记录探针返回、目标行数、连接身份与观察序列
完成判定以后 → 恢复 patch/事件 → 清理 probe → 结束 writer context
最后从独立读取核对业务/审计与授权副作用
```

普通非提交终态要求“事务未活跃 + probe 可锁定目标行 + 本次业务零变更”同时成立。若实现以后使用等价事务管理，不要求一定调用某个名字的方法；要求行为不变量成立。COMMIT\_UNKNOWN 的真实断链处置另有范围，见 §6。

### 4.2 独立连接与可命中的行

probe 在服务调用前从 engine 预留并持续持有连接，避免服务回滚归还连接后被顺序复用；writer 必须使用另一个物理连接。probe 与 writer 的 CONNECTION\_ID 不同，连接 ID 的含义依据[MySQL Information Functions](https://dev.mysql.com/doc/refman/8.0/en/information-functions.html#function_connection-id)。不修改 pseudo\_thread\_id。

writer ID 建议由仅绑定该 concrete Session 的 SQLAlchemy `after_begin` 事件获取；在事件中用参数所给 Connection 执行只读标识查询，不用 Session 递归发 SQL。不得在服务返回后调用 Session.connection 或额外 SELECT 来获取 ID，从而新建一个待测事务。probe 在整个场景内不回池；缺少 writer ID、ID 相同或未执行持锁 SQL，场景失败。

探针表与列使用脚本内部固定白名单：rbac\_users.id、user\_groups.id、resource\_groups.id；参数仅含本轮已提交 fixture 的主键。逐个探测当前分支确实锁过的已存在 actor/target 用户行、关系行和请求资源组行。每次 FOR UPDATE 必须返回精确目标行，空结果不算“锁已释放”。该验证不声称覆盖所有范围锁、间隙锁和任意其他事务资源。

### 4.3 判据、超时与清理

沿用 probe 会话级 `innodb_lock_wait_timeout=1`，显式开启探针事务。正常场景必须锁查询成功且返回指定行；负向控制只将 MySQL 原始错误码1205视为预期阻塞，其他错误（包括权限、断连、1213死锁）均失败。不要把所有 OperationalError 都解释成“发现锁”。超时后仍需显式 rollback。

移除“总 wall-clock 小于1秒”作为正确性条件：当前计时还包含取连接、设置变量等成本，主机暂停也会导致误报。耗时单独记录，数据库锁等待结果作行为判据。PyMySQL 的连接/读写超时在测试专用 engine 中设定有界值（建议连接5秒、读写5秒），避免基础设施故障无限等待；不改生产 engine。SQL 超时与网络超时不混为一类。

probe 的等待变量在使用前记录，finally 恢复后再回池；每次探针事务显式 rollback，异常恢复失败则丢弃测试连接而不是带着污染状态回池。writer 必须在证据采集后 finally 调用原始清理能力；变异 patch 先恢复再清理。测试进程异常时也保留专用库，无 DROP/TRUNCATE/全表清空，不增加 kill 其他会话或全局参数权限。

### 4.4 两类控制实验，证明测试能拒绝错误

1. **探针校准：**在同一专用库对存在行明确取得 FOR UPDATE 锁，保持 holder context/事务存活，独立 probe 必须得到1205；holder 显式 rollback 后，同样探针必须成功。InnoDB 引擎、正确主键、事务方式和独立连接任何一项配置错误，校准都不能算通过。
2. **服务变异：**在 CONFLICT、ALREADY\_APPLIED 和一个锁后 FAILED 场景分别省略当例的终态 rollback。仅在锁 SQL 已成功执行后武装，保留服务入口的首次 rollback；命中次数必须精确一次。返回时事务应仍活跃，probe应1205，正式正常判据应拒绝；恢复原方法、原始 rollback后应重新可锁。
3. **旧盲点对照：**至少一个 CONFLICT 变异场景完成“teardown前 probe阻塞 → 清理后 probe成功”的真实 MySQL演练。后者仅作诊断，不能代替前者的正式判定。相同 outcome 和最终业务值不变，依然必须识别锁边界缺失。

测试变异只在独立验收进程内使用 unittest.mock 和局部事件观察，不编辑服务源文件，不增加路由或生产配置开关。若代码重构后无法确认终态省略确实命中，应让校准失败，重新核对绑定方式，不能静默跳过负向控制。

## 5. 终态与资源验收矩阵

| 场景 | 准备与预期 | 同 context 的观察 | 副作用与控制 |
| --- | --- | --- | --- |
| 资料 CONFLICT | T0旧花名；数据库已为另一个值；请求第三值。 | actor/target、已锁关系和所选资源组可被独立连接锁定，原Session无活动事务。 | 保留并发值，零成功审计/授权变化；有省略rollback负向控制。 |
| 授权 CONFLICT | 角色/完整组已发生非等价并发变化。 | 探测本分支实际锁定的现存资源。 | 不部分保存、范围外组不恢复旧值；事务已结束。 |
| ALREADY\_APPLIED | 页面有意图，当前值已等于请求值。 | 锁定后等价退出仍需清理；不能把页面no-op拿来代替。 | 零DML/写commit/审计/Token/auth\_version副作用；有变异控制。 |
| 锁后 FAILED：actor权限撤销/target停用 | 直接服务调用，在读取并锁定用户行后拒绝。 | actor/target用户行可锁；不要求尚未执行分支的组锁证据。 | 零业务写/成功审计；证明是锁后拒绝。 |
| 锁后 FAILED：editor\_scope变化 | 准备T0后改变actor可编辑范围。 | 用户行、已经读取的关系行可锁。 | 不授予或删除任何目标组。 |
| 锁后 FAILED：清空理由缺失 | 直接服务调用，清空邮箱但无理由；不会被路由前置校验短路。 | 完整只读锁区经过后失败，现存目标行/关系/资源组可锁。 | 邮箱不清空；有省略rollback负向控制。 |
| flush后失败 | 测试进程先调用原flush，使业务与审计DML真实入事务，再受控抛错。 | 服务正常回滚后独立探针可锁。 | 独立读确认标量/关系/auth\_version/Token与审计均无残留；不把仅mock成“未执行SQL即失败”当成已写事务回滚实证。 |
| UPDATED基线 | 一次正常资料保存。 | 已提交的写锁可获得；不机械要求commit后绝无新的只读事务。 | 一次业务+成功审计；作为未破坏原有脚本功能的回归。 |
| 写前无效/NO\_CHANGE | 保持现有内存/路由测试。 | 这些路径本来不获取写锁，不能冒充锁后终态测试。 | 继续零业务写，不扩大本专项。 |

early FAILED只能承诺其已经执行的锁集；查询未命中的行、未执行的分支不伪造覆盖。上述正常终态均保留服务原结果，不以测试要求改变生产响应。

## 9. 风险、回退与预防

- **测试自己持锁：**probe每次取得锁后立即回滚，控制实验中1205也显式回滚；finally总能恢复writer。运行超时或清理不确定则失败，不继续下一场景。
- **连接复用假独立：**先预留probe并比较物理ID；不能仅比较两个Python对象。源ID观察器不在返回后重新经Session取连接。
- **负向变异污染后续：**仅patch当例具体Session，不patch全局scoped\_session/所有worker；恢复原方法和事件后才清理；每例独立fixture。不增加生产跳过回滚的配置键。
- **超时误报：**DB行为判据与耗时分开；探针网络故障不是锁证据。移除严格亚秒wall-clock断言，不通过延长无界sleep掩盖故障。
- **自动清理再次越过观察：**永久用例固定service\_return→probe\_complete→cleanup顺序；正常与省略回滚控制成对运行。
- **回退：**只撤销测试脚本/守卫增强，不改生产事务；保留已建立的专用空库隔离。回退时F1恢复开放，不能保留“已关闭”状态。

**预防落点：**拟新增 `tests/test_user_edit_lock_release_guard.py` 固定生命周期顺序和省略终态rollback的敏感性；现有MySQL脚本固定正负校准与同context观察。验证命令见§8，新增措施直接针对“fixture清理代劳、正确实现单向自证”的根因。

实施后在 `doc/postmortem/` 记录Bug定位、行为根因、旧测试漏洞、最小测试修复、防护用例、同类验收脚本排查和上述预防方案。纯测试能力增强原则上不宣称用户可感知功能变更，也不编造API Breaking Change。
