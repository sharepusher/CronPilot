2. 当前发现与处理优先级

F1 · P2（验收质量）· 锁释放探针受到上下文自动清理干扰

定位：scripts/verify_user_edit_transaction_mysql.py:175–197。冲突服务调用位于 request context 内，第二连接的锁探针却在该上下文退出之后。当前 Flask-SQLAlchemy 在 app context teardown 中执行 session.remove()；Session 关闭会结束未提交事务。因此，服务遗漏显式 rollback 时，后置探针仍可能通过，无法证明“服务返回即释放锁”。本轮已读取当前环境 flask_sqlalchemy/extension.py::_teardown_session 确认这一生命周期。

实证：使用现有内存 fixture，临时拦截 rollback，仅放行服务写边界的首次 rollback、跳过冲突返回前 rollback。未修改仓库代码；输出如下。SQLite 实验只证明事务被 teardown 清理，不冒称真实 MySQL 行锁复现。

outcome=conflict
transaction_active_before_context_exit=True
transaction_active_after_context_exit=False

当前产品判断：服务的冲突、already_applied 和锁内拒绝分支目前显式 rollback，未发现本次实现实际遗留锁。缺口在防退化能力，不能据此把产品升级为 P1 锁泄漏事故。

建议验收标准：让独立连接在原 request/app context 仍存活、服务已返回时尝试锁定同一目标；使用有界等待并覆盖 CONFLICT、ALREADY_APPLIED 和代表性锁后 FAILED。加入反向变异实验：故意屏蔽对应 rollback 时探针必须失败；恢复时通过。正式修改脚本前仍遵循仓库设计确认流程。

F2 · P2（完成度）· 七种结果状态尚缺完整、可重放的浏览器证据

定位：父设计 §9 的 U3 验收明确列出 CONFIRM_REQUIRED、UPDATED、NO_CHANGE、ALREADY_APPLIED、CONFLICT、FAILED、COMMIT_UNKNOWN。现有 P1/P2/R5 的 results.json、截图和 validation.txt 能支持正常保存、no-op、清空确认、冲突、组选项和越权拒绝，但未找到 ALREADY_APPLIED 与 COMMIT_UNKNOWN 在目标角色浏览器中的逐场景、可重放证据。相关单元测试覆盖服务/路由语义，不等于浏览器 outcome 事件、按钮恢复、留页和提示均已验证。

复现性限制：永久 verify_user_edit_group_preflight.py 运行真实模板 JS/jQuery，但使用隔离 DOM 并替换 Ajax transport，只能证明 18 个提交前判断场景。它不能替代登录、真实 POST、响应处理、导航和数据库审计一致性的全流程。live JSON/截图是有价值的执行记录，但没有仓库内可直接重跑的完整 live harness。

建议验收标准：保留目标角色登录流程和七状态测试驱动，记录触发方式、响应、页面提示/URL、按钮可再次使用、业务 POST 次数与数据库/成功审计副作用。COMMIT_UNKNOWN 的故障注入仅用于隔离测试服务，分别说明“提交前失败”与“提交已完成但确认丢失”的证据边界。补齐之前宜写“主要功能已验证，七状态浏览器矩阵待补”，不写“全部验收闭环”。

F3 · P3（方案准确性）· 锁成本描述没有覆盖管理员降权分支

定位：父设计 §7 一方面说明降权锁定启用 admin，另一方面又把真正写入的成本概括为仅涉及两个用户。实际 services.py:985–999 在潜在管理员降权时将所有启用 admin 纳入锁定查询；:1024 附近还读取并锁定 actor 和 target 的关系行。普通资料编辑与降权路径成本不同。

影响与建议：当前低并发管理场景没有已证实的性能故障；应把固定成本表述限定为普通路径，说明降权与启用管理员数量相关。不要为修正文案而立即重构锁协议。此偏差在初评中已被提示，当前仍可见。

4. 核心实现核对结果

  • 原始快照连续：只有 GET 建立基线；可恢复 POST 保留收到的已验签 token，错误回显分离 form_values 与 ORM。无效 token 不提供悄悄重新签发的可提交表单。P1 的关键错误已消除。
  • 完整事实与可编辑投影：v2 token 包含 editor_scope 与完整目标组；前后端意图使用同一投影，锁内重新验证当前范围。A 管理员编辑 A+B 用户不会把未展示的 B 误当删除意图。
  • 只写有效差异：资料字段独立比较；资料-only 不写关系表、不改角色、不 bump/重签/失效缓存。真实授权变更仍对完整 role+group_ids 做耦合三方比较，并保留范围外绑定。新增 SQL 监听断言比只看最终值更有效。
  • 并发与授权：写边界先结束路由只读事务，再重读并锁定 actor/target、组关系和选中组；拒绝失活 actor、无权 actor、陈旧范围、停用 target 和非等价并发。SQLite 功能测试与 MySQL 锁语义不能互相替代。
  • 业务/审计原子性：成功审计直接加入同一 Session 后 flush/commit，避免调用会独立提交的 write_audit_log。实际差异白名单决定审计内容；凭据值不入快照/detail。flush 与 commit 异常分阶段表达，后者保守返回结果未知。
  • 页面与兼容：状态只读、邮箱清空确认与必填理由、取消零提交、原生回退、动态字段唯一性、组选择和留页结果均有相应实现。公共 Ajax 以事件扩展，默认行为继续兼容。模板安全转义，无 Bootstrap modal 新引入。
  • 审计 reader：版本、顶层、changes 白名单、值形状与清空理由整条验证；坏记录不部分猜测展示。历史合法字符串不套用当前业务枚举二次判死，兼顾兼容性。
  • 验收库隔离：MySQL URL/专用库名、实际 schema、空表与空视图检查、固定四表非幂等创建、失败不 DML、无 drop_all，均有防护。专用库名不等于所有权证明，仍应使用专用 schema 权限。

5. 边界、专业取舍与维护风险

授权策略边界：既有管理员 Scope 设计 §3.5/§3.6 允许有组交集的管理员编辑目标角色；角色属于用户全局字段。因此“保留范围外组”保证关系不被误删，不代表实现了按组分别授予角色。R5 沿用此策略，不能擅自把现有管理员操作认定为越权并收紧权限。若未来需要每组独立角色，属于新的权限模型设计。

兼容性：旧 v1 编辑 token 必须刷新；审计历史 detail 原文不迁移，严格 reader 改变部分坏记录的展示。无数据库列变更、依赖 pin 变更或 app/api 字段变更。此次是管理页 JSON 结果扩展，不应误报公共 API Breaking Change。

残余边界：签名 token 不设 TTL 是已明确的设计取舍，三方值比较不提供每次历史变更的版本追踪；缓存失效仅当前 worker，不能据此宣称全 worker 强一致；原子成功审计目前只覆盖本编辑入口，不能推广为密码、Token、停用、创建和审批全部同事务。横向风险审计仍应按各入口另立设计。

维护性：当前服务函数较长，但立即拆分可能扰动 Session 和锁边界。后续若重构，应先保护“无变化零写、错误回显同基线、终态释放事务、授权变化一次副作用”等可观测不变量，再提取纯策略。文档数量丰富有助溯源，也带来状态判断成本；建议保留历史、让最新评估成为统一入口，源设计数值和细节仍只在源文档维护。

发布治理：信任根文档将所有者风险接受与技术保护分开，表述较此前清楚。本轮没有远端认证证据，不能宣称 branch/tag ruleset 或 Environment 已配置；也不将明确接受的单维护者治理风险重新包装为本次产品阻断项。
