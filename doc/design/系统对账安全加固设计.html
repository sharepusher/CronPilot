系统对账安全加固设计

编号：OPT-P0-18   版本：rev.3   日期：2026-09-02

关联：app/crons.py::cron_check()、app/services/cron_service.py::apply_retire()

1. 问题

1.1 现状

cron_check() 定时扫描 cron_infos 与 apscheduler_jobs 的差异，若发现 cron_infos 中存在但 apscheduler_jobs 中不存在的任务（孤儿），直接调用 apply_retire() 将其永久下线（status = -1，不可恢复）。

1.2 预期

对账仅负责检测异常并告警，不执行任何不可逆操作。孤儿任务的处置由管理员通过 Web UI 手动决策。

1.3 风险事件（真实案例）

2026-09 事件：因 conf.ini 数据库 URL 配置错误（sqlite:///:memory:），APScheduler 的 JobStore 指向了临时数据库。服务重启后 apscheduler_jobs 为空，cron_check() 将全部 9 个任务自动下线。管理员在浏览器验收时才发现所有任务状态异常。

2. 根因

根因描述
检测与修复耦合 cron_check 将"发现异常"和"执行修复"合并在同一函数中，违反了 Alerting ≠ Remediation 原则
无批量保护 无论孤儿数量占比多大，都逐个执行 apply_retire，无熔断机制
不区分场景 JobStore 完全为空（配置错误/迁移中）与个别任务孤立是完全不同的场景，但代码一视同仁
不可逆操作无确认 下线操作在 CronPilot 中不可恢复，但对账自动执行此操作无需人工确认

3. 行业对照

维度CronPilot 当前KubernetesAirflow行业最佳实践
孤儿处理 自动下线（不可逆） 标记 Suspended（可恢复） 标记 deactivated（可恢复） 检测 → 告警 → 人工决策
批量保护 无 Pod Disruption Budget 无批量操作 熔断阈值 + 告警
告警机制 操作日志（被动） Event + Metrics Alert Rules 结构化日志 + Metrics + Webhook

4. 方案

4.1 核心原则

对账只做两件事：检测异常 + 发出告警。绝不自动执行下线等不可逆操作。

4.2 五步模型：检测 → 标记 → 告警 → 展示 → 人工决策

步骤职责实现
1. 检测 定时扫描 cron_infos vs apscheduler_jobs 差异 保留 cron_check() 的扫描逻辑
2. 标记 将孤儿任务标记为"待确认"状态 设置 job_health.reconcile_flag = 'orphan'（或独立字段）
3. 告警 通过日志 + Metrics + 可选 Webhook 通知运维 logger.warning() + Prometheus cronpilot_orphan_tasks_total gauge
4. 展示 Dashboard 展示孤儿任务提醒 统计卡片增加"待确认"计数（或复用"持续异常"面板提示）
5. 人工决策 管理员通过 UI 逐任务处理：恢复调度 / 手动下线 / 标记已知 任务列表增加"孤儿"筛选 + 操作按钮

4.3 实现分批

Phase 1（最小可用 · 推荐立即实施）：移除自动下线 + 告警

  • 移除 cron_check() 中对 apply_retire() 的调用
  • 替换为 结构化日志 logger.warning("orphan_detected", ...)
  • 新增 Prometheus gauge cronpilot_orphan_tasks
  • 范围：仅改 app/crons.py + app/metrics.py
  • 验收：模拟孤儿场景（手动从 apscheduler_jobs 删除一条），确认日志告警但任务不下线

Phase 2（增强 · 后续迭代）：Dashboard 展示 + 人工操作入口

  • Dashboard 统计卡片增加"孤儿任务"计数
  • 任务列表增加 health='orphan' 筛选
  • 操作列增加"重新加载到调度器"/"确认下线"按钮

Phase 3（可选 · 长期演进）：Webhook 告警 + 自动恢复

  • Webhook 通知（微信/钉钉/邮件）
  • "自动恢复调度"选项（将任务重新 add_job 到 APScheduler，而非下线）

4.4 Phase 1 代码变更

# app/crons.py — cron_check() 修改前
for item in cifs:
    if "cron_%s" % item.id not in job_ids:
        if item.status == -1:
            continue
        apply_retire(item, RETIRE_REASON_ORPHAN, ...)  # ← 删除
        db.session.commit()                              # ← 删除
        record_operation(...)                            # ← 保留，改为 action='orphan_detected'

# app/crons.py — cron_check() 修改后
orphan_count = 0
for item in cifs:
    if "cron_%s" % item.id not in job_ids:
        if item.status == -1:
            continue
        orphan_count += 1
        current_app.logger.warning(
            "orphan task detected",
            extra={
                "event": "cron_check.orphan",
                "cron_id": item.id,
                "task_name": item.task_name,
                "status": item.status,
            },
        )
if orphan_count > 0:
    ORPHAN_TASKS.set(orphan_count)  # Prometheus gauge
    current_app.logger.warning(
        "reconciliation: %d orphan tasks detected, manual action required",
        orphan_count,
        extra={"event": "cron_check.orphan_summary", "count": orphan_count},
    )
else:
    ORPHAN_TASKS.set(0)

7. 风险

风险影响缓解
真正的孤儿任务不再自动下线 低：孤儿任务不占资源（APScheduler 中已不存在，不会触发回调）；但 Dashboard 统计可能包含 Phase 2 增加 UI 展示和操作入口
告警疲劳 中：如果长期不处理孤儿，每次 cron_check 都会重复告警 日志去重（仅首次和计数变化时告警）；Phase 2 增加"标记已知"操作

Phase 2 — Dashboard 孤儿任务展示与人工操作入口

P2.1 问题

Phase 1 移除了自动下线，改为日志告警。但管理员必须查看服务器日志才能发现孤儿任务。Web UI 中无任何提示，不符合"运维可观测性"原则。

P2.2 方案概述

在 Dashboard 和任务列表中增加孤儿任务的展示与操作能力，形成 「发现 → 告知 → 定位 → 处置」 的完整闭环。

维度变更交互方式
Dashboard 统计卡片 新增第 5 张卡片「调度异常」或将孤儿计数整合到「持续异常」卡片的 sub-text 点击卡片跳转到孤儿任务列表
Exception Panel 在 failing_tasks 面板上方增加「调度脱节」警告条 展示孤儿任务列表（名称 + 状态 + 最后执行时间）
任务列表筛选 健康维度增加 health='orphan' 筛选按钮 点击后列表仅展示孤儿任务
操作列 孤儿任务行增加「重新调度」和「确认下线」操作 AJAX 操作 + 确认对话框

P2.7 「重新调度」操作的技术设计

「重新调度」= 将任务重新 add_job 到 APScheduler：

# 后端 API: POST /api/cron/reschedule
def reschedule_task(cron_id):
    cif = db.session.get(CronInfos, cron_id)
    if not cif or cif.status == -1:
        return error("任务不存在或已下线")
    job_id = "cron_%s" % cif.id
    try:
        scheduler.get_job(job_id)
        return error("任务已在调度器中")
    except:
        pass
    # 根据 cron 表达式重新注册
    scheduler.add_job(
        func=cron_do, id=job_id,
        trigger=build_trigger(cif),
        args=[cif.id, cif.task_name, ...],
    )
    return success("已重新注册到调度器")

P2.8 数据流设计

核心问题：cron_check() 在后台线程运行，其发现的孤儿列表如何传递给 Dashboard 渲染？

方案描述优劣
A. 进程级缓存 cron_check 将孤儿 ID 列表写入模块级变量（类似 _overdue_cache）；Dashboard 读取 零额外查询；但多 worker 时各自独立（gevent 单进程无此问题）
B. 数据库字段 job_health 新增 orphan_since 列 持久化；多 worker 共享；但增加 schema 迁移
C. Dashboard 实时查询 Dashboard 每次加载时执行 cron_infos vs apscheduler_jobs 差集查询 数据始终最新；但增加页面延迟
推荐方案 A：与现有 _overdue_cache 模式一致（进程级 TTL 缓存）。CronPilot 使用 gevent 单进程模型，不存在多 worker 不一致问题。实现最简单，零额外查询。

P2.13 对账可观测性：频率与执行记录

P2.13.1 当前现状

维度现状可见性
对账频率 config.py 配置 minute='*/30'（每 30 分钟一次） 仅开发者可看代码
最后执行时间 无记录 ❌ 不可见
执行结果 Phase 1 后写入 logger.warning() 仅运维可看服务器日志

P2.13.4 超时检测逻辑

Dashboard 渲染时检查 _last_reconcile_time：

  • 若为 None（服务刚启动，对账尚未运行过）：显示「对账尚未完成」灰色提示
  • 若 now - _last_reconcile_time < 45 分钟：正常（绿色或紫色，取决于 orphan_count）
  • 若 now - _last_reconcile_time ≥ 45 分钟：超时告警（红色）— 说明 cron_check 可能因异常停止

阈值 45 分钟 = 30 分钟间隔 × 1.5 倍容差，避免因调度延迟误报。
