# RBAC 用户编辑并发覆盖与审计分裂 U2 修复复盘

日期：2026-10-29 · 状态：已修复并验证

## 1. Bug 定位

旧写服务只锁目标用户，信任路由已完成的 actor/Scope 判断，直接覆盖全部表单字段；业务先 commit，成功审计随后独立 commit。页面停留期间出现并发修改、actor 降权或审计失败时，可能覆盖新值、越过当前授权，或形成“业务成功但无成功审计”。收口复核还发现：冲突/失败分支曾把请求角色写回已持久化的 `User` ORM 实例，后续查询或提交存在 autoflush 被拒绝值的风险。

## 2. 根因

路由校验与写入之间缺少数据库当前事实的最终授权边界；服务没有原值，无法区分正常应用、等价完成和三值冲突；通用 `write_audit_log()` 自行 commit，使审计天然脱离业务事务。展示回填与持久化实体复用了同一对象，失败路径没有维持“不得再污染 Unit of Work”的边界。

## 3. 测试漏洞

原测试只验证最终字段和 `auth_version`，没有双连接行锁、original/current/requested 三方矩阵、actor 在写前降权、审计 flush 失败、commit 确认丢失、冲突后锁释放，以及路由冲突后数据库当前值保持不变的断言。

## 4. 修复

写服务现在结束路由只读事务后，按确定顺序锁定 actor/target、相关管理员、用户组关系和目标业务组；使用数据库当前权限与 Scope 再授权。资料字段独立三方比较，角色和组整体比较；只应用有效差异。成功审计实体与业务变化进入同一 Session、同一 flush/commit，授权副作用仅随真实授权差异触发。路由失败回显不再修改持久化 `User` 实例，消除失败路径的意外 dirty/autoflush 写入面。

## 5. 防护测试

`tests/test_user_edit_change_set.py` 固化 19 项专项契约，其中路由级冲突用例直接断言并发新值不被回填对象覆盖；`scripts/verify_user_edit_transaction_mysql.py` 使用真实 MySQL 双连接证明锁等待和冲突后及时释放。相关回归 106/106、Scope 回归 38/38、路由 86/86，浏览器正向和并发冲突反向均通过。

## 6. 同类排查

本轮只收口 `/rbac/users/edit`。密码、Token、停用、注册审批及其他编辑入口维持各自现有事务，不借本次修改扩大范围；同类风险继续由[独立风险审计](../qa/编辑与修改业务流程同类一致性风险审计-2026-10-28.html)跟踪。

## 7. 预防方案

- 写边界 API 强制接收 actor、target、original、requested 和 intent；路由调用签名由专项测试固定，禁止退回“调用方已授权”的隐式约定。
- 把真实 MySQL 双连接脚本落在 `scripts/verify_user_edit_transaction_mysql.py`；可用隔离数据库 URL 重现锁等待、冲突回滚和锁释放。
- 审计 detail 必须直接由 `effective_change_set` 五字段白名单构建；专项测试精确断言键集合并搜索密码、Token、Session、CSRF 零出现。
- 任何新增写终态必须明确属于 UPDATED、ALREADY\_APPLIED、CONFLICT、FAILED 或 COMMIT\_UNKNOWN，并具有相应的数据库和副作用断言。
- 失败或冲突后的表单回显不得修改持久化 ORM 实例；防护位置为 `tests/test_user_edit_change_set.py` 的路由冲突用例，必须同时断言响应提示、数据库当前值与审计行数。
