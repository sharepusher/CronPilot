执行记录标识符与术语统一设计

状态：待确认  |  作者：AI Agent  |  日期：2026-08-26

1. 问题

1.1 标识符命名歧义

当前执行记录系统中存在两个标识符，使用了容易混淆的命名：

现状数据源实际含义用户认知
列表页列头 "LOG ID" → 显示 18463 job_log.id（数据库自增主键） 数据库内部序号 "这是日志的 ID"
详情页标题 "执行 #ca04c15c" job_log.log_id UUID 前 8 位 跨系统追踪码 "这是什么？跟列表里的 18463 什么关系？"
详情页元数据 "Log ID" → 显示完整 UUID job_log.log_id 同上 "又一个 Log ID？跟上面哪个一样？"

核心问题：用户在列表看到 18463，点进详情后看到 #ca04c15c，两者之间没有任何可见关联。

1.2 代码层命名不一致

app/crons.py 中同一个值在 4 行内用了两个名字：

cronpilot_log_id = str(uuid.uuid1())    # 生成时叫 "log_id"
_ctx_trace_id.set(cronpilot_log_id)      # 设上下文时叫 "trace_id"

1.3 术语不准确

多处文档和代码注释使用"回调"（callback）描述 CronPilot 发起的定时请求。实际上 CronPilot 是主动发起方（trigger），不存在被动回调的语义。准确术语应为"定时触发"或"调度请求"。

"回调"出现在约 60+ 文件中，共 200+ 处引用。

2. 根因

  1. 早期设计未区分标识符用途：log_id 字段名暗示"日志的 ID"，但实际用途是跨系统追踪码（trace ID），与数据库主键 id 语义冲突。
  2. UI 列头 "LOG ID" 使用了数据库主键：列表页 "LOG ID" 展示 id（自增序号），详情页 "执行 #" 展示 log_id（UUID），从列表到详情的导航链路中标识符发生了无声切换。
  3. 外部协议参数命名传播：cronpilot_log_id 作为定时触发请求的参数名传递给目标服务，名称中的 "log" 进一步强化了歧义。
  4. 术语惯性：项目早期（xiaoniu_cron 时期）使用"回调"描述定时触发行为，后续文档沿用未更正。

3. 方案

3.1 标识符重命名（一步到位）

CronPilot 是开源项目，当前无已知外部集成方，可直接重命名而无需兼容过渡。

Model 属性 JobLogItems.log_id JobLogItems.trace_id 内部
Model 属性 JobHealth.last_run_log_id JobHealth.last_run_trace_id 内部
数据库列 job_log.log_id
job_log_items.log_id
job_health.last_run_log_id		 job_log.trace_id
job_log_items.trace_id
job_health.last_run_trace_id		 迁移

3.2 UI 标识符展示优化

页面元素旧展示新展示
执行记录列表 列头 LOG ID（显示 id） #（显示 id，行业惯例序号列标记）
执行记录详情 页面标题 执行 #ca04c15c（UUID 前 8 位） 执行记录 #18463（数字序号，与列表一致）
执行记录详情 面包屑 执行 #ca04c15c #18463
执行记录详情 元数据区 Log ID: a13114a8-... 追踪码 (Trace ID): a13114a8-...（可复制）
执行记录详情 浏览器标签 执行 #ca04c15c — CronPilot 执行记录 #18463 — CronPilot
v1 列表页 列头 log_id（显示 UUID） 追踪码（显示 UUID，与 redesign 元数据标签一致）
认知连贯性：用户在列表看到 #18463 → 点击 → 详情标题 执行记录 #18463。追踪码（UUID）作为开发者级信息，降至元数据区域单独标注。
⚠️ 实现安全边界：job_log.id（自增 PK，int 类型）绝对不改名。本次重命名仅涉及 log_id（UUID 追踪码，str 类型）→ trace_id。改名后 jl.id 仍是数字序号（18463），jl.trace_id 是 UUID 字符串（a13114a8-...），类型和名称完全不同，混淆风险为零。

3.3 术语修正

将用户可见的"回调"术语修正为"定时触发"。

位置旧文案新文案
任务表单提示 GET 时系统附加 query 参数 cronpilot_log_id / cronpilot_sign 定时触发时系统附加 query 参数 cronpilot_trace_id / cronpilot_sign
任务表单提示 系统仍会注入 cronpilot_log_id / cronpilot_sign 系统仍会注入 cronpilot_trace_id / cronpilot_sign
API Schema 描述 CronPilot 发给业务方的执行记录 ID CronPilot 定时触发时生成的追踪码 (UUID)
关于"回调"全量替换：项目中约 60+ 文件含"回调"一词（200+ 处），大多在架构文档和设计文档中。本次设计仅修正用户可见的模板文案和 API Schema 描述中的术语，文档层面的全量替换作为独立低优先级任务跟踪，避免 diff 膨胀。

7. 风险

风险概率影响缓解措施
SQLite ALTER TABLE RENAME COLUMN 需要 3.25.0+（2018-09-15） 低 中 Python 3.8+ 内置 SQLite 均 ≥ 3.25；迁移脚本增加版本检查
MySQL ALTER TABLE CHANGE COLUMN 对大表加锁 中 中 job_log 表可能较大；文档提示在低峰期执行迁移脚本
签名算法中参数名变更导致旧签名失效 确定 低（无已知外部集成） RELEASE_NOTES 标注 ⚠️ API Breaking Change
漏改某处引用导致运行时 AttributeError 中 高 全量测试 + rg 旧名残留检查 + import smoke test
⚠️ API Breaking Change：定时触发参数名从 cronpilot_log_id 改为 cronpilot_trace_id，签名计算随之变化。已部署的目标服务如有验签逻辑，需同步更新参数名。POST /api/cron/add_log 接口入参名同步变更。
