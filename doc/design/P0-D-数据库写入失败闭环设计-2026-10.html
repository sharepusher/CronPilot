1. 问题与根因

app/rbac/views.py 的 users_edit 先更新用户及组，再保存资料字段；资料 commit 异常时只记录日志和 rollback，仍沿用此前成功 result。最终 _users_form_response 接收到 true，可能误报整体成功。现阶段未对 update_user/set_user_groups 内部事务边界作完整冻结，不能假定一次 rollback 能撤销全部操作。

2. 方案与范围

第一切片只修复成功判定及错误传播：资料提交异常必须返回整体未完成；所有输入尽可能预检，错误摘要不含数据库异常。明确区分“确定失败”“已有阶段提交”“提交结果未知”。只有所有要求的阶段确认成功才返回整体成功；若此前阶段已提交，提示“操作未全部完成，请核实当前信息”，不得声称全部回滚。保留原有响应适配器、权限与成功路径，不依赖新增 JSON 字段。

审计必须与事实一致：已提交子阶段可以保留其真实审计，不能冒充整体成功；失败审计写入也可能失败，不能以再次写库必成功为前提。整体事务合并或补偿属于后续另行详设，不在此切片自动扩展。

3. 分批

D-0：读出所有 service commit/rollback、审计写入点及 _users_form_response 分支，冻结阶段矩阵和原生/Ajax 当前响应截图；D-1：确认后实施首个用户编辑失败闭环；D-2：扫描其余人工数据库写入入口，逐项登记并确认切片。D-0 中发现无法区分提交结果时，先定义核实路径，不伪造原子性。

4. Before / After 行为对比

BEFORE（源码推导，截图待 D-0）：资料 commit 异常后仍传 result['ok']=true，可能成功跳转。AFTER：已确认异常返回未完成，留在既有表单失败呈现路径；已有提交如实说明；成功路径保持现有呈现。此为行为示意，D-0 必须补同一真实页面、目标角色、字段与成功/失败截图，确认前不得实施页面改动。

5. 验收

D-01：注入资料提交失败，断言最终适配器收到 false；Ajax 无成功字段/跳转，原生 POST 无成功提示。D-02：分别注入前置阶段失败、资料失败、提交结果未知，数据库实际值与提示/审计一致。D-03：正常成功与权限/CSRF 拒绝基线保持，拒绝无写入。D-04：日志脱敏且后续审计失败不覆盖主错误。拟新增 tests/test_user_edit_write_failure.py，命令 python -m unittest tests.test_user_edit_write_failure -v，使用内存数据库；当前未创建/运行。浏览器按填写→提交→失败/成功逐条截图留证。

6. 风险与关闭条件

失败响应不能恢复已提交数据，回滚代码版本也不能撤销历史业务变更；重试前必须核实状态。首切片通过不代表所有写入口完成；D-2 清单中每个已发现同类错误都须有处置和验收。P0-D 与其他 P0 分别关闭，不能以 P1 信封延期为由延期此错误修复。
