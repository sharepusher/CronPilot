1. 问题、根因、目标与范围

1.1 P0 问题与已验证根因

  • P0-1，失败响应无法关联排查：现有 json_response、web_api_return、api_return 主要返回 errcode/errmsg。请求入口虽已设置 g.trace_id 和日志 ContextVar，但响应尚未稳定返回该值；另有 APIFlask 校验处理器、HTML 404/500、CSRF/鉴权装饰器等独立出口。
  • P0-2，写入失败后仍可能呈现成功：部分路径 rollback 后未把失败状态传回响应。例如用户编辑页的资料字段 commit 异常后仍可能沿用此前成功的 result；任务创建、编辑的 DB 提交与 scheduler 副作用也没有统一失败状态机。

1.2 目标

使每个纳入范围的人工写操作在失败时具备：可由安全的 trace_id 关联、稳定分类的错误码、不会误入成功分支、不会向浏览器/通知/业务日志泄漏凭据，并且在 scheduler 失败时拥有可恢复的最终一致性状态。

1.3 范围与非范围

纳入 P0明确不在 P0 首期完成
登记范围内的 Web Ajax/普通 POST/内部 API 写入口及其 APIFlask 校验、CSRF、鉴权失败；任务/RBAC 写入与 scheduler 失败闭环；以及这些入口和后台执行路径写入的 job_log、operation detail、应用日志、Webhook/IM 通知等敏感输出 sink 脱敏。改变既有 API HTTP 状态语义（P0-A-lite 对缺失/非法 request_id 的协议 400 除外）；把错误信封强加到 OpenAPI、metrics、下载、下游服务请求等非登记 JSON；重写后台任务的业务响应；建设集中式日志平台；向客户端返回原始 exception/traceback。

2. 历史分层契约（已迁入子方案）

确认决议：P0-A-lite 只适用于 API Blueprint 业务 API、纯 JSON 管理端端点与显式登记的 partial=1 GET JSON 模式。X-Request-Id 为必填 UUID v4 Header；缺失、非 UUID v4 或同一个请求含多个值，在 Flask 完成路由匹配和协议分类后、应用鉴权/CSRF/view/业务副作用前返回 HTTP 400。合法值在该次 required 请求进入 Flask after_request 的应用响应（含 2xx、3xx、4xx、5xx）中原样回传，并写入受控结构化 HTTP 日志的 request_id；代理/网关在请求到达 Flask 前自行拒绝、或 Flask 无法形成响应对象的进程级失败，不承诺该 Header。scheduler 使用独立 execution_trace_id；手动执行期间两个字段同时存在且互不覆盖。管理端只对登记为 required 的异步请求生成 UUID v4；正常 HTML、原生 form 与双模式 POST 不注入、不读取、不生成、不回传该 Header。不得通过 Accept、Session、Token、X-Requested-With、响应状态或 Header 是否存在猜测协议模式。完整 JSON v1 错误信封移至后续 P0-A2；lite 仅增加协议级稳定错误码 REQUEST_ID_INVALID。

2.1 P0-A-lite：来源感知的 request_id、请求—响应关联与日志传播

问题与根因：当前请求钩子对所有 HTTP 请求直接接受来访 X-Request-Id，缺失时自动生成 UUID，并写入 g.trace_id 与共享 logging ContextVar；它既没有输入校验，也没有响应回传、协议模式分类或显式生命周期恢复。scheduler 又复用同一 ContextVar 表达执行 trace，导致 HTTP request_id 与后台 execution trace 的语义耦合。

范围：改 API Blueprint、纯 JSON 管理端端点与显式登记的 partial=1 GET JSON 模式的 request_id 校验/响应传播、登记范围内的前端生成点、HTTP/scheduler 双 ID 日志模型、完整 ContextVar 生命周期、OpenAPI/Swagger Header 契约及专项测试。HTML 文档导航、普通页面 GET、链接点击、原生 form，以及同一 POST 的原生 form/Ajax 双模式明确不在范围内；无数据库迁移、无 JSON body/query 字段、无正常业务 HTTP status 变化（入口协议 400 除外）。

唯一行为契约：对任一已登记 API 或管理 JSON 模式，调用方必须提供符合 ^[0-9A-Fa-f]{8}-[0-9A-Fa-f]{4}-4[0-9A-Fa-f]{3}-[89AaBb][0-9A-Fa-f]{3}-[0-9A-Fa-f]{12}$ 的 UUID v4；使用完整匹配，长度固定为 36，前后空白、逗号和多值均非法，字母大小写均可，合法值按原文回传。服务端将合法值写入 g.trace_id、HTTP ContextVar、受控结构化日志 request_id 和响应 X-Request-Id；服务端不查询或拒绝历史重复值。缺失、格式非法或多值在路由匹配/分类之后、应用鉴权/CSRF/view/DB/scheduler/外部副作用之前返回 400，不生成替代 ID、不回显原文、不返回响应 Header。scheduler 每次执行另行生成 UUID v4 execution_trace_id，继续通过既有 cronpilot_trace_id 关联 JobLog；手动执行时 request_id 与 execution_trace_id 同时存在。request_id 不是鉴权、幂等、JobLog trace 或业务主键；P0-A-lite 不新增业务数据库 request_id 列，不把它加入正常 JSON body，但允许写入访问受控、按保留策略管理的结构化应用日志。

2.1.1 实施步骤与责任边界

  1. 协议模式登记与校验顺序：实现前冻结“endpoint + method + URL + Blueprint + 显式模式 + 调用位置 + 分类 + 生成点 + 缓存/OpenAPI 要求 + 测试 ID”机器登记表。分类键固定为 endpoint + method + 显式模式。API Blueprint 业务 GET/POST 为 API_REQUIRED；纯 JSON 管理端点和已定义 partial=1 的 GET 模式为 MANAGEMENT_JSON_REQUIRED；普通 SSR 为 SSR_EXEMPT；只有业务响应本身同时支持原生 form 与 JSON 的 POST 才是 DUAL_POST_EXEMPT。应用内顺序固定为：代理/服务器 HTTP 解析 → Flask 路由匹配 → endpoint/method/mode 分类 → request_id 校验 → 应用鉴权 → CSRF → schema/view → 副作用。自动 HEAD/OPTIONS、Swagger/OpenAPI、static、metrics、文档、未匹配 URL 的 404 与方法不匹配 405 均豁免；已匹配 required endpoint 内部产生的 302/401/403/404/422/500 仍遵循 required 契约。不能因端点可能触发登录重定向就把它改为豁免。
  2. 响应传播与精确 400：after_request 只依据“本请求分类为 required 且已经验证成功”的状态回传同值 Header，不依据 status、Content-Type 或是否重定向。真值表固定为：required + valid → 进入 Flask after_request 的应用 2xx、302、业务 400、401、403、404、422、500 均回传；required + missing/invalid/multiple → request-id 协议 400 且不回传；exempt → 不新增 Header；代理/网关提前拒绝或进程级失败 → 由该层定义响应，不能冒充 Flask 契约。API Blueprint 的协议 400 body 固定为 {"errcode":1,"code":"REQUEST_ID_INVALID","errmsg":"X-Request-Id 缺失或格式不符合 UUID v4 要求","data":null,"result":null}；管理端 JSON 固定为 {"errcode":1,"code":"REQUEST_ID_INVALID","errmsg":"X-Request-Id 缺失或格式不符合 UUID v4 要求","result":null,"url":null}。稳定 code 用于区分已有业务 400（例如 POST /api/cron 的 scope 错误）；对外只公开这一协议码，内部日志可记录 missing/invalid_format/multiple_values，但不记录原始非法值。使用独立入口响应函数，避免扩大公共 helper；该加法字段须在实施时按 API 返回结构变更规范在 Release Notes 标注 ⚠️ API Breaking Change。
  3. 管理页面受控请求：公共 jQuery 工具仅在调用点或表单显式设置 requestIdRequired: true 时注入 Header；js-ajax-form 通过表单标记启用，fetch() 走 required-JSON wrapper，直接 XMLHttpRequest 使用同一生成工具。直接 $.post()（包括 dashboard 的 POST /cron_retire）改为共享 JSON POST 封装或显式 $.ajax，不得依赖无法携带选项的快捷调用。真正双模式 POST 不设置标记。优先使用安全上下文中的 crypto.randomUUID()；不支持时仅可用 crypto.getRandomValues() 构造 UUID v4，禁止 Math.random()。每次重试生成新值；禁止 hidden input，也不得仅凭存在全局 ajaxSetup() 宣称覆盖完成。
  4. 调度执行与双 ID 日志：scheduler 每次 cron_do 生成独立 UUID v4 execution trace，并通过既有 cronpilot_trace_id 关联 JobLog。结构化日志新增规范字段 request_id 与 execution_trace_id：定时执行前者为空；HTTP 手动执行期间两者同时存在；响应只回传 request_id。兼容字段 trace_id 暂按 execution_trace_id or request_id 输出，新实现不得依赖其识别语义。P0-A-lite 不新增 JobLog request_id 列，也不把 HTTP request_id 传播为被触发下游请求的 Header。
  5. 内部 API 文档：使用 APIFlask 2.4 的全局 spec_processor 为每个业务 operation 注入同一 OpenAPI 参数组件：name: X-Request-Id、in: header、required: true、schema: string、format: uuid 及 UUID v4 pattern。响应文档明确区分：来自已验证请求的所有已声明响应均包含同值 response Header；request-id 协议 400 响应不含该 Header且 body 含 code=REQUEST_ID_INVALID；既有业务 400 仍属于已验证请求并回传 Header。不得以 body 字段或 APIFlask input(..., location='headers') 取代该文档注入。
  6. ContextVar 生命周期：HTTP 使用 _ctx_http_request_id；scheduler 使用 execution trace、cron_id、task_name、duration_ms、status；single_task() 另有 enqueue_time。HTTP 状态机为：required + valid → set 并把 ContextVar 恢复令牌和“未消费”标志存入请求局部 g → after_request 回传 → teardown 只 reset 一次并标记已消费；invalid/exempt 不创建令牌，重复 teardown 不得重复 reset。cron_do 最外层 try/finally 必须包住 execution trace 分配、JobLog、配置读取、执行、指标和最终日志，并反向 reset 首次 set 的全部令牌。single_task() 的 enqueue_time 也由覆盖所有 early return/异常的 try/finally 恢复。ContextVar 的 Token 是标准 API 返回的恢复句柄，不是认证 token；仅在创建它的同一上下文使用一次，不得以 set(None) 代替 reset。
  7. execution trace 分配：先生成 UUID v4 候选并初始化 scheduler 上下文，再创建 pending JobLog；只有捕获到并确认是 execution trace 唯一约束冲突的 IntegrityError 才允许生成新候选重试，其他完整性错误必须 rollback 后原样抛出。JobLog 创建成功后才记录正式 cron.start；分配失败记录 cron.allocate_failed，不得制造“已经开始”的假事件。最终 JobLog、上下文和结束日志必须使用同一个 execution_trace_id。
  8. 日志与缓存/代理边界：logging filter 同时输出 request_id 与 execution_trace_id，不能用“优先级”丢弃其中之一。所有 required 动态 JSON GET 的响应设置 Cache-Control: no-store；fetch 使用 cache:'no-store'，jQuery GET 使用 cache:false，直接 XHR GET 必须走 wrapper；发布时清理代理相关动态路径的历史缓存。不得以 Vary: X-Request-Id 或 query 参数 ID 替代。调用方只发送一个长度 36 的 UUID v4；代理不得静默选择重复值，可保留多值供 Flask 拒绝或在代理层直接拒绝。只有请求到达 Flask 时才承诺上述 JSON 400；代理前置拒绝使用代理自己的响应体。上线前同时验证直连应用和真实代理路径不覆盖/剥离合法响应 Header。

2.1.2 明确不做与后续接口

  • 不建立 request_id 历史唯一索引或幂等表：UUID v4 是格式约束，不是幂等键；格式合法的重复值不改变业务语义。
  • 不把 request_id 加入正常 JSON body、query、HTML 页面、JobLog trace 或业务数据库列。受控结构化应用日志可以保存 request_id；后续如需在补偿记录保存人工请求关联，必须在 P0-C 详设中单独定义字段、保留期和访问面。
  • 不向被 scheduler 触发的下游服务自动传播 HTTP request_id；execution trace 继续使用既有 cronpilot_trace_id 协议。
  • REQUEST_ID_INVALID 是 lite 为解决协议 400 可判定性而新增的唯一稳定协议码，不代表提前实施完整 P0-A2 错误信封；异常脱敏、commit 失败误报成功和 scheduler 最终一致性分别由 P0-S、P0-A2、P0-C1/C2 处理。

2.1.3 验收、停止条件与风险

验收边界补充：本节“全部应用响应”的含义仅限于已验证 required 请求在 Flask 内形成且进入 after_request 的响应对象；代理/网关在请求到达 Flask 前的拒绝、进程崩溃或连接中断，由相应基础设施负责，不能断言带有应用 Header 或应用 JSON body。HTTP 集成矩阵必须按 endpoint + method + mode 覆盖，而不是只覆盖写接口。

  • HTTP 集成：每个 required 模式用合法 UUID v4 覆盖 2xx、302、业务 400、401、403、404、422、500，均断言响应 Header 与请求完全相同；浏览器测试对 302 禁止自动跟随并检查原始响应，随后到达的登录页是新的 exempt 请求。缺失、非 UUID v4、前后空白、逗号和同请求多值在应用鉴权/副作用前返回带 REQUEST_ID_INVALID 的精确 body 与 HTTP 400，且无响应 Header。未匹配 404、405、自动 HEAD/OPTIONS、HTML、原生 form 与双模式 POST 保持原行为且无 Header。
  • 协议登记：静态测试将实际路由、method、显式模式和前端调用点与机器登记表交叉核对；任何未分类业务 operation 或 required 调用点漏设标记即失败。混合 GET 分别测试 SSR 与 partial=1；同一路由 GET/POST 可属于不同分类；双模式 POST 同时断言客户端不发送、服务端不要求/回传 Header。
  • OpenAPI / Swagger：下载 /api/openapi.json，断言每个内部业务 operation 包含 required Header 参数、UUID v4 pattern、已验证请求的响应 Header，以及“不含 Header + REQUEST_ID_INVALID”的协议 400；业务 400 单独保留并声明同值 Header。
  • 来源、双 ID 与生命周期：仅 required 的 jQuery/fetch/XHR 调用发出 UUID v4；两次尝试不同，非安全上下文走 getRandomValues()。普通 HTTP 只含 request_id；定时任务只含 execution_trace_id；手动立即执行同时包含两者且响应仍为 request_id。并发、嵌套、重复 teardown、early return，以及 execution trace 分配、JobLog、配置、执行和最终日志处注入异常，均断言 HTTP request_id、五个 scheduler 字段和 enqueue_time 恢复外层值、不串链；非唯一约束 IntegrityError 不重试，分配失败不产生 cron.start。
  • 缓存与代理：对同一 required 动态 JSON GET 连续发送不同 UUID v4，两次均真实到达 Flask 并分别同值回传；断言响应 no-store、fetch no-store、jQuery cache:false、直接 XHR wrapper 和历史代理缓存失效。直连应用与实际代理分别测试单值、重复 Header 与代理前置拒绝；禁止把代理错误体误判为 Flask 精确 body。
  • 发布与回滚：执行单次原子发布：发布前完成全部调用方清单与改造、静态资源版本化、动态缓存清理和代理预检；同一版本上线调用方与服务端强制校验，随后做真实代理/浏览器验证。已打开的旧页面可能收到 REQUEST_ID_INVALID，须提供“刷新页面后重试”的操作提示。失败时整版回滚请求钩子、前端资源、OpenAPI 与缓存配置并重跑旧基线；只有未来发现独立部署的内部客户端时，才另立两阶段兼容发布方案。

3. trace_id、日志与脱敏安全契约

  1. HTTP request trace：已登记 API/JSON 模式的合法 UUID v4 X-Request-Id 是本请求的 request_id，并在响应 Header、结构化日志、g.trace_id 与 HTTP ContextVar 中保持同值；它不是全局唯一主键。仅 required 的页面异步请求在源头生成 UUID v4；缺失 Header 绝不由服务端补生成，而是 400；HTML 与双模式 POST 不进入此协议。
  2. 输入安全：已登记 API/JSON 模式只接受 UUID v4；Header 缺失、格式非法或同请求多值时，业务逻辑前 400，不回显、不进入 trace/log 字段，也不生成替代 request_id。合法值仅用于本请求日志关联，不进入业务持久化字段、JobLog 或通知正文。
  3. 后台执行 trace：scheduler 的 execution_trace_id 与 HTTP request_id 是不同实体；手动执行日志同时记录两者，JobLog 主 trace 继续使用 execution trace。P0-A-lite 不新增业务数据库 request_id 列，但可在受控结构化应用日志中记录；后续补偿记录若需保存 request_trace_id，须经 P0-C 详设确认字段、保留期和访问面。失败日志至少记录规范 ID 字段、code、operation、transport 与 outcome，查询不得依赖自由文本。
  4. 建立唯一脱敏函数和 sink 清单，覆盖 request 参数/header/body、错误上下文、通知正文、job_log、operation detail、应用日志与异常格式化文本。密码、token、sign、cookie、连接串及请求体不得出现于客户端、Webhook/IM 或业务持久化诊断字段。
  5. 不以 str(e) 作为用户、通知或业务日志文案；异常类型只映射到注册错误码和安全 detail。受保护的应用错误日志可保留排障堆栈，但写入前仍经脱敏函数处理；不得以“后台任务不在响应范围”为由跳过该要求。

4. DB 与 scheduler：逐接口最终一致性状态机

实施门禁：本节是 P0-C 的状态机概要，不属于 P0-A-lite，也不能直接作为数据库/scheduler 实现规格。P0-C 开始前必须另立正式详设，验证具体 scheduler 与 SQLAlchemy API、SQLite/MySQL 迁移、并发条件更新和任务级串行化；未经确认不得实施。

术语澄清：DB commit 成功后不能“rollback”。scheduler 失败必须由新的补偿事务或持久化同步状态处理；返回失败不等于撤销已提交的数据。

4.1 统一状态机

validate → assign desired_generation → db_commit(PENDING, desired state)
        → scheduler_apply(generation) → db_commit(READY, applied_generation)
        → success response
        └→ db_commit(SYNC_FAILED) → failure response + retry/reconciliation
  • 引入持久化的 scheduler_sync_state、desired_generation、applied_generation 与最后安全错误码。状态只能是 UNKNOWN（存量未对账）、PENDING（期望已提交，尚未应用）、READY（同 generation 已确认收敛）或 SYNC_FAILED（待重试）。具体字段、SQLite/MySQL 迁移和旧数据回填必须先单列设计；迁移不得把存量任务臆定为 READY。
  • 创建/编辑：每次期望调度配置变化须以数据库原子递增或乐观锁获得新 desired_generation，先提交期望配置 + PENDING，再注册或替换带该 generation 的 job。READY/SYNC_FAILED 只能用 WHERE id=? AND desired_generation=? 一类条件更新写回；影响 0 行表示本操作已过期，禁止覆盖更新后的状态。scheduler 应用前后均重新确认当前 generation；同一任务的 scheduler 变更须任务级串行化，或由对账器以最新期望配置再次收敛。错误状态写入失败必须产生基础设施告警，并由启动/周期对账发现 DB 与 scheduler 差异。
  • 并发边界：generation 栅栏只保证尚未越过该次栅栏检查的旧执行被阻止；已经通过检查的执行即使尚未发出 HTTP，也可能继续。它不能撤销已发出的请求。验收与用户文案必须写明检查时点，禁止声称“提交后所有未发 HTTP 的旧 job 都不会触发”或“绝不触发”。若产品要求取消在飞行请求，须另立设计引入执行租约/取消协议。
  • 启停：持久化目标状态和 generation 后调用 pause/resume。失败时写入 SYNC_FAILED，由对账按持久化目标收敛；下线先写入禁止执行的目标状态与新 generation，再移除 job。两者都不得声称对已提交状态 rollback 成功。
  • 只有 READY 且两 generation 相等才允许成功响应和成功 operation log。scheduler 已成功但 READY 写入失败时，响应仍为失败；对账必须比较实际 trigger/参数与期望配置指纹及 generation，不能仅以同名 job 存在为依据。补偿记录是否持久化 request_trace_id 由 P0-C 详设决定，不得提前把 P0-A-lite request_id 当作业务主键。

4.2 外部副作用的成功边界

副作用是否决定用户操作成功失败处理
主业务 DB 写入是commit 失败即 rollback、返回失败；不得继续刷新/跳转。
scheduler 应用是（任务类操作）写 SYNC_FAILED、返回失败、幂等对账；不得产生成功 operation log。
安全审计RBAC 安全敏感操作：是须与主写入同一可恢复持久化边界设计；不得静默吞掉失败。
operation log、通知、指标否不得改变已收敛业务结果；记录 OBSERVABILITY_FAILED 并告警，通知正文仍须脱敏。

6. 全量入口登记与分批计划

6.1 机械覆盖口径

P0-A-lite 实施前即新增 AST 路由扫描与人工批准的分类清单，覆盖 Flask/APIFlask 的 GET、POST 及其他显式业务 method，并单独识别自动 HEAD/OPTIONS、未匹配 404 与 405。每行必须登记 endpoint、method、URL、Blueprint、显式模式、调用方代码位置、分类、request_id 生成点、响应/缓存/OpenAPI 要求和测试 ID；P0 后续批次再关联写资源、commit 与外部副作用。扫描发现未登记业务端点、required 调用点漏标或前后端登记不一致即失败；豁免必须使用具名理由。

6.3 每批的执行步骤与停止条件

  1. 冻结基线：记录路由扫描清单、每端点当前 HTTP/JSON 样本（含字段存在性及 null/空字符串语义）、现有日志字段和 scheduler 状态；基线未入测试不得改公共 helper。
  2. 先写失败测试：为本批目标端点写入兼容、commit 失败、scheduler 失败、脱敏、generation 栅栏和无成功跳转断言；任何测试依赖真实开发 DB 均停止，改用内存库或隔离环境。
  3. 实施单一垂直切片：一次只改一个入口及其必要的 service/serializer/UI 路径；每处外部副作用必须对应第 4.2 节的结果记录。
  4. 本批验证：运行专项单元/HTTP 集成、静态路由登记、路由烟测；涉及 UI 时 restart 后以目标角色浏览器验证失败和成功路径并截图。
  5. 准入判定：仅当全部断言通过、无未登记入口、无凭据输出且没有成功响应/成功审计错配时，才能迁移下一个端点；任一项失败即停止扩面，只修当前切片。

6.4 发布、降级与恢复顺序

6.4.1 P0-A-lite

  1. 发布前置：当前 API 无外部使用方，管理端与服务端同仓发布，因此规范方案采用单次原子发布。上线前必须完成机器登记冻结、内部脚本/测试/Swagger/浏览器全部调用方改造、静态资源版本化、代理规则核验和相关动态缓存清理，不允许把“服务端先宽松接受缺失 Header”作为默认生产阶段。
  2. 原子切换：同一版本同时发布调用方与服务端强制校验，立即执行直连应用、真实代理和目标浏览器验收。旧的已打开页面可能仍运行旧 JS 并收到 REQUEST_ID_INVALID；用户提示固定为“页面版本已更新，请刷新后重试”，不得静默生成服务端替代 ID。
  3. 回滚：P0-A-lite 以完整版本为回滚单位，同时恢复上一版本的请求钩子、前端资源、OpenAPI、日志字段接入和缓存配置，随后重跑 SSR、双模式 POST 与旧 API 基线；禁止只删除新 hook。P0-B 后续纯 UI 渲染问题才允许只回退 UI 分支。
  4. 条件性替代：只有实施前清点发现存在独立部署、无法原子升级的内部客户端时，才暂停本方案并另立两阶段兼容发布设计，明确观测期、强制切换门槛和移除兼容逻辑的日期；不得在当前规范中同时保留两种模糊主路径。

6.4.2 P0-C（须先完成正式详设）

  1. 先发布纯加法数据库迁移；旧应用必须能忽略新列，存量任务不得自动标为 READY。
  2. 先运行只读 reconciliation，输出 DB 期望配置指纹/generation、实际 scheduler trigger/参数与差异理由；结果只能是“可证明匹配 / 不匹配 / 无法证明”。
  3. 仅对可证明匹配的任务，以条件更新写入 READY 与 applied_generation；其余保留 UNKNOWN/SYNC_FAILED。该步骤必须有 dry-run、任务级清单、失败重跑和回滚说明。

主要风险与回滚/降级

  • 兼容风险：正常业务响应字段和既有业务 HTTP 行为不变；唯一加法字段是 request-id 协议 400 的 code=REQUEST_ID_INVALID，required 模式缺失/非法 Header 明确返回 400。发现兼容问题时 P0-A-lite 必须整版回滚；仅 P0-B 后续 UI 渲染问题可单独回退 UI。
  • 一致性风险：禁止把已 commit 数据称为“已回滚”；以 PENDING/SYNC_FAILED、generation 栅栏、幂等重试和实际 trigger+配置指纹对账恢复一致性。已在飞行的网络请求不可撤销，必须如实记录该边界。
  • 迁移风险：存量任务初始为 UNKNOWN，必须先只读证明、后受控写入 READY；不得因默认 READY 或同名 job 存在让错误调度状态被掩盖。
  • 安全风险：服务端接受并仅使用已验证的 UUID v4 request_id；无效输入不回显、不写 trace，合法值不具备鉴权语义。默认不回显原始异常；脱敏测试覆盖所有输出 sink，包含后台 JobLog 与通知。发现泄漏时立即禁用 detail 呈现并仅保留通用 message + trace_id。
  • 范围风险：“所有人工写入”以冻结的机器登记为准，而非本文候选手写表；新增或转换路由必须同时更新登记和测试才可合并。双模式判定只看业务响应能力，禁止以登录重定向或请求头猜测。

8. 最终关闭条件

仅当机器登记表已冻结且无漏项，required 合法请求的 request_id 在全部应用响应 Header 与 HTTP 日志一致，协议 400 可由 REQUEST_ID_INVALID 稳定判定，手动执行双 ID 不覆盖，缺失/非法 Header 在应用鉴权/业务逻辑前拒绝，HTML 与双模式 POST 未改变，OpenAPI 完整，动态 GET 与代理不回放旧 Header，HTTP request_id、五个 scheduler 字段及 enqueue_time 无残留，四类 JSON 出口兼容快照和所有 sink 脱敏通过，且 P0-C 经另行确认的详设实现 generation 条件写回与最终收敛后，方可关闭整体 P0。任何全局 Ajax 无差别注入、双 ID 混用、非法值 fallback、按 status 决定响应 Header、非唯一 IntegrityError 重试、旧 generation 覆盖新状态、遗漏内部 Header 文档或仍将 commit 后失败称作 rollback 的实现均不合格。

9. P0-A-lite request_id 语义修订复盘（设计层）

  1. 定位：rev.4 虽恢复了 API 回显和页面受控请求的 UUID v4，却仍将 request_id 设计为“缺失时服务端生成”，并意外把 Header 传播扩大到 HTML 导航/原生 form；这违背了“REST API 的字段应明确必填、SSR 不被该 API 契约牵连”的边界。
  2. 根因：设计没有先区分内部 REST/JSON 调用契约与管理平台仍存在的 SSR 页面交互，把“服务端可生成关联号”的内部观测便利误当成了 API 的容错语义。因此既弱化了调用方责任，也给非 API 路径引入了不必要的行为变化。
  3. 测试漏洞：原验收只覆盖“合法回显/非法拒绝”，缺少“缺失即 400 且业务零副作用”“OpenAPI required: true”“HTML 页面和原生 form 不新增 Header、不要求 Header”的负向测试，因而无法阻止 fallback 与全局 after hook 回归。
  4. 修复：§2.1 改为按冻结的机器登记强制 UUID v4 Header；request_id 与 execution_trace_id 分离；只对 required 前端调用注入；按真实业务响应能力识别双模式 POST；非法输入返回带稳定协议码的精确 400；合法 required 请求的全部应用响应统一回传；ContextVar 状态机、缓存、代理与原子发布均形成可验证契约。
  5. 防护测试：新增协议/业务 400 区分、全部响应状态 Header 真值表、前端 required/exempt、路由登记交叉核对、手动执行双 ID、重复 teardown 和六个执行 ContextVar 异常恢复、execution trace 唯一冲突、历史缓存/代理重复 Header、OpenAPI 及 SSR 基线测试。
  6. 同类排查：已同步修订 §2.1—3 的 ID/错误契约，§4 的 P0-C 并发门禁，§5 的后续 UI 边界，§6 的登记、批次与发布，§7—8 的验收关闭条件；完整信封、HTML 错误页追踪号与 request_trace_id 持久化仍由后续独立设计决定。
  7. 预防方案：登记表成为实现和测试的单一输入；静态门禁对照实际路由与前端调用点，新增/转换端点必须先登记。P0-A-lite 合入门禁固定运行零副作用 400、OpenAPI、required/exempt 浏览器请求、双 ID、ContextVar 恢复、缓存代理和 SSR 无变化测试。

10. 后续方案：管理平台渐进式 REST API 化

管理平台当前是 SSR 与 Ajax 混合架构。P0-A-lite 只为其中已登记的 JSON 交互建立严格 Header 契约，不等同于把管理页面重写为前后端分离。后续演进的范围、分批、权限/CSRF 边界和页面 Before/After 已单列为 《管理平台渐进式 REST API 化后续方案（2026-09）》。该方案是 P0-A2 之后的 P1 工作：先建立管理端 JSON 层，再按垂直领域迁移页面；不复用对外 Token API，不做一次性 SPA 重写，也不移除 SSR 回退路径。

11. rev.11 评审意见逐项处置（rev.12）

本节是对评审意见的可追溯处置，不替代 §2 的实施契约。结论中的“已采纳”表示已写入本设计；“实施前验证”表示有当前源码证据，但仍须在 P0-A-lite-1 冻结机器登记后才能进入代码。

评审意见当前源码证据专业判断本次完善与验收
Header 必须由分类和校验状态决定，不能由 HTTP 状态或重定向决定。app/__init__.py 当前在全局 before_request 对所有请求自动生成/接受 ID；认证装饰器可能在后续返回 302。已采纳。把 302 视为豁免会让同一 required 请求因认证状态不同而违反协议；但代理前置响应不是 Flask 能控制的范围。§2 固定 “required + validated” 标记；明确仅承诺进入 after_request 的 Flask 响应。测试原始 302，且不自动跟随。
混合路由应按 endpoint + method + 显式模式分类，而非按 URL 或请求头猜测。/cron_retire 在 app/main/views.py 同时注册 GET/POST：GET 渲染模板，POST 返回 web_api_return；partial=1 列表页是显式 JSON 模式。已采纳。GET 与 POST 是不同协议面；X-Requested-With、Accept 或是否带 request_id 不能成为服务端分类依据。§6 候选表将 GET /cron_retire 列为 SSR、POST /cron_retire 列为 required；P0-A-lite-1 生成并冻结机器登记。
reset 类 POST 不应因“看起来像 Ajax”被强行纳入 required。/rbac/api_token/reset、/rbac/users/reset_password、/rbac/users/reset_token 都调用 _users_form_response()；该函数 Ajax 返回 JSON，原生 POST 成功则 redirect。已采纳。它们是实际双模式业务响应；在拆分专用 JSON endpoint 前要求 Header 会破坏原生 form 语义。三条路由列为 DUAL_POST_EXEMPT；验收覆盖 Ajax 与原生 form，均不新增 Header。
request-id 协议 400 必须可与业务 400 稳定区分。POST /api/cron 现有 scope 校验可返回 HTTP 400，不能以 status=400 推断 Header 校验失败。已采纳。仅靠文案、HTTP status 或日志字段均不足以让调用方可靠分支。协议 400 固定增加 code=REQUEST_ID_INVALID；既有业务 400 保持其语义且在已验证时回传 Header。实施时在 Release Notes 标注 ⚠️ API Breaking Change。
HTTP 与 scheduler 的 ContextVar 必须隔离，并使用 reset(token) 恢复。app/logging_config.py 当前共享 _ctx_trace_id；app/__init__.py 仅 set，未保存 token/reset；app/crons.py 同样写共享 trace。已采纳，且是防串链的必要修复。这里的 token 是 Python ContextVar 返回的恢复句柄，不是 API/认证 token。§2 定义 HTTP、scheduler、enqueue 三个生命周期状态机；异常、early return、嵌套与重复 teardown 均须验证。
execution trace 分配只能对明确的唯一约束冲突重试，且不能在 JobLog 创建前记录 start。app/crons.py 当前用 UUID1；任意 IntegrityError 都重试，并在 pending JobLog 前记录 cron.start。已采纳。当前做法会把非重复数据错误掩盖成重试，并可能留下没有对应执行记录的 start 事件。改为 UUID v4 候选；仅识别到 trace 唯一约束冲突时重试；成功创建 JobLog 后才 emit cron.start，否则 emit cron.allocate_failed。
缓存与发布不能依赖“服务端宽松接受缺失 Header”的灰度。管理端和服务端同仓，当前已确认无外部 API 使用方；dashboard 仍有直接 $.post('/cron_retire')，动态 partial GET 有浏览器缓存风险。已采纳。当前最小风险路径是一次性同步调用方和服务端；宽松 fallback 会破坏必填契约并掩盖漏改调用方。§6 固定原子发布、资源版本化、缓存清理和整版回滚；fetch/jQuery/XHR 分别列明缓存要求，旧标签页提示刷新后重试。
OpenAPI 与候选端点表必须是准确契约，而非手写清单替代路由发现。依赖 pin 为 APIFlask 2.4.0，且 create_app() 已启用 /api/openapi.json；当前候选表尚未由机器生成。部分采纳：spec_processor 是可用实施机制，但“所有端点已覆盖”在生成登记前不能宣称完成。§6 将表改为候选清单；P0-A-lite-1 以路由/调用扫描冻结权威登记，再由专项测试断言 OpenAPI 参数、响应 Header 和两类 400。
