1. 问题

项目共有 51 个测试模块、634 个用例，全部通过（11 个集成用例因无运行服务正确 skip）。但 CI（GitHub Actions）仅门禁其中 5 个模块（约 28 个用例），本地命令 cronpilot.sh test 仅执行 32 个模块（约 427 个用例），剩余 19 个模块（207 个用例）完全不在任何自动化门禁中。

2. 根因

2.1 直接原因：硬编码模块列表 + 手动同步

CI workflow 和 cronpilot.sh test 各维护一份独立的硬编码模块名列表。新增测试模块后需要同时更新两个文件的两份列表，这一步在开发流程中没有任何自动化检查，完全依赖开发者记忆。

2.2 历史原因：CI 配置从未跟上测试增长

  1. Phase A 初期（2026-03）：CI workflow 创建时只有 5 个核心守卫模块，这是正确的起点。
  2. 功能迭代期（2026-04—07）：cronpilot.sh test 的列表随功能开发逐步从 5 扩充到 32 个模块，但 CI workflow 始终保持 5 个未变。原因是每个 OPT/安全修复的交付闭环关注的是"本地测试通过"，而非"CI 配置已更新"。
  3. Redesign + 安全修复期（2026-07—08）：新增 19 个模块连 cronpilot.sh test 的列表也未更新，测试存在但完全无门禁。

2.3 结构性原因：无"测试覆盖率门禁"防止漂移

项目有 CI 门禁检查代码质量（ruff、颜色审计、HTML↔MD 同步、前端构建等），但没有"测试模块覆盖率"门禁——即没有自动化机制验证"tests/ 下所有 test_*.py 是否都被 CI 执行"。

3. 方案

3.1 推荐方案：unittest discover（方案 A）

将 CI 和 local test 的命令都改为 python -m unittest discover -s tests -p "test_*.py" -v。

优点

  • 一劳永逸——新增测试文件自动纳入，根因（手动同步）被彻底消除
  • CI 和 local 行为完全一致，消除"本地通过 CI 不跑"的断裂
  • 改动极小（CI 改 1 行命令，cronpilot.sh 改 1 行命令）
  • Python unittest discover 是标准实践（Django、Flask 社区广泛使用）

风险与应对

风险概率应对
CI 耗时增加（5 模块 → 51 模块） 必然 实测 87 秒/版本 × 4 版本 ≈ 6 分钟。可接受；若不可接受可缩减版本矩阵到 3.8+3.11 两个
未来有人写了需要外部依赖的测试但没正确 skip 低 CI 会立即报红暴露（这是 discover 的优势而非劣势）
集成测试在 CI 中意外运行 无 已有 skipUnless(CRONPILOT_BASE_URL) 保护，CI 不设此变量即正确 skip

3.2 备选方案：扩充显式列表（方案 B）

将 CI workflow 的模块列表更新为全部 51 个模块。

缺点

  • 根因未解决——每次新增测试文件仍需同步修改两份列表
  • 维护负担持续存在
  • 需要额外的"列表完整性检查"脚本才能防止再次漂移

结论：推荐方案 A。

4. 范围

4.1 改动文件

文件改动

scripts/cronpilot.shtest) 分支命令从显式列表改为 discover

4.2 不做的事

  • 不修改任何测试文件内容
  • 不变更 Python 版本矩阵（保持 3.8/3.9/3.10/3.11）
  • 不变更 CI 触发条件（paths filter 保持不变）
  • 不引入 pytest（保持 unittest，减少变更面）

5. 分批

本方案改动极小（2 个文件各改 1 行命令），单批次交付即可。

步骤动作验收
1 修改 .github/workflows/unit-tests.yml diff 确认只改了命令行
2 修改 scripts/cronpilot.sh diff 确认只改了 test 分支
3 本地运行 bash scripts/cronpilot.sh test 确认 634 用例全通过 exit code 0, 634 ran, 11 skipped
4 文档更新 RELEASE_NOTES.md + html_docs_to_markdown.py --check

6. 验收

6.1 本地验收

# 改后运行
bash scripts/cronpilot.sh test
# 期望：Ran 634 tests ... OK (skipped=11)

# 确认 discover 等价
.venv-py311/bin/python -m unittest discover -s tests -p "test_*.py" 2>&1 | tail -5
# 期望：Ran 634 tests ... OK (skipped=11)

6.2 CI 验收

push 后 GitHub Actions Unit tests workflow 在 4 个 Python 版本上均绿，且日志中包含"Ran 634 tests"（或更多，随测试增长）。

6.3 回归保障

改为 discover 后，未来新增的 tests/test_*.py 文件自动纳入 CI，无需任何额外操作。这本身就是验收标准的核心：消除手动同步的需求。

7. 风险

风险等级说明
回归风险 极低 不修改任何测试代码或业务代码，只改运行命令
CI 耗时增加 低 从 ~5 秒增加到 ~87 秒/版本，总计 ~6 分钟。若未来不可接受，可另行优化版本矩阵
降级/回滚 — 只需将命令改回显式列表即可恢复原状
