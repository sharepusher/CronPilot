1. 当前基线与偏差校准

领域当前真实实现剩余问题本方案处理
主业务事务update_user_management() 已用一次 db.session.commit() 更新角色、组、资料和 auth_version。旧方案的“多次业务提交”已过时，不应重复重构。保留当前单业务提交架构，只收口剩余缺口。
no-op已计算角色/组是否变化，但仍赋值资料、执行 commit、写成功审计并失效缓存。“什么都没改”仍有真实审计 INSERT 和事务/缓存副作用。引入服务端规范化快照和显式 change set；空集合直接 NO_CHANGE。
页面快照GET 已读取并回显用户资料，但 POST 没有可验证的页面原始快照。无法稳定区分“用户没改”与“页面打开后数据库被别人改过”。GET 生成签名原始快照令牌；前端以 DOM 初值做即时判断，服务端以签名快照重算修改意图。
审计业务 commit 成功后调用 write_audit_log()，该函数再独立 commit 并吞掉审计异常。“业务已成功但成功审计缺失”仍可能。为该端点增加不提交的审计入队原语，与业务同 Session、同 flush、同 commit。
Scope路由已使用数据库当前 actor 与 validate_user_scope_assignment()，关闭了旧 Review 的 __ALL__ 提权面。路由校验到 commit 之间仍存在 TOCTOU 窗口；服务函数明确假设“调用方已校验”。路由保留早期拒绝；写边界再以 actor_user_id 和锁定后数据库状态复核。
停用编辑页仍可直接把 is_active 改为 0；专用 /users/set_active 则强制停用缘由。同一策略存在“有缘由”与“无缘由”两条写入路径。编辑页状态改为只读；停用继续统一走已有专用流程。
前端响应errcode=0 且有 URL 立即跳转；无 URL 则立即刷新。旧方案声称 no-op Toast 可稳定可见，与公共 JS 事实不符。增加显式、加法式 data.outcome=no_change 契约，仅此结果留在本页。

2. 问题与根因

2.1 问题

  • 无变更依然执行 commit、审计 INSERT 和缓存失效，增加无意义的失败面。
  • 资料-only 变更也失效 API Scope 缓存，与授权语义无关。
  • 成功审计在第二个事务中写入，不能作为业务成功的原子证据。
  • 编辑页可绕过专用停用页的缘由契约。
  • 通用异常被统一映射为“保存失败”，无法表达 commit 确认丢失时的结果不确定。

2.2 根因

  • 当前服务以“执行了保存流程”代替“数据状态确实改变”，没有端点级 change set。
  • 旧设计把“判断用户是否改动”放到行锁之后，混淆了页面意图判定与数据库并发保护两个阶段。
  • write_audit_log() 同时承担建模、入 Session、commit 和异常吞掉，无法被原子业务服务组合。
  • 路由级 Scope 校验被误当成写边界授权证据。
  • 审计安全边界若只靠“排除密码/Token”黑名单，新增凭据字段时可能被意外序列化。
  • 状态修改历史上分散在编辑页和专用停用页，策略未收口。

3. 目标、范围与非范围

3.1 目标

  1. GET 完成后结束请求级会话/事务，不跨用户思考时间持有数据库事务或行锁。
  2. 以签名页面原始快照与规范化请求值计算意图 change set；无意图变更时不进入写事务。
  3. 无变更时零业务 DML、零写事务 commit、零成功审计、零 Token/缓存副作用。
  4. 有变更时才在写边界使用数据库当前 actor/target/scope 事实复核授权，并以三方比较拒绝覆盖并发变更。
  5. 只修改有效差异，并把用户、组关系、授权版本和成功审计收口到一次 commit。
  6. 审计以“事件必记录、凭据值永不记录”为边界，每种事件使用固定字段白名单。
  7. 确定失败、并发冲突与提交结果未知均不得返回成功或自动重试。

3.2 修改范围

  • app/rbac/services.py：规范化、change set、事务内授权复核、同事务审计和结果分类。
  • app/rbac/views.py：传入 actor ID、响应适配、审计语义展示和原生 POST 的 PRG 通知。
  • app/templates/redesign/user_form.html：状态改为只读说明，提供可访问的 no-op/邮箱删除确认/未知结果提示。
  • app/templates/redesign/_audit_logs_rows.html：新邮箱清空记录显示语义化文案，旧记录保持原显示。
  • app/static/js/common-redesign.js：仅新增显式 outcome 的 opt-in 留页分支，不改其他 Ajax 表单默认行为。
  • 新增专项测试文件，并扩展用户管理 Scope、Ajax 守卫和浏览器验收。

3.3 明确不做

  • 不重写所有 RBAC 服务，不引入全站 Unit of Work 框架。
  • 不改外部 app/api/ 响应字段，不属于 API Breaking Change。
  • 不增加数据库列、不引入乐观锁版本字段。
  • 不修改停用不可直接恢复、种子 admin 不可停用等已有策略。
  • 不用跨请求内存缓存保存页面快照；快照由签名令牌随表单回传，数据库当前值仍是并发一致性依据。
  • 本切片不重构密码、Token 或 Session 的既有业务流程；它们仍必须产生安全事件审计，但 Token 专用 action 命名收口需另立设计。

4. 已冻结的设计决策

决策契约理由
D1a GET 原始快照GET 读取对象后，渲染前冻结 schema_version、actor_user_id、target_user_id、email、nickname、job_title、role 和排序去重的完整 group_ids，另签名 editor_scope（bypass 与可编辑组）。JS 与服务端意图使用同一可编辑投影；旧 v1 编辑页必须刷新。用已固定的 itsdangerous==2.2.0 中 URLSafeSerializer(current_app.secret_key, salt='rbac-user-edit-snapshot-v2') 的 dumps() 生成 edit_snapshot_token；GET 响应结束时不保留跨请求事务或行锁。令牌不设业务过期时间，但签名无效、版本/类型不符、actor/target 不匹配或密钥轮换后一律返回 FAILED 并要求刷新页面。签名保证原始快照完整性，不将隐藏字段当作可信事实；它不加密，但载荷只含可管理目标的资料、完整组原值与编辑范围，不含密码/Token。完整组原值用于并发保护，不是可编辑控件的比较基准。使用的依赖版本、构造参数与 dumps()/loads() 签名已于设计写入前在当前环境核对。
D1b 提交前意图判定前端使用签名原值派生的同一可编辑投影作为规范化初值，提交前与当前表单值比较：无变化则在本地提示且不发 POST；非空邮箱转空则先打开 CpModal 收集理由。服务端不信任前端结果：POST 先用 loads() 验签并重做规范化，再以“请求值 − 签名原值的可编辑投影”构建 intent_change_set。空集合直接 NO_CHANGE；参数、确认或理由无效在写事务前拒绝。页面判定提供及时交互，服务端重算防止绕过 JavaScript；无变更不需要为了“判断无变更”而先获取行锁。
D1c 写事务三方比较只有 intent_change_set 非空才开启写边界并按确定顺序锁 actor/target。对每个资料字段比较 original/current/requested：current == original 时纳入有效写入；current == requested 时标记已被其他操作等价完成，不重复写；其他情况返回 CONFLICT。role + group_ids 作为一个耦合授权单元整体比较，不拼接两个不同时点的授权状态。若所有意图变更都已等价完成，返回 ALREADY_APPLIED 并零 DML/零成功审计。用户意图与并发保护分层；不用陈旧页面无声覆盖数据库新值，也不对已经到达的目标状态重复写入。
D2 状态修改/users/edit 不再接收 is_active 变更；页面只读显示状态并引导回用户列表使用专用停用流程。已停用目标的 GET 固定重定向只读详情页；Ajax POST 返回固定错误文案和受信任的详情页 URL；原生 POST 重定向详情页。三者均不允许修改资料或权限；重新使用只能走已有同名覆盖启用流程。统一停用缘由、审计、最后管理员和种子账号保护，并对齐列表/详情已有的“停用账号不可编辑”可见语义。
D3 全局 Scope__ALL__ 仍表示“admin + 无 UserGroup 关系行”；表单回显继续使用已实施的 _form_group_ids_for_user() 双向映射。不新增标志列，不改已闭环的全局授权模型。
D4 资料规范化邮箱字段必须出现在编辑请求中：缺少字段视为请求不完整并返回 FAILED；字段存在且 trim 后为空，表示管理员明确删除原邮箱，持久化为 SQL NULL；非空则须包含 @ 且最长 128。花名 trim，空值为 None，最长 64；岗位必填，标准值须在现有枚举内，other: 自定义值 1–20 字符，超长拒绝而非截断。区分“没有提交该字段”和“用户明确提交空值”，并消除路由静默截断和服务缺校验的偏差。
D4b 删除邮箱确认与理由仅当签名原始快照的邮箱非空、规范化请求邮箱为空时触发。前端在首次 POST 之前用表单型 CpModal 要求管理员填写 trim 后 1–500 字的清空理由；取消不发 POST。确认提交携带 edit_snapshot_token、confirm_clear_email=1 与 email_clear_reason，各字段名唯一，动态写入前移除同名旧节点。直接绕过前端且缺少确认时，服务端在写事务前返回非终态 CONFIRM_REQUIRED；理由为空/超长返回 FAILED。写事务内若当前邮箱既不等于快照原值，也不是已经为空，则返回 CONFLICT 并要求刷新。清空是低频信息删除，需要明确意图与可追溯原因；签名快照已绑定管理员当时看到的原值，无需再信任一个可篡改的 expected_current_email 隐藏字段。
D5 change setintent_change_set 只包含请求相对签名原始快照的意图变化；写事务内再生成 effective_change_set，只包含安全可应用且当前尚未到达请求值的 role、group_ids、email、nickname、job_title。组按去重后整数升序列表比较，忽略提交顺序。分开“想改什么”与“锁内还需改什么”，精确触发审计、Token、auth_version 和缓存副作用。
D6a user:update 审计白名单保留单条 user:update 和相同用户 resource。detail 必须直接从 effective_change_set 构建，允许的快照字段精确为 {email,nickname,job_title,role,group_ids}；禁止序列化整个 RbacUser 后再删除敏感键。固定 JSON v1 结构为 {"schema_version":1,"changes":{"email":{"before":"old@example.com","after":null}},"reason":"..."}；reason 仅在邮箱清空时存在，group_ids 以升序整数列表记录。审计行与业务同事务；no-op、已等价完成、未确认、取消、理由无效和并发冲突都不写成功审计。用户变更审计不设时间过期或自动清理。审计安全边界由“允许什么”定义，而不是依赖永远不完整的敏感字段黑名单。邮箱是个人信息但不是认证凭据，当前只在 admin/种子 admin 的 audit:read 面持续保留。
D6b 凭据事件审计边界“凭据值不进快照”不等于“凭据操作不审计”。密码修改、密码重置、Token 签发/重置/撤销必须记录独立安全事件的 actor、target、action、结果、来源/理由与“Session/Token 是否失效”等安全副作用；密码明文、密码哈希、完整 Token、Session ID、CSRF Token 及可恢复/校验凭据的材料永不记录。当前 user:password/user:password_reset 事件保持；当前 Token 流程的泛化 user:update 命名不在本切片内改动，另立需求收口为专用 action。“事件必记录、秘密值永不复制”同时满足问责性与最小暴露原则，也避免将本端点的字段白名单误解为全局审计白名单。
D6c 审计 JSON 容错审计页只解析 schema_version == 1、顶层键符合契约、changes 为对象、字段属于五项白名单且每项只有 before/after 的记录。空 detail、非法 JSON、未知版本、未知字段或类型/形状错误均安全回退到现有通用 resource 文案，不 500、不部分猜测渲染。所有前后值和理由使用 Jinja 普通自动转义，禁止 |safe。版本化只有在模式和失败行为都固定时才能兼容历史数据，并防止损坏或恶意 detail 影响审计页可用性。
D7 授权副作用角色或组真实变化时，auth_version 只增加一次并重签 Token；资料-only 不 bump、不重签。Scope 缓存仅在授权变化且 commit 成功后失效。继承已实施 B2 契约，去掉资料变更的无关副作用。
D8 异常与冲突分类参数/签名快照/确认/授权/存在性失败为 FAILED；当前值既不是原值也不是请求值为 CONFLICT；显式 flush() 失败为 FAILED；进入 commit() 后抛异常保守归为 COMMIT_UNKNOWN。所有已进入锁区但未 commit 的终态（包括 CONFLICT/ALREADY_APPLIED/锁后 FAILED）在返回前显式 rollback() 或正常退出事务上下文，不遗留行锁。结果不自动重试；若本次曾尝试角色/组变更，COMMIT_UNKNOWN 后仍 best-effort 失效当前 worker Scope 缓存。冲突是可预期业务结果，不是服务器异常；连接在 commit 确认阶段丢失时，应用不能证明数据库最终选择。
D9 no-op/已应用响应前端直接识别 no-op 时不发 POST；绕过前端的 Ajax NO_CHANGE 使用 errcode=0、data.outcome=no_change、无 URL，显示 Toast 后留页。ALREADY_APPLIED 使用 data.outcome=already_applied 和“目标状态已存在，无需重复保存”。原生 POST 均以 303/302 PRG 回同一编辑页，由固定 outcome 映射可信提示。不把原始消息放入 URL，不修改其他表单默认跳转，并区分“用户未修改”与“并发操作已等价完成”。
D9a 冲突响应Ajax 返回 errcode=1、data.outcome=conflict，显示“该用户信息已变更，未覆盖新数据，请刷新后重新确认”；原生 POST 以 PRG 回编辑 GET 并显示同类固定文案。不回显陈旧值冒充最新数据，不将可恢复的并发冲突泛化为“服务器错误”。
D9b 未知结果响应Ajax 在当前页显示“保存结果无法确认，请刷新核实当前信息”；原生 POST 使用 PRG 回到同一编辑 GET，用固定 outcome=commit_unknown 映射同类警示，GET 重新读取数据库当前值。避免 POST 结果页刷新导致重复提交，也不用提交前表单值冒充数据库最终事实。
D10 缓存风险当前 worker 在授权 commit 后立即失效；其他 worker 仍接受现有 120 秒 TTL 安全网。本切片不宣称多 worker 立即撤权。如要零窗口多 worker 撤权，需另立共享缓存/版本校验方案。
邮箱语义示例：
  • 数据库原值为 old@example.com，编辑页不改邮箱并保存：请求仍提交 old@example.com，判定为未变更。
  • 管理员删除输入框内全部内容并保存：请求明确提交 email=""，数据库由 old@example.com 变为 SQL NULL。
  • 异常请求完全没有 email 字段：返回参数不完整，不保存，也不将其解释为清空。
当前代码的差异：user.email = (email or '').strip() or user.email 会把明确提交的空值重新替换成旧邮箱，因此当前无法通过编辑页删除已有邮箱。

5. 输入与结果契约

类型数据库事实Ajax原生 POST副作用
CONFIRM_REQUIRED
（非终态）		签名原始快照中的邮箱将被清空，但直接 POST 尚未携带有效确认和理由；未获取行锁，数据库不改变。errcode=1 且 data.confirm_clear_email=true；使用包含 textarea 的表单型 CpModal，禁止使用不支持输入的 CpConfirm.show()。正常 JS 路径在首次 POST 前已完成该流程；服务端结果是绕过前端时的防护。回渲染表单、保留输入，显示理由输入区和“确认清空邮箱并保存”二次动作；重提交保留同一签名快照令牌。全部为 0；取消时留在编辑页且不提交。
UPDATEDeffective_change_set 已应用，业务和成功审计同一次 commit 已确认。errcode=0，保存成功，跳用户列表。PRG 到用户列表。仅按有效差异触发。
NO_CHANGE请求值相对签名页面原始快照没有修改意图；无行锁、无业务 DML/写 commit/审计。通常由前端本地提示且不发 POST；服务端收到构造请求时仍返回 no_change 并留页。PRG 到同一编辑页并显示“未检测到变更，无需保存”。全部为 0。
ALREADY_APPLIED请求存在修改意图，但锁内数据库当前值已等于全部请求值；显式结束锁事务。errcode=0、data.outcome=already_applied，留页并提示目标状态已存在。PRG 回编辑 GET 并从数据库重读。零 DML/零 commit/零成功审计/零授权副作用。
CONFLICT至少一个意图字段的当前值既不是原值也不是请求值；全部拒绝并显式 rollback/退出事务，禁止部分保存。errcode=1、data.outcome=conflict，要求刷新后重新确认。PRG 回编辑 GET，显示固定冲突文案和最新数据。零业务 DML/零成功审计/零 Token/缓存副作用。
FAILED提交前确定失败；rollback 后无业务改变。errcode=1，字段或通用错误，留页。回渲染并保留合法输入。无成功审计/缓存失效。
COMMIT_UNKNOWN应用无法证明 commit 最终结果。errcode=1，“保存结果无法确认，请刷新核实当前信息”，不跳转。PRG 回编辑 GET，显示同类警示并从数据库重读当前值。不自动补成功审计或重试业务；若尝试过授权变更，则 best-effort 失效当前 worker Scope 缓存。

6. 推荐调用链与事务边界

GET /rbac/users/edit?id=target_id
  → 校验当前 actor / target / Scope，读取用户和组回显值
  → 构建规范化 original snapshot
  → URLSafeSerializer.dumps(original snapshot) 生成 edit_snapshot_token
  → 渲染页面；请求结束，不跨页面停留持有事务/行锁

浏览器提交前
  → 以 DOM 初值与当前值计算本地差异
  → 无差异：提示 NO_CHANGE，不发 POST
  → 邮箱非空转空：CpModal 二次确认 + 必填理由；取消不发 POST

POST /rbac/users/edit
  → CSRF + 数据库当前 actor guard + 禁止自编辑
  → URLSafeSerializer.loads(edit_snapshot_token)；校验 schema/actor/target/字段类型
  → 核对签名 editor_scope 与当前范围；规范化 requested，以同一可编辑投影构建 intent_change_set
  → 空集合：NO_CHANGE（无行锁，显式结束请求内读事务）
  → 邮箱清空缺确认：CONFIRM_REQUIRED（无行锁）
  → 参数/理由无效：FAILED（无行锁）
  → update_user_management(actor_user_id, target_user_id, original, requested, intent_change_set)
      → 按确定顺序锁定 actor/target 用户行
      → 重读 actor 权限、禁止自编辑、target 启用状态、target Scope、可分配组与目标组
      → 三方比较 original / current / requested
      → 冲突：CONFLICT（rollback/退出事务）
      → 已全部等价完成：ALREADY_APPLIED（rollback/退出事务）
      → 构建 effective_change_set；资料-only 不写组；真实授权变化仅 diff 可管理关系、保留范围外绑定
      → 按有效授权变化 bump auth_version / 重签 Token
      → 仅从五字段白名单构建 JSON v1，将单条 user:update 审计 add 到同一 Session
      → flush（失败 = FAILED）
      → commit（成功 = UPDATED；异常 = COMMIT_UNKNOWN）
  → 授权有效变化且结果为 UPDATED 或 COMMIT_UNKNOWN 时，best-effort 失效当前 worker API Scope 缓存
  → 路由适配 Ajax / 原生 POST

实施必须复用已核对的 SQLAlchemy db.session.add()、flush()、commit()、rollback() 与 select(...).with_for_update()；禁止在设计确认后临时换成未经代码核对的事务 API。

7. 并发、锁顺序与性能

  • 同一目标编辑：行锁不用来判断用户是否动过表单；它只在存在修改意图时保护数据库当前值的三方比较与原子写入。
  • 字段冲突：资料字段独立比较；角色和组作为一个授权单元。任一意图字段冲突则本次整体拒绝，不做部分保存。
  • 死锁预防：actor 和 target 以用户 ID 升序锁定；组行也以 ID 升序读取/锁定。
  • 最后管理员：本端点不再处理停用；角色从 admin 降级时，在确定顺序锁定启用 admin 行后重新计数。
  • SQLite/MySQL：SQLite 不依赖 FOR UPDATE 提供行锁语义，验收要求实内存 SQLite 功能回归和真实 MySQL 并发/锁释放演练分开执行。
  • 成本：签名快照为小型JSON的本地签名/验签。普通资料/授权写入路径读取并锁定actor、target、相关关系行及所选业务组；管理员降权还会锁定启用管理员集合以维护最后管理员约束，成本随管理员数量及相关关系/组规模变化。同一actor或公共业务组可能形成竞争。不能仅凭低并发场景或ORDER BY认定成本可忽略或不会死锁；热点与物理锁范围须结合实际索引、执行计划和并发测量评估。
  • no-op 收益：正常页面路径连 POST 都不发；服务端防绕过路径也不获取行锁、不 commit、不写审计、不扫描缓存。不引入跨请求内存缓存，避免服务器粘滞状态与失效复杂度。

并发冲突当前值同时不同于原值/请求值；整体 rollback，零部分保存，及时释放行锁。无成功审计和 Token/缓存副作用。不覆盖新值，要求刷新后重新确认。
审计快照只有 UPDATED 随业务同事务写入。changes 键只能是五项白名单中实际变化字段；凭据操作有安全事件，凭据值永不记录。正常 v1 显示前后值；空/损坏/未知结构安全回退，不 500/XSS。
越界 Scope/陈旧 actor零业务变化。只允许 deny 审计，不得有成功审计。403 或约定拒绝，不误报成功。
审计/flush 失败全部 rollback。无成功审计、无失效。确定失败，留页。
commit 确认丢失应用不猜测最终状态。不自动重试、不自动补审计；若尝试授权变更，best-effort 失效当前 worker 缓存。结果无法确认，要求刷新核实。
停用编辑端点不提交状态变化。继续由专用停用流程管理缘由和安全副作用。编辑页状态只读。
停用目标直接编辑GET/POST 均不修改用户或关系行。无成功审计、无 Token/缓存副作用。GET 和原生 POST 固定去只读详情页；Ajax POST 显示固定错误后跳详情页，并引导同名覆盖启用流程。

12. 风险、回滚与预防

风险控制回滚
同事务审计使审计库故障阻断编辑这是“成功必须有成功证据”的明确取舍；仅对用户编辑端点收紧。可回退为原子业务+独立 best-effort 审计，但必须同步恢复文档契约。
签名快照失效或被篡改独立 salt、固定 schema 与 actor/target 绑定；验签/类型失败一律拒绝并要求刷新。令牌不是授权证据，写边界仍重查当前 actor/Scope。可回退为服务端临时快照存储，但会引入跨 worker 共享状态，不是首选。
新锁顺序增加等待无意图或无效请求不获锁；只有低并发真写路径按 ID 确定顺序锁定，真 MySQL 记录锁等待/死锁。回退事务内锁扩展，保留签名意图模型，并登记并发残余风险。
通用 JS outcome 分支影响其他表单仅对显式 data.outcome=no_change 生效；静态门禁+所有 Ajax 表单回归。移除 opt-in 分支即恢复原行为。
邮箱空值改为可清空的行为变更Before/After 和测试明确冻结；只影响用户明确提交空邮箱。若确认前不接受，将 D4 调整为空值继承原值，不在实施时临时决策。
邮箱确认被绕过或确认后原值已变更服务端在写事务前强制复核确认标志/理由，在行锁内将当前邮箱与签名原值/请求值三方比较；不依赖可篡改的 expected_current_email。确认参数不进 URL，不写日志。可移除清空能力并改为空值校验失败；不允许回退到静默保留旧值。
清空理由缺失、超长或被当作 HTML 渲染前端只做即时反馈；服务端强制 trim 后 1–500 字，无效时零写入。审计页以 Jinja 自动转义文本展示理由，禁止 |safe。可临时停用邮箱清空入口；不允许在理由丢失的情况下继续删除。
审计 detail 持久化邮箱/花名等个人信息访问面继续限于 audit:read（当前仅 admin/种子 admin）；页面使用 Jinja 自动转义；只从五字段白名单与 effective_change_set 交集构建 detail，禁止整模型序列化；凭据操作另记事件，凭据值不记录。可改为仅记录字段名/操作语义，但属于审计精度降级，需同步设计与验收契约。

可落地预防措施

  • 在新增专项测试中固化“no-op 不获行锁、零写 commit/零审计/零失效”计数断言。
  • 为签名快照固化 schema、独立 salt、actor/target 绑定、篡改/未知版本/错误类型拒绝测试。
  • 为邮箱清空固化未确认、取消、理由空/超长、有效确认与理由入审计、三方并发比较和动态 hidden input 唯一命名防护测试。
  • 为审计 detail 增加“键集合精确等于五字段白名单与有效差异的交集”、“前后值/理由与同事务业务事实一致”、“凭据操作有事件但凭据值零出现”和四类损坏数据回退断言。
  • 为 update_user_management() 固化“必须传 actor_user_id，写边界再授权”契约，防止新调用方绕过。
  • 在 Ajax 守卫中增加“只有显式 outcome 才留页”静态断言，防止全局行为漂移。
  • 实施后以专项复盘记录旧方案时态偏差、测试漏洞和防再发门禁。

13. 下一确认点

U0–U3 已全部完成。后续若扩展到密码、Token、停用、审批或其他编辑入口，应另立设计并复用本方案的写前意图、数据库当前授权、结果真值和审计事件边界，不在本方案内继续扩张。
