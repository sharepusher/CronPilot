# RBAC 全局权限授予边界加固方案专业评估

版本：rev.1 · 日期：2026-10-15 · 评估对象：[优化需求 rev.2](../design/RBAC全局权限授予边界加固优化需求-2026-10.html) · 评估基线：当前仓库代码与定向测试

**总体结论：专业、准确且合理，达到“可提交用户确认”的设计成熟度。**方案正确把问题定义为授权者边界缺失，而不是普通表单校验；rev.2 已修正对旧测试的错误解读，并将实施拆成可停止、可验收、可局部回滚的 S0–S5。但它仍是待确认设计，不代表已修复。

**实施判定：有条件通过。**用户明确确认后可从 S0 开始；不得跳过红线测试直接改路由，不得把 S3 前端隐藏当作安全修复，不得顺带实施另一份用户编辑事务方案。

## 1. 评估范围与依据

本评估逐项对照了 `app/rbac/views.py` 的用户新增/编辑路由、`app/rbac/services.py` 的组参数校验/用户写入/注册审批、`app/rbac/policy.py` 的 Scope bypass 语义、`app/templates/redesign/user_form.html` 的 `__ALL__` 渲染与 JavaScript，并搜索了 `create_user()`、`set_user_groups()`、`approve_registration()` 生产调用方。

定向基线命令：

```
.venv-py311/bin/python -m unittest \
  tests.test_registration.TestNonAdminCannotSelectGlobal \
  tests.test_registration.TestApproveRejectRegistration \
  tests.test_rbac_scope -v
```

结果：**44 项全部通过**，用时 18.225s。其中 `test_admin_with_all_accepted_on_add` 由于 fixture 未建立注册申请表，触发一次被容错的缺表日志后仍通过；这不改变权限结论，但是 S0 应消除的测试噪声。

## 3. 准确性复核

### 3.1 已证实的核心事实

- 新增和编辑路由都只在 target role 非 admin 时拒绝 `__ALL__`，没有同步判断 actor 是否有全局授予能力；漏洞判定成立。
- `set_user_groups()` 将 `__ALL__` 表达为无具体组关系，而 `user_bypasses_scope(role='admin', group_ids=[])` 将这一状态解释为全局 admin；风险链路完整。
- 用户表单始终输出 `__ALL__` option，现有 JavaScript 只根据 target role 显隐；“模板不渲染+后端拒绝”的改法准确。
- 注册审批已对 admin 申请执行 seed/global/scoped 范围判定，批量入口逐项调用单条审批；将其作为回归基线合理。
- 当前审批 helper 读的是 Session 中的 role/username/group\_ids，不是 helper 内数据库回读。rev.2 已把这一点明示为 S4 的等价性边界，没有夸大现状保证。

### 3.2 已纠正的原方案不准确点

rev.1 曾把 `test_admin_with_all_accepted_on_add` 解读为“按组管理员错误被允许”。实际 fixture 用户名是 `admin`，会命中种子管理员 bypass；该用例期望应保留。rev.2 已改为“新增非种子、单组/多组 Biz Admin 负向用例”，修正后的证据链可信。

## 4. 专业性与合理性分析

| 决策 | 评价 | 专业理由 |
| --- | --- | --- |
| 独立安全需求 | 正确 | 与 no-op、差异写入、单事务解耦，避免安全边界被大型重构掩盖，也可独立回归。 |
| actor 与 target 分离 | 核心正确 | “target 可以成为 admin”不等于“actor 可授予全局范围”；这是权限提升类缺陷的正确建模。 |
| 纯策略+服务数据读取 | 合理 | 使权限矩阵可穷举单测，同时避免纯策略函数隐式依赖 Flask Session 或 DB 事务。 |
| S2 后端先于 S3 UI | 必要 | 前端可被绕过；后端守卫是独立安全边界，UI 只是减少误操作和暴露。 |
| 审批路径优先回归 | 稳健 | 已有保护不应为了“代码统一”被迫重构；只在等价性可证明时才共享新策略。 |
| 红线→策略→写边界→UI→回归→交付 | 风险递减 | 每批都有可观测结果和停止点，故障定位面小，且不会在 UI 完成时误报安全修复完成。 |

## 5. 剩余风险与实施门禁

| 剩余风险 | 等级 | 判断 | 门禁 |
| --- | --- | --- | --- |
| 红线 fixture 把 actor 误建成种子/全局 admin | 高 | 会导致漏洞用例假通过，是本次已暴露的主要测试风险。 | 用非保留用户名、真实 UserGroup 行及显式 actor 类型断言；旧代码上必须稳定红。 |
| 只在 route 层加守卫，未来新调用方绕过 | 中 | 当前生产调用方数量有限，但只靠代码评审不是长期保证。 | S2 用服务层 actor-aware 校验器作为唯一策略，S4 登记全部写入调用方；新入口必须复用。 |
| actor 在授权检查后被并发降权 | 中-低 | 数据库回读缩小陈旧 Session 窗口，但本需求没有许诺串行化或解决编辑多 commit。 | 守卫紧邻第一个写入；文档明示剩余竞态，禁止宣称强原子保证。 |
| 审批从 Session 逻辑迁移时行为回退 | 中 | 现有保护是正确基线，不必为了形式统一贸然改动。 | S4 默认只回归；若迁移，需补齐真实 actor DB fixture 和单条/批量全矩阵。 |
| 定向基线含缺表异常日志 | 低 | 当前容错使测试通过，但会干扰安全用例失败归因。 | S0 完善内存库建表，红线命令不得依赖容错日志证明失败。 |

## 6. 分批计划专业性审查

| 批次 | 审查结论 | 不得弱化的要点 |
| --- | --- | --- |
| S0 | 必要且应单独提交 | 旧代码必须只在真实漏洞路径红；保留种子 admin 允许期望；消除 fixture 缺表噪声。 |
| S1 | 拆分合理 | 策略函数无 Session/DB/事务副作用；actor 与 target 必须是独立输入。 |
| S2 | 安全核心 | 数据库当前 actor 状态、写入前拒绝、零副作用断言缺一不可；不声称解决事务原子性。 |
| S3 | 用户体验增强 | 必须依赖 S2；模板不渲染而非仅 CSS/JS 隐藏；JS 要验证 option 缺席路径。 |
| S4 | 决定是否有遗漏 | 搜索结果必须形成调用方登记；审批优先等价回归，不为代码形式统一扩大风险。 |
| S5 | 交付闭环完整 | 必须用多组 Biz Admin 和非种子全局 admin 实际操作；包含直接 POST 反向验证、截图、复盘、可验证本地环境。 |

## 7. 最终建议

1. **批准方案本身：**rev.2 的权威矩阵、范围边界和分批次序无需重写，可作为实施基线。
2. **实施前只需用户明确确认：**本评估不代替设计确认，当前不应修改业务代码。
3. **S0 作为硬门禁：**先证明非种子 Biz Admin 的新增与编辑路径在旧代码上真红，再写修复。
4. **安全修复与事务优化继续分离：**本轮只保证“无权 actor 在任何写入前被拒绝”，不借机解决 no-op 或多 commit。
5. **交付判定保持严格：**没有调用方清单、浏览器双角色证据和 7 要素复盘，不得标记完成。

**尚未授权实施：**本文是对设计 rev.2 的专业评估，未修改 `app/` 或 `tests/`。后续只能在用户明确确认设计后从 S0 开始。
