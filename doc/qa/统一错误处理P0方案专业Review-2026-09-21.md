# 统一错误处理 P0 方案专业 Review

结论：方案方向正确，但当前计划**不能直接实施**，需要先修订接口清单、trace\_id 现状、API 兼容策略和事务验收边界。

## 1. Review 方法

对照真实的 `app/__init__.py`、`datas/utils/json.py`、`app/decorated.py`、`app/api/views.py`、`app/rbac/views.py`、`app/rbac/services.py` 和 `common-redesign.js`，逐项核对计划中的接口、响应和流程假设。

## 2. 已确认正确的部分

- 错误契约需要同时具备稳定 code、可读 message、脱敏 detail 和 trace\_id。
- 数据库异常必须 rollback 并停止成功路径。
- 前端需要统一处理 Ajax、普通表单、非 JSON、超时和网络失败。
- 保留旧 `errcode/errmsg` 作为兼容字段是合理的。

## 3. 必须修订的准确性问题

| 问题 | 证据 | 影响 | 修订 |
| --- | --- | --- | --- |
| trace\_id 被计划重复建设 | `app/__init__.py::create_app` 已在 `before_request` 生成/透传 `g.trace_id` 并写入 logging context。 | 若重新实现会产生两个 ID，日志与响应可能不一致。 | P0-A 改为复用现有 g.trace\_id，补充响应 header/JSON 传递与日志字段测试。 |
| 接口清单不完整 | 真实写接口还包括 `/rbac/api_token/reset`、`/rbac/users/reset_password`、`/rbac/users/reset_token`、注册审核 approve/reject/batch、`/cron_del`、`/cron_batch_del` 等。 | 只迁移计划表中的接口会留下未治理的人工写入入口。 | 按路由扫描生成完整清单，逐个标记 response/事务/浏览器验收状态。 |
| API 状态码假设有兼容风险 | `api_return` 当前默认只生成 JSON，许多业务错误即使 errcode=1 仍是 HTTP 200；`api_deal_return` 也固定旧 envelope。 | 直接改为 400/500 可能破坏现有 API 客户端。 | 先保持旧 HTTP 状态；新增错误字段和版本/Accept 能力后，再评估状态码切换，必须标注 API Breaking Change。 |
| “完整 traceback”边界不够严谨 | `logger.exception` 会记录异常上下文，但部分路径把 `str(e)` 拼入业务内容或通知。 | 可能把 SQL、URL、凭据或内部路径暴露给操作人。 | 日志上下文也要统一脱敏；原始异常只允许受控日志 sink，不允许进入 job\_log/通知/响应。 |
| scheduler 回滚描述过于抽象 | 现有服务有“先 DB 后 scheduler”和补偿逻辑，但各函数实现不同。 | 统一 commit helper 不能自动解决外部副作用。 | 按每个操作定义状态机和补偿动作，逐接口测试 DB 成功/scheduler 失败。 |

## 4. 方案严谨性评估

**总体评级：B+，修订后可实施。**契约方向和失败闭环正确，但当前计划把“公共基础设施改造”误当成“所有接口自动获得一致行为”。真正的风险在调用方迁移、旧 API 兼容、非 Ajax 表单和 scheduler 外部副作用。

### 建议的严谨实施顺序

1. 先建立路由登记表：扫描所有 POST/写操作，列出入口、service、commit 点、成功副作用和当前响应格式。
2. 复用现有 trace\_id，仅补响应传播和测试，不重复造轮子。
3. 先扩展错误 envelope，不立即改变 HTTP 状态码。
4. 选择一个任务接口和一个 RBAC 接口做垂直切片，验证日志→响应→弹窗全链路。
5. 再按清单迁移其余接口，任何未迁移接口不得标记 P0 完成。

## 5. 修订后的 P0 关闭条件

- 完整写接口清单覆盖率 100%，每个入口有迁移状态。
- 响应中的 trace\_id 与 `g.trace_id`、日志 trace\_id 三方一致。
- 旧 API 字段兼容测试通过，任何 HTTP 状态码变化单独标记 breaking change。
- 每个 commit 异常均能证明 rollback，且成功副作用不会继续执行。
- 任务、RBAC、标签/分组、Token 和审核至少各有一条浏览器失败路径。
- 日志/业务内容/通知/响应均通过敏感字段脱敏测试。

## 6. 最终结论

方案本身专业方向成立，但原实施计划还不够严谨。修订上述五点后，P0-A 应从“新增 trace\_id”改为“复用并传播现有 trace\_id”；P0-C 应从“统一 commit helper”改为“逐接口状态机 + 补偿验证”；API 状态码必须延后处理，避免未经确认的兼容性破坏。
