S-5 API 角色权限校验

P0 安全 状态：已交付 · 编号：R5-S-5 · 日期：2026-08-28 · 关联：OPT-P2-10（RBAC v4）

1. 问题

Web UI 的 RBAC 权限体系通过 @require_permission('cron:write') 等装饰器，在视图层强制校验用户角色是否拥有对应能力（如 cron:write、cron:retire）。

API 层（app/api/views.py）的所有端点仅调用 check_api_scope(cron_info) 做组可见性（scope）校验，完全缺失角色能力校验。这意味着持有任何角色的 API Token 的用户，只要任务在其组内可见，就能执行任意操作。

2. 根因

API Token 鉴权系统（app/api/__init__.py）的设计历史：

  • 初版 API 只有一个全局 api_access_token（conf.ini），等同于 admin，无角色概念
  • OPT-P2-10 引入 RBAC 用户 Token 后，_resolve_user_token() 正确解析了 user_role、group_ids 等信息存入 request._api_scope
  • 但 check_api_scope() 只实现了 scope（组可见性）层面的校验，从未调用 effective_permissions() 做能力校验
  • Web 侧 @require_permission 是视图装饰器，API Blueprint 没有对等的装饰器或拦截器

3. 方案

3.1 新增 check_api_permission(required_perm)

在 app/api/__init__.py 新增函数，复用 Web 侧 effective_permissions()：

def check_api_permission(required_perm):
    """检查当前 API scope 的角色是否拥有指定权限。

    全局 token（role='admin'）直接放行。
    用户 token 依据 user_role + username 计算 effective_permissions。
    返回 None 表示允许，否则返回 403 JSON 响应。
    """
    scope = getattr(request, '_api_scope', None) or {'role': 'admin'}
    if scope.get('role') == 'admin':
        return None
    from app.rbac.policy import effective_permissions
    user_role = scope.get('user_role', '')
    username = scope.get('username', '')
    perms = effective_permissions(user_role, username=username)
    if required_perm not in perms:
        from datas.utils.json import api_return
        return api_return(errcode=1, errmsg='权限不足'), 403
    return None

3.3 调用位置

权限检查应在 scope 检查之前，因为权限是全局性的（不依赖特定资源），scope 是资源级的。

@api.post('/cron/status')
@api_deal_return
@api_data_form(CronStatusIn)
def cron_status(form_data):
    from . import check_api_permission, check_api_scope   # 新增 check_api_permission
    denied = check_api_permission('cron:write')             # ← 新增：角色能力校验
    if denied:
        return denied
    # ... 后续 scope 校验和业务逻辑不变

明确不做：

  • 不修改 GET 端点（所有角色已有读权限）
  • 不修改全局 token（role='admin'）的行为
  • 不修改 check_api_scope() 现有逻辑
  • 不引入 API 端点级的细粒度权限（如 api:cron:write），复用 Web 侧权限字符串

7. 风险

  • 向后兼容：如果现有自动化脚本使用 Viewer/Operator Token 调用写端点，升级后会收到 403。这是预期行为，属于安全修复而非破坏性变更。RELEASE_NOTES 需标注 ⚠️ API Breaking Change
  • 全局 Token 不受影响：使用 conf.ini 中 api_access_token 的调用方不受任何影响
  • 回滚方案：删除 check_api_permission() 调用即可恢复原行为
