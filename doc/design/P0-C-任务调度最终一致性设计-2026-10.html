1. 问题、目标与范围

任务写入与 scheduler 应用无法原子提交。DB commit 成功后 scheduler 失败，或 scheduler 成功后状态写回失败，都不能称作 rollback；并发旧操作可能覆盖新配置。目标是持久化期望状态、记录收敛状态，用 generation 栅栏和对账恢复一致性。非范围：撤销已发 HTTP、取消越过栅栏的 in-flight 执行、绕过此流程直接改 DB/scheduler。

2. 状态机与成功边界

validate → 原子持久化期望版本与 PENDING → 确认提交成功 → 应用 scheduler → 按 generation 条件写回 READY → success；异常按下表处理
状态语义
UNKNOWN存量任务尚未证明与 scheduler 一致。
PENDING期望配置已持久化，尚未确认应用。
READY同 generation 已证明收敛。
SYNC_FAILED已成功持久化的同步失败标记；不能写库时不会自动进入此状态。

成功响应与成功 operation log 的前提是 READY 且 desired_generation=applied_generation。已 commit 数据不能宣称已回滚。

3. 并发、迁移与对账流程

  • 每次配置改变获得新 generation；READY/SYNC_FAILED 仅允许按任务 ID + 预期 generation 条件写回，影响 0 行即旧操作过期。
  • scheduler 应用前后重核 generation；同任务串行化或由对账器按最新期望收敛。
  • 迁移先加字段，存量 UNKNOWN；只读 reconciliation 输出“可证明匹配/不匹配/无法证明”，仅匹配者写 READY。
  • 对账比较实际 trigger、参数/配置指纹与 generation，不能只看同名 job。
  • generation 只能阻止未越过检查点的旧执行；已越过或已发请求者不可撤销，必须如实记录。

4. 实施前 API 验证与分批

当前 cron_do、cron_service、scheduler 封装的真实 API 行为必须逐项 Read 后才能写实现调用；禁止凭印象使用 scheduler 方法或推断 next_run_time 语义。

批次退出条件

5. 验收、风险与确认点

必须注入 DB commit、scheduler apply、READY 写回、generation 不匹配、对账和重试失败；断言无成功响应/审计错配。迁移 SQL 必须 SQLite/MySQL 双后端验证。确认后只进入 C-0；C-1 前需再次确认具体字段、迁移和 scheduler API。

6. C-0 数据与锁决策清单

当前 CronInfos 有任务配置与状态字段，但没有 scheduler 收敛/generation 字段；下列是 C-0 待确认的新增模型，不能先写迁移或删除旧字段。

候选字段独立语义默认/约束
scheduler_sync_state期望配置与 scheduler 的证明状态非空，存量 UNKNOWN；不等价于业务启停状态。
desired_generation最后持久化的期望配置版本非空，从 0 起；每次配置变动递增。
applied_generation最后已证明应用的版本可空；不得用 0 冒充已应用。
scheduler_error_code / scheduler_sync_updated_at / config_fingerprint最近失败分类、证明时点与实际配置比较依据可空；值域、索引、保留期由 C-0 冻结。

双后端与锁：C-0 必须基于现有迁移入口验证 SQLite/MySQL 的加列、默认值、回填和索引语法，不得写只适用于 SQLite 的 SQL。现有 single_task 使用 Redis 锁且 TTL 为两分钟、没有续租；C-0 必须以“执行超过 TTL、进程异常、重试并发”的测试决定它是否可作为任务串行化机制。在决定前不增加第二把锁、不假定该锁能保护 generation。

C-0 输出与风险：完成实际 scheduler API 证据、精确条件更新语义、迁移脚本双后端演练、锁决策、reconciliation 命令/权限/重试策略和完整故障矩阵后，才可提交 C-1 设计确认。最大风险是把业务状态误当作收敛状态、用同名 job 代替配置证明、或让过期操作写回 READY；相应验收必须覆盖这些反例。

失败状态转换与恢复验收

故障阶段持久化事实与允许行为
初次提交确定失败保持旧期望，不应用新 scheduler；返回失败，不声称新增 PENDING/SYNC_FAILED。
初次提交结果不确定不得应用或盲目重复写入；返回结果待核实，恢复连接后读取期望配置与操作证据。C-0 冻结用于判定本次写入的操作标识/证据方案。
PENDING 已提交、scheduler 应用失败按相同 generation 尽力写 SYNC_FAILED；再次写库失败时保留已知 PENDING 事实，安全告警，由对账恢复。
scheduler 已应用、READY 写回失败/不确定不回滚已提交配置、不报告成功；恢复后对照持久化版本及实际配置，可能仍为 PENDING，也可能 READY 已落库；不能假定 SYNC_FAILED 已写入。
条件写回影响 0 行旧操作过期，不覆盖新状态；按最新期望收敛，不能把旧操作记为当前成功。

对账必须处理 UNKNOWN、PENDING、SYNC_FAILED，并识别 READY 后实际配置漂移；并发 UI/API/对账器使用相同配置版本与所有权约束。generation 递增必须在持久化层原子完成，禁止只在内存读取后加一。锁只用于执行串行化不自动等于配置更新锁；C-0 必须验证全部修改者和 TTL 失效场景。

C-01：首次提交失败 scheduler 未调用。C-02：应用失败且失败状态写回再次失败，状态不得伪报。C-03：READY 提交结果未知，通过重读和对账恢复。C-04：并发两个编辑及对账，旧版本不能写 READY。C-05：SQLite/MySQL 迁移、存量 UNKNOWN 和锁超时恢复。拟新增 tests/test_scheduler_consistency.py，命令 python -m unittest tests.test_scheduler_consistency -v；C-0 详细设计记录到本文件，验收证据 doc/qa/scheduler-consistency-acceptance.html。当前均未执行业务测试，C-1 仍待详细机制确认。
