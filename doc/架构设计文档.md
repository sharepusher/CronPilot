## 1. 文档说明

**目的：**为开发、运维、集成方提供 CronPilot 的结构性视图，说明模块边界、运行时拓扑、数据流向及扩展点。

**读者：**后端工程师、SRE、架构师、需对接回调的业务研发。

**范围：**应用层（`app/`）、数据层（`datas/`）、配置与容器化部署；不包含业务回调服务内部实现。

| 术语 | 含义 |
| --- | --- |
| 调度 Job | APScheduler 中 id 为 `cron_{cron_infos.id}` 的持久化任务 |
| 回调 | 触发时对 `req_url` 发起的 HTTP GET |
| 双库 | `cron_db_url`（JobStore）与 `cron_job_log_db_url`（业务 ORM） |
| 体验版 | `is_dev=1`，禁用秒级字段 |

## 2. 架构目标与约束

### 2.1 设计目标

| 目标 | 架构手段 | 源码体现 |
| --- | --- | --- |
| Crontab 语义兼容 | 字段级 Cron + APScheduler cron trigger | `views.py` 校验 + `scheduler.add_job` |
| 可视化运维 | SSR Web + Session 鉴权 | `main/views.py`、templates |
| 自动化集成 | REST API + access\_token | `api/views.py` |
| 水平扩展 | Redis 任务互斥 + 文件锁拉取 Job | `single_task`、`CuBackgroundScheduler` |
| 故障可感知 | 关键词检测 + 三通道推送 | `crons.cron_do`、`send_text` |
| 低部署成本 | Docker + Supervisor + 默认 SQLite | Dockerfile、docker-compose |

### 2.2 约束条件

- 回调仅支持 **GET**，超时固定 **120s**（`requests.get(..., timeout=120)`）
- 集群模式要求 MySQL JobStore + Redis，SQLite 仅适合单机
- 每 Gunicorn worker 独立启动完整 Scheduler（非集中式 Master）
- Web 鉴权为单密码 Session，无 RBAC

```
                    │           运维人员 / 开发者                  │
                    │    (浏览器访问 Web 管理界面)                  │
                    └────────────────────┬─────────────────────┘
                                         │ HTTPS/HTTP
                                         ▼
┌─────────────┐              ┌─────────────────────────┐              ┌─────────────────┐
│  conf.ini   │──配置────────▶│   CronPilot 系统      │──HTTP GET───▶│  业务回调服务    │
│  (本地文件)  │              │  定时调度 + 日志 + 告警   │◀──响应体────│  (用户自有 API)  │
└─────────────┘              └───────────┬─────────────┘              └─────────────────┘
                                         │
              ┌──────────────────────────┼──────────────────────────┐
              │                          │                          │
              ▼                          ▼                          ▼
     ┌────────────────┐        ┌────────────────┐        ┌────────────────────┐
     │ SQLite/MySQL  │        │     Redis       │        │ 企微 / 钉钉 / WebHook │
     │  (任务+日志)   │        │  (集群分布式锁)  │        │   (异常通知)          │
     └────────────────┘        └────────────────┘        └────────────────────┘

外部系统还可通过 REST API（/api/cron*）编程式管理任务，无需经过 Web UI。
```

系统在生态中的角色是 **调度编排中枢（Orchestrator）**：不执行业务逻辑，只负责按时间表触发 HTTP 调用并审计结果。

## 4. 容器架构（Level 2）

```
┌──────────────────────────────── Docker Host / 物理机 ────────────────────────────────┐
│  Supervisor (nodaemon)                                                                │
│    └── docker_start.sh                                                                │
│          ├── flask db migrate / upgrade  (首次初始化 migrations)                      │
│          └── gunicorn -c docker_gun.py manage:app                                     │
│                ├── Worker 1 (gevent) ──► Flask App + APScheduler Instance             │
│                ├── Worker 2 ...                                                       │
│                └── Worker N (docker: 4, gun.py本地: 2)                                │
│                                                                                       │
│  每个 Worker 进程内：                                                                  │
│  ┌─────────────────────────────────────────────────────────────────────────────────┐ │
│  │  WSGI Layer: Flask Application (create_app)                                      │ │
│  │    ├── Blueprint: main  (/, Web UI)                                              │ │
│  │    ├── Blueprint: api   (/api, JSON API)                                         │ │
│  │    ├── SQLAlchemy ORM  → cron_job_log_db                                         │ │
│  │    └── Flask-APScheduler → CuBackgroundScheduler                                 │ │
│  │              ├── SQLAlchemyJobStore → cron_db (apscheduler_jobs)               │ │
│  │              ├── ThreadPoolExecutor (max_workers=30)                             │ │
│  │              └── portalocker(scheduler.lock) 进程间互斥拉取 due jobs             │ │
│  └─────────────────────────────────────────────────────────────────────────────────┘ │
│                                                                                       │
│  文件系统：datas/logs/{info,error,server}.log  |  scheduler.lock  |  caches/         │
└───────────────────────────────────────────────────────────────────────────────────────┘
```

### 4.1 运行时双进程模型说明

**重要：**Gunicorn 多 worker 意味着同一主机存在 **N 个 APScheduler 实例**。它们通过 `scheduler.lock`（portalocker 非阻塞排他锁）保证**同一时刻仅一个进程**执行 `_process_jobs()` 拉取到期任务；任务执行函数 `cron_do` 在集群模式下再由 Redis `@single_task` 保证跨节点互斥。

- `admin_base.html` — 全局静态资源、GV 变量

- `api/views.py` — cron CRUD、status、add\_log

#### 调度层组件

- `app/__init__.py` — scheduler 生命周期
- `config.py JOBS` — 内置维护任务
- `CuBackgroundScheduler` — 锁 + date 任务收尾

#### 执行层组件

- `crons.cron_do` — HTTP 回调主路径
- `get_cronpilot_sign` — 回调签名

## 7. 调度子系统架构

### 7.1 触发器策略

| 业务模式 | 判定条件 | APScheduler | 字段映射 |
| --- | --- | --- | --- |
| 一次性 | run\_date 非空 | date | run\_date=字符串时间 |
| 周期 | 至少一个 cron 字段 | cron | day, day\_of\_week, hour, minute, second 非空则传入 |

### 7.2 执行器与并发

| 参数 | 值 | 影响 |
| --- | --- | --- |
| SCHEDULER\_EXECUTORS | threadpool, max\_workers=30 | 同进程最多 30 并发执行任务 |
| max\_instances | 20（per job） | 单任务最多 20 个重叠实例 |
| misfire\_grace\_time | 50s | 错过触发 50s 内仍可补跑 |
| coalesce | False | 积压触发不合并，可能连续执行 |

### 7.3 内置守护任务

| ID | Cron | 职责 |
| --- | --- | --- |
| cron\_check | \*/30 分钟 | JobStore 与 cron\_infos 对账，孤儿任务标 -1 |
| cron\_del\_job\_log | 每 8 小时 | 按 job\_log\_counts 删历史 |
| cron\_check\_db\_sleep | 每 15 秒 | SELECT 1 探活 + 告警 |

## 8. 集群与高可用架构

```
  Node A (Gunicorn×4)                    Node B (Gunicorn×4)
  ┌─────────────────────┐               ┌─────────────────────┐
  │ scheduler.lock       │               │ scheduler.lock       │
  │ (本机仅1 worker拉取)  │               │ (本机仅1 worker拉取)  │
  └──────────┬──────────┘               └──────────┬──────────┘
             │                                      │
             └──────────────┬───────────────────────┘
                            ▼
                    ┌───────────────┐
                    │     Redis      │
                    │ task:cron_do:  │
                    │   {cron_id}    │  TTL 120s
                    └───────────────┘
                            │
             ┌──────────────┴──────────────┐
             ▼                             ▼
    ┌─────────────────┐           ┌─────────────────┐
    │ MySQL JobStore │           │ MySQL 业务库     │
    │ (共享调度状态)  │           │ cron_infos/logs │
    └─────────────────┘           └─────────────────┘
```

### 8.1 两层互斥的设计 rationale

| 层级 | 机制 | 解决的问题 |
| --- | --- | --- |
| L1 进程间 | portalocker + scheduler.lock | 同机多 Gunicorn worker 重复 poll due jobs |
| L2 节点间 | Redis SET NX EX + @single\_task | 多机同时执行同一 cron\_do |

局限：非强一致 Leader 选举；Redis 锁 TTL 120s 内进程崩溃可能导致短暂空窗或重复（取决于崩溃时机）。生产环境建议监控 Redis 与调度延迟。

## 10. 部署架构

### 10.1 推荐拓扑

| 场景 | 拓扑 | 存储 |
| --- | --- | --- |
| 开发/演示 | 单容器，1 worker | SQLite 双文件 |
| 生产单机 | 1 主机 Supervisor + Gunicorn gevent×2~4 | SQLite 或 MySQL |
| 生产集群 | ≥2 节点 + 负载均衡（仅 Web）；调度依赖共享 DB+Redis | MySQL + Redis 必须 |

### 10.2 端口与入口

| 环境 | 绑定 | 说明 |
| --- | --- | --- |
| Docker | 容器 :80 → 宿主机映射（如 5002） | docker\_gun.py |
| 本地 gun.py | 0.0.0.0:5860 | 2 workers gevent |

## 11. 横切关注点

| 关注点 | 实现 | 缺口 |
| --- | --- | --- |
| 日志 | TimedRotatingFileHandler → datas/logs | 无集中式 ELK 集成 |
| 监控 | 无内置 metrics | 需外挂探活 / 日志告警 |
| 安全 | Session 密码、API token、回调 MD5 签 | 无 HTTPS 强制、无 RBAC |
| 配置 | conf.ini 静态文件 | 无热更新、无密钥管理 |
| 国际化 | 中文 UI | 无 i18n |

## 12. 架构决策记录（ADR）

| ID | 决策 | 理由 | 代价 |
| --- | --- | --- | --- |
| ADR-01 | 选用 APScheduler 而非 Celery Beat | 轻量、内嵌 Flask、Crontab 语义直接 | 多 worker 需自研锁 |
| ADR-02 | HTTP GET 回调而非 Agent 拉取 | 集成简单，防火墙友好 | 无请求体、幂等需业务保证 |
| ADR-03 | 双数据库 URL | JobStore 与业务 schema 解耦 | 运维需维护两套连接 |
| ADR-04 | SSR 管理台而非 SPA | 2019 前后主流、部署简单 | 前端体验与可维护性弱 |
| ADR-05 | portalocker + Redis 双锁 | 渐进式支持集群 | 语义复杂，调试难度大 |

## 13. 与 Plombery 架构对照

对照基准：Plombery `docs/architecture.html`（v1.0 · 2026-05）及 `src/plombery`、`frontend/src` 源码。
页面级交互、API 契约、代码路径的**完整 16 章对比**见
<Plombery深度对比分析.html>。

### 13.1 架构范式差异（C4 视角）

| 视图 | CronPilot | Plombery |
| --- | --- | --- |
| 系统角色 | 外部**编排中枢**：触发业务 HTTP，不执行业务逻辑 | 嵌入式**执行运行时**：在用户 Python 进程内跑 Pipeline |
| 容器（运行时） | Gunicorn 多 worker × 每 worker 一套 Scheduler | Uvicorn 单 worker × AsyncIOScheduler 与 FastAPI 同循环 |
| 外部依赖 | 业务回调 URL、可选 Redis/MySQL、通知通道 | 可选 OAuth IdP、Apprise 通知；无「回调农场」 |
| 前端容器 | 无独立前端服务（Jinja SSR 同进程） | React SPA 静态资源由 FastAPI 挂载 |

### 13.2 分层架构对照

```
CronPilot                          Plombery
────────────────────────────────────────────────────────────
表现  Jinja2 + jQuery (SSR)              React 19 SPA + TanStack Query
接口  Flask main (HTML) + api (JSON)     FastAPI REST /api + Socket.IO /ws
领域  CronInfos + cron_do(HTTP)          Pipeline/Task/Trigger + executor.run
调度  CuBackgroundScheduler + ThreadPool  AsyncIOScheduler + async run()
数据  cron_infos / job_log (DB)          pipeline_runs (DB) + .data/runs/ (FS)
横切  conf.ini / 企微钉钉 / Redis锁       Settings yaml / Apprise / contextvars
```

### 13.3 前后端交互架构

| 维度 | CronPilot | Plombery |
| --- | --- | --- |
| 交互模式 | 多页 SSR；表单 POST → JSON `{errcode,errmsg,url}`（`js-ajax-form`） | SPA；REST JSON + HTTP 状态码；422 字段级错误 |
| 任务配置 UI | Web 动态 CRUD `cron_infos` | 代码 `register_pipeline`；UI 仅展示与手动 Run |
| 运行观测 UI | 日志表 + iframe 明细；无 Run 状态机页面 | RunsList + WS `run-update`；LogViewer + WS `logs.{id}` |
| 认证流 | 单密码 Session | OAuth2 Session（可关闭） |

### 13.4 调度与执行架构

| 项 | CronPilot | Plombery |
| --- | --- | --- |
| Job 函数 | `cron_do` → HTTP 客户端 | `run` → 循环 `_execute_task` |
| 拓扑 | 1 Job : 1 URL | 1 Trigger : 1 Pipeline : N Task（线性） |
| 成功语义 | 响应体 + error\_keyword；无 COMPLETED 状态 | Task 异常 → PipelineRun FAILED |
| coalesce | false | true |
| 多副本 | 文件锁 + Redis 锁（设计支持集群） | 文档禁止多 worker；无内置分布式锁 |

### 13.5 数据架构对照

| 数据 | CronPilot | Plombery |
| --- | --- | --- |
| 定义持久化 | DB 表（可 API 改） | 代码内存注册 |
| 运行记录 | `job_log`（回调响应 TEXT） | `pipeline_runs` + `tasks_run[]` |
| 大对象 | 塞进 content 字段 | 文件系统 `task.json`、`logs.jsonl` |
| 双存储 | JobStore DB + 业务 DB | SQLite 元数据 + .data 产物 |

### 13.6 部署拓扑对照

#### CronPilot

- Supervisor → Gunicorn gevent (N workers)
- 集群：共享 MySQL JobStore + Redis
- 无需 WebSocket 代理

#### Plombery

- Nginx TLS + Uvicorn workers=1
- 必须代理 `/ws` WebSocket
- 单卷：db + .data

### 13.7 ADR 级对照（为何选型不同）

| 决策点 | CronPilot 选择 | Plombery 选择 |
| --- | --- | --- |
| 执行位置 | ADR-02 HTTP 回调 | 进程内 Python（Library-first） |
| UI 技术 | ADR-04 SSR 简化部署 | SPA 内嵌包（单进程交付） |
| 扩展方式 | DB/API 动态任务 | 代码注册 Pipeline |
| 水平扩展 | ADR-05 双锁 | 单实例；扩展靠外置调度或未来 Redis 锁 |
| 可观测 | 日志表 + 关键词告警 | 双存储 + WS 实时 + Apprise 状态告警 |

### 13.8 架构层选型建议

| 架构诉求 | 更合适 |
| --- | --- |
| 异构微服务统一 Cron 入口、调度与业务解耦 | CronPilot |
| Python 数据管道、要强 Run 状态机与实时日志 | Plombery |
| 既要统一调度台又要 Python 多步管道 | CronPilot 触发 → Plombery `POST /api/pipelines/{id}/run` |

## 14. 可借鉴的架构优化方向

完整论证见 [产品优化需求（详版 PRD）](产品优化需求-借鉴Plombery.html)；
对比文档 [§17](Plombery深度对比分析.html#s17) 含差距总览与路线图。此处仅列架构层要点。

### 14.1 守正：必须保留

- HTTP GET 回调 + 跨语言；Web/API 动态 `cron_infos`
- 双锁集群、秒级 Cron、签名与 add\_log

### 14.2 出奇：优先借鉴（不改变执行模型）

| 领域 | 借鉴 Plombery | 架构落点 |
| --- | --- | --- |
| 可观测 | Run 状态机 + 结构化日志 | `job_log.status`、SSE、`/metrics` |
| 契约 | REST + OpenAPI + 422 | 统一 envelope、校验服务层 |
| 存储 | DB 元数据 + 文件大对象 | 超大响应落盘 |
| 安全 | OAuth 可选 | SSRF 白名单 + 密码哈希（P0） |
| 工程 | pytest + 新 Python | SQL 参数化、CI |

### 14.3 不借鉴

进程内 Pipeline、代码唯一任务定义、强制单 worker、全量 React 重写 —— 均会削弱 CronPilot 现有定位。
