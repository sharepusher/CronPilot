RBAC 批量审批失败项最终状态真值优化方案

日期：2026-10-27 · 状态：待用户确认 · 关联：R-04、四项 Review 闭环方案 §7

1. 问题

注册审批页的批量通过在出现部分失败时，一律显示“成功项已经生效，失败项保持原状态”。该断言不成立：approve_registration() 发现同名启用账号、失效的停用账号目标或用户名不匹配时，会将待审批申请写为 rejected、提交事务，然后仍以 ok=False 返回。批量层把所有 ok=False 聚为 failure，页面遂将“请求未获批准”错误等同于“记录未改变”。

2. 根因

当前服务响应只有动作成败布尔值，缺少数据库最终状态效果；_batch_failure_from_result() 只透传 id 与文案；模板又从 failure 集合推导状态未变。逐项文案虽包含“已自动拒绝”，但摘要与数据库事实矛盾，且前端若解析中文文案会形成不稳定契约。

3. 推荐方案

保留 ok 的既有定义：用户请求的 approve/reject 动作是否成功；新增稳定的最终处置字段，前端只消费结构化字段，不解析中文消息。

层变更关键语义
审批服务所有失败结果显式给出 disposition 与 final_statusauto_rejected/rejected 表示“未批准但已自动拒绝”；常规前置校验失败为 unchanged/pending；事务或未捕获异常为 unknown/null。
批量 View失败项原样映射 disposition/final_status；summary 新增三类失败计数changed_failure_count、unchanged_failure_count、unknown_failure_count 之和必须等于 failure_count；保留旧字段以维持调用兼容。
页面校验新增字段与逐项 disposition，并按计数渲染事实摘要不再出现绝对化“失败项保持原状态”；逐项显示“已自动拒绝 / 未改变 / 状态待核对”。

内部异常的 unknown 维持现有“刷新列表核对、不要立即重试”安全提示；不把异常误报为未改变。单条审批继续使用既有受控消息，不改变其跳转行为；本批只扩展批量 JSON 契约和批量页面展示。

4. 范围

包含不包含
批量通过/拒绝的失败项最终状态契约、结果摘要、逐项显示、接口和浏览器回归。自动拒绝的业务规则、审批 Scope、角色权限、数据库模式、单条审批页面布局与历史数据回写。

5. 分批实施

  1. B0 红线测试：构造“一条正常批准 + 一条同名冲突自动拒绝”，断言 HTTP summary 计数、失败项 disposition/final_status 与数据库 rejected 一致；同时覆盖 scope 拒绝的 unchanged 和异常的 unknown。
  2. B1 服务与 View：在自动拒绝、普通业务拒绝、内部异常三类出口赋予明确最终处置；集中校验计数守恒，禁止 View 从中文 msg 推断。
  3. B2 页面：扩展 JS 严格契约校验、摘要与逐项标签。页面仅使用既有 CSS token 和页面作用域样式。
  4. B3 验证与复盘：运行专项、Ruff、静态 UI 门禁、路由冒烟；以目标管理账号进行批量操作浏览器自动化并截图；完成复盘、Release Notes 和文档同步。

6. 验收标准

  • 自动拒绝项在 response 中为 ok=false 的 failure，但 disposition=auto_rejected、final_status=rejected；数据库记录同为 rejected。
  • scope/已处理/存储一致性等无写入失败项为 unchanged，最终状态如可确定则为 pending 或原已处理状态；不得被计入 changed。
  • 未捕获异常为 unknown，不承诺最终状态；三类失败计数严格守恒。
  • 部分失败页面摘要与每条详情不矛盾；页面上不再有“失败项保持原状态”的全称表述。
  • 旧的 success_count/failure_count/outcome 语义不变；所有 JSON 新增字段在 Release Notes 标注 ⚠️ API Breaking Change，并有契约测试。

7. 风险与控制

风险控制
以消息文本判断状态，中文文案调整即破坏页面只读取 disposition/final_status；JS 对枚举、计数与每项字段做 fail-closed 校验，格式异常提示核对列表。
异常后状态未知被错误标为未变，诱发重复提交unknown 单独计数和高风险提示；失败回调继续要求刷新核对且不自动重试。
新增 JSON 字段影响现有消费者保留原字段和 outcome；补充 Release Notes 的兼容性标注及服务/HTTP 契约测试。
把自动拒绝计作批量“成功”不改变 ok 和 success_count；它仍是 requested action 未成功，只是最终状态真实可见。

8. Before / After 页面与响应对比

BEFORE

批量通过：成功 1 条，失败 1 条。成功项已经生效，失败项保持原状态。

详情：#18 用户名已被占用，申请已自动拒绝。

摘要与详情、数据库状态互相冲突。

AFTER

按请求通过 1 条；未按请求完成 1 条。其中：已自动拒绝 1 条，未改变 0 条，状态待核对 0 条。

详情：#18 · 已自动拒绝 · 用户名已被占用。

响应：{disposition:'auto_rejected', final_status:'rejected'}；摘要、详情、数据库同源。

9. 方案评估结论

A，建议实施。这不是把错误文案换成模糊文案，而是补齐“请求动作结果”和“最终持久化状态”两个正交事实。方案将真值产生在拥有事务上下文的服务层，批量层只聚合，前端只呈现；边界清晰、可测试、不会改变自动拒绝或授权语义。相较于只删除该句或让前端匹配“自动拒绝”中文文本，结构化处置枚举可避免再次出现摘要与数据不一致。
