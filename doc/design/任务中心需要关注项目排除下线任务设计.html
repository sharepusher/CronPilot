任务中心需要关注项目排除下线任务设计

日期：2026-09-09　类型：问题修复设计　状态：已确认并实施

1. 问题

任务中心 Dashboard 的“需要关注的任务”面板会展示大量已经下线的异常任务。下线任务不再调度，也不应继续作为当前需要处理的异常提醒。

期望结果：下线任务（CronInfos.status = -1）即使历史健康记录仍为持续失败，也不出现在该面板；仍可在任务列表的“已下线”状态筛选中查看。

2. 根因与 API 假设验证

app/main/views.py 的 cron_list() 以 repo.top_failing(filter_arr, limit=5) 获取面板数据；filter_arr 仅包含 Scope、名称、状态、标签等列表过滤条件。

已读取并核对 app/repositories/cron_repository.py：top_failing() 当前只 Join JobHealth 并筛选 health_status == HEALTH_FAILING，没有状态条件。作为对照，同文件的 metrics()、count_consecutive_failing() 和 today_success_rate() 已明确使用 CronInfos.status != -1。因此本设计中的查询修改基于已验证的实际 API 与字段行为，不是凭印象假设。

3. 方案

推荐方案：在 CronRepository.top_failing() 的基础查询中增加 CronInfos.status != -1，使所有调用该 Repository 方法的“持续异常 Top N”结果统一排除下线任务。

不修改健康记录、不删除历史数据、不改变任务列表的状态筛选，也不改变 Scope 逻辑。面板标题数量由过滤后的结果自然计算，最多仍展示 5 条。

交互契约：无新增表单或前端交互；保留现有普通链接跳转到任务执行日志详情页。

3.1 SQL 与性能评估

修改后的核心 SQL 形状如下（实际 SQL 由 SQLAlchemy 按数据库方言生成）：

SELECT cron_infos.*, job_health.*
FROM cron_infos
JOIN job_health ON job_health.cron_info_id = cron_infos.id
WHERE job_health.health_status = 'failing'
  AND cron_infos.status != -1
  /* 既有 Scope / 名称 / 标签条件 */
ORDER BY job_health.consecutive_failures DESC,
         job_health.last_fail_at DESC
LIMIT 5;
  • 连接成本：job_health.cron_info_id 是主键，cron_infos.id 是主键；Join 使用索引/主键查找，不引入新的 Join 路径。
  • 过滤成本：新增的 cron_infos.status != -1 是低选择性状态过滤，通常在 Join 后完成；它不会单独触发全表排序或额外查询，但会减少进入 Top-N 排序的候选行。
  • 排序成本：现有查询已经按连续失败次数、最近失败时间排序并 LIMIT 5；本次不改变排序字段，因此不新增排序成本。当前模型未为 job_health.health_status 或排序组合声明索引，数据量较大时主要成本仍是健康表筛选/排序，而不是新增状态条件。
  • 索引决策：本次不新增索引，避免为单个低选择性状态谓词引入迁移和双后端维护成本。若生产执行计划显示 job_health 扫描或排序成为瓶颈，再单独提交索引设计，评估 (health_status, consecutive_failures, last_fail_at) 的 SQLite/MySQL 兼容性。

性能验收：在代表性数据量（包括下线异常任务占比较高和较低两组）上分别执行修改前后的 SQL/等价查询，记录 SQLite 与生产 MySQL 的 EXPLAIN（必要时 EXPLAIN ANALYZE）中的扫描行数、是否使用主键/索引、排序方式和总耗时。验收阈值为：结果语义符合第 6 节，查询次数不增加，P95 耗时不劣化超过 10%；若超过阈值，暂停实现并补充索引/查询方案评审。

4. 范围

文件变更
app/repositories/cron_repository.py“需要关注”查询排除 status=-1
tests/新增回归断言：运行中持续失败任务出现，下线持续失败任务不出现；必要时验证暂停任务既有语义不被改变
RELEASE_NOTES.md、对应 HTML/Markdown 文档记录用户可感知修复并保持双格式同步

明确不在范围：清理既有 JobHealth 数据、改变任务下线流程、修改统计卡片口径、修改任务列表“持续异常”筛选的既有业务规则。

5. 分批实施

  1. Batch 1：按本设计修改 Repository，并补充最小回归测试。
  2. Batch 2：运行定向测试、全量测试与必要的 Dashboard 路由冒烟；修复发现的问题并形成复盘。
  3. Batch 3：重启本地服务，用登录会话访问 http://127.0.0.1:5001/ 验证面板；同步 Release Notes 与 HTML/Markdown 文档。

6. 验收

  • 构造一个 status=1 且健康状态为 failing 的任务：面板展示该任务。
  • 构造一个 status=-1 且健康状态为 failing 的任务：面板不展示该任务，面板数量不计入该任务。
  • 访问任务列表的“已下线”状态筛选：该任务仍可查询，证明只是提醒口径过滤。
  • 现有 Scope 过滤和最多 5 条排序行为保持不变。
  • 验证命令至少包括定向回归、ruff check app/、python scripts/smoke_routes.py --check；交付前按仓库要求重启服务并提供 Agent 自证输出。

7. 风险与回滚

风险低：仅增加 SQL WHERE 条件，可能导致面板数量减少，这是预期行为。若发现业务需要继续追踪下线任务，可回滚该单一条件；历史健康数据和任务数据不会受影响。

实施结果：已按本设计完成实现与回归验证；下线任务仍保留在任务列表的状态筛选中，但不再进入“需要关注的任务”面板。
