RBAC 注册审批 R2-4 浏览器最终验收与 F-02 关闭方案

版本：rev.2 · 日期：2026-10-26 · 状态：实施与验收完成，F-02 已关闭 · 父方案：Scope 精确化 rev.20 · 验收：R2-4 QA · 前序：R2-3 已完成

实施结果：五类真实浏览器角色矩阵、组 1 第二页、标题/侧边栏 badge、旧 Cookie 降权即时收敛全部通过；207 项相关回归、86/86 路由及 Ruff 通过，专用用户/申请/关联行清理后为 0/0/0。生产业务代码和 API 契约未改变。

1. 问题与目标

R2-0–R2-3 已证明单元、Repository、路由和静态调用图正确，但 F-02 是用户可见的信息隔离问题。浏览器中的真实 Cookie、模板上下文、侧边栏 context processor、筛选参数和数据库当前 actor 必须同时生效，才能证明问题真正关闭。

R2-4 的目标是用五类真实角色矩阵验证正向能力、反向隔离和旧 Session 收敛，冻结截图与 DOM 断言证据，完成父 Review、Release Notes、路线图和本地可验证环境。

2. 根因回顾与验证重点

  • 原缺陷一：CSV 子串匹配使组 1 命中组 10。
  • 原缺陷二：读取授权信任旧 Session，数据库降权或组收窄后仍可能扩大范围。
  • 原缺陷三：admin 子集在分页后过滤，造成页面行、total、页数和 badge 分裂。

因此浏览器验收不能只看“页面能打开”，必须同时检查可见用户名集合、不可见用户名集合、页脚 total、分页页数、标题 pending 数和侧边栏 badge。

3. 范围与非范围

纳入非范围
本地开发环境的五角色登录、真实 Cookie、筛选与分页、页面 DOM/截图、数据库降权后的同 Cookie 再访问、最终回归和文档关闭。不重新进行 MySQL 性能压测；不修改关联表结构、审批写入协议或页面布局；不将审计日志等其他领域的逗号 Scope 查询并入 F-02。

4. 测试数据与安全控制

  1. 使用统一前缀 r2_r4_ 创建专用资源组、角色账号和申请，避免依赖现有人工数据。
  2. 测试账号密码只在本地准备过程使用，不写入设计、QA、日志或截图。
  3. 记录创建的主键清单；验收后删除专用申请、关联行、UserGroup、用户和资源组。旧 Session 降权场景在专用账号上执行，不修改真实管理员。
  4. 数据准备完成后先运行关联表对账；数据清理后再次确认无 r2_r4_ 残留且本地服务仍可登录。

5. 五角色浏览器矩阵

角色场景正向断言反向断言
仅组 1 Biz Admin普通角色组 1、组 1+10 可见；admin 组 1 可见。仅组 10、admin 组 1+10、__ALL__ 不可见。
仅组 10 Biz Admin普通角色组 10、组 1+10 可见；admin 组 10 可见。仅组 1、admin 组 1+10、__ALL__ 不可见。
组 1+10 Biz Admin组 1、组 10、组 1+10 普通角色与 admin 子集均可见。__ALL__ 不可见；无关联/非法数据不进入页面。
全局管理员所有合法具体组申请和 __ALL__ 均可见。不得因为 scoped 查询切换丢失合法全局能力。
旧 Session 降权先以全局管理员登录并确认全量；保持同一 Cookie，将数据库当前关系降为仅组 1，再刷新。刷新后立即只保留组 1 合法集合；不得继续显示组 10、admin 超集或 __ALL__。

6. 页面 Before / After（锚定父 Demo §5 AFTER）

本设计承接父方案 Demo §5 AFTER，不改变布局。页面保持七列：选择、用户名、申请角色、申请业务组、岗位、申请时间、操作；关键样例仍是组 1 管理员只显示组 1 合法申请，组 10 申请不进入结果，行数、total、页数与 badge 同源。

BEFORE · 原风险

组 1 管理员可能同时看到组 1 与组 10；标题或侧边栏 badge、页脚 total 与实际行不一致；降权后旧 Cookie 仍显示全量。

AFTER · R2-4 验收目标

五角色每次访问的可见行集合与数据库当前授权一致；筛选和翻页不扩权；两处 badge、total 和页数与相同 Scope 的查询结果一致。

7. 执行步骤

  1. 环境基线：确认开发服务、登录 POST、数据库关联对账及 R2-3 回归正常。
  2. 准备隔离数据：创建专用组、五类账号和可区分的申请集合，记录期望可见集合及 pending 数。
  3. 浏览器矩阵：逐账号真实登录；验证“全部”、pending、approved、用户名搜索和需要时的第二页；保存关键截图与 DOM 断言。
  4. 旧 Session 场景：登录专用全局管理员后，在数据库中只改变该账号的当前组关系；保留 Cookie 刷新并验证立即收敛，随后恢复/清理专用账号。
  5. 回归与清理：运行 Scope、注册、会话撤销、侧边栏、CSRF、86 路由、Ruff、文档门禁；清理专用数据并再次实际登录。
  6. 关闭评审：逐项对照 F-02 完成定义；全部满足才将父方案、父 S0–S5 Review、Release Notes 与路线图标记为 F-02 已关闭。

8. 验收与停止条件

  • 每个角色必须记录：URL、数据库当前角色/组、可见用户名、不可见用户名、total、pages、标题 pending 数、侧边栏 badge 和截图。
  • 任何范围外用户名出现，或任何数量指标不一致，R2-4 判失败；不得用刷新、跳过数据或改预期消除失败。
  • 浏览器自动化无法真实保留 Cookie、切换账号或触发筛选时，先修复验证环境，不降级为只用 test client。
  • 测试数据清理不完整、登录页非 200、管理员 POST 登录失败或本地服务未保持运行，均不得交付。

9. 风险评估与回滚

  • 主要风险：专用数据误混入现有审批列表。通过唯一前缀、主键清单和清理后残留查询控制。
  • 旧 Session 操作风险：仅操作专用账号，不改种子 admin 或真实业务管理员。
  • 证据风险：截图可能含邮箱等申请信息；使用专用虚构数据，并在 QA 中只记录必要字段。
  • 回滚：本批预期无生产代码；若仅测试数据失败，删除专用数据即可恢复。若发现代码缺陷，停止并另立最小修复批次，不在 R2-4 中静默改动。

10. 完成定义

五角色矩阵全部通过；页面行、total、pages、标题与侧边栏 badge 一致；旧 Session 降权即时收敛；专用数据零残留；完整回归和文档门禁通过；本地服务可复验。满足以上条件后，才能关闭 F-02 并复评父 S5，不因 R2-2/R2-3 已完成而提前关闭。

完成判定（2026-10-26）：以上条件全部满足。可重复脚本、结构化结果与脱敏截图见 R2-4 QA；F-02 正式关闭。
