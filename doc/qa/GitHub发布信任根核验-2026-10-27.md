# GitHub 发布信任根核验

日期：2026-10-27 · 仓库：`sharepusher/CronPilot` · 本地基线：`061f73f` · 远端 `main`：`8e3a1b0` · 状态：**只读核验完成，远端发布信任根未闭环**

## 3. 核心风险分析

### 3.1 远端仍使用旧 workflow（P0）

本地提交完成不等于远端生效。在 `061f73f` 进入默认分支前，新 tag 仍会使用旧 workflow：构建、验证和发布共享写 token，缺少严格 tag 校验、Environment 隔离和远端资产内容比对。因此“当前不创建新 tag”是必须的停止条件。

### 3.2 分支与标签信任根未加固（P0）

发布 workflow 来自被 tag 指向的 Git 提交。当 `main` 无保护且无 ruleset 时，应用内的最小权限设计仍可被后续直接提交改写。只修 workflow 而不保护 workflow 的代码来源，不能形成完整供应链边界。

### 3.3 Environment 名称存在不等于审批存在（P0 核验）

GitHub 官方文档说明：workflow 引用不存在的 Environment 时，GitHub 会自动创建同名 Environment；普通 workflow 自动创建的 Environment 默认没有保护规则或 secrets。所以必须在首次 tag 演练前由管理员显式确认审批者和允许的部署分支/tag。

## 4. 建议的安全执行顺序

1. **先配置远端保护：**为 `main` 创建活动 branch ruleset，至少禁止 force push/删除并要求 PR；为 `v*.*.*` 创建活动 tag ruleset，限制创建、更新和删除主体。
2. **显式配置 `release` Environment：**设置 required reviewers，部署来源只允许受保护的发布 tag；不依赖 workflow 首次运行隐式创建。
3. **收紧 Actions 仓库默认值：**默认 `GITHUB_TOKEN` 只读；关闭 Actions 创建/批准 PR；保留 workflow 内 publish Job 的显式最小 `contents: write`。
4. **通过 PR 纳入 `061f73f`：**不在未保护 `main` 上直接 push 作为正常发布流程的范例。
5. **再做受控演练：**用新版本 tag 验证 build Job 无写权、publish Job 等待审批、资产回读后才解除 draft。该步会产生外部状态，须另行明确授权。

## 5. 管理员认证后的验收清单

| 对象 | 最低验收断言 | 不通过时的处理 |
| --- | --- | --- |
| Branch ruleset | 目标包含 default branch；enforcement 为 active；要求 PR；禁止 force push 和 deletion；bypass 主体最小化。 | 不 push 发布加固提交，不创建发布 tag。 |
| Tag ruleset | 目标模式覆盖 `v*.*.*`；active；限制 create/update/delete；bypass 主体是审核后的发布账号/应用。 | 停止所有新 tag 发布。 |
| `release` Environment | 存在 required reviewers；禁止自审（若计划支持）；部署来源限制正确。 | 不进行受控 tag 演练。 |
| Actions settings | Workflow permissions 为 read-only contents/packages；Actions 不可创建或批准 PR。 | 修正默认值后再推进。 |
| 远端 workflow | 默认分支已包含 `061f73f` 或其等价后继；workflow 显示两个 Job 及 `release` Environment。 | 不得用旧 workflow 创建新 Release。 |

## 6. 准确性与局限

- `protected: false`、空 ruleset、远端 commit 和远端 workflow 内容均是当前可重现的远端事实。
- Environment、Actions 默认权限和历史 tag protection 没有认证证据，本报告只标记“未验证”，不标记“不存在”。
- 本地 `origin/main` 与 GitHub 分支 API 均指向 `8e3a1b0`；`git ls-remote` 曾因一次 DNS 解析失败未返回，不影响 API 和本地远端跟踪引用的交叉结论。
