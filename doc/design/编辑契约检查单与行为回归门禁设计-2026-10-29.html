1. 现状、问题与根因

已核实：.github/workflows/unit-tests.yml 在相关路径的 push/PR 上运行 Python 兼容矩阵及 unittest discover；现有 user_edit_change_set、user_edit_scope_projection、user_edit_mysql_guard 均在发现范围内。因此“没有自动回归”并不准确。该 workflow 顶层有 paths 过滤，其 GitHub required 状态未在本轮查询，不能推定已配置。

scripts/verify_user_edit_group_preflight.py 已执行真实模板 JS，但只在隔离 DOM 拦截 Ajax，不连接服务；不能替代角色登录、确认和数据库断言。visual-regression.yml 负责截图比较，不能代替行为测试。MySQL 工具有专用库保护和业务验证，但锁释放增强设计仍待确认，其服务返回边界证据缺口不能冒称已补齐。

根因：规范、人工 Review、运行入口与合并条件缺少可追踪连接；全量绿测不能展示哪些条款真正被执行，缺失真实环境也可能只得到 skip。方案以检查责任、场景标识和结果证据建立连接，不靠搜索函数名判断正确性。

2. 可直接使用的检查单

作者在设计/PR 填 PASS、N/A 或 TODO；PASS 必须附精确实现位置和测试标识/本次运行链接，N/A 必须解释语义和替代保证。TODO 不可进入最终验收。Reviewer 逐项核对适用性，不接受作者仅填“全量已绿”。自动执行结果只来自 CI，人工 PASS 只是评审声明。

4. 分层门禁与改动分类

复用现有全量 unittest 兼容矩阵，保持原 job 不变。新增一个 Python 3.11 专项 runner 产生条款级结果，承担少量有意重复以获得稳定诊断；不再复制整个 Python 矩阵。暂不引入复杂通用测试框架、全站端点注册平台或新增运行时依赖。

层内容与触发通过条件
G0 适用性/契约检查每个 PR、main/master push 都执行；读取 git diff（base→tested SHA）、改名/删除的两侧路径。规则/契约文件变动也触发自身测试。无法分类时保守执行所有相关层或报错，不默认免测。分类报告有效；声明范围与选定层匹配；拟新增 runner 的自测覆盖改名、删除、坏 diff、缺基线、取消/skip 和缺报告。
G1 服务行为app/**、datas/**、tests/**、配置/依赖及编辑验证工具改动均执行。仅普通文档变更可 N/A；规范/分类器/映射改动至少执行 G0/G1。固定加载已有三个用户编辑模块，按 B01–B09 登记覆盖，不复制算法。固定模块存在、用例发现数非零、登记用例均执行且无 skip；失败/删除/无法导入阻断。测试数量变化需评审，不用历史固定数量当唯一正确性门禁。
G2 浏览器行为app/templates/**、app/static/js/**、样式及用户编辑路由/服务/Scope/policy/context、对应浏览器脚本和测试/依赖变动。包括纯后端影响页面的路径，不能只看模板后缀。实际模板 DOM preflight + 独立测试服务的目标角色登录/正反向/确认/原生回显；网络与 DB 断言全部通过。无浏览器或无样本不 skip。
G3 MySQL 事务RBAC services/views/policy/Scope/认证边界、datas 模型/迁移、DB相关配置/依赖、事务测试/专用 MySQL 工具变更。ORM 和 DB 依赖按保守规则升级。专用新空库真实通过业务事务、关系保留与 B08。B08 未实施前本层不得标“全部完成”。非事务普通 CSS/JS 不强制启动 MySQL。

分类器是保守的路径触发器，不是语义证明。所有新增/修改编辑行为还必须由作者/Reviewer 检查 C01–C10；新入口的测试映射与分类规则同 PR 修改。示例：只改 user_form→G1+G2；只改 update_user_management→G1+G2+G3；只改说明文档→G0，其他层明确 N/A。

场景映射契约：拟新增 tests/contracts/edit_contract_cases.json，每项记录稳定 case_id、适用入口、规范条款、执行层与测试完整标识。runner 必须将实际发现/执行的测试标识与映射逐项核对，禁止仅检索测试名称存在；必测项缺失、重复标识、所属层不符或被 skip 均阻断。该文件不接受人工 pass 值。首次只登记已有用户编辑入口；扩展新入口须补自己的业务断言，不能借基线通过冒称覆盖。

5. 稳定的合并检查与防假绿

拟新增 .github/workflows/edit-contract.yml，使用 pull_request、push main/master、workflow_dispatch；若仓库启用 merge queue，则补 merge_group 并按该事件的 base/head 计算。workflow 顶层不设 paths 过滤，子 job 根据 G0 结果执行；最终 Edit contract / required 必须使用 always 语义收集全部依赖结果。

只有 G0 有效且所有被选层都成功、报告齐全且 tested SHA 与当前 run 一致时才通过；被选层的 skipped/cancelled/failure/空报告一律不通过。不适用层必须有 G0 记录的理由，汇总不能简单把所有 skipped 当 success。整次 workflow 因提交信息或 Actions 平台而没运行，不能生成虚假的汇总成功；required 状态缺失应保持阻断。

GitHub 官方说明：required workflow 被 paths 过滤跳过时可能保持 Pending。因此不直接把现有带 paths 的 job 改成新的唯一 required。具体规则设置属于外部仓库管理，不从 YAML 存在推定已启用。

PR 清单内容真实与否仍由 Reviewer 判断；结构检查只能发现缺项，无法证明业务语义正确。规范/映射/关键测试被同一 PR 删除或弱化时须重点人工审查，runner 的自测与可审查的固定场景防止无意绕过。具有仓库管理权限者仍可能修改规则或绕过，不能承诺绝对不可绕过。

本期不引入解释自然语言的 PR 清单机器人；检查单完整性与 N/A 真实性由 Reviewer 把关，CI 自动阻断的是分类、映射和真实行为结果。PR 事件保留 head/base 身份，并明确报告被测试的是平台合并引用还是 head；从事件提供的基线计算实际差异，push 首次零 before 等无法取得基线时走保守分支。不得将历史 run 或别的 SHA 的 artifact 当当前证据。

6. 测试隔离、执行与结果格式

  • 权限：PR 执行无仓库秘密、GITHUB_TOKEN contents:read，checkout 不保留写凭据；不使用 pull_request_target 执行 PR 代码。fork 首次运行需平台批准时仍视为未完成。依据GitHub 官方安全说明。
  • 服务：G2 显式设置 CI 临时 SQLite、独立端口、随机测试 secret 和专用测试账号，只清理该 job 自己的资源；不使用 manage 导入开发配置，不调用接管本机5001的黄金路径脚本并行跑 UI。等待明确健康条件，不靠固定 sleep 判通过。
  • MySQL：job service 使用独立 MySQL 8/InnoDB；每次新建符合现有约束的专用 schema，随机凭据仅传入 job 环境，不打印 URL。验收账号限制在该 schema，允许测试所需 DML/建表、无 DROP；管理权限只用于 disposable 实例准备，结束由 job 生命周期销毁实例。
  • 反向校准：B08 遵循已有增强设计，需单独确认或与本方案明确一并确认后实施；不得把本轮“制定门禁”当作增强设计已确认。正式汇总全部强制前，负向版本必须能被检出。
  • 超时/重试：为 job、进程、网络/锁等待设明确上限；具体值在实施读取源脚本并按首次 CI 运行校准记录。禁止无限等候或业务失败自动重跑到绿；基础设施问题明确失败，可由维护者触发完整新 run。

runner 拟生成固定 JSON：schema_version、tested_sha、base_sha、selected_tiers、cases（case_id、test_id、tier、status、duration、reason）、environment、artifact_refs。pass/fail 只取 runner 的真实执行结果；文件中不得包含密码、签名载荷、Token 或个人资料。CI 临时 artifact 存截图/JSON/脱敏失败日志（建议保留7天），普通运行产物不 commit。报告生成失败或必需 artifact 未上传视为门禁失败；结果明确记录观测发生在 cleanup 之前。

8. 验收标准与风险

  1. 修改一个资料字段时，G1 检测到任何额外组DML/Token轮换/认证版本改变必须失败；构造只返回200但DB错的实现也必须失败。
