统一错误处理现状评估

评估基线：统一人工操作错误处理设计（2026-09） · 结论：未满足设计方案，不建议直接宣称完成

1. 评估范围与方法

检查 Flask 路由/服务层异常捕获、web_api_return/api_return 响应、Redesign Ajax 提交器、toast/确认组件、数据库提交失败路径及异常脱敏规则。采用静态调用链审查和现有测试结构核对，未修改生产代码。

2. 结论总览

设计要求现状等级
异常写入错误日志多数 service commit 异常使用 logger.exception，但没有统一操作上下文/trace_id；部分 view 只 warning 或吞掉后继续。P1
失败响应包含 code/detail/trace_id当前主要是 errcode/errmsg/result/data/url，没有统一 code、detail、trace_id。P0
前端弹窗提示失败Ajax 主要使用 toast 或字段内联错误；网络异常只提示“网络错误，请重试”，没有详情复制。P1
异常详情安全展示服务层多数只返回通用文案，但 cron 等路径仍把 str(e) 写入业务内容/日志，缺少统一脱敏契约。P1
写入失败回滚并停止后续业务部分服务层正确 rollback；profile 提交失败后仍继续构造成功页面，违反失败闭环。P0

3. P0 问题详细分析

P0-1 错误响应无法关联排查

datas/utils/json.py::json_response 只返回 errcode、errmsg、result/data/url；app/common/functions.py::web_api_return 进一步固定旧结构。路由和前端没有稳定的错误码、脱敏 detail 或 trace_id，操作人即使看到失败 toast，也无法把一次失败准确关联到服务端日志。

影响：无法按操作、资源和请求定位异常；不同页面文案相同但根因不同；支持人员只能人工搜索时间窗口日志。

P0-2 数据库写入失败后仍可能继续返回页面

app/rbac/views.py 的 profile 提交路径在 db.session.commit() 异常时只记录 warning 并 rollback，随后仍继续刷新上下文并返回表单响应，没有将失败状态传给统一错误呈现层。这会让操作人误以为保存完成。

影响：用户看到成功页面但数据未保存，可能重复操作或覆盖后续修改；日志和用户感知不一致。

4. P1/P2 问题

  • P1：common-redesign.js 失败路径主要调用 CpToast.error，没有设计要求的错误详情/trace_id/复制能力；普通表单与 Ajax 的失败呈现也未统一。
  • P1：大量 service 返回 {ok: False, msg: '创建失败'}，虽有完整 traceback，但缺少错误码和可反馈编号。
  • P1：app/crons.py 多处把 str(e) 拼入通知、日志或任务内容，未统一脱敏；需要区分内部日志详情与操作人可见详情。
  • P2：没有统一异常分类矩阵和浏览器 E2E 断言，现有测试偏向 JSON 状态，未证明“失败日志 + 弹窗 + trace_id”同时出现。

5. 方案对比评估

方案做法评价
A. 各页面局部补丁逐页追加 toast 文案和 try/except。短期快，但继续产生结构漂移，不采用。
B. 统一契约与渲染器新增错误码、trace_id、脱敏 detail；后端序列化器和前端错误弹窗统一消费。改动可控、可测试，符合已确认设计，推荐。
C. 全局异常拦截替代业务处理所有异常交给全局 500 handler。无法表达字段错误、权限错误和回滚语义，只能作为兜底，不可替代 B。

6. 修复顺序

  1. 先修 P0-1：建立 error_code、trace_id、脱敏 detail 和统一响应序列化。
  2. 再修 P0-2：所有 commit 异常必须返回失败并停止后续成功路径。
  3. 迁移 Redesign Ajax/普通表单到统一错误弹窗，支持复制 trace_id。
  4. 清理 catch-all 的原始异常输出，补齐异常矩阵和浏览器验证。

7. 验收标准

  • 每个人工写入异常均有 logger.exception/错误事件和稳定 trace_id。
  • 失败响应包含 code、message、脱敏 detail、trace_id。
  • 浏览器出现失败弹窗，且不显示凭据/连接串/完整请求体。
  • 数据库失败后事务回滚，路由不得继续返回成功。
  • 任务、用户、分组/标签各至少有成功、校验失败、权限失败、DB 异常四类自动化与浏览器断言。

8. 评估结论

当前实现具备部分日志和 rollback 基础，但尚未形成统一错误契约、统一前端弹窗和可关联排查链路，且存在数据库失败后继续返回页面的 P0 缺口。应按设计 B1→B4 分批实施。
