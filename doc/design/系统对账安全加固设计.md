# 系统对账安全加固设计

**编号**：OPT-P0-18   **版本**：rev.5   **日期**：2026-09-03

**关联**：`app/crons.py::cron_check()`、`app/services/cron_service.py::apply_retire()`

## 1. 问题

### 1.1 现状

`cron_check()` 定时扫描 `cron_infos` 与 `apscheduler_jobs` 的差异，若发现 `cron_infos` 中存在但 `apscheduler_jobs` 中不存在的任务（孤儿），**直接调用 `apply_retire()` 将其永久下线**（`status = -1`，不可恢复）。

### 1.2 预期

对账仅负责**检测异常并告警**，不执行任何不可逆操作。孤儿任务的处置由管理员通过 Web UI 手动决策。

### 1.3 风险事件（真实案例）

**2026-09 事件**：因 `conf.ini` 数据库 URL 配置错误（`sqlite:///:memory:`），APScheduler 的 JobStore 指向了临时数据库。服务重启后 `apscheduler_jobs` 为空，`cron_check()` 将全部 9 个任务自动下线。管理员在浏览器验收时才发现所有任务状态异常。

## 2. 根因

| 根因 | 描述 |
| --- | --- |
| 检测与修复耦合 | `cron_check` 将"发现异常"和"执行修复"合并在同一函数中，违反了 **Alerting ≠ Remediation** 原则 |
| 无批量保护 | 无论孤儿数量占比多大，都逐个执行 `apply_retire`，无熔断机制 |
| 不区分场景 | JobStore 完全为空（配置错误/迁移中）与个别任务孤立是完全不同的场景，但代码一视同仁 |
| 不可逆操作无确认 | 下线操作在 CronPilot 中不可恢复，但对账自动执行此操作无需人工确认 |

## 3. 行业对照

| 维度 | CronPilot 当前 | Kubernetes | Airflow | 行业最佳实践 |
| --- | --- | --- | --- | --- |
| 孤儿处理 | **自动下线（不可逆）** | 标记 Suspended（可恢复） | 标记 deactivated（可恢复） | 检测 → 告警 → 人工决策 |
| 批量保护 | 无 | Pod Disruption Budget | 无批量操作 | 熔断阈值 + 告警 |
| 告警机制 | 操作日志（被动） | Event + Metrics | Alert Rules | 结构化日志 + Metrics + Webhook |

## 4. 方案

### 4.1 核心原则

**对账只做两件事：检测异常 + 发出告警。绝不自动执行下线等不可逆操作。**

### 4.2 五步模型：检测 → 标记 → 告警 → 展示 → 人工决策

| 步骤 | 职责 | 实现 |
| --- | --- | --- |
| **1. 检测** | 定时扫描 cron\_infos vs apscheduler\_jobs 差异 | 保留 `cron_check()` 的扫描逻辑 |
| **2. 标记** | 将孤儿任务标记为"待确认"状态 | 设置 `job_health.reconcile_flag = 'orphan'`（或独立字段） |
| **3. 告警** | 通过日志 + Metrics + 可选 Webhook 通知运维 | `logger.warning()` + Prometheus `cronpilot_orphan_tasks_total` gauge |
| **4. 展示** | Dashboard 展示孤儿任务提醒 | 统计卡片增加"待确认"计数（或复用"持续异常"面板提示） |
| **5. 人工决策** | 管理员通过 UI 逐任务处理：恢复调度 / 手动下线 / 标记已知 | 任务列表增加"孤儿"筛选 + 操作按钮 |

### 4.3 实现分批

#### Phase 1（最小可用 · 推荐立即实施）：移除自动下线 + 告警

- **移除** `cron_check()` 中对 `apply_retire()` 的调用
- **替换为** 结构化日志 `logger.warning("orphan_detected", ...)`
- **新增** Prometheus gauge `cronpilot_orphan_tasks`
- **范围**：仅改 `app/crons.py` + `app/metrics.py`
- **验收**：模拟孤儿场景（手动从 apscheduler\_jobs 删除一条），确认日志告警但任务不下线

#### Phase 2（增强 · 后续迭代）：Dashboard 展示 + 人工操作入口

- Dashboard 统计卡片增加"孤儿任务"计数
- 任务列表增加 `health='orphan'` 筛选
- 操作列增加"重新加载到调度器"/"确认下线"按钮

#### Phase 3（可选 · 长期演进）：Webhook 告警 + 自动恢复

- Webhook 通知（微信/钉钉/邮件）
- "自动恢复调度"选项（将任务重新 add\_job 到 APScheduler，而非下线）

### 4.4 Phase 1 代码变更

```
# app/crons.py — cron_check() 修改前
for item in cifs:
    if "cron_%s" % item.id not in job_ids:
        if item.status == -1:
            continue
        apply_retire(item, RETIRE_REASON_ORPHAN, ...)  # ← 删除
        db.session.commit()                              # ← 删除
        record_operation(...)                            # ← 保留，改为 action='orphan_detected'
```

```
# app/crons.py — cron_check() 修改后
orphan_count = 0
for item in cifs:
    if "cron_%s" % item.id not in job_ids:
        if item.status == -1:
            continue
        orphan_count += 1
        current_app.logger.warning(
            "orphan task detected",
            extra={
                "event": "cron_check.orphan",
                "cron_id": item.id,
                "task_name": item.task_name,
                "status": item.status,
            },
        )
if orphan_count > 0:
    ORPHAN_TASKS.set(orphan_count)  # Prometheus gauge
    current_app.logger.warning(
        "reconciliation: %d orphan tasks detected, manual action required",
        orphan_count,
        extra={"event": "cron_check.orphan_summary", "count": orphan_count},
    )
else:
    ORPHAN_TASKS.set(0)
```

## Phase 2 — Dashboard 孤儿任务展示与人工操作入口

### P2.1 问题

Phase 1 移除了自动下线，改为日志告警。但管理员必须查看服务器日志才能发现孤儿任务。Web UI 中无任何提示，不符合"运维可观测性"原则。

### P2.2 方案概述

在 Dashboard 和任务列表中增加孤儿任务的展示与操作能力，形成 **「发现 → 告知 → 定位 → 处置」** 的完整闭环。

| 维度 | 变更 | 交互方式 |
| --- | --- | --- |
| Dashboard 统计卡片 | 新增第 5 张卡片「调度异常」或将孤儿计数整合到「持续异常」卡片的 sub-text | 点击卡片跳转到孤儿任务列表 |
| Exception Panel | 在 failing\_tasks 面板上方增加「调度脱节」警告条 | 展示孤儿任务列表（名称 + 状态 + 最后执行时间） |
| 任务列表筛选 | 健康维度增加 `health='orphan'` 筛选按钮 | 点击后列表仅展示孤儿任务 |
| 操作列 | 孤儿任务行增加「重新调度」和「确认下线」操作 | AJAX 操作 + 确认对话框 |

### P2.7 「重新调度」操作的技术设计

「重新调度」= 将任务重新 `add_job` 到 APScheduler：

```
# 后端 API: POST /api/cron/reschedule
def reschedule_task(cron_id):
    cif = db.session.get(CronInfos, cron_id)
    if not cif or cif.status == -1:
        return error("任务不存在或已下线")
    job_id = "cron_%s" % cif.id
    try:
        scheduler.get_job(job_id)
        return error("任务已在调度器中")
    except:
        pass
    # 根据 cron 表达式重新注册
    scheduler.add_job(
        func=cron_do, id=job_id,
        trigger=build_trigger(cif),
        args=[cif.id, cif.task_name, ...],
    )
    return success("已重新注册到调度器")
```

### P2.8 数据流设计

**核心问题**：`cron_check()` 在后台线程运行，其发现的孤儿列表如何传递给 Dashboard 渲染？

| 方案 | 描述 | 优劣 |
| --- | --- | --- |
| **A. 进程级缓存** | `cron_check` 将孤儿 ID 列表写入模块级变量（类似 `_overdue_cache`）；Dashboard 读取 | 零额外查询；但多 worker 时各自独立（gevent 单进程无此问题） |
| B. 数据库字段 | `job_health` 新增 `orphan_since` 列 | 持久化；多 worker 共享；但增加 schema 迁移 |
| C. Dashboard 实时查询 | Dashboard 每次加载时执行 `cron_infos vs apscheduler_jobs` 差集查询 | 数据始终最新；但增加页面延迟 |

**推荐方案 A**：与现有 `_overdue_cache` 模式一致（进程级 TTL 缓存）。CronPilot 使用 gevent 单进程模型，不存在多 worker 不一致问题。实现最简单，零额外查询。

### P2.13 对账可观测性：频率与执行记录

#### P2.13.1 当前现状

| 维度 | 现状 | 可见性 |
| --- | --- | --- |
| 对账频率 | `config.py` 配置 `minute='*/30'`（每 30 分钟一次） | 仅开发者可看代码 |
| 最后执行时间 | 无记录 | ❌ 不可见 |

| 对账频率说明 | 静态文案「每 30 分钟自动执行」 | 不变 |

#### P2.13.4 超时检测逻辑

Dashboard 渲染时检查 `_last_reconcile_time`：

- 若为 `None`（服务刚启动，对账尚未运行过）：显示「对账尚未完成」灰色提示
- 若 `now - _last_reconcile_time < 45 分钟`：正常（绿色或紫色，取决于 orphan\_count）
- 若 `now - _last_reconcile_time ≥ 45 分钟`：超时告警（红色）— 说明 cron\_check 可能因异常停止

阈值 45 分钟 = 30 分钟间隔 × 1.5 倍容差，避免因调度延迟误报。

#### P2.13.5 数据结构（进程级缓存扩展）

```

    _last_reconcile_time = time.time()
```

## Phase 3 — Webhook 告警 + 智能恢复

### P3.1 问题

Phase 1 实现了日志告警 + Prometheus gauge，Phase 2 增加了 Dashboard 可视化和手动操作。但仍有两个缺口：

| # | 缺口 | 影响 |
| --- | --- | --- |
| G1 | **被动发现**：管理员必须打开 Dashboard 才能看到孤儿任务告警 | 非工作时间段（凌晨/节假日）的孤儿无法及时被感知，恢复时效 = 下次人工打开 Dashboard 的间隔 |
| G2 | **纯手动恢复**：每个孤儿任务都需要管理员逐个点击「重新调度」 | 配置迁移、数据库恢复等场景可能产生几十个孤儿，逐个操作效率极低 |

### P3.2 根因分析

| 根因 | 说明 |
| --- | --- |
| 通知通道未接入对账 | 现有 `send_text()`（企业微信 + 通用 Webhook + 钉钉）仅被任务执行异常（`cron_do`）调用，对账模块未接入 |
| 无自动恢复安全框架 | Phase 1 正确地移除了自动下线（不可逆），但未建立自动恢复（可逆、安全）的框架 |

### P3.3 行业对照：告警 + 自动恢复

| 维度 | Kubernetes | Airflow | CronPilot Phase 2 | Phase 3 目标 |
| --- | --- | --- | --- | --- |
| 主动告警 | AlertManager（Webhook/PagerDuty/Slack） | SLA miss callback + Email | 仅 Dashboard + Prometheus | 复用 `send_text()` 三通道推送 |
| 去重/抑制 | AlertManager group\_wait / group\_interval / inhibit\_rules | 每 SLA miss 仅触发一次 | 无（每次 cron\_check 重复日志） | 孤儿集合不变 → 不重复推送 |
| 自动恢复 | ReplicaSet controller（自动拉起 Pod） | backfill（需手动触发或 catchup=True） | 仅手动「重新调度」 | 可选自动恢复 + 熔断 |
| 熔断保护 | PDB（Pod Disruption Budget） | 无 | 无 | 孤儿占比 > 阈值 → 仅告警不恢复 |

### P3.4 方案总览

**核心原则**：自动恢复是**可逆的**（add\_job，不是 retire），因此可以在安全框架下自动执行。但必须有**熔断阀**：当孤儿数量异常大（可能是全局故障而非个别脱节），自动恢复应暂停，仅发告警等人工介入。

| 能力 | 描述 | 配置项 |
| --- | --- | --- |
| **P3-A：Webhook 告警** | 对账发现孤儿时，通过现有三通道推送告警消息（含任务清单、数量、建议操作） | `reconcile_alert_enabled`（默认 1，复用现有 `error_web_hook` / `dingding_*` / `qywechat_*` 配置） |
| **P3-B：告警去重** | 孤儿 ID 集合与上次一致时不重复推送；新增或减少孤儿时才触发告警 | `reconcile_alert_dedup`（默认 1） |
| **P3-C：智能自动恢复** | 对账发现孤儿且满足安全条件时，自动调用 `reschedule_orphan_task()` | `reconcile_auto_recover`（默认 0 = 关闭，需管理员显式开启） |
| **P3-D：熔断保护** | 孤儿数量占活跃任务比例超阈值时，暂停自动恢复，仅告警 | `reconcile_fuse_threshold`（默认 0.5 = 50%） |

| --- | --- |
| 孤儿数 = 0 | 不告警 |

| 从 > 0 恢复到 0（全部处置完毕） | 发送**恢复通知**：「对账正常，所有脱节已处置」 |

#### P3.5.4 代码设计

```
# app/crons.py — cron_check() 告警增强

_last_alerted_orphan_ids = set()  # 去重：上次告警时的孤儿 ID 集合

def _should_alert_orphan(current_ids):
    """判断是否需要发送告警（去重逻辑）"""
    global _last_alerted_orphan_ids
    if not current_ids and not _last_alerted_orphan_ids:
        return False          # 无变化：都是 0
    if current_ids == _last_alerted_orphan_ids:
        return False          # 无变化：ID 集合一致
    return True               # 新增/减少/恢复

def _build_orphan_alert_message(orphan_tasks, total_scanned):
    """构建告警消息正文"""
    if not orphan_tasks:
        return '调度脱节已全部处置\n结果：0 个孤儿任务（共扫描 %d 个活跃任务）\n状态：✓ 正常' % total_scanned
    lines = ['发现 %d 个孤儿任务（共扫描 %d 个活跃任务）' % (len(orphan_tasks), total_scanned), '']
    lines.append('脱节任务列表：')
    for i, t in enumerate(orphan_tasks[:10], 1):  # 最多展示 10 个
        lines.append('  %d. [ID:%s] %s — 状态:%s' % (i, t['id'], t['name'], t['status_text']))
    if len(orphan_tasks) > 10:
        lines.append('  ... 还有 %d 个（详见 Dashboard）' % (len(orphan_tasks) - 10))
    lines.append('')
    lines.append('建议：登录 Dashboard → 筛选「调度脱节」→ 逐任务处理')
    return '\n'.join(lines)

# 在 cron_check() 中调用：
if _should_alert_orphan(orphan_id_set):
    alert_msg = _build_orphan_alert_message(orphan_tasks_info, len(cifs))
    wechat_info_err('对账告警' if orphan_id_set else '对账恢复', alert_msg)
    _last_alerted_orphan_ids = set(orphan_id_set)
```

### P3.6 P3-B 告警去重机制

| 维度 | 策略 | 理由 |
| --- | --- | --- |
| 去重粒度 | 基于孤儿 ID **集合**（非计数） | ID 集合变化才代表真正的状态变更（新发现/已处置）；仅靠计数相同可能掩盖「旧孤儿恢复 + 新孤儿出现」 |
| 恢复通知 | 从非空 → 空时发送一次恢复通知 | 让管理员确认「告警已自动收敛」；对标 Prometheus AlertManager 的 resolved 通知 |
| 长期未处理 | 连续 N 次 cron\_check 孤儿不变 → 每 24h 发一次提醒 | 防止告警被遗忘；阈值可配置（`reconcile_remind_interval_hours`，默认 24） |
| 进程重启 | `_last_alerted_orphan_ids` 重置为空 → 首次扫描若有孤儿会重新告警 | 可接受：重启不频繁；重启后重新告警是安全的（避免遗漏） |

### P3.7 P3-C 智能自动恢复设计

#### P3.7.1 核心决策：为什么自动恢复是安全的

**关键区别**：Phase 1 移除的「自动下线」是**不可逆**操作（`status = -1`，数据库永久状态变更）。而「自动恢复」是**可逆**操作（`scheduler.add_job`，仅在内存中注册调度条目，下次 cron\_check 若仍异常会再次检测到）。因此自动恢复可以在受控条件下安全执行。

#### P3.7.2 安全框架

| 安全措施 | 说明 | 配置 |
| --- | --- | --- |
| **默认关闭** | 自动恢复默认不启用，需管理员在 `conf.ini` 中显式开启 | `reconcile_auto_recover=1` |
| **熔断阈值** | 孤儿数量 / 活跃任务总数 > 阈值时，自动恢复暂停，仅告警 | `reconcile_fuse_threshold=0.5`（默认 50%） |
| **单次上限** | 每次 cron\_check 最多自动恢复 N 个任务 | `reconcile_max_auto_recover=10` |
| **状态过滤** | 仅恢复 `status != -1`（非已下线）且调度表达式有效的任务 | 内置逻辑，不可配置 |
| **审计日志** | 每次自动恢复记录操作日志（`record_operation`，操作人=「系统对账」） | 内置逻辑 |
| **恢复失败不重试** | 如果 `reschedule_orphan_task` 返回失败（如表达式无效），标记为需人工处理，不循环重试 | 内置逻辑 |

#### P3.7.3 自动恢复流程图

```
cron_check() 发现孤儿
    │
    ├─ reconcile_auto_recover = 0 ?
    │   → 仅告警（现有 Phase 2 行为）
    │
    ├─ 孤儿占比 > fuse_threshold ?
    │   → 熔断：仅告警 + 日志 "auto-recover fused: orphan ratio %.1f%% exceeds threshold"
    │
    ├─ 孤儿数 > max_auto_recover ?
    │   → 截断：只恢复前 N 个，其余告警等人工
    │
    └─ 逐个执行 reschedule_orphan_task(cron_id)
        ├─ 成功 → record_operation(action='auto_recover', operator='系统对账')
        └─ 失败 → logger.warning + 计入告警消息
```

### P3.9 代码变更设计

#### P3.9.1 `app/crons.py`

```
# 新增模块级变量
_last_alerted_orphan_ids = set()
_last_alert_time = 0.0

def _reconcile_alert(orphan_tasks_info, orphan_id_set, total_scanned, recover_results=None):
    """对账 Webhook 告警（含去重）"""
    global _last_alerted_orphan_ids, _last_alert_time
    config = current_app.config.get('CRON_CONFIG', {})
    if not int(config.get('reconcile_alert_enabled', '1')):
        return
    dedup = int(config.get('reconcile_alert_dedup', '1'))
    remind_hours = int(config.get('reconcile_remind_interval_hours', '24'))

    # 去重判断
    if dedup and orphan_id_set == _last_alerted_orphan_ids:
        if orphan_id_set and remind_hours > 0:
            elapsed = time.time() - _last_alert_time
            if elapsed < remind_hours * 3600:
                return  # 未到定期提醒时间
        else:
            return  # 无变化且无孤儿

    msg = _build_orphan_alert_message(orphan_tasks_info, total_scanned, recover_results)
    title = '对账恢复' if not orphan_id_set else '对账告警'
    wechat_info_err(title, msg)
    _last_alerted_orphan_ids = set(orphan_id_set)
    _last_alert_time = time.time()

def _try_auto_recover(orphan_items, total_active):
    """智能自动恢复（带熔断）"""
    config = current_app.config.get('CRON_CONFIG', {})
    if not int(config.get('reconcile_auto_recover', '0')):
        return None  # 功能未启用

    fuse_threshold = float(config.get('reconcile_fuse_threshold', '0.5'))
    max_recover = int(config.get('reconcile_max_auto_recover', '10'))

    orphan_ratio = len(orphan_items) / max(total_active, 1)
    if orphan_ratio > fuse_threshold:
        current_app.logger.warning(
            "auto-recover fused: orphan ratio %.1f%% exceeds threshold %.1f%%",
            orphan_ratio * 100, fuse_threshold * 100,
        )
        return {'fused': True, 'ratio': orphan_ratio, 'results': []}

    results = []
    for i, item in enumerate(orphan_items):
        if i >= max_recover:
            results.append({'id': item.id, 'name': item.task_name, 'status': 'pending'})
            continue
        ok, msg = reschedule_orphan_task(item.id)
        results.append({
            'id': item.id, 'name': item.task_name,
            'status': 'success' if ok else 'failed', 'msg': msg,
        })
        if ok:
            record_operation(...)  # 审计日志
    return {'fused': False, 'ratio': orphan_ratio, 'results': results}
```

### P3.10 方案对比：是否引入自动恢复

| 维度 | 方案 α：仅告警（不含自动恢复） | 方案 β：告警 + 自动恢复（推荐） |
| --- | --- | --- |
| 实现复杂度 | 低（~60 行） | 中（~150 行） |
| 运维效率 | 每次孤儿都需人工处理 | 常规场景自动恢复，异常场景（熔断）才需人工 |
| 安全性 | 最安全（完全人工） | 安全（默认关闭 + 熔断 + 审计） |
| 适用场景 | 任务少（< 20）或对自动化信任度低的团队 | 任务多（50+）或需 7×24 无人值守的团队 |
| 行业对照 | 保守策略（类似 Airflow） | 主流策略（类似 Kubernetes ReplicaSet） |

**推荐方案 β**：自动恢复默认关闭，安全性等同于方案 α。显式开启后，熔断 + 单次上限 + 审计三重保护确保不会因全局故障而错误地批量恢复。对于经验证的稳定环境（如偶发进程重启导致的个别孤儿），自动恢复可显著减少运维负担。

| 告警风暴（高频孤儿变化） | 低：去重机制确保同一 ID 集合只告警一次；通道自身有限频（钉钉 20 条/分钟） | 去重 + 通道限频 |
| 自动恢复的调度表达式已变更 | 中：`reschedule_orphan_task` 读取 `cron_infos` 当前表达式，可能是旧值 | `reschedule_orphan_task` 已内置表达式校验；失败不重试，等人工 |
| 自动恢复+人工操作并发 | 低：`scheduler.add_job(replace_existing=True)` 幂等 | APScheduler 内置幂等保证 |
| 进程重启丢失去重状态 | 低：重启后首次扫描重新告警，可接受 | 不持久化去重状态（与 Phase 2 缓存策略一致） |

## Phase 2.5 — Orphan UI 全面重设计（OPT-P0-18-UI）

### P2.5.1 问题

Phase 2 实现的 orphan（对账脱节）UI 存在以下专业性问题：

| # | 问题 | 表现 |
| --- | --- | --- |
| 1 | **操作图标风格脱节** | orphan 操作使用 emoji（🔄 ✕）+ 文字药片型按钮（`act-btn-orphan`），而其他操作列统一使用 SVG + 28×28 图标按钮（`act-btn`）。两者在大小、形状、视觉语言上完全不一致 |
| 2 | **术语「调度脱节」晦涩** | 用户不理解"脱节"的含义。该词是技术概念（scheduler orphan），对管理端用户而言过于抽象。行内标签、筛选按钮、Warning Bar 中均使用此词 |
| 3 | **orphan 行替换全部操作** | orphan 任务的操作列只显示「重新调度」「确认下线」两个按钮，连「执行记录」链接也消失了。用户无法查看该任务的历史执行日志 |
| 4 | **健康列未标记 orphan 状态** | 设计文档规划了 `orphan-status` CSS（`⚠ 调度器无记录`），但未实际实现。orphan 行健康列仍显示普通 badge（ok/failing/N/A） |
| 5 | **Warning Bar 信息密度低** | 大面积紫色背景 + 仅一行文字 + 「查看详情」链接，视觉重量过大但信息量不足 |
| 6 | **行背景色过于突出** | 紫色背景 (`var(--cp-orphan-bg)`) 在全白列表中过于跳跃，视觉噪音大 |

### P2.5.2 术语方案对比

| 方案 | 显示文案 | 标签 | 说明 | 评价 |
| --- | --- | --- | --- | --- |
| T1 | 调度脱节 | 脱节 | 当前使用 | ❌ 技术术语，用户不理解"脱节"的含义 |
| T2 | 待恢复调度 | 待恢复 | 任务在系统中存在但调度器中缺失 → 需要恢复调度 | ✓ 面向动作（恢复），用户能理解该做什么 |
| **T3** | **调度异常** | **调度异常** | 统一使用"异常"语系（与「持续异常」「健康异常」呼应），但前缀区分 | **✓ 推荐**：与现有「持续异常」语义体系一致，用户无歧义 |
| T4 | 调度器未注册 | 未注册 | 精确描述技术状态 | △ 对非技术用户仍然抽象 |

**推荐 T3「调度异常」**：① 与「持续异常」（执行失败）形成对比，前者是调度层，后者是执行层；② 用户直觉理解"异常"需要处理；③ 行内标签 2 字「调度异常」简洁；④ 不需要理解"脱节"的技术含义。

### P2.5.3 操作列重设计

#### 原则

- **复用 `act-btn` 系统**：所有操作图标统一为 28×28 SVG icon box，用 `data-tooltip` 展示文字
- **orphan 行保留"执行记录"入口**：不因 orphan 状态而隐藏历史日志链接
- **orphan 特有操作后置**：「重新调度」「下线」使用独立的语义颜色（紫色/红色）但仍是 `act-btn` 尺寸
- **删除 `act-btn-orphan` 类**：用 `act-btn.orphan-act` 修饰器替代，复用尺寸/悬停/tooltip 体系
