任务执行链路可观测性当前实现评估

评估基准：收敛版设计 rev.6；对象：当前工作区代码、模板、测试与 Prometheus 指标

结论：有条件可用（Conditional）。执行侧（cron_do）已经具备“提前创建运行记录 → 阶段事件 → 终态结果 → 运行检查器展示”的基本闭环；调度侧（配置提交 → APScheduler 注册 → cron_check 对账）仍主要写应用日志、Prometheus 指标和进程内 orphan cache，没有持久化的注册健康记录，也没有在任务详情页形成可操作的注册诊断。因此，当前可以用于排查“已经进入执行链路的某次运行”，不能宣称整条任务链路已经完成可观测。

1. 评估范围与判定方法

本次只评估当前实现，不修改业务代码。重点核查五个问题：①观测点是否实际写入；②数据是否可关联和长期查询；③页面是否消费这些数据；④权限/脱敏是否闭环；⑤测试是否覆盖否定路径。

证据核查结果
实现app/crons.py、app/services/execution_tracer.py、run_inspector_presenter.py、app/main/views.py、相关模板与 Repository。
数据JobLog、JobLogEvent、JobLogItems 与 cron_check 的存储/查询路径。
测试执行观测契约、Tracer、上下文执行器、运行详情、结果筛选、保留策略等 41 条定向测试。

2. 当前真实链路

配置CronInfos 持久化
→
注册scheduler.add_job
→
对账cron_check 检查 orphan/ghost
→
触发APScheduler 调用 cron_do
→
执行JobLog + job_log_events + items

当前链路存在两个不同成熟度的区域：最后两步可追踪；前面三步只能部分追踪。特别是配置提交成功后再注册调度器的非原子边界，尚没有一个持久化对象记录“注册成功/失败/缺失”的最新事实。

3. 分层完成度

能力域状态事实依据专业判断
运行父记录已实现cron_do 提前创建 pending，进入执行后更新为 running，最终写终态。能区分已入队、执行中和终态；历史记录可查询。
阶段事件写入已实现Tracer 写入 epoch ms、序号、偏移、结果；有事件数量和写入耗时预算。采用独立连接 best-effort，避免观测失败污染业务事务，工程取舍合理。
阶段事件展示基本实现Presenter 白名单摘要，模板不读 ORM 原对象和原始 detail；时间线置于请求/响应之前。执行路径可读，但事件字段仍不完整，诊断粒度有限。
角色脱敏基本实现viewer/operator/admin 有 URL、响应正文、业务日志差异化展示；契约测试覆盖。现有角色矩阵可用，但仍需浏览器端正反向验收。
执行列表已实现支持 in_progress，列表复用 job_log_badge；pending 显示“已入队”。此前 pending 显示未知的问题已修复。
调度注册观测部分实现cron_check 写 orphan/ghost 日志并更新 ORPHAN_TASKS/GHOST_TASKS；orphan cache 为进程内字典。可告警、可临时看指标，但不可按任务、时间、操作者回放，也没有任务详情页诊断闭环。
注册失败展示/重试未实现未发现 register_failed、missing 的持久化模型、任务详情卡片或幂等重试路由。这是整条链路的主要缺口：配置保存成功不等于调度接管成功。
调度未触发诊断部分实现有 JobStore 对账和 active/orphan 指标；无按任务的预期触发窗口、misfire 诊断记录。只能知道“有/无 Job”，不能完整回答“为何没有按时触发”。

4. 执行观测功能的专业评价

已达到的工程质量

  • 事件写入失败会熔断当前 Tracer，并通过指标 EXECUTION_EVENT_WRITE_FAILED 记录，不回滚业务事务。
  • 事件 detail 有写入白名单，Presenter 只生成摘要，避免将异常原文和敏感 URL 直接交给模板。
  • 运行检查器按 trace 查询事件和业务日志记录，且 pending/running 明确为“最终结果未知”。
  • 锁竞争发生在进入 cron_do 前，不创建虚假的执行记录；这与“主动 skip 不属于正常执行结果”的语义一致。

仍限制诊断深度的问题

  • http.start 只保留 method，未保留脱敏 URL、timeout 或计划时间；超时只能看到“等待超过阈值”，无法在页面确认实际阈值。
  • JobLogEvent 通过 trace_id 关联，模型没有指向 JobLog.id 的外键；trace 生成或迁移异常时，数据完整性依赖应用约定。
  • Tracer 采用“首次写入异常即禁用当前运行后续事件”的策略，合理但需要暴露“观测降级”信号，否则用户可能把不完整时间线误解为业务链路缺阶段。
  • “业务日志（N 条）”仅对有权限角色展示，计数语义正确；但业务日志记录与阶段事件仍是两个查询集合，页面没有统一的时间排序视图。

5. 页面与交互完成度

页面当前能力缺口
任务列表 execution_logs.html结果筛选、进行中筛选、任务名和运行详情入口。没有调度注册健康列；用户无法从列表发现“配置存在但 Job 缺失”。
任务详情 task_detail.html展示任务业务配置和执行记录入口。没有“配置保存/调度注册/最近对账/下一次触发”的任务级健康卡片。
运行检查器 run_inspector.html时间线、请求、响应、元数据、业务日志记录和角色脱敏已接入。只适用于已经存在的 JobLog；不能解释注册失败或从未触发。
交互结论：当前“运行检查器”已经是可用的单次执行诊断页；但“任务详情 → 调度健康 → 注册事件/重试”的任务级诊断页尚未实现。故当前功能不是完整链路观测，而是“执行链路观测 + 调度对账告警”。

尚不能据此宣称交付完成：本轮没有完成重启后的浏览器四角色正反向验收、调度注册失败的端到端演练、双后端验证、长期保留/容量压测。因此 B6 全量验收仍未完成。

7. 风险等级与收口建议

优先级问题建议
P0配置保存与调度注册没有持久化关联结论，创建成功提示可能造成误判。新增任务级注册健康摘要与不可变注册事件；创建/编辑响应分别返回配置和注册结果。
P1任务详情不能诊断 orphan/missing，也没有安全重试入口。在任务详情加入调度健康卡片、最近对账事件、POST+CSRF+scope 的幂等重试。
P1事件 detail 字段不足以解释调度延迟和超时配置。补充脱敏 URL、scheduled_at、timeout_sec 等白名单字段，并同步契约测试。
P2观测降级仅有指标，用户不可见。在运行详情显示“阶段事件不完整/观测写入降级”提示，并保留服务端指标。

8. 最终判定

当前完成度：约 65%（按“执行观测 + 调度观测 + 页面闭环 + 验收”四个维度综合判断）。

若目标是“查看某次 HTTP 任务执行经过了哪些阶段、为何失败”，当前版本已基本可用。若目标是“从任务创建开始，区分配置保存、APScheduler 注册、调度触发和执行失败，并在管理端完成闭环排查”，当前版本尚未完成，不能标记为完整交付。

本评估仅记录事实和收口建议，不代表已获实现确认。
