OPT-P0-22：停用用户同名申请恢复设计

状态：已交付（B1–B5 · 2026-09-09）　创建：2026-09-09　更新：2026-09-09　优先级：P0（权限与身份连续性）

编号说明：本方案为独立纠偏项 OPT-P0-22。原 OPT-P1-10 仍专指「用户注册审批与忘记密码」已交付能力；本设计覆盖并替代《用户注册审批与忘记密码设计》§3.1.7「删除同名停用用户后新建」策略，并同步修订《注册审批结果状态显示设计》相关数据流与警示文案。

产品语义（rev.3 · 强制）：
  • 同名再申请不一定是原使用人，更常见是另一同名人占用该用户名。
  • 对申请人（注册表单 / 登录注册提示）不做任何「同名停用 / 恢复」提示；申请人流程与普通新注册一致。
  • 仅审批人（注册审批）与管理员（添加用户）在命中同名停用账号时需要知情：将覆盖该停用账号的全部资料与权限，但因复用同一 user_id，历史审计/操作等日志会被继承。

1. 问题

用户停用时仅写 is_active=0，但同名注册获批或管理员同名添加时，现有实现会物理删除停用用户并新建一行。该行为破坏用户身份连续性，并可能使没有外键的业务组、审批人和审计引用成为孤儿；SQLite 复用被删除的最高行号时，新用户还可能继承旧用户关系。

独立安全问题：Web 鉴权当前主要信任 Session 内的角色与业务组，停用操作没有可靠撤销所有已登录 Session。新策略保留原 user_id 并恢复启用，因此必须同时引入会话版本校验，不能只更新用户资料。

2. 根因

  1. rbac_users.username 为全表唯一，但产品又允许停用用户名重新申请，现有实现通过删除旧行释放唯一约束。
  2. 把“同一用户名再次申请”错误建模成「删除旧身份、插入新身份」，而工程上必须保留同一 user_id 以免历史日志与引用断裂；产品上则不假定申请人为原使用人。
  3. user_groups.user_id、reviewer_id、审计 user_id 缺少完整外键/生命周期约束。
  4. 用户创建、业务组绑定和部分资料保存存在分次提交，不能保证整体原子性。
  5. 停用只清理 API Token，没有使已签发 Web Session 立即失效。

3. 方案

决策：停用用户永不删除。同名注册申请或管理员同名添加命中停用用户时：仅审批人/管理员看到警示；确认后在原用户行上全量覆盖资料与权限并重新启用，保留原 user_id（因此历史日志继承）。禁止“删除旧用户 + 插入新用户”。申请人对同名停用无任何提示。

3.1 两条入口

入口发现同名启用用户发现同名停用用户
自主注册申请提交阶段拒绝允许提交；申请人侧无提示、无特殊文案；后台标记 is_reactivation=1（仅供审批侧识别）；审批列表标签 + 批准弹窗对审批人警示
管理员添加用户拒绝不立即写入；对管理员展示同名停用警示与覆盖后果，确认后覆盖原行并启用（见 §4.5）

用户名匹配：统一执行 _normalize_username() = strip()（本轮不强制 lower；SQLite/MySQL 均按当前列 collation 做等值匹配）。双后端回归测试覆盖同名启用冲突与同名停用处理。若未来改为大小写不敏感，须单独设计迁移，本轮不做。

3.2 审批/确认后的原子覆盖启用

注册审批与管理员确认复用同一内部函数（如 _reactivate_user_from_payload(...)），在单个数据库事务内完成：

  1. 重新读取并锁定同名用户（SELECT … FOR UPDATE）；若已被其他请求恢复为启用，当前操作失败，不覆盖现有资料。
  2. 保留 id、username、create_time；历史 last_login_at 可保留（审计连续性），不向新使用人展示为“欢迎回来”。
  3. 按入口语义全量覆盖资料与凭据（见 §4.5）——角色、业务组、邮箱、花名、岗位、密码策略均以本次申请/表单为准。
  4. 业务组全量替换，禁止与旧业务组合并；全局管理员（__ALL__）应删除全部旧 user_groups 行。
  5. 撤销旧 API Token，签发全新 Token 和有效期。
  6. 递增 auth_version，使停用前签发的全部 Web Session 永久失效。
  7. 最后设置 is_active=1，写入 status_reason（含申请编号或「管理员确认同名覆盖启用」）；更新注册申请为 approved（若来自注册）。
  8. 事务成功后清除 API scope 缓存，并记录 user:reactivate 审计 + detail 前后快照（见 §4.3）。

审批人必须知情的后果：① 新资料/权限覆盖旧停用账号全部配置；② 不删除用户行，user_id 不变，因此历史审计/操作日志等仍挂在同一 ID 下被继承；③ 旧 Session 与 Token 全部失效。弹窗文案禁止写成「本人回来恢复」或暗示申请人即原使用人。

3.3 停用与会话撤销

  • set_user_active() / update_user() 停用时除清空 Token 外，同时递增 auth_version。
  • 登录成功时把 auth_version 写入 Session。
  • 所有已登录 Web 请求（before_app_request）校验：用户存在、is_active=1、Session auth_version 等于数据库版本；失败立即 session.clear() 并要求重新登录。
  • 恢复账号后只能使用该入口规定的新密码重新登录（见 §4.5）。
  • 普通「设置启用」接口仍禁止直接启用；同名覆盖启用只能来自审批通过或管理员添加时的显式确认。

4.4 Session fail-closed 迁移策略（选定方案 A）

选定 A：功能首次启用时强制全员 Web Session 失效，禁止「缺省 0 == 0」放行旧 Session。
  1. 模型增加 rbac_users.auth_version INTEGER NOT NULL DEFAULT 0（已规划）。
  2. 一次性迁移（ensure_business_tables.py，幂等标记）：列创建成功后立即执行
    UPDATE rbac_users SET auth_version = COALESCE(auth_version, 0) + 1
    使得所有既有 Session（无 auth_version 或值为 0）与库中版本不一致。
  3. 登录成功：session['auth_version'] = int(user.auth_version)。
  4. 请求校验：int(session.get('auth_version')) 与 DB 比较时，若 Session 缺少该键 → 视为失效（不得用 or 0 把缺失当成 0 去匹配）。推荐实现： 
    if 'auth_version' not in session: return False
return int(session['auth_version']) == int(user.auth_version or 0)
  5. 停用 / 恢复：各自再 auth_version += 1。
  6. API Token：停用与恢复均清空并重签；API 路径继续以 Token + is_active 为准（与 Web Session 独立）。

明确不做方案 B（「仅停用后才踢 Session」）。风险表中的「全员重登」承诺与本方案一致。

7. 验收

  1. 停用用户行在停用、提交同名申请、审批前后均未发生 DELETE，启用后 user_id 保持不变。
  2. 同名启用用户不能注册或添加；同名停用可提交注册，且申请人页面/响应无任何同名提示。
  3. 审批人列表显示「同名停用」；批准弹窗明确：覆盖资料/权限 + 同一 user_id 继承历史日志 + 非假定原使用人。
  4. 审批通过后角色、资料和业务组与申请完全一致；停用前多余业务组为零。
  5. 管理员添加同名停用用户与注册审批共用核心；凭据行为符合 §4.5；确认弹窗语义同审批人。
  6. 功能首次启用后：既有 Web Session 下一请求失效；停用/覆盖启用后旧 Session、Token 均不可继续访问。
  7. 两个管理员并发审批同一用户名时只有一个成功，另一个安全失败。
  8. 覆盖事务任一步骤故障时，用户保持停用、原资料和原业务组完整。
  9. 历史审计仍可按原 user_id 正确展示；新审计含 detail 前后摘要且无凭据。
  10. is_reactivation / target_user_id 在提交同名停用冲突申请时正确写入；四种 RBAC 角色回归与文档门禁通过。

9. 预期复盘提纲（实现后落库）

正式复盘在实现完成后写入 doc/postmortem/2026-09-停用用户同名恢复.html。提纲：

  1. Bug 定位：同名注册审批和管理员添加路径会删除停用用户；Web Session 停用后未被可靠撤销。
  2. 根因：为满足用户名唯一约束，把账号恢复错误实现为「删除旧身份、创建新身份」，同时把 Session 中的权限快照当成持续可信状态。
  3. 测试漏洞：现有测试只断言旧用户被删除，没有验证旧组、旧 Session、审批引用、审计连续性和事务失败。
  4. 修复：保留原行、审批警示、原子更新资料后恢复，并引入认证版本 + §4.4 fail-closed。
  5. 防护测试：ID 不变、组全量替换、旧 Session 失效、缺键失效、双审批竞态和事务回滚。
  6. 同类排查：检查所有 RbacUser DELETE 与 is_active 赋值点。
  7. 预防方案：静态门禁禁止生产路径 db.session.delete(RbacUser…)；落地 tests/test_user_reactivation.py + CI。

10. 用户确认点

确认本设计（OPT-P0-22 rev.3）即表示同意：

  • 停用用户永久保留；同名再占用经审批/管理员确认后，在原 user_id 上覆盖资料与权限并启用，历史日志继承。
  • 申请人零同名提示；仅审批人与管理员看到「同名停用 → 覆盖 + 日志继承」警示。
