1. 文档说明

目的：为开发、运维、集成方提供 CronPilot 的结构性视图，说明模块边界、运行时拓扑、数据流向及扩展点。

读者：后端工程师、SRE、架构师、需对接回调的业务研发。

范围：应用层（app/）、数据层（datas/）、配置与容器化部署；不包含业务回调服务内部实现。

术语含义
调度 JobAPScheduler 中 id 为 cron_{cron_infos.id} 的持久化任务
回调触发时对 req_url 发起的 HTTP GET
双库cron_db_url（JobStore）与 cron_job_log_db_url（业务 ORM）
体验版is_dev=1，禁用秒级字段

2. 架构目标与约束

2.1 设计目标

目标架构手段源码体现
Crontab 语义兼容字段级 Cron + APScheduler cron triggerviews.py 校验 + scheduler.add_job
可视化运维SSR Web + Session 鉴权main/views.py、templates
自动化集成REST API + access_tokenapi/views.py
水平扩展Redis 任务互斥 + 文件锁拉取 Jobsingle_task、CuBackgroundScheduler
故障可感知关键词检测 + 三通道推送crons.cron_do、send_text
低部署成本Docker + Supervisor + 默认 SQLiteDockerfile、docker-compose

2.2 约束条件

  • 回调仅支持 GET，超时固定 120s（requests.get(..., timeout=120)）
  • 集群模式要求 MySQL JobStore + Redis，SQLite 仅适合单机
  • 每 Gunicorn worker 独立启动完整 Scheduler（非集中式 Master）
  • Web 鉴权为三角色 RBAC（用户名+密码 / Session；空表种子 admin）；login_pwd 仅作初始种子

4.1 运行时双进程模型说明

重要：Gunicorn 多 worker 意味着同一主机存在 N 个 APScheduler 实例。它们通过 scheduler.lock（portalocker 非阻塞排他锁）保证同一时刻仅一个进程执行 _process_jobs() 拉取到期任务；任务执行函数 cron_do 在集群模式下再由 Redis @single_task 保证跨节点互斥。

5.2 Web 管理端调用链（与 APScheduler 的关系）

结论：管理页面（任务添加/编辑、执行时间、启动/暂停、删除等）不会由浏览器直接调用 APScheduler 或 Flask-APScheduler 接口。前端仅通过 HTML 表单 / Ajax 请求 Flask 的 main 蓝图路由；服务端在 cron_service 或 main/views.py 内完成校验、写 cron_infos，再调用 scheduler.add_job / pause_job / resume_job / remove_job。

┌─────────────── 浏览器（jQuery + common.js）────────────────────────────┐
│  cron_add.html / cron_edit.html  →  js-ajax-form  →  POST Flask 路由    │
│  cron_list.html  →  js-ajax-dialog-btn / js-ajax-delete  →  GET 路由     │
│  ❌ 无 apscheduler SDK；❌ 不请求 /api/cron（管理 UI 走 main，不走 api）   │
└───────────────────────────────┬────────────────────────────────────────┘
                                ▼
┌─────────────── Flask 表现层（app/main/views.py）────────────────────────┐
│  /cron_add  /cron_edit  /update_status  /cron_del  /cron_list  …         │
└───────────────────────────────┬────────────────────────────────────────┘
                                ▼
┌─────────────── 服务层（app/services/）──────────────────────────────────┐
│  cron_validator.validate_cron_form  — Web/API 共用校验（执行时间字段等）   │
│  cron_service.add_cron_web / edit_cron_web / create_cron / update_cron   │
│       → INSERT/UPDATE cron_infos  → register_cron_job()                  │
└───────────────────────────────┬────────────────────────────────────────┘
                                ▼
┌─────────────── 调度层（进程内 Flask-APScheduler，非 HTTP）────────────────┐
│  scheduler.add_job('cron_{id}', cron_do, trigger=date|cron, …)           │
│  scheduler.pause_job / resume_job / remove_job                           │
│  持久化 → apscheduler_jobs（SQLAlchemyJobStore）                          │
└─────────────────────────────────────────────────────────────────────────┘

管理页操作对照表

管理页操作前端请求Flask 路由服务/逻辑APScheduler（服务端）
添加任务（含执行时间）POST 表单 Ajax/cron_addadd_cron_web → create_cronadd_job
编辑任务 / 改时间POST 表单 Ajax/cron_editedit_cron_web → update_cronadd_job(replace_existing)
启动 / 暂停GET Ajax 对话框/update_statusmain/views.pyresume_job / pause_job
下线（生命周期终点）GET / POST/cron_retire写 status=-1；LIFECYCLE-2 另写 retire_reason/retired_at（人工必传 reason；无 retired_by）；保留行与日志remove_job
任务列表 / 执行记录GET 页面/cron_list、/job_log_*ORM 分页查询无（只读 DB）

无删除：禁止人工删除任务与执行流水。暂停 ≠ 下线。权威设计见 任务生命周期与无删除（含 LIFECYCLE-2 元数据）。

操作审计（现状）：配置变更写入 operation_log（管理页「操作记录」，权限 operation:read）；身份/权限事件写入 rbac_audit_logs（「审计」，权限 audit:read）。审计 action 用 retire_cron，不用 delete_cron。行内查阅（原因/时间戳）由 LIFECYCLE-2 扩展 cron_infos。

外部系统集成走 REST API（/api/cron、/api/cron/status），同样经 cron_service 写库后由服务端注册调度，亦非直连 APScheduler。详见 技术方案与前端设计 第 6 节 API 规范。

6.6 P2 多用户与 RBAC（OPT-P2-10 · v4）

权威文档：RBAC架构设计方案 v4（已交付）。

6.6.1 设计目标

目标说明
多用户单表 rbac_users（username + role）；复用 hash_password
RBAC三角色；@require_permission 替换 @login_required（仅装饰器，函数体不动）
可审计rbac_audit_logs 记 RBAC 事件；P1 operation_log 记业务变更，共用 Session user_id/role
分权始终启用三角色矩阵始终生效；登录须 rbac_users（空表种子 admin）；无旁路开关

6.6.2 数据模型

表要点

rolepermissions

/rbac/login → session[is_login, role, user_id, username]

6.6.6 迁移

  1. flask --app manage:app db migrate / db upgrade（Flask-Migrate；Tier 0 退役 Flask-Script，见 依赖升级 RFC）。
  2. 种子：空表时自动写入 admin（密码=login_pwd）。有用户后改密走「用户管理 → 编辑 → 新密码」；改 login_pwd 不再同步库内哈希。
  3. 重启进程使模板与鉴权变更生效。

6.6.7 验收标准

  • viewer 不可写任务；operator 不可下线/管用户/看 RBAC 审计。
  • admin 可管理 /rbac/users。
  • API access_token 未破坏。

8.1 两层互斥的设计 rationale

层级机制解决的问题
L1 进程间portalocker + scheduler.lock同机多 Gunicorn worker 重复 poll due jobs
L2 节点间Redis SET NX EX + @single_task多机同时执行同一 cron_do

局限：非强一致 Leader 选举；Redis 锁 TTL 120s 内进程崩溃可能导致短暂空窗或重复（取决于崩溃时机）。生产环境建议监控 Redis 与调度延迟。

15.8 与 operation_log 集成

15.9 依赖升级排期（与 RBAC）

RBAC 不依赖 Flask 2 / gevent 升级。权威路线：依赖升级 RFC — Tier 0 flask db → Tier 1 SA 1.4 渐进 → Tier 2 gevent → Tier 3/4 代际；RBAC 在 Tier 0 后可与 Tier 1 并行。

15.10 ADR-06（修订）

决策理由
应用内三角色 + 单表用户轻量、贴合 Flask 装饰器习惯、最小 diff
装饰器而非全局中间件与现有 @login_required 模式一致；可逐路由迁移
API token 与 Web RBAC 分离不破坏外部 access_token 集成

12. 架构决策记录（ADR）

ID决策理由代价
ADR-01选用 APScheduler 而非 Celery Beat轻量、内嵌 Flask、Crontab 语义直接多 worker 需自研锁
ADR-02HTTP GET 回调而非 Agent 拉取集成简单，防火墙友好无请求体、幂等需业务保证
