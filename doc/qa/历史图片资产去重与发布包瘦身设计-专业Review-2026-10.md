# 历史图片资产去重与发布包瘦身设计专业 Review

版本：v1.4 · 日期：2026-10-13 · 对象：[历史图片资产去重与发布包瘦身设计 v1.4](../design/历史图片资产去重与发布包瘦身设计-2026-10.html) · 结论：**修订后通过；方向合理，关键工程闭环已补齐，实施仍须按 H1–H5 验证**

## 1. 结论

按“历史图片保留在仓库，但不得进入 4.1.0 公开发布包”的用户目标全面复核后，原 v1.3 的方向正确，但存在四个会影响可实施性的缺口：没有现成发布构建器、入口文档可能断链、现有链接门禁不检查图片、缺少截图敏感信息审查。v1.4 已逐项补齐，因此方案层面可以确认。

v1.4 不额外发布历史证据包，仓库本身即是完整证据载体；公开安装包从最终 tag 以机器可读白名单构建。这一边界直接对齐“仓库完整、公开安装包轻量”的目标。

## 2. Review 发现与处置

1. **P1 · 发布构建不可复现：**仓库当前没有 Release asset 构建脚本或 workflow。v1.4 要求新增 manifest、构建器、独立校验器和 tag workflow，禁止正式版本使用手工 tar。
2. **P1 · 入口文档断链：**README、INSTALL、Release Notes 当前引用 41 个不同的仓库文档路径。v1.4 增加包内链接闭包门禁，未入包目标必须确定性改写为固定到 `v4.1.0` tag 的 URL。
3. **P1 · 图片门禁误用：**`check_doc_links.py` 不检查图片 `src`、Markdown 图片、哈希或解码。v1.4 明确新增专用结构化检查器，并保留浏览器代表性验证。
4. **P1 · 公开截图内容与来源：**图片继续保留在公开仓库时，必须检查凭据、个人信息、内部环境数据、元数据和公开使用依据。v1.4 将审查前置；发现敏感内容或来源不清时，字节保真和不重写历史的默认规则不能作为继续公开的理由。
5. **P2 · 19 张 QA 图旁路：**如决定提交，必须与引用文档同批纳入哈希资产库和安全审查，不允许继续放在未治理目录。
6. **P2 · 3.09 MiB 口径：**该值是当前基线的隔离模拟，不是最终 4.1.0 的硬承诺；最终报告必须解释核心代码增量，同时确保历史截图贡献为 0。

## 3. 合理性评估

| 决策 | 评价 | 专业依据 |
| --- | --- | --- |
| 按 SHA-256 去重 | 合理 | 只合并字节完全相同的图片，不使用感知哈希或相似度判定，不会误合并视觉相似但证据不同的截图。 |
| 使用完整 SHA-256 文件名 | 合理 | 命名规则确定，无前缀长度歧义；可直接验证文件名与内容是否一致。 |
| Base64 外置 | 合理且优先级高 | 减少 HTML/Markdown 重复编码，使 diff 可审查，并让图片可单独校验。 |
| 保持原始字节 | 合理且稳妥 | 不做 WebP/JPEG 转码，不改像素、颜色、压缩参数和截图内容，保留历史证据完整性。 |
| 不使用 Git LFS | 合理 | 当前图片规模不需要引入额外克隆、配额和发布归档复杂度。 |
| 不重写 Git 历史 | 合理 | 目标是缩小后续 HEAD/source archive，无需为回收旧 commit 空间承担历史改写风险。 |
| 仓库/公开发布包分层 | 合理且必要 | 去重后唯一历史截图仍占完整 source archive 约 83.5%；仓库保留证据而公开安装包排除截图，可同时保留审计性和正常发布体积。 |
| 发布文件白名单 | 合理且必要 | 从最终 tag/commit 明确选择运行文件与核心文档，比持续维护排除黑名单更不容易误带截图、未跟踪文件或本地数据。 |
| Python 确定性归档 | 合理 | 避免依赖 GNU/BSD tar 的参数差异；排序、时间戳、属主和权限归一化后，可用双构建同哈希证明可重现。 |
| 链接闭包与 tag 固定 URL | 必要 | 安装包不携带全部仓库文档时，必须保证入口文档仍可导航；固定 tag 避免链接随主分支漂移。 |
| 图片专项门禁 | 必要 | 通用文档链接检查不覆盖图片，必须验证引用存在、可解码、哈希一致、manifest 完整和发布包排除。 |
| 截图公开内容与来源审查 | 必要 | 仓库保留意味着截图仍公开可下载；体积优化不能替代凭据、个人信息、元数据和公开使用依据检查。 |

## 5. 历次版本已收敛的准确性细节

1. 原验收命令 `rg 'data:image' doc/` 会匹配说明文字，v1.1 已改为只检查 HTML `src` 和 Markdown 图片语法中的真实数据 URI。
2. 同名 HTML 与 Markdown 实际位于同一目录；v1.1 已将风险修正为“不同 HTML 目录到统一资产库的相对层级不同”。
3. 公开发布包必须同时排除历史截图和仅为它们服务的非核心文档，禁止只排除图片却留下断链文档。
4. 3.09 MiB 是当前基线模拟值，不应伪装成未来代码冻结后的绝对值；最终门禁是截图贡献为 0，并对获批核心代码造成的体积增量作可审计说明。

四项都属实施边界与验收口径修正，不是图片去重思路或数据基础的方向性问题。

## 6. 范围与专业性确认

- **本次实施 H1–H5：**安全清单、Base64 外置、严格去重、图片专项门禁、索引分层、可重现公开发布包。
- **不改业务代码：**不影响 UI、API、数据库、部署或运行时行为。
- **不改图片语义：**只有字节完全一致的副本才合并，不做相似图自动删除。
- **可回滚：**普通资产迁移与引用变更都可通过对应 commit 回退；若发现既有历史包含真实敏感信息，则转入安全处置，不受普通回滚结论约束。
- **可验证：**SHA-256、图片专项门禁、文档链接闭包、HTML→Markdown 同步、浏览器图片自然尺寸和解压安装测试构成完整验收链。

## 7. 最终专业意见

**合理性：高。准确性：高。复杂度：中。实施风险：中低。**

该方案符合历史证据资产的常规治理方式：公开内容先审、内容寻址、字节保真、引用收敛、可重现构建、仓库与发布产物职责分离。v1.4 在设计层面没有遗留阻断问题；但“通过”只表示可以进入实施，不表示构建器、图片门禁或 4.1.0 包已经完成。用户明确确认后方可实施 H1–H5。
