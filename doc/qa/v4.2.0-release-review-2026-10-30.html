2. 发现与优先级

F1 · P1 · SQLite 未将授权与用户三方比较保护到写入完成

定位：app/services/cron_edit_concurrency.py:148–156、app/rbac/services.py:994–1024。两个保存边界以 with_for_update() 保护 actor/target/关系，但 SQLite 不执行行级 FOR UPDATE。当前 Python 3.11 sqlite3 默认事务模式下，SQLAlchemy Session 已进入逻辑事务也不意味着 SELECT 已开始可保护后续写入的 SQLite 读写事务。

复现：在保存已读 actor 或 actor+target、尚未读完关系时，使用另一个独立 engine/connection 完成提交。第一例将任务编辑者从 Operator 改为 Viewer；第二例将用户管理者从 Admin 改为 Viewer；第三例将目标花名改为 concurrent-value。原请求随后继续执行真实保存边界。

task_revoke: independent_commit=true, outcome=updated, current_actor_role=viewer, stored_value=request-value
user_revoke: independent_commit=true, outcome=updated, current_actor_role=viewer, stored_value=request-value
user_conflict: independent_commit=true, outcome=updated, stored_value=request-value

第三例覆盖了另一连接已经提交的 concurrent-value，却没有返回 conflict。任务 edit_revision 只保护任务自身，无法发现 actor 行发生变化；用户编辑没有为读取的 target 字段提供 SQLite 等效原子比较条件。只要依赖的行未进入同一有效保护协议，增加一次普通重读也会留下新的竞态窗口。

影响：SQLite 部署中，已撤销权限的在途请求仍可能完成写入；用户资料同字段并发仍可能丢失更新。未证实 MySQL 同样存在本交错，不能据此否定 MySQL FOR UPDATE。三个场景均是在临时库独立连接上完成，不是仅修改同一 Session 对象的顺序测试。

建议：先设计并确认 SQLite 保存事务策略，使保护从读取当前授权/目标前开始，覆盖到业务和审计提交结束；或采用能原子约束所有相关授权/目标事实的条件写协议。评估 SQLite 写锁等待和错误分类，保留 no-op 零业务写语义。新增独立连接的授权撤销、同字段更新、目标停用与关系变更交错，并为原有 MySQL 锁回归保留验证。修复前不应宣称双后端编辑原子性完成。

4. 准确性、专业性与合理性评价

准确性：需修正双后端保障范围。无变更检测、范围外组保留、T0 连续、HMAC 保密基线、有效差异和结果未知分类均有对应实现；但“事务中读取+FOR UPDATE”不能在 SQLite 上替代真实原子保护。已有验收计数主要是不同批次的历史快照，Release 应汇总最终基线而非叠加计数。

专业性：基础良好，发布证据仍不充分。无新增运行时依赖；敏感 URL/body 不进入明文快照；审计 reader 使用整条结构白名单和转义；用户业务与审计同事务；MySQL 验收工具拒绝占用库且具备负向校准。这些选择克制且可维护。保存函数较长，后续可在场景不变量保护下提取纯比较策略，但不应为赶本版同时扩大结构重构。

合理性：分批路线合理。任务 edit_revision 区分墙钟与逻辑并发版本；三方比较允许无关字段合并；保留旧调用返回约定减少兼容风险。问题在后端事务实现覆盖与测试交错矩阵，不在选择版本列本身。无需因本次发现推翻整个设计，也不能只补 UI 提示规避数据边界问题。

文档可读性：历史评估已标注后续状态，双索引齐全；但设计中“当前没有版本字段/当前仅文档”的初稿语句与“已实现”页眉并存，建议将其标为实施前快照。内部设计标识应留在维护文档，最终 Release 以用户变化、升级、验证和剩余风险为主，避免复盘链接和历史数字喧宾夺主。
