任务中心「逾期未执行」提示设计

编号：OPT-P1-16 子项（Dashboard 逾期提示）
状态：已交付
创建：2026-08-26
涉及页面：app/templates/redesign/dashboard.html、app/main/views.py

1. 问题

用户在 Dashboard 上看到「持续异常: 4」但「今日失败: 3」（或更少），所有任务都配置了每小时执行，数据差异让用户困惑——以为是系统 bug。

实际原因：「持续异常」是累积健康状态（consecutive_failures ≥ 3），一旦标记会持续保持直到任务成功执行。某些任务虽然处于「持续异常」状态，但由于服务重启等原因今天还没有被调度执行，因此不会出现在「今日失败」中。

当前 Dashboard 没有任何视觉提示来区分：

  • 活跃异常：任务今天执行了但失败了（正在持续失败）
  • 逾期未执行：任务已经超过预期调度间隔未执行（可能是调度器问题、服务中断等）

2. 根因

Dashboard 的 Exception Panel 和健康度列只展示了 JobHealth.health_status（ok / failing）和 consecutive_failures 计数，缺少「上次执行时间 vs 调度间隔」的对比逻辑。

用户无法仅从界面判断一个「持续异常」的任务是「一直在跑但一直失败」还是「很久没跑了」，两者的排障优先级和处理方式完全不同：

状态含义处理方式
持续异常 + 活跃失败任务在执行但回调目标有问题检查目标服务 / URL 配置
持续异常 + 逾期未执行任务没有被调度器触发检查服务是否运行 / 调度是否正确

3. 方案对比分析

「逾期」和「持续异常」是两个正交维度。一个任务可以处于以下四种状态之一：

未逾期（在调度间隔内执行过）已逾期（超过调度间隔未执行）
健康正常 — 无需关注⚠ 调度器可能异常
持续异常🔴 正在失败 — 检查目标服务🟠 已停跑 — 先恢复调度

  1. 独立筛选按钮可直接过滤出全部逾期任务，适合任务量增长后的管理需求

4. 实现方案详细设计（方案 A — 独立维度）

4.1 逾期判定逻辑

逾期 = (当前时间 - 上次执行时间) > max(调度间隔 × 2, 10min)

调度间隔 = 由 croniter 从 cron 表达式计算相邻两次执行的时间差
上次执行时间 = 最近一条 JobLog.create_time（不限 status）
最小阈值 = 10 分钟（避免高频任务频繁闪烁）

排除条件：一次性任务（run_date 非空）、已暂停（status=0）、已下线（status=-1）不参与逾期判定。

7. 性能分析

7.1 架构决策：实时计算 vs 持久化

方式优势劣势适用规模
实时计算（当前方案） 零维护成本，数据始终准确，无需迁移脚本和后台任务 每次页面加载都需计算，CPU 和 SQL 开销随任务数线性增长 < 500 个活跃任务
持久化到 JobHealth 页面加载时直接读取，无 croniter 开销 需后台定时更新、数据可能滞后、增加模型迁移和运维复杂度 > 500 个活跃任务

选择理由：CronPilot 典型部署规模 10-200 个任务，实时计算在此范围内性能充裕（见下方基准测试）。持久化方案的运维复杂度（后台 worker + 状态同步 + 数据库迁移）远超收益。当任务数超过 500 时，可考虑升级为持久化方案。

7.2 新增查询分析

逾期功能在每次 Dashboard 加载时新增以下 SQL 查询和计算步骤：

#操作SQL 语句索引利用时间复杂度
Q1 当前页面任务的最近执行时间 SELECT cron_info_id, MAX(create_time) FROM job_log WHERE cron_info_id IN (:page_ids) GROUP BY cron_info_id ✅ ix_job_log_cron_info_id O(page_size × log_depth)
Q2 全量活跃任务查询（Stats 卡片 + 筛选时） SELECT * FROM cron_infos WHERE status = 1 全表扫描（cron_infos 表小） O(N_active)
Q3 全量活跃任务的最近执行时间 同 Q1，IN 参数为全部活跃 ID ✅ ix_job_log_cron_info_id O(N_active × log_depth)
C1 croniter 调度间隔计算 纯 Python 计算（无 SQL） — O(N_active)

其中 Q1 仅在 v2 渲染分支执行（当前页面）；Q2+Q3+C1 在需要 overdue_count（Stats 卡片）或 health=overdue（筛选过滤）时执行。

7.4 开销分解与规模化预估

逾期功能的开销由两个独立瓶颈组成，各有独立的优化路径：

瓶颈本质增长方式优化手段
SQL: MAX(create_time) GROUP BY 数据库 I/O 与 job_log 总行数和每任务日志深度相关 复合索引 (cron_info_id, create_time)
CPU: croniter 调度间隔计算 纯 CPU 计算 与活跃任务数严格线性（~0.21 ms/任务） 结果缓存（30-60s TTL）

7.4.1 SQL 开销：单列索引 vs 复合索引

MAX(create_time) GROUP BY cron_info_id 在两种索引策略下的 MySQL InnoDB 行为完全不同：

单列索引 ix_job_log_cron_info_id（当前）复合索引 (cron_info_id, create_time)
查询计划 Index Scan → 按 cron_info_id 分组后，逐行回表读取 create_time 做 MAX 聚合 Loose Index Scan（Skip Scan） → 直接跳到每组 B+ 树最后一个叶子节点，取 MAX 值，无需回表
I/O 模式 每行一次随机 I/O（聚簇索引 → 数据页），总 I/O = Σ(每任务日志行数) 每组一次 B+ 树 seek（顺序 I/O），总 I/O = 任务数
EXPLAIN Extra Using where; Using index Using index for group-by (loose index scan) — 覆盖索引扫描

7.6 MySQL 场景深度分析

CronPilot 支持 SQLite（开发/小规模）和 MySQL（生产推荐）两种后端。以下分析 MySQL 场景下逾期功能的性能特征。

7.6.1 索引利用差异

查询SQLiteMySQL (InnoDB)优化建议
MAX(create_time) WHERE cron_info_id IN (...) GROUP BY cron_info_id SEARCH USING INDEX ix_job_log_cron_info_id — 索引扫描 + 逐行回表取 create_time 同左 — 单列索引命中后仍需回表读取 create_time 列 如任务 > 200：添加复合索引 (cron_info_id, create_time) 使查询变为覆盖索引扫描（Index-Only Scan），避免回表
LIKE 'YYYY-MM-DD%'（已有的今日失败/成功率查询） 前缀匹配可用索引 VARCHAR LIKE 前缀可用 ix_job_log_create_time；但因 create_time 为 VARCHAR(25) 而非 DATETIME，无法利用 MySQL 的范围分区和原生日期函数加速 长期：将 create_time 改为 DATETIME 类型可获得更好的范围查询性能（需要数据迁移）

关键发现：逾期功能的 MAX(create_time) GROUP BY 查询缺少 (cron_info_id, create_time) 复合索引。当前单列索引 ix_job_log_cron_info_id 需要逐行回表取 create_time 做 MAX 聚合。在 MySQL 中每次回表是一次随机 I/O（B+ 树叶子节点 → 聚簇索引），当单任务日志量大（如每小时 1 条 × 365 天 = 8760 行/任务）时，回表成本显著。

7.6.2 MySQL 性能预估

场景活跃任务job_log 行数单列索引 SQL复合索引 SQL推荐

中型 100 ~1M ~15-110 ms ~2 ms 添加复合索引

单列索引范围取决于日志深度：下限为 100 条/任务（新部署），上限为 1000 条/任务（运行 42 天的每小时任务）。复合索引利用 Loose Index Scan（MySQL 优化器直接跳到每组 B+ 树最后一个叶子节点取 MAX），性能与日志深度无关，仅与任务数线性增长。

7.6.3 复合索引优化方案

-- 当任务数 > 200 且 job_log > 1M 行时推荐添加
CREATE INDEX ix_job_log_cron_id_create_time ON job_log (cron_info_id, create_time);

-- MySQL EXPLAIN 预期：
-- type: range
-- key: ix_job_log_cron_id_create_time
-- Extra: Using index (覆盖索引，无需回表)

影响评估：

  • 写性能：每条 job_log INSERT 多维护一个 B+ 树索引，约增加 5-10% 写入延迟
  • 存储：每行额外 ~40 字节索引条目（cron_info_id INT + create_time VARCHAR(25)），100 万行 ≈ 40MB
  • 读性能：MAX(create_time) GROUP BY cron_info_id 从回表扫描变为覆盖索引扫描，预期提速 5-10x
  • 附带收益：已有的 last_run_details_by_ids()、today_fail 等查询也可受益

# config.py — 生产 MySQL 连接池建议
SQLALCHEMY_ENGINE_OPTIONS = {
    'pool_recycle': 3000,
    'pool_size': 10,       # 默认 5，Dashboard 高并发时可能不足
    'max_overflow': 20,    # 默认 10，允许突发连接
    'pool_timeout': 30,    # 默认 30s，超时即抛异常
    'pool_pre_ping': True, # 每次从池中取连接前先 ping，避免 MySQL 8h 超时断开
}

7.7.4 已有 Dashboard SQL 瓶颈对比

逾期功能的性能影响需要放在 Dashboard 已有查询负担的上下文中理解：

查询类别查询数耗时（6 任务 / 17K 日志）瓶颈分析
已有: 今日统计（metrics.today_fail + success_rate） 3 条 42.8 ms（占 SQL 总耗时 88%） 每条都 JOIN + LIKE 全天日志扫描；create_time 为 VARCHAR 无法利用 DATE 范围

结论：Dashboard 性能的真正瓶颈是已有的「今日统计」查询（3 条占 88% SQL 时间），逾期功能新增开销仅占 3.5%。如需优化 Dashboard 整体性能，优先级应为：① 将 create_time 改为 DATETIME 并使用范围查询；② 添加 (cron_info_id, create_time) 复合索引；③ 页面级结果缓存 30-60 秒。

7.8 create_time 字段类型对性能的影响

job_log.create_time 当前为 VARCHAR(25)（格式 'YYYY-MM-DD HH:MM:SS'），而非 DATETIME。这对逾期功能和已有查询都有影响：

影响VARCHAR(25)（当前）DATETIME（理想）
范围查询 LIKE 'YYYY-MM-DD%' — 字符串前缀匹配，无法利用 MySQL 分区 BETWEEN '2026-08-26' AND '2026-08-27' — 原生范围扫描，可利用日期分区
MAX() 聚合 字典序比较（YYYY-MM-DD 格式恰好等价时间序），功能正确 原生时间比较，无需字符串解析，更高效
Python 解析 需要 datetime.strptime() 解析字符串（_compute_overdue_map 第 194 行） SQLAlchemy 自动转为 datetime 对象，无需手动解析
存储空间 25 字节/行 8 字节/行（节省 68%）
索引效率 B+ 树按字节序排列，25 字节 key 8 字节 key，索引更紧凑，缓存命中率更高

注意：create_time VARCHAR → DATETIME 迁移是一个独立优化项（影响全站 job_log 相关查询），不在本功能范围内。但本功能的 Python 解析逻辑（strptime）已兼容两种类型（第 193-196 行的 isinstance 检查）。

8. 风险

风险评估缓解
croniter 计算间隔可能对复杂 cron 表达式不准 低 — 项目中绝大多数是简单的 */N * * * * 表达式 取相邻两次执行的间隔，覆盖单元测试中的常见表达式
新增 SQL 查询影响页面加载性能 低 — 实测新增 1.68 ms（占 Dashboard 总耗时 0.8%），索引命中 GROUP BY cron_info_id 单次批量查询 + 索引 ix_job_log_cron_info_id
croniter 计算 CPU 开销随任务数线性增长 低（<200 任务）/ 中（200-500 任务） 实测 500 任务 ~120 ms；超 200 任务可加缓存层或后台预计算
全量活跃任务查询（overdue_count）在大数据量下偏慢 低 — cron_infos 表通常 < 500 行 status = 1 过滤后行数很少；未来可缓存 30-60 秒
2 倍间隔阈值过于敏感或过于迟钝 中 — 每分钟执行的任务 2 分钟就报逾期，每天执行的任务 2 天才报 使用 max(interval × 2, 10min) 作为最小阈值，避免高频任务频繁闪烁
health=overdue 筛选时需预计算全量 低 — 仅在用户点击筛选按钮时触发 预计算结果复用于分页和计数；非筛选路径不执行全量计算
